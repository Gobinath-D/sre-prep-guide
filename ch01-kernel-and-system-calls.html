The kernel, user space & system calls

Every command you run, every packet nginx sends, every file a pod writes — all of it eventually asks one program for permission: the kernel. Understand this one boundary and half of Linux stops being mysterious.

Start: Beginner→→→End: Staff-level ~35 min read · Linux lab (Docker)

By the end of this chapter you can

  • Explain user space vs kernel space to a colleague without hand-waving.
  • Describe exactly what happens when a program calls read() — trap, mode switch, and return.
  • Use strace to see the system calls a process makes, and read the output.
  • Diagnose the classic "100% CPU but the app looks idle" incident, and "too many open files".
  • Say why a container shares the host kernel — the fact that makes containers cheap and also leaky.

Why this exists · the problemThe problem the kernel solves

Picture a single machine. One CPU, some RAM, a disk, a network card. Now you want to run twenty programs on it at once — a web server, a database, your shell, a log shipper, whatever. Three problems show up immediately.

First, they'd fight over the hardware. If two programs both wrote to the disk whenever they liked, they'd scribble over each other's data. Second, they'd fight over memory — one program could read another's passwords straight out of RAM, or crash the machine by grabbing all of it. Third, nothing would be fair: a busy program could hog the CPU forever and starve everything else.

Somebody has to sit in the middle and referee. That referee is the kernel. It's the core of the operating system — a program that boots first, never exits, and owns the hardware. Every other program has to go through it to touch anything real: the disk, the network, memory, the clock, another process. The kernel hands out slices of the CPU, keeps each program's memory walled off from the others, and decides who gets to do what.

Key point

The kernel isn't a background service you can restart. It is the operating system's core. Your programs are guests; the kernel is the one holding the keys to the hardware. Nothing reaches the disk, the network, or another process without asking it.

Mental model · analogyThe mental model: a secured office building

Here's the picture I want you to carry for the rest of the book.

Real-world analogy

Think of the machine as an office building. The valuables — the wiring, the safe, the mail room, the phone lines — are the hardware. They live in a locked back room that only the facilities team can enter. That team is the kernel.

You and every other program are tenants in the front offices. You can't walk into the back room and grab the phone lines yourself. When you need something — "send this letter," "open that filing cabinet," "what time is it?" — you fill in a request form and slide it through a service window. The facilities team checks that you're allowed, does the privileged thing on your behalf, and slides the result back.

That service window is the system call. Passing a form through it means going through a security checkpoint, which takes a moment — so you don't want to queue at the window a million times a second if you can avoid it. And for a few read-only questions like "what time is it?", there's a notice board on the wall you can just glance at without queuing at all. (That notice board is real; it's called the vDSO, and we'll get to it.)

Every term in that analogy maps onto something concrete:

ArchitectureUser space and kernel space

The CPU itself enforces this split. Modern CPUs run code at different privilege levels, called rings. Linux uses two of them:

  • Ring 3 — user mode. Where your programs run. Code here cannot touch hardware directly, cannot read arbitrary physical memory, and cannot execute privileged CPU instructions. If it tries, the CPU faults and the kernel kills it (that's a segfault).
  • Ring 0 — kernel mode. Where the kernel runs. Full access to everything.

Alongside privilege, each process gets its own virtual address space — its own private map of memory. When your program looks at address 0x400000, that's not really byte 4-million of the RAM chip; the kernel and the CPU's memory-management unit translate it to some physical page, and your neighbour's 0x400000 maps somewhere completely different. That's why one crashing program doesn't take down the others, and why it can't read their memory. We go deep on this in Chapter 3.

Why an SRE cares

This split is exactly why a container "shares the host kernel." A container is a normal user-space process; there's no second kernel inside it. That's why containers start in milliseconds and weigh almost nothing — but also why a kernel bug or a too-generous capability in one container can affect the whole host. A VM, by contrast, ships its own kernel. Hold that thought for Chapter 21; it's the single most important difference between a container and a VM.

Internal workingWhat a system call actually does

"Go through the service window" is the analogy. Here's the machinery underneath, step by step, for a call like read(fd, buf, 4096):

  1. Your program calls a libc function. You wrote read(...) in C (or Python's f.read(), which calls it eventually). libc puts the syscall number for read into a specific CPU register and the arguments into others.
  2. It executes a special instruction. On x86-64 that's syscall. This isn't a normal jump — it's a deliberate trap that flips the CPU from ring 3 into ring 0 and jumps to a fixed entry point the kernel registered at boot.
  3. The CPU switches mode. This is the checkpoint. The CPU saves your program's state, switches to the kernel's stack, and now runs with full privilege. This switch has a real cost — hundreds of nanoseconds — because the CPU has to change protection state and often flush some caches.
  4. The kernel looks up the call. It uses the syscall number as an index into the system-call table and jumps to the handler — here, sys_read.
  5. The kernel does the privileged work — and checks you're allowed. It validates the file descriptor, copies data from the page cache or asks the disk driver, and copies the bytes into your buffer. If you're waiting on a slow disk or an empty socket, the kernel puts your process to sleep and runs someone else in the meantime.
  6. It returns. The kernel puts a return value in a register (bytes read, or a negative error), switches the CPU back to ring 3, and restores your program. libc turns a negative return into -1 plus errno.

So a system call is a controlled, one-way door: the only way into the kernel is through an entry point the kernel itself chose. Your program never runs kernel code of its choosing. That's the whole security model in one sentence.

The cost, and the vDSO

Because every syscall pays for a mode switch, doing millions of them adds up. The kernel optimises the most common read-only calls — like "what time is it?" (clock_gettime) — by mapping a small read-only page into every process called the vDSO. For those calls, your program reads the answer straight from memory with no trap at all. That's the notice board from the analogy. It's why gettimeofday is basically free while read is not.

Think first: a program wants to read a file. Can it talk to the disk itself?

No. Reading a disk means driving hardware, which only ring-0 code may do. The program calls read(), which traps into the kernel; the kernel's filesystem and block layers fetch the data (often from the page cache in RAM, sometimes from the physical disk) and copy it into the program's buffer. The program only ever sees the bytes handed back, never the disk.

This is also why you can't "speed up" disk reads from user space alone — the ceiling is set by how the kernel and hardware move the data. Keep this in mind for the page-cache chapter.

ComponentsThe pieces involved

Four actors show up in every syscall story, and you'll name them constantly on the job:

  • The kernel subsystems. The scheduler (who gets the CPU), the memory manager (virtual-to-physical mapping, the page cache), the VFS and filesystems (files and inodes), and the network stack and device drivers. Each syscall lands in one of these.
  • libc. Almost nobody writes raw syscall instructions. You call C library functions and libc does the register-loading and trapping for you. On most Linux distros that's glibc; Alpine images use musl, which behaves differently in a few places (DNS resolution, most famously — a real source of "works on Ubuntu, breaks on Alpine" bugs you'll meet in Chapter 15).
  • The syscall itself — identified by a stable number. read is 0 on x86-64, write is 1, and so on. These numbers are a permanent contract, which is why old binaries keep working on new kernels.
  • /proc. The kernel exposes each process's state as files under /proc/<pid>/. It's not a real disk directory — it's a live window into kernel data structures. You'll live in here when troubleshooting.

Data flowFollowing one real program

Enough theory. Let's watch a trivial program and see every door it opens. When you run cat /etc/hostname, the kernel does a lot on your behalf: it loads the program, opens the file, reads it, writes to your terminal, and exits. Each of those is a syscall, and we can see them all. That's the next section — the lab.

Hands-onLabs — build, understand, break, troubleshoot

These labs need a Linux environment. You're on a Mac, so the cleanest option is a throwaway Linux container — which also ties straight into the Docker chapters. Everything below runs inside it. Start the container once:

bash
# A disposable Ubuntu box. --cap-add SYS_PTRACE lets strace attach.
docker run --rm -it --cap-add=SYS_PTRACE ubuntu:24.04 bash

# Inside the container, install the tools we'll use:
apt-get update && apt-get install -y strace procps lsof
Lab 1Build — see a program's system callsBuild

Run the simplest useful program under strace, which prints every syscall a process makes.

bash
echo "hello-sre" > /tmp/host
strace -f cat /tmp/host

You'll see dozens of lines. Ignore the startup noise for now (that's the kernel loading libc). Look for the heart of it near the end:

Output (trimmed)openat(AT_FDCWD, "/tmp/host", O_RDONLY) = 3 read(3, "hello-sre\n", 131072) = 10 write(1, "hello-sre\n", 10) = 10 read(3, "", 131072) = 0 close(3) = 0

Read it like a sentence. openat asks the kernel to open the file and hands back file descriptor 3 — a small integer that means "this open file" for the rest of the program. read(3, …) pulls 10 bytes into a buffer and returns the count. write(1, …) sends those bytes to descriptor 1, which is standard output — your terminal. The second read returns 0: end of file. Then close(3). That's the entire job of cat, laid bare.

Descriptors 0, 1, 2 are always standard input, output, and error. Descriptor 3 is the first one this program opened. We'll use file descriptors constantly — they're the subject of Chapter 4.

Lab 2Understand — count and time the callsUnderstand

strace -c doesn't print every call — it counts them and times them. This one flag is the difference between guessing and knowing where a process spends its kernel time.

bash
strace -c cat /tmp/host
Output% time seconds usecs/call calls errors syscall ------ ----------- ----------- --------- --------- ---------------- 24.1 0.000112 9 12 mmap 15.6 0.000072 9 8 openat … 0.0 0.000000 0 1 read 0.0 0.000000 0 1 write

Now peek at the live view of a running process. Open a second shell into the container (docker exec -it <id> bash) and watch a sleeping process do nothing:

bash
sleep 300 &
strace -p $!
Outputstrace: Process 141 attached clock_nanosleep(CLOCK_REALTIME, 0, {tv_sec=300, …

It's parked in a single syscall, clock_nanosleep, waiting. The process is not "using" the CPU — the kernel put it to sleep and will wake it in 300 seconds. This is the difference between a process that's blocked and one that's burning CPU, and telling them apart is a core troubleshooting skill.

Think first: you attach strace to a stuck production process and it just sits in read(7, …) forever. Is it crashed?

No — it's blocked, waiting for data that isn't coming. A crashed process is gone; this one is alive and parked in a syscall. read(7, …) means it's waiting on file descriptor 7. Your next move is to find out what fd 7 is: ls -l /proc/<pid>/fd/7. If it's a socket to a database that's not answering, you've just found your incident — the app is waiting on a dependency, not broken itself. That single reframe ("blocked, not dead") saves hours.

Lab 3Break — watch a syscall failBreak

Failures are just syscalls returning errors. Force one and read it:

bash
strace -f cat /tmp/does-not-exist
Output (trimmed)openat(AT_FDCWD, "/tmp/does-not-exist", O_RDONLY) = -1 ENOENT (No such file or directory)

The kernel returned -1 and set errno to ENOENT. That error name is worth memorising — you'll see ENOENT (missing file), EACCES (permission denied), ECONNREFUSED (nothing listening on that port), and EMFILE (too many open files) for the rest of your career. Now a permission failure:

bash
touch /tmp/secret && chmod 000 /tmp/secret
strace -f cat /tmp/secret 2>&1 | grep secret
Outputopenat(AT_FDCWD, "/tmp/secret", O_RDONLY) = -1 EACCES (Permission denied)

When an app logs a vague "could not read config," this is how you find the truth: strace shows you the exact path it tried and the exact reason the kernel said no.

Lab 4Troubleshoot — the "busy but idle" processTroubleshoot

Here's a small program that pins a CPU by asking the kernel the time in a tight loop — a stand-in for a real app with a bad polling loop. Run it and investigate as if you didn't write it.

bash
# A process that burns CPU entirely inside a syscall loop:
bash -c 'while true; do date >/dev/null; done' &
PID=$!
top -b -n1 -p $PID | tail -2

You'll see it near 100% CPU. The question a senior SRE asks first: is that CPU being spent in my code (user) or in the kernel (system)? Check, then confirm with strace:

bash
cat /proc/$PID/status | grep -i state
strace -c -p $PID   # let it run a few seconds, then Ctrl-C
Output% time seconds usecs/call calls errors syscall ------ ----------- ----------- --------- --------- ---------------- 38.0 0.451 2 210443 clock_gettime / openat / execve …

Hundreds of thousands of calls in seconds. The process isn't computing anything — it's hammering the syscall boundary. In the real world this is a library polling a clock, a health check with no sleep, or a retry loop with no backoff. The fix is never "add CPU"; it's "stop making so many syscalls." Kill it with kill $PID.

Lab 5Production challenge — "too many open files"Senior challenge

Every open file, socket, and pipe is a file descriptor, and the kernel caps how many each process may hold. Hit the cap and openat starts returning EMFILE — which surfaces as your service refusing new connections while looking otherwise healthy. Reproduce it:

bash
ulimit -n 20            # set a tiny FD limit for this shell
python3 -c 'f=[open("/etc/hostname") for _ in range(50)]'
OutputOSError: [Errno 24] Too many open files: '/etc/hostname'

Errno 24 is EMFILE. Now the senior question: given a running service throwing this, how would you confirm the cause and find the leak, without restarting it? Think it through before opening the answer.

Reveal an approach

Count what the process currently holds and compare to its limit:

bash
ls /proc/<pid>/fd | wc -l          # how many FDs open right now
cat /proc/<pid>/limits | grep 'open files'   # the ceiling
ls -l /proc/<pid>/fd | awk '{print $NF}' | sort | uniq -c | sort -rn | head

The last command groups the descriptors by what they point to. If you see thousands of sockets to the same host, that's a connection leak — the app opens connections and never closes them. The real fix is in the app (close what you open, or use a pool); raising ulimit only delays the next outage. You'll meet this exact shape again as database connection exhaustion in Chapter 86.

Failure & troubleshootingHow this shows up in real incidents

You now have the four highest-value patterns. Here they are as an SRE would file them mentally:

Incident pattern · high system CPU

Symptom: a host or pod is at 100% CPU but the app seems to be doing little useful work. First cut: split user vs system CPU (top shows %us vs %sy). High %sy means time spent in the kernel — a syscall storm. Confirm: strace -c -p <pid> for a few seconds and look for one syscall with a huge count. Cause is usually: a poll loop with no backoff, excessive logging (every log line is a write), or a library checking the clock or a lock too often.

Incident pattern · the hung service

Symptom: requests time out; the process is up but unresponsive. First cut: strace -p <pid>. If it sits in one read/futex/connect, it's blocked, not crashed. Confirm what it waits on: ls -l /proc/<pid>/fd/<n>. Cause is usually: a downstream dependency (DB, cache, another service) that stopped answering — so fix the dependency, not this process.

Incident pattern · "operation not permitted" in a container

Symptom: code that works on a VM fails inside a container with EPERM on a syscall that should be allowed. Cause is usually: the container's seccomp profile blocks that syscall. seccomp is a kernel feature that filters which syscalls a process may make — the security payoff of the shared-kernel model. You'll configure it in Chapter 27. The tell is that the failing syscall is something unusual (clone3, mount, a keyring call), and it's EPERM, not ENOENT or EACCES.

Production · security · performanceWhat matters in production

Security. The syscall boundary is the main security boundary on a Linux host. Three kernel features tighten it, and you'll see all three in the container and Kubernetes chapters: capabilities break root's power into fine-grained pieces (so a process can bind a low port without full root), seccomp filters which syscalls are even allowed, and namespaces change what a syscall can see (a different set of processes, network interfaces, mounts). Containers are built entirely out of these.

Performance. Because each syscall costs a mode switch, high-throughput systems try to make fewer, bigger calls. That's the reasoning behind buffered I/O (write 64 KB at once, not a byte at a time), behind epoll (watch thousands of sockets with one call instead of one call per socket), and behind newer interfaces like io_uring that batch I/O submissions to cut trap overhead. You don't need to implement these, but when someone says "we reduced syscalls per request," this is what they mean and why it helped.

Common mistakes engineers make before they understand this layer: blaming "slow disk" when the process is actually blocked on a network socket; adding CPU to a syscall-storm problem; raising ulimit to paper over an FD leak; and assuming a container is as isolated as a VM. Each of those is a wrong turn this chapter should now stop you from taking.

System-design connectionWhere this reaches into architecture

This looks like low-level trivia, but it sets ceilings you design around. The cost of syscalls and context switches is why a single machine can only accept so many connections per second, which is why you put a load balancer in front and scale horizontally (Chapter 94). It's why event-driven servers like nginx and Envoy handle far more connections than thread-per-request designs — they spend fewer syscalls per connection. And "the app is blocked on a dependency, not broken" is the seed of timeouts, circuit breakers, and bulkheads in Chapter 88: in a distributed system, most of your processes are usually asleep in a syscall, waiting on someone else.

InterviewInterview questions & answers

Open each one only after you've answered it in your head.

30-secWhat's the difference between user space and kernel space?

Kernel space is privileged code that owns the hardware and runs in CPU ring 0; user space is where normal programs run, in ring 3, with no direct hardware access. A user program reaches hardware only by making a system call, which traps into the kernel, has it do the privileged work, and returns the result. The split is what keeps processes isolated and the machine stable.

2-minWalk me through what happens when a program calls read().

The program calls libc's read, which loads the syscall number and arguments into registers and executes the syscall instruction. That traps the CPU from ring 3 to ring 0 — a mode switch — and jumps to the kernel's entry point. The kernel indexes the syscall table to sys_read, validates the file descriptor and the buffer, and fetches the data — from the page cache if it's warm, otherwise by asking the block or network layer, during which it may put the process to sleep and schedule another. When the data's ready it copies it into the program's buffer, puts the byte count (or a negative errno) in a register, switches back to ring 3, and resumes the program. libc turns a negative return into -1 and sets errno. The key ideas I'd stress: the boundary is a controlled trap, the mode switch has a cost, and a blocking call means the kernel parks the process rather than spinning.

DeepWhy is a mode switch expensive, and how does the vDSO help?

A mode switch changes CPU protection state, swaps to a kernel stack, and can disturb caches and pipelines, so it costs on the order of hundreds of nanoseconds even when the call does almost nothing. For calls made constantly and needing no privileged action — reading the clock, the PID — the kernel maps a read-only page, the vDSO, into every process's address space, so those calls read the answer directly in user mode with no trap. It matters because latency-sensitive code that timestamps every request would otherwise pay a syscall on every timestamp; the vDSO removes that. It's also a good segue into why we batch I/O and use epoll/io_uring: all of it is about paying the boundary cost fewer times.

ScenarioA service is pinned at 100% CPU but throughput is low. How do you investigate?

First I split the CPU: top to see user versus system time. High system time points at the kernel, so I'd run strace -c -p <pid> for a few seconds and look for a single syscall with an enormous count — that's a syscall storm, usually a poll loop without backoff or excessive logging. High user time instead points at the code itself, and I'd reach for a CPU profiler or perf top to find the hot function. Either way I'm separating "spending time in my code" from "spending time crossing into the kernel" before I touch anything, and I'd never respond by just adding CPU until I know which it is.

Follow-upHow does all this relate to containers?

A container is just a user-space process sharing the host's single kernel — there's no kernel inside it. That's why containers are cheap and start instantly, and why the same syscall reasoning applies unchanged inside a pod. It's also why container security lives at this boundary: capabilities limit privileged operations, seccomp filters which syscalls are allowed, and namespaces change what those syscalls can see. A VM differs precisely here — it runs its own kernel, so the isolation is stronger and the overhead higher. If someone gets EPERM on a normal syscall inside a container, my first guess is a seccomp profile.

RetainQuick revision

The kernel owns the hardware and referees every program. Programs run unprivileged in user space (ring 3) and reach hardware only through system calls, which trap into kernel space (ring 0), have the kernel do the privileged work, and return a value or an error. The mode switch costs real time, so fewer, larger syscalls beat many tiny ones. strace shows you the calls; strace -c counts them; /proc/<pid>/ is your window into a live process. Blocked is not the same as crashed. And a container is a user-space process on a shared kernel — cheap, fast, and only as isolated as capabilities, seccomp, and namespaces make it.

The 10 things to remember

  1. The kernel is the OS core: it owns the hardware and never exits. Programs are guests.
  2. User space (ring 3) is unprivileged; kernel space (ring 0) has full access. The CPU enforces the split.
  3. A system call is the only door from user space into the kernel — a deliberate trap to a fixed entry point.
  4. Every syscall pays a mode-switch cost, so batching I/O and using epoll/io_uring reduce that cost.
  5. The vDSO lets a few read-only calls (like the clock) skip the trap entirely.
  6. File descriptors (0/1/2 = stdin/stdout/stderr) are how programs refer to open files and sockets.
  7. strace shows syscalls; strace -c counts and times them; both are first-reach tools.
  8. High %sy CPU = kernel time = likely a syscall storm; high %us = your code.
  9. A process sitting in a syscall is blocked (waiting), not crashed — find what it waits on via /proc/<pid>/fd.
  10. A container shares the host kernel; its isolation is capabilities + seccomp + namespaces, not a second kernel.
