Memory: virtual memory, page cache, swap & OOM

Every process thinks it has the machine's whole memory to itself, laid out in a neat private map that starts at zero. It's a lie the kernel maintains with hardware help — and understanding the lie is the difference between "the box is out of RAM" (usually wrong) and knowing exactly which pod the OOM killer is about to shoot.

Why this exists · the problemThe problem: many programs, one pool of RAM

Give programs direct access to physical RAM and everything falls apart. Two programs both want the address at byte zero, so they collide. A program compiled to load at a fixed address can't run if that region is already taken. A process could read its neighbour's memory — passwords, keys, anything — by just reading the right physical address. And you could never run a program that needs more memory than is free right now, even if most of what's allocated is never actually touched.

Linux fixes all of this with one idea: no process ever sees physical memory. Each gets its own virtual address space — a private map that always starts at zero and looks contiguous and enormous, regardless of what's physically there. When a program reads address 0x400000, the CPU and kernel translate that, on the fly, to wherever the real bytes live: some physical page, or a spot in the page cache, or out on swap, or nowhere yet at all. Your neighbour's 0x400000 translates somewhere completely different.

That translation buys three things at once. Isolation: you can't name, let alone touch, another process's memory. Flexibility: the kernel can move physical pages around, share them, or write them to disk without the program noticing. And overcommit: the kernel can promise more memory than exists, because most of what programs ask for, they never touch — until they do, which is where the OOM killer comes in.

Key point

Memory is handed out lazily. malloc(1 GB) almost always succeeds instantly and costs nothing — it just reserves address space. Real physical RAM is only committed when your program writes to a page and triggers a fault. This is why a process can show a 10 GB virtual size (VSZ) while using 200 MB of real RAM (RSS), and why "out of memory" happens on a write, not on the allocation.

Mental model · analogyThe mental model: an apartment building with a translation desk

Hold this picture for the rest of the chapter.

Real-world analogy

Think of physical RAM as an apartment building with a fixed number of units — that's finite and real. Each tenant (process) is handed their own private floor plan that always numbers rooms from 1 upward. Every tenant's "room 1" is a different actual apartment; they never learn the real unit numbers. When a tenant wants to enter "their" room 5, they ask the translation desk in the lobby, which looks up the real unit and lets them in. That desk is the MMU, and the clerk keeps a sticky note of the last few lookups so repeat visits are instant — that note is the TLB.

Near the entrance is a lending shelf holding copies of documents tenants recently pulled from the deep archive in the basement (the disk). Read a document once and its copy stays on the shelf, so the next read is instant. That shelf is the page cache, and it grows to fill whatever space is spare — which is exactly what it should do. When a real apartment is needed and none is free, management first clears space off the lending shelf (those are just copies; toss them).

If that's not enough, management moves a tenant's belongings to a storage annex across town — the apartment is freed, but reaching those belongings is slow. That's swap. And when the building is genuinely, hopelessly full and a new tenant must be housed, the manager evicts whoever has the worst eviction score — the tenant using the most space and least protected. That manager is the OOM killer, and the score is oom_score.

ArchitectureVirtual to physical, and where pages live

The address space is divided into fixed-size pages — 4 KiB each on x86-64. Physical RAM is divided into equal-size frames. The kernel keeps, per process, a page table: a lookup from virtual page to physical frame (or to "on swap," or to "not present"). The MMU does this lookup in hardware on every memory access, caching recent results in the TLB so it doesn't have to walk the multi-level table each time.

Not every page is the same kind. Anonymous pages are your heap and stack — they have no file behind them, so if the kernel needs to reclaim them it must write them to swap first. File-backed pages are memory that mirrors a file on disk (program code, memory-mapped files, and the page cache); a clean file page can be dropped instantly and re-read later, while a dirty one (modified, not yet saved) must be written back first.

This is where the memory numbers people misread come from. VSZ (virtual size) is the whole left column — every mapping, backed or not. RSS (resident set size) is only the pages actually in physical RAM right now — and it counts shared pages (like libc) in full for every process that maps them, so summing everyone's RSS overcounts real usage. Shared is the portion backed by pages other processes also map. When you need the honest per-process number, look at PSS (proportional set size), which splits shared pages by how many share them.

Why an SRE cares

Almost every memory incident is a misread of these numbers. A dashboard shows "95% memory used" and someone panics — but most of that is page cache, which the kernel gives back the instant anything needs it. The real question is always MemAvailable (how much you can use without swapping) and, in containers, the cgroup working set versus its limit. Get comfortable reading those two and you'll stop chasing phantom memory emergencies — and catch the real ones, where anonymous memory is genuinely climbing toward a limit.

Internal workingThe page fault, demand paging, and reclaim

The engine underneath all of this is the page fault. Here's what happens when your program touches memory:

  1. The program reads or writes a virtual address. The MMU checks the TLB. Hit → instant translation, done. Miss → the MMU walks the page table.
  2. If the page table entry is present, the MMU fills the TLB and the access proceeds. No kernel involvement — this is the fast, common case.
  3. If the entry is not present, the CPU raises a page fault and traps into the kernel. Now the kernel decides what kind of fault this is.
  4. Minor fault: the data is already in RAM but not yet mapped for this process — it's in the page cache, or it's a copy-on-write page, or it's a fresh anonymous page. The kernel just maps a frame (handing out a zeroed page for new anonymous memory) and returns. Fast — microseconds.
  5. Major fault: the data isn't in RAM at all — it's on disk (a file not yet cached) or on swap. The kernel issues I/O, puts the process to sleep in D state while it waits, and maps the frame when the read completes. Slow — this is disk latency, and a storm of major faults is what swap thrash feels like.

This is demand paging: memory is only made real when touched. It's why VSZ can dwarf RSS, and why the reckoning for overcommit arrives on a write. When RAM fills, the kernel runs reclaim: it frees clean page-cache pages first (free, since they're just copies of files), writes back dirty pages, and — under real pressure — pages anonymous memory out to swap. The knob vm.swappiness (default 60) tunes how eagerly it prefers swapping anonymous pages versus dropping file cache.

Overcommit and the OOM killer

Linux lets total promised memory exceed RAM+swap — vm.overcommit_memory=0 (the heuristic default) allows reasonable overcommit; =2 refuses to overcommit at all. The bet is that not everyone cashes their promise at once. When the bet fails — processes actually touch more than can be backed, and reclaim has nothing left to free — the kernel invokes the OOM killer. It doesn't fail the allocation; it picks a process to kill so the rest can continue.

It chooses by oom_score, which is driven mostly by how much memory the process uses (killing the biggest hog frees the most), adjustable per process via oom_score_adj (range −1000 to +1000; −1000 makes a process effectively unkillable by OOM). The victim gets SIGKILL — no cleanup, no handler, gone. In cgroup v2, a memory limit (memory.max) scopes this: when a cgroup hits its limit and can't reclaim, the OOM killer fires inside that cgroup only, killing a process there rather than touching the rest of the host. That scoped kill is exactly what a Kubernetes memory limit gives you — and why an OOMKilled container shows exit code 137 (128 + signal 9).

Think first: free -m shows only 300 MB "free" out of 16 GB. Is the box about to run out of memory?

Almost certainly not. Low "free" is the normal, healthy state, because Linux uses spare RAM as page cache rather than leaving it idle — and that cache is instantly reclaimable. The number that answers "am I about to run out" is available (the available column in free, or MemAvailable in /proc/meminfo): the kernel's estimate of how much you can allocate without swapping. If available is several GB, you're fine even with "free" near zero. You'd only worry if available is small and anonymous memory (not cache) is what's filling RAM — that's memory you can't just drop.

ComponentsThe pieces, and what each owns

  • MMU + TLB. Hardware. Translates virtual to physical on every access; the TLB caches recent translations. A context switch to another address space flushes the TLB unless the CPU tags entries (PCID). Huge pages (2 MiB/1 GiB) cut TLB misses for big memory footprints.
  • Page tables. Per-process, kernel-maintained. Map virtual pages to frames, swap slots, or "not present." The source of truth the MMU walks.
  • The page cache. File data cached in RAM. Clean pages are droppable for free; dirty pages must be written back (writeback is driven by vm.dirty_* ratios). This is the "buff/cache" you see grow when you read files — and it's why re-reads are fast.
  • Anonymous memory & swap. Heap/stack pages with no file behind them. Under pressure they go to swap; with no swap configured, they can't be reclaimed at all — so the OOM killer is the only relief valve.
  • The OOM killer. Fires when allocation can't be satisfied and reclaim is exhausted. Ranks processes by oom_score (usage + oom_score_adj) and SIGKILLs one. Scoped per-cgroup when a cgroup limit is the constraint.
  • cgroup v2 memory controller. memory.max (hard limit → cgroup OOM), memory.high (soft limit → throttle and reclaim, no kill), memory.current (usage now), memory.swap.max, and memory.events (counters including oom_kill). This is the machinery behind Kubernetes requests/limits.
  • /proc/meminfo & /proc/<pid>/status. The truth. MemTotal/MemFree/MemAvailable/Cached/Dirty/SwapTotal/SwapFree for the system; VmSize (VSZ), VmRSS, RssAnon, RssFile, RssShmem per process.

Data flowFollowing one allocation to its grave

Watch a process ask for a gigabyte and use it:

  1. The program calls malloc(1 GB). glibc satisfies this with an mmap of anonymous memory. VSZ jumps by 1 GB; RSS doesn't move — nothing is backed yet.
  2. The program writes to the first page. Page fault → minor fault → the kernel hands out a zeroed frame and maps it. RSS grows by 4 KiB. Repeat for every page it touches; RSS climbs only as far as it actually writes.
  3. RAM starts filling. The kernel reclaims: it drops clean page-cache pages first (cheap), then writes back dirty file pages.
  4. Still under pressure, the kernel pages some anonymous memory out to swap. If this process (or others) keep touching swapped-out pages, you get major faults in both directions — swap thrash: the box spends its time moving pages instead of doing work, latency spikes, and CPU looks busy in I/O wait.
  5. If there's a cgroup limit and usage hits memory.max with nothing left to reclaim, the cgroup OOM killer fires and SIGKILLs a process in that cgroup. On the whole host with no limit and no swap left, the global OOM killer picks the highest oom_score victim.
  6. When the process exits (or is killed), all its pages — resident and swapped — are freed, and the frames return to the pool, mostly becoming page cache again until something needs them.

Lab 1Build — read the memory numbers correctlyBuild

Start with free -m and learn to read the one column that matters.

bash
free -m
grep -E 'MemTotal|MemFree|MemAvailable|^Cached|Buffers|Dirty' /proc/meminfo
Output (example) total used free shared buff/cache available Mem: 7940 1120 240 30 6580 6560 MemTotal: 8130400 kB MemFree: 245900 kB MemAvailable: 6717600 kB Cached: 6210300 kB

Only 240 MB "free," but 6560 MB available — because 6.5 GB is page cache the kernel will surrender on demand. The rule: ignore "free," read "available." Now prove the RSS-vs-VSZ gap. Map half a gigabyte, touch almost none of it, and watch the two diverge:

bash
python3 - <<'EOF' &
import mmap, os, time
m = mmap.mmap(-1, 512*1024*1024)      # reserve 512 MiB, touch nothing
print("pid", os.getpid())
time.sleep(15)
for i in range(0, 64*1024*1024, 4096): m[i] = 1   # now touch 64 MiB
time.sleep(60)
EOF
PID=$!
sleep 2 ; grep -E 'VmSize|VmRSS' /proc/$PID/status   # before touching
sleep 20; grep -E 'VmSize|VmRSS' /proc/$PID/status   # after touching 64 MiB
OutputVmSize: 538000 kB # ~512 MiB reserved VmRSS: 6100 kB # almost nothing resident --- after touching 64 MiB --- VmSize: 538000 kB # unchanged: the reservation didn't move VmRSS: 71000 kB # ~64 MiB now resident

VSZ is the promise; RSS is the reality, and it only grows as pages are touched. That single demo kills more memory confusion than any dashboard.

Lab 2Understand — watch the page cache breatheUnderstand

The page cache is invisible until you make it move. Write a file, watch cache grow; read it back, watch reads get instant.

bash
free -m | awk 'NR==2{print "buff/cache before:", $6}'
dd if=/dev/zero of=/tmp/big bs=1M count=1024 status=none   # write 1 GiB
free -m | awk 'NR==2{print "buff/cache after write:", $6}'

# First read is from disk; second is from cache — time both.
sync
time dd if=/tmp/big of=/dev/null bs=1M status=none          # cold-ish
time dd if=/tmp/big of=/dev/null bs=1M status=none          # now cached — much faster
Output (example)buff/cache before: 210 buff/cache after write: 1240 real 0m0.640s # first read real 0m0.120s # second read — served from the page cache

The second read is several times faster because the bytes never left RAM. This is why "warming the cache" is a real thing, and why the first request after a deploy is slower. On a real host you can force the cache empty to compare (a diagnostic, never a fix, and it needs a privileged/host context):

bash
# On a host or privileged container only. Never do this to "free memory" in prod.
sync && echo 3 > /proc/sys/vm/drop_caches
free -m | awk 'NR==2{print "buff/cache after drop:", $6}'

Dropping caches just makes the next reads slow again while the kernel refills it. If someone proposes cron-ing drop_caches to "keep memory free," that's the misunderstanding this lab exists to cure.

Think first: a teammate says "our monitoring shows the node at 92% memory — we need bigger instances." What do you check before agreeing?

Whether that 92% is anonymous memory or page cache. Pull MemAvailable from /proc/meminfo (or the available column) and the split of Cached vs anonymous. If most of "used" is cache and MemAvailable is comfortably large, the node is healthy and using RAM the way it should — bigger instances would just give you a bigger cache. If instead anonymous memory is high and available is shrinking over time, that's a real trend (a leak or genuine growth), and now instance size or a limit review is the right conversation. Same 92%, opposite conclusions — the metric to trust is available, not used.

Lab 3Break — trigger an OOM kill inside a memory-limited containerBreak

This is the OOMKilled pod, reproduced on your laptop. Start a container with a hard 256 MB limit and no swap, then allocate past it.

bash
# --memory sets the cgroup memory.max; equal --memory-swap disables swap.
docker run --rm -it --memory=256m --memory-swap=256m ubuntu:24.04 bash

# Inside: look at the limit the cgroup enforces.
cat /sys/fs/cgroup/memory.max          # 268435456 (256 MiB)
cat /sys/fs/cgroup/memory.current      # current usage

Now allocate and touch 400 MB — more than the 256 MB ceiling — and watch what the kernel does:

bash
python3 -c 'a = bytearray(400*1024*1024)'   # bytearray zeroes it → touches every page
echo "exit code: $?"
OutputKilled exit code: 137

Exit 137 = 128 + 9: the process took a SIGKILL from the OOM killer. Before I tell you the mechanism, confirm it from inside the container — where did the evidence show up?

Reveal the evidence and the mechanism

The cgroup recorded it. memory.events increments an oom_kill counter every time the controller kills a process in this cgroup:

bash
cat /sys/fs/cgroup/memory.events
Outputlow 0 high 0 max 3 oom 1 oom_kill 1

The max counter counts times usage hit the ceiling; oom_kill counts actual kills. On the host, dmesg shows the full report: Memory cgroup out of memory: Killed process … (python3) total-vm:… anon-rss:…. This is precisely what Kubernetes surfaces as OOMKilled with exit code 137 — the container's memory limit is a cgroup memory.max, and exceeding it kills a process in that container, not the node. The fix is never "just raise the limit" reflexively; it's to learn the app's real working set and set the limit above it (with headroom), or fix the leak.

Lab 4Troubleshoot — "the container is out of memory" (but is it?)Troubleshoot

A common false alarm: a dashboard shows a container near its memory limit, an alert fires, someone wants to bump the limit. Reproduce the ambiguous picture and learn to read it. In a 512 MB container, fill the cache by reading a big file, then inspect what's actually accounted.

bash
docker run --rm -it --memory=512m ubuntu:24.04 bash
apt-get update && apt-get install -y procps python3
dd if=/dev/zero of=/tmp/f bs=1M count=400 status=none   # 400 MiB into page cache
cat /tmp/f > /dev/null                                   # pull it through cache
cat /sys/fs/cgroup/memory.current                        # looks high — near the limit!

memory.current looks alarmingly close to memory.max. Is this container actually about to OOM? Investigate before deciding — the breakdown is in the stats file.

bash
grep -E '^anon |^file |^inactive_file|^active_file' /sys/fs/cgroup/memory.stat
Reveal how to read it

memory.current includes page cache, and cache is reclaimable. The honest question is: how much of the usage is anon (unreclaimable — heap/stack) versus file (page cache — droppable under pressure)?

Outputanon 24117248 # ~23 MiB truly resident anonymous file 419430400 # ~400 MiB page cache — will be dropped before any OOM

Only ~23 MB is anonymous; the rest is cache the kernel will evict the moment the cgroup needs room. This container is not about to OOM — cache pressure inside a cgroup causes reclaim, not kills. The tell for a real problem is rising anon approaching memory.max, plus a climbing oom_kill count in memory.events. Kubernetes' "working set" metric already excludes reclaimable cache for exactly this reason, so alert on working set (or anon), not raw usage. Bumping the limit here would waste memory and hide nothing, because there's nothing wrong.

Lab 5Production challenge — swap thrash and a slow leakSenior challenge

A service on a swap-enabled host gets slower and slower over days; CPU shows high I/O wait, latency is erratic, but nothing has crashed. On another host, a process's RSS climbs steadily and never plateaus. Two different diseases with overlapping symptoms. First, feel swap thrash directly — allocate well past RAM on a swap-enabled box (do this on a disposable VM, not a shared host):

bash
vmstat 1 5            # baseline: watch the si/so (swap-in/out) columns
stress-ng --vm 2 --vm-bytes 90% --vm-keep --timeout 30s &
vmstat 1 30           # si/so climb, 'wa' (I/O wait) climbs, throughput tanks

Nonzero si/so that stay high is the signature of thrash — the box is moving pages to and from disk constantly. Now the senior task: on a struggling host, how do you tell swap thrash from a genuine memory leak, and what do you actually do about each? Work it out, then reveal.

Reveal the method and the fixes

Distinguish them. Swap thrash shows sustained si/so in vmstat and high %wa, with total committed memory over RAM — but individual RSS may be stable. A leak shows one process's RssAnon climbing monotonically over hours with no plateau; watch it directly:

bash
for i in $(seq 1 20); do
  grep -H RssAnon /proc/<pid>/status; sleep 60
done                                  # steady climb = leak, not cache
ps -eo pid,rss,comm --sort=-rss | head # who is the biggest anon consumer?

Thrash fix: reduce demand or add RAM. On latency-sensitive hosts many teams disable swap entirely (or set vm.swappiness=1) so the box fails fast via OOM instead of degrading slowly — a slow-dying host is often worse than a fast-failing one you can replace. Kubernetes historically required swap off on nodes for exactly this predictability.

Leak fix: the durable answer is in the app (find and fix the leak). Operationally, contain the blast radius: set a cgroup memory.high to apply reclaim pressure and slow the climb, and a memory.max so the leak gets OOMKilled in its own cgroup instead of taking the node down. Protect the truly critical process with oom_score_adj:

bash
echo -800 > /proc/<critical-pid>/oom_score_adj   # make it a last resort for the OOM killer

The mindset: you can't stop a leak from the outside, but you can decide who the OOM killer takes and where the failure is contained. That's the cgroup story we build fully in Chapter 23.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · OOMKilled pod (exit 137)

Symptom: a pod restarts repeatedly; kubectl describe pod shows Last State: Terminated, Reason: OOMKilled, Exit Code: 137. First cut: compare the container's memory limit to its actual working set (metrics-server / kubectl top pod, or the container's memory.current and memory.stat anon). Confirm: the node's dmesg shows a memory-cgroup OOM naming the process. Usual cause: limit set below the real working set, a memory leak, or a workload spike (large request payload, batch job). Fix: set the limit above the observed working set with headroom, or fix the leak. Raising the limit blindly just moves the cliff; it's the right move only when the limit was genuinely too tight.

Incident pattern · "we're out of memory" that isn't

Symptom: an alert fires on "memory used > 90%"; the app is fine. First cut: read MemAvailable (system) or the anon line of memory.stat (cgroup) — not raw "used." Confirm: most of "used" is Cached/file, and available is large. Usual cause: the alert thresholds on total usage including reclaimable cache. Fix: alert on available / working set / anon, not on used. Never cron drop_caches to make the graph look better — you're just slowing every subsequent read.

Incident pattern · swap thrash

Symptom: a host degrades slowly — rising latency, high I/O wait, CPU "busy" but low useful throughput, nothing crashes. First cut: vmstat 1 and watch si/so (swap in/out) and wa. Confirm: committed memory exceeds RAM and si/so stay nonzero. Usual cause: genuine overcommit under load, or a leak slowly pushing anon into swap. Fix: reduce memory demand or add RAM; on latency-sensitive nodes, prefer swap off / low swappiness so you fail fast via OOM rather than thrashing. A host that dies quickly and gets replaced beats one that limps for an hour.

Production · security · performanceWhat matters in production

Set limits from the working set, not from guesswork. A container memory limit that's below the app's real anonymous footprint guarantees OOMKills under load; one that's wildly above wastes schedulable memory and lets a leak run longer before it's contained. Measure the working set over a representative period, set the limit above the peak with headroom, and alert on approach — not on the kill.

Requests vs limits shape the node. In Kubernetes, the memory request is what the scheduler reserves and what protects a pod from eviction; the limit is the cgroup memory.max that triggers an OOMKill when exceeded. Requests too low overcommit the node and invite node-pressure evictions; limits too low invite per-pod OOMKills. Both are this chapter wearing a Kubernetes hat, and we return to it in Chapter 37.

Performance lives in the TLB and the cache. Big-memory workloads (databases, JVMs with huge heaps) suffer TLB misses; huge pages reduce that cost. And the page cache is doing more for your latency than most app-level caching — which is why cold caches after a deploy or a node replacement produce a latency bump you should expect and warm deliberately.

Common mistakes: reading "free" instead of "available"; treating page cache as memory pressure; setting swap up on latency-critical nodes and then being surprised by thrash; raising a memory limit to "fix" an OOMKill without checking whether it's a leak; and forgetting that overcommit means the failure lands on a write, sometimes far from the code that over-allocated.

System-design connectionWhere this reaches into architecture

Memory sets a hard ceiling on density: how many pods fit on a node, how big a cache or heap you can run, when you scale out versus up. The page cache is the reason read-heavy systems put hot data in RAM and design around cache hit ratio, and it's the same principle that reappears one layer up as Redis, CDNs, and application caches in Chapter 85. Overcommit and the OOM killer are why capacity planning (Chapter 89) is about the touched working set under peak load, not the requested virtual size — plan for what processes cash in, not what they promise. And the choice to run without swap so nodes fail fast rather than thrash is a reliability decision: a predictable hard failure you can automate around beats a slow degradation that pages a human.

InterviewInterview questions & answers

Answer each in your head first.

30-secWhat's the difference between RSS and VSZ?

VSZ (virtual size) is the total virtual address space a process has mapped — every allocation and mapping, whether or not it's backed by physical memory. RSS (resident set size) is the subset actually resident in RAM right now. VSZ is the promise; RSS is what's real. They diverge because Linux allocates lazily — malloc reserves virtual space, and physical pages are only committed when the process writes to them. One catch: RSS counts shared pages (like libc) fully in every process that maps them, so summing RSS across processes overcounts; PSS is the number that splits shared pages proportionally.

2-minWalk me through what happens on a page fault.

When a process accesses a virtual address, the MMU tries to translate it, checking the TLB first. A TLB hit is instant. On a miss it walks the page table. If the page-table entry says the page is present, it fills the TLB and the access proceeds — no kernel involvement. If the entry is not present, the CPU raises a page fault and traps into the kernel. The kernel classifies it: a minor fault means the data is already in RAM but not mapped for this process — a page-cache page, a copy-on-write page, or a brand-new anonymous page — so the kernel just maps a frame (handing out a zeroed page for new memory) and returns; that's microseconds. A major fault means the data has to come from disk — a file not yet cached, or a page that was swapped out — so the kernel issues I/O, parks the process in uninterruptible sleep while it waits, and maps the frame when the read completes; that's disk latency. This whole mechanism is demand paging: memory becomes real only when touched, which is why a process's VSZ can be far larger than its RSS, and why a storm of major faults — swap thrash — makes a box slow without crashing it.

DeepHow does the OOM killer choose a victim, and how do cgroup limits change that?

When an allocation can't be satisfied and reclaim has nothing left to free, the kernel invokes the OOM killer rather than failing the allocation. It scores candidate processes with oom_score, driven mainly by memory usage — killing the biggest consumer frees the most and, ideally, ends the emergency in one shot — adjustable per process with oom_score_adj from −1000 to +1000, where −1000 makes a process effectively exempt. The victim gets an uncatchable SIGKILL. Scope is the important part: with cgroup v2, a memory limit (memory.max) means that when a cgroup hits its ceiling and can't reclaim, the OOM killer fires inside that cgroup and kills a process there, leaving the rest of the host alone. That scoped kill is exactly what a Kubernetes memory limit provides, and it's why an OOMKilled container reports exit code 137 — 128 plus signal 9 — while the node stays up. There's also memory.high, a softer limit that throttles and reclaims under pressure without killing, which you can use to slow a leak instead of letting it hit the hard wall.

ScenarioA pod keeps getting OOMKilled. How do you decide whether to raise the limit or fix the app?

I'd first confirm it's a limit problem, not a node problem: kubectl describe to see OOMKilled with exit 137, then compare the container's actual working set over time — via kubectl top or the cgroup's memory.current and the anon line of memory.stat — against the configured limit. If the working set is stable and simply sits above a too-tight limit, that's a sizing bug: raise the limit above the observed peak with headroom. If instead the anonymous footprint climbs steadily and never plateaus across restarts, that's a leak, and raising the limit only delays the next kill — the fix belongs in the app. I'd also check whether the kills correlate with a spike, like large request payloads or a batch path, which points at a specific code path rather than steady growth. The discipline is to look at the working-set trend before touching the limit; the reflex of bumping the limit is right maybe a third of the time and hides a real bug the other two-thirds.

Follow-upShould production nodes have swap on or off, and why?

For latency-sensitive services I lean toward swap off, or swappiness very low, on the nodes. The reason is failure mode: with swap, a memory-overcommitted box degrades slowly into thrash — sustained swap-in/out, high I/O wait, erratic latency — and a slowly dying host that still answers health checks is harder to detect and automate around than one that fails fast. With swap off, exceeding memory triggers the OOM killer promptly, which in a cgroup world means one pod dies cleanly and gets rescheduled while the node stays healthy. That predictability is why Kubernetes historically required swap disabled on nodes. Swap still has legitimate uses — batch or memory-elastic workloads where slow-but-alive beats killed, and modern setups can use it more surgically — but the default instinct for a service tier is: fail fast and let the scheduler replace the pod, rather than thrash.

RetainQuick revision

Every process gets a private virtual address space; the MMU (with the TLB caching recent lookups) translates virtual pages to physical frames via per-process page tables. Memory is handed out lazily on demand, so a write triggers a page fault — minor if the data's already in RAM, major if it must come from disk or swap. VSZ is the mapped promise, RSS the resident reality, and shared pages skew per-process sums (use PSS). Spare RAM becomes page cache, which is reclaimable — so read available, not free. Under pressure the kernel drops clean cache, writes back dirty pages, then swaps anonymous memory; sustained swap-in/out is thrash. Linux overcommits, and when the bet fails the OOM killer SIGKILLs the highest-oom_score victim — scoped to a cgroup when a limit is the constraint, which is exactly what a Kubernetes memory limit and its exit-137 OOMKilled are.

The 10 things to remember

  1. Every process sees a private virtual address space; the MMU translates it to physical RAM, TLB caches the lookups.
  2. Memory is paged (4 KiB) and allocated lazily — malloc reserves; physical RAM is committed only on the first write.
  3. VSZ is what's mapped; RSS is what's resident. Shared pages inflate summed RSS — use PSS for honest per-process totals.
  4. A minor page fault maps a frame already in RAM (fast); a major fault reads from disk/swap and blocks in D (slow).
  5. Spare RAM is page cache and it's reclaimable — read available/MemAvailable, not free.
  6. Anonymous memory needs swap to be reclaimed; clean file pages can be dropped for free, dirty ones written back first.
  7. Linux overcommits memory; the reckoning is the OOM killer, which SIGKILLs by oom_score (tune with oom_score_adj).
  8. A cgroup memory.max scopes the OOM kill to that cgroup — this is a Kubernetes memory limit, and OOMKilled = exit 137.
  9. In a cgroup, read the anon vs file split in memory.stat; cache pressure causes reclaim, not kills.
  10. Sustained swap-in/out (vmstat si/so) is thrash — prefer swap off / low swappiness on latency-sensitive nodes to fail fast.
