Filesystems, inodes, file descriptors & disk I/O

A filename is just a label on a drawer. The file itself — its bytes, its owner, its size — lives somewhere else entirely, and it survives as long as one label or one open handle still points to it. Miss that one fact and you'll stare at "disk full" while df swears there's space, or delete a 40 GB log and watch the disk not budge.

Why this exists · the problemThe problem: turning a dumb block device into files

A disk — spinning platter, SSD, cloud volume — knows nothing about files. It offers one thing: a huge array of fixed-size blocks you can read or write by number. Block 0, block 1, block 4,001,912. That's it. No names, no folders, no "this file is 3 KB and belongs to user 1000."

Everything else is software the kernel layers on top. A filesystem is the scheme that carves those raw blocks into named files and directories, records who owns what and how big it is, and tracks which blocks belong to which file. And because there are many filesystems (ext4, xfs, btrfs), many device types (local SSD, NFS, a container's overlay), and thousands of programs that just want to call open and read without caring, the kernel puts one uniform layer in front of all of them: the VFS, the virtual filesystem. Your program calls the same five syscalls whether the bytes are on a local SSD, an NFS server three racks away, or a tmpfs that only exists in RAM.

The one idea that trips up more engineers than any other: the filesystem deliberately splits a file's name from its identity. The name is a label in a directory. The identity — the metadata and the pointers to the data — is a separate object called an inode. A name points to an inode; several names can point to the same inode; and the inode (and its disk blocks) lives until zero names point to it and no process holds it open. That single rule explains most of this chapter's incidents.

Key point

Deleting a file does not delete its data. rm removes a name (a directory entry) and decrements the inode's link count. The data blocks are freed only when the link count reaches zero and no open file descriptor still references the inode. A process holding the file open keeps every byte on disk — nameless, invisible to ls, but very much still consuming space.

Mental model · analogyThe mental model: a library with a card catalog

Carry this the whole way through.

Real-world analogy

Picture a library. Each book sits on a shelf with a unique shelf ID stamped inside — but no title on the spine. The book is the content plus its record card: how many pages, who donated it, when. That book-plus-record is the inode, and the shelf ID is its inode number.

You find books through the card catalog. Each card shows a human title — "Moby Dick" — and the shelf ID it points to. Those cards are directory entries (dentries). Two cards can point to the same shelf ID: two titles, one physical book. That's a hard link. Pull one card and the book's still there, because the other card still points to it. The book is only sent to the incinerator when the last card is pulled — and even then, not while a reader is holding it at a desk.

To read, you fill a slip and the librarian hands you the book; your library card lists what you've currently got out, each on a numbered line. That numbered line is a file descriptor, and the slip that tracks which page you're on is the open file description with its offset. You never walk into the stacks yourself — the front desk (the VFS) takes your slip and deals with whichever room, branch, or off-site archive the book actually lives in. For speed, the desk keeps photocopies of recently requested pages up front (the page cache); insisting on the original from the deep archive every time is direct I/O; and getting a stamped receipt that your donation was truly filed in the permanent archive — not just left on the return cart — is fsync.

ArchitectureName, inode, blocks — and the descriptor chain

Three levels of indirection sit between the name you type and the bytes on the platter, and every filesystem incident is really a question about one of the links in this chain.

  • A directory is itself a file whose contents are a list of (name → inode number) pairs. Path resolution walks these, component by component.
  • An inode holds the file's identity: mode/permissions, owner uid/gid, size, timestamps, a link count (how many names point here), and pointers to the data blocks. It has no name.
  • The data blocks hold the actual bytes, scattered across the device wherever the filesystem found room.

On the process side, an open file is a chain too: a small integer file descriptor indexes the process's fd table; that entry points to an open file description in the kernel (holding the current offset and the open flags); and that points to the inode. The middle object matters more than people expect — because fork() and dup() copy the fd but share the open file description, two descriptors can share one offset, which is exactly how a shell's >> append and pipelines behave sanely.

Why an SRE cares

Two of the most common "the disk is full" pages have nothing to do with a full disk. One is inode exhaustion: you ran out of inodes (names) while blocks are free, so df -h looks fine but every write fails with ENOSPC. The other is a deleted-but-open file: someone rm'd a giant log to reclaim space, but the process still has it open, so the blocks stay pinned and df doesn't move. Both are invisible unless you know the name/inode/fd split — and both are five-minute fixes once you do.

Internal workingWhat open, read, write, and fsync actually do

Walk the four calls through the VFS. This is the machinery behind every log line and every database commit.

  1. open("/var/log/app.log", …) — path resolution. The kernel walks the path one component at a time, looking each name up in the dentry cache (or reading the directory from disk on a miss), checking execute/search permission on each directory as it goes, until it reaches the target inode. It creates a new open file description (offset 0, your flags), installs it in the process's fd table at the lowest free slot, and returns that fd number.
  2. read(fd, buf, n). fd → open file description → inode. The VFS asks the filesystem for the bytes at the current offset. If they're warm in the page cache, it's a fast copy into your buffer. If not, the block layer issues I/O to the device and the process sleeps in D until it lands (a major fault from Chapter 3). The offset in the open file description advances by the number of bytes read.
  3. write(fd, buf, n) — and here's the surprise. By default it's buffered: the kernel copies your bytes into the page cache, marks those pages dirty, advances the offset, and returns success — before anything reaches the disk. The data is durable only once writeback (driven by the vm.dirty_* thresholds and a background flusher) pushes it out. A crash in that window loses the "written" data. This is why write returning is not a promise the bytes survived a power cut.
  4. fsync(fd) — the durability barrier. It forces the dirty pages for this inode (and its metadata) out to the physical device and waits for the device to confirm. Only after fsync returns is the data truly persistent. fdatasync is a cheaper cousin that skips metadata-only updates. Databases fsync their write-ahead log on every commit for exactly this reason — and it's often their dominant latency cost.
  5. close(fd). Drops this descriptor's reference to the open file description. When the last reference closes and the inode's link count is already zero, now the filesystem frees the data blocks. Until then, the file lives on.

Buffered vs direct. The default page-cache path is great — reads get cached, writes get batched. Some workloads don't want it: a database that maintains its own carefully tuned cache doesn't want the kernel double-caching the same data, so it opens files with O_DIRECT, which bypasses the page cache and DMAs straight between the device and the app's buffer (with alignment requirements). Direct I/O trades the kernel's help for control and predictability.

iowait is the metric that surfaces all of this. %wa in top is the fraction of time CPUs sat idle with at least one disk I/O outstanding — "we have nothing to do but wait for the disk." It's a symptom, not a diagnosis: high iowait with one saturated device is a storage bottleneck; high iowait with idle devices can just mean the CPU had nothing else to run. You confirm with iostat, not with %wa alone.

Think first: your app calls write(), it returns 0 errors, and one second later the box loses power. Is the data safe?

No. A successful write() only means the bytes made it into the kernel's page cache — they're marked dirty and scheduled for writeback, but they may not have touched the disk yet. A power loss in that window loses them. The only way to know data survived is to fsync() (or fdatasync()) the descriptor and have it return, which forces the dirty pages to the device and waits for confirmation. This is the whole reason databases pay the fsync cost on every commit, and why "we wrote it, why did we lose it after the crash?" is nearly always a missing fsync — or a storage layer that lied about honoring the flush.

ComponentsThe pieces, and what each owns

  • Inode. The file's identity: mode, uid/gid, size, timestamps (mtime = content changed, ctime = inode changed, atime = last accessed), link count, and block pointers. Owns everything about the file except its name.
  • Directory entry (dentry) & name. A name lives only inside a directory as a (name → inode number) pair. The dentry cache makes repeated path lookups fast. Multiple dentries → one inode is a hard link; a symlink is a separate inode whose data is a path string.
  • File-descriptor table. Per process. Maps small integers (0/1/2 = stdin/stdout/stderr, then 3+) to open file descriptions. Capped by ulimit -n and the kernel's nr_open.
  • Open file description. The kernel object holding the current offset and status flags. Shared across dup() and inherited across fork(), which is why sharing an offset is possible and intentional.
  • VFS. The uniform layer with four object types — superblock (a mounted filesystem), inode, dentry, and file — that each concrete filesystem implements. Gives every filesystem the same open/read/write surface.
  • Filesystems. ext4 and xfs (the common server pair), plus tmpfs (RAM), overlayfs (container images, Chapter 24), procfs/sysfs (kernel windows), and network filesystems like NFS. A key difference: ext4 fixes its inode count at format time, while xfs allocates inodes dynamically — so ext4 can exhaust inodes and xfs almost never does.
  • Block layer + device. Turns filesystem block requests into device I/O, with an I/O scheduler and queues. This is where iostat reads %util, await, and queue depth.

Data flowFollowing one appended log line

Your app writes a line to /var/log/app.log. Here's the whole path:

  1. The app called open("/var/log/app.log", O_WRONLY|O_APPEND|O_CREAT, 0644) at startup. The kernel resolved the path, found (or created) the inode, and returned fd 3 with an open file description in append mode.
  2. It calls write(3, "…line…\n", 42). The kernel copies 42 bytes into the page cache, marks the page dirty, bumps the offset, and returns 42. The line is now visible to readers and would be lost on a power cut.
  3. Seconds later, background writeback flushes the dirty page to the device — or, if this were a database WAL, an explicit fsync would force and confirm it immediately.
  4. A log-rotation tool renames app.log to app.log.1 and creates a fresh app.log. Crucially, the app still holds fd 3 pointing at the old inode — so it keeps writing to the rotated file unless it's told to reopen. That's the whole reason logrotate uses copytruncate or sends the process a signal to reopen its log.
  5. On shutdown the app closes fd 3. If by then no name points at that inode and no other fd holds it, its blocks are freed.

Lab 1Build — names, inodes, and linksBuild

Prove that a name and a file are different things. Create a file, look at its inode, then give it a second name.

bash
echo "payload" > /tmp/a.txt
stat /tmp/a.txt                          # inode number, links, size, timestamps
ln /tmp/a.txt /tmp/b.txt                  # HARD link: a second name for the SAME inode
ln -s /tmp/a.txt /tmp/c.txt               # SOFT link: a new inode holding the path string
ls -li /tmp/a.txt /tmp/b.txt /tmp/c.txt
Output131074 -rw-r--r-- 2 root root 8 ... /tmp/a.txt 131074 -rw-r--r-- 2 root root 8 ... /tmp/b.txt # SAME inode 131074, link count 2 131099 lrwxrwxrwx 1 root root 10 ... /tmp/c.txt -> /tmp/a.txt # different inode

a.txt and b.txt share inode 131074 and a link count of 2 — they are the same file with two names. c.txt is a symlink: its own inode whose contents are the text /tmp/a.txt. Now delete the original name and watch the data survive:

bash
rm /tmp/a.txt
cat /tmp/b.txt        # still "payload" — the inode lives; link count is now 1
cat /tmp/c.txt        # error: symlink now dangles (points at a gone name)
stat -c '%h links' /tmp/b.txt

Removing a.txt dropped the link count from 2 to 1; the data is untouched because b.txt still points at the inode. The symlink, which only ever held a path, is now broken. This is the entire hard-link vs symlink distinction, on one screen.

Lab 2Understand — the fd table, and buffered vs durable writesUnderstand

Look at a process's open descriptors, then prove that write is not durable but fsync is. First, the fd table via /proc and lsof:

bash
sleep 600 < /etc/hostname &   # a process with a file open on fd 0
PID=$!
ls -l /proc/$PID/fd            # 0/1/2 plus anything opened
cat /proc/$PID/fdinfo/0        # the offset + flags of the open file description
lsof -p $PID
Output (trimmed)lr-x------ 1 root root ... 0 -> /etc/hostname lrwx------ 1 root root ... 1 -> /dev/pts/0 pos: 0 flags: 0100000

Descriptor 0 points at /etc/hostname; fdinfo shows the offset (pos) and flags. That offset is the "which page am I on" slip from the analogy. Now watch a write's durability with strace — note that write returns instantly while fsync is the call that actually costs time and guarantees persistence:

bash
strace -T -e trace=openat,write,fsync python3 -c '
import os
fd = os.open("/tmp/durable", os.O_WRONLY|os.O_CREAT, 0o644)
os.write(fd, b"a commit that must survive a crash\n")
os.fsync(fd)          # the durability barrier
os.close(fd)'
Outputopenat(AT_FDCWD, "/tmp/durable", O_WRONLY|O_CREAT, 0644) = 3 <0.000034> write(3, "a commit that must survive a cra"..., 35) = 35 <0.000021> fsync(3) = 0 <0.004180>

The <…> is each call's duration. write took 21 microseconds — it just touched the page cache. fsync took 4.2 milliseconds — 200× longer — because it drove the data to the physical device and waited. That gap is why fsync-per-commit dominates database latency, and why the durability question is always "did you fsync?"

Lab 3Break — "disk full" with plenty of space (inode exhaustion)Break

Make a tiny filesystem with very few inodes, then run out of inodes while blocks stay free. A tmpfs lets you cap the inode count directly.

bash
mkdir -p /mnt/small
# 200 MiB of space, but only 200 inodes allowed.
mount -t tmpfs -o size=200m,nr_inodes=200 tmpfs /mnt/small

# Create empty files until it fails. Empty files use an inode, ~no blocks.
i=0
while : > /mnt/small/f$i 2>/dev/null; do i=$((i+1)); done
echo "stopped after creating $i files"

It stops well before filling 200 MB. Now look at the two different resources — blocks and inodes — and watch them disagree:

bash
df -h /mnt/small     # space: almost all FREE
df -i /mnt/small     # inodes: 100% used
: > /mnt/small/one-more   # the error your app actually sees
OutputFilesystem Size Used Avail Use% Mounted on tmpfs 200M 4.0K 200M 1% /mnt/small # df -h: 1% used Filesystem Inodes IUsed IFree IUse% Mounted on tmpfs 200 200 0 100% /mnt/small # df -i: 100% used bash: one-more: No space left on device # ENOSPC — despite free space!

ENOSPC ("No space left on device") with 200 MB free. Before the reveal: which command told you the truth, and what's the real-world version of "200 empty files"?

Reveal the cause and the fix

Inodes are a separate, finite resource from blocks. Every file — even a zero-byte one — consumes exactly one inode, and on ext4 the inode count is fixed at format time. Run out of inodes and you can't create any new file, no matter how much space is free. df -h (blocks) says you're fine; df -i (inodes) shows the real problem. The real-world culprits are always the same: millions of tiny files — a mail queue, a session-file directory, a cache of small objects, per-request temp files never cleaned up, or a runaway job writing one file per event.

Fix: find and delete the tiny-file swarm — for d in /var/*; do echo "$(find "$d" -xdev 2>/dev/null | wc -l) $d"; done | sort -rn | head points you at the directory holding the most entries. Longer term, ext4 needs a reformat with more inodes (mkfs.ext4 -N or a smaller bytes-per-inode ratio), or switch to xfs, which allocates inodes dynamically and effectively doesn't hit this wall. This is why "the disk is full" should always be two checks: df -h and df -i.

Lab 4Troubleshoot — the deleted log that won't free spaceTroubleshoot

The classic 2 a.m. page: disk near full, someone deletes a huge log, and df doesn't move. Reproduce it — a writer that holds a large file open, then delete the file out from under it.

bash
# A process that opens a file, writes 300 MiB, and keeps the fd open.
python3 - <<'EOF' &
import time
f = open('/tmp/app.log', 'wb')
f.write(b'x' * 300*1024*1024); f.flush()
while True:
    f.write(b'still writing\n'); f.flush(); time.sleep(1)
EOF
WRITER=$!
sleep 1
du -sh /tmp/app.log ; df -h /tmp | tail -1        # 300 MiB used
rm /tmp/app.log                                   # "reclaim" the space...
df -h /tmp | tail -1                               # ...but df DIDN'T drop. Why?

ls /tmp shows the file is gone, yet the space is still used. Investigate before revealing — where does a deleted-but-still-held file show up?

bash
ls -l /proc/$WRITER/fd | grep -i deleted     # the fd still points at the gone inode
lsof -p $WRITER | grep -i deleted            # lsof marks it (deleted)
lsof +L1 2>/dev/null | head                  # every file with link count < 1, system-wide
Reveal what happened, how to recover the data, and how to reclaim space without a restart

rm removed the name, dropping the inode's link count to 0 — but the writer still holds fd 3 open, so the inode and its 300 MB of blocks stay alive, nameless. df counts those blocks; du can't find them (no name to walk to). The space returns only when that fd is closed.

Two moves. First, you can still recover the contents — the data is right there behind the descriptor:

bash
FD=$(ls /proc/$WRITER/fd -l | awk '/deleted/{print $9}' | head -1)
cp /proc/$WRITER/fd/$FD /tmp/app.log.recovered   # the "deleted" bytes, read straight back

Second, reclaim the space without killing the process by truncating through the descriptor (keeps the process running, just empties the file):

bash
: > /proc/$WRITER/fd/$FD      # truncate the open file to 0 via its fd
df -h /tmp | tail -1          # space reclaimed now

The durable fix is process hygiene: rotate logs with copytruncate or by signaling the process to reopen its log file (SIGHUP for many daemons), never by rm-ing a file a process still holds. Restarting the process also frees it — but now you know how to do it without the restart, and how to get the data back.

Lab 5Production challenge — is this box slow on CPU or on I/O?Senior challenge

A service feels slow, load is up, and top shows high %wa. The wrong move is to assume "slow disk" and file a ticket. Generate real I/O pressure, then diagnose it the way a senior does — find the device, find the process, and decide the actual fix.

bash
# A synchronous-write workload: fsync after every block. This is fsync-bound.
( for i in $(seq 1 2000); do dd if=/dev/zero of=/tmp/sync.dat bs=1M count=1 \
    conv=fdatasync status=none; done ) &
IO=$!
iostat -x 1 3        # %util, await (latency), aqu-sz (queue depth) per device
top -b -n1 | head -5 # confirm the CPU is idle-waiting, not computing (%wa high, %us low)

Now the senior question: %wa is high, but is the disk actually the bottleneck, and which process is responsible? Investigate, then reveal.

Reveal the method and the decision

%wa alone doesn't prove a storage problem — it only says CPUs were idle with I/O outstanding. Confirm with iostat -x: if a device shows %util near 100 with high await, that device is genuinely saturated. Then attribute it to a process — you don't need root-only tools; /proc/<pid>/io shows real block I/O:

bash
pidstat -d 1 3 2>/dev/null || cat /proc/$IO/io   # write_bytes = actual device writes
strace -T -f -e trace=fdatasync,fsync,write -p $IO 2>&1 | head   # where the time goes

The strace -T timings will show each fdatasync taking milliseconds — the workload is fsync-bound, not throughput-bound. That changes the fix entirely: throwing bandwidth at it won't help; you need fewer, batched fsyncs (group commits), a faster-latency device (NVMe / provisioned-IOPS volume), or moving the sync-heavy component off the shared box. If instead iostat showed high throughput and moderate await, it'd be a bandwidth problem with a different fix. The discipline: %wa raises the question, iostat + /proc/<pid>/io + strace -T answer it, and only then do you choose between "batch the writes," "faster storage," or "separate the workload." Storage runbooks live in Chapter 104.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · inode exhaustion

Symptom: writes fail with ENOSPC / "No space left on device," but df -h shows free space. First cut: df -i — inodes at 100%. Confirm: find the directory with the most entries (a mail spool, session dir, tiny-object cache, uncleaned temp files). Usual cause: a flood of small or empty files on an ext4 filesystem whose inode count was fixed at format time. Fix: delete the tiny-file swarm; longer term, reformat with more inodes or move to xfs (dynamic inodes). Always check df -h and df -i.

Incident pattern · deleted-but-open file eating the disk

Symptom: disk near full; someone deleted a big log; df didn't drop; du can't find the space. First cut: lsof +L1 (files with link count < 1) or lsof | grep deleted. Confirm: a process holds a large "(deleted)" file open — see it in /proc/<pid>/fd. Usual cause: log rotation by rm instead of truncate/reopen, or a crashed rotation. Fix: truncate through the fd (: > /proc/<pid>/fd/<n>) or restart/signal the process to reopen; recover contents from the fd first if needed. Prevent with copytruncate or a reopen signal.

Incident pattern · iowait latency

Symptom: broad slowness, load up, top shows high %wa and low %us. First cut: iostat -x 1 — look for a device at %util ≈ 100 with high await. Confirm: attribute the I/O with pidstat -d or /proc/<pid>/io; check whether it's fsync-bound with strace -T. Usual cause: a saturated volume, an fsync-per-op pattern (database WAL, sync logging), or a noisy neighbour on shared storage. Fix: depends on the shape — batch/group commits for fsync-bound, faster/higher-IOPS storage for throughput-bound, or isolate the workload. Don't conclude "slow disk" from %wa alone.

Production · security · performanceWhat matters in production

Durability is a decision, not a default. A returned write means "in the page cache," not "on the disk." Anything that must survive a crash — a payment record, a WAL entry, a critical checkpoint — needs an fsync whose return you actually wait for, and a storage stack that honors the flush (some virtualized and consumer devices have lied about this, which is how "we fsync'd and still lost data" happens). Everything else can stay buffered for speed. Know which of your writes are which.

Watch both dimensions of "full." Monitor free blocks and free inodes; alert on both. A filesystem at 100% inodes is just as down as one at 100% blocks, and it's the one people forget. Prefer xfs for workloads that create huge numbers of small files.

File descriptors are a finite resource too. Every open file, socket, and pipe is an fd against a per-process limit (ulimit -n) and a system limit. Leaks surface as EMFILE ("too many open files") and look like a service mysteriously refusing connections while otherwise healthy — the same shape you met in Chapter 1. ls /proc/<pid>/fd | wc -l versus /proc/<pid>/limits is the check.

Common mistakes: rotating logs by rm instead of truncate-or-reopen (hello, deleted-but-open); trusting %wa as a diagnosis instead of a hint; assuming write is durable; forgetting df -i; and using du to hunt space that only df and lsof can see because it has no name.

System-design connectionWhere this reaches into architecture

The fsync cost is a load-bearing number in data-system design. It's why databases batch commits into group-fsyncs, why write-ahead logs exist (turn many random durable writes into one sequential one), and why the durability tier of a system — how many fsync'd copies before you acknowledge a write — is a core reliability trade-off you'll make again in Chapter 82 and Chapter 86. The name/inode split is exactly how container image layers and overlayfs present one merged filesystem from many read-only layers (Chapter 24). And the "buffered vs durable" line is the seed of every write-back cache, every "eventually persisted" queue, and every debate about whether an acknowledgement means "received" or "safe."

InterviewInterview questions & answers

Answer each in your head first.

30-secWhat's the difference between a filename and an inode?

The inode is the file's actual identity — its metadata (permissions, owner, size, timestamps, link count) and the pointers to its data blocks. It has no name. A filename is a separate thing: an entry in a directory that maps a human-readable name to an inode number. Several names can point to one inode (hard links), which is why the inode tracks a link count. Deleting a name just removes the directory entry and decrements that count; the file's data is freed only when the count hits zero and nothing holds it open. So "the file" and "the name of the file" are genuinely different objects, and most filesystem surprises come from conflating them.

2-minWalk me through what the kernel does for open() then read().

On open, the kernel resolves the path one component at a time, looking each name up in the dentry cache or reading the directory from disk, and checking search permission on each directory along the way, until it reaches the target inode. It then creates an open file description — a kernel object holding the current offset and the open flags — installs a pointer to it in the process's file-descriptor table at the lowest free slot, and returns that integer as the fd. On read(fd, buf, n), the fd indexes the table to the open file description, which points at the inode; the VFS asks the concrete filesystem for the bytes at the current offset. If they're warm in the page cache it's a fast copy into the user buffer; if not, the block layer issues device I/O and the process sleeps in D state until it completes. Then the kernel copies the bytes out and advances the offset in the open file description. The three-level chain — fd → open file description → inode — is the part worth stressing, because it's why dup and fork can share an offset and why two names can share one inode.

DeepDoes a successful write() mean the data is safe? Explain buffered vs direct I/O and fsync.

No. A successful write in the default buffered mode only means the bytes were copied into the page cache and the pages marked dirty; they're durable only once writeback flushes them to the device, which a crash in between will lose. To make a write durable you call fsync (or fdatasync, which skips pure-metadata updates) and wait for it to return — that forces the dirty pages to the physical device and confirms. This is why fsync-per-commit is usually a database's dominant latency cost; in a lab you'll see write take microseconds and fsync take milliseconds. Direct I/O (O_DIRECT) is the other mode: it bypasses the page cache entirely and DMAs between the device and the application's own buffer, with alignment constraints. Databases use it when they maintain their own cache and don't want the kernel double-caching the same data — they trade the kernel's help for predictable control. The mental model: buffered is fast and forgiving but not durable until fsync; direct is unbuffered and self-managed; and durability is always an explicit fsync you waited on, not a side effect of write returning.

Scenariodf -h says 40% used, but every write fails with "No space left on device." What's going on?

Two prime suspects, and I'd check both fast. First, inode exhaustion: df -i. Blocks and inodes are independent resources, and on ext4 the inode count is fixed at format time — a flood of tiny or empty files (a session directory, a mail queue, uncleaned temp files) can use every inode while blocks stay free, and then no new file can be created regardless of space. The fix is to find and delete the tiny-file swarm, and longer term add inodes or move to xfs. Second, if inodes are also fine, I'd look for a mount subtlety — for example writing to a path that's actually on a different, full filesystem, or a reserved-blocks setting — but inode exhaustion is by far the most common answer to this exact phrasing. The reflex I want is: "disk full" is always two checks, df -h and df -i, because the second one is the one everybody forgets.

Follow-upYou deleted a 40 GB log but the disk didn't free up. Why, and how do you fix it live?

Because a process still has the file open. rm removed the name and dropped the inode's link count to zero, but the open file descriptor keeps the inode and its 40 GB of blocks alive — nameless, so du can't see it, but df still counts it. I'd confirm with lsof +L1 or lsof | grep deleted, which shows the process holding a "(deleted)" file, and I'd see the descriptor under /proc/<pid>/fd. To fix it live without a restart, I truncate through that descriptor — : > /proc/<pid>/fd/<n> — which empties the file and returns the space while the process keeps running; if I need the contents first I can cp /proc/<pid>/fd/<n> to recover them. Restarting the process would also release it, but truncating the fd avoids the disruption. The real fix is to stop rotating logs with rm: use copytruncate or signal the process to reopen its log file.

RetainQuick revision

A disk is just numbered blocks; a filesystem turns them into named files, and the VFS gives every filesystem one uniform open/read/write/close interface. A file is three separate things: the name (a directory entry), the inode (identity — metadata, link count, block pointers), and the data blocks. Data is freed only when the link count is 0 and no fd holds it open — the rule behind deleted-but-open files. On the process side, fd → open file description (offset + flags) → inode, and that middle object can be shared. Writes are buffered into the page cache and durable only after an fsync you waited on; direct I/O bypasses the cache for self-caching apps. "Disk full" is two checks — df -h for blocks and df -i for inodes — and iowait is a hint that iostat and /proc/<pid>/io turn into a diagnosis.

The 10 things to remember

  1. A file is a name (directory entry), an inode (identity + block pointers), and data blocks — three separate things.
  2. Hard links are multiple names for one inode; a symlink is its own inode holding a path string.
  3. Data is freed only when link count = 0 and no open fd references the inode.
  4. The chain is fd → open file description (offset, flags) → inode; fork/dup share the description, so they share the offset.
  5. The VFS gives ext4, xfs, tmpfs, overlayfs, and NFS one uniform syscall interface.
  6. Buffered write only reaches the page cache; data is durable only after an fsync (or fdatasync) that returned.
  7. Direct I/O (O_DIRECT) bypasses the page cache — for databases that manage their own cache.
  8. "Disk full" is two checks: df -h (blocks) and df -i (inodes); ext4 fixes inode count at format time, xfs is dynamic.
  9. A deleted-but-open file keeps its blocks; find it with lsof +L1, reclaim via : > /proc/<pid>/fd/<n>, recover by copying that fd.
  10. High %wa is a hint, not a verdict — confirm with iostat -x and /proc/<pid>/io, and check whether it's fsync-bound.
