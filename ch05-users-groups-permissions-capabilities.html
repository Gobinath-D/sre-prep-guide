Users, groups, permissions & capabilities

"Just run it as root" is the most expensive shortcut in infrastructure. Linux gives you a far better deal: split root's absolute power into single-purpose keys, and hand a process only the one it needs. A web server can bind port 80 without ever being able to reformat your disks — once you know how the check actually works.

Why this exists · the problemThe problem: one machine, many users, one root

A machine is shared — by real people, by services, by a hundred processes that don't trust each other. You need to answer, on every single file access, network bind, and privileged operation: is this actor allowed to do this thing? Get it wrong one way and a log shipper reads your private keys; get it wrong the other way and a service can't open its own config.

The classic Unix answer is simple and gets you 80% of the way: every process runs as a user (a uid) belonging to one or more groups (gids), every file records an owner, a group, and a nine-bit rule of who may read, write, or execute it, and one all-powerful user — root, uid 0 — bypasses the rules entirely. That model has run the internet for fifty years.

But "root bypasses everything" is a blunt instrument, and it's the source of most privilege-related incidents. A web server needs exactly one privileged power — bind a port below 1024 — yet the old way to get it was to run the whole server as root, handing it the ability to also read every file, kill every process, load kernel modules, and wipe the disk. If that server is ever exploited, the attacker inherits all of root's power, not just the port bind. Linux fixes this with capabilities: root's monolithic power chopped into about forty independent pieces, so you can grant just CAP_NET_BIND_SERVICE and nothing else. That single idea is what makes a hardened container possible.

Key point

There are two permission systems stacked here, and you need both. The mode bits (owner/group/other × read/write/execute) govern access to files. Capabilities govern privileged operations that used to require being root — binding low ports, changing file ownership, mounting filesystems, changing the clock. "Can this process read /etc/passwd?" is a mode-bits question. "Can this process bind port 80?" is a capabilities question.

Mental model · analogyThe mental model: badges, door locks, and a ring of keys

Real-world analogy

Think of an office building. Everyone has an ID badge showing an employee number (your uid) and which departments they're in (their groups). Every door — every file — has a small posted rule: what the owner may do, what people in the door's department may do, and what everyone else may do. Those three tiers, each allowing some combination of enter/modify/use, are the mode bits.

The building superintendent (root) has traditionally carried a single master key that opens every door and overrides every posted rule. Convenient, and terrifying — lose that key and you lose the building. So the modern building replaced the master key with a ring of single-purpose keys: one that opens the low-numbered phone jacks (CAP_NET_BIND_SERVICE), one that lets you reassign who owns a door (CAP_CHOWN), one that opens the storage rooms (CAP_SYS_ADMIN). Now you hand a contractor exactly the one key their job needs, and nothing more. Those keys are capabilities.

A few special doors have quirks. A setuid door temporarily lends you the owner's badge while you're inside, so you can do one supervised privileged task (that's how the password-change room lets an ordinary employee edit the guarded shadow file). A sticky shared closet lets anyone drop things in, but only the person who put an item there can take it back out (that's /tmp). And a one-way switch on your badge — no_new_privs — can be flipped so that from that moment on, no door you walk through can ever grant you more authority than you already hold, slamming shut the setuid escalation trick for good.

ArchitectureThe permission check path

Every access decision runs the same short algorithm inside the kernel. A process carries credentials — an effective uid, an effective gid, a list of supplementary groups, and its capability sets. A file carries an owner uid, a group gid, and its mode bits. When the process asks to read, write, or execute, the kernel walks this path:

That last point is the one that bites people. The classes are checked in order and the first match wins, even when a later class would have been more permissive. If a file's owner bits say "no write" but the group bits say "write," the owner still can't write — because as the owner, only the owner bits apply to you. We'll make you feel this in the lab; it's a five-minute confusion that has cost people hours.

Why an SRE cares

Two of the most common permission incidents are opposite failures. One is EACCES where a service can't reach a file it "obviously" owns — and the real cause is a missing execute bit on a parent directory, not the file at all. The other is a service running as root "because it needs port 80," which quietly hands an attacker the whole box if that service is ever compromised. This chapter fixes both: you'll debug the first with strace in seconds, and kill the second with one capability.

Internal workingCredentials, mode bits, and capabilities

Process credentials and mode bits

  1. Every process carries credentials. Real, effective, and saved UID and GID, plus supplementary groups and capability sets. The effective uid/gid is what the kernel checks for file access; the saved set exists so a program can temporarily drop and regain privilege.
  2. Mode bits are twelve bits. Nine are three rwx triples for owner/group/other — 0644 is rw-r--r--, 0755 is rwxr-xr-x. Three more are the special bits, written as a leading octal digit: setuid (4000), setgid (2000), and sticky (1000). So 4755 is a setuid executable.
  3. Bits mean different things on directories. On a file, x means "executable." On a directory, x means "may traverse/search it" (resolve a path through it), r means "may list its names," and w means "may create or delete entries in it." You can have r without x on a directory and be able to see the names but not cd into it — a genuine source of confusion.
  4. umask sets defaults. New files are born with a base mode masked by the process's umask. The common 022 yields 644 files and 755 directories; 077 yields 600/700 (private). umask is a per-process setting daemons often set explicitly so their files aren't world-readable.

setuid, and why capabilities replaced most of it

A setuid executable runs with the effective uid of its owner, not the caller. The textbook example is /usr/bin/passwd: owned by root, setuid, so when you run it your process becomes effectively root just long enough to edit the root-owned shadow file. It's powerful and dangerous — a bug in a setuid-root program is an instant root exploit, because the whole program runs with full root power to do one small privileged thing.

Capabilities are the fix. Root's power is divided into independent units, and a process has capability sets — permitted (what it may use), effective (what's active now), inheritable/ambient (what survives an exec), and a bounding set (the ceiling of what it can ever hold). You can attach a capability to a binary as a file capability with setcap, so on exec the process gains just that one power — no setuid-root, no master key. A web server given only CAP_NET_BIND_SERVICE can bind port 80 and do nothing else privileged; compromise it and the attacker gets a port-binding power, not the disk.

The capabilities worth memorising: CAP_NET_BIND_SERVICE (low ports), CAP_CHOWN (change ownership), CAP_DAC_OVERRIDE (ignore file mode bits — nearly as good as root for reading anything), CAP_SETUID/CAP_SETGID (change identity), CAP_KILL (signal any process), CAP_NET_ADMIN (configure networking), CAP_SYS_PTRACE (attach a debugger), and CAP_SYS_ADMIN — the grab-bag that grants so much it's often called "the new root." Handing a container CAP_SYS_ADMIN undoes most of the benefit of dropping the others.

no_new_privs

no_new_privs is a one-way per-process flag (set via prctl). Once on, an execve can never grant the process more privilege than it already has — setuid bits and file capabilities are ignored for privilege-gain. It's cheap, irreversible, and inherited by children, which is why systemd (NoNewPrivileges=yes) and container runtimes (--security-opt=no-new-privileges) use it as a baseline hardening switch. It also gates unprivileged seccomp (Chapter 1) — you can't install a seccomp filter as non-root without it.

Think first: why is giving a container CAP_NET_BIND_SERVICE so much safer than running its process as root, if both let it bind port 80?

Because they grant wildly different amounts of power for the same result. Running as root gives the process the entire capability set — it can bind port 80, yes, but also read every file (CAP_DAC_OVERRIDE), change ownership, kill any process, load kernel modules, mount filesystems, and change the clock. If that process is ever exploited, the attacker inherits all of it. Granting only CAP_NET_BIND_SERVICE gives it exactly one privileged power — bind a low port — and nothing else; an exploit yields a process that can bind ports and is otherwise as constrained as any unprivileged program. Same functional outcome, dramatically smaller blast radius. That's the whole argument for least privilege, and it's why "run as non-root, add the one capability you need" is the container security default.

ComponentsThe pieces, and what each owns

  • uid / gid and the account databases. /etc/passwd (users → uid, shell, home), /etc/group (groups → members), /etc/shadow (password hashes, root-only). A process's effective uid/gid is what's checked; the real/saved pair lets it drop and regain privilege.
  • Mode bits + special bits. Nine rwx bits plus setuid/setgid/sticky. Set with chmod, owned via chown/chgrp, defaulted by umask.
  • Capability sets on a process. Permitted, effective, inheritable, ambient, and the bounding ceiling. Read them from /proc/<pid>/status (CapEff, CapPrm, CapBnd…) and decode with capsh --decode.
  • File capabilities. Capabilities attached to an executable with setcap and read with getcap; the alternative to setuid for granting one narrow power on exec.
  • no_new_privs. The irreversible "no privilege gain on exec" flag; a baseline for systemd units and containers.
  • MAC layers (context). On top of all this, SELinux or AppArmor add mandatory access control — a separate policy that can deny even when Unix permissions and capabilities would allow. When a permission failure makes no sense under Unix rules, a MAC denial (in dmesg/audit logs) is the usual explanation.

Data flowFollowing a non-root server binding port 80

Trace what happens when a web server tries to listen on port 80, first the wrong way and then the right way:

  1. The process calls bind() on port 80. Ports below 1024 are privileged, so the kernel doesn't just check "are you root" — it checks whether the process holds CAP_NET_BIND_SERVICE in its effective set.
  2. The anti-pattern: run the whole server as root. Its effective uid is 0, so it has the full capability set, including CAP_NET_BIND_SERVICE — the bind succeeds, but the process can now also do everything else root can. Some servers then setuid to an unprivileged user after binding, which helps but still means all that code ran as root during startup.
  3. The right way: give the binary the one capability with setcap 'cap_net_bind_service=+ep' ./server. Now a completely non-root user runs it; on exec the process picks up CAP_NET_BIND_SERVICE in its permitted and effective sets, and nothing else.
  4. The bind() capability check passes — the process has exactly the key for this door. The server listens on port 80 as an unprivileged user with no other privileged powers.
  5. If the capability is missing, the kernel returns EACCES ("Permission denied") from bind() — the exact error you'll debug in the lab.

Lab 1Build — identities and mode bitsBuild

See who you are, make a user, and read/change file ownership and mode.

bash
id                                  # uid, gid, and all your groups
useradd -m -s /bin/bash app         # a normal, unprivileged user
echo "secret config" > /etc/app.conf
chown app:app /etc/app.conf
chmod 640 /etc/app.conf             # owner rw, group r, other nothing
ls -l /etc/app.conf
Outputuid=0(root) gid=0(root) groups=0(root) -rw-r----- 1 app app 14 ... /etc/app.conf

Read the mode string left to right: type (- file), then owner rw-, group r--, other ---. That's 640. Now feel the classes by switching users:

bash
useradd -m teammate
usermod -aG app teammate            # put teammate in the 'app' group
sudo -u app      cat /etc/app.conf   # owner: allowed (rw-)
sudo -u teammate cat /etc/app.conf   # group member: allowed (r--)
useradd -m stranger
sudo -u stranger cat /etc/app.conf   # other: DENIED (---)
Outputsecret config secret config cat: /etc/app.conf: Permission denied

Owner and group member read it; the stranger gets Permission denied because the "other" class has no read bit. Three identities, three different outcomes, one file.

Lab 2Understand — the first-match rule, and setuidUnderstand

Now the counterintuitive part: a file where "other" is more permissive than "group," proving that the first matching class wins. Make a file owned by app:app with mode 604 — owner rw, group ---, other r--:

bash
echo data > /tmp/weird
chown app:app /tmp/weird
chmod 604 /tmp/weird              # owner rw-, group ---, other r--
ls -l /tmp/weird
sudo -u teammate cat /tmp/weird   # teammate is in group 'app' — what happens?
sudo -u stranger cat /tmp/weird   # stranger is 'other' — what happens?
Output-rw----r-- 1 app app 5 ... /tmp/weird cat: /tmp/weird: Permission denied # teammate (GROUP class) — DENIED data # stranger (OTHER class) — ALLOWED

The group member is denied while a stranger is allowed. Because teammate matches the group class first, only the group bits (---) apply — the more-permissive "other" bits never get consulted. This is the rule the diagram warned about, and now you've watched it happen. Next, setuid in the wild:

bash
ls -l /usr/bin/passwd            # the classic setuid-root binary
stat -c '%A %U' /usr/bin/passwd
Output-rwsr-xr-x 1 root root ... /usr/bin/passwd -rwsr-xr-x root

The s where the owner's x would be is the setuid bit. That's why an ordinary user running passwd can edit the root-owned shadow file: for the duration of that program, their effective uid becomes root's. Powerful, and exactly the pattern capabilities exist to shrink.

Think first: a file is -rw-r--r-- and owned by you, yet you get EACCES opening it by its full path. How is that possible?

Because path access needs the execute (search) bit on every directory along the way, and one of the parents is denying you. Reading /data/private/app.conf requires x on /, /data, and /data/private — if /data/private is mode 700 owned by someone else, you can't traverse into it, so you never even reach the file whose own bits look fine. The file's permissions are innocent; a parent directory is the wall. This is the single most common "but I own the file!" confusion, and namei -l /data/private/app.conf (which prints the mode of every component) or an strace showing which openat/stat returns EACCES pins it immediately.

Lab 3Break — an EACCES with a hidden causeBreak

A service can't read a config file it owns. Reproduce the exact trap from the recall prompt, then debug it the way you would in production — don't guess, let strace tell you.

bash
mkdir -p /data/private
echo "db_password=hunter2" > /data/private/app.conf
chown app:app /data/private/app.conf
chmod 644 /data/private/app.conf     # the FILE is world-readable...
chmod 700 /data/private              # ...but the DIRECTORY is locked to its owner
chown root:root /data/private        # owned by root, so 'app' can't traverse it

# 'app' tries to read its own file and fails. Why?
sudo -u app cat /data/private/app.conf
Outputcat: /data/private/app.conf: Permission denied

The file is 644 and owned by app, so the naive conclusion — "fix the file's permissions" — is wrong. Find the truth before revealing:

bash
sudo -u app strace -f -e trace=openat,stat,newfstatat cat /data/private/app.conf 2>&1 | grep -i eacces
namei -l /data/private/app.conf      # prints the mode of EVERY path component
Reveal the cause and the fix

strace shows the EACCES lands while resolving the path, not on the file's own open, and namei -l shows the culprit component:

Outputopenat(AT_FDCWD, "/data/private/app.conf", O_RDONLY) = -1 EACCES (Permission denied) f: /data/private/app.conf drwxr-xr-x root root / drwxr-xr-x root root data drwx------ root root private # <-- 700, root-owned: 'app' cannot traverse -rw-r--r-- app app app.conf # the file itself is fine

/data/private is mode 700 owned by root, so app lacks the execute (search) bit needed to traverse into it — the request dies before the file's own permissions are ever consulted. The fix is on the directory, not the file: give app traversal, e.g. chmod 750 /data/private && chgrp app /data/private (group execute), or make the directory owned appropriately. The lesson is a reflex: on any EACCES, strace to see which syscall on which path failed, and check the whole directory chain with namei -l before touching the file.

Lab 4Troubleshoot — bind port 80 as a non-root userTroubleshoot

The run-as-root anti-pattern, and its cure. Compile a minimal server that binds port 80, then run it as an unprivileged user.

bash
cat > /tmp/bind80.c <<'EOF'
#include <stdio.h>
#include <netinet/in.h>
#include <sys/socket.h>
#include <unistd.h>
int main(void){
  int s = socket(AF_INET, SOCK_STREAM, 0);
  struct sockaddr_in a = { .sin_family=AF_INET, .sin_port=htons(80) };
  if (bind(s, (struct sockaddr*)&a, sizeof a) < 0){ perror("bind"); return 1; }
  printf("bound port 80 as uid %d — listening\n", getuid());
  listen(s, 16); pause(); return 0;
}
EOF
gcc -o /tmp/bind80 /tmp/bind80.c
sysctl net.ipv4.ip_unprivileged_port_start   # confirm it's 1024 (privileged <1024)

# Run as the unprivileged 'app' user — this should fail:
sudo -u app /tmp/bind80
Outputnet.ipv4.ip_unprivileged_port_start = 1024 bind: Permission denied

EACCES — the unprivileged user can't bind a low port. You could "fix" this by running as root. Don't. Grant the one capability the job needs and run it unprivileged. Work out the command, then reveal.

Reveal the capability fix and how to verify it

Attach CAP_NET_BIND_SERVICE to the binary as a file capability, then run it as the non-root user:

bash
setcap 'cap_net_bind_service=+ep' /tmp/bind80   # +ep = permitted + effective
getcap /tmp/bind80                              # confirm the capability is attached
sudo -u app /tmp/bind80                         # now it works, as an unprivileged user
Output/tmp/bind80 cap_net_bind_service=ep bound port 80 as uid 1001 — listening

Uid 1001 — not root — bound port 80. The process holds exactly one privileged power and nothing else: no ability to read arbitrary files, kill processes, or touch the disk. Prove it by inspecting the running process's capability sets:

bash
PID=$(pgrep -n bind80)
grep -E 'Cap(Eff|Prm|Bnd)' /proc/$PID/status
capsh --decode=$(grep CapEff /proc/$PID/status | awk '{print $2}')
OutputCapEff: 0000000000000400 cap_net_bind_service

The effective set decodes to precisely cap_net_bind_service. That's the model for every service that needs a low port: run non-root, grant the one capability, verify with getcap/capsh. In Kubernetes you express the same thing in the pod's securityContext.capabilities.add — the container image doesn't even need setcap.

Lab 5Production challenge — audit and drop a container's privilegesSenior challenge

You inherit a service that runs as root in its container "because it always has." Your job: find out what privileges it actually holds, then run it with the least it needs. First, audit a default container.

bash
# In a DEFAULT container, look at what root here can do:
grep -E 'Cap(Eff|Bnd)|NoNewPrivs' /proc/self/status
capsh --decode=$(grep CapEff /proc/self/status | awk '{print $2}')
Output (Docker defaults)CapEff: 00000000a80425fb NoNewPrivs: 0 cap_chown, cap_dac_override, cap_fowner, cap_kill, cap_setgid, cap_setuid, cap_net_bind_service, cap_net_raw, cap_sys_chroot, ...

That's a lot of keys on the ring — chown anything, override file permissions, change identity, kill processes. The senior question: how do you shrink this to nothing-but-what's-needed, and verify it? Design the run, then reveal.

Reveal the least-privilege recipe and verification

Run non-root, drop every capability, add back only the one you need, forbid privilege escalation, and make the root filesystem read-only:

bash
docker run --rm -it \
  --user 1000:1000 \
  --cap-drop=ALL \
  --cap-add=NET_BIND_SERVICE \
  --security-opt=no-new-privileges \
  --read-only \
  ubuntu:24.04 bash

# Verify from inside: effective caps should be just one, NoNewPrivs on.
grep -E 'Uid|Cap(Eff|Bnd)|NoNewPrivs' /proc/self/status
capsh --decode=$(grep CapEff /proc/self/status | awk '{print $2}')
OutputUid: 1000 1000 1000 1000 CapEff: 0000000000000400 CapBnd: 0000000000000400 NoNewPrivs: 1 cap_net_bind_service

Now the container runs as uid 1000, its bounding set is capped at a single capability (so it can never gain more, even via a setuid binary), no_new_privs is on, and the root filesystem is read-only. Compromising this process yields almost nothing. In Kubernetes this is a securityContext: runAsNonRoot: true, capabilities: {drop: ["ALL"], add: ["NET_BIND_SERVICE"]}, allowPrivilegeEscalation: false, readOnlyRootFilesystem: true. The audit-then-minimise loop — read CapEff/CapBnd from /proc/self/status, decode with capsh, drop what's unused — is exactly the container-hardening work we go deep on in Chapter 27.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · EACCES that isn't about the file

Symptom: a service logs "permission denied" opening a file it owns with sensible mode bits. First cut: strace -f -e openat,stat to see which syscall on which exact path returns EACCES. Confirm: namei -l <path> to print every directory's mode — look for a parent missing the execute/search bit for your uid. Usual cause: a locked-down parent directory (mode 700, wrong owner), not the file. Secondary suspects: the process's effective uid isn't what you think (it dropped privileges), or a MAC layer (SELinux/AppArmor) denial visible in dmesg/audit. Fix: grant directory traversal or correct ownership; don't chmod the file.

Incident pattern · the run-as-root anti-pattern

Symptom: a service runs as root "because it needs a low port / to write somewhere / it was easier." Why it's a problem: the process holds the full capability set, so any RCE or path-traversal bug becomes full host compromise — read every secret, tamper with any file, and (in a container) a much shorter path to escape. First cut: check the running uid and CapEff; ask what privileged operation it actually needs. Fix: run as a dedicated non-root user and grant only the specific capability (usually CAP_NET_BIND_SERVICE), or move the low-port need behind a proxy/load balancer. The cost of fixing this is minutes; the cost of not fixing it is the whole box.

Incident pattern · over-privileged containers

Symptom: containers run as root with Docker's full default capability set and no no_new_privs — or worse, --privileged or CAP_SYS_ADMIN. First cut: capsh --decode of /proc/1/status's CapEff inside the container; inspect the pod's securityContext. Usual cause: copy-pasted run commands and images that assume root. Fix: runAsNonRoot, drop: ["ALL"] then add only what's needed, allowPrivilegeEscalation: false, read-only rootfs. Treat CAP_SYS_ADMIN and --privileged as "this is basically root on the host" — because they are. Full treatment in Chapter 27.

Production · security · performanceWhat matters in production

Least privilege is a default, not a project. Every service should run as a dedicated non-root user with only the capabilities it provably needs. This is the single highest-impact security control you own as an SRE, and it costs almost nothing: a user, a capability or two, no_new_privs, and a read-only root filesystem. The habit to build is "start from zero privilege and add back the minimum," never "start as root and hope."

Know the dangerous grants. CAP_SYS_ADMIN, CAP_DAC_OVERRIDE, CAP_SETUID, and --privileged each hand back most of what dropping capabilities bought you. If a workload "needs" CAP_SYS_ADMIN, that's a design smell worth pushing on — it's usually one specific operation (a mount, a sysctl) that has a narrower solution.

Permissions on secrets are load-bearing. A key file that's 644 instead of 600 is readable by every process on the box. Set a tight umask for daemons, keep secret material 600/owner-only, and remember that group membership is transitive through supplementary groups — adding a service account to a broad group can silently widen what it can read.

Common mistakes: chmod-ing a file when the real block is a parent directory's missing x; running as root for one low port; leaving Docker's default capabilities on a workload that needs none of them; confusing "readable directory" (r) with "traversable directory" (x); and forgetting that SELinux/AppArmor can deny even when Unix says yes.

System-design connectionWhere this reaches into architecture

The principle here — grant the minimum authority for the job, and contain the blast radius when something is compromised — is the same principle that reappears at every layer of a platform. It's IAM roles scoped to one action on one resource (Chapter 54), it's IRSA giving a pod exactly one AWS role instead of node-wide credentials (Chapter 55), it's Kubernetes RBAC and Pod Security admission (Chapter 39), and it's mutual-TLS service identity in a mesh (Chapter 69). Capabilities are where you first meet it, on a single host: the realisation that "all or nothing" privilege is a design failure, and that safety comes from decomposing power into the smallest useful pieces and handing out exactly one. Every security review you'll sit in is, at its core, someone asking "why does this need that permission?" — and this chapter is where you learn to answer.

InterviewInterview questions & answers

Answer each in your head first.

30-secWhat does mode 0755 mean, and how is it different from 0644?

0755 is three permission triples: owner rwx (read, write, execute), group r-x, and other r-x. So the owner can do everything, and everyone else can read and execute but not modify — typical for an executable or a directory you want others to traverse. 0644 is owner rw-, group r--, other r--: readable by all, writable only by the owner, executable by none — typical for a regular data or config file. The leading zero is the special-bits slot (setuid/setgid/sticky), zero here meaning none set. On a directory the execute bit means "may traverse," which is why data files are usually 644 but directories are 755.

2-minWalk me through how the kernel decides whether a process may read a file.

The process carries an effective uid, effective gid, and a set of supplementary groups; the file carries an owner uid, a group gid, and its mode bits. The kernel first checks the privileged path: if the process is root or holds the relevant capability — CAP_DAC_OVERRIDE for read/write, CAP_DAC_READ_SEARCH for read and directory search — it's allowed outright. Otherwise it selects exactly one class by the first match: if the effective uid equals the file's owner, it uses the owner bits; else if the file's group is among the process's groups, it uses the group bits; else it uses the other bits. Then it checks whether that chosen class has the requested bit set — read, in this case — and returns success or EACCES. The subtlety worth stating is that the first matching class is the only one consulted, so a more-permissive group or other tier can't help someone who matches an earlier, stricter class. And path resolution needs the execute/search bit on every parent directory, which is why an EACCES is often really a locked parent directory rather than the file itself.

DeepWhat are Linux capabilities, and why are they better than setuid-root?

Capabilities split root's historically monolithic power into about forty independent units — bind low ports (CAP_NET_BIND_SERVICE), change ownership (CAP_CHOWN), bypass file permissions (CAP_DAC_OVERRIDE), configure networking (CAP_NET_ADMIN), and so on. A process has several capability sets: permitted (what it may use), effective (what's active), inheritable/ambient (what survives an exec), and a bounding set that caps what it can ever hold. The advantage over setuid-root is blast radius. A setuid-root program runs the entire program with full root power to accomplish one small privileged task, so any bug in it is a total root compromise. With capabilities you attach just the one power the program needs — as a file capability via setcap, or granted by a container runtime — and the process runs otherwise unprivileged, often as a non-root uid. A web server given only CAP_NET_BIND_SERVICE can bind port 80 and do nothing else privileged; an exploit yields a port-binding power, not the disk and every secret. Pair that with no_new_privs, which makes exec unable to grant new privilege, and a tight bounding set, and you've decomposed "all of root" into "exactly this one thing," which is the entire point of container and service hardening. The one caveat is CAP_SYS_ADMIN, which is so broad it's effectively root — granting it undoes most of the benefit.

ScenarioA service owned by its user, with a 644 config, gets EACCES reading it. How do you debug?

I wouldn't touch the file's permissions, because a 644 file owned by the running user should be readable — the failure is almost certainly elsewhere. I'd strace -f -e trace=openat,stat the service (or run its exact command under strace as the same user) to see precisely which syscall on which path returns EACCES; that usually shows the denial happening during path resolution, not on the file's own open. Then namei -l on the full path prints the mode and owner of every directory component, which nearly always reveals a parent directory missing the execute/search bit for that uid — a 700 directory owned by someone else is the classic. If the directory chain is clean, I'd verify the process's effective uid is actually what I think (it may have dropped privileges to a different user than expected), and I'd check dmesg or the audit log for an SELinux/AppArmor denial, since a MAC layer can refuse even when Unix permissions allow. The fix follows the finding: fix the directory traversal, correct the runtime user, or adjust the MAC policy — but I let strace and namei tell me which before changing anything.

Follow-upHow do you run a container with least privilege, and why does it matter?

I run it as a non-root user (runAsNonRoot / --user), drop all capabilities and add back only the ones the workload provably needs (--cap-drop=ALL --cap-add=NET_BIND_SERVICE, or the pod's securityContext.capabilities), set no_new_privs (allowPrivilegeEscalation: false) so a setuid binary inside can't escalate, and make the root filesystem read-only. I verify by decoding /proc/1/status's CapEff and CapBnd with capsh from inside the container. It matters because a container is just a process on the shared host kernel — the isolation is capabilities plus namespaces plus seccomp, not a second kernel — so an over-privileged container is a short hop from host compromise, especially anything with CAP_SYS_ADMIN or --privileged. Least privilege shrinks what an attacker gets from a successful exploit down to almost nothing, and it's cheap to apply, so it's a baseline I'd enforce with admission policy rather than leave to each team's discretion.

RetainQuick revision

Linux stacks two permission systems. Mode bits govern file access: owner/group/other × read/write/execute, plus setuid/setgid/sticky, defaulted by umask, and read straight off ls -l. The kernel picks the first matching class — owner, then group, then other — and checks only that class, which is why a permissive group/other tier can't rescue a stricter owner match, and why path access needs execute on every parent directory. The second system is capabilities: root's power split into ~40 independent units, so you grant CAP_NET_BIND_SERVICE to bind port 80 without any of root's other powers. Attach capabilities to binaries with setcap/getcap, read a process's sets from /proc/<pid>/status and decode with capsh, and lock the door behind you with no_new_privs. The production reflex: run non-root, drop all capabilities, add back the minimum — and on any EACCES, let strace and namei -l name the real cause before you change a thing.

The 10 things to remember

  1. A process runs as a uid with groups; a file has an owner, a group, and nine rwx mode bits plus setuid/setgid/sticky.
  2. The kernel uses the first matching class — owner, then group, then other — and checks only that class's bits.
  3. On a directory, x means traverse/search, r means list names, w means create/delete entries — not the same as on a file.
  4. Path access needs the execute bit on every parent directory; a locked parent is the usual hidden EACCES.
  5. setuid runs a program as its owner's uid (that's how passwd edits shadow); powerful and a big attack surface.
  6. Capabilities split root into ~40 units, so you grant one power (e.g. CAP_NET_BIND_SERVICE) instead of all of root.
  7. Use setcap/getcap for file capabilities; read a process's CapEff/CapBnd from /proc and decode with capsh.
  8. no_new_privs makes exec unable to grant new privilege — a cheap, irreversible hardening default.
  9. Debug EACCES with strace (which syscall/path/errno) and namei -l (every directory's mode) — don't guess.
  10. Least privilege in containers: run non-root, drop ALL caps, add only what's needed, no_new_privs, read-only rootfs — beware CAP_SYS_ADMIN.
