systemd, journald, cron & the service lifecycle

On nearly every Linux box you'll ever touch, PID 1 is systemd. It decides what starts and in what order, keeps services alive when they crash, tracks every process a service spawns, and funnels all their logs into one place you can query. Learn its vocabulary and "the service won't start" stops being a mystery and becomes two commands.

Start: Beginner→→→End: Staff-level ~40 min read · Linux lab (Docker)

By the end of this chapter you can

  • Explain what a unit is, and how Requires/Wants/After and targets build the dependency graph.
  • Choose the right Type= for a service and say why Type=notify gives correct ordering.
  • Write, enable, and supervise a real unit — with a restart policy and resource limits.
  • Read the journal like a pro: journalctl -u, -b, -p, --since, -f.
  • Diagnose a unit that won't start and a crash-restart loop, including "start request repeated too quickly."
  • Replace a fragile cron job with a systemd timer that catches up, logs, and is resource-limited.

Why this exists · the problemThe problem: booting and babysitting a machine's services

A server boots and has to bring up dozens of things — networking, the clock, mounts, a database, your app, a log shipper — in an order that respects who needs whom. Then it has to keep them running: notice when a daemon crashes and restart it, know which processes belong to which service so it can stop all of them cleanly, capture every service's output so you can read it later, and run scheduled jobs. That's a lot of jobs, and for decades the tooling for it was thin.

The old way (SysV init) was a pile of shell scripts run in a fixed, hand-numbered sequence. It had no real dependency model — you encoded order by naming scripts S10foo, S20bar and hoping. It had no supervision — a daemon that crashed simply stayed dead unless some other tool watched it. It had no idea which processes belonged to a service, so stopping one could leak orphaned children. And logs went wherever each script felt like writing them.

systemd replaced all of that with a declarative model. You describe each service and its dependencies in a unit file; systemd builds a dependency graph, starts independent things in parallel, and supervises everything it launches. Crucially, it puts each service in its own cgroup, so it always knows the exact set of processes a service owns — which fixes the leaked-children problem for good. It captures all output into one queryable log via journald, and it runs scheduled work with timers that are smarter than cron. It's PID 1 on Debian, Ubuntu, RHEL, Fedora, SUSE, Amazon Linux — basically everywhere.

Key point

systemd's superpower is the cgroup per service. Because every process a unit spawns — and every child of those — stays in the unit's cgroup, systemd can answer "what belongs to this service?" exactly, stop all of it with no leaks, attribute CPU and memory to it, and enforce limits on it. This is the same cgroup machinery Kubernetes uses for pods (Chapter 23); a systemd service and a container are cousins.

Mental model · analogyThe mental model: the site operations manager

Real-world analogy

Picture a large construction site with one operations manager holding the master schedule — that's systemd, and it never leaves. Every job on site comes with a work order (a unit) that says what to do and what must be done first: "pour the foundation" lists "site cleared" as a prerequisite. The manager reads all the work orders, works out the order from those stated dependencies rather than a fixed list, and runs everything that can run in parallel at once.

The schedule has named milestones — "site ready for framing," "building ready for tenants" — and the manager drives toward the day's goal milestone. Those are targets. Each crew gets its own marked-off zone so the manager always knows exactly which workers belong to which job; if a crew walks off the site, the manager can send the whole crew home cleanly or call them straight back (the restart policy) — but if a crew keeps quitting every five minutes, the manager stops re-hiring them and flags the job as failed (the restart rate limit).

Every crew's radio chatter is recorded, timestamped and labelled with who spoke, in one site logbook — that's journald, and it's why you don't hunt through twenty scattered notebooks. And recurring maintenance — "test the generators every Tuesday at 2 a.m." — goes on a maintenance calendar (a timer). Unlike the old paper calendar (cron), if the site was closed on Tuesday, the manager still runs the test as soon as it reopens.

ArchitectureUnits, targets, cgroups, and the journal

systemd is PID 1, and everything it manages is a unit. Units come in types you'll name daily: .service (a process to run), .target (a named group/milestone), .timer (a schedule that triggers a service), .socket (a listening socket that can start a service on demand), .mount (a filesystem mount), and .slice (a node in the cgroup resource tree). Units declare dependencies, and systemd assembles them into one graph it drives toward a goal target at boot.

Two independent axes control startup, and mixing them up is the most common unit-file bug. Requirement dependencies say what to pull in: Requires= is hard (if the dependency fails, this unit fails too), Wants= is soft (start it, but don't fail if it doesn't). Ordering dependencies say what goes first: After=/Before=. These are orthogonal — Requires=db.service does not mean "start db first"; you also need After=db.service or the two race. Targets like multi-user.target are just units with no process, used as synchronisation points and boot goals (roughly the modern replacement for SysV runlevels).

Why an SRE cares

Almost every "the service is down" ticket is answered by two commands: systemctl status <unit> (is it active, failed, or restarting, what's the main PID, what's the cgroup, and the last few log lines) and journalctl -u <unit> (the full story). If you can read a status block — Active: failed (Result: exit-code), code=exited, status=203/EXEC, "start request repeated too quickly" — you've diagnosed the top three service incidents before you've finished your coffee.

Internal workingThe lifecycle of a service, start to stop

  1. systemd loads units. Unit files are read from a search path with clear precedence: /etc/systemd/system (your overrides) beats /run/systemd/system beats /usr/lib/systemd/system (package defaults). After editing any unit file you must systemctl daemon-reload so systemd re-reads them.
  2. It builds a transaction. On systemctl start web.service (or at boot toward the default target), systemd gathers everything pulled in by Requires/Wants and orders it by After/Before, then starts independent units in parallel.
  3. It creates the cgroup and runs ExecStart. The service gets its own cgroup under system.slice, and systemd forks the command. When systemd considers the unit "started" depends on Type= — this is the part people get wrong:
    • Type=simple (default): considered up the moment it's forked — even if the app isn't ready yet.
    • Type=exec: up once execve succeeds (catches a bad binary path immediately).
    • Type=forking: for old-style daemons that fork and let the parent exit; systemd waits for the parent to exit (best paired with a PIDFile=).
    • Type=notify: the service calls sd_notify(READY=1) when it's genuinely ready to serve; systemd waits for that. This is what makes "start web only after the DB is truly accepting connections" actually work.
    • Type=oneshot: runs to completion, for setup tasks; add RemainAfterExit=yes to have it count as active afterward.
  4. It supervises via the cgroup. systemd knows every PID in the unit. When the main process exits, the Restart= policy decides what happens — no (default), on-failure (nonzero exit or signal), always, on-abnormal, and others — after a RestartSec delay. A rate limiter (StartLimitBurst starts within StartLimitIntervalSec, default 5 in 10s) stops infinite tight loops: exceed it and the unit goes to failed with "start request repeated too quickly."
  5. Stopping is clean because of the cgroup. ExecStop (or a SIGTERM to the whole cgroup), then wait TimeoutStopSec, then SIGKILL anything still alive. Because systemd tracks the cgroup, stray children get killed too — no leaked processes, the exact problem SysV had.
  6. All output goes to the journal. The service's stdout/stderr are captured by journald and stored as structured records tagged with the unit name, PID, uid, timestamps, and boot ID — queryable later with journalctl, no matter where or whether the app wrote a log file.

One more mechanism worth knowing: socket activation. A .socket unit can hold a listening socket and start its service only on the first connection, passing the ready socket in. It's how systemd starts rarely-used services on demand and how it can begin queuing connections before the service is even up.

Think first: your web service starts "successfully" at boot but the first requests fail because the database isn't ready yet — even though you set After=postgresql.service. What's wrong?

After= only orders when systemd starts the database process, not when the database is ready to accept connections. With the database running as Type=simple or Type=forking, systemd marks it "started" long before Postgres has finished recovery and opened its socket — so your web service, correctly ordered after it, still races ahead of actual readiness. The real fix is a proper readiness signal: run the dependency as Type=notify so it reports ready only when it truly is (Postgres and many daemons support this), and keep After=. Ordering plus a real readiness protocol is what makes the dependency meaningful; ordering alone just sequences the fork. As a fallback, an application-level retry/wait-for-dependency loop covers daemons that don't speak notify.

ComponentsThe pieces, and what each owns

  • Unit files & sections. [Unit] (Description, After, Requires, Wants), [Service] (ExecStart, Type, Restart, User, environment, sandboxing, resource limits), and [Install] (WantedBy — what enable hooks the unit into). Edit under /etc/systemd/system; prefer drop-ins (systemctl edit) over editing package files.
  • Dependency directives. Requires (hard), Wants (soft), After/Before (ordering only), BindsTo (stop with the dependency), Conflicts (mutually exclusive).
  • Targets. Named groups and boot goals: multi-user.target (server default), graphical.target, network-online.target (actually reachable) vs network.target (config applied). systemctl get-default shows the boot goal.
  • Slices & resource control. The cgroup tree (system.slice, user.slice). Directives like MemoryMax=, CPUQuota=, and TasksMax= compile straight to cgroup v2 limits (Chapter 23) — resource control for plain services, no container required.
  • Sandboxing directives. User=/DynamicUser=, NoNewPrivileges=, ProtectSystem=, ProtectHome=, PrivateTmp=, CapabilityBoundingSet= — the Chapter 5 primitives (users, capabilities, no_new_privs) exposed as one-line unit settings.
  • journald. The structured log for every unit. Volatile in /run/log/journal by default; persistent once /var/log/journal exists (or Storage=persistent). Query with journalctl; it can forward to syslog.
  • Timers vs cron. A .timer triggers a .service on a schedule (OnCalendar=, OnUnitActiveSec=), with Persistent=true for catch-up and RandomizedDelaySec= to spread a fleet. Classic cron (crontab -e) still exists and is fine for simple, dependency-free jobs.

Data flowFollowing systemctl start web.service

  1. You run systemctl start web.service. systemctl is just a client; it sends the request to systemd (PID 1) over the system D-Bus.
  2. systemd resolves the unit's dependencies — it needs the database, so it ensures postgresql.service is started first (Requires + After), waiting for real readiness if that unit is Type=notify.
  3. systemd creates system.slice/web.service as a cgroup, applies the unit's User=, capability, and MemoryMax= settings, and forks ExecStart inside it.
  4. Per Type=, systemd decides when "started" is true and marks the unit active. The app's stdout/stderr stream into journald, tagged with the unit.
  5. The app serves traffic. If it crashes, Restart=on-failure restarts it after RestartSec — unless it's crashed too many times too fast, in which case the rate limiter parks it in failed.
  6. You run systemctl status web.service and see: active state, main PID, the full cgroup tree of worker processes, and the last ten journal lines — the whole health picture in one screen.

Hands-onLabs — build, understand, break, troubleshoot

Most containers don't run systemd — the app is PID 1 (Chapter 2). To practice systemd itself, boot it as PID 1 in a privileged container with cgroup v2 (the --privileged and cgroup mount let systemd manage the cgroup tree):

bash
docker run -d --name sysd --privileged --cgroupns=host \
  -v /sys/fs/cgroup:/sys/fs/cgroup:rw ubuntu:24.04 \
  bash -c 'apt-get update -qq && apt-get install -y -qq systemd systemd-sysv >/dev/null && exec /sbin/init'

sleep 20                          # let it boot
docker exec -it sysd bash         # get a shell inside the running system
systemctl is-system-running       # 'running' or 'degraded' — either is fine here
Lab 1Build — write, enable, and supervise a unitBuild

Create a tiny service and hand it to systemd. First the program it runs, then the unit.

bash
cat > /usr/local/bin/heartbeat.sh <<'EOF'
#!/bin/bash
while true; do echo "heartbeat $(date +%T) pid=$$"; sleep 3; done
EOF
chmod +x /usr/local/bin/heartbeat.sh

cat > /etc/systemd/system/heartbeat.service <<'EOF'
[Unit]
Description=Demo heartbeat service
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/local/bin/heartbeat.sh
Restart=on-failure
RestartSec=2
NoNewPrivileges=yes
MemoryMax=64M

[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload           # re-read unit files after any edit
systemctl enable --now heartbeat  # enable (start at boot) + start now
systemctl status heartbeat
Output (trimmed)● heartbeat.service - Demo heartbeat service Loaded: loaded (/etc/systemd/system/heartbeat.service; enabled; ...) Active: active (running) since ...; 5s ago Main PID: 812 (heartbeat.sh) Memory: 512.0K (max: 64.0M) CGroup: /system.slice/heartbeat.service ├─812 /bin/bash /usr/local/bin/heartbeat.sh └─826 sleep 3

Read that status block — it's the single most useful screen in Linux service management. Active: active (running), the main PID, the MemoryMax you set, and the cgroup tree showing both the script and its sleep child. systemd owns that whole subtree. Confirm with systemctl cat heartbeat (prints the effective unit file, including any drop-ins).

Lab 2Understand — read the journal and the dependency graphUnderstand

Everything the service prints went to the journal, tagged by unit. Query it the ways you'll actually use.

bash
journalctl -u heartbeat --no-pager | tail          # this unit's logs
journalctl -u heartbeat -f                          # follow live (Ctrl-C to stop)
journalctl -u heartbeat --since "2 min ago"         # time window
journalctl -b -p err                                # errors this boot, all units
OutputJun 03 10:22:04 sysd heartbeat.sh[812]: heartbeat 10:22:04 pid=812 Jun 03 10:22:07 sysd heartbeat.sh[812]: heartbeat 10:22:07 pid=812

No log file, no hunting — the unit name is the query key. Now look at ordering and the resource tree:

bash
systemctl list-dependencies heartbeat        # what it pulls in / orders after
systemctl show -p Type,Restart,WantedBy,MemoryMax heartbeat   # resolved properties
systemd-cgls /system.slice/heartbeat.service # the cgroup, i.e. every process it owns

systemctl show prints the fully-resolved values (not just what's in the file), which is how you confirm what systemd actually thinks a setting is. This trio — status, cat, show — answers "what is this unit configured to do and what is it doing right now."

Lab 3Break — a unit that refuses to startBreak

Introduce the most common unit bug — an ExecStart that can't be executed — and diagnose it the way you would a real failing service. Don't assume; read the status and the journal.

bash
cat > /etc/systemd/system/broken.service <<'EOF'
[Unit]
Description=A service that won't start
[Service]
Type=simple
ExecStart=/usr/local/bin/does-not-exist --serve
[Install]
WantedBy=multi-user.target
EOF
systemctl daemon-reload
systemctl start broken            # this fails
systemctl status broken --no-pager
Output× broken.service - A service that won't start Active: failed (Result: exit-code) since ... Process: 901 ExecStart=/usr/local/bin/does-not-exist --serve (code=exited, status=203/EXEC) ...

Active: failed and status=203/EXEC. Before the reveal: what does 203/EXEC tell you specifically, and where would you look to confirm?

Reveal what the exit code means and how to fix it

203/EXEC is systemd's code for "I could not execve the ExecStart command" — the binary doesn't exist, isn't on the given path, isn't executable, or has a bad interpreter line. It's distinct from the program running and exiting nonzero (which would show status=1 or similar). The journal spells it out:

bash
journalctl -u broken -n 20 --no-pager
Outputsystemd[1]: broken.service: Failed to locate executable /usr/local/bin/does-not-exist: No such file or directory systemd[1]: broken.service: Failed at step EXEC spawning /usr/local/bin/does-not-exist: No such file or directory

The fix is exactly what the message says: correct the path, ensure the file exists and is chmod +x, and use an absolute path (systemd doesn't search $PATH for ExecStart). The neighbouring exit codes are worth recognising too: 200/CHDIR (bad WorkingDirectory=), 217/USER (the User= doesn't exist), 226/NAMESPACE (a sandboxing directive couldn't be applied). Every one of them is printed in the journal — status tells you it failed, journalctl -xe tells you why.

Lab 4Troubleshoot — the crash-restart loopTroubleshoot

A service that keeps dying and restarting is a classic 2 a.m. page. Build one — an app that exits nonzero immediately, with Restart=always — and watch systemd's rate limiter kick in.

bash
cat > /usr/local/bin/flaky.sh <<'EOF'
#!/bin/bash
echo "starting up..."
sleep 1
echo "config error: cannot connect to db, exiting" >&2
exit 1
EOF
chmod +x /usr/local/bin/flaky.sh

cat > /etc/systemd/system/flaky.service <<'EOF'
[Service]
ExecStart=/usr/local/bin/flaky.sh
Restart=always
RestartSec=1
EOF
systemctl daemon-reload
systemctl start flaky
sleep 12
systemctl status flaky --no-pager
Output× flaky.service Active: failed (Result: start-limit-hit) since ... ... systemd[1]: flaky.service: Start request repeated too quickly. systemd[1]: flaky.service: Failed with result 'start-limit-hit'.

It restarted a few times, then systemd gave up with start-limit-hit. Two questions to answer before revealing: why did systemd stop restarting, and — more importantly — what's the actual bug, and where is it recorded?

Reveal the mechanism, the root cause, and the fix

systemd stopped because of the start rate limiter: by default, more than StartLimitBurst (5) starts within StartLimitIntervalSec (10s) trips start-limit-hit and the unit is parked in failed rather than looping forever. That limiter is a feature — it stops a broken service from pinning a core in a tight restart loop and spamming the journal. But it is not the bug. The bug is in the app, and the journal has it verbatim:

bash
journalctl -u flaky --no-pager | tail
Outputflaky.sh[...]: starting up... flaky.sh[...]: config error: cannot connect to db, exiting

There it is: "cannot connect to db." Restart=always was masking a real failure by hiding it behind a loop. The correct move is never to just raise the limits — it's to read the journal for the exit reason and fix the root cause (here, a missing/wrong DB dependency or config). Once fixed, clear the failed state with systemctl reset-failed flaky and start it again. If restarts are legitimately expected (a service that occasionally exits by design), tune Restart=on-failure, RestartSec, and the StartLimit* pair deliberately — but only after the journal has told you the loop isn't hiding a bug.

Lab 5Production challenge — the scheduled job that silently stoppedSenior challenge

A nightly backup "hasn't run in three days" and nobody noticed until now. It's a cron job. The senior task: figure out why it silently failed, then rebuild it as a systemd timer that logs, catches up, and can't run the box out of memory. First, feel why cron is easy to lose:

bash
# A cron-style job with no logging and no supervision — where does its output go?
apt-get install -y -qq cron
echo '30 2 * * * /usr/local/bin/backup.sh' | crontab -
crontab -l

If backup.sh fails, cron mails the output to a local mailbox nobody reads, and there's no record in your logging stack, no catch-up if the box was down at 02:30, and no resource cap. Now build the systemd equivalent and diagnose the "didn't fire" case. Design it before revealing.

Reveal the production-grade timer and the diagnosis method

A timer triggers a service; you write both. The service is a oneshot with a memory cap and a nice level; the timer schedules it with catch-up and jitter:

bash
cat > /etc/systemd/system/backup.service <<'EOF'
[Unit]
Description=Nightly backup
[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh
MemoryMax=512M
Nice=10
EOF

cat > /etc/systemd/system/backup.timer <<'EOF'
[Unit]
Description=Run backup at 02:30 daily
[Timer]
OnCalendar=*-*-* 02:30:00
Persistent=true              # if the box was off at 02:30, run at next boot
RandomizedDelaySec=300       # spread load across a fleet
[Install]
WantedBy=timers.target
EOF

systemctl daemon-reload
systemctl enable --now backup.timer
systemctl list-timers --all   # shows NEXT and LAST run for every timer

Why this beats cron: the job's output is in the journal (journalctl -u backup.service), Persistent=true gives catch-up cron can't do without anacron, MemoryMax/Nice keep a runaway backup from starving the box, and a failure shows up in systemctl --failed and your monitoring instead of an unread mailbox. Diagnosing "it didn't run" becomes systematic: systemctl list-timers shows whether the timer is active and when it last/next fires; systemctl status backup.timer confirms it's enabled; systemd-analyze calendar "*-*-* 02:30:00" validates the schedule expression; and journalctl -u backup.service shows whether the service fired and failed versus never fired at all. The most common silent-cron causes — a job that errored into a black hole, a missed run while the box was down, no alert on failure — are each visible or prevented here. This resource-control and scheduling model is the same cgroup foundation Kubernetes builds on in Chapter 23 and Chapter 34's CronJob.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · service won't start

Symptom: systemctl start returns nonzero, or the unit is Active: failed. First cut: systemctl status <unit> — read the Process: line and its exit code. Confirm: journalctl -u <unit> -xe for the verbatim error. Usual causes by code: 203/EXEC (bad/non-absolute/non-executable ExecStart path), 217/USER (User= doesn't exist), 200/CHDIR (bad WorkingDirectory=), 226/NAMESPACE (a sandboxing directive failed), or the app exiting nonzero on a config/dependency problem. Fix: whatever the journal names; and remember daemon-reload after editing a unit.

Incident pattern · crash-restart loop

Symptom: a unit flaps between activating (auto-restart) and failed, often ending in Result: start-limit-hit with "start request repeated too quickly." First cut: journalctl -u <unit> — the app's own error is in there; the restart loop is a symptom, not the cause. Usual cause: a real startup failure (missing dependency, bad config, unreachable DB) that Restart= keeps papering over. Fix: fix the root cause the journal shows, then systemctl reset-failed. Don't reflexively raise StartLimitBurst — that just restores the tight loop and hides the bug.

Incident pattern · "where are the logs?"

Symptom: an app doesn't write a log file and you need its output. First cut: it's in the journal — journalctl -u <unit> -b (this boot), add -p err for errors only, --since for a window, -f to follow. Gotcha: if the journal looks empty after a reboot, it's volatile — logs live in /run and vanish on reboot unless /var/log/journal exists. Fix: make it persistent (create /var/log/journal or set Storage=persistent), and cap size with SystemMaxUse= so it doesn't fill the disk. journalctl --disk-usage shows current size.

Production · security · performanceWhat matters in production

Model dependencies honestly, and use readiness. The recurring bug is treating After= as "wait until ready." It only orders the fork. For a dependency that must be truly serving before dependents start, run it as Type=notify so it reports real readiness, and have apps that can't rely on that do their own wait-and-retry. Racing a half-started database is a self-inflicted outage.

Sandboxing is free hardening. The Chapter 5 primitives are one-liners here: User= (never run a service as root without a reason), NoNewPrivileges=yes, ProtectSystem=strict, PrivateTmp=yes, CapabilityBoundingSet= to drop everything but what's needed. Add MemoryMax=, CPUQuota=, and TasksMax= and a plain systemd service gets the same resource isolation as a container — useful on VMs and bare metal where there's no Kubernetes.

Prefer timers to cron for anything that matters. Timers log to the journal, catch up with Persistent=true, spread fleet load with RandomizedDelaySec=, get resource limits, and surface failures in systemctl --failed and your monitoring. Cron's silent failure into an unread local mailbox is exactly how "the backup hasn't run in three days" happens.

Common mistakes: forgetting daemon-reload after editing a unit; confusing Requires (pull in) with After (order); using Restart=always to hide a crash instead of reading the journal; a relative or non-executable ExecStart (203/EXEC); a volatile journal that loses everything on reboot; and running services as root out of habit when a User= and a dropped capability set would do.

System-design connectionWhere this reaches into architecture

systemd is the single-node version of the ideas Kubernetes scales to a cluster, and seeing the parallel makes both click. A unit's declared dependency graph and readiness protocol is a Deployment's readiness probes and init containers. The cgroup-per-service with MemoryMax/CPUQuota is a pod's requests and limits (Chapter 23). Restart= policies are a pod's restartPolicy and the kubelet's back-off. A systemd timer is a Kubernetes CronJob (Chapter 34). And journald's "one queryable log, tagged by source" is the local seed of centralised logging (Chapter 78). The declarative, supervised, resource-bounded service is the atom; an orchestrator is the same atom, reconciled across a fleet — which is the mental bridge into Chapter 28.

InterviewInterview questions & answers

Answer each in your head first.

30-secWhat is a systemd unit, and what does systemd do that SysV init didn't?

A unit is a declarative description of something systemd manages — most often a .service (a process to run), but also targets, timers, sockets, and mounts. Compared to SysV init's serial shell scripts, systemd adds a real dependency graph so it can start independent things in parallel and in the right order; process supervision with restart policies so a crashed service comes back; a cgroup per service so it knows and can cleanly stop every process the service spawned, with no leaked children; one structured log for everything via journald; and scheduled jobs via timers. In short, it turned "run these scripts in a numbered order and hope" into "declare what you want and let PID 1 make it so and keep it so."

2-minWalk me through what happens when you start a service.

systemctl start is a client that asks systemd, PID 1, over D-Bus to start the unit. systemd resolves the unit's dependencies: it pulls in whatever Requires/Wants name and orders the startup by After/Before, starting independent units in parallel. For the target unit it creates a cgroup under system.slice, applies settings like User=, capability bounding, and MemoryMax=, and forks ExecStart inside that cgroup. When it considers the unit "started" depends on Type=: simple means as soon as it's forked, forking waits for the parent to exit, and notify waits for the app to send a readiness signal — which is what makes ordering actually meaningful. From then on systemd supervises via the cgroup: if the main process exits, the Restart= policy decides whether and when to restart it, with a rate limiter that parks it in failed if it crashes too fast. All the service's output streams to journald tagged by unit. Stopping sends SIGTERM to the whole cgroup, waits, then SIGKILLs stragglers — so nothing leaks. And systemctl status shows the whole picture: state, main PID, the cgroup process tree, and recent logs.

DeepExplain the Type= values and the difference between Requires, Wants, and After.

Type= tells systemd when a service counts as started. simple (default) considers it up the instant it's forked, even if the app isn't ready — fine for leaf services, risky for dependencies. exec waits until execve succeeds, so a bad binary path fails immediately. forking is for traditional daemons that double-fork and let the parent exit; systemd waits for that exit, ideally with a PIDFile. oneshot runs to completion for setup tasks, often with RemainAfterExit=yes. And notify is the important one: the service calls sd_notify(READY=1) when it's genuinely ready to serve, and systemd blocks dependents until then. Now the dependency directives, which are two orthogonal axes people conflate. Requires and Wants control what gets pulled in: Requires is a hard dependency — if it fails or stops, this unit fails or stops too — while Wants is soft, pulling the dependency in but tolerating its failure. After and Before control ordering only and say nothing about pulling anything in. The classic bug is writing Requires=db.service and expecting the database to start first — it won't, because requirement isn't ordering; you also need After=db.service. And even correct ordering only sequences the fork, so for real "don't start until the DB is serving," the DB should be Type=notify.

ScenarioA service is flapping — "start request repeated too quickly." How do you handle it?

I'd treat the restart loop as a symptom and go straight to the cause. First, systemctl status confirms the flap and shows Result: start-limit-hit — systemd's rate limiter (default 5 starts in 10s) parked it in failed so it wouldn't loop forever, which is working as intended. The real bug is in the app, and it's in the journal: journalctl -u <unit> almost always shows the actual error on each start — a missing config, an unreachable dependency, a permissions problem. I fix that root cause, then systemctl reset-failed to clear the failed state and start it again. What I would not do is bump StartLimitBurst or set RestartSec higher to "make it stop failing" — that just re-enables the tight loop and hides the defect. If the service legitimately exits sometimes and restarts are expected, I'd set Restart=on-failure with a sensible RestartSec and tune the start limits deliberately, but only after the journal confirms the loop isn't masking a genuine failure. The discipline is: the loop is never the problem, the exit reason in the journal is.

Follow-upWhen would you use a systemd timer instead of cron?

For anything whose failure matters, I default to a timer. A timer triggers a service, so I get everything systemd services get: the job's output lands in the journal (queryable, centralised, not a local mailbox nobody reads), Persistent=true gives catch-up if the machine was down at the scheduled time — which plain cron can't do without anacron — RandomizedDelaySec spreads a job across a fleet so a thousand nodes don't all hit a backend at 02:00, and I can apply MemoryMax/CPUQuota/Nice so a runaway job doesn't starve the box. Failures surface in systemctl --failed and my monitoring instead of vanishing. Timers can also key off events, like "10 minutes after boot" or "1 hour after the last run," which cron can't express. I'd still use cron for genuinely trivial, dependency-free, best-effort jobs on a box that already uses it — it's simpler and universally present — but for scheduled work in production, the observability and catch-up of timers is worth the extra unit file. It's also the same model as a Kubernetes CronJob, so the concept transfers.

RetainQuick revision

systemd is PID 1: it reads declarative units, builds a dependency graph from Requires/Wants (what to pull in) and After/Before (ordering — orthogonal to each other), and drives boot toward a goal target. It runs each service in its own cgroup, so it knows and can cleanly stop every process the service owns and can cap its resources. Type= decides when a service counts as started — notify for real readiness — and Restart= with a start rate limiter supervises crashes without looping forever. All output goes to journald, queried by unit with journalctl -u (plus -b, -p, --since, -f). Diagnosing is two commands: systemctl status for state and exit code, journalctl for the verbatim reason. And timers beat cron for anything that matters, thanks to journal logging, catch-up, jitter, and resource control.

The 10 things to remember

  1. systemd is PID 1; everything it manages is a unit (.service, .target, .timer, .socket, .mount, .slice).
  2. Requires/Wants control what gets pulled in; After/Before control ordering — they're independent, and you usually need both.
  3. Targets are boot goals and sync points (multi-user.target), the modern replacement for runlevels.
  4. Each service runs in its own cgroup, so systemd tracks every child, stops it cleanly, and can cap CPU/memory/tasks.
  5. Type= sets readiness: simple (forked), forking, oneshot, and notify (real "ready" signal) — use notify for dependencies.
  6. Restart= plus StartLimitBurst/Interval supervise crashes; too-fast restarts hit start-limit-hit and park in failed.
  7. Diagnose with two commands: systemctl status (state + exit code like 203/EXEC) and journalctl -u <unit> -xe (why).
  8. The journal is the log — journalctl -u/-b/-p err/--since/-f; make it persistent with /var/log/journal.
  9. Always systemctl daemon-reload after editing a unit; use absolute paths in ExecStart.
  10. Prefer timers to cron for real work: journal logging, Persistent= catch-up, RandomizedDelaySec=, and resource limits.
