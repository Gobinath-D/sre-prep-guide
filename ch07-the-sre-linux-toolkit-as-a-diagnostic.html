The SRE Linux toolkit as a diagnostic system

A page fires at 3am. You have thirty commands in muscle memory and sixty seconds before someone asks "what's going on?". The difference between senior and junior isn't knowing more tools — it's knowing which tool answers which question, and reaching for it without thinking.

Start: Beginner→→→End: Staff-level ~40 min read · Linux lab (Docker)

By the end of this chapter you can

  • Run a 60-second triage on any Linux host and say whether it's CPU-, memory-, disk-, or network-bound.
  • Map every tool — top, vmstat, iostat, pidstat, sar, free, ss, lsof, strace — to the exact question it answers, using the USE method.
  • Read the columns that matter: run-queue length, %wa, si/so, await, %util, MemAvailable, socket states.
  • Localise a synthetic CPU, memory, and I/O load to the responsible process every time.
  • Know when the fixed tools run out and reach for bpftrace/eBPF — and know what it costs you.

Why this exists · the problemThe problem: flailing under pressure

Watch someone junior debug a slow host and you'll see the same thing every time. They SSH in, run top, stare at it, run top again, maybe df -h, maybe ps aux | grep something, then paste a screenshot into Slack and ask what to do. It's not that they don't know commands. It's that they have no system — no ordered set of questions that narrows "the box is unhappy" down to "this process is saturating this resource."

The tools themselves aren't the hard part. Any of them takes ten minutes to learn. The hard part is that under pressure, with an SLO burning and people watching, you need to know — reflexively — that a rising load average with idle CPU means you look at disk and uninterruptible sleep, not at CPU; that free showing "100 MB free" is almost never the memory problem people think it is; that 100% disk %util on an NVMe drive might mean nothing at all. Reflexes, not knowledge.

So this chapter isn't a tour of commands. It's a diagnostic system: a small, ordered method that turns any Linux host into a set of four resources — CPU, memory, disk, network — and asks the same three questions of each. Once you have the method, the tools slot into place as answers, and you stop guessing.

Key point

You will not remember thirty tools under pressure. You will remember one method and the two or three tools that hang off each branch of it. Learn the method first; the tools are just where you go to read the number.

Mental model · analogyThe mental model: USE, like a triage nurse

The method is the USE method: for every resource, check three things in order — Utilisation, Saturation, Errors. Utilisation is "how busy is it" (percent of time doing work). Saturation is "how much work is queued that it can't get to yet" (the backlog). Errors is "is it failing" (dropped packets, I/O errors, failed allocations). Do that for CPU, memory, disk, and network and you have covered almost every host-level performance problem there is.

Real-world analogy

A good ER triage nurse does not start with an MRI. When you walk in, they take vitals in a fixed order — pulse, blood pressure, temperature, oxygen — because those cheap, fast numbers tell them which system is in trouble before they order an expensive scan. A racing pulse and low oxygen sends you one way; a fever sends you another. Only then do they call the specialist and run the deep test.

USE is your triage vitals. vmstat, free, and uptime are the pulse and blood-pressure cuff: cheap, instant, and they tell you whether this is a CPU story, a memory story, a disk story, or a network story. strace, lsof, and bpftrace are the MRI — precise, more expensive to run, and you only order them once triage has pointed you at the organ. Reach for the MRI first and you waste the golden minute reading detail about the wrong system.

ArchitectureWhich tool answers which question

Here's the whole toolkit as one decision path. Start at the top with the cheap vitals, let them point you at a resource, then localise. This is the picture to burn into memory — everything after it is detail.

Notice the shape. The top is broad and cheap — two commands that cost nothing and cover the whole machine. The middle narrows to one resource. The bottom is expensive and precise. You always move down, never sideways, and you don't reach the bottom row until the middle row has told you where to point it.

Internal workingWhere the numbers actually come from

Every one of these tools is a thin reader over kernel counters. Almost none of them measure anything themselves — they read files the kernel exposes and, for the rate tools, take two samples and divide by the time between them. Understanding that is what lets you trust or distrust a number.

  1. The kernel keeps running counters in /proc and /sys. /proc/stat holds cumulative CPU time in jiffies split into user, nice, system, idle, iowait, irq, softirq, and steal. /proc/meminfo holds memory totals. /proc/diskstats holds per-device I/O counts and accumulated service time. These only ever go up.
  2. Rate tools sample twice and subtract. When you run vmstat 1 or iostat 1, the first line is the average since boot — usually useless. Every line after it is (counter_now − counter_1s_ago) / 1s. That's why the first line is a lie and you always read the second onward.
  3. CPU percent is jiffies, not magic. top reads the CPU-time fields from /proc/stat, waits, reads again, and divides each field's delta by the total delta. %us is time in your code, %sy in the kernel, %wa is idle-waiting-on-I/O, and %st (steal) is time the hypervisor gave to another tenant — the number that quietly explains slow EC2 instances.
  4. Load average counts more than CPU. /proc/loadavg is an exponentially-weighted moving average (1, 5, 15 min) of tasks that are runnable plus tasks in uninterruptible sleep (state D, usually blocked on disk). This is the single most misread number in Linux: a load of 30 on a 4-core box can mean CPU saturation or thirty processes all stuck waiting on a slow disk. Load alone can't tell you which — vmstat's r vs b columns can.
  5. Disk %util is a single-queue relic. iostat computes %util as the fraction of wall-clock time the device had at least one request in flight. On a spinning disk that maps to "how busy," but SSDs and NVMe serve dozens of requests in parallel, so they can show 100% %util while nowhere near saturated. On modern storage, trust await (average latency per I/O) and queue depth, not %util.
  6. free's "available" is the kernel's own estimate. MemAvailable in /proc/meminfo is the kernel telling you how much a new process could get without swapping, already accounting for reclaimable page cache. It's the number that matters. "free" (truly untouched RAM) is nearly always small and nearly always irrelevant, because Linux spends free RAM on cache by design.
The number everyone misreads

"We're out of memory — free shows only 200 MB free!" No. Linux uses spare RAM as page cache (Chapter 3), and that cache is reclaimable on demand. The question is never "how much is free," it's "how much is available, and are we swapping?" Read MemAvailable and watch si/so in vmstat. A box with 200 MB free and 12 GB available and zero swap activity is perfectly healthy.

Think first: load average is 40 on an 8-core host, but top shows the CPUs are 85% idle. What's happening?

The CPUs are idle, so this isn't a CPU problem — the load is coming from tasks in uninterruptible sleep (state D), almost always blocked on I/O. Load average counts runnable and D-state tasks, so a slow or failing disk (or an NFS mount that stopped answering) drives load up while the CPUs sit waiting. Your next move is vmstat 1 and look at the b column and wa%, then iostat -xz 1 to find the device with high await. Adding CPU here would do nothing; the bottleneck is storage.

ComponentsThe toolkit, named

Now the tools themselves, each filed under the question it answers. Learn them in this frame and you'll never again wonder "which one do I run?"

  • uptime — "is it getting worse?" Three load averages: 1, 5, 15 minutes. You read them as a trend. 1 min > 15 min means the problem is growing right now; the reverse means it's recovering. It's the cheapest command there is and the right first move.
  • vmstat 1 — the whole machine on one line. Your primary vital sign. r = runnable tasks (CPU demand), b = blocked/uninterruptible (I/O demand), si/so = swap in/out (memory pressure), bi/bo = block I/O, us/sy/id/wa/st = CPU split. One screen tells you which of the four resources to chase.
  • mpstat -P ALL 1 — "one core or all of them?" Per-CPU breakdown. Catches the classic single-threaded bottleneck: one core pinned at 100% while seven sit idle, so aggregate CPU looks fine (12%) but the app is capped. Aggregate numbers hide this; mpstat reveals it.
  • top / htop — "who, roughly?" The live leaderboard of processes by CPU and memory. htop adds colour, per-core bars, and tree view. Good for a first glance and for sorting, but it samples slowly and doesn't attribute I/O well — which is where pidstat earns its keep.
  • pidstat 1 — "which process, precisely?" The bridge from "the machine is disk-bound" to "and it's this PID doing it." pidstat -u for CPU, -r for memory faults, -d for disk read/write per process, -w for context switches. This is the tool that turns a system-wide symptom into a named culprit.
  • iostat -xz 1 — disk saturation. Per-device. await = average latency per I/O in ms (the number to trust), r/s w/s = IOPS, rkB/s wkB/s = throughput, aqu-sz = average queue depth (saturation), %util = busy time (trust it only on spinning disks).
  • free -m — memory at a glance. Read the available column, not free. Cross-check with vmstat's si/so: available high and no swapping means memory is fine no matter how little shows as "free."
  • ss -tanp / ss -s — sockets and connection state. The modern replacement for netstat, reading straight from the kernel. ss -s summarises counts by state; ss -tanp lists every TCP socket with the owning process; ss -ti shows per-connection TCP internals (rtt, cwnd, retransmits). On a LISTEN socket, Recv-Q is the current accept-backlog depth and Send-Q is its ceiling — a full backlog is dropped connections.
  • lsof — "what is this process holding open?" Every open file, socket, and pipe, with the owning PID. Finds FD leaks (lsof -p <pid> | wc -l), the process pinning a filesystem you can't unmount (lsof +D /mnt), and deleted-but-still-open files quietly eating disk (lsof | grep deleted).
  • strace — syscall-level truth. From Chapter 1: shows exactly what a process asks the kernel and what it gets back. Order it once triage has narrowed things down — it's precise but it slows the target, so it's an MRI, not a vital sign.
  • sar — the time machine. The sysstat package can collect all of the above every few minutes into a rotating archive. When the incident was at 2am and you were asleep, sar replays exactly what CPU, memory, disk, and network were doing then. Enable it before you need it; you cannot go back and collect the past.
  • bpftrace / eBPF — the questions the fixed tools can't ask. Programmable, in-kernel, low-overhead tracing. When you need "which process caused this disk I/O," "what's the latency distribution of block reads," or "which files take longest to open," the counter-reading tools can't answer — but a one-line eBPF program can, safely, in production. This is where the toolkit ends and the deep observability chapters (Chapter 74) begin.
Think first: aggregate CPU is 12% but the service is clearly capped and slow. Which tool proves what's wrong, and what will it show?

mpstat -P ALL 1. On an 8-core box, 12% aggregate is roughly one core fully busy (1/8 ≈ 12.5%). mpstat will show one CPU at ~100% and the rest near idle — a single-threaded hot path. The fix isn't more cores or more replicas of the box; it's parallelising the workload (more worker threads/processes) or splitting the hot function. top pressing 1 shows per-core too, but mpstat gives you a clean averaged view over an interval.

Data flowThe first 60 seconds

Netflix's performance team made a famous checklist: the commands a good engineer runs in the first minute on an unfamiliar, unhappy host. Here is my version of that flow — the order I actually type when a host pages me, and why each step earns its seconds.

  1. uptime — load trend. Rising fast, or already recovering? Sets the urgency.
  2. dmesg -T | tail -30 — the kernel's own words. OOM kills, I/O errors, TCP SYN flooding, filesystem-read-only events. If the kernel already logged the cause, you're done in ten seconds.
  3. vmstat 1 5 — read lines 2 onward. r high → CPU. b high + wa high → disk. si/so nonzero → memory/swap. st high → noisy hypervisor neighbour. This one command usually names the resource.
  4. mpstat -P ALL 1 3 — if it looked CPU-bound: one core or all? And is it %usr (your code) or %sys (kernel/syscall storm)?
  5. pidstat 1 3 — attribute it to a process. Pair with -d for disk, -r for memory. Now you have a PID, not just a symptom.
  6. iostat -xz 1 3 — if disk-bound: which device, what's await, is the queue deep?
  7. free -m — available and swap. Confirms or clears the memory hypothesis.
  8. ss -s and sar -n DEV 1 3 — socket counts and per-interface throughput/drops, if the story points at network.

Eight commands, well under a minute. At the end you can say a real sentence — "the host is disk-bound, device nvme0n1 at 40 ms await, driven by PID 8842, the log shipper" — and then you order the MRI: strace -p 8842 or a bpftrace histogram to confirm exactly why. You never skip to the MRI. The whole point is that the cheap steps stop you pointing an expensive, target-slowing tool at the wrong process.

Why an SRE cares

This flow is what separates a two-minute triage from a thirty-minute one. The junior version — SSH in, run top, guess — usually lands on CPU because that's the column people watch, and then the "fix" is to add replicas or cores, which does nothing when the real bottleneck was a saturated disk or a swap storm. The flow forces you to check all four resources cheaply before you commit to a theory. On call, that discipline is the difference between a fixed incident and a widened one.

r is 2 (two runnable tasks), us is up, b/wa/si/so are all 0. This is textbook CPU-bound, in user space, not the kernel. Now: one core or several, and which process?

bash

Two PIDs at ~99% %usr, zero %system. Diagnosis complete: user-space CPU burn, two workers, named. In a real incident "high %usr" sends you to a code profiler (Chapter 104); "high %system" sends you to strace -c for a syscall storm, exactly as in Chapter 1.

Lab 4Troubleshoot — memory pressure, then diskTroubleshoot

Two loads back to back. First, squeeze memory hard enough to swap; investigate before you read the reveal.

bash
# Allocate and touch more RAM than is comfortable, for 60s.
stress-ng --vm 2 --vm-bytes 90% --vm-keep --timeout 60s &
vmstat 1 5
free -m

What in the output tells you this is memory and not CPU? Which single column would you screenshot to prove it to a colleague? Decide, then check.

Reveal — the memory tell

si and so (swap-in / swap-out) go nonzero in vmstat, and free's available collapses while swap used climbs. That's the proof: the box is reclaiming and paging to disk. Watch for b and wa to rise too, because swapping is disk I/O — a memory problem that masquerades as a disk problem. pidstat -r 1 names the process by major-fault rate. If it goes far enough the kernel invokes the OOM killer and you'll see it in dmesg -T — the topic of Chapter 3.

Now a disk load. Write a steady stream and localise the device and the process:

bash
stress-ng --hdd 2 --hdd-bytes 1g --timeout 60s &
iostat -xz 1 3        # which device, what await, how deep the queue
pidstat -d 1 3        # which process is writing
Output (iostat, trimmed)Device r/s w/s rkB/s wkB/s aqu-sz await %util nvme0n1 0.0 920.0 0.0 235000.0 6.40 7.10 99.8

High w/s and wkB/s, a queue depth over 6, await at 7 ms. Note %util reads 99.8% — but on NVMe that alone wouldn't prove saturation; the aqu-sz and await climbing is the real signal. pidstat -d gives you the writing PID. That's the full disk path: resource → device → process.

Lab 5Production challenge — when the fixed tools run out (eBPF)Senior challenge

The counter-reading tools tell you that the disk is busy, but not always which process issued each read, or the latency distribution of those reads. That's an eBPF question. eBPF needs kernel access, so run a privileged container (on Docker Desktop the LinuxKit kernel ships BTF, so this usually just works):

bash
docker run --rm -it --privileged --pid=host ubuntu:24.04 bash
apt-get update && apt-get install -y bpftrace

# Count every syscall by process name, whole machine, ~0% overhead.
bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'
Output (Ctrl-C to print)@[systemd]: 1240 @[stress-ng-cpu]: 88190 @[containerd]: 210934

One tracepoint, the whole system, negligible overhead — the thing strace could never do safely in production because it slows its target. Now the senior question: a service shows 15 ms disk await in iostat, but the team swears their reads are tiny. How would you prove where the latency lives — and what would you look at if bpftrace won't load at all?

Reveal an approach

Draw the latency as a histogram, not an average — averages hide the tail that's actually hurting you:

bash
# Block I/O latency histogram (ships with bpftrace as biolatency.bt too):
bpftrace -e 'tracepoint:block:block_rq_issue { @s[args.dev, args.sector] = nsecs; }
  tracepoint:block:block_rq_complete /@s[args.dev, args.sector]/ {
    @us = hist((nsecs - @s[args.dev, args.sector]) / 1000);
    delete(@s[args.dev, args.sector]); }'

A bimodal histogram — most I/O at 200 µs but a fat bump at 20 ms — tells you the average of 15 ms is a lie: most reads are fast and a tail is slow (a noisy neighbour, or cache misses hitting cold storage). If bpftrace can't load (no BTF, locked-down kernel, some managed nodes), fall back to perf record -e block:block_rq_issue, to /proc/<pid>/stack to see where a blocked task is parked, or to sar -d historical device latency. The point is the method — reach for the tool that answers "distribution and attribution," not just "how busy."

Failure & troubleshootingHow this shows up in real incidents

Four patterns cover most of what pages you. Filed the way an SRE actually holds them:

Incident pattern · high load, idle CPU

Symptom: load average alarming, CPU graphs calm. First cut: vmstat 1 — is it the r column (CPU demand) or the b column (uninterruptible, usually I/O)? Confirm: iostat -xz 1 for device await, and ps -eo state,pid,cmd | grep '^D' to list the stuck tasks. Cause is usually: a slow or failing disk, or a hung network filesystem (NFS/EFS) that turns every read into a multi-second wait. Adding CPU never helps.

Incident pattern · "out of memory" that isn't

Symptom: someone panics that free shows almost no free memory. First cut: read available, not free, and check vmstat si/so. Confirm: dmesg -T | grep -i oom for actual kills. Cause is usually: nothing — Linux is using RAM as cache as designed. The real memory incident looks different: available low and swap active and OOM kills in dmesg. Learn to tell the two apart and you'll stop half your "memory" pages at a glance.

Incident pattern · connections refused, box looks fine

Symptom: clients get connection refused or timeouts; CPU, memory, disk all healthy. First cut: ss -s for socket counts, then ss -tanp state listening and look at Recv-Q/Send-Q on the listener. Confirm: a full accept backlog (Recv-Q pinned at Send-Q) means the app isn't accepting fast enough, or you're being flooded. Cause is usually: an app stuck not calling accept(), an FD limit hit (lsof -p <pid> | wc -l vs /proc/<pid>/limits), or a real connection surge you can see in dmesg as "possible SYN flooding."

Incident pattern · the cloud host that's mysteriously slow

Symptom: an EC2 or VM instance runs slower than its specs say it should, intermittently. First cut: vmstat 1 and read the st (steal) column. Confirm: mpstat -P ALL 1 — steal spread across cores. Cause is usually: a noisy neighbour on the same physical host, or a burstable instance (t-family) that ran out of CPU credits. No amount of in-guest tuning fixes steal; you change instance type or move.

Production · security · performanceWhat matters in production

You do not SSH to a thousand boxes. Everything in this chapter is the right tool for one host you're actively debugging, or the reflexes behind an automated collector. At scale you run an agent — node_exporter feeding Prometheus (Chapter 75) — that scrapes exactly these /proc and /sys counters continuously, so the USE method becomes a dashboard and an alert instead of a login. The manual toolkit is what you fall back to when the dashboard says "something's wrong here" and you need to go deep on the one box. Both live on the same numbers.

Overhead is real and uneven. vmstat, iostat, free are counter reads — effectively free, safe on a hot production box. strace is not: it stops the target on every syscall via ptrace and can slow a busy process by an order of magnitude, so never attach it to a latency-critical process without knowing that. eBPF sits in between — designed for production, single-digit-percent overhead — which is exactly why the industry moved toward it for always-on tracing.

USE vs RED. USE (utilisation/saturation/errors) is a resource lens — perfect for hosts and hardware. Its sibling RED (rate/errors/duration) is a request lens — perfect for services. You use USE to answer "is this machine sick?" and RED to answer "is this service sick?"; a mature on-call reaches for both and knows which question they're asking. RED comes back in the SLO chapter (Chapter 80).

Common mistakes that this chapter should stop: reading free's "free" instead of "available"; trusting load average as a CPU metric; treating %util as saturation on SSD/NVMe; running strace on a critical process during peak; and — the big one — reaching for the deep tool before the cheap vitals have told you where to point it. Order matters more than which tools you know.

System-design connectionWhere this reaches into architecture

The USE method isn't only a debugging trick; it's how you size and reason about systems. Capacity planning (Chapter 89) is USE applied ahead of time: for each resource, at what utilisation does saturation begin, and how much headroom do you keep before it? Autoscaling signals are USE turned into triggers — you scale on the resource that saturates first, and picking the wrong one (scaling on CPU when the real limit is memory or connection count) is a classic outage. Dashboards worth having (Chapter 76) are laid out by resource with utilisation, saturation, and errors visible together, because that's the shape a human triages in. And the deepest link: knowing that a single machine has finite CPU, finite I/O, and finite sockets — and being able to see which runs out first — is what tells you when to scale a box up versus scale the service out. That decision starts here, at the counters.

InterviewInterview questions & answers

Answer each in your head before you open it.

30-secWhat's the USE method?

For every resource on the system — CPU, memory, disk, network — you check three things: Utilisation (how busy it is), Saturation (how much work is queued that it can't get to yet), and Errors. It gives you a complete, ordered checklist so you cover every resource instead of fixating on the one metric you happened to look at. In practice it turns "the box is slow" into "this resource is saturated," which is the question that actually leads to a fix.

2-minWalk me through your first 60 seconds on a host that just paged you.

uptime first — is load rising or recovering, how urgent. Then dmesg -T | tail in case the kernel already logged the cause: OOM kills, I/O errors, TCP drops. Then vmstat 1, reading past the first line: the r column for CPU demand, b and wa for disk waiting, si/so for swapping, st for hypervisor steal. That one command usually names the resource. From there I branch: mpstat -P ALL 1 to see if CPU pressure is one core or all and whether it's user or system time; iostat -xz 1 for device await if it's disk; free -m reading available for memory; ss -s and sar -n DEV for network. Then pidstat to attribute the load to a specific process. Only after all that do I reach for the precise tools — strace, lsof, bpftrace — because they're expensive or slow the target, so I want to know exactly where to point them first.

DeepLoad average is 40 on an 8-core box but CPUs are 90% idle. Explain, and where do you look?

Load average on Linux isn't a CPU metric — it's an exponentially-weighted count of tasks that are runnable plus tasks in uninterruptible sleep, state D, which almost always means blocked on I/O. So idle CPUs with high load means a lot of tasks are stuck waiting, not computing. I'd run vmstat 1 and expect a high b column and high %wa; then iostat -xz 1 to find the device with high await and a deep queue, and ps -eo state,pid,wchan,cmd | grep '^D' to see the blocked tasks and what kernel function they're parked in. The usual culprits are a saturated or failing disk, or a hung network mount like NFS/EFS where every syscall blocks for seconds. The important reflex is that adding CPU does nothing here — the fix is on the storage or network path.

ScenarioA service is capped and slow, but overall CPU shows only ~12% on an 8-core box. What's going on and how do you prove it?

12% of 8 cores is almost exactly one core fully busy, which smells like a single-threaded bottleneck hidden by the aggregate. I'd prove it with mpstat -P ALL 1 (or top then press 1): I expect one CPU near 100% and the rest idle. pidstat -t can show it's one hot thread within the process. The fix isn't more replicas or a bigger box — extra cores sit idle — it's parallelising the work: more worker threads or processes, sharding the hot loop, or moving the serial section off the request path. This is why aggregate CPU is a trap: it averages away the exact thing that's saturated.

Follow-upWhen would you reach past these tools for eBPF/bpftrace, and what does it cost you?

When the fixed tools tell me that a resource is busy but can't tell me which process caused each event or the distribution of a latency — questions like "which PID issued these disk reads," "what's the histogram of block-I/O latency," "which files are slowest to open." Those need programmable, in-kernel tracing, which is eBPF. The cost is mainly access and portability: it needs a recent kernel with BTF and privileged (root) access, and it doesn't run everywhere (some locked-down managed nodes). The runtime overhead is low by design — single-digit percent — which is the whole reason it's safe in production where strace isn't, since strace stops the target on every syscall. So I reach for it deliberately, after triage has narrowed the question, not as a first move.

RetainQuick revision

Under pressure you won't recall thirty tools — you'll recall one method. The USE method checks Utilisation, Saturation, and Errors for each of CPU, memory, disk, and network. The 60-second flow runs the cheap, whole-machine vitals first (uptime, dmesg, vmstat), lets them name the resource, then localises with the per-resource tools (mpstat, iostat, free, ss) and attributes to a PID with pidstat. Only then do you order the expensive, precise tools — strace, lsof, bpftrace — because they cost overhead or slow the target. Every tool is just a reader over kernel counters in /proc and /sys; the rate tools sample twice and divide, so line one is always a lie. Read available not free, trust await not %util on SSDs, and remember load average counts I/O waiters, not just CPU.

The 10 things to remember

  1. USE: for each resource (CPU, memory, disk, network) check Utilisation, Saturation, Errors — in that order.
  2. Cheap vitals first, expensive tools last: uptime → vmstat → localise → pidstat → then strace/bpftrace.
  3. vmstat 1 is the one-screen triage: r=CPU demand, b+wa=disk, si/so=swap, st=hypervisor steal.
  4. Load average counts runnable and uninterruptible (D-state) tasks — high load with idle CPU means I/O, not CPU.
  5. Read free's available column, never "free" — Linux uses spare RAM as reclaimable cache by design.
  6. On SSD/NVMe, %util lies; trust await (latency) and queue depth for real disk saturation.
  7. mpstat -P ALL exposes single-threaded bottlenecks that aggregate CPU averages away.
  8. pidstat is the bridge from "the machine is X-bound" to "and it's this PID"; -u/-r/-d/-w for CPU/mem/disk/switches.
  9. strace is an MRI — precise but it slows the target; eBPF/bpftrace answers attribution and distribution at low overhead.
  10. Every tool reads kernel counters; rate tools sample twice, so ignore the first line and enable sar before you need history.
