Bash and shell scripting for automation

Bash is the glue holding every Linux platform together — the entrypoint of your container, the body of your cron job, the first ten lines of every CI pipeline. It's also a minefield of quoting and silent failure. This chapter teaches you to write it deliberately, and to know the exact moment it stops being the right tool.

Start: Beginner→→→End: Staff-level ~40 min read · Linux lab (Docker)

By the end of this chapter you can

  • Build a log-analysis pipeline one stage at a time and explain what each of grep, awk, sed, cut, sort, uniq, xargs transforms.
  • Explain exit codes, $?, and PIPESTATUS, and why a broken pipeline can still "succeed" without them.
  • Start every script with set -euo pipefail and know precisely what each flag does and where -e quietly won't fire.
  • Quote correctly — and reproduce the classic unquoted-variable disaster on purpose so you never ship it.
  • Write a safe, idempotent script with functions, a cleanup trap, and graceful signal handling — and say when to reach for Python instead.

Why this exists · the problemThe problem: gluing programs together

Half of operations is moving text between programs. A log file comes out of nginx; you need the top IPs by error count. A command prints a list of pods; you need to restart the ones older than a day. A deploy needs to run four steps in order and stop if any of them fails. None of this deserves a compiled program. It deserves a few lines that wire existing tools together — and the thing that wires them together, on literally every Linux box you'll ever touch, is the shell.

That ubiquity is exactly why it matters. You don't get to skip bash by preferring Python, because bash is already there: it's ENTRYPOINT ["/bin/sh","-c", …] in your Dockerfile, the command: in your Kubernetes manifest, the run: steps in your CI, the health-check probe, the init script. If you can't read and write it confidently, large parts of your own platform are opaque to you.

And here's the tension. Bash makes the easy things trivial and the medium things dangerous. A missing quote turns rm -rf "$dir/" into rm -rf / when $dir is empty. A pipeline reports success while its most important stage failed silently. A cron job runs half-way, errors, and exits 0 so nobody notices until the data's wrong. This chapter is about writing bash on purpose — with the guardrails that turn it from a foot-gun into a dependable tool — and about recognising the line past which you should stop and write Python (Chapter 9).

Key point

Bash's defaults are hostile: it keeps going after errors, splits unquoted variables on whitespace, and hides all but the last exit code in a pipeline. Every safe script starts by turning those defaults off. The language didn't change; you changed how strict it is.

Mental model · analogyThe mental model: an assembly line of small machines

The Unix idea underneath the shell is old and simple: build a few small programs that each do one thing well, and let them read from standard input and write to standard output, so you can chain them. The shell's job is to stand up that chain and connect the machines.

Real-world analogy

Picture a factory conveyor belt. Raw material — a log file — drops onto the belt at one end. It passes through a line of single-purpose machines: one filters out everything that isn't an error (grep), the next cuts a single column off each item (awk), the next groups identical items (sort), the next counts each group (uniq -c), the last ranks and keeps the top few (sort -rn | head). Each machine takes what the previous one produced and hands its result down the line. None of them knows or cares what the others do.

The belt itself — the thing carrying material from one machine's output to the next machine's input — is the pipe (|). And every machine, when it finishes, flips a little green or red light: an exit code, 0 for "I did my job," nonzero for "I failed." The danger is that by default the factory only looks at the last machine's light. If the filter jammed in the middle but the ranker at the end ran fine, the line reports success and ships a wrong result. pipefail is the supervisor who checks every machine's light, not just the last one.

ArchitectureHow a pipeline is wired

A pipeline isn't a single program reading the file five ways. It's five separate processes, running at the same time, with the kernel carrying bytes between them. Here's the exact shape of the top-offending-IPs pipeline, the one you'll build in the labs.

That "runs at the same time" detail matters. The pipeline doesn't wait for grep to finish the whole file before awk starts; they run concurrently and the kernel back-pressures the fast ones when a slow one can't keep up. It's genuine parallelism, which is part of why a shell pipeline can chew through a multi-gigabyte log faster than a naive single-threaded script.

Internal workingWhat the shell does with a line you type

When you press Enter on grep ' 500 ' access.log | awk '{print $1}', the shell does a precise, ordered dance. Knowing the order is what lets you predict — instead of discover — how quoting and expansion behave.

  1. Expansion, in a fixed order. Before any program runs, the shell rewrites the line: brace expansion, then tilde (~), then parameter/variable expansion ($var), command substitution ($(…)), and arithmetic, then — critically — word splitting on IFS, then pathname expansion (globbing *). Word splitting and globbing happen to the result of the variable expansion, which is the whole reason unquoted variables are dangerous.
  2. Fork a process per stage. For each command in the pipeline, the shell calls fork() to make a child (Chapter 1's syscalls at work).
  3. Wire the pipes with dup2. The shell creates a kernel pipe between each pair and uses dup2() to point the left child's fd 1 (stdout) and the right child's fd 0 (stdin) at the two ends. This is why "stdout becomes stdin" is literal, not a metaphor.
  4. exec the real program. Each child replaces itself with the actual grep/awk binary. If it's a shell builtin (cd, echo, [[) there's no fork/exec — the shell runs it itself, which is why cd in a subshell can't change your current directory.
  5. Wait and collect exit codes. The shell wait()s for the children. The exit status of the last command lands in $?; the full set lands in the array ${PIPESTATUS[@]}. This is the single most important internal detail for reliability: a pipeline's $? is only its last stage.
  6. The set flags change the rules. set -e makes the shell exit the moment a command returns nonzero (with exceptions — see the gotcha). set -u turns any reference to an unset variable into an error instead of an empty string. set -o pipefail makes a pipeline's exit code the rightmost nonzero one, so a mid-pipe failure is no longer swallowed.
Where set -e quietly won't save you

set -e does not trigger for a command whose result is being tested: anything in an if, while, or until condition, anything joined by && or ||, or a command negated with !. So if grep foo file; then … won't exit even when grep "fails" (finds nothing) — which is correct, but surprises people. Worse, a failing command inside a function called in one of those contexts also won't abort. And local x=$(false) hides the failure because local's own success masks it. This is why set -e is a helpful default but never your only error handling — you still check the exit codes that matter explicitly.

Think first: grep ERROR app.log | wc -l prints 0 and $? is 0. But the log file doesn't exist. Why did it look like success, and what would have caught it?

Two things conspired. First, grep failed (no such file), but its error went to stderr and its output to wc -l was empty, so wc -l happily printed 0 and exited 0. Second, $? is only the last stage — wc — so grep's failure never reached it. With set -o pipefail, the pipeline's exit code would become grep's nonzero status and you'd know. To see it directly: after the pipeline, inspect ${PIPESTATUS[@]} and you'd find 2 0 — stage one failed, stage two succeeded. This exact shape is how broken cron jobs report success for months.

ComponentsThe pieces, named

You'll reach for the same small set constantly. Each does one job; the skill is combining them.

  • grep — filter lines. Keeps (or with -v, drops) lines matching a pattern. -i ignore case, -E extended regex, -c count, -o print only the match, -P Perl regex when you need lookahead. Your first-line filter in almost every pipeline.
  • awk — column-aware processing. The heavy hitter: splits each line into fields ($1, $2, …), matches patterns, does arithmetic and aggregation. awk '$9==500 {print $1}' filters and extracts in one step. When you find yourself piping grep | cut | grep, awk usually replaces all three.
  • sed — stream edit. Substitution and line surgery: sed 's/old/new/g', delete lines, print ranges. Great for in-place text transforms; reach for awk once you need fields or logic.
  • cut — grab fixed columns. Simple field extraction by delimiter (cut -d: -f1 /etc/passwd) or byte range. Lighter than awk when the split is trivial.
  • sort / uniq — order and dedupe. uniq only collapses adjacent duplicates, so it's almost always sort | uniq. sort -rn ranks numerically descending; uniq -c counts. The "top N of anything" idiom is sort | uniq -c | sort -rn | head.
  • xargs — turn output into arguments. Takes a list on stdin and runs a command with those items as arguments. -n1 one at a time, -P in parallel, and always -0 with find -print0 to survive filenames with spaces. This is how you bridge "a list of things" to "do something to each."
  • Exit codes, $?, PIPESTATUS. The success/failure channel, separate from output. Every reliability decision hangs off these.
  • Functions. Named blocks with their own local variables and their own exit code (via return or the last command). They keep a script readable past twenty lines and make behaviour testable.
  • Traps and signals. trap 'cmd' EXIT runs cleanup no matter how the script ends; trap 'cmd' INT TERM handles Ctrl-C and kill. This is how you avoid leaving temp files, lock files, or half-applied changes behind (signals in depth: Chapter 2).
  • Tests — [[ … ]]. The bash conditional: [[ -f "$f" ]] file exists, [[ -z "$x" ]] empty, [[ "$a" == "$b" ]]. Prefer [[ ]] over the older [ ] — it doesn't word-split and has saner operators.
Think first: cat access.log | grep " 500 " | wc -l works — so why would a senior rewrite it?

Two smells. The cat is redundant — a "useless use of cat" — because grep reads files directly: grep -c " 500 " access.log does the whole job in one process, and grep -c even replaces the wc -l. So three processes collapse to one. It's not about the microseconds saved; it's that fewer moving parts means fewer places to get quoting, exit codes, and pipefail wrong, and the intent reads clearer. The habit generalises: whenever a pipeline has a stage that only exists to feed the next tool something it could have read itself, cut it. Reserve pipes for genuine transformations, not for shuffling data a tool already accepts directly.

Data flowFollowing the top-IPs one-liner

Trace one real request-for-data end to end. You've been asked: "which clients are causing our 500s?" The pipeline is awk '$9==500 {print $1}' access.log | sort | uniq -c | sort -rn | head. Watch the stream change shape at each stage. awk reads the log line by line, keeps only lines whose 9th field (the HTTP status) is 500, and emits just the client IP from field 1 — so a megabyte of log becomes a thin column of IPs, most repeated. sort brings identical IPs next to each other (because uniq only sees adjacent lines). uniq -c collapses each run into a single line prefixed by its count. sort -rn re-sorts those counts, largest first. head keeps the top ten. Out the end drops exactly what was asked: the worst offenders and how many 500s each caused. That's the whole discipline — every stage is a small, total transformation, and you can stop the pipeline at any | to see the intermediate shape when something looks wrong. That "cut the pipe and look" habit is how you debug one-liners, and it's the lab you're about to do.

Lab 1Build — the top-offenders pipeline, one stage at a timeBuild

Build it incrementally and look at each intermediate result. This is how you write pipelines for real — never all at once.

bash
awk '$9==500 {print $1}' /tmp/access.log | head        # stage 1+2: just 500s, just the IP
awk '$9==500 {print $1}' /tmp/access.log | sort | head  # stage 3: identical IPs now adjacent
awk '$9==500 {print $1}' /tmp/access.log | sort | uniq -c        # stage 4: counted
awk '$9==500 {print $1}' /tmp/access.log | sort | uniq -c | sort -rn | head   # stage 5: ranked
Output 41 10.2.0.9 27 198.51.100.7 14 203.0.113.4

There's your answer: 10.2.0.9 caused 41 of the 500s. Notice awk did the work of a grep plus a cut in one step — $9==500 filters, {print $1} extracts. That's the idiom to reach for whenever you catch yourself chaining grep | cut.

Lab 2Understand — exit codes and pipefailUnderstand

Make the silent-failure problem visible, then fix it.

bash
grep 500 /tmp/nope.log | wc -l ; echo "exit=$?"    # file doesn't exist
Outputgrep: /tmp/nope.log: No such file or directory 0 exit=0

Exit 0 — "success" — even though grep failed. That's $? reporting only wc. Now see the truth two ways:

bash
grep 500 /tmp/nope.log | wc -l ; echo "codes=${PIPESTATUS[@]}"
set -o pipefail
grep 500 /tmp/nope.log | wc -l ; echo "exit=$?"
Outputcodes=2 0 ... exit=2

PIPESTATUS shows 2 0 — stage one failed, stage two didn't — and with pipefail the whole pipeline now reports 2. Put set -o pipefail in every script and this class of bug disappears.

Lab 3Break — the quoting disasterBreak

Reproduce the mistake that has wiped real directories, in a safe sandbox. Watch word-splitting turn one argument into many.

bash
mkdir -p /tmp/demo && cd /tmp/demo
touch "important file.txt" a b c
f="important file.txt"
for x in $f; do echo "would delete: [$x]"; done     # unquoted $f
Outputwould delete: [important] would delete: [file.txt]

One filename became two arguments because the shell split $f on the space. An unquoted rm $f would have tried to delete important and file.txt — not your file. Now the truly dangerous version: what does an empty or unset variable do?

bash
dir=""
echo rm -rf $dir/          # echo first — NEVER run the real thing to test

What did echo reveal the real command would have been? Work it out before you look — this is the exact bug behind famous production disasters.

Reveal — why this deletes the world

With dir="", $dir/ expands to just /, so rm -rf $dir/ becomes rm -rf /. The empty variable vanished and left the slash behind. Two habits prevent it forever: always quote (rm -rf "$dir/" would try to delete a directory literally named "/", which fails safely), and always set -u so an unset $dir aborts the script instead of expanding to nothing. Add : "${dir:?dir must be set}" at the top of destructive scripts to hard-fail on an empty value. And when in doubt, echo the command first — exactly as you just did.

Lab 4Troubleshoot — the script that isn't idempotentTroubleshoot

Here's a "reap old temp files" script a teammate wrote. Run it twice and watch it misbehave on the second run and on failure.

bash
cat > /tmp/reap.sh <<'EOF'
#!/usr/bin/env bash
work=/tmp/reap-work
mkdir /tmp/reap-work                 # fails on 2nd run: already exists
echo "scratch data" > "$work/scratch"
find /var/log -name '*.log' -mtime +7 > "$work/old"   # may find nothing
process_the_list "$work/old"         # a command that might not exist → error mid-run
rm -r /tmp/reap-work
EOF
bash /tmp/reap.sh ; echo "exit=$?"
bash /tmp/reap.sh ; echo "exit=$?"   # run again
ls -d /tmp/reap-work 2>/dev/null && echo "LEFTOVER dir still here"

You'll see it fail the second time (mkdir can't recreate the dir), and when the middle command errors it leaves /tmp/reap-work behind — so the next run is now guaranteed to fail too. What two changes make it safe to run any number of times, and clean up even when it crashes? Think before revealing.

Reveal — make it idempotent and self-cleaning

Two fixes. First, idempotency: use mkdir -p (succeeds whether or not the dir exists) or a fresh mktemp -d each run, so re-running is always safe. Second, guaranteed cleanup via a trap on EXIT, so the scratch dir is removed no matter how the script ends — success, error, or Ctrl-C. Here's the safe rewrite:

bash
#!/usr/bin/env bash
set -euo pipefail
work="$(mktemp -d)"                       # unique dir every run
trap 'rm -rf "$work"' EXIT                # always cleans up
echo "scratch data" > "$work/scratch"
find /var/log -name '*.log' -mtime +7 > "$work/old" || true   # tolerate no matches
echo "found $(wc -l < "$work/old") old logs"

Now every run gets its own directory, the trap removes it even on failure, and set -euo pipefail stops the script the instant a real error happens instead of blundering onward. Idempotency plus a cleanup trap is the backbone of every ops script you'll trust in cron.

Lab 5Production challenge — a safe script with signal handlingSenior challenge

Put it together: a script that holds a lock so two copies can't run at once, cleans up on any exit, and shuts down gracefully when Kubernetes sends it SIGTERM. This is the shape of a real maintenance job.

bash
cat > /tmp/job.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail

readonly LOCK=/tmp/job.lock
log() { printf '%s %s\n' "$(date -Is)" "$*" >&2; }   # structured-ish log to stderr

cleanup() { rm -f "$LOCK"; log "cleaned up, exiting"; }
trap cleanup EXIT
trap 'log "caught SIGTERM, finishing current item"; STOP=1' TERM INT

if ! ( set -o noclobber; : > "$LOCK" ) 2>/dev/null; then
  log "another run holds the lock; exiting"; exit 0        # idempotent: safe no-op
fi

STOP=0
for item in one two three four five; do
  [[ "$STOP" == 1 ]] && { log "stopping early, was on $item"; break; }
  log "processing $item"
  sleep 1
done
log "done"
EOF
bash /tmp/job.sh &
sleep 2 && kill -TERM %1     # simulate Kubernetes stopping the pod
wait
Output2024-... processing one 2024-... processing two 2024-... caught SIGTERM, finishing current item 2024-... stopping early, was on three 2024-... cleaned up, exiting

It finished the item it was on, then stopped cleanly and released the lock — no corruption, no orphaned lock file. Now the senior question, the one that decides whether this should even be bash: at what point should you rewrite this in Python?

Reveal — when bash stops being the right tool

Stop reaching for bash the moment you need any of these: real data structures (nested maps, anything past flat strings and simple arrays); parsing structured data like JSON, YAML, or XML (piping through jq once is fine; building logic around it is a smell); calling HTTP APIs with retries, pagination, and error handling; non-trivial math (bash is integer-only); concurrency you have to coordinate; and anything you need to unit-test or that will outlive a quick fix. A rough line: past ~100–200 lines, or the second time you fight quoting instead of writing logic, you've left bash's comfort zone. Bash is unbeatable glue for "run these commands in order, wire their I/O, check their exit codes." When the logic between the commands becomes the point, that's Python — Chapter 9.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · the cron job that "succeeded" for months

Symptom: a nightly job is green in every log, but the data it produces has been subtly wrong or stale for weeks. First cut: read the script for a pipeline without set -o pipefail and for a missing set -e. Confirm: add set -euo pipefail and re-run; watch it fail where it always silently did. Cause is usually: a mid-pipeline stage failing while the last stage returned 0, so $? — and therefore cron — saw success. The fix is strict mode plus checking PIPESTATUS where it matters.

Incident pattern · the destructive unquoted variable

Symptom: a script deleted, moved, or overwrote far more than intended. First cut: grep the script for unquoted $var in rm, mv, cp, and redirects, and for a variable that can be empty. Cause is usually: word-splitting a value with spaces, or an empty variable collapsing so rm -rf "$base/$sub" became rm -rf /-adjacent. The prevention is permanent: quote every expansion, run set -u, guard destructive paths with ${x:?}, and lint with ShellCheck in CI.

Incident pattern · the counter that resets to zero

Symptom: a script counts things in a while read loop fed by a pipe, but the total is always 0 afterward. First cut: look for … | while read line; do ((n++)); done; echo "$n". Cause is usually: the piped while runs in a subshell, so n is incremented in the child and lost when it exits. Fix by feeding the loop with process substitution — while read line; do …; done < <(command) — so the loop runs in the current shell and keeps its variables.

Production · security · performanceWhat matters in production

Strict mode is not optional. Every script you commit starts with #!/usr/bin/env bash and set -euo pipefail. It's the difference between a script that stops at the first problem and one that charges ahead corrupting state. Pair it with a cleanup trap … EXIT and idempotency (safe to run twice) and you've covered the majority of what makes shell automation dangerous.

Lint it. Run ShellCheck on every script, in your editor and in CI. It catches unquoted variables, useless-cat, subshell-loop bugs, and the [ ] vs [[ ]] traps automatically. There is no reason to ship unlinted shell; the tool knows the footguns better than you do at 3am.

Security lives in quoting and input. Never build a command out of untrusted input and eval it — that's shell injection, and it's how a filename or an environment variable becomes remote code execution. Quote everything, set a sane PATH at the top rather than trusting the caller's, use printf instead of echo for anything with user data, and treat every external string as hostile. A script that runs as root and interpolates untrusted input is a vulnerability with a shebang.

Know the ceiling, and cross it on purpose. Bash is glue: brilliant for orchestrating commands, wiring I/O, and gating on exit codes. It is bad at data structures, structured formats, HTTP with retries, floating-point math, testing, and anything long-lived. The mature move is not "always bash" or "never bash" — it's using bash for the ten-line orchestration and switching to Python the moment the logic between the commands becomes the hard part. Fighting quoting instead of writing logic is the tell that you've crossed the line.

Common mistakes beyond the incidents above: parsing ls output (use globs or find -print0 | xargs -0); forgetting that uniq needs a prior sort; assuming sort orders numbers without -n; and ignoring locale, which can make sort and grep behave differently across machines (pin LC_ALL=C for byte-stable, faster text processing in scripts).

System-design connectionWhere this reaches into architecture

Shell is the substrate the rest of the platform sits on, which is why fluency here pays off everywhere later. A container's ENTRYPOINT is almost always a shell script that sets up the environment and then execs the real process — and exec matters, because without it the shell stays PID 1 and swallows the SIGTERM Kubernetes sends to stop the pod gracefully (the signal-handling you just practised is the same problem, Chapter 30). Every CI/CD pipeline is a sequence of shell steps whose exit codes decide whether the build goes green (Chapter 73); a stage that swallows a failure ships a broken artifact. Health-check and readiness probes are frequently one-line shell tests. Init and bootstrap scripts, log-rotation, backup jobs, the "glue" between two systems that don't quite fit — all shell. The design lesson is where to draw the boundary: shell for orchestration at the edges, real programs and services for logic and state. Draw it well and your platform is debuggable; draw it badly — business logic buried in a 900-line bash script — and you've built something no one can safely change.

InterviewInterview questions & answers

Answer each in your head first.

30-secWhat does set -euo pipefail do?

It turns off bash's dangerous defaults. -e exits the script the moment any command fails instead of charging on. -u treats a reference to an unset variable as an error rather than silently expanding to empty — which is what stops the classic rm -rf $dir/ disaster. -o pipefail makes a pipeline fail if any stage fails, not just the last one, so a broken middle command can't be masked by a successful wc -l at the end. Together they make bash fail loud and early, which is exactly what you want in automation.

2-minWalk me through a pipeline to find the top 10 IPs causing HTTP 500s in an access log.

awk '$9==500 {print $1}' access.log | sort | uniq -c | sort -rn | head. awk reads each line, keeps only those where the 9th field — the status code in combined log format — is 500, and prints field 1, the client IP; that filters and extracts in one pass. sort puts identical IPs next to each other, which matters because uniq only collapses adjacent duplicates. uniq -c turns each run of the same IP into one line with a count. sort -rn re-sorts by that count, numerically, largest first. head keeps the top ten. I'd build it stage by stage, checking the intermediate output at each |, and in a script I'd run under set -o pipefail so a missing file doesn't look like success. If I needed to do more with the result than rank it, that's my cue to move to Python.

DeepWhy does cmd | while read x; do ((n++)); done; echo $n print 0, and how do you fix it?

Because each stage of a pipeline runs in its own process. The while loop on the right of the pipe runs in a subshell, so n++ increments a variable in that child process; when the subshell exits at the end of the pipeline, its environment — including n — is discarded, and the parent's n was never touched. It's the same fork-per-stage mechanics that make cd in a subshell not change your directory. The fix is to run the loop in the current shell instead of a subshell, by feeding it with process substitution: while read x; do ((n++)); done < <(cmd). Now the loop is in the parent, so n survives. Bash's shopt -s lastpipe (non-interactive shells) also runs the last pipeline stage in the current shell, but process substitution is the portable habit.

ScenarioA nightly cron script has reported success for months, but its output is wrong. How do you find out why?

My first suspicion is swallowed failure. I'd read the script for two things: a pipeline without set -o pipefail, and the absence of set -e. The classic cause is a pipeline like generate | transform | write where transform failed but write exited 0, so $? — and therefore cron's success/failure — only saw the last stage. I'd confirm by adding set -euo pipefail and inspecting ${PIPESTATUS[@]} after the suspect pipeline; I'd expect to see a nonzero code in a middle position. Other candidates: a while read subshell losing its accumulated result, an unquoted variable matching nothing, or a command whose failure was hidden inside an if or a local x=$(…). The durable fix is strict mode, explicit checks on the exit codes that matter, and running ShellCheck in CI so this never ships again.

Follow-upWhen would you refuse to write something in bash and reach for Python?

When the hard part stops being "run these commands in order" and becomes "the logic between them." Concretely: I need nested data structures, not flat strings; I'm parsing JSON/YAML and building real logic on it, not just piping through jq once; I'm calling an HTTP API with retries, pagination, timeouts, and typed error handling; I need floating-point math, which bash can't do; I need concurrency I have to coordinate; or I need to unit-test the code. A practical threshold is around 100–200 lines, or the second time I'm fighting quoting instead of writing logic. Bash stays unbeatable for the thin orchestration layer — the container entrypoint, the CI step, the glue — and I keep it there deliberately rather than letting business logic accrete into an unmaintainable script.

RetainQuick revision

Bash is the universal glue: it stands up pipelines of small, single-purpose programs and wires their standard streams together with kernel pipes, running every stage concurrently. Its defaults are unsafe — it continues after errors, splits unquoted variables on whitespace, and hides all but the last exit code in a pipeline — so every real script opens with set -euo pipefail, quotes every expansion, and installs a cleanup trap … EXIT. $? is only the last stage; ${PIPESTATUS[@]} and pipefail reveal the rest. The core toolkit is grep (filter), awk (columns and logic), sed (edit), cut/sort/uniq (shape and count), and xargs (list to arguments); the "top N of anything" idiom is sort | uniq -c | sort -rn | head. Build pipelines one stage at a time and look at each intermediate. Write scripts to be idempotent and to handle SIGTERM gracefully. And when the logic between commands becomes the point — data structures, JSON, HTTP, tests, ~150+ lines — stop, and switch to Python.

The 10 things to remember

  1. A pipeline is N concurrent processes; each | is a kernel pipe from one's stdout to the next's stdin.
  2. $? is only the last stage's exit code — use ${PIPESTATUS[@]} and set -o pipefail to catch mid-pipe failures.
  3. Start every script with set -euo pipefail; know that -e won't fire inside if/&&/||/local x=$(…).
  4. Quote every expansion ("$var", "$@"); unquoted variables word-split and glob, and empty ones collapse dangerously.
  5. set -u plus ${x:?msg} stops the empty-variable rm -rf $dir/ catastrophe cold.
  6. awk filters and extracts columns in one pass — reach for it when you're chaining grep | cut.
  7. uniq only collapses adjacent lines, so it's always sort | uniq; ranking is sort -rn | head.
  8. Make scripts idempotent (mkdir -p, mktemp -d) and install trap cleanup EXIT so failures don't leave state behind.
  9. Handle SIGTERM/INT with a trap so cron and Kubernetes can stop your job cleanly; exec the real process in entrypoints.
  10. Bash is for orchestration; when you need data structures, JSON, HTTP, math, or tests, switch to Python.
