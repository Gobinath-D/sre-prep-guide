Python for SRE automation

When the logic between your commands becomes the hard part, bash stops paying its way. Python is the ops lingua franca that picks up where it leaves off: real data structures, real error handling, and — the part that separates a script from a tool — something you can actually test.

Start: Beginner→→→End: Staff-level ~40 min read · Python 3 lab (Docker)

By the end of this chapter you can

  • Structure a Python CLI tool properly: main(), argparse, functions, and the if __name__ == "__main__" guard.
  • Call an HTTP API with a timeout and exit with meaningful, automation-friendly exit codes.
  • Run subprocesses safely — no shell=True injection, always a timeout, always a checked return code.
  • Handle errors deliberately, log to stderr, and never dump a raw traceback at an operator.
  • Write a pytest test by isolating the I/O boundary, and package the tool as an installable command.

Why this exists · the problemThe problem: automation that has to last

Chapter 8 ended with a line: the moment the logic between your commands becomes the point, walk away from bash. This is where you walk to. The tasks that cross that line share a shape — they hold state in structures more complex than a flat list, they talk to APIs that return JSON and fail in a dozen ways, they need retries and timeouts and clear exit codes, and, above all, they're going to be run by other people for years after you write them. A 200-line bash script doing that is a liability; the same thing in Python is a tool.

Python won this job for boring, decisive reasons. It's already on every Linux box and in every base image. Its standard library covers the ops surface — HTTP, JSON, subprocesses, filesystem, logging, argument parsing — without a single dependency. It reads closely enough to pseudocode that the next on-call can understand it under pressure. And it has a real testing story, which is the thing that turns "a script that worked once on my laptop" into "automation the team trusts in production."

That last point is the whole reason this chapter exists. Anyone can make Python do a thing. The difference between a junior's script and a senior's tool is everything around the doing: the arguments are parsed and validated, the HTTP call has a timeout, the failure modes each map to a distinct exit code, the errors are logged instead of crashing, and there's a test that proves the logic without hitting the network. Get those right and your automation outlives you gracefully.

Key point

The value of ops code isn't that it runs — it's that it keeps running correctly when you're not watching, and that the next person can change it without fear. That comes from structure, explicit error handling, and tests. Python gives you all three cheaply; use them, or you've just written slower bash.

Mental model · analogyThe mental model: a well-run service desk

Think of a good CLI tool as a small, disciplined service desk, not a person frantically doing everything at once.

Real-world analogy

A request arrives at the desk. First it goes to the intake clerk, who checks the form is filled in correctly and rejects it politely if not — that's argparse, validating your arguments before any work starts. The clerk hands a clean request to the back office, which does the actual job in small, named steps — your functions. When the job needs something from another department, the desk uses the phone line — an HTTP call to an API, or a runner sent to fetch something — a subprocess — always with a rule: if there's no answer in thirty seconds, hang up (the timeout).

Everything the desk does goes in the logbook — logging to stderr — so there's a record separate from the actual result it hands back. And when the request is finished, the desk stamps it with a clear verdict: done, couldn't do it, don't know — the exit code, which the automation upstream reads to decide what happens next. Finally, a good desk has a QA reviewer who runs sample requests through it regularly to confirm it still behaves — your tests. A script without that reviewer is a desk nobody has checked since the day it opened.

ArchitectureThe anatomy of a CLI tool

Every well-structured ops tool has the same skeleton, and it's worth internalising because you'll type it hundreds of times. Arguments come in the top, get validated, flow through a coordinating main() into worker functions that talk to the outside world with timeouts, and a verdict comes out the bottom as an exit code — with a running commentary in the logs. Here's the runtime shape, including where it branches on failure.

The three-channel discipline at the bottom is what makes a tool composable. Results go to stdout so another program can consume them; logs go to stderr so they don't pollute that output; and the exit code is the machine-readable verdict that lets a monitoring system, a CI step, or a shell && chain decide what happens next. Mix these up — print logs to stdout, or always exit 0 — and your tool can't be automated against, which defeats the purpose.

Internal workingWhat happens when you run it

Understanding the runtime keeps you from being surprised by tracebacks, exit codes, and subprocess behaviour.

  1. The interpreter starts and builds sys.argv. python check.py --url x launches the CPython interpreter, which reads your file and populates sys.argv with the command-line words. Running as python -m tool instead imports it as a module — the reason for the if __name__ == "__main__" guard, which runs your main() only when the file is executed directly, not when it's imported (by a test, say).
  2. argparse builds a parser and validates. parse_args() matches your definitions against sys.argv. If something required is missing or the wrong type, argparse prints a usage message to stderr and exits with code 2 on its own — you don't write that logic, you get it for free.
  3. main() coordinates; functions do the work. Control flows into your worker functions. Each returns a value or raises an exception on failure — Python's error channel is exceptions, not return codes, which is why you handle them with try/except rather than checking $? after every call.
  4. The HTTP or subprocess call crosses the boundary. urllib.request.urlopen(req, timeout=5) opens a socket and blocks until a response or the timeout — the same syscalls from Chapter 1, one layer up. subprocess.run([...]) does a fork()+exec() exactly like the shell does, which is why you pass a list of arguments (no shell to word-split them) and why shell=True with untrusted input is an injection hole.
  5. Exceptions propagate; the traceback is the default failure. An unhandled exception unwinds the stack, prints a traceback to stderr, and exits with code 1. That traceback is a gift to you and an insult to your operator — great for debugging, terrible as a user-facing failure. Handling errors means catching the specific exceptions you expect and turning them into a clear message plus a chosen exit code.
  6. The exit code is the last word. sys.exit(main()) makes the interpreter exit with whatever integer main() returned. That integer is what every automation upstream actually reads. 0 is success; the meaning of nonzero is yours to define and document — and for check-style tools there's a widely-used convention: 0 OK, 1 WARNING, 2 CRITICAL, 3 UNKNOWN.
The two mistakes that make ops code untrustworthy

No timeout, and bare except. A network call without a timeout can hang forever — your "health check" becomes the thing that never returns, and now you have two incidents. Always pass timeout= to every call that touches the network or another process. And except: (or except Exception:) that swallows everything will also swallow KeyboardInterrupt and the very bug you needed to see, then probably exit 0 as if all was well. Catch the specific exceptions you expect; let the ones you don't crash loudly.

Think first: your Python check script hangs in production and never exits, wedging the monitoring that calls it. What's the most likely cause, and the one-line fix?

A network or subprocess call with no timeout, blocked on something that will never answer — a dead endpoint, a hung DNS lookup, a child process waiting on input. The fix is to pass an explicit timeout to every boundary call: urlopen(req, timeout=5), subprocess.run([...], timeout=10), and a socket-level default as a backstop. A check that can hang forever is worse than one that fails, because it takes the caller down with it and reports nothing. Timeouts turn "hangs silently" into "fails with a clear UNKNOWN," which is a state your automation can act on.

ComponentsThe stdlib ops toolbox

You can build almost any ops tool from the standard library alone, which keeps your dependencies — and your supply-chain risk — near zero. The pieces, each filed by what it owns:

  • argparse — the front door. Declares your arguments (required, typed, with defaults and help), validates them, and generates --help and usage errors. It's the intake clerk; nothing should reach your logic unvalidated.
  • subprocess — calling other programs. subprocess.run([...], capture_output=True, text=True, timeout=10, check=True). Pass a list (never a string with shell=True on untrusted input), capture output, set a timeout, and let check=True raise on a nonzero exit. This is how Python does what bash does natively — carefully.
  • urllib.request (or requests) — HTTP. The stdlib urllib needs no install and is fine for straightforward calls; the third-party requests is friendlier for sessions, retries, and JSON. Either way: always a timeout, always handle the error classes, and check the status.
  • json — structured data. json.loads/json.dumps. The reason you left bash: parsing an API response into real dicts and lists and working with them, instead of wrestling jq and string-mangling.
  • logging — the record. logging.basicConfig(level=…, stream=sys.stderr) then log.info/warning/error. Structured, level-filtered output to stderr, separate from your result. Never print() your diagnostics into stdout.
  • pathlib and os — the filesystem and environment. pathlib.Path for clean, cross-platform path handling; os.environ for configuration and secrets passed by environment (never hard-code them).
  • sys — the process interface. sys.argv, sys.exit(code), sys.stdout/sys.stderr. The direct line to the exit-code and channel discipline the whole design rests on.
  • pytest — the QA reviewer. Plain functions named test_* with assert. Combined with monkeypatch to replace the I/O boundary, it lets you test all your logic — including every failure branch — without a network. This is the component that makes the difference between a script and a tool.
  • Packaging — pyproject.toml. A few lines that turn your file into an installable command with a real entry point, pinned dependencies, and a version. It's how the tool stops being "that script on the jump box" and becomes something the team installs and upgrades.
Think first: your tool prints results and debug lines with print(). A colleague pipes its output into another script and it breaks. Why?

Because print() writes to stdout, so your debug chatter is now mixed into the same stream as the real results — and the downstream script, which expected only clean results on stdout, chokes on the noise. The fix is the three-channel discipline: results to stdout, diagnostics to stderr (that's what logging does by default, or print(..., file=sys.stderr)), and the verdict in the exit code. Then a consumer can do yourtool | jq . and get exactly the data, while a human still sees the logs on the terminal. Muddling stdout is the single most common reason an otherwise-working tool can't be composed with others — and composability is the whole point of a CLI.

Data flowFollowing one invocation

Trace a single run of the health-check tool you'll build. You run healthcheck --url https://api.internal/health --timeout 5. The interpreter starts and fills sys.argv; argparse confirms --url is present and --timeout is a float, and — had you fat-fingered the flag — it would have printed usage to stderr and exited 2 without any work happening. main() configures logging to stderr and calls http_get(url, timeout). That opens a socket, sends the request, and blocks — but only for five seconds, because of the timeout. Three things can come back: a 200, which the tool logs as OK, prints a one-line result to stdout, and returns exit 0; an HTTPError for a 4xx/5xx, which it logs as CRITICAL and returns exit 2; or a timeout or connection error, which it logs as UNKNOWN and returns exit 3. Whatever happens, the operator sees a readable log line on stderr, any consumer sees a clean result on stdout, and the monitoring system that called it reads the exit code and decides whether to page. One invocation, three channels, every failure mode named — that's the tool you're about to write and test.

Lab 1Build — scaffold the CLI toolBuild

Write the skeleton every tool shares: argparse, a main(), worker functions, and the guard. Save as check.py.

python
#!/usr/bin/env python3
"""Check an HTTP endpoint and exit with a monitoring-style code."""
import argparse, logging, sys
import urllib.request, urllib.error

OK, WARN, CRIT, UNKNOWN = 0, 1, 2, 3
log = logging.getLogger("healthcheck")

def http_get(url: str, timeout: float) -> int:
    """Return the HTTP status code, or raise. This is the I/O boundary."""
    req = urllib.request.Request(url, method="GET")
    with urllib.request.urlopen(req, timeout=timeout) as resp:
        return resp.status

def check(url: str, timeout: float) -> int:
    """Pure logic: turn the outcome into an exit code. Easy to test."""
    try:
        status = http_get(url, timeout)
    except urllib.error.HTTPError as e:
        log.error("%s returned HTTP %s", url, e.code)
        return CRIT
    except (urllib.error.URLError, TimeoutError) as e:
        log.error("%s unreachable: %s", url, e)
        return UNKNOWN
    if status == 200:
        log.info("%s OK (200)", url)
        print(f"OK {url} 200")
        return OK
    log.warning("%s returned %s", url, status)
    return WARN

def parse_args(argv=None):
    p = argparse.ArgumentParser(description="HTTP health check")
    p.add_argument("--url", required=True, help="endpoint to check")
    p.add_argument("--timeout", type=float, default=5.0)
    p.add_argument("-v", "--verbose", action="store_true")
    return p.parse_args(argv)

def main(argv=None) -> int:
    args = parse_args(argv)
    logging.basicConfig(
        level=logging.DEBUG if args.verbose else logging.INFO,
        format="%(asctime)s %(levelname)s %(message)s", stream=sys.stderr)
    return check(args.url, args.timeout)

if __name__ == "__main__":
    sys.exit(main())

Run it against a real endpoint and inspect the exit code:

bash
python check.py --url https://example.com ; echo "exit=$?"
Output2024-... INFO https://example.com OK (200) OK https://example.com 200 exit=0

Notice the split already working: the INFO line went to stderr, the OK … result to stdout, and the exit code is 0. Three channels, each doing its job. The two functions are deliberately separated — http_get is the only part that touches the network, and check is pure logic. That separation is what makes Lab 5's test trivial.

Lab 2Understand — exit codes as an interfaceUnderstand

The exit code is a contract with whatever runs your tool. Prove each branch produces the code you designed.

bash
python check.py --url https://example.com/nope ; echo "exit=$?"   # 404 → CRIT (2)
python check.py --url https://10.255.255.1 --timeout 2 ; echo "exit=$?"  # unroutable → UNKNOWN (3)
python check.py ; echo "exit=$?"                                  # missing --url → argparse exits 2
Output (trimmed)2024-... ERROR https://example.com/nope returned HTTP 404 exit=2 2024-... ERROR https://10.255.255.1 unreachable: <urlopen error timed out> exit=3 usage: check.py [-h] --url URL [--timeout TIMEOUT] [-v] check.py: error: the following arguments are required: --url exit=2

Now you can chain it: python check.py --url X && ./deploy.sh only deploys if the check passes. That composability is the entire reason to be strict about exit codes. The convention here — 0/1/2/3 as OK/WARN/CRIT/UNKNOWN — is the one Nagios-style monitoring expects, so this tool drops straight into a monitoring pipeline.

Lab 3Break — the traceback and the hangBreak

See what bad error handling looks like from the operator's chair. Temporarily break check by removing the except clauses (just call http_get directly) and hit a dead host with no timeout:

python
# A deliberately bad version — no timeout, no handling:
import urllib.request
urllib.request.urlopen("http://10.255.255.1")   # hangs... then, eventually:
Output (after a long wait)Traceback (most recent call last): File "<stdin>", line 1, in <module> ... urllib.error.URLError: <urlopen error [Errno 113] No route to host>

Two failures at once: it hung with no timeout, and when it finally died it vomited a traceback with an exit code of 1 — no distinction between "endpoint down" and "your code has a bug." Why is a raw traceback the wrong thing to show an operator, and what should the tool do instead? Decide before revealing.

Reveal — what good error handling gives you

A raw traceback is a debugging artifact aimed at you, the author. To the operator at 3am it's noise that buries the one fact they need — what failed and what to do about it. And because every unhandled exception exits 1, automation can't tell a real outage from a typo in your code. The fix is exactly what Lab 1 already does: catch the specific exceptions you expect (HTTPError, URLError, TimeoutError), log a one-line human message, and return a distinct exit code per failure class. Let exceptions you didn't expect crash with their traceback — those are bugs you want to see loudly, not swallow. "Handle what you predicted; crash on what you didn't" is the rule.

Lab 4Troubleshoot — subprocess done wrongTroubleshoot

A teammate's tool shells out to ping to check a host. It works in the demo and is a security hole in production. Run it and see the problem.

python
import subprocess
def ping_bad(host):
    # DANGER: shell=True + string interpolation = injection
    return subprocess.run(f"ping -c1 {host}", shell=True).returncode

ping_bad("example.com")                 # works...
ping_bad("example.com; echo PWNED")     # ...and runs arbitrary commands
OutputPING example.com ... PWNED

The injected echo PWNED ran — with an attacker-controlled host that could be rm -rf or worse. There are three separate problems here: injection, no timeout, and no check of the result. What does the safe version look like? Work it out, then reveal.

Reveal — the safe subprocess pattern

Pass arguments as a list so there's no shell to interpret them, add a timeout, and check the return code deliberately:

python
import subprocess
def ping(host: str) -> bool:
    try:
        r = subprocess.run(
            ["ping", "-c1", "-W2", host],   # list = no shell, no injection
            capture_output=True, text=True, timeout=5, check=True)
        return True
    except subprocess.CalledProcessError:   # ping exited nonzero (host down)
        return False
    except subprocess.TimeoutExpired:       # didn't finish in 5s
        return False

With a list, "example.com; echo PWNED" is passed to ping as a single (invalid) hostname — ping just fails, nothing executes. This is the same lesson as bash quoting in Chapter 8: untrusted input must never become executable syntax. Reach for shell=True only with fully-trusted, static strings, and even then, prefer the list.

Lab 5Production challenge — test it, then package itSenior challenge

The thing that turns a script into a tool: a test that proves the logic without touching the network, and a package that installs as a real command. Because Lab 1 kept the I/O in http_get and the logic in check, you can replace the boundary and test every branch. Save as test_check.py:

python
import urllib.error
import check

def test_ok(monkeypatch):
    monkeypatch.setattr(check, "http_get", lambda url, timeout: 200)
    assert check.check("http://x", 1) == check.OK

def test_500_is_critical(monkeypatch):
    def boom(url, timeout):
        raise urllib.error.HTTPError(url, 500, "err", {}, None)
    monkeypatch.setattr(check, "http_get", boom)
    assert check.check("http://x", 1) == check.CRIT

def test_timeout_is_unknown(monkeypatch):
    def boom(url, timeout):
        raise TimeoutError("timed out")
    monkeypatch.setattr(check, "http_get", boom)
    assert check.check("http://x", 1) == check.UNKNOWN
bash
pytest -q
Output... [100%] 3 passed in 0.03s

Three failure branches proven in 30 milliseconds, offline. Now package it so it's an installable command, not a loose file. Create pyproject.toml:

toml

[build-system]

bash
pip install -e .
healthcheck --url https://example.com ; echo "exit=$?"   # now a real command on PATH

Now the senior question: which one design choice in Lab 1 made this test possible, and how would you argue for it in code review? Think it through.

Reveal — the choice that makes ops code testable

Isolating the I/O at a single boundary. http_get is the only function that touches the network; check is pure decision logic over its result. That one seam lets a test swap http_get for a stub and exercise every branch — OK, CRITICAL, UNKNOWN — deterministically and offline. If the HTTP call had been buried inside a 60-line main(), you could only test it by hitting a real (or faked) server, which is slow, flaky, and often skipped. The review argument is simple and it's the core of testable ops code: push side effects to the edges and keep the logic pure in the middle. Everything hard to test — network, disk, subprocess, clock — goes behind a thin function you can replace. Do that and your automation earns the trust to run unattended.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · the automation that hangs

Symptom: a scheduled job or health check stops returning; the thing meant to detect problems is now itself stuck, and nothing pages. First cut: strace -p <pid> or py-spy dump --pid <pid> — it's parked in a socket read or a wait. Cause is usually: a network call or subprocess with no timeout, blocked on a dead endpoint or a child waiting for input. The fix is a timeout on every boundary call, plus an overall wall-clock guard.

Incident pattern · the tool that always exits 0

Symptom: a check reports healthy while the thing it checks is broken, so no alert fires. First cut: read for a bare except: that swallows the error and falls through to a return 0, or a main() with no sys.exit(...). Cause is usually: over-broad exception handling hiding the failure, or forgetting that returning from main() without sys.exit exits 0. Catch specific exceptions and map each to a real exit code.

Incident pattern · works on my machine, breaks in the pod

Symptom: a tool runs on the author's laptop and crashes in production with an import error or wrong behaviour. First cut: compare Python versions and installed packages; check whether it relied on a globally-installed dependency. Cause is usually: no pinned dependencies and no virtualenv — the laptop had a package the container doesn't, or a different Python. The fix is packaging with pinned deps (a lockfile or exact versions) and running in a clean environment, so "it worked here" means "it works everywhere."

Production · security · performanceWhat matters in production

Stdlib first, dependencies deliberately. Every third-party package is a version to track and a supply-chain risk to own. For most ops tools, urllib, json, subprocess, and logging are enough. When you do add a dependency — requests, boto3, a Kubernetes client — pin it exactly and install into a virtualenv or a locked container image, never against the system Python. "Works on my machine" is almost always an unpinned-dependency story.

Timeouts and exit codes are non-negotiable. Every call that leaves the process — HTTP, subprocess, DNS, database — gets an explicit timeout, because a tool that can hang is worse than one that fails. And every exit path returns a documented code, because that's the only thing your monitoring and CI can act on. These two habits, more than any clever code, are what make automation safe to run unattended.

Security. Never build a shell command from untrusted input — pass argument lists to subprocess and keep shell=True away from anything a user or an API can influence. Read secrets from the environment or a secrets manager, never from source or command-line arguments (which land in ps and shell history). Validate and constrain inputs at the argparse boundary. The injection lesson from bash is identical here; the language changed, the discipline didn't.

Test the logic, log the actions. Push side effects to thin boundary functions so the decision logic stays pure and testable, and write tests for the failure branches specifically — the happy path rarely breaks, the error paths do. Log to stderr at sensible levels so an operator can see what the tool did and a machine can still consume stdout. Add type hints and run mypy if the tool grows; it catches a class of bugs before runtime.

Know Python's ceiling too. Python is close to perfect for ops glue and control-plane logic, but it's slow for hot loops and its threading is limited by the GIL for CPU-bound work. When you need a single static binary, heavy concurrency, or predictable low-latency performance — a high-throughput controller, a network proxy, a CLI shipped to thousands of machines — that's the argument for Go (Chapter 121). Most of the time Python is right; know when it isn't.

System-design connectionWhere this reaches into architecture

Python is the layer just above the glue — where a platform's operational intelligence lives. The custom Prometheus exporter that scrapes a system's metrics (Chapter 75), the ChatOps bot that runs runbooks, the CI helper that gates a deploy, the internal CLI every engineer uses to talk to your platform, the small controller that reconciles some resource Kubernetes doesn't natively know about — these are overwhelmingly Python. The design principle that carries over is the one from the labs: isolate side effects at the edges, keep logic pure and tested in the middle. That's not just a testing trick; it's the same boundary thinking that separates a stateless service from its datastore, or a controller's reconcile logic from the API calls it makes. Tools built this way are the ones a platform team can hand off, extend, and trust — and untested automation that touches production is, in the end, just a faster way to cause an incident. The reliability of your automation is part of the reliability of your system.

InterviewInterview questions & answers

Answer each in your head first.

30-secWhy if __name__ == "__main__"?

It makes the block run only when the file is executed directly, not when it's imported as a module. That matters because it lets a test import your tool to call its functions without triggering the whole program to run, and it lets other code reuse your functions cleanly. The idiom is if __name__ == "__main__": sys.exit(main()) — so the script's behaviour is in main(), importable and testable, and the guard just wires it to the command line.

2-minHow do you structure a production CLI tool in Python?

A fixed skeleton. argparse at the front to declare, validate, and document arguments — it handles usage errors and exits 2 on bad input for free. A main(argv=None) that configures logging to stderr and coordinates the work, returning an integer exit code. The actual work split into small functions, with the I/O — HTTP, subprocess, filesystem — isolated behind thin boundary functions so the logic in the middle stays pure and testable. Every external call gets an explicit timeout. Errors are handled by catching the specific exceptions I expect and mapping each to a distinct, documented exit code, while unexpected exceptions crash loudly. Output discipline: results to stdout, logs to stderr, verdict in the exit code. Then a pytest suite that stubs the boundaries to test every branch offline, and a pyproject.toml so it installs as a real command with pinned dependencies. That structure is what makes it safe to run unattended and easy for the next person to change.

DeepWhy is subprocess.run(f"cmd {x}", shell=True) dangerous, and what's the right way?

With shell=True, Python hands the whole string to /bin/sh, which interprets shell metacharacters — so if x is attacker- or user-controlled, a value like "host; rm -rf /" runs a second command. It's shell injection, the same class as SQL injection. The right way is to pass a list of arguments — subprocess.run(["cmd", x], ...) — with no shell=True; then there's no shell to interpret anything, and x is passed as a single literal argument no matter what it contains. I'd also always add a timeout so it can't hang, and either check=True to raise on failure or an explicit check of returncode. Reserve shell=True for fully-static, trusted strings where you actually need a pipe or a glob — and even then a list is usually cleaner.

ScenarioYour monitoring calls a Python check script, and one day it stops reporting entirely — no OK, no alert. What happened and how do you prevent it?

The script is almost certainly hung on a boundary call with no timeout — an HTTP request or subprocess blocked on a dead dependency — so it never returns an exit code, and the monitoring is stuck waiting on it. I'd confirm by looking at the process: it'll be parked in a socket read (strace -p or a Python stack dump shows it). Two failures compound here: the missing timeout, and often a bare except that would have hidden a related error. Prevention is a timeout on every external call, an overall wall-clock budget for the whole check, and mapping every outcome — including "couldn't tell" — to a real exit code, so the worst case is a fast UNKNOWN the monitoring can act on rather than an indefinite hang. A health check that can hang is an outage generator.

Follow-upWhen would you write ops automation in Go instead of Python?

When Python's weaknesses become the bottleneck. Three cases mainly: I need a single static binary with no runtime or dependency to install — a CLI shipped to thousands of hosts, or a tool that has to run in a scratch container; I need heavy concurrency or CPU-bound throughput, where Python's GIL and interpreter overhead hurt and Go's goroutines and compilation win; or I'm building something latency-sensitive and long-running, like a controller or proxy in the request path, where predictable performance matters. For the vast majority of ops work — glue, API calls, report generation, one-shot tools — Python's speed of writing and its stdlib make it the right default, and the runtime cost is irrelevant. I switch to Go deliberately when distribution, concurrency, or performance is the actual requirement, not by habit.

RetainQuick revision

Python takes over from bash when the logic between commands becomes the point — data structures, JSON, HTTP with error handling, and code that must be tested and maintained for years. A well-built tool has one skeleton: argparse validates and documents the arguments and exits 2 on bad input; main() configures logging to stderr and coordinates small functions; the I/O — HTTP, subprocess, filesystem — is isolated behind thin boundary functions with explicit timeouts on every call; errors are handled by catching the specific exceptions you expect and mapping each to a distinct exit code, while unexpected ones crash loudly. Keep the three channels separate: results to stdout, logs to stderr, verdict in the exit code. Call subprocesses with argument lists, never shell=True on untrusted input. The move that makes ops code trustworthy is isolating side effects at the edges so the middle stays pure and testable — then a pytest suite proves every failure branch offline, and a pyproject.toml ships it as a real, pinned, installable command. Reach for Go only when distribution, concurrency, or latency demands it.

The 10 things to remember

  1. The skeleton is always the same: argparse → main() → small functions → if __name__ == "__main__": sys.exit(main()).
  2. Three channels, three jobs: stdout = result, stderr = logs, exit code = machine-readable verdict.
  3. Define exit codes deliberately; for checks, 0/1/2/3 = OK/WARN/CRIT/UNKNOWN is the standard convention.
  4. Every network or subprocess call gets an explicit timeout — a tool that can hang is worse than one that fails.
  5. Catch the specific exceptions you expect and map each to an exit code; let unexpected ones crash loudly. Never bare except.
  6. Call subprocesses with an argument list, not shell=True + string — that's injection, the same bug as bash quoting.
  7. Isolate I/O behind thin boundary functions so the decision logic stays pure — that's what makes it testable.
  8. Write pytest tests for the failure branches specifically, stubbing the boundary so they run offline in milliseconds.
  9. Stdlib first (urllib, json, subprocess, logging); pin any dependency and install into a clean environment.
  10. Package with pyproject.toml and an entry point so it's a real command; reach for Go only for distribution, concurrency, or latency.
