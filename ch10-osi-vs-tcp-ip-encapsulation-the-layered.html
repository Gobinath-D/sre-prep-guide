Part II · Networking from First Principles · Chapter 10

OSI vs TCP/IP, encapsulation, the layered model

Getting bytes from your app to a server across the planet is too big a problem to solve at once — so the internet doesn't. It splits the job into layers, each solving one thing and trusting the one below. Learn where the seams are and every network fault stops being "the network is down" and becomes "this layer owns this problem."

Start: Beginner→→→End: Staff-level ~45 min read · Linux lab (Docker)

By the end of this chapter you can

  • Explain why networking is layered, and map the OSI 7-layer model onto the 4-layer TCP/IP model the internet actually runs.
  • Describe exactly what each header adds — ports, IP addresses, MAC addresses — and who reads and strips it.
  • Walk encapsulation on the way out and decapsulation on the way in, and say which addresses change at each hop and which don't.
  • Capture one real HTTP request with tcpdump and point at the Ethernet, IP, and TCP headers in the bytes.
  • Localise a fault by layer — the master reflex that the rest of Part II is built on.

Why this exists · the problemThe problem: one job too big to solve at once

Say you type curl https://api.example.com on your laptop in a café and a server in another country answers. Think about everything that has to be true for that to work. Something has to know which application on that server the bytes are for. Something has to make sure none of the bytes are lost, duplicated, or reordered on a 10,000-kilometre trip over dozens of unreliable hops. Something has to figure out a route across networks owned by companies that have never heard of each other. Something has to actually put electrical or optical signals onto the café's Wi-Fi, then copper, then fibre. And all of it has to work between a MacBook, a Linux server, a Cisco router, and a phone — none of which share code.

Try to design one program that does all of that and you get a monster nobody can build, test, or replace. So the internet's designers did the only thing that scales: they cut the problem along its natural seams and stacked the pieces. Each layer solves exactly one concern and assumes the layer beneath it already solved the ones below. The application layer worries about "what does this request mean" and trusts that the bytes will arrive. The transport layer worries about "get these bytes there reliably, to the right app" and trusts that individual packets can be delivered. The network layer worries about "route this packet toward that address" and trusts the link below to move it one hop. The link layer worries about "put this on the wire to the next box" and trusts the physical layer to carry the signal.

That decomposition buys three things that made the modern internet possible. Independent evolution: IPv4 could give way to IPv6 without rewriting TCP or HTTP, because the layers only touch through a thin contract. Interoperability: any two machines that agree on the layer contracts can talk, regardless of vendor or OS. And, the one you'll use every single day, fault isolation: when something breaks, the layers tell you where to look, so "the network is broken" becomes a specific, answerable question.

Key point

Layering is not academic. It is the single most useful troubleshooting tool in networking. Every fault lives at one layer, and the symptom tells you which. "Can I reach the host at all?" is a different layer from "is the right app answering?" — and mixing them up is why people waste hours restarting the wrong thing.

Mental model · analogyThe mental model: nested envelopes in the post

The mechanism that makes layering work on the wire is encapsulation: each layer wraps the layer above it in its own envelope, adding a header that only its counterpart on the far side will read.

Real-world analogy

You want to send a document to a specific colleague in a company across the country. You don't hand it to a courier and hope. You put the document — the actual content — inside an inter-office envelope marked with the colleague's name and desk number. That goes inside a shipping parcel addressed to the company's street address. The parcel goes into the courier's mail sack for the next depot on the route.

Now watch who reads what. The long-haul courier only reads the mail-sack tag — the next depot. It never opens the parcel; it doesn't care about the street address yet, and it certainly doesn't read your document. At each depot the sack tag is stripped and a new one added for the next depot, while the parcel's street address stays exactly the same the whole way. Only when the parcel reaches the destination building does someone open it, read the inter-office envelope, and walk the document to the right desk. Each label is read and removed by its own peer in the chain, and the innermost content is touched only by the two people who actually correspond.

In the postOn the network
The document itselfApplication data (the HTTP request, the DNS query)
Inter-office envelope with a desk numberTCP/UDP header — the port picks the app on the host
Parcel with the company's street address (unchanged all the way)IP header — source and destination IP addresses, end-to-end
Mail-sack tag for the next depot (replaced at each depot)Ethernet header — next-hop MAC address, rewritten every hop
The trucks, roads, and sorting beltsThe physical layer — signals on Wi-Fi, copper, fibre

Hold onto the two addresses that behave differently, because it's the thing people forget: the IP address is like the street address — it stays the same the entire journey, source and destination fixed end to end. The MAC address is like the mail-sack tag — it's replaced at every hop, always naming just the next box along the way. That single fact explains most of L2 and L3 (Chapters 11 and 12).

ArchitectureTwo models, one stack of headers

There are two ways people name the layers. The OSI model (from ITU-T X.200 / ISO 7498) has seven layers and is the vocabulary everyone uses in conversation — "that's a layer 7 problem," "we need a layer 4 load balancer." The TCP/IP model (from RFC 1122) has four and is what the internet actually implements. They line up cleanly; OSI just splits the top into more pieces than the real stack bothers with.

OSI (7 layers)TCP/IP (4 layers)PDU & addressExample
7 Application · 6 Presentation · 5 SessionApplicationdata / messageHTTP, DNS, TLS
4 TransportTransportsegment (TCP) / datagram (UDP) — portTCP, UDP
3 NetworkInternetpacket — IP addressIPv4, IPv6, ICMP
2 Data Link · 1 PhysicalLinkframe — MAC address · then bitsEthernet, Wi-Fi, ARP

Now the part that matters most: what happens to your data as it goes down the stack. Each layer prepends its own header, so by the time your HTTP request hits the wire it's wrapped in three envelopes. Here is that encapsulation, and the actual bytes it produces.

Two structural details from that picture pay off constantly. First, each header carries a "what's inside me" field so the receiver knows who to hand the payload to next: Ethernet's EtherType (0x0800 = IPv4, 0x0806 = ARP), IP's protocol number (6 = TCP, 17 = UDP, 1 = ICMP), and TCP's destination port (80, 443). Those are the values IANA registers so every implementation agrees. Second, the headers are pure overhead — every byte of header is a byte you didn't send of payload — which is why the maximum payload (the MSS) is the link's MTU minus the IP and TCP headers, and why anything that adds another layer of wrapping, like a VPN or a Kubernetes overlay, has to shrink the usable size to fit.

Internal workingEncapsulation out, decapsulation in

Follow the bytes through the kernel, step by step. On the way out, the stack builds the envelopes from the inside out.

  1. The app writes data. curl calls write() on a socket with GET / HTTP/1.1\r\nHost: …. That's the innermost content — the document. The app has no idea about IP or MAC; it only knows the socket.
  2. TCP makes a segment. The transport layer prepends a TCP header: source and destination ports (which app on each end), a sequence number so the far side can reorder and detect loss, an acknowledgement number, and flags. If the data is bigger than the MSS, TCP splits it into multiple segments here. This is the layer that turns an unreliable packet service into an ordered, reliable byte stream (deep dive in Chapter 13).
  3. IP makes a packet. The internet layer prepends an IP header: source and destination IP addresses, a TTL (hop budget), and a protocol number (6) recording that TCP is inside. The destination IP is the final server, set once and — outside of NAT — never changed on the journey.
  4. The stack decides the next hop and resolves its MAC. The kernel consults its routing table: is the destination on my local network, or do I send it to a gateway? Either way it needs the next hop's hardware address, which it looks up with ARP (Chapter 11). This is where "which box do I physically hand this to" is answered.
  5. Ethernet makes a frame. The link layer prepends an Ethernet header — destination MAC (the next hop), source MAC (this NIC), and EtherType (0x0800 for IPv4) — and appends a 4-byte FCS checksum trailer so the receiver can detect corruption. Now it's a complete frame.
  6. The NIC serialises bits. The physical layer clocks the frame out as electrical, optical, or radio signals to the next device on the wire.
  7. Each hop rewrites only the outermost envelope. A router that receives the frame checks the FCS, strips the Ethernet header, looks at the destination IP, decrements the TTL, decides the next hop, resolves that hop's MAC, wraps a brand-new Ethernet header, and sends it on. The IP and TCP headers ride untouched; only the L2 frame is replaced, hop after hop, until the packet reaches the destination's local network.
  8. Decapsulation reverses it. The destination NIC checks the FCS and that the destination MAC is its own, strips Ethernet, reads EtherType to hand the rest to IP; IP confirms the destination address is local and reads the protocol field to hand the payload to TCP; TCP reassembles segments in sequence order and uses the destination port to deliver the byte stream to the process listening there. The app reads exactly the bytes the sender wrote, with no knowledge of the three envelopes that carried them.

The elegant part is the peer-layer illusion. Even though every byte physically travels all the way down one stack and up another, each layer behaves as if it's talking straight across to its counterpart. The sender's TCP acts like it has a direct line to the receiver's TCP; the two IP layers act like they're adjacent. Encapsulation is what makes that illusion real — each layer's header is a private message to its peer, invisible to the layers in between.

The addresses that trip people up

Destination IP names the final machine and is constant across the whole path (NAT aside). Destination MAC names only the next device — your gateway, then the next router, then the next — and is rewritten at every single hop. So "I can see the packet leaving with the right destination IP" tells you nothing about whether the next-hop MAC is correct, and a stale or wrong MAC (an ARP problem) drops traffic that looks perfectly addressed at L3. Keep the two addresses in separate mental boxes.

Think first: a packet crosses six routers between you and a server. How many times is the destination IP rewritten, and how many times is the destination MAC rewritten?

The destination IP is rewritten zero times — it names the final server and stays constant the whole way (ignoring NAT, which is a deliberate exception at a boundary). The destination MAC is rewritten at every hop: your host sets it to the first router's MAC, that router replaces it with the second router's MAC, and so on — so across six routers it's rewritten roughly six times, once per link, always naming the next box. This is the difference between end-to-end addressing (L3, the whole route) and hop-by-hop addressing (L2, one link). If you internalise only one thing from this chapter, make it this.

ComponentsThe layers, named

Each layer, what it owns, and — the SRE-relevant bit — where its faults show up.

  • L7 Application — HTTP, DNS, TLS, gRPC. The meaning of the exchange: a request, a query, a response. This is where your services and their protocols live. Faults look like 500s, bad payloads, TLS handshake failures, wrong DNS answers. Tools: curl -v, application logs, dig. (OSI splits this into session/presentation/application; TCP/IP doesn't bother — TLS and content encoding just live "in the app.")
  • L4 Transport — TCP and UDP. Delivering to the right application via ports, and — for TCP — making delivery reliable and ordered with sequence numbers, acknowledgements, retransmission, and flow control. UDP skips all that for speed. Faults look like connection refused, resets, retransmit storms, ports exhausted. Tools: ss, tcpdump flags, nc.
  • L3 Internet — IP (v4/v6), ICMP. Global addressing and routing: getting a packet from any network to any other, hop by hop, with a TTL to kill loops. ICMP is IP's control channel (ping, "time exceeded," "fragmentation needed"). Faults look like unreachable networks, no route, TTL-expired, blackholes. Tools: ip route, ping, traceroute, mtr.
  • L2 Data Link — Ethernet, Wi-Fi, ARP. Moving a frame across one physical segment to the next device, using MAC addresses, plus the FCS integrity check. ARP is the glue that maps an IP to the next-hop MAC. Faults look like a down link, wrong VLAN, duplicate IP/ARP conflicts, a stale ARP cache. Tools: ip link, ip neigh, arping.
  • L1 Physical — cables, radio, optics, the NIC. Actual signals and the electrical/optical standards for them. Faults look like a dead port, a bad cable, a flapping link, CRC errors. Tools: ethtool, link LEDs, interface error counters.
  • The registries that make it interoperate — IANA. Not a layer, but the reason the layers agree: IANA assigns the numbers each header uses to say "what's inside me" — EtherTypes, IP protocol numbers, and well-known ports. When you write 0x0800 means IPv4 and 6 means TCP, that's an IANA registry, honoured by every stack on earth.
Think first: ping server succeeds but curl http://server says "connection refused." Which layers are proven good, and which one owns the problem?

A successful ping proves L1 through L3 end-to-end: the cable/radio works, the frames are being delivered, and IP can route a packet to that host and get one back. So the link, the addressing, and the route are all fine. "Connection refused" is a TCP-level answer — the host actively sent back a reset because nothing is listening on that port. That's an L4/L7 problem: the service is down, crashed, or bound to a different port. The fix is on the application, not the network — and the ping succeeding is exactly why "the network is fine, check the app" is the right call here. Reasoning by layer turned a vague outage into a precise one in two commands.

Data flowFollowing one HTTP request down and up

Put it together with a single curl http://web/ from one container to another on the same Docker network. curl writes the HTTP request bytes to a socket. TCP wraps them with source port (some ephemeral number) and destination port 80, plus a sequence number. IP wraps that with the source container's IP and the destination container's IP and protocol 6. The kernel sees the destination is on the same subnet, so the next hop is the destination; it resolves the destination's MAC via ARP and Ethernet wraps the packet with that destination MAC, this NIC's source MAC, and EtherType 0x0800, plus an FCS. The NIC sends the frame over the veth pair into the Docker bridge, which forwards it to the destination container's NIC. There, decapsulation runs in reverse: the NIC accepts the frame (MAC matches, FCS good) and strips Ethernet; IP sees the destination address is local and strips the IP header; TCP sees destination port 80, reassembles, and hands the byte stream to nginx listening there; nginx reads the same GET / HTTP/1.1 bytes curl wrote. The response makes the identical trip in reverse. You are about to watch exactly this happen, byte for byte, in the labs — and pointing at each header in the capture is the whole point.

Hands-onLabs — build, understand, break, troubleshoot

You need two hosts on a network so there's a real Ethernet header to see (loopback has none). Two containers on a user-defined Docker network is the cleanest local setup. Build it:

bash
# A private bridge network, a web server, and a client box with the tools.
docker network create labnet
docker run -d --name web --network labnet nginx:alpine

docker run --rm -it --network labnet --name box ubuntu:24.04 bash
# inside box:
apt-get update && apt-get install -y tcpdump curl iproute2 tshark dnsutils
Lab 1Build — capture exactly one requestBuild

Capture the frames of a single HTTP request. Start tcpdump in the background writing a pcap, make the request, then stop and read it back.

bash
# -e prints the Ethernet header; -c 12 stops after 12 packets.
tcpdump -ni eth0 -e -c 12 -w /tmp/req.pcap 'tcp port 80' &
sleep 1
curl -s http://web/ >/dev/null
wait
tcpdump -nr /tmp/req.pcap -e -c 4        # read back the first few frames
Output (trimmed)02:11:03.1 02:42:ac:12:00:03 > 02:42:ac:12:00:02, ethertype IPv4 (0x0800), length 74: 172.18.0.3.45678 > 172.18.0.2.80: Flags [S], seq 1234567, win 64240, length 0 02:11:03.1 02:42:ac:12:00:02 > 02:42:ac:12:00:03, ethertype IPv4 (0x0800), length 74: 172.18.0.2.80 > 172.18.0.3.45678: Flags [S.], seq 998877, ack 1234568, length 0

Every layer is on that one line. 02:42:ac:12:00:03 > 02:42:ac:12:00:02 is the L2 Ethernet header — source and destination MAC. ethertype IPv4 (0x0800) is the field that says "IP is inside." 172.18.0.3 > 172.18.0.2 is the L3 IP header. .45678 > .80 and Flags [S] are the L4 TCP header — the ports and the SYN that opens the connection. You've just seen encapsulation as raw output.

Lab 2Understand — point at each header in the bytesUnderstand

Now see it two ways: the full layered dissection, and the raw hex with the header boundaries. First, tshark spells out every layer:

bash
tshark -r /tmp/req.pcap -V -c 1 | grep -E 'Ethernet|Internet Protocol|Transmission Control|Type:|Protocol:|Src Port|Dst Port'
Output (trimmed)Ethernet II, Src: 02:42:ac:12:00:03, Dst: 02:42:ac:12:00:02 Type: IPv4 (0x0800) Internet Protocol Version 4, Src: 172.18.0.3, Dst: 172.18.0.2 Protocol: TCP (6) Transmission Control Protocol, Src Port: 45678, Dst Port: 80

Read the "what's inside me" chain top to bottom: Ethernet Type: IPv4 (0x0800) → IP Protocol: TCP (6) → TCP Dst Port: 80. Each header names the next. Now the raw bytes, and count the boundaries yourself:

bash
tcpdump -nr /tmp/req.pcap -xx -c 1

Bytes 0–13 are the 14-byte Ethernet header (6 dst MAC, 6 src MAC, 2 EtherType — the last two are 08 00). Bytes 14–33 are the 20-byte IPv4 header (it starts with 45: version 4, header length 5×4=20). Bytes 34–53 are the 20-byte TCP header. Everything after is payload. You can physically point at where one envelope ends and the next begins — that's encapsulation made concrete.

Lab 3Break — same host, different layerBreak

Prove that "the host is up" and "the service works" are different layers. The web container is reachable, port 80 is open, port 81 is not:

bash
ping -c1 web              # L3: is the host reachable at all?
curl -s -m3 http://web/    && echo OK-80    # L7 on an open port
curl -s -m3 http://web:81/ ; echo "exit=$?"   # L4 on a closed port
Output64 bytes from 172.18.0.2: icmp_seq=1 ttl=64 time=0.09 ms <html>... OK-80 curl: (7) Failed to connect to web port 81: Connection refused exit=7

Same host, three different answers. What does each one tell you about which layers are healthy, and why can't a successful ping ever prove your service is up? Reason it out before revealing.

Reveal — read the layers off the symptoms

The ping succeeding proves L1–L3 are fine end-to-end: the link carries frames, and IP can route a packet to web and back. Port 80 answering proves L4 and L7 are healthy for that service. Port 81 returning "connection refused" is a clean L4 signal: the host is up and reachable (L3 fine, or you'd get "no route"/timeout), but no process is listening on 81, so TCP replied with a reset. The lesson that drives all of Part II: a working ping only proves the network can carry packets to the host — it says nothing about whether the right app is listening. "Refused" means the host is there but the door is shut (L4/L7); a timeout, by contrast, usually means a firewall is silently dropping (L3/L4) or the host is gone. Different symptoms, different layers, different fixes.

Lab 4Troubleshoot — walk the ladderTroubleshoot

When something's unreachable and you don't know why, don't guess — walk the layers bottom-up, one command each. Run the ladder against web and read what each rung proves:

bash
ip link show eth0                 # L2: is the interface UP?
ip addr show eth0                 # L3: do I have an IP on the right subnet?
ip route                          # L3: do I have a route to the destination?
ip neigh                          # L2: has ARP resolved the next hop's MAC?
ping -c1 web                      # L3: end-to-end reachability
getent hosts web                  # L7: does the name resolve?
ss -tnp                           # L4: my connection states
curl -v -m3 http://web/           # L7: does the app actually answer?

Now a scenario: a colleague says "the app is down." getent hosts web returns an address, ping works, but curl hangs until the 3-second timeout with no "refused." Which layer owns this, and how is it different from the Lab 3 failure? Think, then reveal.

Reveal — timeout vs refused is the whole clue

Name resolves (L7 DNS fine) and ping works (L1–L3 fine), so the network path and addressing are healthy. The difference from Lab 3 is hang vs refused. "Refused" is an active TCP reset — the host said "no." A silent hang to timeout means the SYN is going into a void: nothing is sending back either a SYN-ACK or a reset. That points at L3/L4 filtering — a firewall or security group dropping the packets — or an app that accepted the connection but never responds (an L7 stall). Your next moves: tcpdump to see whether the SYN even leaves and whether anything comes back (if the SYN leaves and nothing returns, it's being dropped in the path, not refused at the host); and check firewall rules between you and the service. The reflex — refused means the door is shut, timeout means the letter is being intercepted — tells you which layer to chase without touching the app at all.

Lab 5Production challenge — encapsulation on top of encapsulation (MTU)Senior challenge

Real overlays wrap an entire frame inside another IP/UDP packet — VXLAN, the technology under most Kubernetes networks, does exactly this. That extra envelope steals bytes from the payload, and getting the MTU wrong causes one of the nastiest, most layer-confusing bugs there is. See the overhead and reason about the failure. First, confirm your link's MTU and compute the room a normal frame leaves:

bash
ip link show eth0 | grep -o 'mtu [0-9]*'      # usually mtu 1500
# Force a large, do-not-fragment ping to probe the real path MTU:
ping -c1 -M do -s 1472 web    # 1472 + 8 ICMP + 20 IP = 1500 → fits exactly
ping -c1 -M do -s 1500 web    # too big to fragment → should fail on a 1500 link
Output1480 bytes from 172.18.0.2: icmp_seq=1 ttl=64 time=0.1 ms ping: local error: message too long, mtu=1500

Now the senior question. A team reports: small API calls and ping work perfectly, TLS handshakes complete, but any response larger than ~1.4 KB hangs and eventually fails — and only for pods on different nodes. Which layer owns this, what's the mechanism, and why does the layered model make it hard to spot? Work it fully before revealing.

Reveal — a path-MTU blackhole, and why layering hides it

This is a classic PMTU blackhole at L3, caused by an overlay adding an envelope. When pods sit on different nodes, their traffic is wrapped in VXLAN — an extra ~50 bytes of outer IP/UDP/VXLAN header. If the overlay interface still claims a 1500 MTU, a full-size inner packet becomes a 1550-byte outer packet that won't fit on the physical 1500 link. The router should send back an ICMP "fragmentation needed" so the sender shrinks — but ICMP is very often filtered, so that message never arrives. The result: small packets (handshakes, tiny requests) sail through, and the first big packet vanishes with no error. It looks maddening because every layer reports healthy — ping is fine (small), TCP connects (small), TLS handshakes (small), and only bulk data dies. The layered model, which usually helps, here hides the fault between layers: the symptom is at L7 (big responses hang) but the cause is L3 (MTU) triggered by an encapsulation you can't see from inside the pod. The fix is to set the overlay MTU correctly (e.g. 1450) so inner packets always fit after wrapping, or to allow the ICMP that lets PMTU discovery work. Recognising this from the "small works, big hangs, only cross-node" signature is a genuinely senior move — and it's the exact trap Part V will disarm.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · asking the wrong layer

Symptom: "the service is down," and everyone starts restarting the app. First cut: walk the ladder — ping for L3, ss/"refused vs timeout" for L4, curl -v for L7 — before touching anything. Confirm: which is the lowest layer that's unhealthy; that's where the fault is. Cause is usually: the fix was at a different layer than the panic. Ping works, so it was never a network problem; the app was bound to the wrong port. Layer-first reasoning would have found it in 30 seconds.

Incident pattern · the MTU blackhole

Symptom: small requests and pings succeed; large transfers or big responses hang, frequently only across a VPN, tunnel, or overlay. First cut: a "small works, big hangs" pattern is an MTU story until proven otherwise. Confirm: ping -M do -s <size> to find the real path MTU; check the overlay interface's MTU against the physical link minus encapsulation overhead. Cause is usually: an extra encapsulation layer plus filtered ICMP, so PMTU discovery blackholes. Fix the MTU or allow the ICMP.

Incident pattern · right IP, wrong hop

Symptom: traffic to a host that just moved, or whose NIC was replaced, fails even though the routing and IP look correct. First cut: ip neigh — is the ARP entry for that IP stale or pointing at an old MAC? Confirm: flush it (ip neigh flush) and watch it re-resolve. Cause is usually: a stale L2 mapping — the L3 address is right but the frame is being sent to a MAC that no longer owns it. A perfect example of a fault that's invisible at L3 and obvious at L2 (all of Chapter 11).

Production · security · performanceWhat matters in production

Layer-first is the master reflex. Every network incident you'll ever work reduces to "which layer owns this?" Find the lowest unhealthy layer and fix there — fixing above it is treating a symptom. The whole rest of Part II is you getting fast and precise at this, layer by layer, until "the network is down" is a phrase you never say because you always know which layer it actually is. Ping proves L1–L3, "refused vs timeout" splits L4 from filtering, curl -v and logs cover L7. Bottom-up when nothing works, top-down when it's slow or flaky.

Encapsulation overhead is real and compounding. Every layer's header is payload you didn't send, and every extra layer of wrapping — a VPN, a service mesh's mTLS, a Kubernetes overlay — adds more and shrinks the usable MTU. Get the MTU math wrong and you get blackholes that masquerade as application bugs. This is why overlay networks run at 1450 rather than 1500, and why "small works, big hangs" should ring an MTU bell immediately.

Security lives at specific layers, and so do the controls. A firewall or a cloud security group filters at L3/L4 (addresses and ports). TLS encrypts at the top of the stack, so everything below it still sees IP and TCP headers in the clear — which is how load balancers and network policy work without decrypting. A WAF inspects L7. Knowing which layer a control operates at tells you what it can and can't see: a security group can't block a URL path, and a WAF can't stop a SYN flood. Match the control to the layer of the threat.

The OSI vocabulary is worth keeping even though the internet is TCP/IP. People say "L3 vs L7 load balancer," "layer 2 adjacency," "a layer 4 proxy" constantly, and they mean the OSI numbers. You'll pick a network load balancer (L4) or an application load balancer (L7) based on which layer you need to make routing decisions at (Chapter 52). Speak both models fluently.

Common mistakes this chapter should end: treating a successful ping as proof the service works; confusing "connection refused" (L4, host up, no listener) with a timeout (dropped in the path); forgetting that the destination MAC changes every hop while the IP doesn't; and ignoring encapsulation overhead until an MTU blackhole eats a production transfer.

System-design connectionWhere this reaches into architecture

Layering isn't just how packets move; it's how the whole networked world is allowed to change without coordination. IPv4 gave way to IPv6 at L3 while every L4 and L7 protocol above kept working, because the layers meet only at a thin contract — the same reason HTTP could go from 1.1 to 2 to 3 (even swapping TCP for QUIC underneath) without touching IP. When you design systems you make layer choices constantly: an L4 load balancer is cheap, fast, and protocol-blind because it only reads IP and ports; an L7 load balancer can route by URL, terminate TLS, and retry requests because it reads the application layer — and it costs more to do so (Chapter 52). A service mesh inserts an L7 proxy beside every workload precisely to make application-layer decisions the network layer can't (Chapter 66). Kubernetes networking is layers stacked on layers — pods on an overlay on the node network on the VPC — and almost every hard cluster-networking bug is really a "which layer, and what did the encapsulation change" question (all of Part V). The layered model is the map you'll use to reason about every one of them; the rest of Part II fills in each layer so the map becomes a place you can navigate under pressure.

InterviewInterview questions & answers

Answer each in your head first.

30-secWhy is networking layered at all?

Because getting bytes from one app to another across the world is too big a problem to solve in one piece. Layering splits it into independent concerns — the application's meaning, reliable delivery to the right app, global routing, and moving a frame across one link — where each layer solves one thing and trusts the layer below. That buys three things: independent evolution (you can replace IPv4 with IPv6 without touching TCP or HTTP), interoperability (any two machines that agree on the contracts can talk), and fault isolation, which is the one I use daily — every problem lives at one layer, so the symptom tells me where to look.

2-minWalk me through what happens to an HTTP request as it goes down the stack and out the wire.

The app writes the HTTP bytes to a socket — that's the payload. TCP prepends a header with the source and destination ports, so the far side knows which app, plus a sequence number for reliable, ordered delivery; that's a segment. IP prepends the source and destination IP addresses, a TTL, and a protocol number saying TCP is inside; that's a packet, and the destination IP is set once and stays constant the whole trip. The kernel then decides the next hop from its routing table and resolves that hop's MAC with ARP, and Ethernet prepends the destination MAC (the next hop), the source MAC, and an EtherType saying IPv4, with an FCS checksum appended; that's a frame. The NIC clocks it out as signals. At each router the outermost Ethernet header is stripped and rebuilt for the next hop — MAC changes every hop, TTL drops by one — while the IP and TCP headers ride untouched. At the destination it's decapsulated in reverse: strip Ethernet, IP confirms it's local, TCP reassembles by sequence and uses the destination port to hand the byte stream to the listening process. Each header is a private note from one layer to its peer on the other side.

DeepAcross ten routers, which addresses in the packet change and which stay the same, and why?

The source and destination IP addresses stay the same the entire way — barring NAT, which is a deliberate exception at a boundary — because IP is end-to-end addressing: it names the final machine, and routing's whole job is to move that unchanged packet toward it. The source and destination MAC addresses change at every hop, because Ethernet is hop-by-hop: a MAC only has meaning on one link, and each router rewrites the frame's destination MAC to the next hop and the source MAC to its own outgoing interface. The TTL in the IP header decrements by one at each router, which is the loop-killer — if it hits zero the packet is dropped and an ICMP "time exceeded" comes back, which is exactly how traceroute maps the path. So the L3 envelope is constant and travels the whole route, while the L2 envelope is torn off and rebuilt on every link. That distinction is why an ARP/L2 fault can drop traffic that looks perfectly addressed at L3.

ScenarioA service is "unreachable." How do you localise it by layer?

I walk the ladder bottom-up. ip link — is the interface up (L2)? ip addr and ip route — do I have an address on the right subnet and a route to the destination (L3)? ping — end-to-end reachability (L3); if that works, L1 through L3 are healthy. Then the key split at L4: does curl/nc get "connection refused" or a timeout? Refused means the host is up but nothing's listening — an app or wrong-port problem, L4/L7. A silent timeout means packets are being dropped in the path — a firewall or security group at L3/L4 — or the app accepted and stalled at L7. I'd confirm with tcpdump: if the SYN leaves and nothing comes back, it's being dropped, not refused. And I'd check DNS with getent hosts in case the name resolves to the wrong place entirely. The discipline is to find the lowest unhealthy layer and fix there, because fixing above it just treats a symptom.

Follow-upSmall requests work but large responses hang, only across the overlay. What is it?

That signature is a path-MTU blackhole caused by encapsulation. The overlay — VXLAN in most Kubernetes clusters — wraps each frame in an extra outer IP/UDP header, roughly 50 bytes. If the overlay interface still advertises a 1500 MTU, a full-size inner packet becomes an oversize outer packet that won't fit on the physical link. The router should send ICMP "fragmentation needed" so the sender shrinks, but ICMP is commonly filtered, so the big packets just disappear with no error. Small packets fit, so pings, handshakes, and tiny requests all succeed — which is why it looks like an application bug even though it's an L3 MTU problem triggered by an encapsulation you can't see from inside the pod. The fix is to set the overlay MTU correctly, typically 1450, so inner packets always fit after wrapping, or to permit the ICMP that makes PMTU discovery work. I'd confirm with a do-not-fragment ping sweep to find the real path MTU.

RetainQuick revision

Networking is layered because the end-to-end job is too big to solve at once: each layer owns one concern and trusts the one below, which buys independent evolution, interoperability, and — the daily win — fault isolation. OSI names seven layers as the shared vocabulary; TCP/IP implements four (Application, Transport, Internet, Link). Encapsulation is the mechanism: going down, each layer wraps the one above in a header — TCP adds ports and sequencing (segment), IP adds end-to-end addresses and a TTL (packet), Ethernet adds next-hop MACs and an FCS (frame) — and each header names what's inside it (EtherType, protocol number, port). Going up, the receiver strips them outermost-first, each header telling it who to hand the rest to. The destination IP is constant end-to-end while the destination MAC is rewritten every hop and the TTL drops by one. Every header is overhead, so extra wrapping (VPN, overlay) shrinks the MTU and can blackhole large packets. And the reflex the whole of Part II rests on: localise faults by layer — ping proves L1–L3, refused-vs-timeout splits L4 from filtering, curl -v and logs cover L7 — then fix the lowest unhealthy layer.

The 10 things to remember

  1. Layering exists to break one impossible problem into independent ones — and its daily payoff is telling you which layer a fault lives at.
  2. OSI has 7 layers (the vocabulary), TCP/IP has 4 (the implementation): Application, Transport, Internet, Link.
  3. Encapsulation = each layer wraps the one above in a header; decapsulation strips outermost-first on receive.
  4. TCP header adds ports (which app) and sequencing (reliable order); it's a segment.
  5. IP header adds end-to-end source/destination addresses and a TTL; it's a packet, and the destination IP never changes en route.
  6. Ethernet header adds next-hop source/destination MACs and an FCS; it's a frame, and the destination MAC is rewritten every hop.
  7. Each header names what's inside it — EtherType (0x0800 = IPv4), IP protocol (6 = TCP), destination port (80) — so the receiver knows who to hand it to.
  8. A working ping proves L1–L3 only; it says nothing about whether the right app is listening (L4/L7).
  9. "Refused" = host up, no listener (L4); a silent timeout = dropped in the path (filtering) or stalled app — different layers, different fixes.
  10. Headers are overhead; extra encapsulation (VPN, VXLAN overlay) shrinks the MTU, and "small works, big hangs" means an MTU blackhole.
