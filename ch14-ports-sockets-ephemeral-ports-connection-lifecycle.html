Part II · Networking from First Principles · Chapter 14

Ports, sockets, ephemeral ports & the connection lifecycle

One server, one IP, one port 443 — and fifty thousand connections at once, none of them confused for another. The trick is a four-part key the kernel stamps on every packet. Understand that key and two of the ugliest production bugs — port exhaustion and CLOSE_WAIT leaks — become obvious instead of terrifying.

Why this exists · the problemThe problem ports solve

An IP address gets a packet to the right machine. But a machine runs many programs that all want the network at once — a web server, an SSH daemon, a metrics agent, your shell's outbound curl. When a packet arrives at 10.0.0.10, which program gets it? IP alone can't say; it only names the host. You need a second number that names the conversation inside the host. That number is the port.

But a single port isn't enough either. A busy web server has one port — 443 — and thousands of clients talking to it simultaneously. If "port 443" were the whole identity, every client's packets would blur into one indistinguishable stream. So the real identity of a connection is not one port but four values together: the local IP, the local port, the remote IP, and the remote port. That quartet — the 4-tuple — is unique across the whole connection, and it's how one server keeps fifty thousand conversations on port 443 perfectly separated.

Everything in this chapter follows from that idea. A socket is the kernel object that holds one endpoint of a connection (or the willingness to accept new ones). Ports come in ranges with different meanings. Clients borrow a throwaway ephemeral port for each outbound connection, and running out of them is a real outage. And a connection has a lifecycle from creation to close that, if the application skips the last step, leaks sockets until the process falls over.

Key point

A connection is identified by the 4-tuple (local IP, local port, remote IP, remote port). A server does not spend a port per client — every client shares the server's one listening port, and the differing remote IP:port keeps them distinct. This is why "we'll run out of ports" is almost always a client-side fear, not a server-side one.

Mental model · analogyThe mental model: a company switchboard

Real-world analogy

Picture a large company with one public phone number (the IP address) and internal extensions (the ports). Extension 443 is the sales desk; extension 22 is IT. When you dial in and ask for extension 443, the switchboard connects you to sales. So far, one number, many extensions — that's IP plus port.

Now here's the part people miss: the sales desk can be on fifty calls at once, all "on extension 443." How does the desk keep them straight? By who's on the other end. Each live call is identified not just by "extension 443" but by the full pair of endpoints: this outside caller's number and line, talking to our number and extension. That full identity — both ends — is the 4-tuple. The extension is shared; the calls are distinct because the callers are distinct.

A listening socket is the sales desk sitting by the phone, ready to answer — it's not a call, it's the ability to receive calls. The moment a call connects, it becomes a separate connected socket, its own conversation with its own handle, and the desk goes right back to waiting for the next ring. When a caller hangs up, someone at the desk has to actually put the receiver down; if they wander off leaving it off the hook, that line is stuck forever — that's a CLOSE_WAIT leak.

Why an SRE cares

When someone worries "can our service handle 100k connections on one port?", the answer is: ports aren't the constraint — file descriptors and memory are. Each connected socket is a file descriptor and a chunk of kernel memory, so the ceiling is ulimit -n and RAM, tuned exactly like the "too many open files" problem from Chapter 1. Port exhaustion is a different bug entirely, and it's on the client. Knowing which side runs out of what stops you from tuning the wrong machine at 3 a.m.

Internal workingThe 4-tuple, sockets, and the syscall lifecycle

Here's the machinery, in the order a connection actually happens. The server path first:

  1. socket() creates an endpoint and returns a file descriptor. At this point it's just an fd with no address — it can't receive anything yet.
  2. bind() pins it to a local address and port, e.g. 0.0.0.0:443 (all interfaces) or 10.0.0.10:443 (one interface). This is where "address already in use" comes from if something else holds the port.
  3. listen() marks the socket passive and creates the two queues from Chapter 13: the SYN queue and the accept queue. The socket is now in LISTEN. It is not a connection — it's a factory for connections.
  4. accept() pops one completed connection off the accept queue and returns a new file descriptor for it. The listening socket stays open and keeps accepting; each accepted connection is its own connected socket with a full 4-tuple.

The client path is shorter:

  1. socket() — an fd, as before.
  2. connect(remote) — the client usually skips explicit bind(), so the kernel auto-binds a local ephemeral port for it, then sends the SYN. From this moment the connection has its full 4-tuple: the kernel-chosen local port plus the remote it's dialling.

Now the part that makes it all work — demultiplexing. When a packet arrives, the kernel builds its 4-tuple and looks for a match, most specific first:

  1. Exact 4-tuple match to an established socket? Deliver it there. This is the common case — packets on existing connections.
  2. No established match, but a listening socket owns that local IP:port? It's a new connection (a SYN); hand it to the listener to begin a handshake.
  3. No match at all? The kernel replies with a RST (TCP) or an ICMP port-unreachable (UDP) — that's the ECONNREFUSED from the last chapter.

That ordering is why a server needs only one port for countless clients: established connections are matched by the whole tuple before the listener is ever consulted. It's also why the ephemeral port matters so much on the client: for connections to the same destination, the local IP, remote IP, and remote port are all fixed, so the local ephemeral port is the only thing making each connection's tuple unique — and there are a finite number of them.

Think first: a load-balancer node opens connections to one backend at 10.0.5.9:8080. Roughly how many simultaneous connections can it make before something breaks, and what breaks?

About 28,000 — the size of the default ephemeral port range (32768–60999). To one fixed destination, three of the four tuple values are constant (the node's local IP, the backend IP, the backend port 8080), so uniqueness rides entirely on the local ephemeral port. Once every ephemeral port is in use for a connection to that destination, the next connect() fails with EADDRNOTAVAIL ("cannot assign requested address"). The server, by contrast, is nowhere near a limit — it's demuxing all of these by their differing remote ports on its single port 8080. The lesson: exhaustion is per-(local IP, destination), and it's a client problem you solve with connection reuse or more source addresses, not by touching the backend.

ComponentsPort ranges, reuse options, keep-alive, pooling

The port ranges (IANA / RFC 6335)

A port is a 16-bit number, so 0–65535, split by IANA into three bands: system / well-known ports 0–1023 (443, 80, 22, 53 — binding these needs privilege or the CAP_NET_BIND_SERVICE capability), user / registered ports 1024–49151 (assigned to specific applications), and dynamic / ephemeral ports 49152–65535 (never assigned, free for temporary client use). Linux doesn't follow IANA's ephemeral boundary exactly — its default is net.ipv4.ip_local_port_range = 32768 60999, roughly 28,000 ports. That number is the budget you can exhaust.

SO_REUSEADDR vs SO_REUSEPORT

Two socket options people confuse constantly. SO_REUSEADDR mainly lets a server bind() a port that's still held by connections in TIME_WAIT — without it, restarting a crashed server often fails with "address already in use" until the old TIME_WAITs drain. SO_REUSEPORT is different and newer: it lets multiple sockets bind the same port simultaneously, and the kernel load-balances incoming connections across them. That's how a multi-process server (nginx workers, a Go server with several listeners) spreads accept load across cores without a single accepting thread becoming the bottleneck.

Keep-alive — two different things with the same name

TCP keep-alive is a kernel feature: after a connection is idle for tcp_keepalive_time (default 7200 seconds — two hours), the kernel sends probe packets to check the peer is still there, tearing the connection down if it's gone. Its real value in production is keeping middleboxes from silently dropping idle flows, so you tune it far below the default. Application keep-alive is separate — it's the decision to reuse an established connection for multiple requests instead of closing it, which is HTTP's persistent-connection behaviour (Chapter 16). Same word, two layers.

Connection reuse and pooling

The single most valuable pattern in this whole chapter: don't open a connection per request. A connection pool keeps a set of established connections open and hands them out for reuse, so you pay the handshake and slow-start cost once and amortise it over thousands of requests. Pooling is what keeps a client's ephemeral-port usage flat instead of climbing, what keeps TIME_WAIT from piling up, and what makes high request rates cheap. Every serious HTTP client, database driver, and RPC library ships a pool; misconfiguring it (pool too small, or accidentally disabled) is a top cause of the exhaustion incidents below.

Think first: your app pool is set to "no keep-alive, new connection per request," and it talks to one internal API. Under load you see thousands of TIME_WAIT and occasional connect failures. What's the single change that fixes it?

Turn on connection reuse (keep-alive / a real pool). Per-request connections mean every request opens a fresh 4-tuple, does a handshake, and — because the client is the active closer — leaves a TIME_WAIT holding an ephemeral port for 60 seconds. At a few hundred requests per second to one destination you approach the ~28k/60s ceiling and connect() starts failing. Reusing connections collapses thousands of short-lived tuples into a handful of long-lived ones, so ephemeral-port usage goes flat and TIME_WAIT nearly vanishes. Bumping the port range or enabling tcp_tw_reuse buys headroom, but the actual defect is opening connections you didn't need to.

Data flowFollowing a socket from birth to leak-free death

A client does socket() → gets fd 3 → connect("10.0.0.10:443"); the kernel auto-binds ephemeral port 51001, and the 4-tuple (client:51001, 10.0.0.10:443) exists. Bytes flow over fd 3. When the client is done it calls close(3), which sends a FIN and releases the fd. On the server, the listening socket (fd 4) had returned a connected socket (fd 7) from accept(); the server reads and writes fd 7, and — this is the step that matters — when it's finished it calls close(7), sending its own FIN and freeing the fd. Both sides tore down cleanly: the client passes through TIME_WAIT (it closed first), the server reaches CLOSED immediately, and no descriptors leak. The whole difference between a healthy service and a CLOSE_WAIT leak is whether the server reliably reaches that close(7) on every path, including error paths. Miss it — an exception that skips the close, a handler that returns without cleaning up — and fd 7 sits in CLOSE_WAIT forever, one leaked descriptor at a time, until the process hits its fd limit and stops accepting anything.

Lab 1Build — read every socket with ss -tanpBuild

ss -tanp is the command you'll type ten thousand times: tcp, all states, numeric (don't resolve names), process. Start a server and read the sockets.

bash
python3 -m http.server 8080 &
ss -tanp | grep -E 'State|8080'
OutputState Recv-Q Send-Q Local Address:Port Peer Address:Port Process LISTEN 0 5 0.0.0.0:8080 0.0.0.0:* users:(("python3",pid=42,fd=3))

Read the listener: local 0.0.0.0:8080 (all interfaces), peer 0.0.0.0:* (any — the wildcard that says "I'm a factory, not a call"), and the owning process with its file descriptor 3. That fd link is gold: it ties a socket straight to a process and a descriptor, so ls -l /proc/42/fd/3 confirms it. # Three connections held open with sleep so we can observe them:

Lab 3Break — exhaust the ephemeral port rangeBreak

Shrink the ephemeral range to a tiny window, then try to open more connections than there are ports — all to one destination. Predict the failure before you read it.

bash
sysctl -w net.ipv4.ip_local_port_range="60000 60009"   # only 10 source ports
python3 -m http.server 9000 &
python3 - <<'PY'
import socket
held=[]
try:
    for i in range(40):
        c=socket.create_connection(("127.0.0.1",9000))   # keep it open
        held.append(c)
    print("opened all 40 (unexpected)")
except OSError as e:
    print(f"failed after {len(held)} connections -> errno {e.errno}: {e.strerror}")
PY
Outputfailed after 10 connections -> errno 99: Cannot assign requested address

It dies at ten — exactly the number of ports in the range. Why does the same machine, moments earlier, happily serve on :9000 yet can't open an eleventh outbound connection?

Reveal what ran out

Source ports, not connections in general. All ten connections go to the identical destination 127.0.0.1:9000, so the destination IP and port are fixed and the local IP is fixed — the only free variable in the 4-tuple is the local ephemeral port, and you gave the kernel only ten of them. The eleventh connect() has no unique tuple left to form, so it fails with EADDRNOTAVAIL (errno 99). The server side never even notices — it's demuxing the ten fine. In the real world this is a load balancer, sidecar proxy, or batch job hammering one backend with fresh connections. Fixes: reuse connections (pooling), spread across more destinations, add source IPs, or widen the range. Reset it: sysctl -w net.ipv4.ip_local_port_range="32768 60999".

Lab 4Troubleshoot — spot a CLOSE_WAIT leakTroubleshoot

Run a server that accepts connections but never closes them — the classic application bug. Then disconnect clients and watch the sockets get stuck.

bash
# A leaky server: accept() forever, keep every fd, never close():
python3 - <<'PY' &
import socket
s=socket.socket(); s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(("0.0.0.0",9100)); s.listen(128)
leaked=[]
while True:
    c,_=s.accept(); leaked.append(c)   # BUG: never c.close()
PY
sleep 1
# Five clients connect and immediately hang up:
for i in $(seq 1 5); do nc -w1 127.0.0.1 9100 </dev/null; done
sleep 1
ss -tanp state close-wait 'sport = :9100'
OutputRecv-Q Send-Q Local Address:Port Peer Address:Port Process 1 0 127.0.0.1:9100 127.0.0.1:43102 users:(("python3",pid=88,fd=6)) 1 0 127.0.0.1:9100 127.0.0.1:43110 users:(("python3",pid=88,fd=7)) ...

Five sockets stuck in CLOSE-WAIT, each pinned to the python process and a distinct fd (6, 7, 8…). They will never clear on their own — and that's the diagnostic tell. Here's the distinction that matters most in this chapter:

Reveal: CLOSE_WAIT vs TIME_WAIT — which is the app's fault?

CLOSE_WAIT is always the application's bug. It means the peer sent a FIN, the kernel ACKed it, and the socket is now waiting for your program to call close() — which it never did. The kernel can't clean it up; only the app can, so CLOSE_WAIT sockets accumulate without limit until the process runs out of file descriptors and stops serving, while looking healthy on CPU and memory. TIME_WAIT, by contrast, is the kernel's doing and self-heals in ~60 seconds; it's normal and protective (Chapter 13). So the one-line rule on call: a growing pile of TIME_WAIT is a rate problem (too many short connections) that clears itself; a growing pile of CLOSE_WAIT is a code problem (a missing close on some path) that never clears and will eventually take the process down. The fix is in the app — close every socket on every path, including errors — and ss -tanp state close-wait hands you the exact PID and fd to blame. Kill the server to reset: kill %1.

Lab 5Production challenge — prove pooling fixes port churnSenior challenge

Measure the difference between per-request connections and a reused connection, the way you'd justify a pooling change to a skeptical team. Fire 300 requests two ways and count the aftermath.

bash
python3 -m http.server 9200 &

# A) New connection per request (curl default per invocation):
for i in $(seq 1 300); do curl -s http://127.0.0.1:9200/ -o /dev/null; done
echo "per-request TIME_WAIT:  $(ss -tan state time-wait 'sport = :9200' | wc -l)"

# B) One connection reused for all 300 requests (keep-alive):
curl -s $(printf 'http://127.0.0.1:9200/ ' {1..300}) -o /dev/null
echo "reused    TIME_WAIT:  $(ss -tan state time-wait 'sport = :9200' | wc -l)"
Output (order of magnitude)per-request TIME_WAIT: ~300 reused TIME_WAIT: ~1

Same 300 requests, same work done — but per-request connections leave ~300 ephemeral ports parked in TIME_WAIT, while a single reused connection leaves essentially none. Now the senior question: why is reuse not just "less TIME_WAIT" but genuinely faster?

Reveal the full payoff

Three wins stack up. First, ephemeral-port and TIME_WAIT pressure drop to near zero, so you can't exhaust the range no matter the request rate. Second, you skip the handshake round trip on every request after the first — for a cross-region call that's tens of milliseconds saved per request. Third, you skip TCP slow start each time: a fresh connection starts with a small congestion window and ramps up, so early requests on a new connection are throttled, whereas a warm reused connection already has a large cwnd and runs at full speed. That's why a well-configured connection pool is one of the biggest, cheapest latency wins available, and why "new connection per request" is a performance bug even when it isn't yet an outage. It's the same reasoning that makes HTTP keep-alive and HTTP/2 multiplexing matter in Chapter 16.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · ephemeral-port exhaustion

Symptom: a client, proxy, or job starts failing outbound connections to one destination with "cannot assign requested address" (EADDRNOTAVAIL), while the destination is healthy and other destinations work. First cut: ss -tan | grep <dst> | wc -l and sysctl net.ipv4.ip_local_port_range. Confirm: the count of sockets to that destination is near the range size. Cause is usually: per-request connections to one backend. Fix: connection pooling first; then tcp_tw_reuse, a wider range, or more source IPs as headroom.

Incident pattern · CLOSE_WAIT leak

Symptom: a service slowly stops accepting connections over hours or days; restarting fixes it temporarily; CPU and memory look fine. First cut: ss -tanp state close-wait | wc -l and watch it climb; ls /proc/<pid>/fd | wc -l approaching the fd limit. Confirm: CLOSE_WAIT count grows and never falls. Cause is usually: the application doesn't call close() on some code path — often an error path, a dropped exception, or a framework misuse. Fix: in the code; the OS cannot reclaim these.

Incident pattern · "address already in use" on restart

Symptom: a service fails to start right after a crash or redeploy with EADDRINUSE, then succeeds a minute later. First cut: ss -tan state time-wait 'sport = :<port>'. Confirm: old connections in TIME_WAIT still hold the port. Cause is usually: the listener didn't set SO_REUSEADDR, so it can't bind over draining TIME_WAITs. Fix: set SO_REUSEADDR on the listening socket (most frameworks expose a flag).

Incident pattern · fd exhaustion masquerading as "port exhaustion"

Symptom: a high-connection server stops accepting with EMFILE/"too many open files." First cut: ls /proc/<pid>/fd | wc -l vs cat /proc/<pid>/limits. Cause is usually: the server hit its file-descriptor limit — each connection is an fd. This is not a port problem (the server reuses one port); it's the ulimit -n ceiling. Fix: raise the limit and, if the growth is unbounded, hunt a socket leak.

Production · security · performanceWhat matters in production

Know which side runs out of what. Servers are bounded by file descriptors and memory (one fd per connection, all on one port); clients are bounded by ephemeral ports (per local-IP-to-destination). Tune the limit on the machine that actually hits its ceiling — raising the server's port range does nothing for a client's exhaustion, and vice versa. This single distinction resolves a huge fraction of connection incidents.

Pool and keep alive by default. The cheapest reliability and latency win in networked systems is reusing connections. Set connection pools deliberately (sized to concurrency, not left at a tiny default), enable HTTP keep-alive, and tune TCP keep-alive below any middlebox idle timeout so long-lived pooled connections don't get silently reset. A pool that's too small serialises requests; a pool that never reuses churns ports — both are common misconfigurations.

Security lives partly here too. Binding a well-known port (<1024) needs privilege or CAP_NET_BIND_SERVICE — which is why containers often run apps on high ports and let a proxy or a service map the low one. Listening on 0.0.0.0 exposes a service on every interface, including ones you didn't mean to; binding to a specific interface or 127.0.0.1 is a real access control. And ss -tlnp is a security tool: it shows exactly what's listening and who owns it, which is step one of "what is this box exposing?"

Common mistakes: assuming a server can run out of ports (it runs out of fds); disabling keep-alive and then fighting TIME_WAIT with kernel tunables; leaving CLOSE_WAIT unmonitored until a service tips over; forgetting SO_REUSEADDR and blaming a slow restart on something else; and binding to 0.0.0.0 by habit when the service should be local-only.

System-design connectionWhere this reaches into architecture

The 4-tuple and the ephemeral-port ceiling shape how you build the middle of a system. Any component that fans in — a load balancer, an API gateway, a service-mesh sidecar — is a client to everything behind it, so it's exactly where ephemeral-port exhaustion bites, which is why these components live and die by connection pooling and why some spread across multiple source IPs. The listening-vs-connected distinction is the foundation of how services scale on a box: SO_REUSEPORT across worker processes is how a single port saturates many cores. And the connection lifecycle is why graceful shutdown is a design concern — draining in-flight connections and closing cleanly, rather than dropping them, is the difference between a deploy that's invisible to users and one that spikes errors. When you get to Kubernetes Services (Chapter 43), the DNAT that maps a service IP to pod IPs is manipulating these very tuples, and conntrack is tracking them — the same machinery, one layer up.

InterviewInterview questions & answers

Answer each in your head first.

30-secHow does one server handle 50,000 connections on a single port without confusion?

Because a connection is identified by the full 4-tuple — local IP, local port, remote IP, remote port — not by the port alone. All 50,000 share the server's one local port, but each has a different remote IP:port, so the kernel demultiplexes every incoming packet to exactly one connected socket by matching all four values. The server spends no extra ports per client; its real limits are file descriptors and memory, one per connection.

2-minWalk me through the syscalls for a server and a client, and where the ephemeral port appears.

The server calls socket() to get a file descriptor, bind() to pin it to a local address and port like 0.0.0.0:443, and listen() to make it passive — that creates the SYN and accept queues and puts it in LISTEN. It then calls accept() in a loop, and each call pops one completed connection and returns a brand-new fd for that connected socket, while the listening socket keeps accepting. The client calls socket() and then connect(remote); it usually doesn't bind(), so the kernel auto-assigns a local ephemeral port from ip_local_port_range — that's where the ephemeral port appears, and it's the value that makes each client connection's 4-tuple unique when they all go to the same destination. Data flows over the connected fds, and each side calls close() when done, which sends a FIN. The step people forget is that missing close() on the server is what causes a CLOSE_WAIT leak.

DeepExplain the difference between a CLOSE_WAIT pile-up and a TIME_WAIT pile-up.

They look similar in ss but have opposite causes and opposite owners. TIME_WAIT is held by the active closer — whoever sent the first FIN — after it has acknowledged the peer's FIN, for about 60 seconds on Linux, and then it clears itself. It's the kernel doing its job: protecting a reused 4-tuple from delayed duplicates and keeping the final ACK re-sendable. A big TIME_WAIT pile is a rate symptom — too many short-lived connections per second — and it self-heals; you relieve it with connection reuse, not by disabling it. CLOSE_WAIT is the other side of a close: the peer sent a FIN, your kernel ACKed it, and the socket now waits for your application to call close(). If the app never does, the socket is stuck in CLOSE_WAIT indefinitely — the kernel can't reclaim it. So a growing CLOSE_WAIT pile is always an application bug, usually a missing close on an error path, and it never clears on its own; it grows until the process exhausts its file descriptors and stops accepting, all while CPU and memory look fine. The diagnostic value is that ss -tanp state close-wait gives you the exact PID and fd to fix, and the mental model is: TIME_WAIT self-heals and is the OS's; CLOSE_WAIT accumulates and is yours.

ScenarioA sidecar proxy fails outbound connections to one upstream with "cannot assign requested address." How do you fix it?

That error is EADDRNOTAVAIL, and it means the proxy ran out of ephemeral source ports to that upstream. Because every connection from the proxy to that one upstream shares the proxy's local IP and the upstream's IP:port, the only unique part of the 4-tuple is the local ephemeral port, and there are only about 28,000 by default. I'd confirm by counting sockets to that upstream with ss -tan and checking ip_local_port_range — if the count is near the range size, that's it. The real fix is connection reuse: the proxy should pool and keep connections to the upstream alive instead of opening a new one per request, which collapses thousands of short-lived tuples into a few long-lived ones and takes the pressure off entirely. As headroom I'd also enable tcp_tw_reuse for outbound connections and could widen the port range or add source IPs, but those are band-aids — if the proxy is opening a connection per request, that's the defect. Crucially, the upstream server is fine and needs no change; this is a client-side limit.

Follow-upWhat's the difference between SO_REUSEADDR and SO_REUSEPORT?

SO_REUSEADDR mostly solves the "address already in use" problem on restart: it lets a server bind() a port that still has connections lingering in TIME_WAIT, so a crashed service can come straight back up instead of waiting a minute for those to drain. It does not let two live listeners share a port. SO_REUSEPORT is the newer, stronger option: it allows multiple sockets — typically one per worker process or thread — to bind the same port at the same time, and the kernel load-balances incoming connections across them. That's how a multi-process server like nginx or a multi-listener Go service spreads accept work across CPU cores without a single accepting thread becoming the bottleneck. So: SO_REUSEADDR is about reusing an address that's draining; SO_REUSEPORT is about sharing a live address across workers for scale.

RetainQuick revision

A port names a conversation inside a host, but a connection's real identity is the 4-tuple: local IP, local port, remote IP, remote port. The kernel demultiplexes every packet by matching the full tuple to a connected socket first, falling back to a listening socket for new connections, and a RST/ICMP for no match. A server needs only one listening port for countless clients — its limits are file descriptors and memory, not ports. Clients borrow an ephemeral port per outbound connection from a ~28,000-port range, and exhausting it (per local-IP-to-destination) is a client-side outage fixed by connection reuse. The lifecycle is socket → bind → listen → accept on the server, socket → connect on the client, and close() on both — skip the server's close and you leak sockets in CLOSE_WAIT until the process dies. TIME_WAIT self-heals and is the OS's; CLOSE_WAIT accumulates and is your code's bug. Read all of it with ss -tanp.

The 10 things to remember

  1. A connection is the 4-tuple (local IP, local port, remote IP, remote port), not a single port.
  2. One listening port serves unlimited clients; they're told apart by their differing remote IP:port.
  3. Servers run out of file descriptors and memory, not ports. Port exhaustion is a client-side problem.
  4. Ephemeral range is ~28,000 ports (32768–60999 default); to one destination that's your simultaneous-connection ceiling.
  5. Lifecycle: socket → bind → listen → accept (server), socket → connect (client); connect() auto-binds an ephemeral port.
  6. A listening socket is a factory (LISTEN, wildcard remote); accept() returns a new fd per connection.
  7. CLOSE_WAIT means your app never called close() — it never clears and is always a code bug.
  8. TIME_WAIT is the kernel's, self-heals in ~60s; don't confuse the two.
  9. SO_REUSEADDR rebinds a draining port on restart; SO_REUSEPORT shares a live port across workers.
  10. Connection pooling and keep-alive fix port churn and cut latency (no handshake, no slow-start restart) — the default win.
