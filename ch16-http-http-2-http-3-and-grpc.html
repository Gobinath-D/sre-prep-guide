HTTP, HTTP/2, HTTP/3, and gRPC

HTTP started as plain text you could type by hand and grew into the load-bearing protocol of the internet. Each version — 1.1, 2, 3 — exists to kill a specific kind of head-of-line blocking. And gRPC's habit of pinning everything to one long-lived connection quietly breaks the naive load balancer you thought was fine. Get these distinctions right and you'll debug latency and traffic-skew problems others can only guess at.

Why this exists · the problemThe problem HTTP keeps re-solving

HTTP began as almost nothing: a client opens a connection, sends a line of text — GET /page HTTP/1.0 — and the server sends back some headers and a body. That simplicity is why it won. You can speak it by hand over nc, it's stateless (each request stands alone), and it carries anything. But the same simplicity created a performance problem that has taken three protocol revisions to chase down, and the problem has a name you'll say constantly: head-of-line blocking — one thing stuck at the front of a queue holding up everything behind it.

The story of HTTP is the story of that blocking moving down the stack as each version fixes it at one layer only to expose it at the next. HTTP/1.0 opened a fresh connection per request — expensive. HTTP/1.1 kept connections alive and reused them, but a connection could only carry one response at a time, so a slow response blocked every request queued behind it; browsers papered over this by opening six connections per site. HTTP/2 fixed that by multiplexing many independent streams over a single connection — but because they all ride one TCP connection, a single lost packet stalls all the streams, because TCP insists on in-order delivery. HTTP/3 fixes that by abandoning TCP for QUIC over UDP, where streams are genuinely independent and one stream's packet loss doesn't touch the others.

So the versions aren't arbitrary marketing numbers. Each one exists to remove a specific stall: application-layer blocking (1.1 keep-alive helped, multiplexing in 2 solved), then transport-layer blocking (3/QUIC solved). Meanwhile gRPC took HTTP/2's multiplexing and built RPC on top — long-lived connections carrying thousands of calls — which is wonderful for efficiency and terrible for any load balancer that only understands connections, not requests.

Key point

There are three distinct head-of-line blocking problems: (1) HTTP/1.1 — one response per connection at a time; (2) HTTP/2 — many streams share one TCP connection, so one lost segment blocks all of them; (3) solved by HTTP/3 — QUIC gives each stream independent loss recovery. Know which layer each version fixes and the rest of this chapter — including the gRPC load-balancing trap — follows.

Mental model · analogyThe mental model: lanes on a road

Real-world analogy

Picture traffic between two towns. HTTP/1.1 is a single-lane road where cars must stay in order. Send a truck (a big, slow response) and every car behind it crawls at truck speed until the truck arrives — head-of-line blocking. The workaround browsers used was to build six parallel single-lane roads (six connections) so a truck on one lane doesn't block the others. Wasteful, but it worked.

HTTP/2 is one road with many lanes. Cars for different destinations (different requests, called streams) interleave freely on the same road, so a truck in one lane no longer blocks cars in another — you got concurrency back with a single connection. But there's a catch: it's still one road surface. If a pothole (a lost TCP packet) appears, the whole road is closed until the crew patches that one spot, because the rule is "nothing may pass the pothole until it's fixed and everything stays in order." One lost packet, and every lane stalls. That's TCP-level head-of-line blocking.

HTTP/3 gives every lane its own independent surface. A pothole in lane 2 (a lost packet on stream 2) closes only lane 2; lanes 1 and 3 keep flowing while lane 2 is patched. That's what QUIC's per-stream loss recovery buys, and it's why HTTP/3 shines exactly where TCP struggles — lossy mobile networks. QUIC also lets a car keep its plate when it changes roads (connection migration), so your phone switching from Wi-Fi to cellular doesn't drop the connection.

Why an SRE cares

These distinctions decide real dashboards. HTTP/2 to a service over a lossy path can be slower than HTTP/1.1's six connections, because one loss stalls every stream — a genuinely counterintuitive incident. gRPC (built on HTTP/2) will happily send all traffic down one connection to one backend and starve the rest of your fleet if your load balancer only balances connections. And keep-alive misconfigured either way churns connections and hammers you with the TIME_WAIT and handshake costs from Chapters 13 and 14. This chapter is where L4 meets the app.

Internal workingAnatomy, then multiplexing, then QUIC

Start with the part that never changed across versions — the semantics (methods, status codes, headers), standardised in RFC 9110 — then the wire formats that did change.

Methods and what they promise

The method is a verb with a contract. GET retrieves and is safe (no side effects) and idempotent (repeating it changes nothing). PUT and DELETE are idempotent but not safe — doing them twice lands you in the same state as once. POST is neither: two POSTs may create two resources, which is exactly why a double-submitted payment is dangerous and why retries need idempotency keys. HEAD is GET without a body; OPTIONS asks what's allowed (and drives CORS preflight); PATCH is a partial update. The safe/idempotent distinction isn't trivia — it's what tells a proxy, a cache, or a retry layer whether it may repeat a request on your behalf.

Status classes

Five classes, and the boundaries carry meaning. 1xx informational (100 Continue, 101 Switching Protocols); 2xx success (200, 201 Created, 204 No Content); 3xx redirection (301 permanent vs 302 temporary, 304 Not Modified for caching); 4xx the client's fault (400, 401 unauthenticated vs 403 forbidden, 404, 429 Too Many Requests); 5xx the server's fault (500, and the trio SREs live in: 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout). That last trio is diagnostic: a proxy returns 502 when the upstream gave a broken reply, 503 when it's overloaded or has no healthy upstream, and 504 when the upstream didn't answer in time — three different failures people lump together as "the site's down" (the runbook is Chapter 106).

Headers and keep-alive

Headers carry the metadata: Host (mandatory in 1.1, so one IP can serve many sites), Content-Type and Content-Length, Transfer-Encoding: chunked (stream a body of unknown length), Cache-Control, Authorization. And Connection: keep-alive — the default in HTTP/1.1 — is the header that says "don't close this TCP connection, I'll reuse it," which is the same connection-reuse win from Chapter 14: skip the handshake and the slow-start ramp on every request after the first.

HTTP/2: binary framing and multiplexing

HTTP/2 keeps all of that semantics and changes only the wire format. Instead of text, it uses a binary framing layer: the connection is divided into streams, each stream carries one request/response, and streams are chopped into frames that interleave on the single connection. That interleaving is multiplexing — the many-lanes road. Headers get compressed with HPACK (a shared, stateful table, so repeated headers like cookies cost almost nothing after the first request). One connection now does what used to need six. The cost, again: all streams share one TCP byte stream, so a single lost segment blocks delivery of every stream until it's retransmitted — TCP-level head-of-line blocking that HTTP/2 cannot escape because it's below HTTP/2.

Frame by frame, here's what one HTTP/2 request actually does on the wire — this is the staff-level detail behind "multiplexing":

  1. One TCP connection opens and TLS negotiates h2. During the TLS handshake, ALPN advertises h2; both sides agree, and no second connection is needed for the rest of the session.
  2. Each side sends a SETTINGS frame. This connection preface exchanges limits — maximum concurrent streams, initial flow-control window, max frame size — so neither end overwhelms the other.
  3. The client opens a stream with a HEADERS frame. It carries the request as HPACK-compressed headers, including pseudo-headers (:method, :path, :authority, :scheme). Client-initiated streams get odd IDs; the ID is how every later frame is routed to the right request.
  4. Body bytes ride DATA frames on that stream — and a second request can open its own stream immediately, its frames interleaving with the first on the same connection. That interleaving is the multiplexing.
  5. The server replies with HEADERS then DATA on the same stream ID. Responses from many streams come back interleaved; the receiver reassembles each by stream ID. Per-stream and per-connection flow control is managed with WINDOW_UPDATE frames.
  6. The stream ends when both sides flag END_STREAM; the connection stays open for reuse. To wind the whole connection down gracefully, either side sends a GOAWAY frame telling the peer which stream IDs it will still finish — the same mechanism gRPC uses to shed a connection.

HTTP/3: QUIC over UDP

To remove that last stall you have to leave TCP, and that's QUIC (RFC 9000). QUIC runs over UDP and reimplements the good parts of TCP — reliability, ordering, congestion control — but per stream, so a lost packet only delays the one stream whose data it carried; the others keep flowing. QUIC also folds the TLS 1.3 handshake into the connection setup, so a new connection is encrypted from the first byte and set up in fewer round trips (often 1-RTT, sometimes 0-RTT for resumption). And because a QUIC connection is identified by a connection ID rather than the 4-tuple, it survives an IP change — your phone moving from Wi-Fi to cellular keeps the same connection instead of re-establishing it. HTTP/3 is just HTTP semantics over QUIC, with QPACK replacing HPACK to avoid re-introducing head-of-line blocking in header decoding.

Think first: you move a service from HTTP/1.1 to HTTP/2 and, on one lossy network path, tail latency gets worse. How is that possible?

TCP-level head-of-line blocking. Under HTTP/1.1 the browser used six separate TCP connections, so a lost packet only stalled the one connection it was on — the other five kept delivering. Under HTTP/2 everything shares a single TCP connection, so that same lost packet now stalls all the multiplexed streams at once until it's retransmitted. On a clean network HTTP/2 wins easily (one connection, no per-connection overhead, multiplexing); on a lossy path the single shared byte stream can lose to six independent ones. This is exactly the problem HTTP/3 was built to solve by giving each stream independent loss recovery over QUIC. The lesson: HTTP/2 is not a universal win, and "we upgraded to h2 and tail latency regressed on mobile" is a real, explainable incident, not a mystery.

gRPC — HTTP/2 as an RPC substrate

gRPC is a remote-procedure-call framework that uses HTTP/2 as its transport and Protocol Buffers as its message format. Each RPC is an HTTP/2 stream, so a single long-lived connection multiplexes many concurrent calls, and gRPC adds four call shapes: unary (one request, one response), server-streaming, client-streaming, and bidirectional streaming — the last two being genuinely long-lived streams that stay open for the life of the interaction. That efficiency (one warm connection, no per-call handshake, binary messages) is why gRPC is the default for internal service-to-service traffic. It's also the root of the load-balancing problem in the next section: everything a client sends goes down one connection.

gRPC leans on HTTP/2's keep-alive PING frames to keep those long-lived connections healthy — detecting a dead peer and keeping middleboxes from dropping an idle connection. Tuned too aggressively, though, the pings themselves become a problem: a server can respond to a client pinging too often with a GOAWAY carrying ENHANCE_YOUR_CALM / too_many_pings, tearing the connection down. Keep-alive tuning is therefore a two-sided negotiation, not a knob you crank.

Think first: you add three new replicas behind your gRPC service, but the existing replicas stay hot and the new ones get almost no traffic. What's going on?

Your load balancer is balancing connections, not requests. gRPC clients open one long-lived HTTP/2 connection and multiplex all their calls over it, so a connection-level (L4) load balancer makes its decision once, at connect time, and pins that connection — and therefore every request on it — to whichever backend it picked. New replicas added later get no share of existing connections, so they stay cold; the old replicas keep serving everything. The fix is to balance at the request/stream level: an L7, HTTP/2-aware proxy (like Envoy) that distributes individual streams across backends, or client-side load balancing where the gRPC client resolves all backend addresses and round-robins calls across sub-connections, or a service mesh that does the L7 balancing for you. This is the single most common gRPC-in-production surprise, and it looks exactly like "autoscaling isn't working."

Data flowOne request, three ways

A client fetches a page needing three resources. Over HTTP/1.1 with keep-alive, the browser opens up to six TCP connections and pipelines nothing risky, sending requests and getting responses one-per-connection-at-a-time; the three resources race across the six lanes, and a slow one only blocks its own connection. Over HTTP/2, the browser opens one TCP connection, negotiates h2 via TLS ALPN, and sends all three requests as concurrent streams; frames interleave, headers are HPACK-compressed, and the responses come back multiplexed — unless a packet is lost, in which case all three stall until it's retransmitted. Over HTTP/3, the client opens a QUIC connection over UDP (TLS 1.3 folded in, so it's encrypted and set up in one round trip), sends the three requests as independent QUIC streams, and a loss affecting one stream leaves the other two flowing. Same request, same HTTP semantics (methods, headers, status codes are identical across all three), but a completely different behaviour under concurrency and loss — which is the whole reason the versions exist and the whole reason your latency graphs change shape when you switch.

Lab 1Build — read an HTTP exchange with curl -vBuild

curl -v prints the request line, the headers both ways, and the status line. Learn to read it top to bottom.

bash
curl -v http://localhost:8080/ 2>&1 | sed -n '1,20p'
Output (trimmed)> GET / HTTP/1.1 # request line: method, path, version > Host: localhost:8080 # mandatory in 1.1 > User-Agent: curl/8.5.0 > Accept: */* > < HTTP/1.1 200 OK # status line: version, code, reason < Server: nginx < Content-Type: text/plain < Content-Length: 15 < hi over HTTP/1.1

Lines starting > are what curl sent; < are what the server replied. That's the whole protocol laid bare — a verb, a path, a version, headers, a blank line, then the body. Everything else in this chapter is a smarter way to move these same bytes.

Lab 2Understand — negotiate HTTP/2 with ALPNUnderstand

HTTP/2 in the real world is negotiated during the TLS handshake via ALPN. Ask for it, and watch the protocol get chosen.

bash
curl -k -v --http2 https://localhost:8443/ 2>&1 | grep -iE 'ALPN|HTTP/2|using HTTP'
echo "---"
curl -k -s --http1.1 https://localhost:8443/     # force old version on the same server
Output* ALPN: curl offers h2,http/1.1 * ALPN: server accepted h2 * using HTTP/2 hi over HTTP/2 --- hi over HTTP/1.1

Same server, same URL — the protocol is negotiated. curl offered h2 and http/1.1 in the TLS ClientHello's ALPN extension, and the server picked h2. Force --http1.1 and the identical endpoint speaks 1.1. This is why "which HTTP version am I actually using?" is a real question in production: it depends on what both sides negotiated, not on what you assumed.

Lab 3Break — see multiplexing, and the connection that carries itBreak

Prove that HTTP/2 puts many requests on one connection while HTTP/1.1 needs several. First, nghttp shows the individual streams; then ss shows how many TCP connections each approach actually opens.

bash
# nghttp: request several paths at once, watch distinct stream IDs on ONE connection
nghttp -ns https://localhost:8443/ https://localhost:8443/ https://localhost:8443/ 2>&1 | grep -E 'stream|recv'

# Count connections: 3 requests over h2 (one conn) vs http/1.1 (curl opens per-URL)
curl -k -s --http2 https://localhost:8443/{a,b,c} -o /dev/null -w '%{num_connects} connects\n'
Output[ id=13 ] recv HEADERS ... # stream 13 [ id=15 ] recv HEADERS ... # stream 15 — different streams, [ id=17 ] recv HEADERS ... # stream 17 — same connection 1 connects # three requests, one TCP connection

Three requests, three stream IDs, but one TCP connection (num_connects = 1) — that's multiplexing. Now the "break": what makes this a problem rather than a pure win?

Reveal the shared-connection risk

Everything riding one connection means everything shares the fate of that one TCP byte stream. A single lost segment blocks delivery of all three streams (TCP-level head-of-line blocking), which is why HTTP/2 can lose to HTTP/1.1's multiple connections on a lossy path — and exactly what HTTP/3 fixes by giving each stream independent loss recovery over QUIC. It also means the single connection is a single point of contention: if a proxy or load balancer routes by connection, all three requests go to the same backend (the gRPC problem in Lab 5). The takeaway: multiplexing trades many connections for one, which is a big efficiency win and a concentration of risk — and whether it helps or hurts depends on packet loss and on how your load balancer makes decisions.

Lab 4Troubleshoot — keep-alive and connection churnTroubleshoot

Keep-alive decides whether requests reuse a connection or open a fresh one each time. Measure both against the HTTP/1.1 endpoint and watch the connection count and leftover sockets.

bash
# A) Reuse one connection for 100 requests (keep-alive, curl's default per invocation):
curl -s http://localhost:8080/$(printf '%.0s ' {1..1}) -o /dev/null
curl -s -w 'reused: %{num_connects} connects for 100 reqs\n' -o /dev/null \
  $(printf 'http://localhost:8080/ %.0s' {1..100})

# B) Force a new connection per request (Connection: close):
for i in $(seq 1 100); do curl -s -H 'Connection: close' http://localhost:8080/ -o /dev/null; done
echo "close-per-request TIME_WAIT: $(ss -tan state time-wait 'sport = :8080 or dport = :8080' | wc -l)"
Outputreused: 1 connects for 100 reqs close-per-request TIME_WAIT: ~100

Reusing keep-alive: 100 requests, one connection, zero churn. Forcing Connection: close: 100 handshakes and ~100 sockets left in TIME_WAIT — the exact port-pressure and latency cost from Chapter 14. In production the usual bug is a mismatch: the client wants to keep connections alive but the server's keepalive_timeout is too low (or a proxy in the middle closes early), so connections die between requests and the client silently pays for a fresh handshake every time. Tune the server keep-alive to comfortably outlast the client's request interval, and make sure no middlebox closes connections earlier than either endpoint expects.

Lab 5Production challenge — the gRPC L4 load-balancing trapSenior challenge

You don't need a full gRPC stack to see the mechanism — you need to internalise that gRPC pins all its calls to one long-lived HTTP/2 connection. Demonstrate the pinning with the tools you have, then reason about the fix. First, prove that many h2 requests share one connection to one backend:

bash
# 50 requests over h2 — count how many TCP connections (backends) they touch:
curl -k -s --http2 -o /dev/null -w '%{num_connects} connects for 50 requests\n' \
  $(printf 'https://localhost:8443/ %.0s' {1..50})
Output1 connects for 50 requests

All 50 rode one connection. Now imagine that connection went through a connection-level (L4) load balancer to a pool of backends. The senior question: which backends served the 50 requests, and what happens when you scale the pool from 2 to 5? Reason it fully before opening the answer.

Reveal the trap and the three fixes

All 50 requests hit exactly one backend — whichever one the L4 load balancer chose when the single connection was established. An L4 balancer makes its routing decision per connection, at connect time, and then forwards that connection's whole byte stream unchanged; it has no idea the connection carries 50 independent HTTP/2 streams. So scaling from 2 to 5 backends does nothing for existing clients: their connections are already pinned, the three new backends stay cold, and load stays skewed. That's the gRPC load-balancing pitfall, and it fools people because it looks like autoscaling or the balancer is broken when both are working exactly as designed.

The three fixes, in order of how often you'll reach for them: (1) L7 / request-level load balancing — put an HTTP/2-aware proxy like Envoy in front that terminates the connection and balances individual streams across backends; (2) client-side load balancing — have the gRPC client resolve all backend addresses (e.g. via a headless Service in Kubernetes) and round-robin calls across multiple sub-connections itself; (3) a service mesh, which is really option 1 automated for every service. You'll also tune HTTP/2 keep-alive so long-lived connections stay healthy through idle timeouts — but not so aggressively that the server sends GOAWAY too_many_pings. This is the flagship reason "gRPC needs different load balancing than REST," and it's a near-certain interview question for any platform role.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · gRPC traffic skew after scaling

Symptom: new replicas behind a gRPC service get little or no traffic; old replicas stay hot; autoscaling "doesn't help." First cut: check per-backend request rates and how the load balancer routes (L4 vs L7). Confirm: each client's requests all land on one backend. Cause is usually: connection-level (L4) balancing of long-lived HTTP/2 connections. Fix: L7/request-level balancing (Envoy), client-side LB with a headless Service, or a mesh.

Incident pattern · HTTP/2 tail latency worse on mobile

Symptom: after enabling HTTP/2, p99 latency regresses specifically on lossy/mobile networks. First cut: compare loss rates and connection counts. Confirm: the regression tracks packet loss. Cause is usually: TCP-level head-of-line blocking — one lost segment stalls all multiplexed streams, where HTTP/1.1's multiple connections would have isolated the loss. Fix: enable HTTP/3/QUIC where clients support it; it's precisely this problem's cure.

Incident pattern · connections dropped by a keep-alive mismatch

Symptom: intermittent request failures or unexplained latency; connections seem to reset between requests. First cut: compare the client's idle interval to the server's and any proxy's keep-alive/idle timeouts. Confirm: the server or a middlebox closes the connection before the client reuses it. Cause is usually: a keepalive_timeout (or LB idle timeout) shorter than the client's reuse interval, or gRPC keep-alive pings so aggressive the server sends GOAWAY too_many_pings. Fix: align the timeouts so the endpoints and every middlebox agree.

Incident pattern · 502 vs 503 vs 504 confusion

Symptom: a spike of 5xx from a proxy or gateway, reported vaguely as "the site is down." First cut: separate the codes. Confirm & cause: 502 = the upstream returned a broken/invalid response (crashed worker, protocol mismatch); 503 = no healthy upstream or the service is shedding load; 504 = the upstream didn't respond within the proxy's timeout (slow backend or dependency). Fix: each points at a different layer — treating them as one number wastes the first ten minutes (the runbook is Chapter 106).

Production · security · performanceWhat matters in production

Pick the version for the path, not the fashion. HTTP/2 is the right default for most service-to-service and browser traffic on reliable networks — one connection, multiplexing, header compression. But it is not a free upgrade on lossy paths, where TCP head-of-line blocking can make it lose to HTTP/1.1's parallel connections; that's the case for HTTP/3, especially for mobile and edge clients. Enable HTTP/3 where clients support it and keep HTTP/2 as the negotiated fallback.

Load-balance gRPC at L7 or client-side, always. The single biggest gRPC operational rule: never put long-lived HTTP/2 connections behind a connection-level balancer and expect even distribution. Use an HTTP/2-aware proxy, client-side balancing over a headless Service, or a mesh — and monitor per-backend request rates so skew is visible before it becomes an outage.

Security is increasingly non-optional. Browsers require TLS for HTTP/2 in practice, and HTTP/3 builds TLS 1.3 into the protocol — there is no unencrypted HTTP/3. That's good, but it means your observability has to adapt: you can't read encrypted traffic off the wire, so you rely on structured logs, application metrics, and mesh telemetry instead of tcpdump of cleartext. And QUIC rides UDP, which some corporate firewalls block or rate-limit, so plan for graceful fallback to HTTP/2 over TCP rather than a hard failure.

Common mistakes: assuming HTTP/2 is always faster; L4-balancing gRPC and blaming autoscaling for the skew; keep-alive timeouts that disagree across client, server, and proxy; lumping 502/503/504 together; and forgetting that a retried non-idempotent POST can double an effect, so retries need idempotency keys. Every one of these is avoidable with the model from this chapter.

System-design connectionWhere this reaches into architecture

HTTP's shape drives edge and service-to-service design. At the edge, terminating HTTP/2 and HTTP/3 at a load balancer or CDN and speaking a simpler protocol to origins is a standard pattern — it puts the version negotiation, TLS, and QUIC handling in one tuned tier. Inside the mesh, the choice between REST-over-HTTP and gRPC is partly a load-balancing decision: gRPC's long-lived multiplexed connections demand L7 balancing, which is a major reason service meshes exist and put an Envoy sidecar next to every pod (Chapter 66). Keep-alive and connection pooling connect straight back to the port and socket limits of Chapter 14 — a gateway fanning in thousands of client connections and out to a pool of backends is doing exactly the reuse math you learned there. And the idempotency of methods is the foundation of safe retries, timeouts, and circuit breakers in Chapter 88: you can only retry automatically what's safe to repeat. HTTP isn't just how the browser talks to the server; it's the contract that shapes the whole request path.

InterviewInterview questions & answers

Answer each in your head first.

30-secWhat problem does HTTP/2 multiplexing solve, and what does it not solve?

It solves application-layer head-of-line blocking: HTTP/1.1 could only carry one response at a time per connection, so a slow response blocked everything behind it and browsers opened about six connections to cope. HTTP/2 puts many independent streams on one connection and interleaves their frames, so requests no longer wait in line. What it does not solve is transport-layer head-of-line blocking: all those streams share one TCP byte stream, so a single lost packet stalls every stream until it's retransmitted. That remaining problem is exactly what HTTP/3 over QUIC fixes.

2-minWalk me through the three HTTP versions and the blocking each addresses.

HTTP/1.1 uses TCP and text, keeps connections alive for reuse, but carries one response at a time per connection — so a slow response head-of-line-blocks the rest, and browsers work around it with roughly six parallel connections per origin. HTTP/2 keeps the same semantics but switches to a binary framing layer with streams multiplexed over a single TCP connection, plus HPACK header compression; that removes the application-layer blocking and the need for many connections. But because every stream shares one TCP connection, and TCP delivers its byte stream strictly in order, one lost segment now blocks all streams — transport-layer head-of-line blocking that HTTP/2 can't escape because it lives below it. HTTP/3 fixes that by moving off TCP entirely to QUIC over UDP, which implements reliability and ordering per stream, so a lost packet only delays its own stream while the others keep flowing; QUIC also folds in TLS 1.3 for faster, always-encrypted setup and uses connection IDs so a connection survives an IP change. So each version removes a specific stall, and the blocking moves down a layer until QUIC eliminates it.

DeepWhy does gRPC break L4 load balancing, and how do you fix it?

gRPC runs over HTTP/2 and multiplexes every call as a stream over a single long-lived connection to a backend. A layer-4 load balancer balances connections — it picks a backend when the TCP connection is established and then forwards that connection's bytes unchanged, with no visibility into the many requests inside it. So a gRPC client's one connection pins all of its calls to one backend for the life of that connection. The consequences are traffic skew and dead new replicas: when you scale the backend pool, existing clients keep their pinned connections, so the new backends get no traffic and load stays lopsided — which looks like broken autoscaling but is the balancer working exactly as an L4 balancer should. The fixes all move the decision to the request/stream level. First, an L7, HTTP/2-aware proxy such as Envoy terminates the connection and distributes individual streams across backends. Second, client-side load balancing: the gRPC client resolves all backend addresses — in Kubernetes via a headless Service returning every pod IP — and round-robins calls across multiple sub-connections itself. Third, a service mesh, which is really the first option applied automatically to every service via sidecars. Alongside any of these I'd tune HTTP/2 keep-alive so long-lived connections survive idle timeouts, but not so aggressively that the server responds with GOAWAY and too_many_pings. The core insight is that gRPC needs request-level balancing precisely because it deliberately reuses one connection for everything.

ScenarioYou enabled HTTP/2 and p99 latency got worse for mobile users. What happened and what do you do?

This is TCP-level head-of-line blocking showing up on a lossy network. Before, mobile browsers used several independent TCP connections, so a lost packet stalled only the one connection it was on and the others kept delivering. After enabling HTTP/2, all the streams share a single TCP connection, so that same lost packet now stalls every stream at once until it's retransmitted — and mobile networks have enough loss for this to dominate the tail. On clean networks HTTP/2 still wins, which is why the regression is specifically mobile/lossy. I'd confirm by correlating the p99 regression with packet-loss rates and checking it's absent on low-loss paths. The real fix is HTTP/3 over QUIC, whose per-stream loss recovery means one lost packet only delays its own stream — this is the exact problem QUIC was designed for. So I'd enable HTTP/3 for clients that support it while keeping HTTP/2 as the negotiated fallback, and I would not simply "roll back to HTTP/1.1" as a permanent answer, because that's giving up multiplexing to dodge a problem QUIC solves properly.

Follow-upWhat's the difference between 502, 503, and 504, and why does it matter?

All three are 5xx errors returned by a proxy or gateway, but they point at different failures. A 502 Bad Gateway means the upstream gave the proxy an invalid or broken response — a crashed worker, a protocol mismatch, the backend closing the connection mid-reply. A 503 Service Unavailable means there's no healthy upstream to send to or the service is deliberately shedding load — often all backends failing health checks, or a rate limiter kicking in. A 504 Gateway Timeout means the upstream was reachable but didn't respond within the proxy's timeout — a slow backend, or a slow dependency behind it. It matters because each sends you to a different layer: a 502 says look at the backend process and the proxy-to-backend protocol, a 503 says look at capacity and health checks, and a 504 says look at latency and downstream dependencies and your timeout budget. Teams that lump them together as "the site's down" waste the first ten minutes of an incident; separating them is often the fastest path to the right subsystem.

RetainQuick revision

HTTP's semantics — methods, status codes, headers — are stable across versions; what changed is how the bytes move. HTTP/1.1 reuses connections with keep-alive but carries one response at a time, so browsers open ~6 connections to get concurrency. HTTP/2 multiplexes many streams over one TCP connection with binary frames and HPACK, killing application-layer head-of-line blocking — but the shared TCP stream means one lost segment stalls all streams (transport-layer HOL). HTTP/3 moves to QUIC over UDP, giving each stream independent loss recovery, folding in TLS 1.3, and surviving IP changes via connection IDs. gRPC runs on HTTP/2 and multiplexes all calls over one long-lived connection, which breaks connection-level (L4) load balancing — fix it with L7/request-level balancing, client-side LB, or a mesh, and tune keep-alive carefully. Know your status classes, especially 502 vs 503 vs 504, and remember only idempotent methods are safe to retry automatically.

The 10 things to remember

  1. HTTP semantics (methods, status codes, headers) are identical across 1.1/2/3; only the wire transport changes.
  2. HTTP/1.1 = one response per connection at a time (app-layer HOL); browsers open ~6 connections to work around it.
  3. HTTP/2 = binary frames + streams multiplexed over one TCP connection + HPACK; solves app-layer HOL.
  4. HTTP/2's catch: one lost TCP segment stalls all streams — transport-layer HOL it can't escape.
  5. HTTP/3 = QUIC over UDP: per-stream loss recovery (no transport HOL), built-in TLS 1.3, connection migration.
  6. gRPC rides HTTP/2 and pins all calls to one long-lived connection — great efficiency, breaks L4 balancing.
  7. Fix gRPC balancing at L7 (Envoy), client-side (headless Service), or with a mesh — never connection-level.
  8. Keep-alive reuses connections (no handshake, no slow-start restart); mismatched timeouts cause churn and resets.
  9. Status classes: 2xx ok, 3xx redirect, 4xx client, 5xx server; 502=bad upstream reply, 503=no healthy upstream, 504=upstream timeout.
  10. Only safe/idempotent methods (GET, PUT, DELETE) are safe to auto-retry; POST needs idempotency keys.
