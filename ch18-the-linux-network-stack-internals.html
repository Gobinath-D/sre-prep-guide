Part II · Networking from First Principles · Chapter 18

The Linux network stack internals

A Kubernetes pod is not magic. It's a network namespace, a virtual cable, a software switch, and a pile of firewall rules — all primitives that ship in the kernel and that you can assemble by hand in ten commands. Build it once and container networking stops being a black box for the rest of your career.

Start: Beginner→→→End: Staff-level ~50 min read · ip/nft lab (Docker)

By the end of this chapter you can

  • Build two network namespaces joined by a veth pair over a Linux bridge, by hand, and ping across them.
  • Name the five netfilter hooks and say which one DNAT, SNAT, conntrack, and filtering each run at.
  • Trace a packet through PREROUTING → routing → FORWARD/INPUT → POSTROUTING and know where it can be dropped or rewritten.
  • Read conntrack -L and explain how return traffic and NAT find their way back.
  • Point at any pod's networking and say "that's a netns, a veth, a bridge, and iptables — I know exactly what each does."

Why this exists · the problemThe problem: many isolated networks on one host

You have one machine with one network card, and you want to run fifty containers on it. Each needs its own IP, its own routing table, its own view of the network — as if each were its own little host — yet they all have to share that single physical NIC and reach the outside world. And you need to control what talks to what: this container may reach the database, that one may not. On a physical network you'd solve this with separate machines, cables, a switch, and a firewall. Linux gives you all four in software.

The kernel provides network namespaces (each a private network stack — its own interfaces, routes, and firewall), veth pairs (virtual cables that connect one namespace to another), bridges (a software Ethernet switch), netfilter (the hook framework where iptables and nftables enforce rules and do NAT), and conntrack (a table that remembers connections so replies get back and NAT is consistent). Stack those and you have exactly what a container runtime gives a pod. There is no extra layer.

Key point — read this twice

This chapter is the foundation of everything in Parts III and V. A container's network is a network namespace joined to the host by a veth pair (Chapter 25). A Kubernetes pod's network is the same veth-into-a-bridge (or a routed variant) that a CNI plugin sets up (Chapter 42). A Kubernetes Service is a pile of NAT rules in netfilter that kube-proxy writes (Chapter 43). When you understand the primitives here, those three chapters become "oh, it's just this again."

Mental model · analogyThe mental model: an office building's wiring

Real-world analogy

Think of one big office building (the host) that you're subdividing into independent tenant suites (the containers). Each suite gets its own internal phone system and wiring that can't see the neighbours' — that's a network namespace. To connect a suite to the building's shared infrastructure you run a patch cable with a plug at each end: one end in the suite, one in the wiring closet. That two-ended cable is a veth pair — whatever goes in one end comes out the other.

In the wiring closet sits a switch that all the suite cables plug into, so any suite can reach any other. That's the Linux bridge. And at the building's front door sits a security desk with a rulebook — who may enter, who may leave, who gets redirected to a different floor. That desk is netfilter, and the rulebook is what iptables or nftables writes. The desk also keeps a visitor logbook: when someone leaves the building it remembers them, so when their reply courier arrives it knows which suite to send it to without re-checking every rule. That logbook is conntrack.

The reason this matters: a pod is a tenant suite. When you debug "pod A can't reach service B," you're asking whether the cable is plugged in, whether the switch learned the address, and whether the security desk dropped or misrouted the packet. Same four questions, every time.

ArchitectureHow a packet actually travels

Here's the whole picture: two namespaces plugged into a bridge, and the netfilter hooks a packet crosses when it heads for the outside world. Trace it left to right, top to bottom.

Why an SRE cares

When a pod can't reach a Service, this diagram is your map. Is the veth up and the bridge learning the MAC (L2, top)? Did a NetworkPolicy or kube-proxy rule drop or misroute it (the hooks, bottom)? Did the conntrack table fill up and start dropping established connections (a real, brutal outage we'll reproduce)? You can't debug what you can't picture, and this is the picture under every Kubernetes networking problem you'll ever get paged for.

Internal workingThe netfilter hooks, in order

netfilter is five hook points the kernel exposes in the packet path. iptables and nftables don't invent anything — they register rules at these hooks. There are exactly five, and the order a packet meets them depends on where it's going, which the kernel decides at the routing decision in the middle.

  1. A packet arrives on an interface (a veth, a physical NIC). Before anything, the kernel runs the PREROUTING hook.
  2. PREROUTING runs, in priority order: raw (mark packets to skip tracking), then conntrack which looks the packet up in the connection table and tags it NEW / ESTABLISHED / RELATED, then mangle, then DNAT (destination NAT — this is where a Service VIP becomes a real pod IP). DNAT happens before routing on purpose, so the routing decision uses the real destination.
  3. The routing decision. The kernel looks at the (possibly rewritten) destination and asks: is this for me, or does it need forwarding? This split is the fork in the diagram.
  4. If destined for a local address → INPUT, then up to a local process (your nginx, sshd). If the packet is to be forwarded to another interface → FORWARD, where the filter rules decide whether routing between namespaces/interfaces is even allowed. A pod-to-pod packet crossing the host takes the FORWARD path, which is why net.ipv4.ip_forward=1 must be on.
  5. Locally generated packets skip PREROUTING and start at OUTPUT (which also runs raw/conntrack/mangle/DNAT), then hit the routing decision.
  6. POSTROUTING is the last stop before the wire, for both forwarded and locally generated traffic. It runs mangle, then SNAT / MASQUERADE (source NAT — rewrite the source so replies come back to this host), then conntrack confirms the connection into the table. Then the frame goes out the egress interface.

The priorities are fixed and worth memorising because they explain why rules fire in the order they do. From the netfilter project itself: conntrack runs at priority −200 (early), raw at −300 (before conntrack, to opt out), mangle at −150, DNAT at −100, filter at 0, SNAT at +100, and the conntrack "confirm" step runs last in INPUT and POSTROUTING. Lower number = earlier.

Conntrack is why NAT and stateful firewalls work at all

Conntrack records each connection as two tuples: the original direction and the expected reply. When a reply packet arrives, conntrack matches it to an existing entry and marks it ESTABLISHED, so your firewall can say "allow established/related" and only scrutinise NEW packets. It's also how NAT is reversible: the entry remembers that 10.0.0.11:52840 → 93.184.x.x:443 was masqueraded to <host-ip>:PORT, so the reply to the host gets rewritten straight back to the pod. No conntrack, no return path. This is also its weakness — the table is finite, and when it fills, new connections are dropped.

Think first: you set the FORWARD chain's policy to DROP and suddenly your two namespaces can't ping each other, even though the veth and bridge are fine. Why?

Because a packet from ns1 to ns2 isn't for the host — it's being routed through it from one interface to another, so it takes the FORWARD path, not INPUT. With FORWARD policy DROP and no accept rule, the kernel drops it after the routing decision. The L2 wiring is irrelevant here; the packet made it onto the bridge fine. This is the exact shape of a NetworkPolicy denying pod-to-pod traffic: the wiring is intact, the hook said no. Fix it with a rule that accepts the forwarded traffic (and ip_forward=1), which is precisely what a CNI plugin does for you.

ComponentsThe pieces, named

  • Network namespace. A private copy of the entire network stack: its own interfaces, routing table, ARP/neighbour table, conntrack table, and firewall rules. ip netns manages the named ones; every container gets one whether it's named or not.
  • veth pair. Two interfaces that are the two ends of one virtual cable. A frame written to one end appears on the other. You put one end in the container's namespace (it becomes eth0 there) and leave the other in the host, usually enslaved to a bridge.
  • Bridge. A software Ethernet switch. Enslave veth ends to it and it learns which MAC is behind which port (the forwarding database, fdb) and forwards frames accordingly — exactly like a physical switch.
  • netfilter + iptables/nftables. netfilter is the kernel hook framework; iptables and nftables are the userspace tools that program it. On modern distros iptables is actually iptables-nft — a compatibility shim that writes nftables rules underneath. New work should use nft directly.
  • conntrack. The connection-tracking table (module nf_conntrack). Inspect it with conntrack -L; size it with net.netfilter.nf_conntrack_max.
  • The routing table + neighbour table. ip route decides the next hop; ip neigh is the ARP cache mapping next-hop IPs to MACs (Chapter 11).

Data flowFollowing one packet: ns1 pings ns2

ns1 wants to reach 10.0.0.12. Its routing table says that's on-link via eth0, so it needs the MAC for 10.0.0.12. It broadcasts an ARP request out its veth; the bridge floods it to all ports; ns2 replies; ns1 caches the MAC in its neighbour table. Now ns1 sends the ICMP echo to that MAC. The frame goes ns1's eth0 → veth → bridge; the bridge has learned ns2's MAC is on veth2, so it forwards the frame straight there → ns2's eth0. ns2 replies the same way in reverse. That's pure L2 — the packet never left the bridge, so it never touched a routing decision or the FORWARD hook. Contrast that with ns1 reaching the Internet: that destination isn't on-link, so ns1 sends it to its default gateway (10.0.0.1, the bridge), the host routes it toward the uplink (the FORWARD path), and POSTROUTING masquerades the source so replies come home. The labs below build exactly this and let you watch each step.

Hands-onLabs — build, understand, break, troubleshoot

These need CAP_NET_ADMIN, so run a privileged container (the cleanest way to get the capabilities without touching your host's real network):

bash
# --privileged gives us netns/bridge/nft; --rm throws it all away on exit.
docker run --rm -it --privileged ubuntu:24.04 bash
apt-get update && apt-get install -y iproute2 nftables iptables conntrack tcpdump iputils-ping
Lab 1Build — two namespaces, a veth each, one bridgeBuild

This is the whole point of the chapter. Build the topology from the diagram: a bridge in the host, and two namespaces each cabled to it.

bash
ip netns add ns1 && ip netns add ns2

# The bridge acts as the switch and the gateway (10.0.0.1)
ip link add br0 type bridge && ip link set br0 up
ip addr add 10.0.0.1/24 dev br0

# For each namespace: a veth whose far end is created directly inside the ns as eth0
for n in 1 2; do
  ip link add veth$n type veth peer name eth0 netns ns$n
  ip link set veth$n master br0          # plug the host end into the switch
  ip link set veth$n up
  ip netns exec ns$n ip addr add 10.0.0.1$n/24 dev eth0
  ip netns exec ns$n ip link set eth0 up
  ip netns exec ns$n ip link set lo up
  ip netns exec ns$n ip route add default via 10.0.0.1
done

Check the switch learned both ports, and look at ns1 from the inside:

bash
bridge link                          # which veths are enslaved to br0
ip netns exec ns1 ip -br addr
Output3: veth1@br0: <BROADCAST,MULTICAST,UP,LOWER_UP> ... master br0 state forwarding 4: veth2@br0: <BROADCAST,MULTICAST,UP,LOWER_UP> ... master br0 state forwarding lo UNKNOWN 127.0.0.1/8 ::1/128 eth0@if3 UP 10.0.0.11/24 fe80::b022:eff:fe16:166c/64

eth0@if3 tells you ns1's eth0 is one half of veth pair index 3 — the other half is veth1 in the host. state forwarding means the bridge port is live. You've built a two-host network in software.

Lab 2Understand — ping across, then watch ARP and MAC learningUnderstand

Ping ns2 from ns1 and then inspect what that one ping created in the two tables that make L2 work.

bash
ip netns exec ns1 ping -c2 10.0.0.12
ip netns exec ns1 ip neigh          # ns1's ARP cache: who did it learn?
bridge fdb show br br0 | grep -v permanent   # the switch's MAC table
Output2 packets transmitted, 2 received, 0% packet loss, time 1034ms rtt min/avg/max/mdev = 0.110/0.524/0.938/0.416 ms 10.0.0.12 dev eth0 lladdr d2:8c:33:f2:e0:07 REACHABLE b2:22:0e:16:16:6c dev veth1 master br0 d2:8c:33:f2:e0:07 dev veth2 master br0

Three things to read. The ping worked — pure L2 across the bridge. ns1's neighbour table now maps 10.0.0.12 to ns2's MAC, marked REACHABLE (that's the ARP resolution from Chapter 11, live). And the bridge's fdb learned both MACs and which port each sits behind — that's how a switch forwards without flooding. This is the entire L2 datapath, visible in three commands.

Lab 3Understand — write the five hooks, and see conntrackUnderstand

Now the L3 side. Program a small nftables ruleset with base chains at every hook, and watch conntrack record a connection. First, a firewall + NAT ruleset:

bash
nft -f - <<'EOF'
table inet filter {
  chain input   { type filter hook input priority filter; policy drop;
                  ct state established,related accept; iif "lo" accept; }
  chain forward { type filter hook forward priority filter; policy drop;
                  ct state established,related accept; }
  chain output  { type filter hook output priority filter; policy accept; }
}
table ip nat {
  chain postrouting { type nat hook postrouting priority srcnat; policy accept;
                      oifname "eth0" masquerade; }
}
EOF
nft list ruleset
Output (trimmed)table inet filter { chain forward { type filter hook forward priority filter; policy drop; ct state established,related accept } chain input { type filter hook input priority filter; policy drop; ct state established,related accept iif "lo" accept } } table ip nat { chain postrouting { type nat hook postrouting priority srcnat; policy accept; oifname "eth0" masquerade } }

Notice nftables predefines no chains — unlike legacy iptables, which always had INPUT/FORWARD/OUTPUT sitting there. You attach a base chain to a hook explicitly, with a priority. Now generate a connection and read the tracking table:

bash
ip netns exec ns1 ping -c1 10.0.0.12 >/dev/null
conntrack -L 2>/dev/null
Outputicmp 1 29 src=10.0.0.11 dst=10.0.0.12 type=8 code=0 id=8 src=10.0.0.12 dst=10.0.0.11 type=0 code=0 id=8 mark=0 use=1 conntrack v1.4.6: 1 flow entries have been shown.

One entry, two tuples: the original direction (src=.11 dst=.12) and the expected reply (src=.12 dst=.11). That reply tuple is how return traffic is matched and how NAT knows what to undo. For a TCP flow you'd see the state (ESTABLISHED) and [ASSURED] once traffic flowed both ways.

Lab 4Break — the ping stops workingBreak

Reach outside the bridge now — have ns1 route through the host to a fictional external host — but first sabotage one setting. Run this and investigate as if you inherited the box:

bash
sysctl -w net.ipv4.ip_forward=0        # the sabotage
# From ns1, try to reach something that must be ROUTED (not on the bridge):
ip netns exec ns1 ping -c2 -W1 8.8.8.8
Output2 packets transmitted, 0 received, 100% packet loss, time 1015ms

The packet leaves ns1 fine, arrives at the host, and then vanishes. Pings within the bridge still work. What single thing would you check, and why does on-bridge traffic survive while routed traffic dies? Work it out before revealing.

Reveal — the diagnosis

On-bridge traffic (ns1→ns2) is pure L2 and never needs the host to route, so it's unaffected. But 8.8.8.8 isn't on 10.0.0.0/24, so ns1 sends it to the gateway and the host must forward it from the bridge toward the uplink — the FORWARD path. With ip_forward=0 the kernel refuses to route between interfaces and silently drops it. Confirm and fix:

bash
sysctl net.ipv4.ip_forward           # reads 0 — there's your cause
sysctl -w net.ipv4.ip_forward=1      # and it routes again

This is the number-one "my pods have no internet" cause on a hand-built or misconfigured node. Every CNI turns forwarding on; when someone's custom node image resets it, this is the symptom. The tell is that pod-to-pod on the same node works while anything routed fails.

Lab 5Production challenge — "nf_conntrack: table full, dropping packet"Senior challenge

This is one of the nastiest production incidents in container land, because it drops healthy, established connections, not just new ones. Shrink the table to force it:

bash
sysctl net.netfilter.nf_conntrack_max          # the ceiling (often ~262144 on a real node)
cat /proc/sys/net/netfilter/nf_conntrack_count # how many entries right now
sysctl -w net.netfilter.nf_conntrack_max=8      # tiny, to reproduce fast
# now open a burst of connections and watch the kernel log
dmesg | tail -3
Outputnet.netfilter.nf_conntrack_max = 8 [ 1123.44 ] nf_conntrack: nf_conntrack: table full, dropping packet

The senior scenario: a busy node under load starts dropping a small fraction of packets; latency spikes, retries pile on, and it gets worse as traffic grows. Health checks flap. How do you confirm conntrack is the cause and fix it without just restarting nodes and hoping? Think first.

Reveal an approach

Confirm by comparing count to max and checking for the drop counter, then look at what's filling the table:

bash
cat /proc/sys/net/netfilter/nf_conntrack_count   # vs nf_conntrack_max
conntrack -S                                     # per-cpu 'insert_failed' / 'drop' counters
conntrack -L | awk '{print $1}' | sort | uniq -c # which protocol dominates

If count is pinned at max and drop/insert_failed are climbing, that's it. The usual causes: a client opening thousands of short-lived connections without reuse (each leaves a conntrack entry in TIME_WAIT for a while), an unclosed connection leak, or a SNAT/masquerade path (every masqueraded flow is tracked). Fixes, in order: raise nf_conntrack_max and the hashtable size to give headroom; fix the app to reuse connections/pools; and for pure L3/L4 forwarding that doesn't need NAT, mark packets notrack in the raw table so they never consume an entry. On Kubernetes this exact failure shows up as random pod connection drops under load, and it's why large clusters tune conntrack on every node — you'll see it again in Chapter 43. Reset with sysctl -w net.netfilter.nf_conntrack_max=262144.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · conntrack table full

Symptom: a node drops a small, growing fraction of packets under load; established connections break, not just new ones; latency and retries climb. First cut: dmesg | grep nf_conntrack and compare nf_conntrack_count to nf_conntrack_max. Confirm: count pinned at max, conntrack -S shows rising drops. Cause is usually: connection churn without reuse, a leak, or heavy NAT. Raise the limit for breathing room, fix the client, and consider notrack for flows that don't need tracking.

Incident pattern · forwarding disabled

Symptom: containers/pods on a node reach each other but have no external connectivity. First cut: sysctl net.ipv4.ip_forward. Confirm: it reads 0. Cause is usually: a hardened node image or a sysctl drop-in that reset it, undoing what the CNI set. The tell is that on-node pod-to-pod works while anything routed fails.

Incident pattern · missing MASQUERADE

Symptom: pods can send packets out but get no replies; captures show the SYN leaving with the pod's private source IP. First cut: nft list ruleset or iptables -t nat -L POSTROUTING -n for a masquerade/SNAT rule on the uplink. Confirm: no SNAT rule, so the far end tries to reply to an unroutable private address. Cause: a wiped or misordered NAT table — exactly what happens if something flushes iptables on a node running kube-proxy.

Production · security · performanceWhat matters in production

Performance and scale. Two limits bite real clusters. First, conntrack: it's a fixed-size hash table, and both its max entries (nf_conntrack_max) and bucket count (nf_conntrack_hashsize) must be sized for the node's connection volume, or you get the table-full outage above. Second, iptables rule scaling: kube-proxy in iptables mode writes O(services × endpoints) linear rules, and on clusters with thousands of Services the rule set gets large enough that programming and matching cost real CPU — which is why IPVS mode and, increasingly, eBPF-based dataplanes (Cilium) exist. Know that the primitive is the same; only how the rules are stored and matched changes.

Security. Namespaces isolate the view of the network but not the kernel — all namespaces share one netfilter/conntrack engine, so a rule or a table-exhaustion in one place can affect others on the host. The FORWARD chain is where cross-namespace policy lives; a NetworkPolicy is ultimately rules at that hook. And because iptables is now iptables-nft on most distros, mixing legacy-iptables and nft tooling on the same host is a genuine footgun — pick one.

Common mistakes: flushing iptables on a node and wondering why every Service broke (you deleted kube-proxy's rules); forgetting ip_forward on a custom image; assuming a dropped ping is L2 when it's the FORWARD policy; and reading iptables -L output as if it showed NAT (it doesn't — you need -t nat). Each of those is an afternoon lost until you've built the stack by hand once.

System-design connectionWhere this reaches into architecture

Everything above is the container and Kubernetes datapath — there's no separate technology to learn later, only these primitives arranged differently. A container's network is a namespace on a veth (Chapter 25). Pod-to-pod networking is veth-into-a-bridge or a routed CNI overlay (Chapter 42). A Service is DNAT rules that turn a stable VIP into a live pod IP, plus SNAT so replies return — written by kube-proxy at exactly the PREROUTING/POSTROUTING hooks you programmed above (Chapter 43). A NetworkPolicy is filter rules at FORWARD. When you architect a cluster's networking — choosing a CNI, sizing conntrack, deciding iptables vs IPVS vs eBPF — you're making decisions about these components at scale. InterviewInterview questions & answers

Answer each in your head first.

30-secWhat is a veth pair and what is it for?

A veth pair is two virtual network interfaces that act as the two ends of a single cable — a frame written to one end comes out the other. You use it to connect a network namespace to something outside it: put one end inside a container's namespace where it becomes eth0, and leave the other end in the host, usually enslaved to a bridge. That's how a container, which lives in its own network namespace, gets a link to the host's network. It's the fundamental building block of container networking.

2-minTrace a packet through the netfilter hooks and say where NAT and filtering happen.

A packet arriving on an interface hits PREROUTING first, where conntrack looks it up and DNAT can rewrite the destination — DNAT is before routing so the routing decision uses the real target. Then the kernel makes the routing decision: if the destination is a local address it goes to INPUT and up to a local process; if it needs forwarding to another interface it goes to FORWARD, where the filter rules decide whether that's allowed. Locally generated packets skip PREROUTING and start at OUTPUT, then hit the routing decision too. Everything heading out ends at POSTROUTING, where SNAT or masquerade rewrites the source and conntrack confirms the connection into its table, before the frame goes on the wire. So: DNAT in PREROUTING, filtering in INPUT/FORWARD, SNAT in POSTROUTING, and conntrack early in PREROUTING and confirmed at the end. That mapping is the whole model.

DeepWhy does conntrack matter, and how can it take down a node?

Conntrack makes stateful firewalling and NAT possible: it stores each connection as an original tuple and an expected reply tuple, so return packets are matched to ESTABLISHED and NAT is reversible — the entry remembers what was rewritten so the reply can be un-rewritten. The catch is that it's a fixed-size hash table. Under high connection churn — think a client opening thousands of short-lived connections, all masqueraded — entries pile up (including TIME_WAIT stragglers) and the table fills. When it's full the kernel logs "nf_conntrack: table full, dropping packet" and drops packets, including ones belonging to established healthy connections, so the failure looks like random latency and resets that get worse under load. You confirm it by comparing nf_conntrack_count to nf_conntrack_max and watching conntrack -S drops. You fix it by sizing the table up, fixing the client to reuse connections, and marking flows that don't need tracking as notrack. On large Kubernetes clusters this is a standard node-tuning item.

ScenarioTwo pods on the same node can talk, but neither can reach the internet. Walk me through it.

Pod-to-pod on one node working tells me L2 is fine — the veths are up and the bridge is forwarding — so the problem is in routing or NAT, the L3 path. I'd check three things in order. First, sysctl net.ipv4.ip_forward; if it's 0 the kernel won't route from the pod bridge to the uplink, which is my top suspect and matches the symptom exactly. Second, the NAT table — iptables -t nat -L POSTROUTING -n or nft list ruleset — for a masquerade rule on the egress interface; without SNAT the far end tries to reply to a private pod IP and can't. Third, conntrack and the FORWARD policy, in case a rule is dropping the routed traffic. I'd confirm with a capture on the uplink to see whether the SYN even leaves and with what source IP. The reasoning is that same-node pod traffic is L2 and unaffected, so I focus entirely on the forward-and-NAT path.

Follow-upHow does all this relate to a Kubernetes pod?

A pod is exactly this: a network namespace connected to the node by a veth pair, with the host end wired into a bridge or a routed CNI setup — the same commands from Lab 1, run by a CNI plugin instead of by me. The pod's eth0 is one end of a veth; the node holds the other. A Service is netfilter rules: kube-proxy programs DNAT in PREROUTING to turn the Service VIP into a real pod IP and SNAT in POSTROUTING for return traffic, at the same hooks we used. A NetworkPolicy becomes filter rules at the FORWARD hook. So debugging pod networking is debugging namespaces, veths, bridges, and netfilter — there's nothing else under it. That's why building it by hand once makes the whole of Kubernetes networking legible.

RetainQuick revision

Linux builds many isolated networks on one host from five primitives. A network namespace is a private stack (interfaces, routes, ARP, conntrack, firewall). A veth pair is a virtual cable joining namespaces. A bridge is a software switch that learns MACs. netfilter exposes five hooks — PREROUTING, INPUT, FORWARD, OUTPUT, POSTROUTING — and iptables/nftables register rules there: DNAT in PREROUTING (before the routing decision), filtering in INPUT/FORWARD, SNAT/masquerade in POSTROUTING. conntrack records each connection as original+reply tuples so replies match and NAT is reversible — and its fixed-size table, when full, drops even established packets. On-bridge traffic is pure L2 and never routes; cross-subnet traffic takes the FORWARD path and needs ip_forward=1. Every container and every Kubernetes pod is built from precisely these pieces.

The 10 things to remember

  1. A network namespace is a complete private network stack; every container gets one.
  2. A veth pair is a two-ended virtual cable — one end in the namespace (eth0), one in the host.
  3. A Linux bridge is a software switch: enslave veth ends to it and it learns MACs into its fdb.
  4. There are five netfilter hooks: PREROUTING, INPUT, FORWARD, OUTPUT, POSTROUTING.
  5. DNAT runs in PREROUTING (before routing); SNAT/masquerade runs in POSTROUTING (last).
  6. The routing decision splits traffic: local → INPUT, forwarded → FORWARD, out → POSTROUTING.
  7. Cross-subnet/pod-to-internet traffic takes FORWARD and needs net.ipv4.ip_forward=1.
  8. conntrack stores original+reply tuples; it's why stateful firewalls and reversible NAT work.
  9. A full conntrack table drops established packets — a growing, load-dependent outage.
  10. Containers and Kubernetes pods, Services, and NetworkPolicies are all just these primitives.
