Capstone trace: curl https://example.com

One command. Twelve subsystems. You've met each of them alone in Chapters 10–18 — now watch them fire in sequence, in real time, in the order the packets actually leave your NIC. When you can narrate this trace from memory, you understand networking.

By the end of this chapter you can

  • Narrate every stage of an HTTPS request end to end, from process start to connection teardown, without notes.
  • Name the exact command or packet that reveals each stage, and run them yourself.
  • Map each stage back to the chapter that owns it — DNS, sockets, routing, ARP, TCP, TLS, HTTP.

Why this exists · the problemThe problem: the layers only make sense together

You've spent nine chapters taking the network apart. The layered model, Ethernet and ARP, IP and routing, TCP, sockets and ports, DNS, HTTP, TLS, and the kernel stack that carries all of it. Each was a clean, isolated idea. But nobody runs "a TCP handshake" for its own sake. In production these layers fire together, in a fixed order, in milliseconds — and when something breaks, the symptom ("the site is down") gives you no clue which layer failed.

So here's the problem this chapter solves: turning nine separate mental models into one. We take the most ordinary command an SRE runs — curl https://example.com — and follow it all the way down and back up, watching each layer hand off to the next with the actual tool that exposes the handoff. By the end, "the site is slow" stops being a mystery and becomes a decision tree, because you'll know exactly what happens between pressing Enter and seeing the HTML.

Key point

Every distributed-systems failure you'll ever debug is a variation of this one request. A service calling another service does the same DNS lookup, the same routing decision, the same TCP and TLS handshakes, the same HTTP exchange. Master this trace and you've master the shape of all network requests — the only thing that changes is the endpoints.

Mental model · analogyThe mental model: posting an international parcel

Real-world analogy

Say you want to send a sealed, signed contract to a company overseas and get their signed copy back. You can't just throw it in the air. First you look up their address in a directory — you know the company name, not the street (that's DNS: name → IP). Then you decide which courier and route gets it out of your country — you don't know every road, you just hand it to the right outbound gateway (that's routing: which next hop). To physically hand the parcel to that first courier, you need to find them at the depot — their specific loading bay (that's ARP: next-hop IP → MAC).

Before either side sends anything valuable, you open an account with the courier and agree terms — a back-and-forth that both sides confirm (that's the TCP handshake). Because the contract is confidential, you also agree a private seal and check each other's ID against a trusted authority before exchanging anything (that's the TLS handshake and PKI). Only now do you send the actual letter — "please send me your homepage" — and get the reply (that's HTTP). When you're done, you both formally close the account so no charges linger (that's the connection teardown, and the reason TIME_WAIT exists).

Every step depends on the one before. Get the address wrong and nothing else happens. Find the depot but the courier never confirms the account, and your letter sits undelivered. That dependency chain is exactly why localising a network failure means walking the stages in order.

Why an SRE cares

Count the round trips in that diagram: one for DNS (if uncached), one for TCP, one for the TLS 1.3 handshake — then the request. For a user 100 ms away that's ~300 ms of pure overhead before a single byte of content. This is the entire reason connection reuse, keep-alive, session resumption, and CDNs exist, and why "just add a retry" sometimes makes latency worse. You can't reason about any of it until you can see all the round trips at once.

Internal workingThe twelve stages, and the tool that reveals each

Here is the full journey. For every stage: what happens, and the exact command or packet that shows it to you.

  1. Process start. Your shell fork()s and execve()s curl; the dynamic linker (ld.so) maps libc and libcurl; curl parses the URL into scheme https, host example.com, port 443, path /. Reveal: strace -f curl ... — the opening execve, openat, and mmap lines (Ch 1).
  2. DNS resolution. curl calls getaddrinfo("example.com"). libc reads /etc/nsswitch.conf to learn the lookup order, checks /etc/hosts, then reads /etc/resolv.conf for the resolver and sends a UDP query to port 53. The resolver returns A and AAAA records. Reveal: in strace, the openat of those files then a socket(AF_INET, SOCK_DGRAM) + connect(...:53); on the wire, tcpdump -n port 53 (Ch 15).
  3. Address selection. With both an A and AAAA answer, curl picks one (Happy Eyeballs: it may race IPv6 and IPv4 and take whichever connects first). Say it picks 104.20.23.154. Reveal: curl -v prints * Trying 104.20.23.154:443....
  4. Socket creation. curl calls socket(AF_INET, SOCK_STREAM, 0) to get a TCP socket — a file descriptor it will connect(), write(), and read() like any other fd. Reveal: strace shows the socket() returning an fd (Ch 14).
  5. Routing decision. Before a SYN can leave, the kernel asks: how do I reach 104.20.23.154? It consults the routing table. The destination isn't on any local subnet, so it matches the default route and the next hop is the gateway. Reveal: ip route get 104.20.23.154 prints the chosen source IP, device, and gateway (Ch 12).
  6. ARP for the next hop. To build the Ethernet frame the kernel needs the gateway's MAC. If it's not cached, it broadcasts an ARP request ("who has 192.168.1.1?") and caches the reply. Note: it resolves the MAC of the gateway, not of example.com — L2 only ever reaches the next hop. Reveal: ip neigh shows the cached MAC; tcpdump -n arp shows the request/reply (Ch 11).
  7. TCP three-way handshake. The kernel sends SYN, gets SYN,ACK, sends ACK; connect() returns and the socket is ESTABLISHED. One round trip. Reveal: tcpdump shows Flags [S], [S.], [.]; ss -tan shows the state (Ch 13). This whole exchange rides through the netfilter hooks of Ch 18.
  8. TLS handshake. Over the now-open stream, curl sends a ClientHello with SNI=example.com, ALPN offering h2,http/1.1, and a key_share. The server replies with ServerHello, its certificate chain, CertificateVerify, and Finished; curl validates the chain to a root in its trust store, checks the SAN and dates, and sends Finished. One round trip in TLS 1.3. Reveal: curl -v narrates each TLS handshake, ClientHello (1) line and prints the negotiated version and cipher (Ch 17).
  9. Application protocol chosen. ALPN resolved to h2, so curl speaks HTTP/2. Reveal: curl -v prints * ALPN: server accepted h2 (Ch 16).
  10. HTTP request. curl sends the request headers — for HTTP/2 as a HEADERS frame with :method GET, :authority example.com, :path / — encrypted inside TLS records. Reveal: strace shows a sendto() (opaque ciphertext for HTTPS); curl -v prints the > GET / lines it sent in the clear before encryption.
  11. Server processing and response. The server routes the request, renders, and streams back HTTP/2 200 with headers and the HTML body. Reveal: recvfrom() in strace; < HTTP/2 200 in curl -v; the body on stdout.
  12. Teardown. curl is done, so it close()s the socket. TCP exchanges FIN/ACK both ways; the side that closed first sits in TIME_WAIT for a couple of minutes to absorb stray packets. Reveal: tcpdump shows the [F.] flags; ss -tan shows TIME-WAIT (Ch 14).
The dependency chain is the debugging order

Stages 2→7→8 are strictly sequential: no DNS answer, no SYN; no ESTABLISHED socket, no TLS; no TLS, no HTTP. That's why you localise a failure by walking the stages in order and stopping at the first one that fails. A slow or failed request is always one specific stage, and the timing breakdown in Lab 5 tells you which in one command.

ComponentsThe actors involved

  • curl — the user-space process driving the whole thing, making syscalls.
  • libc's resolver (getaddrinfo) — turns the name into addresses using nsswitch, hosts, and resolv.conf.
  • The DNS resolver — a separate server (your router, systemd-resolved on 127.0.0.53, or a public resolver) that answers the query. A different endpoint from the web server.
  • The kernel socket + TCP/IP stack — creates the socket, makes the routing decision, runs the handshake, moves bytes, and runs it all through the netfilter hooks.
  • The routing table and neighbour (ARP) cache — decide the next hop and its MAC.
  • The NIC and everything past it — the gateway, the internet, and finally the web server (here, Cloudflare's edge serving example.com).
  • The web server — terminates TLS, speaks HTTP, and returns the response.

Data flowThe whole thing in one breath

curl starts, parses the URL, and asks libc to resolve example.com; libc checks nsswitch and hosts, then fires a UDP query to the resolver in resolv.conf and gets back 104.20.23.154. curl opens a TCP socket; the kernel checks the routing table, finds the default gateway is the next hop, ARPs for the gateway's MAC, and sends a SYN. After SYN/SYN-ACK/ACK the socket is established. curl runs a TLS 1.3 handshake over it — ClientHello with SNI and ALPN, server certificate validated to a trusted root — then sends an HTTP/2 GET inside encrypted records. The server returns 200 and the HTML. curl prints the body and closes the socket, leaving it in TIME_WAIT. Three round trips of setup (DNS, TCP, TLS), one for the request, done. Now let's watch it happen.

Lab 1Build — strace the whole request and read the syscallsBuild

strace shows the request as the kernel sees it. Filter to the network-relevant calls so the DNS → socket → connect → send → recv sequence stands out:

bash
strace -f -e trace=openat,socket,connect,sendto,recvfrom -s 80 curl -s https://example.com -o /dev/null

First you'll see the DNS resolver consult its files, then reach for a UDP socket to port 53 — this is stages 1–2, exactly:

Output — the DNS resolution (real, trimmed)openat(AT_FDCWD, "/etc/host.conf", O_RDONLY|O_CLOEXEC) = 3 openat(AT_FDCWD, "/etc/resolv.conf", O_RDONLY|O_CLOEXEC) = 3 connect(3, {sa_family=AF_UNIX, sun_path="/var/run/nscd/socket"}, 110) = -1 ENOENT (No such file or directory) openat(AT_FDCWD, "/etc/nsswitch.conf", O_RDONLY|O_CLOEXEC) = 3 openat(AT_FDCWD, "/etc/hosts", O_RDONLY|O_CLOEXEC) = 3 socket(AF_INET, SOCK_DGRAM|SOCK_CLOEXEC|SOCK_NONBLOCK, IPPROTO_IP) = 3 connect(3, {sa_family=AF_INET, sin_port=htons(53), sin_addr=inet_addr("127.0.0.53")}, 16) = 0

Read it as the resolver's decision process: check nsswitch.conf for order, try the caching daemon (nscd, absent here → ENOENT), read /etc/hosts, then open a UDP socket and connect it to the resolver from resolv.conf on port 53. That's Chapter 15 in six lines. Then comes the TCP socket for the actual request and the payload — this is the same real trace against a plain HTTP server, so you can see the cleartext GET (with HTTPS the bytes are encrypted, but the syscalls are identical):

Output — the TCP socket & HTTP (real, from an http:// fetch)socket(AF_INET, SOCK_STREAM, IPPROTO_IP) = 5 connect(5, {sa_family=AF_INET, sin_port=htons(80), sin_addr=inet_addr("...")}, 16) = -1 EINPROGRESS (Operation now in progress) sendto(5, "GET / HTTP/1.1\r\nHost: example.com\r\nUser-Agent: curl/8.5.0\r\n..."..., 78, MSG_NOSIGNAL, NULL, 0) = 78 recvfrom(5, "HTTP/1.1 200 OK\r\nContent-Type: text/html\r\n..."..., 102400, 0, NULL, NULL) = 724

connect returns EINPROGRESS because curl uses a non-blocking socket and waits with poll/epoll — normal. Then one sendto carries the request and recvfrom receives the response. Socket → connect → send → receive: the L4 lifecycle from Chapter 14, live.

Lab 4Break — three different failures, same commandBreak

The whole point of the trace is that different failures stop at different stages. Reproduce three and learn to tell them apart before reading the cause:

bash
curl -v https://nonexistent.invalid          # A
curl -v --connect-timeout 3 https://10.255.255.1   # B (unroutable / no reply)
curl -v https://expired.badssl.com           # C (needs internet)
Output — the first line of each failureA: curl: (6) Could not resolve host: nonexistent.invalid B: curl: (28) Failed to connect ... Connection timed out after 3000 ms C: curl: (60) SSL certificate problem: certificate has expired

Three exit codes, three different stages. Before you read on: which stage did each stop at, and how would curl -v confirm it? Think it through.

Reveal — the diagnosis for each

A (exit 6) failed at stage 2, DNS — the name never resolved, so no socket was even created. In curl -v you'd see it stop right after "Host ... was resolved" fails; nothing about "Trying" or "Connected." B (exit 28) resolved fine and got to stage 7, the TCP handshake: it printed "Trying 10.255.255.1:443..." and then hung — the SYN went out and no SYN-ACK came back (a silent drop by a firewall or a dead host). A connection refused would be instant (RST); a timeout means the packet vanished. C (exit 60) completed DNS, TCP, and reached stage 8, TLS, where certificate validation failed — you'd see the ClientHello/ServerHello lines and then the cert error. Same command, and the stage it dies at names the layer. This is the reflex Chapter 20 turns into a full toolkit.

Lab 5Production challenge — "the site is slow." Which layer?Senior challenge

"Slow" is useless until you attribute the milliseconds to a stage. curl's -w flag prints a timing breakdown that maps one-to-one onto the diagram — this single command is how a senior localises latency instantly.

bash
curl -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' \
  -s -o /dev/null https://example.com
Output (example)dns=0.084 connect=0.121 tls=0.204 ttfb=0.336 total=0.340

These are cumulative seconds from the start. The senior skill is reading the gaps: DNS took 84 ms; the TCP handshake added connect − dns = 37 ms; the TLS handshake added tls − connect = 83 ms; the server's think time was ttfb − tls = 132 ms. The challenge: three services each report "slow," with these breakdowns — service X has dns=1.9, service Y has connect=2.0 but tiny DNS, service Z has ttfb=3.0 but tiny everything-else. What's wrong with each, and where do you look? Decide before revealing.

Reveal — attributing each

X (dns=1.9s): DNS is slow — a failing or far-away resolver, or a record with a tiny TTL causing constant re-lookups. Look at /etc/resolv.conf, the resolver's health, and whether a cache (systemd-resolved, nscd, or a CoreDNS pod in-cluster) is doing its job. Y (connect=2.0s, dns small): the TCP handshake is slow — SYNs are being dropped and retransmitted (a saturated path, a firewall doing SYN-cookie games, or an overloaded server backlog), because a healthy handshake is one RTT. Capture with tcpdump and look for retransmitted [S]. Z (ttfb=3.0s, rest small): the network is fine; the server is slow to produce the first byte — a slow query, a cold cache, GC pause, or a downstream dependency. This is an application problem, not a network one, and no amount of network tuning fixes it. The lesson: the breakdown tells you which team's problem it is before you've opened a single dashboard. This is exactly the reasoning the next chapter systematises.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · "half our requests are slow"

Symptom: intermittent latency with no obvious pattern. First cut: run curl -w repeatedly and watch which phase varies. Confirm: if time_namelookup spikes on some runs, it's DNS (a flaky resolver in the pool); if time_connect spikes, it's packet loss causing SYN retransmits; if only time_starttransfer spikes, it's the server. Cause is usually: one bad resolver, one lossy path/AZ, or one slow backend — the breakdown tells you which without guessing.

Incident pattern · "connection refused vs timeout"

Symptom: curl fails to connect. First cut: is it instant or does it hang? Confirm: instant "Connection refused" (exit 7) means the SYN reached a host that sent back a RST — something's there but nothing is listening on that port. A hang then "timed out" (exit 28) means the SYN got no reply at all — a firewall drop or a black-holed route. Cause: refused → wrong port / crashed service / not started; timeout → firewall, security group, or routing. These two feel identical to users and are opposite problems; the distinction is stage 7 behaviour.

Incident pattern · "works from my laptop, fails from the pod"

Symptom: the same curl succeeds from one place and fails from another. First cut: run the identical curl -v from both and diff where they diverge. Confirm: different resolved IPs (split-horizon DNS), a TLS failure only from the pod (missing CA bundle in the image), or a connect timeout only from the pod (NetworkPolicy or security group). Cause: the environment differs at exactly one stage — and the trace shows which.

Production · security · performanceWhat matters in production

Every round trip is latency you pay per connection. DNS, TCP, and TLS are three round trips of setup before the first request. That's why production clients reuse connections (HTTP keep-alive, HTTP/2 multiplexing, connection pools) so those three round trips are amortised over thousands of requests, and why CDNs put the TLS-terminating edge physically close to users to shrink each RTT. It's also why "add a retry" can backfire: a retry that opens a fresh connection re-pays all three handshakes.

Caching hides stages, which is good until it's stale. A warm DNS cache skips stage 2; a resumed TLS session skips most of stage 8; a pooled connection skips 5–8 entirely. Great for latency — but it means a DNS change, a cert rotation, or a moved backend can take effect at wildly different times for different clients. When "it updated for me but not for them," a cache somewhere is holding an old stage-2 or stage-8 result.

Security lives at stages 2 and 8. DNS is the soft underbelly — poison a resolver and stage 2 hands out an attacker's IP, and every later stage happily connects to it (which is what DNSSEC and DoH address). TLS at stage 8 is what makes stage-2 hijacking survivable: even if you connect to the wrong IP, certificate validation should fail. This is exactly why disabling verification (curl -k) is so dangerous — it removes the one check that catches a mis-resolved or intercepted connection. Common mistakes: reading a timeout as "server down" when it's a dropped SYN; blaming the network for a slow ttfb that's really the app; and assuming a browser's success proves the path works when it's using a cached everything.

System-design connectionWhere this reaches into architecture

This single trace is the latency budget you design systems around. When you place a CDN or edge, you're cutting the RTT on stages 5–8 for distant users. When you choose connection pooling or a service mesh with persistent mTLS connections, you're amortising the three setup round trips across many requests (Chapter 66). When you design a multi-region system, DNS-based routing (stage 2) is how you send users to the nearest healthy region, and its TTL is how fast you can fail over (Chapter 53). The end-to-end AWS synthesis in Chapter 60 is literally this trace with an ALB, target group, and pod substituted for the single server — same stages, more hops. Every building block in Chapter 94 is a way to make one of these stages faster, cheaper, or more reliable.

InterviewInterview questions & answers

The classic "what happens when you type a URL and press Enter?" is this chapter. Answer each before opening.

30-secWhat happens when you run curl https://example.com?

curl parses the URL, then resolves example.com to an IP via DNS. The kernel makes a routing decision to find the next hop, ARPs for its MAC, and opens a TCP connection with a three-way handshake. Over that connection curl runs a TLS handshake — sending SNI and ALPN, validating the server's certificate against a trusted root — then sends an HTTP request inside encrypted records. The server returns the response, curl prints it, and the connection is torn down with FIN/ACK, leaving the client end in TIME_WAIT. DNS, TCP, and TLS are three round trips of setup before the request even goes out.

2-minWalk me through the same command in full detail.

The shell execs curl, which parses out scheme, host, and port. curl calls getaddrinfo, so libc reads nsswitch.conf for order, checks /etc/hosts, then queries the resolver from resolv.conf over UDP port 53 and gets back A and AAAA records; it selects one, possibly racing v6 and v4. It creates a TCP socket. Before the SYN leaves, the kernel consults the routing table — example.com isn't local, so the next hop is the default gateway — and resolves the gateway's MAC via ARP if it's not cached. Then the three-way handshake: SYN, SYN-ACK, ACK, and connect() returns. Over the established stream curl sends a TLS 1.3 ClientHello with SNI=example.com, ALPN offering h2, and a key_share; the server replies with ServerHello, its certificate chain, CertificateVerify, and Finished; curl builds the chain to a trusted root, checks the SAN and validity, and sends its Finished — one round trip. ALPN chose h2, so curl sends an HTTP/2 GET encrypted inside TLS records. The server returns 200 and the body. curl closes the socket; TCP does FIN/ACK both ways and the closing side sits in TIME_WAIT. I can see the syscalls with strace, the packets with tcpdump, and the labelled stages with curl -v.

DeepThe command hangs for 30 seconds then fails. How do you find out where?

A long hang points at a stage that waits on a network reply that never comes — most likely DNS or the TCP handshake, since those are the ones that block. I'd run curl -v and watch how far it gets: if it hangs before "Trying," DNS is timing out (a dead or unreachable resolver); if it prints "Trying <ip>" and then hangs, the SYN is going unanswered — a dropped packet, a firewall black hole, or a host that isn't there — which is different from an instant "Connection refused" that would mean a RST from a live host with nothing listening. To confirm, curl -w shows whether time_namelookup or time_connect is where the seconds go, and tcpdump shows whether SYNs are being retransmitted with no reply. The 30-second figure itself is a clue — it's near default connect/DNS timeouts. The method is always the same: walk the stages in order and stop at the first that doesn't complete.

ScenarioDNS resolves to the right IP, TCP connects, but TLS fails. What are the possibilities?

Getting to TLS means stages 1–7 are healthy, so it's a certificate or handshake problem. The usual causes: an expired certificate; an incomplete chain (server didn't send the intermediate, so curl can't build a path to a root even though a browser could); a hostname mismatch (the name I asked for isn't in the cert's SAN, or I didn't send SNI and got the wrong default cert); a protocol/cipher mismatch (client and server share no common TLS version or suite); or a missing CA bundle on the client side, common in minimal container images. I'd confirm with openssl s_client -connect host:443 -servername host to see the chain, dates, and negotiated version directly. Each of these is a distinct fix, and they all present as "TLS failed" until you look — which is why stage 8 has its own diagnostic command from Chapter 17.

Follow-upHow does this trace change for a service calling another service inside Kubernetes?

The shape is identical; the endpoints and hops change. DNS resolves a Service name via CoreDNS instead of a public resolver. The routing decision and ARP happen inside the node's network namespace and across the pod bridge or CNI overlay from Chapter 18, and the Service IP gets DNAT'd by kube-proxy to a real pod IP. The TCP handshake is pod-to-pod. If there's a service mesh, the TLS handshake is mutual — both sides present workload certificates — and the connection is long-lived and pooled by the sidecars, so those setup round trips are paid once, not per request. Then it's the same HTTP exchange. So everything I described still happens; it just happens between two pods with a couple of extra NAT and policy hops, which is why the same debugging order — resolve, connect, handshake, request — works there too.

RetainQuick revision

curl https://example.com touches every layer in order. The process starts and parses the URL; DNS resolves the name to an IP via nsswitch/hosts/resolv.conf over UDP 53; curl opens a TCP socket; the kernel makes a routing decision (next hop = gateway) and ARPs for its MAC; the TCP three-way handshake establishes the connection; a TLS 1.3 handshake exchanges keys and validates the certificate; ALPN picks HTTP/2; curl sends the request and reads the response inside encrypted records; the socket is closed with FIN/ACK and sits in TIME_WAIT. DNS, TCP, and TLS are three sequential round trips before the request. You see the syscalls with strace, the packets with tcpdump, the labelled stages with curl -v, and the latency per stage with curl -w. Because the stages are strictly ordered, you localise any failure by walking them and stopping at the first that breaks.

The 10 things to remember

  1. The order is fixed: process → DNS → socket → route → ARP → TCP → TLS → HTTP → teardown.
  2. DNS is a side-trip to a different server (UDP 53) and must finish before any SYN goes out.
  3. The routing decision picks the next hop; ARP resolves the gateway's MAC, not the server's.
  4. DNS, TCP, and TLS are three round trips of setup — the reason keep-alive, pooling, and CDNs exist.
  5. strace shows syscalls, tcpdump shows packets, curl -v shows labelled stages, curl -w shows per-stage timing.
  6. Failures stop at a stage: DNS (exit 6), connect timeout (28), refused (7), TLS (60) — the exit code names the layer.
  7. "Refused" (instant RST) and "timeout" (silent drop) feel the same to users but are opposite problems.
  8. Read curl -w as gaps: dns, connect−dns, tls−connect, ttfb−tls attribute the milliseconds.
  9. A slow ttfb with fast setup is the server's problem, not the network's.
  10. A service-to-service call in Kubernetes is this exact trace with extra NAT, policy, and mTLS hops.
