Part II · Networking from First Principles · Chapter 20

The network troubleshooting toolkit

At 3 a.m. nobody has time to "explore." You need to know, cold, which one command answers the question in front of you — and how to tell a refused connection from a timeout from a reset. This chapter turns ten tools into reflexes and a decision tree.

Start: Beginner→→→End: Staff-level ~45 min read · Linux lab (Docker)

By the end of this chapter you can

  • Map each tool — ip, ss, dig, ping, traceroute, mtr, nc, curl, tcpdump, conntrack — to the one question it answers.
  • Tell "connection refused" from "timeout" from "reset" from "DNS failure" instantly, and know what each implies.
  • Bisect any network problem by layer instead of guessing, using a repeatable decision tree.
  • Read a tcpdump capture and a ss state table well enough to name the fault.
  • Debug under pressure without making the incident worse.

Why this exists · the problemThe problem: "the network is broken" is not a diagnosis

A ticket says "app can't reach the database." That sentence spans seven layers and a dozen possible faults: a bad DNS record, a wrong route, a missing security-group rule, a crashed service, a full conntrack table, an expired cert. If you start poking at random you'll waste the first twenty minutes — the expensive minutes — on the wrong layer. The previous chapter showed that a request is a strict sequence of stages; this chapter gives you the instruments to check each stage and a tree that tells you which to check first.

The core skill isn't knowing many tools — it's knowing which single tool answers the exact question you have right now, so you can confirm or eliminate a layer in one command and move on. A senior SRE debugging a network problem looks slow and calm because they're not searching; they're running a decision tree they've internalised. That tree is the deliverable of this chapter.

Key point

Every tool here answers one question. dig: does the name resolve, and to what? ping: is the host reachable at L3? ss: what's listening and what state are connections in? nc: is that port open? tcpdump: what's actually on the wire? Learn the question, not just the flags, and the right tool picks itself.

Mental model · analogyThe mental model: a doctor's instruments

Real-world analogy

A good doctor doesn't run every test on every patient. They work from symptom to instrument: fever? thermometer. Chest complaint? stethoscope, then maybe an X-ray. Each instrument answers one narrow question, and they're ordered from cheap-and-broad to expensive-and-specific. You don't start with an MRI.

Network debugging is the same triage. The symptom ("can't connect") points you to the first cheap instrument (dig, then nc), and only if those don't localise it do you reach for the expensive, detailed one (tcpdump, the packet-level MRI that shows everything but takes time to read). The mistake juniors make is starting with tcpdump on everything — like ordering a full-body scan for a headache. Start broad, narrow down, and let each answer tell you which instrument to pick up next.

ArchitectureThe decision tree

Here's the tree. A failed or slow request enters at the top; each diamond is one cheap command; each leaf is a class of fault with the tool that confirms it. Memorise the shape — under pressure you walk it top to bottom.

Why an SRE cares

The three red boxes — refused, timeout, reset — feel identical to a user ("it doesn't work") and are three completely different root causes. Refused means something answered and said "no" (nothing on that port). Timeout means nothing answered at all (a drop). Reset means it worked and then something killed it mid-flight. Confusing them sends you to the wrong team. Getting them right in the first minute is the difference between a 10-minute incident and a 2-hour one.

Internal workingThe bisection method, and what each signal means

The method is layer bisection: check the middle-cheap things first, and let each result cut the search space in half. Here's the disciplined order for "can't reach X."

  1. Resolve it. dig X. If it returns NXDOMAIN, the name doesn't exist (typo, wrong domain, record deleted). SERVFAIL means the resolver tried and failed (broken delegation, DNSSEC problem). A hang means the resolver itself is unreachable. If DNS is wrong, stop — nothing downstream matters.
  2. Reach the host. ping X tells you L3 reachability, but treat a failed ping carefully: many hosts and clouds block ICMP, so "ping fails" is not "host down." It's a hint, not a verdict.
  3. Reach the port. nc -vz X PORT. This is the decisive one, and its manner of failing is the diagnosis. Succeeded → L4 is fine, move to L7. Connection refused (instant) → the SYN reached a live host that returned a RST because nothing listens on that port. Timed out (hangs) → the SYN got no answer at all: a firewall/security-group drop, a black-holed route, or a dead host.
  4. If refused, look at the server. The service isn't listening where you think. ss -tlnp on the server shows exactly what's bound to which port and which process owns it. Often it's bound to 127.0.0.1 instead of 0.0.0.0, so it works locally and refuses from outside.
  5. If timed out, find where it dies. mtr X (or traceroute) shows per-hop loss over time; the hop where replies stop is where the drop is — often the last hop before the destination (its firewall) or a specific segment losing packets.
  6. If it connects but the app fails, go to L7. curl -v shows how far the request got and whether it's a TLS problem or an HTTP status; curl -w attributes the latency (Chapter 19). A 4xx/5xx is the app's problem, not the network's.
  7. When nothing adds up, watch the wire. tcpdump is the ground truth: it shows whether packets actually leave, arrive, and with what flags. If curl says "timeout" but tcpdump shows a SYN leaving and a RST coming back, curl was lying to you about "timeout" — it was refused. tcpdump settles every argument.
Refused vs timeout vs reset — the one distinction to never get wrong

Refused = a RST came back immediately. A host is up; nothing is listening on that port (or a firewall is actively rejecting). Timeout = silence. The packet was dropped on the floor — firewall DROP, wrong route, or host truly down. Reset mid-stream = the connection established and moved data, then a RST arrived — the app crashed, was OOM-killed, or a load balancer/idle-timeout tore down a connection it considered stale. Same three letters to a user; three different on-call responses.

Think first: curl to a service hangs for 30 seconds then fails, but the same service answers when you curl localhost on the box it runs on. What's your first command and why?

The hang (not an instant refuse) says the SYN is getting no reply from outside, yet it works locally — so the process is up and listening, but not reachable from where you are. My first command is ss -tlnp on the server: I bet it's bound to 127.0.0.1 (or a specific interface) instead of 0.0.0.0, so it accepts local connections and silently ignores remote ones. If ss shows 0.0.0.0:PORT, then it's a firewall/security-group drop between us and I switch to mtr/tcpdump to find where the SYN dies. The "works locally, hangs remotely" pattern is almost always a bind address or a firewall — and ss distinguishes them in one line.

ComponentsThe tools, grouped by layer

  • Addressing & routing (L2/L3): ip addr (interfaces/IPs), ip route get (which route a packet takes), ip neigh (the ARP cache). The ip command replaced the deprecated ifconfig/route/arp — use ip.
  • Reachability (L3): ping (is it up at L3, and round-trip time), traceroute (the hop-by-hop path), mtr (traceroute + ping continuously, the best tool for intermittent loss because it shows loss per hop over time).
  • Ports & connections (L4): ss (sockets: what's listening, connection states, replaces netstat), nc (open a raw TCP/UDP connection to test a port), conntrack (the kernel's connection table and its counters, from Chapter 18).
  • Names (DNS): dig (query any record from any server, see the full answer and timing — far more precise than nslookup).
  • Application (L7): curl (make the real request, see every stage with -v, time each stage with -w).
  • Ground truth (all layers): tcpdump (capture and decode actual packets; the final arbiter when tools disagree).

Data flowWalking one symptom through the tree

Symptom: "the checkout service can't reach payments." I run dig payments.internal — it returns an IP, so DNS is fine, cut that branch. nc -vz payments.internal 8443 — it hangs and times out, not an instant refuse, so the SYN is being dropped, not rejected. That rules out "service crashed" (which would refuse) and points at a firewall or policy. mtr payments.internal shows loss starting at the last hop, consistent with the destination's firewall dropping us. I check the security group / NetworkPolicy for port 8443 from the checkout subnet — and there's the missing rule. Total time: three commands, because each answer eliminated a layer instead of me guessing. That's the whole method.

Hands-onLabs — build, understand, break, troubleshoot

Everything runs in one container; give it the capture capabilities:

bash
docker run --rm -it --cap-add=NET_ADMIN --cap-add=NET_RAW ubuntu:24.04 bash
apt-get update && apt-get install -y iproute2 dnsutils netcat-openbsd tcpdump curl mtr-tiny iputils-ping conntrack
Lab 1Build — see what's listening and what's connectedBuild

Start a listener, then use ss to answer the two questions it's for: what's bound, and what states are connections in.

bash
python3 -m http.server 8080 --bind 127.0.0.1 &
ss -tlnp                        # t=tcp l=listening n=numeric p=process
curl -s http://127.0.0.1:8080 -o /dev/null
ss -tan | head                  # a=all: see the connection states
OutputState Recv-Q Send-Q Local Address:Port Peer Address:Port Process LISTEN 0 5 127.0.0.1:8080 0.0.0.0:* users:(("python3",pid=9,fd=3)) State Recv-Q Send-Q Local Address:Port Peer Address:Port LISTEN 0 5 127.0.0.1:8080 0.0.0.0:* TIME-WAIT 0 0 127.0.0.1:8080 127.0.0.1:43402

Two lessons in one output. The LISTEN line shows the server is bound to 127.0.0.1 — local only, the exact misconfiguration that makes a service refuse remote connections. And the TIME-WAIT after the curl is the closing side holding the socket briefly (Chapter 14); thousands of these is a sign of connection churn. ss answers "what's listening?" and "what state are connections in?" — nothing else does both this fast.

Lab 2Understand — refused vs timeout, felt directlyUnderstand

Use nc to hit an open port and a closed one, and feel the difference the whole tree hinges on.

bash
nc -vz 127.0.0.1 8080     # open — something is listening
nc -vz 127.0.0.1 9090     # closed — nothing listening here
OutputConnection to 127.0.0.1 8080 port [tcp/http-alt] succeeded! nc: connect to 127.0.0.1 port 9090 (tcp) failed: Connection refused

The closed port returns Connection refused instantly — a RST, because the host is up and simply has nothing on 9090. Now contrast a timeout: a firewalled or non-existent host doesn't send a RST, it sends nothing, so nc hangs until it gives up:

bash
nc -vz -w3 10.255.255.1 9090   # unroutable/black-holed — hangs ~3s then times out
Outputnc: connect to 10.255.255.1 port 9090 (tcp) timed out: Operation now in progress

Refused = instant RST from a live host (wrong port, crashed service). Timeout = silence (firewall/route/host). This one sensory difference — instant error vs. hang — is the single most useful reflex in network debugging.

Lab 3Understand — read a capture, and query DNS preciselyUnderstand

tcpdump is ground truth. Capture your own loopback traffic while curling, and learn to read the flags:

bash
tcpdump -n -i lo port 8080 &
curl -s http://127.0.0.1:8080 -o /dev/null; sleep 1; kill %2 2>/dev/null
Output (representative)IP 127.0.0.1.43410 > 127.0.0.1.8080: Flags [S], seq 12345 # SYN IP 127.0.0.1.8080 > 127.0.0.1.43410: Flags [S.], seq 99, ack 12346 # SYN,ACK IP 127.0.0.1.43410 > 127.0.0.1.8080: Flags [.], ack 100 # ACK IP 127.0.0.1.43410 > 127.0.0.1.8080: Flags [P.], length 78 # the GET IP 127.0.0.1.8080 > 127.0.0.1.43410: Flags [F.], ... # FIN

[S]=SYN, [S.]=SYN-ACK, [.]=bare ACK, [P.]=data (push), [F.]=FIN, [R]=RST. Seeing a [R] where you expected [S.] is a refused connection on the wire. Now dig, which answers DNS questions precisely — note you can ask a specific server with @:

bash
dig +short example.com A            # just the answer
dig @1.1.1.1 example.com            # ask a specific resolver, see the full response
dig +trace example.com              # follow the delegation from the root down
Output (representative — dig example.com);; ANSWER SECTION: example.com. 6 IN A 104.20.23.154 ;; Query time: 12 msec ;; SERVER: 127.0.0.53#53(127.0.0.53) ;; status: NOERROR

Read the status line: NOERROR with an answer is healthy; NXDOMAIN means the name doesn't exist; SERVFAIL means the resolver failed. The SERVER line tells you which resolver answered — vital when you suspect one bad resolver in a pool. dig is far more precise than nslookup; use it.

Lab 4Break — a symptom, and you pick the toolBreak

Here's a scenario. A teammate says: "our app logs connection refused talking to the cache at cache.svc:6379, but the cache pods are Running and healthy." You have shell on the app pod. Before revealing, decide: what do you run, in what order, and what does each result mean?

Reveal — the sequence and the reasoning

"Refused," not "timeout," is the biggest clue — a RST came back, so a host is reachable and up; it's the port that's wrong, not the network. So I skip DNS-hang and firewall theories for a moment and check what's actually listening.

bash
dig +short cache.svc                 # 1. does the name point where I expect?
nc -vz cache.svc 6379                # 2. confirm: instant refuse or hang?
# If DNS returns a Service IP and nc refuses instantly, the pods aren't
# actually serving 6379 where the Service sends traffic. Check endpoints:
ss -tlnp | grep 6379                 # on a cache pod: is redis bound to 0.0.0.0:6379?

The usual answer: the cache is bound to 127.0.0.1:6379 inside its own pod, or listening on a different port than the Service targets, so the connection reaches the pod and gets refused because nothing listens on that address/port from outside. "Running and healthy" only means the process is up — not that it's listening where clients connect. ss on the target settles it. If instead nc had timed out, I'd pivot entirely to NetworkPolicy/security-group and mtr. The manner of failure chose the whole investigation.

Lab 5Production challenge — intermittent packet loss under pressureSenior challenge

The hardest network problems are intermittent — 2% of requests time out, no pattern, and it comes and goes. A single ping or traceroute "looks fine" because the loss is rare. How do you catch a fault that only shows up 2% of the time, and prove where it is?

Reveal an approach

mtr is built for exactly this — it runs traceroute continuously and shows loss percentage per hop over hundreds of probes, so a 2% drop becomes visible where a one-shot traceroute misses it:

bash
mtr -rwc 500 payments.internal   # report mode, wide, 500 cycles
Output (representative)HOST: app-pod Loss% Snt Last Avg Best Wrst 1. gateway 0.0% 500 0.4 0.5 0.3 1.1 2. spine-sw-3 0.0% 500 0.8 0.9 0.6 2.0 3. edge-fw 2.2% 500 1.1 1.3 0.9 9.8 # loss starts here 4. payments.internal 2.2% 500 1.2 1.4 1.0 10.1

Loss that starts at a hop and continues to the destination points at that hop (here edge-fw) or its uplink. One caveat that trips people up: loss shown at a middle hop but not at the destination is usually harmless — routers de-prioritise replying to the traceroute probes themselves (ICMP TTL-exceeded), so they under-report. Only loss that persists to the final hop is real. To corroborate, run tcpdump at both ends simultaneously and diff: packets that leave the sender but never arrive prove drops in between. For the conntrack angle from Chapter 18, check conntrack -S for rising drop/insert_failed counters — a full table causes exactly this "random 2% loss under load." The senior move is choosing the tool that accumulates evidence (mtr over 500 probes, conntrack counters) rather than the one-shot tool that hides rare faults.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · refused

Symptom: instant "connection refused." First cut: nc -vz host port confirms the instant RST. Confirm: ss -tlnp on the target — nothing bound there, or bound to 127.0.0.1. Cause is usually: service not started, crashed, wrong port, or listening on localhost only. It is not a firewall — a firewall drops, it doesn't refuse.

Incident pattern · timeout

Symptom: connection hangs, then times out. First cut: nc -vz -w3 confirms silence. Confirm: mtr/traceroute to see where packets die; tcpdump to see SYNs leave with no reply. Cause is usually: a firewall/security-group/NetworkPolicy dropping the packet, a bad route, or a host that's genuinely down. This is the one people mis-file as "server down" when it's a policy.

Incident pattern · reset mid-stream

Symptom: requests succeed sometimes, or succeed then die partway with "connection reset by peer." First cut: tcpdump to catch the [R] and see who sent it. Confirm: correlate the RST timing with server logs. Cause is usually: the server crashed/OOM'd mid-request, a load balancer's idle timeout closed a pooled connection the client thought was alive, or a keep-alive mismatch — the client reuses a connection the server already closed.

Incident pattern · DNS

Symptom: "name or service not known," or intermittent slowness on first request. First cut: dig NAME and read the status. Confirm: NXDOMAIN (record gone/typo), SERVFAIL (broken delegation/DNSSEC), or a hang (resolver unreachable); compare against @a known-good resolver. Cause is usually: a deleted or mis-propagated record, one unhealthy resolver in the pool, or a too-low TTL hammering a slow resolver.

Production · security · performanceWhat matters in production

Debug without making it worse. tcpdump on a busy host can itself add load and, unfiltered, can fill a disk fast — always scope it with a filter (host X and port Y), a packet count (-c 1000), or a size-limited ring buffer (-C 100 -W 5), and prefer writing to a file (-w) over decoding live. Capturing packets means capturing data, so treat captures as sensitive — they can contain tokens, PII, and anything not encrypted; store and share them carefully, and prefer capturing metadata over payloads.

Know what needs privilege. Raw packet capture and most ip mutations need CAP_NET_RAW/CAP_NET_ADMIN; read-only tools like ss, dig, and ip … show mostly don't. In a locked-down container you may have curl and ss but not tcpdump — plan your triage around what's actually installed, and bake a minimal toolkit (ss, dig, curl, nc) into your debug images. A distroless production image may have none of these, which is why ephemeral debug containers exist (Chapter 40).

Common mistakes: concluding "host down" from a failed ping when ICMP is simply blocked; starting with tcpdump before the cheap tools have narrowed the layer; using deprecated ifconfig/netstat/nslookup and getting subtly different or incomplete output; and — the classic — not distinguishing refused from timeout, so the whole investigation goes to the wrong layer.

System-design connectionWhere this reaches into architecture

These same questions, asked continuously instead of during an incident, become observability. A blackbox probe that runs curl against your endpoints every 30 seconds and records the per-stage timing is Lab 5 of Chapter 19 turned into a monitor — that's the Prometheus blackbox exporter (Chapter 77). Synthetic checks that do a DNS lookup, a TCP connect, and a TLS handshake from multiple locations are these tools on a schedule, alerting when a stage regresses before users notice. When you design a service's health model, you're deciding which of these signals to watch and where to run them from. And the whole layered-bisection discipline is the network-specific case of the universal troubleshooting framework in Chapter 103: form a hypothesis, run the one command that confirms or kills it, repeat.

InterviewInterview questions & answers

Answer each in your head first.

30-secWhat's the difference between "connection refused" and "connection timed out"?

Refused is instant: the SYN reached a live host and got a RST back because nothing is listening on that port — so the service is down, on the wrong port, or bound to localhost. Timed out is silence: the SYN got no reply at all, so the packet was dropped — a firewall or security group, a bad route, or a genuinely dead host. Refused means something said "no"; timeout means nothing answered. They feel the same to a user and point at completely different causes, so distinguishing them is the first thing I do.

2-minGive me your process for "app can't reach the database."

I bisect by layer, cheap tools first. Resolve the name with dig — if it's NXDOMAIN or the wrong IP, that's it. Then test the port with nc -vz host 5432, and the manner of failure drives everything: if it connects, L4 is fine and I go to the app; if it refuses instantly, the DB isn't listening where I'm connecting, so I check ss -tlnp on the DB host for the bind address and port; if it times out, the packet is being dropped, so I check the firewall/security-group/NetworkPolicy and use mtr to see where the path dies. If it connects but the app still fails, I use curl or the DB client with verbose output to see the L7 error, which might be auth or TLS, not networking. If tools disagree, tcpdump on both ends is ground truth — it shows whether packets actually leave and arrive. The point is each command eliminates a layer, so I converge in three or four steps instead of guessing.

DeepPing to a server fails. Is the server down? How do you really tell?

No — a failed ping is a weak signal, because ICMP is frequently blocked by firewalls, security groups, and cloud networks while TCP still works fine. So "ping fails" is a hint, not a verdict. To actually tell whether the server is usable, I test the port I care about with nc -vz host port or curl — a successful TCP connect proves the host is up and reachable at L4 regardless of ICMP. If TCP also fails, then I escalate: mtr to see whether packets reach the host's network at all, and tcpdump to see whether my SYNs leave and whether anything comes back. I'd also flip it around — if the app is serving traffic to others, the "down" is really "unreachable from here," which points at a path or policy between us, not the server. Relying on ping alone is a classic way to declare the wrong thing broken.

Scenario2% of requests to a service intermittently time out. Everything "looks fine." Find it.

Intermittent, low-rate loss hides from one-shot tools, so I use ones that accumulate evidence. mtr -rwc 500 runs hundreds of probes and shows loss per hop over time; loss that starts at a hop and persists to the destination localises the bad segment — with the caveat that loss at a middle hop that doesn't reach the destination is usually just routers de-prioritising ICMP, so I only trust loss that continues to the final hop. I'd corroborate with simultaneous tcpdump at both ends and diff which packets left but never arrived. On a Linux node under load I'd also check conntrack -S for rising drops and compare nf_conntrack_count to max, because a full conntrack table produces exactly this random-2%-under-load symptom. And I'd look at whether the loss correlates with a specific backend, AZ, or the moments of highest connection churn. The theme is measuring over many samples, because the fault is rare by definition.

Follow-upWhen do you reach for tcpdump versus everything else?

Last, not first — after the cheap tools have narrowed the layer, or when tools disagree and I need ground truth. tcpdump shows exactly what's on the wire: whether packets leave, arrive, and with which flags, so it settles arguments like "curl says timeout but is it really being refused?" — if I see a RST come back, it was refused, and curl was summarising. But it's the expensive instrument: it needs privilege, adds load on a busy host, and captures potentially sensitive data, so I always scope it with a filter, a packet count or a ring buffer, and write to a file rather than decode live. I use it to confirm a hypothesis I already have — "I expect to see SYNs with no reply" — not to go fishing. Starting every investigation with an unfiltered tcpdump is the junior move; reaching for it precisely, third or fourth, is the senior one.

RetainQuick revision

Network debugging is layered bisection with the right instrument at each layer. Each tool answers one question: dig (does the name resolve, and from which server?), ping (is it up at L3 — but ICMP may be blocked), traceroute/mtr (where does the path lose packets, especially over time), nc (is the port open?), ss (what's listening and what state are connections in?), curl (does the real request work, and how fast per stage?), conntrack (what's tracked, is the table full?), and tcpdump (what's truly on the wire — the final arbiter). The distinctions that matter most: refused is an instant RST (nothing listening), timeout is silence (a drop), reset mid-stream is a live connection killed (crash/idle-timeout), and a DNS failure stops everything before it starts. Start with the cheap, broad tools; reach for tcpdump last; and never confuse refused with timeout.

The 10 things to remember

  1. Every tool answers one question — learn the question, and the tool picks itself.
  2. Bisect by layer: resolve (dig) → reach the port (nc) → app (curl); each answer cuts the search in half.
  3. Refused = instant RST = nothing listening / wrong port / bound to localhost — check ss -tlnp.
  4. Timeout = silence = a dropped packet = firewall / security group / bad route — check mtr, policy.
  5. Reset mid-stream = a live connection killed = crash, OOM, or LB idle timeout — check logs + tcpdump.
  6. A failed ping is a hint, not a verdict — ICMP is often blocked; test the real port instead.
  7. ss replaced netstat, ip replaced ifconfig/route/arp, dig beats nslookup — use the modern ones.
  8. mtr beats a one-shot traceroute for intermittent loss because it measures per hop over time.
  9. Read dig's status line: NOERROR, NXDOMAIN, SERVFAIL — and the SERVER line tells you which resolver answered.
  10. tcpdump is ground truth but expensive: reach for it last, always filtered, and treat captures as sensitive.
