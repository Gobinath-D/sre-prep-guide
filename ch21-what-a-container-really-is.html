Part III · Containers & Container Internals · Chapter 21

What a container really is

There is no such thing as a "container" in the Linux kernel. There's a process — an ordinary process — that has been given a private view of the system and a budget for its resources. Once you build one by hand from those parts, "it's just an isolated process sharing the host kernel" stops being a slogan and becomes something you can see.

Start: Beginner→→→End: Staff-level ~45 min read · unshare/cgroups lab (Docker)

By the end of this chapter you can

  • State precisely what a container is — and what it is not — in one sentence, and defend it.
  • Assemble a working container by hand from namespaces, cgroups, and pivot_root, with no Docker involved.
  • Explain the three ingredients: namespaces isolate the view, cgroups limit the resources, pivot_root changes the root filesystem.
  • Say exactly why a container is cheaper than a VM and, in the same breath, why it's a weaker security boundary.
  • Map every step of docker run onto the primitives you assembled yourself.

Why this exists · the problemThe problem: isolation without a second kernel

You want to pack many independent workloads onto one machine. Each should believe it has the box to itself — its own filesystem, its own process list, its own network, its own slice of CPU and memory — and one misbehaving workload shouldn't be able to see or starve the others. The old answer was a virtual machine: give each workload a whole simulated computer with its own kernel. That works, and the isolation is strong, but every VM carries a full operating system — gigabytes of image, a kernel to boot, a minute of startup, and RAM reserved just to exist. Run fifty of them and most of your machine is spent running fifty copies of Linux.

The insight behind containers is that you usually don't need a second kernel — you need the illusion of one. The host kernel is already perfectly good at keeping processes apart; it just needs to lie to each workload about what exists. So instead of booting a new kernel per workload, Linux lets a single kernel hand each process a private view (you see only your own processes, your own network, your own filesystem) and a private budget (you get this much CPU and memory, no more). A process wrapped that way looks and feels like it's alone on the machine, but it's just a normal process on the shared host kernel. That wrapped process is a container.

Key point — the one-sentence definition

A container is a normal Linux process (or process tree) that the kernel has given an isolated view of the system — via namespaces — and a capped share of resources — via cgroups — usually running on its own root filesystem set up with pivot_root. There is no "container" object in the kernel; there are only processes with these properties. Everything else — Docker, images, registries — is packaging and tooling around that fact.

Mental model · analogyThe mental model: suites in a shared building

Real-world analogy

Picture one office building with one set of shared utilities — power, water, HVAC, the structure itself. That's the host kernel: a single system everyone actually runs on. Now you partition the floor into tenant suites. Each suite has frosted-glass walls: from inside, a tenant sees only their own rooms, their own staff directory, their own mail slots — they have no idea the other suites exist. That partitioning of what you can see is namespaces. The building didn't get new plumbing; the tenants just can't see past their walls.

Each suite also has metered utilities: a cap on how much power and water it may draw, so one tenant running space heaters can't brown out the floor. That's cgroups — a limit on how much you may consume. And each suite has its own front door and furniture — its own entryway and layout, independent of the others. That's pivot_root: its own root filesystem, the container image.

The contrast that matters: a virtual machine is not a suite — it's a separate building with its own power plant, its own boiler, its own everything. Far more isolated (a fire in one building can't cross to another), and far more expensive (you're paying to run a whole second set of utilities). A container shares the utilities and just partitions the space. That single difference — shared kernel vs. own kernel — explains every trade-off in this chapter.

ArchitectureProcess vs container vs VM — same kernel or not

This one picture is the whole chapter. On the left, a host: ordinary processes and a container, all sharing one kernel. On the right, a VM for contrast, carrying its own kernel. Notice the container process reaches the same kernel the host processes do — it's just walled off from seeing its neighbours.

Why an SRE cares

"Shares the host kernel" is not trivia — it's the fact that drives density, startup speed, and your entire threat model. Containers start in milliseconds and pack hundreds per node because there's no kernel to boot and no OS to run per workload. But the flip side is equally concrete: a kernel bug is a bug in the boundary itself, so a single kernel CVE (Dirty COW, Dirty Pipe) can let a container read or write outside its walls, something a VM's separate kernel would contain. This is why "a container is not a security boundary the way a VM is" is a sentence you'll repeat in design reviews for the rest of your career.

Internal workingAssembling a container by hand

There's no create_container() syscall. A runtime builds a container by combining three independent kernel features. Here's the recipe, which is exactly what the labs run:

  1. Isolate the view with namespaces. The unshare() / clone() syscalls create new namespaces and put the process into them. A new PID namespace makes the process believe it's PID 1 and hides all other processes. A new mount namespace gives it a private set of mounts. A new network namespace gives it its own interfaces (the veth-and-bridge of Chapter 18). A new UTS namespace lets it set its own hostname. Each is independent — you pick which walls to build.
  2. Give it its own root filesystem with pivot_root. Inside the mount namespace, the runtime makes the container's image directory the new / using pivot_root (a safer successor to chroot), so the process sees the image's files as the whole filesystem and can't reach the host's. Then it mounts a fresh /proc so tools see only the container's processes.
  3. Cap the resources with cgroups v2. The runtime creates a cgroup, writes limits into it (memory.max, cpu.max, pids.max), and moves the process into it by writing its PID to cgroup.procs. Now the kernel enforces the budget: exceed memory.max and the process is OOM-killed inside its cgroup, without touching the rest of the host.
  4. Drop privilege with capabilities and seccomp. A well-built runtime also strips Linux capabilities down to a minimal set and installs a seccomp filter that blocks dangerous syscalls — the security tightening of the shared-kernel boundary from Chapter 1.
  5. Exec the workload. Finally the runtime execve()s your actual program (nginx, your app). It's now PID 1 inside its namespaces, rooted at its image, capped by its cgroup — a container. Nothing more happened than these ordinary syscalls in sequence.
The pieces are independent — that's the whole design

Namespaces, cgroups, and pivot_root are orthogonal. You can use a namespace without a cgroup, a cgroup without a namespace, a new hostname without a new network. A "container" is just a convention for combining them a certain way. That's why you can have a network namespace with no resource limits (a bare ip netns), or a cgroup limiting a normal host service with no isolation at all (that's what systemd does to every service). Understanding them as separate Lego bricks is what lets you debug and reason about the combined thing.

Think first: inside a container, ps aux shows only a handful of processes and your app is PID 1. Where did the host's hundreds of processes go?

Nowhere — they're all still running on the same kernel; you just can't see them. The container is in its own PID namespace, which renumbers processes starting from 1 and hides everything outside it. From the host you can see the exact same container process with its real, host-side PID (say 24601). Two names for one process: PID 1 in the container's namespace, PID 24601 in the host's. Nothing was hidden from the kernel; only the view was partitioned. That's the entire trick of namespaces, and it's why nsenter from the host can step into a container's view, and why a host-level tool sees every container's processes at once.

ComponentsThe pieces, named

  • Namespaces (8 kinds). mount (filesystems), PID (process IDs), network (interfaces, routes), UTS (hostname), IPC (shared memory, queues), user (UID/GID mapping — lets an unprivileged host user be root inside), cgroup (the cgroup tree view), and time (clocks, newest). Each covered in depth in Chapter 22.
  • cgroups v2. The unified control-group hierarchy that limits and accounts CPU, memory, IO, and PID count. The controllers are enabled per subtree; limits are just files you write. Deep dive in Chapter 23.
  • The root filesystem (image). The files the container sees as /. In practice built from stacked, read-only image layers with a writable top layer via overlayfs — Chapter 24. pivot_root switches the process onto it.
  • The runtime. The program that actually calls the syscalls above. The low-level one is runc, which reads an OCI spec and does the clone/pivot_root/cgroup/exec dance — Chapter 26. Docker and containerd sit above it.
  • Capabilities & seccomp. The privilege controls that make the shared kernel survivable — dropping root's powers to a minimum and filtering syscalls. Security in Chapter 27.

Data flowWhat docker run actually does

When you type docker run nginx, the Docker daemon asks containerd to start a container; containerd unpacks the image layers into an overlayfs rootfs and calls runc; runc reads the OCI runtime spec and does precisely the by-hand steps above — clone() with new namespace flags, pivot_root onto the overlay rootfs, mount a fresh /proc, create a cgroup and write the limits from your --memory/--cpus flags, apply the default seccomp profile and drop capabilities, then execve("nginx"). Everything you'll do by hand in the labs, runc does programmatically from a JSON spec. There is no extra magic — docker run is a friendly front-end over the same five syscalls.

Hands-onLabs — build, understand, break, troubleshoot

You need a Linux host with privileges to create namespaces and cgroups. A privileged container gives you that safely on your laptop:

bash
docker run --rm -it --privileged ubuntu:24.04 bash
apt-get update && apt-get install -y util-linux iproute2 cgroup-tools
Lab 1Build — create namespaces and see themBuild

unshare creates new namespaces and runs a shell in them. Build the isolating walls of a container — everything but the resource limits — in one command, then look at what you got.

bash
# --user lets us do this unprivileged; --fork+--pid gives a real new PID ns
unshare --user --map-root-user --mount --uts --ipc --pid --net --fork bash
# now inside the new namespaces:
hostname sandbox                 # UTS ns: set our own hostname
ls -l /proc/self/ns/             # the namespace inodes we now belong to
Outputipc -> ipc:[4026532368] mnt -> mnt:[4026532366] net -> net:[4026532370] pid -> pid:[4026532369] user -> user:[4026532365] uts -> uts:[4026532367]

Each line is a namespace this process now belongs to, identified by an inode number. High numbers like 4026532368 are freshly created ones — they differ from the host's. You just built the "frosted-glass walls" of a container. The --user + --map-root-user flags are what let an ordinary user do this: the user namespace maps your unprivileged host UID to root inside, so you're root in the sandbox but powerless outside it.

Lab 2Understand — PID isolation, felt directlyUnderstand

The PID namespace is the most vivid wall. Inside the shell from Lab 1, mount a fresh /proc and look at the process list.

bash
mount -t proc proc /proc      # show THIS namespace's processes, not the host's
echo "I am PID $$"
ps -e                          # how many processes can I see?
OutputI am PID 1 PID TTY TIME CMD 1 pts/0 00:00:00 bash 7 pts/0 00:00:00 ps

Your shell is PID 1 — the same number init/systemd has on a normal host — and ps sees a grand total of two processes. The host's hundreds are still running on the shared kernel; this namespace simply can't see them. From another shell on the host, ps aux | grep bash would show this exact process under its real host PID. One process, two identities. That is the whole idea of a container: not fewer processes, just a partitioned view.

Lab 3Understand — give it its own filesystem with pivot_rootUnderstand

A container's filesystem is just some directory that becomes /. Grab a real minimal rootfs by exporting one from an image, then pivot into it. (Run this part from the host container shell where Docker is available, or use any small rootfs tarball.)

bash
# Get a tiny real root filesystem (busybox/alpine userland) as a directory:
mkdir -p /tmp/rootfs
docker export $(docker create alpine:3.20) | tar -C /tmp/rootfs -xf -

# Now enter fresh namespaces and make that directory the new root:
unshare --user --map-root-user --mount --uts --ipc --pid --net --fork bash
mount --bind /tmp/rootfs /tmp/rootfs        # pivot_root needs a mount point
cd /tmp/rootfs && mkdir -p oldroot
pivot_root . oldroot                        # /tmp/rootfs becomes /
mount -t proc proc /proc
umount -l /oldroot                          # detach the host's old root — no way back
ls /                                        # the alpine rootfs, as the whole world
Outputbin dev etc home lib proc root sbin tmp usr var

That's an Alpine filesystem the process now sees as its entire / — it cannot reach the host's files at all, because after umount -l /oldroot the old root is gone from this mount namespace. Combine this with Labs 1–2 and you have a container's three defining properties: isolated view (namespaces), own hostname (UTS), and own filesystem (pivot_root). All that's missing is the resource cap.

Lab 4Break — cap the memory with a cgroup and watch it enforceBreak

Now the budget. cgroups v2 is a filesystem under /sys/fs/cgroup; you create a group, write a limit, and move a process in. Confirm you're on v2 and see the available controllers:

bash
stat -fc %T /sys/fs/cgroup                    # 'cgroup2fs' = v2
cat /sys/fs/cgroup/cgroup.controllers        # what can be limited
Outputcgroup2fs cpuset cpu io memory hugetlb pids rdma misc

Create a group capped at 50 MB, move the shell in, and try to allocate more. Predict what happens before you run it.

bash
mkdir /sys/fs/cgroup/demo
echo "+memory" > /sys/fs/cgroup/cgroup.subtree_control   # enable the controller
echo 50M > /sys/fs/cgroup/demo/memory.max
echo $$ > /sys/fs/cgroup/demo/cgroup.procs               # move THIS shell into the group
# allocate ~200MB and watch the kernel step in:
python3 -c 'x = bytearray(200*1024*1024)'
OutputKilled # dmesg shows: Memory cgroup out of memory: Killed process ... (python3)

The kernel OOM-killed the process the moment it crossed memory.max — but only this cgroup was affected; the rest of the host never noticed. That is exactly what docker run --memory=50m does under the hood. Why does this matter? Think about a node with no limits before opening the reveal.

Reveal — the noisy-neighbour problem this prevents

Without a memory cgroup, one container with a leak allocates until the host runs out of memory, and the kernel's global OOM killer then picks a victim — often the wrong one, taking down an innocent neighbour or a critical daemon. With per-container memory.max, the blast radius is that one container: it gets killed, restarts, and its neighbours are untouched. This is why Kubernetes requires (or strongly wants) memory limits on every pod, and why "the node went down because one pod leaked" is a story about missing cgroup limits. cgroups turn a shared machine from a free-for-all into metered tenancy — the next-chapter topic, and the foundation of pod resource requests/limits.

Lab 5Production challenge — prove it's the same as docker run, then reason about the shared kernelSenior challenge

You've built a container by hand. Now prove Docker does the same thing, and confront the consequence of the shared kernel.

bash
# Start a real container and inspect its namespaces + PID from the HOST:
docker run -d --name web --memory=64m nginx
PID=$(docker inspect -f '{{.State.Pid}}' web)
lsns -p $PID                       # the namespaces docker created — same kinds as our unshare
cat /proc/$PID/cgroup              # the cgroup docker put it in
readlink /proc/$PID/ns/uts         # a fresh UTS ns inode, just like Lab 1

You'll see nginx sitting in its own mount/PID/net/UTS/IPC namespaces and a cgroup with the 64 MB limit — the exact primitives you assembled. Docker added tooling, an image, and a network setup, but the kernel objects are identical. Now the senior question: given that all these containers share one kernel, what is the actual security posture, and when is a container not enough? Think before revealing.

Reveal — the shared-kernel security reality

Because every container calls into the same kernel, the kernel's syscall surface is the attack surface. A kernel vulnerability reachable from a container's syscalls (Dirty COW, Dirty Pipe, various namespace/overflow bugs) can let a process break its isolation and affect the host or other containers — the isolation is only as strong as the kernel is bug-free. This is why the container security model layers defences on top: drop capabilities to a minimum, apply a seccomp filter to shrink the reachable syscall set, run as a non-root user via user namespaces, and never run --privileged in production (it removes most of these protections). And when you truly need VM-grade isolation — hostile multi-tenant workloads, untrusted code — you reach for a sandbox that gives each container its own kernel or a thin hypervisor: gVisor or Kata Containers / Firecracker microVMs. The trade-off is the whole point of the chapter: containers buy density and speed by sharing the kernel, and you pay for that with a weaker boundary, so you harden it or, when the stakes are high enough, put a real kernel back between tenants. This sets up all of Chapter 27.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · the node dies because one container leaked

Symptom: a whole node goes unhealthy and unrelated workloads get OOM-killed. First cut: check whether the offending container had a memory.max (a Kubernetes memory limit). Confirm: no limit, so its leak consumed host memory and the global OOM killer fired on the host, hitting innocent processes. Cause: missing cgroup memory limit. The fix is per-workload limits so the blast radius is one container, not the node.

Incident pattern · PID 1 and zombie processes

Symptom: a container accumulates defunct (zombie) processes over days. First cut: what's PID 1 in the container? Confirm: the app is PID 1 but doesn't reap children, so orphaned processes never get cleaned up — PID 1 has special reaping duties that a normal app doesn't perform. Cause: running an app directly as PID 1 without an init. The fix is a tiny init (tini, or docker run --init) as PID 1 to reap zombies.

Incident pattern · "it works privileged, fails without"

Symptom: a container works with --privileged and fails otherwise with EPERM or "operation not permitted" on some syscall. First cut: which syscall/capability is being denied. Confirm: the default seccomp profile or dropped capabilities block it. Cause: the workload needs a specific capability (e.g. NET_ADMIN) — grant that one capability, never blanket --privileged, which disables the whole shared-kernel defence layer.

Production · security · performanceWhat matters in production

Density vs. isolation is the core trade. Containers win on density and startup because there's no per-workload kernel — that's why a node runs hundreds of pods and a container starts in milliseconds. You pay for it with a shared kernel, which means the isolation is software isolation enforced by one kernel, not hardware isolation between two. For most workloads that's the right trade; for hostile multi-tenant or untrusted code it isn't, and you add a VM-boundary sandbox (gVisor, Kata/Firecracker) to get a kernel back between tenants.

Harden the boundary you chose. Because the kernel is the boundary, production containers should run as non-root (user namespaces), drop all capabilities and add back only what's needed, keep the default seccomp profile, and never use --privileged. A container that's root with all capabilities and no seccomp is barely isolated at all — it's one kernel bug away from the host. These aren't optional extras; they're what makes the shared-kernel model safe enough to use.

Common mistakes: running without resource limits and being surprised when one workload takes the node; running the app as PID 1 with no init and collecting zombies; treating a container as equivalent to a VM for security and putting untrusted tenants on a shared kernel; and reaching for --privileged to fix a permission error instead of granting the one capability actually needed. Every one of these follows from not internalising "it's a process on a shared kernel."

System-design connectionWhere this reaches into architecture

The container is the unit everything above it is built from. Kubernetes schedules pods, but a pod is a set of containers sharing some namespaces (network and IPC) while keeping others separate — a direct consequence of namespaces being independent bricks, which is why a sidecar can share the pod's network but not its filesystem. The economics of the whole platform — how many pods per node, how fast you can scale out, how cheap a deploy is — come straight from the shared-kernel density this chapter explains. And the isolation ceiling shapes multi-tenancy architecture: a SaaS running its own code can pack tenants into shared-kernel containers, but one running customers' arbitrary code needs stronger isolation per tenant, which is why serverless platforms that run untrusted functions (AWS Lambda) sit each on a Firecracker microVM rather than a bare container. When you design a compute platform, you're choosing where on the density-vs-isolation line to sit — and that choice is exactly the container-vs-VM picture from this chapter, at scale (Chapter 56).

InterviewInterview questions & answers

Answer each in your head first.

30-secWhat is a container, really?

A container is an ordinary Linux process that the kernel has given an isolated view of the system through namespaces, a capped share of resources through cgroups, and usually its own root filesystem via pivot_root. There's no container object in the kernel — just a process with those properties on the shared host kernel. That's the difference from a VM: a VM runs its own kernel on a hypervisor, while a container reuses the host's kernel and only partitions what the process can see and use. That shared kernel is why containers are cheap and fast and also why they're a weaker security boundary.

2-minHow would you build a container by hand?

Three ingredients combined with plain syscalls. First, namespaces: I'd use unshare or clone to create new mount, PID, network, UTS, IPC, and user namespaces, which isolate the process's view — it sees itself as PID 1, gets its own hostname, its own network interfaces, and can't see host processes. Second, the filesystem: inside the mount namespace I'd pivot_root onto the image's directory so it becomes /, then mount a fresh /proc so tools see only this namespace's processes. Third, cgroups v2: create a cgroup, write limits like memory.max and cpu.max, and move the process in by writing its PID to cgroup.procs, so the kernel enforces the budget. I'd also drop capabilities and apply a seccomp profile to harden the shared-kernel boundary, then execve the actual workload. That sequence is exactly what runc does from an OCI spec — docker run is a front-end over these same steps.

DeepWhy is a container a weaker security boundary than a VM, concretely?

Because a container shares the host kernel, the boundary between a container and the host is the kernel's syscall interface, and that interface is huge and occasionally buggy. Every container makes syscalls into the same kernel, so a vulnerability reachable through those syscalls — Dirty COW, Dirty Pipe, namespace or eBPF bugs — can let a process escape its isolation and read or write outside its walls. A VM doesn't share the boundary this way: the guest talks to its own kernel, and only a much smaller, hardware-assisted hypervisor interface separates guests, so the same class of kernel bug is contained inside one guest. That's why we harden containers with least-privilege capabilities, seccomp, and user namespaces, and why for untrusted or hostile-multi-tenant workloads we put a real kernel back with gVisor or Kata/Firecracker. The concrete framing I'd give: a container is one kernel CVE away from a bad day; a VM makes the attacker defeat the hypervisor too.

ScenarioA container is OOM-killed repeatedly but the node has plenty of free memory. Why?

Because the kill is happening at the cgroup level, not the host level. The container has a memory.max (a Kubernetes memory limit), and when its own usage crosses that cap the kernel OOM-kills a process inside that cgroup regardless of how much memory the node has free — the limit is the container's private ceiling. So the fix isn't adding node memory; it's either raising the container's limit if the workload legitimately needs more, or fixing the workload's memory use if it's leaking or over-allocating. I'd confirm by reading the cgroup's memory.max and memory.current and checking dmesg for "Memory cgroup out of memory," which names the cgroup. It's a good illustration that cgroups enforce per-container budgets independent of host capacity — which is the entire point of them.

Follow-upWhat's the relationship between a container and a Kubernetes pod?

A pod is one or more containers that share some namespaces while keeping others separate — which only makes sense once you know namespaces are independent bricks. Specifically, the containers in a pod share a network namespace (so they reach each other on localhost and share one IP) and usually the IPC namespace, but keep their own mount and PID namespaces (their own filesystems and process views, in the common configuration). Kubernetes implements this with a "pause" container that holds the shared namespaces, and the app containers join them. So a pod isn't a new primitive — it's a specific way of composing the same namespaces and cgroups from this chapter, which is exactly why a sidecar can share the main container's network to proxy its traffic but can't see its files. Everything Kubernetes does with pods is namespaces and cgroups underneath.

RetainQuick revision

A container is an ordinary process on the shared host kernel, given an isolated view via namespaces, a resource budget via cgroups v2, and its own root filesystem via pivot_root — there is no container object in the kernel. You build one with plain syscalls: unshare/clone for namespaces (PID makes it think it's PID 1, mount/net/UTS give it its own filesystem/network/hostname), pivot_root onto the image, a cgroup with memory.max/cpu.max to cap it, and capabilities+seccomp to harden the boundary — which is exactly what runc does for docker run. Sharing the kernel is why containers are cheap, fast, and dense, and equally why they're a weaker security boundary than a VM: the kernel is the boundary, so a kernel bug can breach it. Harden with least privilege; for truly untrusted tenants, use a VM-grade sandbox. A pod is just a particular composition of these same namespaces.

The 10 things to remember

  1. A container is a process with namespaces + cgroups + its own rootfs — not a kernel object.
  2. Namespaces isolate the view; cgroups limit the resources; pivot_root sets the root filesystem. Independent bricks.
  3. There are 8 namespaces: mount, PID, network, UTS, IPC, user, cgroup, time.
  4. A container shares the host kernel — no second kernel — which is why it starts in milliseconds and packs densely.
  5. Same shared kernel = weaker isolation: a kernel CVE can breach the boundary a VM would contain.
  6. Inside a container the app is PID 1 and sees only its own processes; the host sees it under its real PID.
  7. cgroup memory.max OOM-kills inside the cgroup only — the fix for noisy-neighbour node deaths.
  8. docker run = containerd + runc doing clone/pivot_root/cgroup/seccomp/exec from an OCI spec.
  9. Harden the shared kernel: non-root (user ns), drop capabilities, keep seccomp, never --privileged in prod.
  10. For untrusted multi-tenant workloads, get a kernel back: gVisor or Kata/Firecracker microVMs.
