Part III · Containers & Container Internals · Chapter 22

Linux namespaces

A container has no walls. What makes the process inside it think it's alone on the machine — its own PID 1, its own hostname, its own network — is eight kernel features called namespaces. Learn to see them, and containers stop being magic.

Start: Beginner→→→End: Staff-level ~40 min read · Linux lab (Docker)

By the end of this chapter you can

  • Name all eight namespace types and say exactly what each one hides or isolates.
  • Read /proc/<pid>/ns/ and tell whether two processes share a namespace by comparing inode numbers.
  • Carve out your own PID, UTS, and network namespaces by hand with unshare, and enter a running container's with nsenter.
  • Answer "why can't the container see the host's processes?" from first principles, not hand-waving.
  • Explain user namespaces and why rootless containers make "root inside" mean "nobody outside".

Why this exists · the problemThe problem namespaces solve

You've got one Linux machine and you want to run ten programs on it that each believe they own the whole box. One wants to be PID 1 and manage its children. One wants to bind port 80. One wants the hostname web-01. Two of them ship the same library at different versions and both want it mounted at /usr/lib. On a plain machine they'd collide immediately: there's one process table, one port 80, one hostname, one filesystem tree.

The old fix was a whole virtual machine per program — its own kernel, its own everything. That works, but it's heavy: a full OS image, minutes to boot, hundreds of megabytes of RAM before your program runs a single line. Most of the time you don't need a second kernel. You need the illusion of a private machine while still sharing the one real kernel underneath. That illusion is what containers sell, and namespaces are what deliver it.

A namespace takes one global kernel resource — the process table, the network stack, the mount table, the hostname — and wraps it so that the processes inside see their own private copy. The man page says it plainly: a namespace makes a global resource "appear to the processes within the namespace that they have their own isolated instance." Change something inside, and processes elsewhere never see it. Eight resources can be virtualised this way, and a container is nothing more than a normal process that has been placed into a fresh set of them.

Key point

Namespaces don't limit how much a process can use — that's cgroups, the next chapter. Namespaces limit what a process can see. Two different jobs, always confused. Isolation of visibility (namespaces) and metering of resources (cgroups) together make a container; neither alone is enough.

Mental model · analogyThe mental model: private rooms in a shared building

Back to the office building from Chapter 1. The kernel still owns the back room with all the hardware. What's new is how the tenants experience the front offices.

Real-world analogy

Imagine a large open floor. Without namespaces, every tenant shares one address book, one phone directory, one supply closet, one wall clock — step on anyone's toes and they notice. Now the building manager installs one-way glass partitions. Each tenant gets a private suite. Inside your suite you have your own address book that starts at "extension 1" (you), your own supply closet arranged how you like, your own name on the door. You genuinely believe you're alone.

But there's still only one building. The plumbing, the power, the elevator — the manager (the kernel) runs all of it, once, for everyone. The partitions only control what each tenant sees. And the manager keeps a master key: from the hallway they can look straight into any suite. That master key is the difference that will bite you later — the host can always see into the container, even though the container can't see out.

Each kind of partition hides a different thing: one hides the phone directory, one hides the supply closet, one hides the name on the door. You can install any subset. Install all eight and the suite feels like its own building — that's a container.

ArchitectureOne process, eight namespaces

A process is not "in a container." A process is a member of exactly one namespace of each type. When all eight of those are fresh and private, we call the collection a container — but the kernel has no object called "container." It only knows processes and the namespaces they belong to. Membership is recorded per type, and you can mix: a process can share the host's network namespace while having a private mount namespace (that's what docker run --network=host does).

Here is each type, and precisely what it hides. The flag column is the CLONE_NEW* constant you pass to clone(2), unshare(2), or the unshare command.

  • PID (CLONE_NEWPID) — process IDs. The first process becomes PID 1 and reaps orphans. Processes in the namespace can't see or signal processes outside it. This is the one that answers "why can't the container see the host's processes."
  • Network (CLONE_NEWNET) — network devices, IPv4/IPv6 stacks, routing tables, firewall rules, port numbers, /proc/net. A fresh net namespace has only a loopback interface, and it starts down. Port 80 in one net namespace has nothing to do with port 80 in another.
  • Mount (CLONE_NEWNS) — the set of mount points, i.e. the filesystem tree. This is the oldest namespace (it predates the others, which is why its flag is the odd-one-out NEWNS and not NEWMNT). It's how a container gets its own root filesystem.
  • UTS (CLONE_NEWUTS) — the hostname and NIS domain name. "UTS" is UNIX Time-sharing System, a historical name; it's just the two strings uname() returns.
  • IPC (CLONE_NEWIPC) — System V IPC objects (shared memory, semaphores, message queues) and POSIX message queues. Two containers can each hold a shared-memory segment with the same key and never touch each other's.
  • User (CLONE_NEWUSER) — user and group IDs, and the capability sets. This is the powerful and dangerous one: it lets a process be root (UID 0) inside the namespace while being an ordinary unprivileged UID outside. Since Linux 3.8 it's the only namespace an unprivileged user can create without CAP_SYS_ADMIN.
  • Cgroup (CLONE_NEWCGROUP, since Linux 4.6) — the cgroup root directory the process sees. It stops a container from reading the host's full cgroup path and hierarchy; inside, its own cgroup looks like the root.
  • Time (CLONE_NEWTIME, since Linux 5.6) — offsets for the CLOCK_MONOTONIC and CLOCK_BOOTTIME clocks. Note the limit: it does not virtualise CLOCK_REALTIME (the wall clock). It exists mainly so a checkpointed/restored or migrated container can keep a consistent uptime.
Why an SRE cares

When you kubectl exec into a pod and run ps, you see two processes, not the node's four hundred. That's the PID namespace. When two pods both listen on :8080 on the same node without colliding, that's the network namespace. When a pod's /etc/hostname says the pod name, that's UTS. Every "how is it isolated?" question about a container decomposes into "which namespace is doing that?" — and every isolation gap ("the container could see the host's X") is a namespace that wasn't applied.

Internal workingHow a process gets its namespaces

There are three system calls in the whole namespace API, and the man page for namespaces(7) lists exactly these. Everything docker, runc, and Kubernetes do reduces to them.

  1. clone(2) creates a new process already inside new namespaces. If you pass CLONE_NEWPID | CLONE_NEWNET | … in the flags, the child is born into fresh namespaces of each type named. This is how a runtime starts a container: fork a child straight into the isolated set. The child's first process becomes PID 1 of its new PID namespace.
  2. unshare(2) moves the caller into new namespaces. Same flags, but instead of creating a new process it detaches the current one from its shared namespaces and gives it private ones. The unshare command-line tool wraps this — it's how you'll experiment by hand in the labs.
  3. setns(2) joins an existing namespace. You open a file under /proc/<pid>/ns/ to get a handle to some process's namespace, then call setns() to enter it. The nsenter command wraps this — it's how you drop into a running container to debug it.
  4. The kernel records membership and enforces visibility. Once a process is in, say, a PID namespace, every syscall that lists or names processes is answered relative to that namespace. getpid() returns the in-namespace PID; kill() can only reach PIDs the namespace knows. The kernel does the translation; the process never learns its "real" host PID.
  5. Creating a namespace needs CAP_SYS_ADMIN — except the user namespace. This is the security hinge. You can't just carve out a new network namespace as a nobody. But you can create a user namespace unprivileged, and inside it you hold a full set of capabilities — which then lets you create the other namespaces. That chain is the entire basis of rootless containers.

Namespaces are exposed as files. Each process has /proc/<pid>/ns/ holding one symlink per type. The symlink's target looks like net:[4026531969] — the type and an inode number. That inode number is the namespace's identity. Two processes are in the same network namespace if, and only if, their net symlinks point to the same inode. That's the whole trick behind lsns and behind the labs below.

Think first: a namespace normally disappears when its last process exits. How could you keep an empty network namespace alive with no process in it?

Pin it with a file descriptor or a bind mount. As namespaces(7) spells out, opening one of the /proc/<pid>/ns/* files — or bind-mounting it somewhere like /run/netns/foo — keeps the namespace alive even after every process in it terminates, because the open handle counts as a reference. That's exactly the mechanism ip netns add uses: it creates a net namespace and bind-mounts it under /run/netns/ so you can configure it before any process joins. It's also how you can leak namespaces: a forgotten bind mount pins a namespace (and its interfaces, its memory) forever.

ComponentsThe tools that name the pieces

Four tools show up constantly, and you should know which syscall each is a front-end for:

  • unshare (util-linux) — front-end for unshare(2). unshare --pid --net --mount-proc bash gives that shell fresh PID and network namespaces. This is your "build a container by hand" tool.
  • nsenter (util-linux) — front-end for setns(2). nsenter -t <pid> -n -p enters the network and PID namespaces of process <pid>. This is your "get inside a running container from the node" tool, and it works even when the container image has no shell or no tools of its own.
  • lsns (util-linux) — lists namespaces on the system, grouped by type, with the owning PID and inode. When you're staring at a node asking "how many net namespaces exist and who owns them," this is the answer.
  • /proc/<pid>/ns/ — the kernel's own record. Not a tool, but the source of truth lsns reads. readlink /proc/$$/ns/net tells you your shell's network-namespace inode directly.

The runtime you actually use in production — runc under containerd under the kubelet, all covered in Chapter 26 — is just a careful, correct sequencer of clone/unshare/setns plus the cgroup and mount setup. Nothing it does is off-limits to you at the shell; it's only doing it in the right order with the right error handling.

Data flowFollowing one docker run

Watch the namespaces come into being when you start a container. docker run -d --name web nginx triggers, roughly, this sequence. The runtime calls clone() with the CLONE_NEW* flags for every namespace type. The child is now alone: PID 1 in its PID namespace, a bare loopback in its net namespace, an empty mount table. The runtime then furnishes the empty rooms — it mounts the image's root filesystem into the mount namespace (that's Chapter 24), creates a veth pair and moves one end into the net namespace and configures an address (that's Chapter 25), sets the hostname in the UTS namespace, and places the process in a cgroup for limits (that's Chapter 23). Finally it execs nginx. From nginx's point of view it booted onto a fresh little machine. From the host's point of view it's PID 4242 with eight interesting symlinks under /proc/4242/ns/. Both views are true at once. The labs make every step of this visible.

Hands-onLabs — build, understand, break, troubleshoot

These labs need a Linux box with the capability to create namespaces. On your Mac, use a throwaway container. Creating most namespaces needs CAP_SYS_ADMIN, so grant it (a real container runtime holds it while setting things up):

bash
# --cap-add SYS_ADMIN lets unshare/nsenter create and enter namespaces.
docker run --rm -it --cap-add=SYS_ADMIN ubuntu:24.04 bash

# Inside the container, install the namespace toolkit:
apt-get update && apt-get install -y util-linux iproute2 procps
Lab 1Build — carve out your own hostname and PID 1Build

Make a shell that has its own hostname (UTS) and its own process table (PID). This is a hand-built container in one command.

bash
hostname                       # note the current name, e.g. 3f9c1a2b4d5e
unshare --uts --pid --fork --mount-proc bash   # new UTS + PID ns, run a shell

# You are now inside. Change the hostname and look at the process table:
hostname box-of-my-own
ps -e
Output PID TTY TIME CMD 1 pts/0 00:00:00 bash 7 pts/0 00:00:00 ps

Your shell is PID 1. There are two processes in the whole table — because this PID namespace was born empty and you're its first inhabitant. The --fork matters: unshare itself can't become PID 1 (it created the namespace from outside), so it forks a child to be PID 1. The --mount-proc matters too: it gives you a fresh /proc mounted for this PID namespace, so ps reads the right process list instead of the host's. Now open a second terminal into the same container (docker exec -it <id> bash) and run hostname — it still shows the original name. You changed the hostname in your private UTS namespace; the host's was never touched. Type exit to leave and watch PID 1 die and the namespaces vanish with it.

Lab 2Understand — a namespace is an inodeUnderstand

"Membership" isn't a label; it's a shared inode. Prove it. First read your shell's namespace inodes, then create a new network namespace and watch one number change.

bash
readlink /proc/$$/ns/net /proc/$$/ns/uts   # $$ = this shell's PID
Outputnet:[4026531840] uts:[4026531838]
bash
unshare --net bash                 # give this shell a private net namespace
readlink /proc/$$/ns/net           # same shell, new PID, read again
ip link                            # what interfaces do we have now?
Outputnet:[4026532567] 1: lo: <LOOPBACK> mtu 65536 qdisc noop state DOWN mode DEFAULT ... link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00

The net inode changed (...840 → ...567): you're in a different network namespace now. And it contains exactly one interface, lo, in state DOWN — a brand-new net namespace has no connectivity at all until someone plugs it in. Now use lsns to see every namespace grouped by type, and nsenter to prove you can re-enter one. Start a sleeper in its own net namespace and enter it from outside:

bash
exit                                        # back to the shell's original namespaces
unshare --net --fork sleep 1000 &
SLEEPER=$!
lsns -t net                                 # list network namespaces + owners
nsenter -t $SLEEPER -n ip link              # enter the sleeper's net ns, look around

nsenter -t $SLEEPER -n opened /proc/$SLEEPER/ns/net and called setns() to join it, then ran ip link there — showing only that namespace's lonely lo. You just did by hand what happens every time an SRE runs nsenter to debug a container's networking from the node.

Think first: in Lab 2, why did the new net namespace show lo as DOWN rather than UP? Wouldn't loopback "just work"?

No interface comes up on its own, not even loopback. A fresh network namespace is genuinely empty except for the loopback device the kernel creates, and that device starts administratively down. Until something runs ip link set lo up, even ping 127.0.0.1 fails inside that namespace. Container runtimes bring lo up for you as part of setup, which is why you never notice — but if you ever build a net namespace by hand and find that localhost doesn't answer, this is why. It's the most common self-inflicted wound when people first script ip netns.

Lab 3Break — the container that can't see the hostBreak

Here's the question everyone asks once: I exec into my container and ps shows almost nothing, but I know the node is running hundreds of processes. Where did they go? Reproduce it, then investigate before revealing the cause.

bash
# From your Mac host terminal, not inside the lab container:
docker run -d --name web nginx
docker exec web ps -e            # the container's view of processes
Output PID TTY TIME CMD 1 ? 00:00:00 nginx 29 ? 00:00:00 nginx 30 ? 00:00:00 ps

Three processes, and nginx is PID 1. Meanwhile the node running this is executing hundreds. The container isn't "hiding" them with a filter you could turn off, and it isn't a permissions issue. What single kernel fact explains both "can't see them" and "nginx is PID 1 not PID 4242"? Work it out, then check your reasoning.

Reveal the cause

It's the PID namespace. nginx was started as the first process in a fresh PID namespace, so inside it is PID 1, and the process table it can read only contains processes that are also members of that PID namespace. The host's processes exist in a different (parent) PID namespace, and there is no syscall a process can make to enumerate a namespace it isn't in — the kernel answers readdir of /proc relative to the caller's PID namespace. Prove it from the node side, where you can see in:

bash
PID=$(docker inspect -f '{{.State.Pid}}' web)   # nginx's REAL host PID
echo $PID                                        # e.g. 4242 — not 1
sudo readlink /proc/$PID/ns/pid                  # its PID-namespace inode
sudo readlink /proc/1/ns/pid                     # the host init's — a different inode

Same nginx process, two identities: PID 1 inside, PID 4242 outside. The host and the container are in different PID namespaces (different inodes). That asymmetry — the host sees in, the container can't see out — is the master key from the analogy, and it's why you always debug containers from the node, never the other way around.

Lab 4Troubleshoot — enter a live container's namespaces to debug itTroubleshoot

A container is misbehaving and its image is a scratch/distroless one — no shell, no curl, no ip. You can't docker exec bash because there is no bash. This is normal in production. How do you inspect its network without adding anything to the image? Think about which tool crosses into a namespace, then look.

Reveal the approach

Use nsenter from a toolbox that has the utilities, targeting the container's PID. On a real Linux node you run nsenter directly; with Docker Desktop you get there through a privileged helper that shares the host's PID namespace, so it can see the container's real PID:

bash
PID=$(docker inspect -f '{{.State.Pid}}' web)

# A toolbox that shares the host PID namespace so $PID is meaningful:
docker run --rm -it --privileged --pid=host ubuntu:24.04 bash
apt-get update && apt-get install -y iproute2 >/dev/null

# Now step into the target's NET namespace only, and inspect it:
nsenter -t <PID> -n ip addr
nsenter -t <PID> -n ss -tlnp        # what's listening inside the container

You borrowed the container's network view using tools that live in your toolbox, not in the container. The -n selects only the net namespace; add -p for PID, -m for mount, or -a for all. This is the single most useful container-debugging move an SRE owns: when the container is too minimal to help you, enter its namespaces from outside and bring your own tools. The same idea powers Kubernetes ephemeral debug containers (Chapter 40).

Lab 5Production challenge — user namespaces & "root that isn't root"Senior challenge

The user namespace is the one that turns "container root" into "unprivileged nobody on the host." Create one with no privilege at all, become root inside it, then find out who you really are from the outside.

bash
id                              # your real identity, e.g. uid=1000(alice)
unshare --user --map-root-user bash
id                              # inside the new user namespace
Outputuid=0(root) gid=0(root) groups=0(root)

You're "root" — inside this user namespace. Now inspect the mapping the kernel installed, and create a file to see how the outside world scores your UID:

bash
cat /proc/self/uid_map          # inside-uid  outside-uid  count
touch /tmp/made-by-container-root
exit                            # back to your real identity
ls -ln /tmp/made-by-container-root   # who owns it out here?

The uid_map reads something like 0 1000 1: "UID 0 inside maps to UID 1000 outside, for a range of 1." So the file you made as root shows owner 1000 on the host. The senior question: given this, why is a rootless container (one where the container's root is a mapped unprivileged UID) meaningfully safer than a normal container, and where does that safety stop? Reason it out before opening the answer.

Reveal the reasoning

Safety: if a process escapes the container, or writes to a bind-mounted host directory, it acts as the mapped unprivileged UID (1000), not real UID 0. A "root" exploit inside a rootless container lands you as a nobody outside — it can't read /etc/shadow, can't load kernel modules, can't touch other users' files. The capabilities the process holds are only valid within its user namespace; they don't translate to power over host-owned resources.

Where it stops: the kernel is still shared and still the boundary from Chapter 1. A kernel bug reachable via a syscall doesn't care about your UID mapping — a local privilege-escalation vulnerability in the kernel can still be a full escape. User namespaces also historically expanded kernel attack surface (they let unprivileged users reach code paths that were previously root-only), which is why some hardened distros restrict them. So rootless raises the floor a lot and is the right default, but it is not a substitute for keeping the kernel patched, seccomp on, and capabilities dropped — the layered story you'll finish in Chapter 27.

Failure & troubleshootingHow this shows up in real incidents

Namespace problems rarely announce themselves as "namespace problems." They show up as spooky isolation gaps or spooky isolation that's too tight.

Incident pattern · the container can see the host's processes

Symptom: a container's ps shows the node's processes, or a compromised container was able to inspect and signal host services. First cut: compare PID-namespace inodes — readlink /proc/1/ns/pid inside vs on the node. Confirm: check how it was launched. Usual cause: docker run --pid=host or a pod with hostPID: true. That flag deliberately joins the host PID namespace — great for a node-debug toolbox, a serious problem for a normal workload. The fix is to stop setting it (and to block it via PodSecurity in Chapter 39).

Incident pattern · "no space left" creating containers, but the disk is empty

Symptom: new containers or pods fail to start; clone/unshare returns ENOSPC even though df shows free space. First cut: this ENOSPC isn't about disk — namespaces(7) defines per-user namespace limits in /proc/sys/user/max_*_namespaces, and hitting them fails with ENOSPC. Confirm: lsns | wc -l and read /proc/sys/user/max_net_namespaces. Usual cause: a leak — namespaces pinned alive by forgotten bind mounts or leaked file descriptors (often orphaned ip netns entries under /run/netns, or a runtime bug). The fix is finding and releasing the pin, not raising the limit.

Incident pattern · localhost works on the VM, breaks in the container

Symptom: a sidecar that talks to the main app over 127.0.0.1 works when co-located but not when split. Usual cause: a network namespace boundary. Two containers share localhost only if they share a net namespace — which is exactly what pods give you (all containers in a pod share one net namespace) and what separate containers do not. The tell is that the connection gets ECONNREFUSED: nothing is listening on that loopback because "that loopback" is a different namespace's loopback. You'll see this reasoning again in pod networking, Chapter 42.

Production · security · performanceWhat matters in production

Security. Namespaces are a visibility boundary, not a hard security boundary on their own. The user namespace is the one that adds real teeth, because it decouples in-container privilege from host privilege — run workloads rootless where you can. But remember what namespaces do not cover: they don't stop a process from reaching the shared kernel through a syscall, so you still need seccomp to shrink the syscall surface and dropped capabilities to remove privileged operations. The three together — namespaces, seccomp, capabilities — are what people mean by "container isolation," and any one missing is a gap. Treat hostPID, hostNetwork, hostIPC, and privileged containers as things you justify in writing, not defaults.

Performance. Namespaces are close to free. Entering one is a pointer swap in the kernel; there's no per-syscall tax the way a VM's trap-and-emulate can cost. This is the whole economic case for containers over VMs: you get most of the isolation at almost none of the overhead because there's no second kernel. The one place cost creeps in is the network namespace — a packet crossing the veth pair and bridge does more work than a packet on the host stack, which is why high-throughput workloads sometimes choose hostNetwork or newer datapaths. That's a Chapter 25 and Chapter 58 conversation.

Common mistakes: conflating namespaces (visibility) with cgroups (resources) and being surprised a container with no memory limit ate the node; assuming a container can't see the host when someone quietly set hostPID: true; forgetting that --network=host throws away the net namespace entirely, so port conflicts and localhost surprises come right back; and treating "root in the container" as "root on the host" when a user namespace is in play, or worse, assuming a user namespace is present when it isn't.

System-design connectionWhere this reaches into architecture

Namespaces are the reason the container model scales the way it does. Because isolation is per-process and nearly free, you can pack dozens of workloads onto one node and schedule them in milliseconds — the premise the entire orchestration stack is built on. The Kubernetes pod is a direct expression of namespace mechanics: the containers in a pod share the network and IPC namespaces (so they reach each other on localhost and share memory) while keeping separate mount namespaces (so their filesystems don't collide). Understanding that one design decision — "share net, split mnt" — explains most of why pods behave as they do, from sidecar patterns to why a crash in one container doesn't reset another's files. When you design a platform, the questions "what should be shared and what should be isolated?" are literally "which namespaces do these processes share?", and getting that mapping right is the difference between a clean sidecar and a debugging nightmare.

InterviewInterview questions & answers

Answer each in your head first, then open it.

30-secWhat is a Linux namespace, in one breath?

A namespace wraps a global kernel resource — like the process table, the network stack, or the mount table — so that the processes inside see their own private instance of it. There are eight types (pid, net, mnt, uts, ipc, user, cgroup, time), and a container is just a normal process placed into a fresh set of them. Namespaces control what a process can see; they don't limit how much it can use — that's cgroups.

2-minWalk me through what makes a process "a container."

The kernel has no container object — only processes and namespaces. A runtime calls clone() with the CLONE_NEW* flags so the new process is born into fresh namespaces of each type: it's PID 1 in a new PID namespace, has a bare loopback in a new net namespace, an empty mount table, its own hostname, and so on. Then the runtime furnishes those empty namespaces — mounts the image's root filesystem into the mount namespace, plumbs a veth into the net namespace, sets the hostname, and drops the process into a cgroup for CPU/memory limits — and finally execs the workload. From inside, it looks like a private machine; from the host it's one process with eight namespace handles under /proc/<pid>/ns/. I'd stress three things: namespaces are per-type membership you can mix, creating them needs CAP_SYS_ADMIN except the user namespace, and the host can always see into the container but not vice-versa.

DeepHow does the kernel know two processes are in the same namespace, and how do you check?

Each namespace has a kernel object identified by an inode number, exposed as a symlink under /proc/<pid>/ns/<type> whose target is like net:[4026531969]. Two processes share a namespace of that type exactly when those symlinks resolve to the same inode — you can compare with readlink or by stat's device+inode. That inode is also what keeps a namespace alive: as long as a process, an open file descriptor, or a bind mount references it, it persists; otherwise it's torn down when the last member exits. Tools like lsns just read these. This is why the debugging move is always "compare the inodes" — it's a definite yes/no, not a guess.

ScenarioA pod's app container reaches its sidecar on 127.0.0.1:9000, but a standalone container can't reach another container the same way. Why?

Because localhost is per network namespace. Containers in the same pod share one network namespace, so they share one loopback and one port space — 127.0.0.1:9000 in the app is the same loopback the sidecar listens on. Two standalone containers each have their own net namespace and therefore their own separate loopback; a connection to 127.0.0.1 stays inside the caller's namespace and gets ECONNREFUSED because nothing is listening there. To make standalone containers talk, you route between their namespaces over the bridge by IP or DNS name, not over loopback. The fix in Kubernetes terms is: co-locate them in a pod if they truly need loopback, otherwise use a Service.

Follow-upWhat does a user namespace change, and why do we call the result "rootless"?

A user namespace remaps user and group IDs and scopes capabilities to that namespace. It lets a process be UID 0 with a full capability set inside the namespace while being an ordinary unprivileged UID outside, via a mapping like 0 100000 65536. "Rootless" means the container's root is one of those mapped unprivileged host UIDs, so a break-out or a write to a host mount happens as a nobody, not as real root. It's also the only namespace an unprivileged user can create without CAP_SYS_ADMIN, which is what lets rootless runtimes work at all. The caveat I'd add: the kernel is still shared, so a kernel-level exploit can still escape — user namespaces raise the bar, they don't remove the need for seccomp, dropped capabilities, and a patched kernel.

RetainQuick revision

A namespace virtualises one global kernel resource so the processes inside see a private instance. There are eight: pid (process IDs, own PID 1), net (interfaces, ports, routes), mnt (the filesystem tree), uts (hostname), ipc (System V IPC and message queues), user (UID/GID and capabilities), cgroup (the cgroup root view), and time (monotonic/boot clock offsets, not the wall clock). A process is a member of one namespace per type; a fresh set of all eight is a container. Three syscalls do everything — clone creates a process in new namespaces, unshare moves you into new ones, setns joins an existing one — fronted by unshare and nsenter. Membership is an inode under /proc/<pid>/ns/; same inode means same namespace. Creating namespaces needs CAP_SYS_ADMIN, except user namespaces since Linux 3.8. The host sees into the container; the container can't see out. Namespaces isolate visibility; they don't meter resources or seal the shared kernel.

The 10 things to remember

  1. A namespace isolates what a process can see of one global resource; cgroups meter how much it can use. Never conflate them.
  2. There are eight types: pid, net, mnt, uts, ipc, user, cgroup, time. A container is a process in a fresh set of all of them.
  3. Three syscalls: clone (born into new ns), unshare (move into new ns), setns (join existing ns). unshare and nsenter are the CLIs.
  4. Membership is an inode shown by readlink /proc/<pid>/ns/<type>; equal inodes mean the same namespace.
  5. The mount namespace's flag is the historical odd one, CLONE_NEWNS — it was the first namespace Linux had.
  6. A fresh net namespace has only lo, and lo starts DOWN — no connectivity until something plumbs it in.
  7. PID namespaces explain "why the container can't see the host": /proc is read relative to the caller's PID namespace, and the same process is PID 1 inside, PID N outside.
  8. Creating namespaces needs CAP_SYS_ADMIN; the exception is user namespaces, creatable unprivileged since Linux 3.8 — the basis of rootless.
  9. User namespaces make "root inside" an unprivileged UID outside; they raise the bar but don't seal the shared kernel.
  10. The host can always see into a container (debug from the node with nsenter); the container cannot see out.
