Container filesystems: overlayfs & image layers

A hundred containers from the same image share one copy of its files on disk and each still gets a private, writable root. The trick is a stacked filesystem and copy-on-write — and it's why Dockerfile line order decides your build time and your image size.

Start: Beginner→→→End: Staff-level ~45 min read · Linux lab (Docker)

By the end of this chapter you can

  • Explain overlayfs — lowerdir, upperdir, workdir, merged — and what each one holds.
  • Describe copy-on-write and whiteouts, and predict exactly where a container's write lands.
  • Read an image's layers with docker history and image inspect, and find its overlay mount.
  • Order a Dockerfile so the build cache actually helps you, and say why a bad order costs minutes per build.
  • Diagnose image bloat and a writable layer that quietly fills a node's disk.

Why this exists · the problemThe problem overlayfs solves

Run twenty containers from the python:3.12-slim image on one node. That image is maybe 120 MB of files — Python, libc, a userland. The naive approach copies all 120 MB twenty times: 2.4 GB of disk to run twenty identical bases, minutes of copying before anything starts, and every byte duplicated. That doesn't scale, and it throws away the one thing you know for certain: the base files are read-only and identical across all twenty.

But you can't just share one directory read-only, because each container does need to write — a log here, a temp file there, a config it rewrites on boot. So you want two things that sound contradictory: one shared, read-only copy of the image, and a private, writable view per container. The resolution is a union filesystem: stack a thin, per-container writable layer on top of the shared read-only image, and present the combination as one normal-looking filesystem tree. Reads fall through to the shared layer; writes land in the private one. On Linux that union filesystem is overlayfs, and it's what every mainstream container runtime uses today.

This isn't a storage detail you can ignore. The layer model reaches straight up into how you build images — because an image is a stack of these read-only layers, and the order you create them in decides what the build cache can reuse. Get it right and rebuilds take seconds; get it wrong and every one-character code change reinstalls all your dependencies. Same mechanism, two consequences: cheap containers at runtime, and fast (or slow) builds.

Key point

An image is read-only, shared, and content-addressed. A container adds exactly one thin writable layer on top. Everything the container writes goes there, and it's deleted when the container is removed. If you don't put persistent data on a volume, you're storing it in a layer that's designed to be thrown away.

Mental model · analogyThe mental model: sheets of glass over a printed page

Real-world analogy

Picture a printed reference page under a stack of clear acetate sheets — the kind animators used. The printed page at the bottom is the image: fixed, read-only, and you can print it once and lay a hundred stacks over the same master. Looking straight down through the stack, you see a single combined picture — that's the merged view, the filesystem the container thinks it has.

You only ever draw on the top clear sheet (the writable layer). Want to change a word that's printed on the page? You can't touch the print, so you copy that word up onto the top sheet and edit it there — now the stack shows your version, but the master page is untouched. That copy-up is exactly copy-on-write. Want to remove something printed below? You can't erase the print either, so you paint an opaque blob over it on the top sheet so it no longer shows through — that opaque blob is a whiteout.

Peel off the top sheet and throw it away, and you're back to the pristine master, ready for the next stack. That's what happens when a container is deleted: the writable sheet is discarded, the shared image untouched. And because the heavy master is shared, adding another container is just laying down one new blank sheet — cheap and instant.

ArchitectureFour directories become one filesystem

An overlay mount is built from four directories, and the kernel's own documentation names them exactly. You give it lowerdir, upperdir, and workdir; it produces the merged mount point:

  • lowerdir — one or more read-only directory trees, the image's layers. Multiple lowers are joined with colons, and they stack: in lowerdir=L3:L2:L1, L3 is the top and L1 the bottom. When a name exists in several, the higher one wins.
  • upperdir — a single writable directory. Everything the container creates or modifies lands here. This is the container's private layer.
  • workdir — an empty directory on the same filesystem as upperdir, which overlay uses as scratch space to make copy-ups and renames atomic. You never look in it; it just has to exist and be on the right filesystem.
  • merged — the mount point. This is what the container sees as /. Reads resolve top-down through upper then the lowers; writes go to upper.

The rule for resolving a path is simple and worth memorising: upper wins over lower; among lowers, higher wins. If /app/config exists in both the writable layer and a base layer, the container sees the writable one. Directories are the exception — when a directory name appears at several levels, overlay merges their contents rather than hiding the lower one, which is how /usr/bin from the base and /usr/bin from a later layer combine into one directory.

Internal workingCopy-up, whiteouts, and content-addressed layers

  1. Reading a file that lives only in a lower layer is nearly free: overlay resolves the name down the stack, finds it in, say, layer 1, and hands the container direct access to the read-only file. No copying, no overhead — this is why a hundred containers reading the same base library cost one copy of that library on disk.
  2. Writing to a lower file triggers copy-up. The first time the container opens a lower-layer file for write (or changes its metadata, or hard-links it), overlay copies it up into upperdir first: it recreates the parent directories in upper, copies the file's metadata, then its data, then its extended attributes, using workdir to stage the operation atomically. After that the file lives in upper and every future access goes straight there. The lower copy is never modified — that's what keeps the layer shareable.
  3. Deleting a lower file creates a whiteout. You can't remove a file from a read-only layer, so overlay records the deletion in upper as a whiteout — a character device with device number 0/0 (or, in newer setups, a zero-size file tagged with the trusted.overlay.whiteout xattr). When overlay sees that whiteout in upper, it hides the matching lower name. Deleting a whole directory that has lower contents uses an opaque directory marker (the trusted.overlay.opaque=y xattr) so nothing shows through.
  4. A copy-up can surprise you on space and time. Modifying one byte of a 2 GB file in a lower layer copies the entire 2 GB into upper before the write completes — copy-up is whole-file for data. That's a real latency spike and a real disk-usage jump the first time a big lower file is touched, and it's why databases and other write-heavy workloads must use volumes, not the overlay writable layer.
  5. Image layers are content-addressed diffs. Each image layer is a tar archive of the filesystem changes that instruction made — new/changed files, plus whiteout entries for deletions — identified by the SHA-256 digest of its contents. Identical layers have identical digests, so they're stored once and shared across images and pulled once. The image's config records the ordered list of layer digests (the diff_ids); the manifest ties config and layers together. This is the OCI image model you'll formalise in Chapter 26.
  6. The build cache keys on the instruction and its inputs. When building, the runtime reuses a cached layer if the instruction text is unchanged, the parent layer is unchanged, and — for COPY/ADD — the checksums of the copied files are unchanged. The moment one layer's key changes, that layer and every layer after it must be rebuilt, because each layer is defined relative to the one below. Cache invalidation cascades downward, never upward. This single fact dictates Dockerfile order.
The kernel's own analogy

The overlayfs documentation frames an overlay mount as morally equivalent to cp -a lower upper && mount --bind upper merged — same resulting permissions and contents. The only difference is when the copy happens: overlay copies each file lazily, on first write, instead of all up front. That "copy on demand, not up front" is the whole performance win, and it's the definition of copy-on-write.

Think first: your Dockerfile ends with RUN rm -rf /tmp/build-cache to shrink the image, but the image is exactly the same size. Why didn't the delete save space?

Because layers are additive and a delete in a later layer doesn't remove anything from an earlier one — it only writes a whiteout in the new layer that hides the files. The bytes of /tmp/build-cache still sit in the layer where they were created, contributing their full size to the image, and now you've added a small extra layer on top for the whiteouts. To actually shrink the image, the files must never enter a persisted layer in the first place: create and delete them within a single RUN (so the layer's net diff is empty), or use a multi-stage build and copy only the artefacts you want into the final stage. This is the same reason a secret you COPY then rm in a later step is still fully recoverable from the image.

ComponentsThe pieces and where they live

  • The overlay driver (Docker's overlay2 storage driver, containerd's overlayfs snapshotter) manages the layer directories and assembles the mount. On Docker it keeps everything under /var/lib/docker/overlay2/, one directory per layer with a diff/ subdirectory holding that layer's files.
  • The image config and manifest — JSON documents. The config lists the ordered layer diff_ids and the build history (what each layer's instruction was); the manifest references the config and the layer blobs by digest. These are what docker image inspect and a registry serve.
  • The writable layer (container layer) — the per-container upperdir, created when the container starts and destroyed when it's removed. Its growth is charged to the node's disk under /var/lib/docker.
  • Volumes and tmpfs — the escape hatch from the layer model. A volume mount bypasses overlay entirely and writes to a persistent location (or RAM, for tmpfs); it's where anything you want to keep, or anything write-heavy, belongs. Kubernetes emptyDir, hostPath, and PVs are the same idea (Chapter 38).

Data flowFollowing a build and a run

You run docker build. For each instruction, the builder checks its cache key; on a miss it runs the instruction in a temporary container, captures the filesystem diff as a new read-only layer, digests it, and moves on — each layer stacked on the last. The finished image is that ordered stack of digested layers plus a config. When you then docker run it, the runtime creates a fresh upperdir and workdir, points lowerdir at the image's layers, and mounts the overlay as the container's root filesystem. The process starts and reads its files straight from the shared lowers. The first time it writes to /app/app.py, that file copies up into the new upper; the first time it writes /tmp/out.log, that's created directly in upper; when it deletes a base file, a whiteout appears in upper. Stop and remove the container and the upper is gone — the image layers sit untouched, ready for the next run. The labs make every one of these visible on disk.

Think first: you already run one container from a 500 MB image, and you start a second from the same image. How much extra disk does the second one use?

Almost none — kilobytes, not megabytes. The 500 MB of image layers are read-only lowerdirs stored once and shared by every container from that image; the second container adds only its own thin, empty upperdir, which starts at essentially nothing and grows only as it writes. That's the whole economic point of the layer model: the heavy shared part is paid for once per node, and each additional container costs only what it actually changes. It's the same reason pulling an image whose base you already have is fast — only the layers you're missing come down the wire.

Hands-onLabs — build, understand, break, troubleshoot

Some labs run docker commands from your Mac terminal; the deep-dive lab builds an overlay mount by hand inside a privileged container so you can see the directories directly.

Lab 1Build — see an image's layersBuild

Pull an image and look at the stack it's made of. docker history shows one row per layer with the instruction that made it and its size; image inspect shows the layer digests and the live overlay paths.

bash
docker pull python:3.12-slim
docker history python:3.12-slim --no-trunc --format 'table {{.Size}}\t{{.CreatedBy}}'
Output (trimmed)SIZE CREATED BY 0B CMD ["python3"] 0B ENV PYTHON_VERSION=3.12... 45.2MB RUN set -eux; ... pip install ... 0B ENV LANG=C.UTF-8 78.9MB /bin/sh -c #(nop) ADD file:... in / (the base rootfs)

Every non-zero row is a layer that carries real bytes; the 0B rows are metadata-only instructions (ENV, CMD) that still create a layer but add no files. Now list the content-addressed layer IDs and the overlay directories a running container would stack:

bash
docker image inspect python:3.12-slim --format '{{json .RootFS.Layers}}' | tr ',' '\n'
docker image inspect python:3.12-slim --format '{{json .GraphDriver.Data}}'
Output (trimmed)["sha256:9c1b6...","sha256:2f4e0...","sha256:7ad88..."] {"LowerDir":"/var/lib/docker/overlay2/abc/diff:/var/lib/docker/overlay2/def/diff", "MergedDir":"...","UpperDir":"...","WorkDir":"..."}

Those sha256: values are the diff_ids — the digests of each layer's contents. Two images that share a base layer share that digest and store it once. The GraphDriver.Data block is overlayfs in the flesh: a colon-separated LowerDir stack and the Upper/Work/Merged directories the runtime will assemble.

Lab 2Understand — build an overlay by hand and watch copy-on-writeUnderstand

The clearest way to internalise overlayfs is to mount one yourself. Do it in a privileged container so the directories are right in front of you.

bash
docker run --rm -it --privileged ubuntu:24.04 bash

# Inside: make the four directories and seed the "image" (lower):
mkdir -p /ov/lower /ov/upper /ov/work /ov/merged
echo "from the base image" > /ov/lower/base.txt
echo "also from the base"  > /ov/lower/keep.txt
mount -t overlay overlay -o lowerdir=/ov/lower,upperdir=/ov/upper,workdir=/ov/work /ov/merged
ls /ov/merged && cat /ov/merged/base.txt   # the union shows lower's files
Outputbase.txt keep.txt from the base image

Now modify a file that exists only in the lower layer, and watch copy-up happen:

bash
echo "appended by the container" >> /ov/merged/base.txt
ls /ov/upper                 # base.txt has appeared in upper — it was copied up
cat /ov/lower/base.txt       # the LOWER copy is unchanged
rm /ov/merged/keep.txt       # delete a lower file through the merged view
ls -l /ov/upper              # keep.txt is now a 0/0 char device: a whiteout
Outputbase.txt from the base image crw-r--r-- 1 root root 0, 0 ... keep.txt

There it is, the whole model in five commands. Editing base.txt copied it up into upper while the lower original stayed pristine (copy-on-write). Deleting keep.txt couldn't touch the read-only lower, so overlay wrote a whiteout — the crw- character device with major/minor 0, 0 — into upper to hide it. This is exactly what a container's writable layer accumulates as it runs.

Lab 3Break — a Dockerfile that busts its own cacheBreak

Build an image, rebuild it (everything cached), then change one line of application code and watch what rebuilds. First the good order:

bash
mkdir demo && cd demo
printf 'flask==3.0.0\n' > requirements.txt
printf 'print("v1")\n'  > app.py
cat > Dockerfile <<'EOF'
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY app.py .
CMD ["python","app.py"]
EOF
docker build -t demo:1 .
docker build -t demo:1 .        # second build: every step says CACHED
printf 'print("v2")\n' > app.py # change ONLY the app code
docker build -t demo:2 .
Output (third build, trimmed) => CACHED [2/5] WORKDIR /app => CACHED [3/5] COPY requirements.txt . => CACHED [4/5] RUN pip install -r requirements.txt => [5/5] COPY app.py .

The pip install stayed CACHED even though you changed the code — only the last COPY app.py and anything after it rebuilt. Now break it: reorder the Dockerfile so COPY . . comes before the install, change the code again, and rebuild. The install re-runs every single time. Figure out why before revealing.

bash
cat > Dockerfile <<'EOF'
FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["python","app.py"]
EOF
docker build -t demo:3 .
printf 'print("v3")\n' > app.py
docker build -t demo:4 .        # watch the pip install line
Reveal why the install re-ran

Cache invalidation cascades downward. The build reuses a layer only if its instruction, its parent layer, and (for COPY) the copied files' checksums are all unchanged. In the bad Dockerfile, COPY . . pulls in app.py, so editing the code changes that layer's checksum — which invalidates it and every layer built on top of it, including the expensive pip install. In the good Dockerfile, requirements.txt is copied and the dependencies installed before the volatile app.py is copied, so a code change only invalidates the cheap final COPY. The rule that falls out: order instructions from least-likely-to-change to most-likely-to-change — base image, then system packages, then dependency manifests and their install, then application code last. On a real service this is the difference between a 3-second rebuild and a 3-minute one, multiplied by every push all day.

Lab 4Troubleshoot — the writable layer that fills the diskTroubleshoot

A node's disk is filling and pods start getting evicted for disk pressure, yet nobody deployed anything new and no volumes look full. Reproduce the shape: a container writing to its own root filesystem instead of a volume.

bash
docker run -d --name hog busybox sh -c \
  'i=0; while true; do dd if=/dev/zero of=/big.$i bs=1M count=20 2>/dev/null; i=$((i+1)); sleep 1; done'
sleep 20
docker ps -s --filter name=hog --format 'table {{.Names}}\t{{.Size}}'
OutputNAMES SIZE hog 412MB (virtual 4.68MB)

The SIZE column is the size of the container's writable layer, climbing every second, while the "virtual" figure (the shared image) stays tiny. The disk is filling but no volume is involved and no new image was pulled. Where is the space going, and what's the fix? Reason it out, then reveal.

Reveal the cause and fix

The writes are landing in the container's ephemeral writable layer (its upperdir under /var/lib/docker/overlay2), because /big.* is on the container root filesystem, not a volume. That layer counts against the node's disk, and nothing caps it by default — a chatty app writing logs, temp files, or caches to its own rootfs will grow until the node runs out. Confirm with docker ps -s (the writable-layer size) and, on a node, du -sh of the overlay diff directory. The fixes: send anything persistent or high-volume to a volume or Kubernetes emptyDir (and set a size limit on it), configure log rotation, and don't write application data to the container root. In Kubernetes this surfaces as node disk pressure and pod eviction — the container's ephemeral storage usage is exactly this writable layer, and it's why ephemeral-storage requests/limits exist. Deleting the container reclaims it instantly (docker rm -f hog), which is the tell that it was the writable layer and not a volume.

Lab 5Production challenge — the secret that's still in the imageSenior challenge

A teammate "removed" a secret from an image by deleting it in a later build step. Build their image and decide whether the secret is actually gone — then extract the image and check.

bash
mkdir leak && cd leak
printf 'SUPER-SECRET-TOKEN-abc123\n' > secret.txt
cat > Dockerfile <<'EOF'
FROM busybox
COPY secret.txt /secret.txt
RUN cat /secret.txt > /dev/null   # "use" it during build
RUN rm -f /secret.txt            # "delete" it so it's not in the image
EOF
docker build -t leaky:1 .
docker run --rm leaky:1 ls /secret.txt   # gone from the running container...
Outputls: /secret.txt: No such file or directory

The running container can't see it — the final layer has a whiteout. But is the secret in the image? The senior question: can someone who pulls leaky:1 recover the token, and if so, how do you actually keep secrets out of images? Decide before revealing.

Reveal — extract the layers and the lesson

The secret is fully recoverable. The rm only added a whiteout in the top layer; the layer created by COPY secret.txt still contains the plaintext token, and anyone with the image can unpack that layer:

bash
docker save leaky:1 -o leaky.tar
mkdir x && tar -xf leaky.tar -C x
# each blob under x/blobs/sha256 is a layer tarball; search them for the token:
for b in x/blobs/sha256/*; do tar -xOf "$b" 2>/dev/null | grep -a SUPER-SECRET && echo "  ^ found in $b"; done
OutputSUPER-SECRET-TOKEN-abc123 ^ found in x/blobs/sha256/6b2f...

There's the token, sitting in an intermediate layer, retrievable by anyone who can pull the image. Deleting a file in a later layer never removes it from an earlier one — layers are additive and immutable. The right ways to keep secrets out: use build secrets (RUN --mount=type=secret) so the file is mounted only during that step and never persisted to a layer; use multi-stage builds and copy only the final artefacts into a clean last stage; and inject runtime secrets through the environment or a secrets manager, never COPY. The same additive-layer fact is why "just rm the build cache at the end" doesn't shrink an image — the bytes already live in a lower layer. Slim images come from creating-and-cleaning within one RUN, multi-stage builds, and a minimal base, not from deleting things afterward.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · node disk pressure with no obvious culprit

Symptom: a node hits disk pressure, the kubelet evicts pods, and df shows /var/lib/docker (or the containerd root) full. First cut: docker ps -s (or per-container ephemeral-storage metrics) to find containers with a large writable layer. Usual cause: an app writing logs, caches, or temp files to its container root instead of a volume, so its upperdir grows unbounded. Fix: route that data to a volume/emptyDir with a size limit, add log rotation, and set ephemeral-storage requests/limits so the scheduler and eviction know about it.

Incident pattern · builds that take minutes for a one-line change

Symptom: CI rebuilds dependencies on every commit even when only application code changed. First cut: read the Dockerfile top to bottom and find where volatile inputs (source code, COPY . .) sit above expensive steps (package installs). Usual cause: instruction order that copies source before installing dependencies, so any code change invalidates the install layer and everything below it. Fix: reorder least-volatile to most-volatile — deps first, code last — and use build caches/cache mounts for package managers.

Incident pattern · images far larger than expected

Symptom: a "small" service image is 1.5 GB, slow to pull, slow to schedule. First cut: docker history to find the fat layers. Usual cause: build tools, caches (apt/pip), or large intermediate files baked into layers and only "deleted" later (which doesn't shrink anything), or a heavyweight base image. Fix: multi-stage builds that ship only artefacts, cleaning within the same RUN that created the mess, and a minimal base. Smaller images pull faster, schedule faster, and shrink attack surface.

Production · security · performanceWhat matters in production

Treat the writable layer as scratch. Anything you want to keep, and anything write-heavy, goes on a volume — full stop. Databases, queues, and log-heavy apps writing to the overlay layer will both lose data on restart and risk filling the node. Set ephemeral-storage requests and limits so the platform can account for and cap the writable layer, and rotate logs so they don't accumulate there.

Performance. Overlay reads are essentially native — the container reads shared lower files directly. The costs are specific and predictable: the first write to a large lower file pays a whole-file copy-up, and write-heavy workloads see overhead from copy-up churn, so they belong on volumes. Deep lower stacks (dozens of layers) add lookup cost and slow pulls; keep layer counts sane. And because layers are shared and cached, a good base-image strategy — everyone on the same slim base — means most of an image is already present on the node and only your thin top layers get pulled.

Security. Images are not opaque: every layer is extractable, so any secret, key, or credential that ever entered a layer is recoverable even if a later step deletes it. Use build secrets and multi-stage builds, never COPY a secret, and scan images for leaked credentials in CI. Pin and verify base images by digest so a mutated upstream tag can't swap the foundation of your stack underneath you — the provenance story that continues in Chapter 27.

System-design connectionWhere this reaches into architecture

Content-addressed, shared, immutable layers are what make container distribution scale. Because a layer is identified by its digest, a registry stores each unique layer once and a node pulls it once no matter how many images reference it — the base layer of a hundred services is downloaded a single time per node. That's the property your whole delivery pipeline leans on: fast pulls, deduplicated storage, cacheable builds, and reproducible artefacts you can pin by digest for supply-chain integrity. The immutability also underwrites the "cattle not pets" model — an image is a fixed, verifiable unit you roll forward or back atomically, which is the foundation for the deployment and rollback strategies in Chapter 73. When you design a build-and-release system, layer caching and image size are not afterthoughts; they set your CI throughput, your rollout speed, and your storage bill.

InterviewInterview questions & answers

Answer each in your head first, then open it.

30-secWhat is overlayfs and why do containers use it?

It's a union filesystem that stacks a read-only lower (the image's layers) under a writable upper (the container's private layer) and presents them as one merged tree. Reads fall through to the shared lowers; writes land in upper, copying a file up from lower on first modification. That lets many containers share one on-disk copy of an image while each gets its own writable root, so containers are cheap to start and cheap to store. The writable layer is ephemeral — deleted with the container.

2-minExplain copy-on-write and whiteouts in overlayfs.

Reading a file that only exists in a lower layer is direct and free. The first time the container writes to such a file — or changes its metadata or hard-links it — overlay copies it up into the writable upper layer first: it recreates the parent dirs, copies metadata then data then xattrs, staged atomically via the workdir. After that the file lives in upper and the lower copy is never touched, which is what keeps lowers shareable. That's copy-on-write, and one gotcha is that copy-up is whole-file, so touching one byte of a huge lower file copies the whole thing. Deletion works the opposite way: you can't remove a file from a read-only lower, so overlay records a whiteout in upper — a 0/0 character device — that hides the lower name; a whole deleted directory uses an opaque-directory xattr. The practical upshots are that write-heavy data belongs on volumes, and that deleting a file in a later image layer never reclaims the space it used in an earlier one.

DeepWhy does Dockerfile instruction order affect build speed, and how do you order it well?

Because each image layer is a diff defined relative to the layer below it, and the build cache reuses a layer only if its instruction, its parent, and — for COPY/ADD — the copied files' checksums are unchanged. So invalidating one layer forces every layer after it to rebuild; cache invalidation cascades strictly downward. If you copy source code early and install dependencies after it, any code change changes the source layer's checksum and re-runs the install. The fix is to order instructions from least-volatile to most-volatile: base image, then OS packages, then the dependency manifest and its install, then the application code last, so a routine code change only invalidates the cheap final copy. On a busy service this is minutes saved per build, every build. I'd also mention build caches/cache mounts for package managers to speed even the cold path.

ScenarioA node fills its disk and evicts pods, but no volumes are full and nothing new deployed. What's happening?

Almost certainly a container's ephemeral writable layer growing. Writes to the container root filesystem — logs, caches, temp files not on a volume — land in that container's overlay upperdir under the runtime's data directory, and it grows unbounded by default, counting against the node's disk as ephemeral storage. I'd confirm with docker ps -s or ephemeral-storage metrics to find the container with a large writable layer, and check du of the overlay diff dir on the node. The fix is to move that data to a volume or emptyDir with a size limit, add log rotation, and set ephemeral-storage requests/limits so the scheduler and eviction account for it. Deleting the offending container reclaims the space immediately, which also confirms it wasn't a volume.

Follow-upSomeone deleted a secret in a later build step. Is it out of the image?

No. Layers are additive and immutable, so deleting a file in a later layer only writes a whiteout that hides it — the bytes still live in the earlier layer that added them, and anyone who can pull the image can docker save it and extract that layer to recover the secret. The same fact explains why "rm the cache at the end" doesn't shrink an image. To actually keep secrets out, they must never be persisted to a layer: use build secrets (RUN --mount=type=secret) so the file exists only during that step, use multi-stage builds that copy only clean artefacts into the final stage, and inject runtime secrets via environment or a secrets manager rather than COPY. And rotate anything that did leak, because it must be assumed compromised.

RetainQuick revision

overlayfs stacks read-only image layers (lowerdir) under a per-container writable layer (upperdir), with a workdir for atomic operations, and presents the union as merged — the container's root. Reads fall through the stack (upper wins over lower; among lowers, higher wins; directories merge); writes go to upper. Modifying a lower file copies it up first (copy-on-write, whole-file); deleting one writes a whiteout (a 0/0 char device) that hides it. An image is an ordered stack of content-addressed layer diffs identified by SHA-256, shared and stored once. The build cache reuses a layer only if its instruction, parent, and copied-file checksums are unchanged, and invalidation cascades downward — so order Dockerfiles least-volatile to most-volatile, code last. The writable layer is ephemeral and uncapped by default: keep persistent and write-heavy data on volumes, and remember that deleting a file in a later layer never reclaims earlier-layer space, which is why secrets and bloat survive.

The 10 things to remember

  1. overlayfs = lowerdir (RO image layers) + upperdir (RW container layer) + workdir (scratch) → merged (what the container sees).
  2. Resolution rule: upper beats lower; among lowers, higher beats lower; same-named directories merge their contents.
  3. Copy-on-write: first write to a lower file copies the whole file up to upper; the lower stays pristine and shareable.
  4. Whiteout: deleting a lower file writes a 0/0 character device in upper to hide it; it can't erase the lower.
  5. A container adds exactly one thin writable layer; it's discarded when the container is removed.
  6. An image is an ordered stack of content-addressed (SHA-256) layer diffs, stored and pulled once per unique layer.
  7. Build cache reuses a layer only if instruction + parent + copied-file checksums are unchanged; invalidation cascades downward.
  8. Order Dockerfiles least-volatile → most-volatile: base, packages, dependency install, then application code last.
  9. Deleting a file in a later layer never reclaims earlier-layer space — secrets and bloat survive; use multi-stage builds and build secrets.
  10. The writable layer is ephemeral and uncapped; put persistent and write-heavy data on volumes and set ephemeral-storage limits.
