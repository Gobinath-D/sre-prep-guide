Part III · Containers & Container Internals · Chapter 25

Container networking

A container has its own network stack, yet somehow reaches the internet, gets reached on a published port, and finds its neighbours by name. Four pieces do all of it — a virtual cable, a software switch, NAT, and a tiny DNS server — and they're the direct ancestor of every Kubernetes CNI.

By the end of this chapter you can

  • Draw the bridge + veth + NAT datapath from a container to the internet and back.
  • Explain what a veth pair and the docker0 bridge are, and trace a packet across them.
  • Say exactly what -p 8080:80 does — the DNAT rule and where it lives.
  • Explain why containers resolve each other by name on a user-defined network but not on the default bridge.
  • Debug port-mapping and DNS problems with docker network inspect, iptables, and tcpdump.

Why this exists · the problemThe problem container networking solves

From Chapter 22 you know a container has its own network namespace: its own interfaces, routing table, and port space, starting with nothing but a loopback that's down. That isolation is exactly what you wanted — two containers can both bind port 80 without colliding — but it creates an immediate problem. A namespace with only loopback is an island. The container can't reach the internet, nothing can reach it, and it can't talk to the container running next to it. Isolation without connectivity is useless.

So you need to wire the island back up, on your terms. Concretely: give each container an address and a path off the box (so apt-get and outbound API calls work); let containers on the same host talk to each other; let the outside world reach a chosen service on a chosen port; and let containers find each other by name instead of chasing IPs that change on every restart. And you have to do all of this without giving the container the host's real network interface, because that would throw away the isolation.

The standard answer — the one Docker ships by default and the one every Kubernetes CNI is a descendant of — is a virtual switch on the host with a virtual cable into each container, plus NAT to bridge the container's private address range to the real network, and a small embedded DNS server for names. Learn these four here on plain Docker and the Kubernetes datapath in Part V will feel familiar instead of alien.

Key point

The container's eth0 is not a real network card. It's one end of a virtual Ethernet cable (a veth pair); the other end lives on the host and plugs into a software bridge. Every packet in or out of a container crosses that cable and that bridge. Once you can see those two objects, container networking stops being magic.

Mental model · analogyThe mental model: an office LAN behind a receptionist

Real-world analogy

Think of the host as an office with one public phone number and an internal switchboard. Each container is a desk with an internal extension (its private IP like 172.17.0.2). The desks are all wired to a small internal switchboard — that's the docker0 bridge — so any desk can call any other desk directly by extension. The wire from a desk to the switchboard is the veth pair: one plug at the desk, one in the switchboard.

When someone at a desk calls out to the world, the switchboard hands the call to the receptionist, who places it from the office's single public number — the outside world sees the receptionist's number, never the desk extension. That's NAT (source NAT / masquerade): the container's private IP is rewritten to the host's IP on the way out. When a call comes in to the public number asking for "the web service on 8080," the receptionist has a rule: forward anything on 8080 to extension 172.17.0.2, line 80. That forwarding rule is port publishing (destination NAT), and it only exists for ports you explicitly ask to publish.

Finally, nobody memorises extensions. There's an internal directory you can ask "what's the extension for db?" and it answers — that's the embedded DNS server. The catch: the directory only covers desks that joined the same named team room. Desks on the generic default floor don't get a directory and must dial extensions directly.

ArchitectureThe bridge + veth + NAT datapath

Here's the whole model on one page. A container's eth0 is one end of a veth pair; the host end (vethXXXX) is enslaved to the docker0 bridge, which also holds the gateway address 172.17.0.1. Containers on the same bridge reach each other at layer 2, directly across the bridge, with no NAT. Traffic leaving the host is source-NATed to the host's IP; traffic arriving on a published port is destination-NATed into the container. Follow both directions:

Two addressing facts anchor everything. The default bridge network uses 172.17.0.0/16 with the bridge itself at 172.17.0.1, and each container's default route points at that gateway. And the container's private IP is never seen on the real network — outbound, it's masqueraded to the host's IP; inbound, the world only ever talks to the host's IP and a published port. The container's address is a host-local detail.

Internal workingWhat Docker does when a container starts

  1. Create the network namespace and a veth pair. The runtime makes the container's net namespace (empty but for loopback), then creates a veth pair — two linked virtual interfaces where whatever goes in one end comes out the other. One end is moved into the container's namespace and renamed eth0; the other stays on the host as vethXXXX.
  2. Enslave the host end to the bridge. The host-side vethXXXX is attached to the docker0 bridge, so it becomes a port on that software switch. Now the container's eth0 is, electrically, one drop on the bridge's LAN.
  3. Assign an address and a route. The runtime gives eth0 an address from the bridge's subnet (172.17.0.2/16), brings lo and eth0 up, and installs a default route via the bridge's gateway 172.17.0.1. The container can now reach any other address on the bridge directly, and anything else via the gateway.
  4. Install the NAT rules. Docker programs iptables: a MASQUERADE rule in the nat table's POSTROUTING chain rewrites the source of outbound container traffic to the host's IP (so replies can find their way back), and IP forwarding is enabled on the host so it routes between the bridge and the outside. Without this, outbound packets would leave with a 172.17.x.x source that the internet can't route back to.
  5. For each published port, add a DNAT rule. -p 8080:80 inserts a rule in the nat table (Docker's DOCKER chain, reached from PREROUTING and OUTPUT) that rewrites the destination of packets arriving on host port 8080 to 172.17.0.2:80. A small userspace helper, docker-proxy, also binds the host port to cover hairpin and localhost cases the iptables path doesn't. No -p, no rule — which is why an unpublished port is unreachable from outside the host even though the container is listening.
  6. Wire up names on user-defined networks. If the container is on a user-defined network, Docker points its /etc/resolv.conf at the embedded DNS server on 127.0.0.11, which resolves other container and service names on that same network to their current IPs. On the default bridge this is absent — a deliberate legacy behaviour.
The distinction that trips everyone: default bridge vs user-defined bridge

Both are bridges and both do NAT and port publishing. The difference is name resolution. On a user-defined bridge (anything you docker network create, and every Compose network), containers get automatic DNS: ping db just works. On the default bridge network, there is no embedded DNS for container names — containers can only reach each other by IP. This is why the standing advice is "always put multi-container apps on a user-defined network," and why Compose does it for you.

Think first: your container listens on port 3000 and you can curl localhost:3000 from inside it, but not from your laptop. Nothing is wrong with the app. Why can't you reach it?

Because you never published the port. Listening inside the container's network namespace makes the service reachable within that namespace and to other containers on the same bridge — but the host has no DNAT rule sending its own :3000 into the container, so from your laptop (which talks to the host) there's nothing routing the connection in. The container is healthy; the doorway just doesn't exist. Add -p 3000:3000 and Docker installs the DNAT rule that forwards host :3000 to the container. The tell is that curl from inside works while curl from the host or laptop gets connection-refused or times out — the app is fine, the publishing is missing.

ComponentsThe pieces and what each owns

  • The veth pair — a virtual Ethernet cable with two ends. One end is the container's eth0; the other is the host's vethXXXX. Packets are simply handed from one end to the other by the kernel.
  • The bridge (docker0 or a user-defined one) — a software layer-2 switch in the host kernel. Every container's host-side veth plugs into it, and it forwards frames between them by MAC, exactly like a physical switch. It also holds the gateway IP for its subnet.
  • iptables/netfilter — does the NAT. MASQUERADE (SNAT) for outbound in POSTROUTING; DNAT for published ports in the DOCKER chain; and the DOCKER-USER chain, evaluated first, where your custom rules belong so they survive daemon restarts and sit ahead of Docker's. Isolation between networks is enforced by the DOCKER-ISOLATION chains.
  • The embedded DNS server at 127.0.0.11 — a resolver Docker runs for each user-defined network, answering container/service names with current IPs and forwarding everything else to the host's upstream resolvers.
  • docker-proxy — a small userspace process per published port that binds the host port, covering hairpin/localhost paths the pure-iptables datapath misses. Mostly invisible until you see it in ps or a "port already in use" error.

Data flowFollowing one request in and one out

Outbound: a process in the container connects to api.example.com. The packet leaves eth0 with source 172.17.0.2, pops out the host-side veth into the docker0 bridge, and hits the host routing table, which sends it toward the real interface. On the way out, POSTROUTING MASQUERADE rewrites the source to the host's IP 10.0.0.5 so the reply can come back. The reply arrives at the host, netfilter's connection tracking reverses the NAT, and the bridge delivers it back to 172.17.0.2. Inbound: a request hits 10.0.0.5:8080. PREROUTING sends it through the DOCKER chain, whose DNAT rule rewrites the destination to 172.17.0.2:80; the host forwards it across the bridge and veth into the container, where the app on port 80 answers. Its reply is un-NATed on the way out so the client sees a response from 10.0.0.5:8080, never learning a container was involved. Container to container on the same bridge skips all of this: it's a plain layer-2 frame across docker0, container IP to container IP. The labs let you watch each of these.

Think first: container A is on user-defined network net1 and container B on net2, both on the same host. Can A reach B by its IP?

No, not by default. Each user-defined network is a separate bridge with its own subnet, and Docker's DOCKER-ISOLATION chains explicitly drop traffic between different bridges — that isolation is the reason to put unrelated apps on separate networks in the first place. Reachability isn't about whether the IP is routable; it's about whether the two containers share a bridge. To let them talk you'd attach one container to both networks with docker network connect (giving it an interface on each), or route between them deliberately. This is the same "same segment = reachable, different segment = blocked" logic that becomes NetworkPolicy in Kubernetes (Chapter 47).

Hands-onLabs — build, understand, break, troubleshoot

These run docker from your Mac terminal. For the packet-capture lab you'll use a privileged helper sharing the host network so you can watch docker0 directly.

Lab 1Build — inspect a network and find the vethBuild

Create a user-defined bridge, attach a container, and look at both ends of its cable.

bash
docker network create appnet
docker run -d --name web --network appnet nginx
docker network inspect appnet --format \
  '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'
docker exec web ip -brief addr           # the container's view: lo + eth0
Outputweb 172.18.0.2/16 lo UNKNOWN 127.0.0.1/8 eth0 UP 172.18.0.2/16

The container has an eth0 with an address from the network's subnet. That eth0 is one end of a veth pair; the other end is on the host, enslaved to this network's bridge. On a real Linux host you'd see it with ip link as a vethXXXX@ifN. From a host-network helper you can confirm the pairing via the interface index:

bash
docker exec web cat /sys/class/net/eth0/iflink   # the host-side veth's index
docker run --rm --net=host ubuntu:24.04 sh -c 'apt-get -qq update; apt-get -qq install -y iproute2; ip -brief link | grep veth'

The number from iflink matches the host-side veth's interface index — that's the two ends of the same virtual cable. One container, one veth pair, one drop on the bridge.

Lab 2Understand — container-to-container by nameUnderstand

On a user-defined network, containers find each other by name through the embedded DNS. Prove it, and see the resolver they're pointed at.

bash
docker run -d --name db  --network appnet nginx
docker run --rm --network appnet busybox sh -c 'cat /etc/resolv.conf; echo ---; nslookup web; ping -c1 db'
Outputnameserver 127.0.0.11 --- Server: 127.0.0.11 Name: web Address 1: 172.18.0.2 64 bytes from 172.18.0.3: seq=0 ttl=64 time=0.1 ms

Its /etc/resolv.conf points at 127.0.0.11 — Docker's embedded DNS for this network — and it resolves web and db to their current bridge IPs, then reaches db directly at layer 2 across the bridge. No NAT, no published port; two containers on one bridge just talk. This is exactly how services in a Compose file reach each other by service name, and the seed of Kubernetes service discovery in Chapter 42 and Chapter 45.

Lab 3Break — names don't resolve on the default bridgeBreak

Run two containers on the default bridge — no --network — and try to reach one from the other by name. It fails. The containers are up, on the same bridge, with routable IPs. Investigate before revealing.

bash
docker run -d --name a1 nginx          # default bridge (no --network)
docker run -d --name a2 nginx
docker exec a2 cat /etc/resolv.conf     # what resolver is it using?
docker exec a2 getent hosts a1 || echo "name 'a1' did NOT resolve"
A1_IP=$(docker inspect -f '{{.NetworkSettings.IPAddress}}' a1)
docker exec a2 ping -c1 "$A1_IP" && echo "but the IP is reachable"
Outputnameserver 192.168.65.7 # the host's upstream resolver, NOT 127.0.0.11 name 'a1' did NOT resolve 64 bytes from 172.17.0.3 ... but the IP is reachable

The IP is reachable but the name isn't. Why does the same ping db that worked in Lab 2 fail here? Reason it out, then check.

Reveal the cause

The default bridge network has no embedded DNS for container names. Notice a2's resolver is the host's upstream (192.168.65.7), not 127.0.0.11 — Docker only points containers at the embedded DNS when they're on a user-defined network. On the default bridge, connectivity works (same subnet, layer-2 reachable by IP) but name resolution doesn't, which is a deliberate legacy behaviour kept for backward compatibility. The fix is not to add a resolver by hand; it's to put the containers on a user-defined network (docker network create, or just use Compose, which always does). This is the single most common "my containers can't talk to each other by name" support question, and the answer is almost always "you're on the default bridge — move to a user-defined network."

Lab 4Troubleshoot — publish a port and trace the packetTroubleshoot

Publish a port, confirm the DNAT rule Docker installed, then watch a request cross docker0 in real time.

bash
docker run -d --name pub -p 8080:80 nginx
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080   # 200 from the host

# See the DNAT rule and capture traffic on the bridge, from a host-net helper:
docker run --rm --net=host --cap-add=NET_ADMIN ubuntu:24.04 sh -c '
  apt-get -qq update >/dev/null; apt-get -qq install -y iptables tcpdump >/dev/null
  echo "=== nat DOCKER chain ==="; iptables -t nat -S DOCKER
  echo "=== capturing on docker0 (run a curl now) ==="; timeout 8 tcpdump -ni docker0 tcp port 80'

While the capture runs, fire another curl http://localhost:8080 from your Mac. You'll see the DNAT rule and the packets arriving at the container's port 80. If a published port ever "doesn't work," this is the investigation. Interpret before revealing.

Reveal how to read it
Output (trimmed)=== nat DOCKER chain === -A DOCKER -p tcp -m tcp --dport 8080 -j DNAT --to-destination 172.17.0.2:80 === capturing on docker0 === IP 172.17.0.1.51524 > 172.17.0.2.80: Flags [S] ... IP 172.17.0.2.80 > 172.17.0.1.51524: Flags [S.] ...

The DNAT --to-destination 172.17.0.2:80 rule is the entire meaning of -p 8080:80: host port 8080 is rewritten to the container's :80. On docker0 you see the SYN arriving at 172.17.0.2:80 and the SYN-ACK coming back — the handshake completing inside the bridge. When a published port fails, the usual causes are: no -p at all (no rule exists — the Lab 3 recall shape); the app bound to 127.0.0.1 inside the container instead of 0.0.0.0, so it rejects the forwarded connection that arrives on eth0; a host firewall ahead of the DOCKER chain dropping it; or publishing the wrong container port. Reading the nat table and capturing on the bridge tells you in seconds which one it is.

Lab 5Production challenge — outbound NAT and the CNI connectionSenior challenge

Confirm the outbound masquerade, then reason about how all of this maps onto Kubernetes. First, watch the source address get rewritten:

bash
# See the MASQUERADE rule that SNATs container traffic to the host IP:
docker run --rm --net=host --cap-add=NET_ADMIN ubuntu:24.04 sh -c '
  apt-get -qq update >/dev/null; apt-get -qq install -y iptables >/dev/null
  iptables -t nat -S POSTROUTING | grep -i masquerade'
# From a container, the world sees the HOST ip, not 172.17.x.x:
docker run --rm curlimages/curl -s https://api.ipify.org; echo
Output-A POSTROUTING -s 172.17.0.0/16 ! -o docker0 -j MASQUERADE <your host's public IP>

The rule masquerades anything from the bridge subnet leaving via a non-bridge interface. The senior question, no commands required: given this bridge + veth + NAT model, what does a Kubernetes CNI change and what does it keep — and why do pods, unlike Docker containers, not need NAT to talk to each other across nodes? Reason it through.

Reveal the reasoning

What's kept: the per-container network namespace and the veth pair are identical — a pod's eth0 is still one end of a veth whose other end lives in the node's root namespace. That much is the same object you just inspected. What changes: the CNI plugin owns IP address management and routing instead of Docker, and crucially the Kubernetes network model requires that every pod gets a real, cluster-routable IP and that any pod can reach any other pod without NAT (Chapter 41). So the pod-to-pod path drops the SNAT you saw here: instead of masquerading to the node IP, the fabric routes the pod's own IP across nodes (via an overlay, or by programming the real network, or — on AWS — by giving pods VPC IPs directly, Chapter 58). NAT doesn't vanish entirely — pod-to-external traffic still gets masqueraded to the node, and Services layer their own DNAT-like translation on top (Chapter 43) — but the flat, NAT-free pod-to-pod space is the defining difference. Everything you built here is the ancestor; CNI is the same primitives with a routing policy that makes pod IPs first-class.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · "the published port doesn't work"

Symptom: a container is up and healthy but a published port refuses connections from outside the host. First cut: curl the port from inside the container (works?) and from the host (fails?). Confirm: check for the DNAT rule (iptables -t nat -S DOCKER) and what address the app bound to. Usual causes: the port wasn't published (-p missing); the app bound to 127.0.0.1 inside the container instead of 0.0.0.0, so it never accepts the forwarded connection; or a host firewall sits ahead of Docker's chains. The reflex "inside works, outside doesn't → it's publishing or bind address, not the app" saves the most time.

Incident pattern · containers can't resolve each other by name

Symptom: service A can't reach service B by name; IPs work. First cut: cat /etc/resolv.conf in the container — is it 127.0.0.11 or the host's upstream? Usual cause: the containers are on the default bridge, which has no embedded DNS. Fix: put them on a user-defined network (or use Compose). In Compose specifically, remember names are the service names on the project network — a common gotcha when someone hard-codes IPs and they change on redeploy (Chapter 42).

Incident pattern · bridge subnet collides with the corporate network

Symptom: from inside containers, a specific range of real destinations is unreachable, or routing behaves strangely. First cut: compare the Docker bridge subnet (172.17.0.0/16 or a custom pool) with the routes the host needs. Usual cause: Docker's address pool overlaps a subnet the host or VPN actually uses, so traffic meant for the real network gets delivered to the bridge instead. Fix: reconfigure Docker's default address pools to a range that doesn't collide. This is common on corporate VPNs that use 172.x space.

Production · security · performanceWhat matters in production

Security. Publishing a port opens a path from the host's network into a container, so publish deliberately and bind to a specific host interface (-p 127.0.0.1:8080:80) when a service should only be local. Put your own firewall rules in the DOCKER-USER chain — it's evaluated before Docker's rules and persists across daemon restarts, so it's the supported place to restrict who can reach published ports. Be aware that Docker's port publishing manipulates iptables directly and can bypass a naively configured host firewall, which surprises people who thought ufw was protecting them. Network segmentation between apps comes from putting them on separate user-defined networks (the DOCKER-ISOLATION chains keep those apart).

Performance. The bridge + veth path adds a little overhead versus the host stack — an extra hop through the bridge and, for NATed traffic, connection-tracking state. For most services it's negligible; for very high packet-rate or latency-critical workloads it's measurable, which is why some run with --network=host (no namespace, no bridge, no NAT — but you lose isolation and port independence) or reach for faster datapaths. The NAT connection-tracking table (conntrack) is finite; a host doing huge numbers of short-lived NATed connections can exhaust it, which shows up as dropped connections and is a real capacity dimension you'll meet again with kube-proxy in Part V.

Common mistakes: relying on the default bridge for multi-container apps and then wondering why DNS by name fails; binding services to 127.0.0.1 inside the container and expecting a published port to reach them; assuming an unpublished port is reachable from the host; and hard-coding container IPs, which change on restart — use names on a user-defined network instead.

System-design connectionWhere this reaches into architecture

This chapter is the blueprint for the entire Kubernetes datapath. A pod's networking is the same veth-into-a-bridge-or-fabric idea, and Docker Compose's "reach services by name on a shared network" is the direct precursor of Kubernetes Services and cluster DNS. The big architectural leap Kubernetes makes — every pod gets a routable IP and pods talk without NAT — is best understood as a deliberate change to this model, keeping the veth pair and dropping the SNAT, so you already know what's being changed and why. The concepts you carry forward are exact: veth pairs (pod interfaces), bridges and routing (the CNI datapath, Chapter 41), DNAT (Service load-balancing, Chapter 43), SNAT (egress to the internet, Chapter 48), and embedded DNS (CoreDNS, Chapter 45). When you design a platform's networking, these primitives set what's cheap (same-host, same-network traffic), what costs NAT state (egress and Services), and where names come from.

InterviewInterview questions & answers

Answer each in your head first, then open it.

30-secHow does a container reach the internet if it has its own network namespace?

Its eth0 is one end of a veth pair; the other end plugs into a host bridge like docker0. The container gets a private IP from the bridge's subnet and a default route to the bridge gateway. Outbound packets cross the veth to the bridge, hit the host's routing, and get source-NATed (MASQUERADE) to the host's IP so replies can return. So connectivity is veth + bridge + NAT, with the container's private address never seen on the real network.

2-minWalk me through exactly what -p 8080:80 does.

It publishes the container's port 80 on the host's port 8080 by installing a destination-NAT rule. Docker adds a rule in the nat table's DOCKER chain, reached from PREROUTING and OUTPUT, that rewrites the destination of packets arriving on host :8080 to the container's IP on :80, and it also runs a small docker-proxy process bound to the host port to cover localhost and hairpin cases. So a client hitting host:8080 is DNATed across the bridge and veth into the container, which answers on 80; the reply is un-NATed so the client only ever sees the host's address and port. Without -p there's no such rule, so even though the app is listening, nothing routes an external connection in — which is why "listening" and "published" are different things. A frequent real bug is the app binding to 127.0.0.1 inside the container, so the DNATed connection arriving on eth0 is refused even though publishing is correct.

DeepWhy do containers resolve each other by name on a user-defined network but not on the default bridge?

Because Docker only runs its embedded DNS server for user-defined networks. When a container is on a user-defined bridge, Docker sets its /etc/resolv.conf nameserver to 127.0.0.11, an embedded resolver that knows the names and current IPs of the other containers on that same network and forwards everything else upstream. On the default bridge network there's no embedded DNS — that's a deliberate legacy behaviour — so containers there are reachable by IP but not by name. The practical rule is to always put multi-container apps on a user-defined network, which is exactly what Compose does automatically. It matters because container IPs change across restarts, so name-based discovery is the only stable way for services to find each other, and it's the direct ancestor of cluster DNS in Kubernetes.

ScenarioA container's app works with curl localhost inside it, but you can't reach the published port from your laptop. Where do you look?

I split inside-versus-outside first. It works inside, so the app is fine; the break is in the path from the host into the container. I'd check three things fast: is the port actually published (is there a DNAT rule in iptables -t nat -S DOCKER)? What address did the app bind to — if it's 127.0.0.1 inside the container rather than 0.0.0.0, the forwarded connection arriving on eth0 gets refused, which perfectly matches "localhost works, published port doesn't." And is a host firewall dropping it ahead of Docker's chains? A quick tcpdump -ni docker0 port 80 while curling from the laptop tells me whether the packet even reaches the container. Nine times out of ten it's the bind address or a missing -p, not the application.

Follow-upHow is this different from Kubernetes pod networking?

The primitives are the same — each pod has a network namespace and a veth pair into the node — but the routing policy differs. Kubernetes mandates that every pod gets a cluster-routable IP and that any pod can reach any other pod without NAT, so the pod-to-pod path drops the source-NAT that Docker's bridge model uses; the CNI plugin routes pod IPs across nodes via an overlay, real-network routes, or native VPC IPs. NAT doesn't disappear entirely — egress to the internet is still masqueraded to the node, and Services add their own DNAT-style translation to a set of backend pods — but the flat, NAT-free pod address space is the defining change. And DNS moves from Docker's embedded 127.0.0.11 to cluster DNS (CoreDNS) resolving Service names. So it's the same building blocks with pod IPs promoted to first-class citizens.

The 10 things to remember

  1. A container's eth0 is one end of a veth pair; the other end is a host vethXXXX plugged into a bridge.
  2. The bridge (docker0) is a software layer-2 switch; same-bridge container-to-container traffic is direct, no NAT.
  3. Outbound traffic is SNAT/MASQUERADE'd to the host IP (POSTROUTING) so the private container IP never appears on the real network.
  4. -p 8080:80 installs a DNAT rule (the DOCKER chain) rewriting host :8080 to the container's :80, plus a docker-proxy.
  5. No -p means no inbound rule — an unpublished port is unreachable from the host even though the app listens.
  6. An app bound to 127.0.0.1 inside the container rejects the forwarded connection; bind 0.0.0.0 to be reachable.
  7. Embedded DNS at 127.0.0.11 resolves names on user-defined networks; the default bridge has no name resolution.
  8. Always put multi-container apps on a user-defined network (Compose does automatically) and reference by name, not IP.
  9. Put custom firewall rules in DOCKER-USER; it runs before Docker's chains and survives restarts.
  10. This bridge/veth/NAT/DNS model is the ancestor of the Kubernetes CNI — which keeps veth but makes pod IPs routable without NAT.
