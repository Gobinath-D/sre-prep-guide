Part III · Containers & Container Internals · Chapter 26

Docker, containerd, runc & the OCI model

"Docker" is not one program, and Kubernetes stopped using it years ago without most people noticing. Underneath sit a daemon, a runtime, a tiny spec-compliant launcher, and a set of open standards — and knowing which does what is the difference between guessing and debugging a node.

Start: Beginner→→→End: Staff-level ~45 min read · Docker + kind lab

By the end of this chapter you can

  • Explain the three OCI specs (image, runtime, distribution) and what a "bundle" is.
  • Describe how the kubelet talks to containerd over the CRI, and what the shim is for.
  • Explain the dockershim removal in Kubernetes 1.24 and what actually changed for operators.

Why this exists · the problemThe problem this stack solves

The first version of Docker was one big binary that did everything: a CLI, a daemon, image building, image storage, networking, and the low-level work of actually creating a container. That's fine for one laptop and a demo. It falls apart the moment other systems want to run containers too. Kubernetes doesn't want Docker's CLI or its build features or its opinions — it just wants to say "run this image with these limits" and get a container. Cloud providers want to swap the piece that talks to the kernel for a more isolated one. And nobody wants an image built by one tool to be un-runnable by another.

Two forces broke the monolith apart. The first is separation of concerns: the job of "manage images and container lifecycle for the whole node" is genuinely different from "make the syscalls that create one container," which is different again from "offer a friendly CLI to a developer." Splitting them lets each be replaced independently. The second is standards: if the image format, the way a container is described, and the registry protocol are all open specifications, then any tool that follows them interoperates. Those specifications are the OCI — the Open Container Initiative — and the split components are containerd and runc, which Docker itself donated to become the shared foundation everyone builds on.

So today "Docker" the product is a stack of layers over that shared foundation, and Kubernetes talks to the same foundation directly through a stable interface called the CRI, bypassing Docker entirely. Understanding the layers isn't trivia — when a node's containers won't start, the fault is in a specific layer, and you can't fix what you can't name.

Key point

The daemon (containerd) manages images and the lifecycle of many containers over the node's lifetime. The runtime (runc) creates one container — sets up its namespaces and cgroups, execs the process — and then exits. They're different jobs with different lifetimes, and confusing them is the root of most "how does a container actually start" confusion.

Mental model · analogyThe mental model: a restaurant kitchen

Real-world analogy

Think of running containers as a restaurant kitchen. The waiter (the docker CLI, or kubectl) takes your order in friendly language and passes it back. The head chef (containerd) runs the kitchen: keeps the pantry stocked (pulls and stores images), tracks every dish in progress, and decides what happens next — but the head chef doesn't personally cook every plate. For each dish, the head chef hands a precise, standardised recipe card (the OCI bundle) to a line cook (runc), who does the actual cooking for that one plate — assembles it exactly to spec — and then steps away. A runner (the shim) stays by the plate to keep it hot and report when it's done, so the head chef can go manage the rest of the kitchen without babysitting each plate.

The point of the recipe card is that it's a standard format. Any line cook who reads OCI recipe cards can cook the dish — you can swap a classic line cook (runc) for a faster one (crun) or an ultra-careful one who works behind glass (a sandboxed runtime) without changing the head chef or the waiter. And the pantry stores ingredients in a standard packaging (OCI images) so a dish prepped by one kitchen can be finished by another.

Kubernetes is a different waiter — the kubelet — who skips the Docker-branded front-of-house entirely and hands orders straight to the head chef through a standard order-ticket window: the CRI.

ArchitectureThe layers, top to bottom

Here's the whole stack in one figure. Follow a Kubernetes request down the left, and note where the Docker CLI path joins the same containerd:

Read the layers by what they own. dockerd owns the developer experience — docker build, the CLI API, Compose integration, Docker networking — and nothing on a Kubernetes node needs any of it. containerd owns node-level container management: pulling and storing images, unpacking layers via its snapshotter (overlayfs, from Chapter 24), and driving the lifecycle of every container. runc owns the actual creation of one container from a bundle. And the shim sits between containerd and each container so containerd can restart or be upgraded without killing running containers.

Internal workingFrom "run this image" to a live process

  1. The request arrives over the CRI. The kubelet decides a pod needs a container and makes a gRPC call — over a Unix socket like /run/containerd/containerd.sock — to containerd's CRI service. The CRI has two halves: a RuntimeService (pods and containers: create, start, stop, exec) and an ImageService (pull, list, remove images). This is a stable contract, so the kubelet doesn't care whether the other side is containerd or CRI-O.
  2. containerd ensures the image is present. If not already cached, it pulls the image per the OCI distribution spec: fetch the manifest, then the config and the layer blobs by digest, verifying each. The snapshotter unpacks the layers into the overlay directories that will become the container's lowerdir stack.
  3. containerd prepares an OCI bundle. It assembles a bundle: the root filesystem (the overlay mount) plus a config.json that is the OCI runtime spec for this container — which namespaces to create, which cgroup limits to apply, the mounts, the process to run, the user, the capabilities, the seccomp profile. This JSON is the precise recipe card.
  4. containerd starts a shim, which invokes runc. containerd launches a containerd-shim-runc-v2 process for the container, and the shim calls runc create/runc start against the bundle. Crucially, the shim is reparented to init (PID 1), not left as a child of containerd — so if containerd restarts, the shim and the container keep running and simply reconnect.
  5. runc creates the container and exits. runc does the low-level work you did by hand in Chapters 22–23: it clones into new namespaces, sets up the cgroup limits, pivots to the new root filesystem, applies seccomp and capabilities, and execs your process — which becomes PID 1 inside the container. Then runc exits. It's a short-lived launcher, not a supervisor. The shim is what remains as the container's parent, holding its stdio, reporting its exit status back to containerd, and keeping the container alive independent of containerd's lifetime.
  6. The process runs; the shim watches. Your workload is now a normal process on the host, isolated by namespaces and metered by cgroups. When it exits, the shim notices, reports the exit code up to containerd, and containerd tells the kubelet — which decides whether to restart it per the pod's policy.
Why a separate shim exists

Without a shim, every container would be a child of the containerd daemon, and restarting or upgrading containerd would orphan or kill every container on the node. The shim breaks that coupling: it's reparented to init and owns the container's stdio and exit reporting, so containerd becomes a stateless manager you can restart at will. This is the single design choice that makes "upgrade the runtime without downtime" possible, and it's why you see a containerd-shim-runc-v2 process per container — not per node.

Think first: you restart the containerd service on a node. Do the running containers die?

No — and the shim is why. Each container is held by its own containerd-shim-runc-v2 process, which is parented to init, not to containerd. When containerd stops, the shims (and therefore the containers) keep running; when containerd comes back, it reconnects to the existing shims and picks up managing them again. The exit codes and stdio that happened during the gap are buffered by the shim and reported once containerd returns. This is exactly what makes a runtime upgrade a non-event for workloads — contrast it with the old world, where the container process was tied to the daemon's lifetime. It's also why runc exiting immediately is fine: runc only creates the container; the shim, not runc, is the lasting parent.

ComponentsThe pieces and the tools that drive them

  • The OCI specifications — three of them. The image spec defines the on-disk/registry format: a manifest referencing a config (with the ordered layer diff_ids and build history) and content-addressed layer blobs. The runtime spec defines a bundle — a rootfs plus config.json — and what it means to run it. The distribution spec defines the registry pull/push API. Together they're why any compliant tool interoperates.
  • runc — the reference implementation of the runtime spec, built on libcontainer. Alternatives that read the same bundle: crun (a faster C implementation), gVisor's runsc (a userspace kernel for stronger isolation), and Kata Containers (each container in a lightweight VM). Swapping the runtime doesn't touch containerd or the kubelet — that's the whole point of the spec.
  • ctr — containerd's own low-level debug CLI. It exposes containerd concepts directly, including containerd namespaces (unrelated to kernel namespaces): Kubernetes containers live in the k8s.io namespace, Docker's in moby. Powerful, unpolished, no stability guarantees.
  • nerdctl — a Docker-compatible CLI for containerd. Same commands as docker (nerdctl run, nerdctl build) but talking to containerd directly, useful when there's no Docker daemon.
  • crictl — the CRI debugging CLI. It speaks the CRI to any compliant runtime, so it's the runtime-agnostic tool for inspecting pods and containers from a node's point of view — crictl ps, crictl images, crictl logs, crictl inspect. This is what you reach for when kubectl can't help because the problem is below the API server.

Data flowFollowing one pod start on a node

The scheduler binds a pod to a node; the kubelet sees it. The kubelet calls the CRI RunPodSandbox to create the pod's shared infrastructure (its network namespace and the "pause" container that holds it), then for each container it calls the ImageService to ensure the image is pulled and the RuntimeService to create and start the container. containerd fields those gRPC calls, unpacks image layers through its snapshotter into an overlay, writes the OCI config.json with the pod's namespaces and the container's cgroup limits, and starts a shim that runs runc against the bundle. runc builds the namespaces and cgroups, execs the app, and exits; the shim stays as parent. The app runs. When you later type kubectl logs, that request travels API server → kubelet → CRI → containerd → the shim, which has been capturing the container's stdout the whole time. Every hop is a named component doing its one job, and when logs are missing or a container is stuck in CreateContainerError, you now know exactly which hop to interrogate — which the labs do with crictl.

Think first: you built an image with docker build on your laptop. Can a node that runs only containerd — no Docker at all — pull and run it?

Yes, with no conversion. docker build produces an OCI-format image — a manifest, a config, and content-addressed layers — pushed to a registry over the OCI distribution API. containerd (or CRI-O, or any compliant runtime) pulls and runs that exact artefact, because the image format is a shared standard independent of whatever built it. This is precisely why removing dockershim didn't break anyone's images, and why "build with Docker, run with containerd" is the normal, correct state of the world rather than a contradiction. The build tool and the runtime are decoupled by the spec.

Lab 1Build — see the layers as processesBuild

Start a container with Docker and look at the process ancestry. The stack isn't a metaphor — it's real processes with a specific parent-child shape.

bash
docker run -d --name web nginx
# A helper that can see the whole host process tree:
docker run --rm --privileged --pid=host ubuntu:24.04 sh -c \
  'apt-get -qq update >/dev/null; apt-get -qq install -y procps >/dev/null
   ps -eo pid,ppid,comm --forest | grep -E "containerd|shim|nginx|dockerd" | grep -v grep'
Output (trimmed) PID PPID COMMAND 841 1 dockerd 902 1 containerd 1503 1 containerd-shim # parented to PID 1, NOT to containerd 1526 1503 \_ nginx # the container process, child of the shim 1560 1526 \_ nginx

Two things to notice. nginx's parent is the shim (containerd-shim-runc-v2), and the shim's parent is PID 1, not containerd — that reparenting is what lets containerd restart without touching nginx. And there's no runc in the tree: it already did its job (create the namespaces, exec nginx) and exited. dockerd and containerd sit as separate top-level daemons. This one ps makes the whole architecture concrete.

Lab 2Understand — crack open an OCI imageUnderstand

An image is a manifest pointing at a config and layers, all content-addressed. Export one and read its structure.

bash
docker pull alpine:3.20
docker save alpine:3.20 -o alpine.tar
mkdir img && tar -xf alpine.tar -C img
find img -maxdepth 2 -name '*.json' -o -name 'index.json' | head   # manifest/config/index
# Read the config: architecture, the layer diff_ids, and the build history:
cfg=$(find img -path '*blobs*' -type f | while read f; do grep -l '"rootfs"' "$f" 2>/dev/null; done | head -1)
cat "$cfg" | python3 -m json.tool | grep -A6 '"rootfs"'
Output (trimmed)"rootfs": { "type": "layers", "diff_ids": [ "sha256:d4fc045c9e3a848011de66f34b81f052d4f2c15a17bb196d637e526349601820" ] }

The config's rootfs.diff_ids is the ordered list of layer digests — the exact stack overlayfs will assemble at run time. The manifest ties this config to the layer blobs (each a sha256: file under blobs/), and the whole thing is content-addressed, so identical layers are shared and pulled once. This is the OCI image spec in the flesh: manifest → config → layers, all by digest. It's what a registry serves and what containerd unpacks.

Lab 3Understand — talk to containerd directly with ctr and crictlUnderstand

On the kind node (docker exec -it lab-control-plane bash), the Kubernetes containers are managed by containerd. Deploy something, then view it from two levels: the CRI (crictl) and containerd's own API (ctr).

bash
# From your Mac: create a workload
kubectl create deployment web --image=nginx
# On the node (docker exec ... bash), see it through the CRI:

ctr namespaces ls
ctr -n k8s.io containers ls | head
Output (trimmed)CONTAINER IMAGE STATE NAME POD 9f2a1c... docker.io/library/ Running web web-... NAME k8s.io CONTAINER IMAGE RUNTIME 9f2a1c... docker.io/library/nginx:latest io.containerd.runc.v2

crictl shows the CRI's abstraction — pods and containers, exactly what the kubelet sees. ctr -n k8s.io shows the same containers as containerd objects, in the k8s.io containerd namespace (a containerd concept, unrelated to the kernel namespaces of Chapter 22). Same container, two altitudes: crictl is the debugging tool you'll actually use, because it speaks the standard CRI and works the same on any node regardless of whether the runtime is containerd or CRI-O.

Lab 4Troubleshoot — debug a broken pod with crictlTroubleshoot

A pod is stuck and kubectl logs gives you nothing useful. On the node, crictl sees what the runtime sees. Break a pod on purpose, then investigate from the node before revealing.

bash
# From your Mac: a pod that references an image that doesn't exist
kubectl run bad --image=nginx:doesnotexist-9x9x
kubectl get pod bad          # stuck: ImagePullBackOff
# On the node — what does the runtime actually report?
crictl pods --name bad
crictl images | grep doesnotexist || echo "image not present on node"

The pod won't start. The API says ImagePullBackOff, but why exactly, and how would you confirm it's genuinely the image and not, say, the runtime or the network? Investigate from the node, then reveal.

Reveal the approach

Go down the stack until something tells you the truth. kubectl describe pod bad shows the events, and on the node crictl confirms the runtime's own view — the sandbox exists but the container image never pulled:

bash
crictl pods --name bad              # the pod sandbox is up (pause container)
crictl ps -a | grep bad || true     # no app container was ever created
# Ask containerd to pull it directly — the raw error, no Kubernetes in the way:
crictl pull nginx:doesnotexist-9x9x
OutputFATA[0002] pulling image: failed to resolve reference "docker.io/library/nginx:doesnotexist-9x9x": not found

That's the ground truth: the runtime tried and the tag doesn't exist in the registry. Now you know it's an image problem, not a runtime crash, not a CRI-socket problem, not a network partition — because you asked the layer that actually does the pull and got its unfiltered error. This is the core value of crictl on a node: when kubectl is too high-level (or the kubelet itself is unhealthy), you drop to the CRI and get the runtime's own answer. The same move diagnoses a wedged container (crictl inspect), missing logs (crictl logs), or a runtime that's down entirely (crictl info failing points at containerd, not your workload). This is the node-level troubleshooting you'll formalise in Chapter 40.

Lab 5Production challenge — the dockershim removalSenior challenge

A team upgrades a cluster to Kubernetes 1.24+ and their nodes — configured years ago to use "Docker" as the runtime — stop being able to run pods. First, confirm what your kind node actually uses, then reason about what happened to them.

bash
# From your Mac: which runtime is each node on?
kubectl get nodes -o wide      # see the CONTAINER-RUNTIME column
OutputNAME STATUS ... CONTAINER-RUNTIME lab-control-plane Ready ... containerd://1.7.x

Your node reports containerd://…, not Docker. The senior question: what was "dockershim," why was removing it in 1.24 mostly a non-event yet broke some clusters, and what should the affected team check and do? Reason it through before revealing.

Reveal the reasoning

What dockershim was: the kubelet couldn't speak Docker Engine's API through the CRI, so it shipped a built-in adapter — dockershim — that translated CRI calls into Docker Engine calls. It was extra code the Kubernetes project had to maintain for one specific runtime, while every other runtime already spoke the CRI natively. It was deprecated in 1.20 and removed in Kubernetes 1.24 (released May 2022).

Why removal was mostly a non-event: Docker Engine already uses containerd under the hood, and most clusters — and all managed offerings — were already configured with containerd or CRI-O as the CRI runtime directly. For them, nothing changed: the kubelet was never using dockershim. It also does not affect images: OCI images built by docker build run unchanged, because the image format is a shared standard.

Who broke and what to do: clusters where nodes were explicitly configured to use Docker Engine as the kubelet's runtime (via dockershim) lost their runtime on upgrade. The fix is one of: point the kubelet at containerd directly (which was already installed as Docker's own dependency) — the common path — or install cri-dockerd, the external CRI adapter for Docker Engine maintained by Mirantis, if they truly must keep Docker Engine. The check is exactly the command above: kubectl get nodes -o wide and the node's kubelet --container-runtime-endpoint. The lasting lesson is the one this whole chapter teaches: "Docker" was always several layers, Kubernetes only ever needed the bottom ones, and standardising on the CRI and containerd made the Docker-branded layers optional on a node. Building images with Docker and running them with containerd is not a contradiction — it's the OCI model working as designed.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · kubectl logs is empty but the app is clearly running

Symptom: kubectl logs returns nothing, yet the container is serving traffic. First cut: on the node, crictl ps to find the container ID, then crictl logs <id>. Usual cause: the app writes logs to a file inside the container instead of stdout/stderr — the shim only captures the standard streams, so file logs never reach the CRI or kubectl. Fix: log to stdout/stderr (twelve-factor style) or run a sidecar that tails the file. Knowing the shim is what captures stdio tells you immediately why file logs are invisible.

Incident pattern · node NotReady, kubelet can't reach the runtime

Symptom: a node goes NotReady; the kubelet log says it can't connect to the container runtime. First cut: on the node, crictl info or crictl ps — if these hang or fail, the problem is containerd, not any workload. Confirm: systemctl status containerd and the CRI socket path the kubelet is configured with. Usual cause: containerd crashed, is out of resources, or the socket path/endpoint is misconfigured. Fix: restart containerd (the shims keep the containers alive across the restart) and correct the endpoint. This is where "the daemon and the runtime are different things with different lifetimes" pays off.

Incident pattern · "works in Docker, fails in the cluster"

Symptom: an image runs under docker run but misbehaves as a pod. First cut: remember the runtimes differ only in a few places — the image is identical (OCI), so suspect what containerd/CRI configures differently: the cgroup driver (systemd vs cgroupfs mismatch causes odd resource behaviour), a stricter default seccomp/AppArmor profile, or a different logging path. Usual cause: a cgroup-driver mismatch between the kubelet and containerd, or the container relying on Docker-specific defaults. Fix: align the cgroup driver on both, and don't assume Docker's conveniences (its default network, its DNS behaviour) exist under the CRI.

Production · security · performanceWhat matters in production

Know your node's runtime, and don't install what you don't need. Production Kubernetes nodes run containerd (or CRI-O) and have no reason to run Docker Engine or the Docker CLI — fewer components mean less to patch and less attack surface. Keep the CRI socket path consistent between the kubelet and the runtime, and align the cgroup driver (use systemd on systemd hosts for both) or you'll get subtle resource-accounting bugs. When you build images, you can still use Docker or BuildKit locally; the resulting OCI image runs on any compliant runtime, which is the point of the standard.

Security. The runtime layer is where a lot of container hardening actually takes effect: the OCI config.json is where seccomp profiles, dropped capabilities, read-only root filesystems, and user mappings are set, and containerd/the kubelet populate it from your pod's securityContext. For workloads that need stronger isolation than shared-kernel namespaces provide, the pluggable-runtime design lets you run specific pods under gVisor or Kata via a RuntimeClass without changing anything else — the payoff of the OCI split. Verify and pin images by digest and use signature verification so the artefact the runtime pulls is the one you built (Chapter 27).

Performance and operations. containerd is designed to be restarted and upgraded without downtime because the shims keep containers alive — so runtime upgrades are routine, not scary. Image pull time dominates cold-start latency, so a good base-image and caching strategy (shared layers, a pull-through cache or registry mirror) matters more than the runtime's own overhead, which is small. For very high container density or fast-scaling workloads, some teams choose crun for lower per-container startup cost; measure before switching, since the difference is usually marginal for long-lived services.

System-design connectionWhere this reaches into architecture

The OCI split is a case study in designing for replaceability through standards, and it's worth internalising as a pattern, not just a fact about containers. By defining narrow, stable interfaces — the image format, the runtime bundle, the registry protocol, and the CRI — the ecosystem made every layer independently swappable: build with any tool, store in any registry, manage with containerd or CRI-O, and execute with runc, crun, gVisor, or Kata, all without the layers above caring. That's why Kubernetes could remove Docker without breaking a single image, and why you can drop a sandboxed runtime under one sensitive workload via RuntimeClass while everything else stays on runc. When you design platforms, this is the lever: a well-placed standard interface turns a monolith you're stuck with into components you can evolve. The CRI in particular is the seam that lets the control plane (Chapter 28) and the node runtime (Chapter 30) evolve on separate schedules — a decoupling you'll rely on every time you upgrade one without the other.

InterviewInterview questions & answers

Answer each in your head first, then open it.

30-secWhat's the difference between containerd and runc?

containerd is a daemon that manages the whole node's containers over time: it pulls and stores images, unpacks layers, and drives container lifecycle. runc is a low-level tool that creates one container from an OCI bundle — it sets up namespaces and cgroups, execs the process, and exits. So containerd is the long-lived manager and runc is the short-lived launcher. containerd calls runc (via a shim) to actually create each container.

2-minWalk me through what happens from a CRI call to a running container.

The kubelet makes a gRPC call over the CRI — a Unix socket — to containerd's CRI service, which has a RuntimeService for pods/containers and an ImageService for images. containerd ensures the image is pulled per the OCI distribution spec and unpacks its layers through the snapshotter into an overlay. It then assembles an OCI bundle: the root filesystem plus a config.json describing the namespaces, cgroup limits, mounts, user, capabilities, and seccomp for this container. containerd starts a containerd-shim-runc-v2 process — reparented to init so it outlives containerd — and the shim invokes runc, which creates the namespaces and cgroups, pivots root, applies security settings, execs the workload as PID 1 inside the container, and exits. The shim stays as the container's parent, owning its stdio and reporting its exit status back to containerd and up to the kubelet. The key ideas: the CRI is a stable seam, runc only creates and then exits, and the shim is what keeps the container independent of containerd's lifetime.

DeepWhat are the OCI specifications and why do they matter?

There are three. The image spec defines how an image is packaged — a manifest referencing a config (with the ordered layer digests and history) and content-addressed layer blobs — so any tool can build or read one. The runtime spec defines a bundle, which is a root filesystem plus a config.json describing exactly how to run a container (namespaces, cgroups, mounts, process, security), so any compliant runtime can execute it. The distribution spec defines the registry pull/push API. They matter because they turn the stack into swappable layers: you can build with Docker or BuildKit, store in any registry, manage with containerd or CRI-O, and execute with runc, crun, gVisor, or Kata, and everything interoperates. It's why Kubernetes removing Docker didn't break any images, and why you can run a sandboxed runtime under one workload without changing the rest. Standards are what made the monolith into components.

ScenarioA node is NotReady and pods won't schedule to it. kubectl logs and kubectl exec fail. How do you triage on the node?

I'd drop below Kubernetes to the runtime. On the node I'd run crictl info and crictl ps — if those hang or error, the container runtime itself is unhealthy, which explains the NotReady, and the workloads are a red herring. I'd check systemctl status containerd and the kubelet's configured CRI socket endpoint, and look at containerd and kubelet logs. If containerd crashed, restarting it is safe because the per-container shims keep the running containers alive and containerd reconnects to them. If crictl works fine but kubectl doesn't, the problem is higher up — the kubelet's connection to the API server, or certificates. The method is to walk the stack downward until a layer gives you an unfiltered error, and crictl is the tool that talks to the CRI directly regardless of which runtime is underneath.

Follow-upKubernetes "removed Docker" in 1.24 — what actually changed?

They removed dockershim, the kubelet's built-in adapter that translated CRI calls to Docker Engine's API. Docker Engine doesn't speak the CRI, so it needed that shim; every other runtime speaks CRI natively, and maintaining special-case code for one runtime wasn't worth it. For almost everyone it was a non-event, because clusters and managed platforms were already using containerd or CRI-O directly — and Docker Engine itself runs on containerd anyway. It did not affect images at all: OCI images built with docker build run unchanged, because the image format is a shared standard. The only people affected were those who'd explicitly configured nodes to use Docker Engine as the kubelet's runtime; they either repointed the kubelet at the containerd that was already installed, or added cri-dockerd, the external Docker CRI adapter. The headline "Kubernetes is dropping Docker" scared people, but the substance was just removing a redundant translation layer.

RetainQuick revision

"Docker" is a stack. The docker CLI drives dockerd, which owns build, the CLI API, and Docker networking, and delegates the actual container work to containerd. containerd is the node's container manager: it pulls and stores OCI images, unpacks layers via its snapshotter, and drives lifecycle. For each container it prepares an OCI bundle (rootfs + config.json) and starts a shim (containerd-shim-runc-v2, reparented to init) that invokes runc. runc is the OCI runtime that creates one container — namespaces, cgroups, pivot root, seccomp, exec — and then exits; the shim stays as the container's parent so containerd can restart without killing workloads. Kubernetes' kubelet skips Docker and calls containerd over the CRI (gRPC: RuntimeService + ImageService) on a Unix socket. The three OCI specs — image, runtime, distribution — make every layer swappable, which is why dockershim was removed in 1.24 without breaking images. Debug from the node with crictl (CRI, runtime-agnostic) and ctr (containerd-native, k8s.io namespace).

The 10 things to remember

  1. The stack: docker CLI → dockerd → containerd → shim → runc → container.
  2. containerd is the long-lived node manager (images, snapshots, lifecycle); runc is the short-lived launcher of one container.
  3. runc creates namespaces + cgroups, pivots root, applies seccomp/caps, execs the process, then exits.
  4. The shim (containerd-shim-runc-v2) is reparented to init and stays as the container's parent, so containerd can restart without killing containers.
  5. The kubelet talks to the runtime over the CRI — gRPC on a Unix socket, with a RuntimeService and an ImageService.
  6. Three OCI specs: image (manifest→config→layers), runtime (bundle = rootfs + config.json), distribution (registry API).
  7. runc is the reference OCI runtime; crun, gVisor's runsc, and Kata are drop-in alternatives selectable via RuntimeClass.
  8. dockershim was removed in Kubernetes 1.24; kubelet uses containerd/CRI-O directly, and cri-dockerd is the external adapter if you must keep Docker Engine.
  9. Images are unaffected by the runtime — an OCI image built by Docker runs on any compliant runtime.
  10. Debug on a node with crictl (CRI, works on any runtime) and ctr -n k8s.io (containerd-native); drop to them when kubectl can't see the problem.
