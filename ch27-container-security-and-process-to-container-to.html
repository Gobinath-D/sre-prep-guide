Part III · Containers & Container Internals · Chapter 27

Container security, and process → container → pod → VM

A container is a normal process wearing three restraints: namespaces decide what it can see, cgroups decide what it can use, and capabilities + seccomp decide what it can do. Loosen any one and the blast radius grows. This chapter is about where those dials sit and why.

Start: Beginner→→→End: Staff-level ~40 min read · Linux + Docker lab

By the end of this chapter you can

  • Place a process, a container, a pod, and a VM on the isolation spectrum — and say what each buys and costs.
  • Drop Linux capabilities to the minimum a workload needs, and name the two or three that actually let you own a host.
  • Write a seccomp profile that blocks a syscall, apply it, and recognise the EPERM it produces (the callback to Chapter 1).
  • Explain why a container escape is even possible — the shared-kernel attack surface — and name the doors people leave open.
  • Say what a pod really is at the namespace level, and why Kubernetes groups containers instead of running them alone.

Why this exists · the problemThe problem: isolation is a dial, not a wall

You already know from Chapter 21 that a container is just a Linux process the kernel has been told to view through a narrower lens. Here's the uncomfortable consequence: by default, that process is far less contained than people assume. Start a plain docker run as root and, out of the box, the process inside runs as UID 0, can still make almost every system call, and is one misconfiguration away from touching the host.

That's the whole tension of this chapter. Containers are cheap because they share the host's single kernel — no second operating system to boot, so they start in tens of milliseconds and cost almost nothing (revisit Chapter 1 if that isn't reflex yet). But "shares the kernel" also means the kernel is the only wall between a container and everything else on the box. If code in the container can reach a kernel bug, or you handed it a capability it didn't need, the wall has a door in it.

So the real question isn't "are containers secure?" — it's "how much of the kernel have I exposed to this workload, and what happens if it turns hostile?" Every feature in this chapter — capabilities, seccomp, user namespaces, read-only root filesystems — is a way to answer that with a smaller number. You are turning dials down until the workload can do its job and nothing more.

Key point

A VM's isolation is a property you get for free from the hardware and the hypervisor. A container's isolation is a property you configure. An unconfigured container is a process that happens to have its own hostname and filesystem — not a security boundary. Treat it like one only after you've set the dials.

Mental model · analogyThe mental model: rooms in a building vs a detached house

Here's the picture to carry through the rest of the Kubernetes chapters.

Real-world analogy

A VM is a detached house. It has its own foundation, its own plumbing, its own electrical panel — its own kernel. If the wiring in one house catches fire, the house next door is fine, because they share nothing but the street.

A container is a room in a large shared building. Every room shares the same plumbing and electrical risers — the host kernel. What makes a room yours is a set of controls the building manager installed: a lock on the door (namespaces — you can't see into other rooms), a metered fuse (cgroups — you can't draw more power than your allowance), and a tenancy agreement listing exactly which shared facilities you may touch (capabilities and seccomp). Weaken the agreement — hand a tenant a master key — and they can walk into the riser room and affect everyone.

A pod is a small suite of adjoining rooms rented together: the containers inside share one phone line and one mailbox (a single network namespace and IP, plus IPC), so they reach each other on localhost, but each keeps its own closet (its own filesystem). That's why you co-locate a sidecar with an app — same phone line, separate luggage.

ArchitectureThe isolation spectrum

Line the four options up from weakest isolation to strongest and the trade-off becomes obvious: the stronger the wall, the more it costs to build and the slower it is to put up.

Now the same four as a table an SRE actually reasons with. These numbers are order-of-magnitude, from a modern Linux host:

Why an SRE cares

This table is the whole "why do we still use VMs?" argument in one place. When you run many workloads you trust (your own microservices), containers give you the density and speed and you accept the shared kernel. When you run code you don't trust — arbitrary customer builds, CI jobs from the internet, a multi-tenant PaaS — the shared kernel is too big a bet, and you reach for a stronger wall: a microVM (Firecracker, Kata Containers) or a syscall-intercepting sandbox (gVisor). Same container image, different runtime, different blast radius.

Internal workingHow the kernel actually contains a process

When runc starts a container from its OCI config (the handoff you traced in Chapter 26), it applies the restraints in a deliberate order, then execves your program. Here's what it sets up, and what each part stops:

  1. Namespaces — change what the process can see. New PID, mount, network, UTS, IPC, and (optionally) user and cgroup namespaces. Inside, your process is PID 1, sees only its own filesystem and network interfaces, and can't even name the host's other processes. This is isolation of visibility, covered in Chapter 22 — it is not, by itself, a security control against a determined attacker.
  2. cgroups v2 — cap what the process can use. CPU, memory, IO, and PID limits (Chapter 23). Security-relevant because it stops one container from starving the host — a fork bomb hits the PID limit instead of taking down the node.
  3. Drop capabilities — shrink what "root" means. Since Linux 2.2, root's power is split into ~40 capabilities. A container's root keeps only a small default set (Docker/runc keep about 14, such as CAP_CHOWN, CAP_NET_BIND_SERVICE, CAP_SETUID) and drops the dangerous ones like CAP_SYS_ADMIN and CAP_SYS_MODULE. Kubernetes lets you drop the lot and add back only what you need.
  4. Install a seccomp filter — restrict which syscalls are even reachable. seccomp (secure computing) loads a small BPF program the kernel consults on every syscall. The default profile blocks around 40+ syscalls that a normal app never needs (e.g. mount, kexec_load, reboot, older keyring calls). A blocked call returns EPERM rather than doing the thing.
  5. Set no_new_privs — freeze privilege forever. The PR_SET_NO_NEW_PRIVS bit means execve can never grant more privilege — so a setuid binary inside the container can't suddenly become full root. In Kubernetes this is allowPrivilegeEscalation: false.
  6. Apply an LSM label — a second opinion from SELinux or AppArmor. The Linux Security Module hooks let SELinux (Red Hat) or AppArmor (Ubuntu) enforce mandatory rules on files and operations, independent of Unix permissions. Distro-default container profiles use these.
  7. pivot_root into the image, often read-only. The process's root becomes the container's overlay filesystem (Chapter 24). Mount it read-only and the running process can't modify its own binaries — so an attacker who lands code execution can't drop a persistent implant on disk.
  8. Optionally, a user namespace — map container-root to a nobody on the host. With a user namespace, UID 0 inside the container maps to an unprivileged high UID (say 100000) on the host. Now "root in the container" owns nothing on the host. This is the difference between rootful and rootless containers.

Read that list as layers of defence, not alternatives. Namespaces hide the neighbours; capabilities and seccomp shrink the API the process can reach; no_new_privs and read-only rootfs stop escalation and persistence; a user namespace makes even a full breakout land on a powerless UID. Miss one layer and the others still hold — that's the point of stacking them.

Think first: a coworker says "we run everything as non-root, so capabilities don't matter." Are they right?

No — the two are different axes. User/UID is who you are; capabilities are what powers you hold. A process can run as a non-root UID and still be granted, say, CAP_NET_RAW or CAP_SYS_ADMIN via the container's capability set or a file capability — and that capability is what actually lets it sniff traffic or mount filesystems, not its UID. Conversely, root inside a container with all capabilities dropped is surprisingly powerless. Running as non-root is good hygiene, but you still drop capabilities explicitly. Belt and braces.

ComponentsThe security pieces, named

You'll say these names constantly once you're on a platform team. Each owns one narrow thing:

  • Capabilities — the split-up powers of root. The ones that effectively are host root: CAP_SYS_ADMIN (mount, many privileged ops — the "new root"), CAP_SYS_MODULE (load a kernel module = arbitrary kernel code), CAP_SYS_PTRACE, CAP_DAC_OVERRIDE (ignore file permissions), and CAP_NET_ADMIN/CAP_NET_RAW for the network. If you grant one, know exactly why.
  • seccomp — a per-process BPF syscall filter. Actions per rule: SCMP_ACT_ALLOW, SCMP_ACT_ERRNO (return an error, usually EPERM), SCMP_ACT_LOG (allow but log — great for profiling), and SCMP_ACT_KILL. Kubernetes exposes three profile types: RuntimeDefault, Localhost (your own file), and Unconfined.
  • User namespaces — the UID/GID remapping that makes rootless containers possible. Container UID 0 → host UID 100000+. A breakout lands on an unprivileged host user.
  • LSMs (SELinux / AppArmor) — mandatory access control layered on top of Unix permissions and capabilities. The distro default profile is usually enough; custom profiles are for hardened multi-tenant platforms.
  • The pause (infra) container — a tiny, do-nothing container that owns a pod's network and IPC namespaces. App containers join its namespaces. It exists so the pod's IP survives an app container crashing and restarting. This is the mechanical reason a pod, not a container, is Kubernetes' smallest unit.
  • PodSecurity Admission — the Kubernetes controller (built in since 1.25, replacing the removed PodSecurityPolicy) that enforces the Privileged / Baseline / Restricted standards per namespace by label. It's how a cluster says "no privileged pods here" and means it.
Legacy warning

If a tutorial tells you to write a PodSecurityPolicy (PSP), stop — PSP was deprecated in 1.21 and removed in 1.25. The current mechanism is Pod Security Admission (namespace labels selecting the Baseline or Restricted profile) for the built-in rules, plus a policy engine like Kyverno or the Validating Admission Policy API for anything custom. We build on this in Chapter 39.

Data flowFollowing one syscall from inside a locked-down container

Put it together with a single call. Your app inside a hardened container calls mount() — maybe a library is trying to remount something. Watch every gate it hits:

  1. The process issues the mount syscall — the trap from Chapter 1, ring 3 → ring 0.
  2. seccomp runs first. The kernel consults the container's BPF filter before executing anything. If mount is set to SCMP_ACT_ERRNO, the kernel returns -EPERM immediately — the syscall never reaches the mount code at all.
  3. If seccomp allows it, the kernel checks capabilities: mount needs CAP_SYS_ADMIN. A default container dropped it, so the mount code itself returns -EPERM.
  4. libc turns the negative return into -1 and sets errno = EPERM. Your app sees "Operation not permitted."

Two independent layers each said no, and the failure looks identical from user space: EPERM. That's why, when you debug this, you have to check both — which syscall, and which layer blocked it. We do exactly that in the labs.

Think first: root inside a container with every capability dropped and seccomp on — how much can it really do?

Far less than the word "root" suggests. UID 0 with an empty capability set can't mount filesystems, can't load kernel modules, can't change most system settings, and can't override file permissions it wasn't granted — those powers are capabilities, and they're gone. seccomp has narrowed the reachable syscall table on top of that, and namespaces mean the process can't even see the host's other processes or interfaces. What's left dangerous is a kernel bug it can reach through an allowed syscall, or a capability someone added back "to make it work." So the honest answer: mostly harmless as configured, and exactly as dangerous as the widest capability or syscall you left open — which is why hardening is about shrinking that surface, not about the UID alone.

Hands-onLabs — build, understand, break, troubleshoot

You're on a Mac, so use a throwaway Linux container as your lab bench, same as Chapter 1. Everything below runs on the host's Docker (Docker Desktop's Linux VM is fine). Start here:

bash
# A disposable box with the tools we need for capability decoding.
docker run --rm -it ubuntu:24.04 bash
apt-get update && apt-get install -y libcap2-bin strace
Lab 1Build — see what your container is actually allowed to doBuild

Every process advertises its capabilities and seccomp mode in /proc. Look at PID 1 inside a default container:

bash
grep -E 'CapEff|Seccomp' /proc/1/status
capsh --decode=$(grep CapEff /proc/1/status | awk '{print $2}')
Output (default docker run)CapEff: 00000000a80425fb Seccomp: 2 0x00000000a80425fb=cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill, cap_setgid,cap_setuid,cap_setpcap,cap_net_bind_service,cap_net_raw, cap_sys_chroot,cap_mknod,cap_audit_write,cap_setfcap

Read that. Seccomp: 2 means mode 2 — a BPF filter is loaded (the Docker default profile). And CapEff decodes to the ~14 capabilities runc keeps by default. Notice what's not there: no cap_sys_admin, no cap_sys_module, no cap_net_admin. The runtime already dropped the truly dangerous ones for you. Now compare with a privileged container — run this from your Mac host, not inside the box:

bash
docker run --rm --privileged ubuntu:24.04 \
  sh -c 'grep -E "CapEff|Seccomp" /proc/1/status'
Output (--privileged)CapEff: 000001ffffffffff Seccomp: 0

CapEff is now all-ones — every capability — and Seccomp: 0 means no filter at all. A privileged container is a process with full root powers and an unfiltered syscall table, sharing your kernel. It is root on the host with extra steps. This is the single most abused flag in container land.

Lab 2Understand — bind port 80 as non-root by keeping one capabilityUnderstand

Capabilities let you grant exactly one power instead of all of root. The classic case: binding a port below 1024 needs CAP_NET_BIND_SERVICE and nothing else. Prove it. First, drop everything and try:

bash
docker run --rm --user 1000 --cap-drop=ALL python:3.12-alpine \
  python3 -c 'import socket; s=socket.socket(); s.bind(("0.0.0.0",80))'
OutputPermissionError: [Errno 13] Permission denied

That's EACCES — a non-root user with no capabilities can't touch a privileged port. Now add back the one capability that authorises it, still as a non-root user:

bash
docker run --rm --user 1000 --cap-drop=ALL \
  --cap-add=NET_BIND_SERVICE python:3.12-alpine \
  python3 -c 'import socket; s=socket.socket(); s.bind(("0.0.0.0",80)); print("bound :80 as UID 1000")'
Outputbound :80 as UID 1000

That's the model in one command: drop ALL, add back the minimum. In Kubernetes this is a three-line securityContext, and it's the difference between "our web pod runs as root because port 80" and "our web pod runs as UID 1000 with exactly one capability." The second one is a much smaller thing to hand an attacker.

Lab 3Break — block a syscall with seccomp and watch EPERMBreak

This is the direct callback to Chapter 1. Write a seccomp profile that allows everything except mkdir, then watch the kernel refuse it. Create the profile on your Mac host:

json
// no-mkdir.json — default-allow, but errno on mkdir/mkdirat
{
  "defaultAction": "SCMP_ACT_ALLOW",
  "syscalls": [
    { "names": ["mkdir", "mkdirat"], "action": "SCMP_ACT_ERRNO", "errnoRet": 1 }
  ]
}

errnoRet: 1 is EPERM. Apply it and try to make a directory:

bash
docker run --rm --security-opt seccomp=no-mkdir.json ubuntu:24.04 \
  sh -c 'mkdir /tmp/x'
Outputmkdir: cannot create directory '/tmp/x': Operation not permitted

"Operation not permitted" is EPERM — errno 1 — exactly what the profile told the kernel to return. Confirm it's seccomp and not permissions by tracing the syscall (needs --cap-add=SYS_PTRACE):

bash
docker run --rm --cap-add=SYS_PTRACE --security-opt seccomp=no-mkdir.json ubuntu:24.04 \
  sh -c 'apt-get install -y strace >/dev/null 2>&1; strace -f mkdir /tmp/x 2>&1 | grep mkdir'
Outputmkdirat(AT_FDCWD, "/tmp/x", 0777) = -1 EPERM (Operation not permitted)

The syscall returned before doing any work — the kernel consulted the filter and bounced it. This is precisely the incident pattern Chapter 1 promised: an unusual syscall failing with EPERM inside a container means a seccomp profile, not a file-permission problem.

Lab 4Troubleshoot — "works on the VM, EPERM in the container"Troubleshoot

Here's the real-world version. A team upgrades a base image; the app now crashes on start inside Kubernetes with EPERM, but runs fine on a plain VM. You're handed the pod. Reproduce the shape locally — a program that calls a syscall a strict profile forgot to allow:

bash
# A profile that allows only a tiny set — realistic of an over-tight custom profile.
cat > tight.json <<'EOF'
{ "defaultAction": "SCMP_ACT_ERRNO", "architectures": ["SCMP_ARCH_X86_64"],
  "syscalls": [ { "names":
    ["read","write","exit","exit_group","brk","mmap","munmap","rt_sigreturn",
     "execve","arch_prctl","access","openat","close","fstat","newfstatat"],
    "action": "SCMP_ACT_ALLOW" } ] }
EOF
docker run --rm --security-opt seccomp=tight.json ubuntu:24.04 sh -c 'echo hi; getcwd 2>/dev/null; ls /'
Outputhi sh: 1: ls: Operation not permitted # or the container dies before printing

Something fails with EPERM, but which syscall? Don't guess. The senior move is to make seccomp tell you instead of blocking. Think about how before you open the answer.

Reveal the approach

Flip the default action to log, not error, so every disallowed syscall is recorded but still runs — then read the kernel's audit log to see exactly what the app needs:

bash
# Temporarily: defaultAction SCMP_ACT_LOG instead of SCMP_ACT_ERRNO.
# On the host, disallowed calls now appear in the audit / kernel log:
journalctl -k | grep -i seccomp | tail
# or watch the container's own strace, as in Lab 3.

You'll see the culprit — commonly statx, faccessat2, clone3, or getrandom: newer syscalls that a modern glibc started using after a base-image bump, which an old hand-written profile never listed. The fix is almost never "disable seccomp." It's "add the missing syscall to the profile," or better, switch to the RuntimeDefault profile, which is maintained to track glibc. This exact class of bug — clone3 under an old Docker seccomp profile — broke countless Alpine and Ubuntu 21.10+ images in the wild.

Lab 5Production challenge — try to break out, and see why you can'tSenior challenge

The best way to trust a boundary is to push on it. First, confirm a locked-down container can't reach the host. Try to see host processes and to mount something:

bash
docker run --rm --cap-drop=ALL ubuntu:24.04 sh -c '
  ps -e | wc -l;                 # how many processes can I even see?
  mount -t proc proc /mnt 2>&1'   # can I mount?
Output2 # only my own process tree — PID namespace mount: permission denied # no CAP_SYS_ADMIN — EPERM

The PID namespace hides the host's hundreds of processes (you see 2), and mounting fails for lack of CAP_SYS_ADMIN. Both walls hold. Now the senior question: given a container that does escape, which misconfigurations opened the door — and how would you spot them in a running cluster before an attacker does?

Reveal the escape surface

Real container escapes almost always ride one of a short list of gifts, not a novel kernel 0-day:

  • --privileged / privileged: true — all caps, no seccomp, host devices. From here you can mount the host disk and chroot into it. Game over.
  • The Docker/containerd socket mounted in (/var/run/docker.sock as a volume) — the container can now ask the daemon to start a new privileged container mounting the host root. A very common CI footgun.
  • hostPath volumes, hostPID, hostNetwork — each punches a specific hole from pod to node.
  • CAP_SYS_ADMIN or CAP_SYS_MODULE granted "to make it work" — the former is effectively root; the latter loads kernel code.
  • An unpatched kernel — the shared kernel means a bug like Dirty Pipe (CVE-2022-0847) is exploitable from inside any container on that host.

How you find them: enforce Pod Security Admission (Restricted) on namespaces so the API server rejects privileged/hostPath pods at admission time, and audit with kubectl get pods -A -o jsonpath for securityContext.privileged and volumes.hostPath. Patch nodes on a schedule. For genuinely untrusted workloads, don't rely on getting the dials perfect — run them under gVisor or in a Kata microVM so a breakout hits a sandbox, not your node.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · EPERM after a base-image or runtime bump

Symptom: a workload that ran for a year starts crash-looping right after an image or containerd upgrade, logging "Operation not permitted" on startup. First cut: kubectl logs the crash, then reproduce with strace to find the failing syscall. Confirm: check the pod's seccompProfile and the node's runtime version. Usual cause: a newer libc uses a syscall (clone3, faccessat2, statx) that an old hand-rolled seccomp profile doesn't list. Fix: move to RuntimeDefault or add the syscall — never blanket-Unconfined.

Incident pattern · the read-only rootfs surprise

Symptom: you set readOnlyRootFilesystem: true for hardening and the app dies writing to /tmp, /var/run, or a cache dir. Cause: plenty of apps write scratch data to the root filesystem. Fix: keep the rootfs read-only and mount an emptyDir at each writable path. This is a good change — it just needs the writable paths declared, which is itself documentation of what the app touches.

Incident pattern · "it works because it's privileged"

Symptom: a chart or DaemonSet only works with privileged: true, so someone ships it that way. Why it's an incident waiting to happen: that pod is root on the node; a supply-chain compromise of that image compromises every node it lands on. Fix: find the one capability or mount it actually needs (often CAP_NET_ADMIN for a CNI agent, or a specific host path) and grant only that. "Privileged" is almost always laziness standing in for "I didn't find the specific permission."

Production · security · performanceWhat matters in production

The baseline every workload should meet. Run as a non-root UID (runAsNonRoot: true, runAsUser: 1000); drop all capabilities and add back only the handful you proved you need; set allowPrivilegeEscalation: false; set seccompProfile: { type: RuntimeDefault } (as of recent Kubernetes the kubelet can even default this cluster-wide); mount the root filesystem read-only with emptyDirs for scratch. Those five lines of securityContext turn a "process with a hostname" into something that resembles a security boundary, and they cost nothing at runtime — seccomp filtering adds a few nanoseconds per syscall, which is lost in the noise for any real app.

Enforce it, don't hope for it. Individual securityContext blocks are opt-in; developers forget them. Pod Security Admission set to Restricted on a namespace makes the API server reject any pod that isn't hardened, so the guarantee is structural rather than aspirational. Add Kyverno or Validating Admission Policy for rules PSA doesn't cover (registry allow-lists, required labels).

When namespaces aren't enough. The shared kernel is a real bet. For multi-tenant platforms running untrusted code — CI runners taking pull requests from strangers, a customer-code PaaS, notebook-as-a-service — assume a container will be broken out of and put a second wall behind it: gVisor (a user-space kernel that intercepts the container's syscalls, so most never reach the host kernel) or a microVM (Kata / Firecracker — a real guest kernel that boots in ~125 ms, close to container speed but with VM-grade isolation). You select these per workload with a Kubernetes RuntimeClass.

The user-namespace frontier. Mapping container-root to an unprivileged host UID (hostUsers: false on the pod, a graduating feature) is the cleanest fix for the "root in the container" problem: even a full breakout lands on a UID that owns nothing. It's worth turning on where your kernel and runtime support it, especially for anything you don't fully trust.

Common mistakes that put teams in the incident channel: reaching for --privileged instead of finding the one capability needed; mounting the Docker socket into a CI container; leaving seccomp: Unconfined because an old profile broke once; treating a bare container as equivalent to a VM for untrusted code; and never patching node kernels, which quietly re-arms every published container-escape CVE.

System-design connectionWhere this reaches into architecture

This chapter is where "how isolated is it?" becomes a design input rather than an afterthought. When you architect a multi-tenant system, the first question is the trust boundary: are tenants separated by application logic (one process, tenant IDs in the query — cheap, one bug leaks everyone), by container (namespaces + seccomp — good for tenants you mostly trust), by pod/node (a node per tenant — coarse but simple), or by VM/microVM (hardware isolation — for untrusted or regulated workloads)? Each step up the isolation spectrum trades density and speed for a smaller blast radius, and that trade is the heart of the design. The same reasoning drives the "cell" and "shuffle-sharding" patterns you'll meet in Chapter 95 and reliability engineering in Chapter 88: contain failure and compromise to the smallest unit you can afford. And it's the reason serverless platforms (AWS Lambda, Fargate) run each tenant's code in a Firecracker microVM rather than a shared-kernel container — at that trust boundary, the VM tax is the price of admission.

InterviewInterview questions & answers

Answer each in your head before you open it.

30-secWhat's the fundamental security difference between a container and a VM?

A VM ships its own guest kernel behind a hypervisor, so the isolation is hardware-enforced and an attacker has to break the hypervisor to escape. A container is a process sharing the host's single kernel; its isolation is a stack of kernel features — namespaces, cgroups, dropped capabilities, seccomp — that you configure. So a container is cheaper and faster (no second kernel to boot) but its wall is the host kernel itself: a kernel bug or an over-broad capability reaches the host. Trust the workload and use containers; don't trust it and add a VM-grade wall.

2-minWalk me through hardening a pod's securityContext from scratch.

I start from "deny everything, add back the minimum." Set runAsNonRoot: true and a specific runAsUser so the process isn't UID 0. Set allowPrivilegeEscalation: false so a setuid binary can't regain privilege — that's no_new_privs under the hood. Drop all capabilities with capabilities.drop: ["ALL"] and add back only what I've proven is needed, e.g. NET_BIND_SERVICE for a low port. Set seccompProfile.type: RuntimeDefault so the maintained syscall filter is on. Make the root filesystem read-only and mount emptyDirs at the paths the app writes to. Then I enforce it at the namespace with Pod Security Admission set to Restricted, so nothing un-hardened even schedules. The theme is that UID, capabilities, and syscalls are three separate axes and I tighten all three, rather than assuming non-root alone is safe.

DeepA syscall returns EPERM inside a container but works on a bare host. How do you find out why?

EPERM from inside a container has two likely sources and they look identical from user space, so I isolate which layer said no. First I strace the process to name the exact failing syscall — say mount or clone3. Then: is it a capability problem or a seccomp problem? I check /proc/<pid>/status — CapEff tells me the effective capabilities, and Seccomp: 2 tells me a filter is loaded. If the syscall needs a capability the container dropped (mount needs CAP_SYS_ADMIN), that's the cause. If the capability is present but the call is still refused, it's the seccomp profile — I confirm by temporarily switching the profile's default action to SCMP_ACT_LOG and reading the audit log, which prints every disallowed call without blocking it. The classic case is a base-image bump where new glibc calls clone3, which an old profile never allowed; the fix is RuntimeDefault or adding the syscall, not disabling seccomp.

ScenarioA vendor's Helm chart requires privileged: true. What do you do?

I treat that as a red flag, not a requirement, because a privileged pod is root on every node it runs on. First I find out why it wants privilege — usually one specific need: a host path, CAP_NET_ADMIN for networking, or a device. I reproduce it with strace/logs and try to replace privileged with the narrow grant: a single added capability, a specific hostPath, or a device plugin. If it genuinely needs broad host access (some storage or CNI agents do), I scope the blast radius instead: pin it to dedicated nodes with taints, restrict its ServiceAccount RBAC to nothing extra, and keep those nodes patched. If it's untrusted, I push back on adopting it at all, or run it under a RuntimeClass that uses a microVM. What I don't do is ship privileged cluster-wide because the chart's default said so.

Follow-upWhy is a pod the smallest unit in Kubernetes, and not a container?

Because a pod is the natural grouping for containers that must share a fate and a network identity. Mechanically, a pod is a set of containers that share a network namespace and IPC — held open by a tiny "pause" container — so they see each other on localhost and share one IP, while keeping separate filesystems. That's exactly what you want for an app plus a sidecar (a proxy, a log shipper): same network endpoint, deployed and scheduled as one unit, but independent images and restarts. Scheduling and lifecycle operate on the pod because these containers only make sense together. It also means the security boundary you tune — capabilities, seccomp — largely applies per container within the pod, but the network trust boundary is the pod: everything in it trusts everything else on localhost.

RetainQuick revision

A container is a process on the shared host kernel, contained by dials you set: namespaces (what it sees), cgroups (what it uses), capabilities (which of root's powers it keeps), and seccomp (which syscalls it can even make). Turn those dials down — drop all caps and add back the minimum, run non-root, forbid privilege escalation, load RuntimeDefault seccomp, make the rootfs read-only — and enforce it with Pod Security Admission (never the removed PodSecurityPolicy). The isolation spectrum runs process → container → pod → VM: each step shrinks blast radius and adds overhead and boot time. A pod groups containers so they share a network namespace and IP via the pause container. When you can't trust the workload, don't perfect the dials — put a VM-grade wall behind it with gVisor or a microVM. And a mysterious EPERM inside a container is a capability or a seccomp filter talking — check /proc/<pid>/status to learn which.

The 10 things to remember

  1. A container's isolation is configured, not inherent; an unconfigured container is not a security boundary.
  2. Isolation spectrum: process < container < pod < VM. Stronger wall = more overhead + slower boot + smaller blast radius.
  3. Containers and pods share the one host kernel; a VM has its own kernel behind a hypervisor. That's the core difference.
  4. Capabilities split root into ~40 powers. Drop ALL, add back the minimum. CAP_SYS_ADMIN ≈ root on the host.
  5. seccomp filters syscalls; a blocked call returns EPERM. Prefer RuntimeDefault over hand-rolled profiles.
  6. allowPrivilegeEscalation: false sets no_new_privs; read-only rootfs + emptyDir stops on-disk persistence.
  7. User namespaces map container-root to an unprivileged host UID, so a breakout lands powerless.
  8. --privileged = all caps + no seccomp + host devices. It is the most abused, most dangerous setting.
  9. A pod shares one network + IPC namespace (held by the pause container), which is why it's the smallest unit.
  10. Enforce hardening with Pod Security Admission (Restricted); for untrusted code use gVisor or a microVM via RuntimeClass.
