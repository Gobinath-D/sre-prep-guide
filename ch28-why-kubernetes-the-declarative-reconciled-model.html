Part IV · Kubernetes — Architecture & Internals · Chapter 28

Why Kubernetes: the declarative, reconciled model

You stop telling the system what to do and start telling it what you want. Then something runs forever, comparing what you asked for against what's real, and quietly closing the gap. Grasp that one shift and the other twelve chapters of Kubernetes become variations on a theme.

Start: Beginner→→→End: Staff-level ~35 min read · kind (Kubernetes-in-Docker)

By the end of this chapter you can

  • State the orchestration problem plainly — the thing scripts and docker run can't solve past a handful of nodes.
  • Explain imperative vs declarative, and desired state vs observed state, without hand-waving.
  • Describe level-triggered reconciliation and why it self-heals where an edge-triggered script wouldn't.
  • Read any Kubernetes object as spec (what you want) and status (what is), and know who owns each.
  • Prove it on a real cluster: apply a Deployment, delete a pod and watch it return, scale and watch it converge.

Why this exists · the problemThe orchestration problem

Parts I–III got you to a container: a process, isolated by the kernel, that you can start with one command. On one laptop that's the whole story. Now scale it up to a real system and count the jobs.

You have 40 microservices. Each runs several replicas for capacity and redundancy. They live on 30 machines. A node dies at 03:00 — who notices, and who starts its containers somewhere else? A container segfaults — who restarts it, and how many times before giving up? You push a new version — who rolls it out replica by replica, checks each one is healthy, and rolls back if not, all without dropping traffic? Traffic doubles at lunchtime — who adds replicas, and where's the room? A replica moved to a new node and got a new IP — who tells everything that talks to it?

You can script all of this. People did, for years — Bash, Ansible, a home-grown scheduler, a spreadsheet of which service runs where. It works until it doesn't: the script assumes a starting state that drifted, a node was down when the script ran so it's now missing a replica forever, two engineers run the script at once and fight. The scripts describe steps, and steps assume the world hasn't changed since you last looked. In a system with 30 nodes and constant churn, the world always changed.

Key point

Orchestration is not "start these containers." It's keep these containers running the way I asked, forever, while the world keeps breaking underneath them. That "forever, despite failures" part is what a pile of scripts can't give you and what Kubernetes is built to give you — through one idea, reconciliation, applied everywhere.

Mental model · analogyThe mental model: a thermostat, not a light switch

The shift is from imperative ("do this sequence of actions") to declarative ("here is the state I want; you figure out the actions"). The cleanest way to feel the difference is heating.

Real-world analogy

An imperative heater is a switch: you flip it on, it runs, you flip it off. If you leave the room, or a window opens, or you fall asleep, the switch doesn't care — it does exactly what you last told it, which is now wrong. To keep the room comfortable you have to keep coming back and flipping the switch. That's docker run and a cron job.

A thermostat is declarative. You set one number — 21°C, the desired state. From then on the thermostat runs a loop forever: read the actual temperature (the observed state), compare it to 21, and act to close the gap — heat if it's cold, rest if it's warm. Open a window and the room cools; the thermostat notices and heats more. You never told it "turn on for ten minutes." You told it the goal, and it continuously drives reality toward the goal.

Kubernetes is a thermostat for your infrastructure. You declare "3 replicas of this image, this much memory, reachable on this name." Controllers run the loop forever: observe what's actually running, compare to what you declared, and create, delete, or replace pods until the two match — then keep watching, because the world will drift again.

The mapping is exact:

In the analogyIn Kubernetes
The number you dial in (21°C)The spec — your declared desired state
The thermometer readingThe status — the observed actual state
The thermostat's forever-loopA controller's reconcile loop
"Heat until it matches, then rest"Create/delete/update objects until status = spec

Thermostat re-heats without youThe controller reschedules the pod — self-healing

ArchitectureThe reconcile loop, drawn

Everything Kubernetes does is this one loop, run by dozens of controllers over dozens of object types. Learn it once here; you'll recognise it in every later chapter.

And the object it operates on always has the same shape. Every Kubernetes API object — a Pod, a Deployment, a Service, a Node — carries four parts:

  • apiVersion + kind — which type and which version of its schema (e.g. apps/v1, Deployment).
  • metadata — name, namespace, labels, annotations, and the ownerReferences that link objects into a tree.
  • spec — the desired state. You write this.
  • status — the observed state. A controller writes this; you read it.

That's the entire mental model: objects with a spec and a status, and loops that push status toward spec. Deployment, StatefulSet, Job, Ingress, even a Node — same shape, same loop, different nouns.

Internal workingLevel-triggered reconciliation, and why it self-heals

The word that makes reconciliation hold up under a messy world is level-triggered. It's borrowed from electronics, and the distinction is the whole reason Kubernetes survives the messiness of real infrastructure.

  • Edge-triggered logic reacts to events — the transitions. "A pod was deleted → create a replacement." If you miss the event (your controller was restarting, the message was dropped), the action never happens and the system is permanently wrong.
  • Level-triggered logic reacts to state — the current level. "Whenever I run, I count the pods; if there are fewer than desired, I create the difference." It doesn't matter how the world got here or whether I saw the event that changed it. I look at what is, compare to what should be, and act.

A controller's reconcile function is level-triggered. Stripped to its essence it's this:

go
// The shape of every controller, from ReplicaSet to a custom operator.
for {
    desired  := readSpec(object)         // what you asked for
    observed := listRealWorld(cluster)   // what is actually there, right now
    if !equal(desired, observed) {
        act(diff(desired, observed))     // create/delete/update to close the gap
    }
    // then wait for a change notification, or a periodic resync, and loop
}

Now watch why this self-heals. Say you want 3 replicas and a node dies, taking one pod with it:

  1. The pod on the dead node stops reporting; eventually its record is removed. Observed replicas drop to 2.
  2. The ReplicaSet controller reconciles: desired is 3, observed is 2, diff is +1. It creates one new pod object.
  3. The scheduler places the new pod on a healthy node; a kubelet there starts it. Observed climbs back to 3.
  4. The controller reconciles again, sees 3 = 3, and does nothing. Equilibrium — until the next disturbance.

Nobody handled a "node died" event with bespoke logic. The controller just kept asking "do I have 3?" and the answer drove the action. That's why you can kill a Kubernetes controller mid-operation, restart it, and it picks up correctly: on start it re-observes the whole world and reconciles from the current level. An edge-triggered script that crashed between "detect" and "act" would have lost the work. This is also why the API stores desired state durably in etcd (the dial on the wall) — restart the entire control plane and the goal is still there to reconcile toward.

Think first: you run kubectl delete pod on a pod that belongs to a Deployment. What happens, and why?

A new pod appears within seconds. You changed the observed world (one fewer pod), but you didn't change the desired state — the Deployment still says "3 replicas," and it owns a ReplicaSet that says the same. On the next reconcile the ReplicaSet controller counts 2, wants 3, and creates one. To actually reduce the count you have to change the desired state: kubectl scale deployment ... --replicas=2, or edit the YAML. Deleting the pod fought the symptom; the controller restored the declared goal. First-timers find this maddening ("why won't it stay deleted?!"); it's the system working exactly as designed.

ComponentsThe pieces of the declarative model

We meet the concrete control-plane binaries in Chapter 29. Here, keep it conceptual:

  • The API object — a typed record with spec and status. The unit of desired state. Everything you do is create, read, update, or delete one of these.
  • The API server — the single front door. Every read and write goes through it; it validates objects and persists them. It is the only thing that talks to etcd, and the only source of truth other components consult.
  • etcd — the durable store behind the API server. Your desired state lives here, so it survives restarts.
  • Controllers — the loops. Each watches a kind of object and reconciles it: the Deployment controller manages ReplicaSets, the ReplicaSet controller manages Pods, the Node controller watches node health, and so on.
  • Labels & selectors — the loose coupling that makes it all compose. A ReplicaSet doesn't hold pointers to its pods; it has a label selector (app=web) and owns whatever pods match. A Service routes to whatever pods match its selector. Sets, not lists — which is exactly why the model tolerates pods coming and going.
  • kubectl apply — your side of the contract. It sends a desired-state document to the API server. It is declarative: run it twice and the second time is a no-op, because you're describing an end state, not issuing commands.
Think first: you run the exact same kubectl apply -f web.yaml a second time. What happens?

Effectively nothing — and that's the point. apply sends your desired state and the API server reconciles the stored object toward it; the second time the live object already matches the file, so the diff is empty and no controller has a gap to close. That idempotency is why apply is safe to run in a loop, safe to re-run in CI after a half-failed deploy, and safe for a GitOps controller to re-apply every few minutes. Contrast imperative kubectl create, which errors the second time because the object already exists — it describes an action, not a state, so repeating it is not a no-op.

Data flowFollowing one kubectl apply end to end

Watch a single kubectl apply -f deployment.yaml (3 replicas) ripple through the system. Notice that no single component does much — each just reconciles its own object and hands off by writing state:

  1. kubectl → API server. Your YAML becomes an HTTP request. The API server authenticates you, validates the Deployment, and writes it to etcd. Desired state now exists. Your command returns — the work has barely started.
  2. Deployment controller reconciles. It sees a Deployment with no matching ReplicaSet at the right version. Diff: create a ReplicaSet (also desired-state, 3 replicas). It writes that to the API server.
  3. ReplicaSet controller reconciles. It sees a ReplicaSet wanting 3 pods and 0 existing that match its selector. Diff: +3. It creates 3 Pod objects — but with no node assigned yet.
  4. Scheduler reconciles. It watches for pods with no node. For each, it picks a node that fits and writes the choice back (spec.nodeName). Still just updating desired state — nothing is running yet.
  5. kubelet reconciles. Each node's kubelet watches for pods assigned to it. It sees its new pods, calls the container runtime to pull images and start containers, and reports back by writing status.
  6. Status flows up. Pod status → ReplicaSet status → Deployment status. When all three pods report Ready, the Deployment's status shows 3/3. The loops fall quiet until something drifts.

Every arrow in that chain is one component writing desired state to the API server and another component watching for it and reconciling. There's no central conductor issuing orders. It's a chain of thermostats, each closing its own small gap. That decoupling is why the whole thing keeps working when any one piece restarts.

Lab 1Build — declare a Deployment and watch it happenBuild

Write desired state, apply it, and see the machinery produce pods you never explicitly created:

bash
cat > web.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: web
          image: nginx:1.27-alpine
EOF
kubectl apply -f web.yaml
kubectl get deploy,replicaset,pods -l app=web
Outputdeployment.apps/web READY 3/3 UP-TO-DATE 3 AVAILABLE 3 replicaset.apps/web-6f9c7 DESIRED 3 CURRENT 3 READY 3 pod/web-6f9c7-2xk4p Running pod/web-6f9c7-8mtq9 Running pod/web-6f9c7-lz7vd Running

You declared one Deployment. It created a ReplicaSet, which created three Pods, which the scheduler placed and the kubelet started. You issued zero run commands. That's the declarative model doing the imperative work for you — and the chain of ownership (Deployment → ReplicaSet → Pods) is exactly the flow from the last section.

Lab 2Understand — read spec vs status on a live objectUnderstand

The whole model is spec (yours) and status (the controller's). See both on the running Deployment:

bash
kubectl get deploy web -o yaml | grep -A4 '^spec:'
echo '---'
kubectl get deploy web -o yaml | grep -A6 '^status:'
Output (trimmed)spec: replicas: 3 # <- YOU wrote this: desired ... --- status: availableReplicas: 3 # <- the CONTROLLER wrote this: observed readyReplicas: 3 observedGeneration: 1

You own everything under spec; you never write status — the controller does, as its report of reality. kubectl explain deploy.spec and kubectl explain deploy.status document each field, and every object type follows this split. Internalising "spec is my intent, status is the system's observation" is 80% of learning to read Kubernetes.

Lab 3Break — delete a pod and watch reconciliation winBreak

Fight the controller and lose. In one terminal, watch the pods live:

bash
kubectl get pods -l app=web --watch

In another, delete one:

bash
kubectl delete pod -l app=web --field-selector … 2>/dev/null; \
kubectl delete pod $(kubectl get pod -l app=web -o name | head -1)
Output (the --watch terminal)web-6f9c7-2xk4p Terminating web-6f9c7-pv8sd Pending web-6f9c7-pv8sd ContainerCreating web-6f9c7-pv8sd Running # a replacement, within ~2s

You removed a pod (changed observed state to 2). The ReplicaSet controller wants 3, saw 2, and created one. You did not ask for a replacement — the declared desired state did. This is self-healing in four seconds, and it's the exact mechanism that survives a node dying at 3am: nobody's awake, but the loop is.

Lab 4Troubleshoot — scale up, then jam the loop with a bad imageTroubleshoot

First, change desired state the right way and watch convergence:

bash
kubectl scale deployment web --replicas=5
kubectl get deploy web -w   # READY climbs 3/5 → 5/5

Now break it. Point the Deployment at an image tag that doesn't exist and watch what the loop does — and doesn't do:

bash
kubectl set image deployment/web web=nginx:does-not-exist
kubectl get pods -l app=web
Outputweb-6f9c7-... Running # old replicas: still up web-7d2aa-... ImagePullBackOff # new replica: can't start

The Deployment is stuck at partial readiness. Why doesn't the whole app go down, and why won't it "just work"? Reason about it before revealing.

Reveal what the loop is doing

Two things, both by design. First, the rolling update is level-triggered and safety-gated: the Deployment won't kill healthy old pods until new ones become Ready, and the new ones never do (the image can't be pulled), so it holds — your old version keeps serving. Second, the reconcile loop doesn't give up; it keeps retrying the pull with backoff (ImagePullBackOff), because desired state still says "run this image." The status tells you the truth:

bash
kubectl describe pod -l app=web | grep -A3 Events
kubectl rollout status deployment/web   # reports it's not progressing

The fix is to change desired state to something achievable — kubectl rollout undo deployment/web (back to the good image) or set a valid tag. The lesson: a "stuck" Kubernetes object is usually a desired state that can't be met. Read status and events; they say why the gap won't close. The loop is fine — the goal was impossible.

Lab 5Production challenge — imperative edits and the drift they causeSenior challenge

This is the trap that bites teams moving to GitOps. Mix an imperative command with a declarative file and predict who wins. You still have web.yaml declaring replicas: 3. Run:

bash
kubectl scale deployment web --replicas=10   # imperative: bump live to 10
kubectl get deploy web                        # READY 10/10
kubectl apply -f web.yaml                      # re-apply the file that says 3
kubectl get deploy web

What's the replica count after the apply? And what does this tell you about running kubectl scale by hand in a repo-driven cluster? Decide, then check.

Reveal the answer and the lesson

It goes back to 3. kubectl apply sends the file's desired state, and the file says replicas: 3, so the API server records 3 and the controller scales down. Your imperative scale to 10 was overwritten — the file is the source of truth for the fields it sets. (Server-side apply tracks field ownership, but the principle holds: whoever last declared the field owns it.)

This is configuration drift, and it's why platform teams forbid manual kubectl edit/scale on anything managed by a repo. In GitOps (Chapter 64, Chapter 65) a controller like Argo CD continuously re-applies the git state, so your 3am hotfix via kubectl silently reverts on the next sync — and you're paged again, baffled. The mindset to keep: the declared source of truth wins, always. If you must change something, change the declaration. Clean up: kind delete cluster --name lab.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · "I fixed it manually and it undid itself"

Symptom: an on-call engineer edits a live object (scales up, patches an env var) and it works — then minutes to hours later the change vanishes and the alert returns. Cause: a controller (a Deployment, or Argo CD in a GitOps setup) is reconciling toward a declared state that doesn't include the manual change, so it reverts it. Fix: make the change where desired state lives — the git repo or the YAML — not on the live object. The manual edit was always going to lose.

Incident pattern · a Deployment that won't progress

Symptom: kubectl rollout status hangs; READY sits at, say, 2/3 for a long time. First cut: kubectl get pods and kubectl describe the unhealthy one; read Events. Usual causes: an image that can't be pulled (ImagePullBackOff), a pod that can't be scheduled (no node fits — see Chapter 29), a failing readiness probe, or a crash loop. The point: the loop isn't broken — it's telling you, via status and Events, that the desired state can't currently be reached. Believe the status.

Production · security · performanceWhat matters in production

Declare everything; command nothing. The production discipline that follows from this chapter is: your cluster's desired state lives in files, in version control, and reaches the cluster through kubectl apply or a GitOps controller — never through a person typing imperative commands against production. That gives you a reviewable history, a rollback (revert the commit), and a single source of truth. Imperative commands (kubectl run, kubectl scale, kubectl edit) are for exploration on scratch clusters and emergencies, and even then you go back and encode the fix in the declaration.

Idempotency is the property you're buying. Because apply describes an end state, applying the same manifest ten times leaves the cluster identical to applying it once. That's what makes CI/CD pipelines safe to re-run and controllers safe to restart. When you write your own automation against Kubernetes, preserve this: converge to a state, don't fire off one-shot actions.

Watch out for the fields you don't own. A common mistake is setting replicas in a manifest while also running the Horizontal Pod Autoscaler, which also writes replicas — now two controllers fight over the same field and the count flaps. The rule: exactly one owner per field. Server-side apply and leaving autoscaled fields out of your manifest are how you avoid the tug-of-war.

The mindset shift is the real deliverable. Every question in Kubernetes has the same answer shape: "what's the desired state, what's the observed state, and which controller closes the gap?" Debugging becomes "read spec, read status, read the controller's events." Once that's reflex, the thirteen chapters ahead are the same idea with more nouns.

System-design connectionWhere this reaches into architecture

Reconciliation is not a Kubernetes quirk — it's a general pattern for building systems that survive partial failure, and you'll see it everywhere once you have the eye for it. Terraform reconciles cloud resources toward a declared state (Chapter 62). Argo CD reconciles a cluster toward a git repo (Chapter 65). A database's replication reconciles replicas toward the primary. The common thread is store desired state durably, observe actual state continuously, and drive the gap to zero with idempotent actions — which beats a script of steps precisely because it doesn't assume the world held still. When you design a control system of your own — a job scheduler, a certificate rotator, an autoscaler — reach for a level-triggered loop over event handlers, and you inherit the same self-healing and restart-safety. It's also the deep reason Kubernetes scales operationally: humans declare intent, and a swarm of small loops does the relentless, error-prone work of keeping reality in line.

InterviewInterview questions & answers

Answer each in your head before opening it.

30-secWhat does "declarative" mean in Kubernetes, versus imperative?

Imperative is a sequence of commands — "start this container, then that one" — where you own the steps and they assume the world hasn't changed. Declarative means you submit the desired end state — "I want 3 replicas of this image" — and controllers continuously make reality match it. You describe the goal, not the path. The payoff is self-healing and idempotency: apply the same manifest repeatedly and you always land in the same state, and if reality drifts (a node dies), the system converges back on its own.

2-minExplain the reconciliation loop and level-triggered logic.

A controller runs a loop forever: read the desired state from the object's spec, observe the actual state of the world, and if they differ, take idempotent actions to close the gap — then wait for a change or a resync and do it again. It's level-triggered, meaning it acts on the current state ("do I have 3 pods?") rather than on events ("a pod was deleted"). That matters because events can be missed — the controller might have been restarting — but the level is always re-observable. So the loop shrugs off crashes and dropped notifications: on startup it re-lists the world and reconciles from whatever it finds. Concretely, if a node dies and a pod vanishes, the ReplicaSet controller just notices observed is 2 against desired 3 and creates one; nobody wrote "handle node death" logic. Desired state is stored durably in etcd, so even a full control-plane restart resumes reconciling toward the same goal.

DeepWhy is level-triggered more resilient than edge-triggered for orchestration?

Edge-triggered logic reacts to transitions, so correctness depends on observing every transition exactly once. In a distributed system that's a bad bet: watch connections drop, controllers restart, events coalesce or arrive out of order. Miss one edge and an edge-triggered system is permanently inconsistent, because nothing will re-fire the event. Level-triggered logic instead reads the full current state each pass and computes the diff, so a missed notification only delays convergence until the next observation — it never corrupts it. Kubernetes leans into this: informers deliver change events as an optimisation to avoid constant polling, but the reconcile always reads the current state from a cache and acts on that, and a periodic resync re-drives everything even if no events arrive. So events are a hint about when to reconcile; the what always comes from observed level versus desired level. That's why you can kill and restart any controller and it self-corrects. We'll see the machinery — watch, informer, work queue — in Chapter 31.

ScenarioA teammate deletes a pod to "restart" a service and it keeps coming back. What's going on?

They're changing observed state without changing desired state. The pod belongs to a ReplicaSet (via a Deployment) whose spec still says N replicas, so on the next reconcile the controller counts one short and recreates it — that's the system working. Deleting a managed pod is a valid way to force a single restart (you get a fresh pod), but it won't reduce the count or stop the service. To actually take it down you change the declaration: scale the Deployment to 0, or delete the Deployment (which garbage-collects its ReplicaSet and pods via ownerReferences). The teaching point is that in Kubernetes you steer by editing desired state, not by fighting the live objects the controllers own.

Follow-upWhere does the desired state actually live, and why does that matter?

It lives in etcd, behind the API server — the only component that reads and writes etcd. That matters for two reasons. First, durability: because desired state is persisted, the whole control plane can restart and every controller resumes reconciling toward the same goal; nothing is lost. Second, single source of truth: every component gets its picture of "what should be" from the API server, so there's no disagreement about intent. In practice, the operational source of truth sits one level up — your git repo of manifests — and something (kubectl apply or Argo CD) keeps etcd in sync with git. But within the cluster, etcd is the durable dial on the wall that reconciliation reads. Chapter 29 is where we open up etcd and the API server.

RetainQuick revision

The orchestration problem is keeping many containers running as declared, forever, while nodes and processes fail underneath — something imperative scripts can't do because steps assume a world that already changed. Kubernetes solves it by being declarative: you write desired state (an object's spec), and controllers run reconcile loops that observe actual state (status) and act to close the gap. The loops are level-triggered — they act on current state, not on events — so they self-heal, survive restarts, and are idempotent. Every object shares the shape apiVersion/kind/metadata/spec/status; you own spec, controllers own status. Delete a managed pod and it returns, because desired state didn't change. A "stuck" object is a desired state that can't be met — read status and events to learn why. The whole discipline is: declare in version control, apply, let the loops do the work, and never fix production by hand.

The 10 things to remember

  1. Orchestration = keep containers running as declared, forever, through failure. Scripts of steps can't do that.
  2. Imperative says "do these actions"; declarative says "here's the state I want" and lets the system find the actions.
  3. Every object has a spec (desired, yours) and a status (observed, the controller's).
  4. A controller runs a reconcile loop forever: read spec, observe status, act to close the gap, repeat.
  5. Reconciliation is level-triggered — it acts on current state, so missed events only delay, never corrupt.
  6. That's why it self-heals: a node dies, observed drops, the loop recreates — with no bespoke event handler.
  7. Desired state is stored durably in etcd behind the API server, so the control plane can restart and resume.
  8. Labels + selectors couple objects as sets, not lists, so pods can come and go without breaking references.
  9. kubectl apply is idempotent: applying twice equals applying once, because you describe an end state.
  10. A "stuck" object usually means an impossible desired state; read status and Events — the loop isn't broken.
