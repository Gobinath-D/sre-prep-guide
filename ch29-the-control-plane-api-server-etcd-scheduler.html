Part IV · Kubernetes — Architecture & Internals · Chapter 29

The control plane: API server, etcd, scheduler, controller manager

Every kubectl command, every controller, every kubelet talks to one door — the API server — which checks you, stamps your object, and files it in etcd. That request path, and the consensus store behind it, are where a cluster is fast, slow, consistent, or wedged. This is the chapter that turns "the control plane is having issues" into a diagnosis.

Start: Beginner→→→End: Staff-level ~50 min read · kind + etcdctl/crictl

By the end of this chapter you can

  • Trace a write through the API server: authentication → authorization → admission → validation → etcd.
  • Explain etcd as the source of truth — Raft, quorum, why an odd number of members, and the 8 GB/latency limits that bite.
  • Describe how the scheduler picks a node (filter, then score) and how it commits the choice.
  • Say what the controller manager is, and why control-plane downtime doesn't stop running pods.
  • Back up and reason about restoring etcd, and recognise API-server throttling (Priority & Fairness / 429s) under load.

Why this exists · the problemSomething has to be the brain — and the ledger

Chapter 28 gave you the model: desired state in, controllers reconcile toward it. But that hand-waved two hard questions. Where does desired state actually live so that it survives a machine dying — and stays consistent when three controllers and two admins all write at once? And who enforces that only the right people can change it, and that what they submit is even valid?

Those are the two jobs of the control plane. It needs a ledger — a single, durable, strongly-consistent record of what should be true — and it needs a door in front of that ledger that authenticates callers, authorizes them, validates their objects, and writes them safely. Get the ledger wrong and two clients disagree about reality, or a crash loses your cluster's entire configuration. Get the door wrong and anyone can do anything, or garbage objects poison the loops.

There's a payoff for learning this precisely. The control plane is where the confusing production symptoms live: "kubectl is slow," "my apply got a 429," "the cluster stopped scheduling but the apps are fine," "we lost an etcd node." Each of those maps to a specific part of the request path or the store. Vague knowledge here means you guess during incidents. Precise knowledge means you look in the right place first.

Key point

Two facts to anchor everything: the API server is the only component that talks to etcd — every other part of Kubernetes reads and writes state through the API server, never the store directly. And the control plane is separate from the data plane — if the whole control plane goes down, pods already running keep running and serving traffic; you just can't schedule, scale, or self-heal until it's back. Hold both.

Mental model · analogyThe mental model: a land registry office

The control plane behaves like the office that keeps a country's official property records — a job that is all about one authoritative record and strict rules for changing it.

Real-world analogy

You want to register a change of ownership. You go to the front counter (the API server). The clerk first checks your ID (authentication — are you who you say?), then checks you're permitted to file this kind of change (authorization — is this your property?). They make sure the form is filled in correctly and stamp on any mandatory clauses (admission and validation — defaults, policy, schema). Only then do they enter it into the official register.

The register itself is kept in a vault by a panel of notaries (etcd). No single notary can declare something official; a majority must agree and co-sign every entry (Raft quorum) before it counts. That's deliberately strict: it means one notary being off sick can't corrupt or lose the record, and two clerks filing at once can't create two conflicting truths.

Elsewhere in the building, an assignments officer (the scheduler) watches for newly-registered requests that need a desk and picks a suitable one. And a room of standing-order clerks (the controller manager) each hold one instruction — "there must always be three copies of this on file" — and keep acting until the register matches. The key detail: all of them work by reading and writing at the front counter. None of them is allowed into the vault directly.

ArchitectureThe request path, and who talks to whom

Here is the whole control plane in one picture: a write enters the API server, runs a gauntlet, lands in etcd; and the scheduler and controllers watch and write through the API server, never touching the store.

Internal workingThe request path, etcd, and the scheduler in depth

Three things deserve real depth: what the API server does to a request, what makes etcd trustworthy, and how the scheduler decides. Take them in turn.

1 · The API server gauntlet

When any client sends a write — say POST /apis/apps/v1/namespaces/default/deployments — the request passes through fixed stages, and a failure at any stage returns before touching the store:

  1. TLS + Authentication. The connection is mutual-TLS or bearer-token. The API server runs its authenticators in turn — client certificate, ServiceAccount token, OIDC — until one identifies you as a username plus a set of groups. No match → 401 Unauthorized. The API server does not manage users; it trusts an external identity source.
  2. Authorization. Given (user, groups, verb, resource, namespace), the authorizers decide allow/deny. In practice this is RBAC: does a Role/ClusterRole bound to you permit create deployments in this namespace? The Node authorizer scopes what kubelets can touch; a webhook authorizer can defer to an external service. No allow → 403 Forbidden.
  3. Mutating admission. Now the object can be changed. Built-in plugins and your MutatingWebhookConfigurations run — they inject sidecars (a service mesh does this), set defaults, add labels. This is the last chance to rewrite the object.
  4. Schema validation & defaulting. The object is checked against the resource's OpenAPI schema and built-in validation, and unset fields get their defaults. Malformed object → 422.
  5. Validating admission. Plugins and ValidatingWebhookConfigurations (and the newer CEL-based ValidatingAdmissionPolicy) get a yes/no vote — they can reject but not modify. This is where Pod Security Admission, ResourceQuota, and your policy engine (Kyverno/Gatekeeper) say "no, that pod is privileged" and return 403.
  6. Persist to etcd. The accepted object is serialized (protobuf, not JSON, for built-in types) and written to etcd under a key like /registry/deployments/default/web. etcd replicates it to a quorum before acknowledging. Secrets are encrypted at rest here if you configured an EncryptionConfiguration.
  7. Notify watchers. The write bumps a global resourceVersion. Everyone with an open watch on deployments — the Deployment controller, your dashboards — receives the change and reconciles. No polling; this is push.

That order is worth memorising because it tells you where a request died. A 401 is identity; a 403 is either RBAC (authz) or a policy webhook (validating admission) — and you distinguish them by the message. A 422 is a bad object. A timeout deep in the path often means a slow admission webhook or a slow etcd.

Think first: your kubectl apply comes back 403 Forbidden. How do you tell an RBAC denial from a policy-webhook rejection?

Both are 403 but from different stages, and the message tells them apart. An authorization (RBAC) denial reads like "User \"x\" cannot create resource \"deployments\" in namespace \"y\"" — you were stopped before admission ever ran, so the fix is a Role/RoleBinding granting that verb on that resource. A validating admission rejection happens later and names a policy: Pod Security says the pod "violates PodSecurity \"restricted\"", or a webhook like Kyverno/Gatekeeper names its own rule. That fix is to make the object comply, or change the policy. So read the message — "cannot <verb> <resource>" is RBAC; anything naming a policy or a webhook is admission — and confirm the RBAC half in isolation with kubectl auth can-i.

2 · etcd: why you can trust the ledger

etcd is a distributed key-value store that uses the Raft consensus algorithm to keep replicas identical. The essentials an SRE must hold:

  • One leader, N members, majority commit. Writes go to the leader, which appends to its log and replicates to followers; the entry is committed only once a quorum — (N/2)+1 members — has persisted it. So a 3-member cluster needs 2 to agree and tolerates losing 1; a 5-member cluster needs 3 and tolerates losing 2.
  • Odd numbers only. 3 tolerates 1 failure; 4 also tolerates only 1 (quorum is 3) while adding a member that can fail — so 4 is strictly worse than 3. Run 3 or 5, never 4 or 6.
  • Lose quorum, lose writes. If 2 of 3 members are down, there's no majority: etcd goes read-only-ish and the API server can't commit writes. The control plane freezes — but, again, running pods keep running.
  • MVCC + watch. etcd keeps a revision history (multi-version concurrency control) and streams changes via watch from a given revision. That's exactly what powers Kubernetes watches and the resourceVersion you saw above.
  • It is brutally disk-latency sensitive. Every commit does an fsync of the write-ahead log. Put etcd on slow or network-attached disks and fsync latency climbs, Raft heartbeats miss, leaders flap, and the whole API server feels slow. etcd wants fast local SSD/NVMe. This is the single most common self-inflicted etcd wound.
  • The size ceiling. etcd's default storage quota is 2 GiB; you can raise it, but the recommended maximum is 8 GB. Cross the quota and etcd raises a NOSPACE alarm and refuses writes until you compact old revisions, defragment, and disarm the alarm. Big clusters and objects that churn a lot (Events, huge ConfigMaps/Secrets) push toward this.
Think first: your 3-node etcd cluster loses one node to a disk failure. Is the cluster still writable? What if it loses two?

One down: yes, still writable. Quorum for 3 is 2, and 2 remain, so the leader can still get a majority to commit. You're now running without redundancy — a second loss is fatal — so you replace the member urgently, but there's no outage. Two down: no. Only 1 of 3 remains, which can't form a majority, so no writes commit and the API server can't persist changes. Reads may still serve from cache, and — say it with me — running pods keep running, but you can't schedule, scale, or change anything until you restore quorum (bring a member back, or restore from a snapshot and re-form the cluster). This is exactly why 3 or 5 members across failure domains matters, and why you keep tested snapshots.

3 · The scheduler: filter, then score, then bind

The scheduler's whole job is to turn a pod with no node into a pod with a node. It watches for pods where spec.nodeName is empty and, for each, runs the scheduling framework's two phases:

  1. Filter (feasibility). Walk the nodes and drop any that can't run this pod: not enough allocatable CPU/memory, a taint the pod doesn't tolerate, a nodeSelector/nodeAffinity that doesn't match, a volume whose topology pins it elsewhere, node not Ready. What survives is the set of feasible nodes. If that set is empty, the pod stays Pending and the scheduler emits a FailedScheduling event saying which predicate eliminated the nodes.
  2. Score (ranking). Give each feasible node a score from plugins: spread pods of the same app across nodes/zones, prefer least-allocated (or most-allocated, for bin-packing), honour pod affinity/anti-affinity and topology spread. Sum the weighted scores; the highest wins (ties broken randomly to avoid hot-spotting).
  3. Bind. The scheduler commits its choice by writing a Binding — effectively setting spec.nodeName — via the API server. It does not start anything. The kubelet on the chosen node is watching, sees a pod assigned to it, and takes over (that's Chapter 30).

Notice the scheduler only decides and records; it never places a container. And it's a normal API client — it watches and writes through the API server like everything else. Swap it out for a custom scheduler and nothing else in the system needs to know.

4 · The controller manager

kube-controller-manager is a single binary that runs dozens of the built-in reconcile loops from Chapter 28 — Deployment, ReplicaSet, Node lifecycle, Job, ServiceAccount, EndpointSlice, and more — each watching its object type through the API server. In an HA control plane you run several replicas, but only one is active at a time: they use leader election (a Lease object) so exactly one instance runs the loops and the others stand by. Same pattern for the scheduler. That's how you get redundancy without two schedulers double-booking a node.

ComponentsThe control-plane binaries, named

  • kube-apiserver — the front door and the only etcd client. Stateless, so you scale it horizontally behind a load balancer; all cluster state is in etcd, not in the API server. Hosts the REST API, authn/authz/admission, and API Priority & Fairness.
  • etcd — the stateful, Raft-replicated key-value store holding all cluster state under /registry/.... The one thing you must back up and must give fast disks. Runs as 3 or 5 members.
  • kube-scheduler — assigns Pending pods to nodes via filter/score/bind. Leader-elected in HA.
  • kube-controller-manager — bundles the core controllers; leader-elected in HA.
  • cloud-controller-manager — the loops that talk to a cloud provider: label nodes, wire up LoadBalancer Services to real load balancers, manage routes. Split out so the core stays cloud-agnostic (this is where EKS/GKE plug in — Part VI).
Where these actually run

On a kubeadm or kind cluster, the four core components run as static pods — the kubelet starts them directly from manifests in /etc/kubernetes/manifests, without the scheduler, because you can't schedule the scheduler. That's why they appear in kube-system but with the node name appended (etcd-lab-control-plane). Managed control planes (EKS, GKE) hide all of this and run it for you — you never see the API-server or etcd pods, which is exactly the point of "managed."

Data flowFollowing one pod from apply to bound

Chapter 28 traced the flow conceptually; now watch the same events land on real components and etcd revisions. You kubectl apply a Deployment (3 replicas):

  1. kubectl opens HTTPS to the API server, authenticates with your kubeconfig cert/token, and POSTs the Deployment. The gauntlet runs; RBAC allows it; admission passes; the object is written to etcd at a new resourceVersion. kubectl returns.
  2. The Deployment controller (in the controller manager), watching deployments, receives the create event and reconciles: it creates a ReplicaSet — another POST through the API server, another etcd write.
  3. The ReplicaSet controller receives its watch event and creates 3 Pod objects, each with spec.nodeName empty. Three more etcd writes.
  4. The scheduler, watching for unassigned pods, wakes for each: filters to feasible nodes, scores them, and POSTs a Binding — setting nodeName. Still no container anywhere; just an etcd update per pod.
  5. Each target node's kubelet, watching for pods bound to it, sees its pod and starts the containers via the runtime, then PATCHes pod status back through the API server (Chapter 30 opens this up).
  6. Status flows up the ownership chain to the Deployment's status. Every arrow here was an API-server call that became an etcd revision — which is why you can literally watch it with kubectl -v=8.

Lab 4Break — create a pod that can't schedule, and read whyBreak / Troubleshoot

Make the scheduler fail on purpose, then diagnose it the way you would in production. Ask for more CPU than any node has:

bash
kubectl run greedy --image=nginx:1.27-alpine \
  --overrides='{"spec":{"containers":[{"name":"greedy","image":"nginx:1.27-alpine","resources":{"requests":{"cpu":"500"}}}]}}'
kubectl get pod greedy
OutputNAME READY STATUS RESTARTS AGE greedy 0/1 Pending 0 15s

It's stuck Pending. Before revealing, ask: which stage is this — did the write fail, or is it something after? Where would the reason be recorded?

Reveal the diagnosis

The write succeeded — the Pod object exists in etcd — so this isn't authn/authz/admission. It's after persistence: the scheduler filtered every node out (none has 500 cores) and left the pod unbound. The scheduler records exactly that as an Event:

bash
kubectl describe pod greedy | sed -n '/Events/,$p'
# or cluster-wide:
kubectl get events --field-selector reason=FailedScheduling
OutputEvents: Warning FailedScheduling default-scheduler 0/1 nodes are available: 1 Insufficient cpu. preemption: 0/1 nodes are available: 1 No preemption victims found.

"Insufficient cpu" names the failing filter. In a real cluster the same message reads "3 Insufficient memory, 2 node(s) had untolerated taint {...}, 1 node(s) didn't match nodeSelector" — a per-predicate tally telling you precisely why each node was rejected. The fix follows from the message: lower the request, add capacity, tolerate the taint, or relax affinity. Clean up: kubectl delete pod greedy.

Lab 5Production challenge — API-server throttling and Priority & FairnessSenior challenge

When a client hammers the API server, Kubernetes doesn't fall over — it throttles, via API Priority & Fairness (APF). Look at the machinery, then reason about an incident. First, the objects that govern it:

bash
kubectl get flowschemas
kubectl get prioritylevelconfigurations
Output (trimmed)NAME PRIORITYLEVEL MATCHINGPRECEDENCE system-leader-election leader-election 100 kube-controller-manager workload-high 800 service-accounts workload-low 9000 ... NAME TYPE NOMINALCONCURRENCYSHARES leader-election Limited 10 workload-high Limited ... catch-all Limited ...

Now the scenario: a homegrown controller is doing LIST pods across all namespaces every second, and other teams report their kubectl is suddenly slow and occasionally returns 429 Too Many Requests. How does APF explain this, and how would you confirm and fix it without restarting the API server?

Reveal the approach

APF sorts every request into a FlowSchema (by user/verb/resource), which maps to a PriorityLevel with a bounded concurrency share and fair queuing within the level. Your noisy controller's requests pile into one priority level; APF fair-queues them and, when the level's queue is full, sheds load by returning 429 with a Retry-After — to requests in that level. Well-behaved traffic in other levels (leader-election, node heartbeats) is deliberately protected, which is the whole point: one bad client can't starve the essentials.

Confirm it: the API server exposes APF metrics — apiserver_flowcontrol_rejected_requests_total and apiserver_flowcontrol_current_inqueue_requests by priority level — and kubectl get --raw /debug/api_priority_and_fairness/dump_priority_levels shows live queue depth. That tells you which level and which flow is saturated. The fix is on the client: replace the every-second full LIST with a watch/informer (Chapter 31) so it reads from a cache instead of re-listing, add a rate limiter, and page over large lists. Raising APF limits or LIST costs (heavy full-object lists are expensive to serialize from etcd) only moves the ceiling; the real bug is a client that lists the world on a timer. This exact pattern — a controller with no informer melting the API server — is one of the most common self-inflicted control-plane incidents at scale.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · slow everything, and it's etcd's disk

Symptom: API calls are slow across the board, kubectl lags, controllers fall behind, occasional 500s. First cut: etcd metrics — etcd_disk_wal_fsync_duration_seconds and etcd_disk_backend_commit_duration_seconds. If p99 fsync is tens of milliseconds or worse, that's your answer. Usual cause: etcd on slow or network-attached storage, a noisy neighbour on the disk, or the DB grown huge. Fix: fast local SSD for etcd, isolate it, compact and defragment to shrink the DB. Never run etcd on EBS-style network disks if you can avoid it.

Incident pattern · etcd out of space (NOSPACE alarm)

Symptom: all writes start failing with an "etcdserver: mvcc: database space exceeded" error; reads still work. Cause: the DB hit its quota (default 2 GiB) because old revisions weren't compacted or something wrote a flood of objects/Events. Fix: compact to the current revision, defrag each member to reclaim space, then disarm the alarm (etcdctl alarm disarm) — writes won't resume until the alarm is cleared. Then find what filled it (often unbounded Events or a controller writing hot).

Incident pattern · control plane down, apps fine

Symptom: kubectl times out, dashboards are blank — panic that "the cluster is down." Reality check: curl your actual services; they're very likely still serving, because the data plane (kubelets, running pods, kube-proxy) runs independently of the control plane. What you've lost: scheduling, scaling, self-healing, and any config change — until the API server/etcd is back. Fix: restore quorum (bring etcd members back, or restore a snapshot). Communicate "control plane impaired, workloads serving," which is a very different severity than "outage."

Production · security · performanceWhat matters in production

Make the control plane HA, and etcd's disk fast. Run 3 (or 5 for large/critical) etcd members and multiple API servers behind a load balancer, spread across failure domains so losing one AZ doesn't cost you quorum. Give etcd dedicated, fast, local SSD — this one choice prevents more control-plane incidents than any other. For big clusters, run etcd on separate machines from the API servers (external etcd topology) so they don't contend.

Back etcd up, and prove you can restore. Take etcdctl snapshot save on a schedule, copy it off the node, and — the part everyone skips — actually run a restore drill into a scratch cluster. An untested backup is a rumour. Keep the DB well under the 8 GB ceiling by compacting and defragmenting on a schedule; watch DB size as a first-class metric. Encrypt Secrets at rest with an EncryptionConfiguration (ideally KMS-backed), because otherwise anyone with an etcd snapshot has every Secret in plaintext.

Protect the API server from clients. Leave API Priority & Fairness on and watch its rejection metrics; it's what keeps one runaway controller from starving leader-election and node heartbeats. Design your own controllers to use informers/watches, not periodic full LISTs, and to page large lists — the most common scaling incident is a client that lists the world on a timer and serializes gigabytes out of etcd. Turn on audit logging so you can answer "who changed this and when."

Least privilege on the door. RBAC is the lock; keep it tight. Don't hand controllers or humans cluster-admin because it's convenient — scope Roles to the verbs and resources actually needed. Restrict who can create admission webhooks and who can read Secrets. A webhook that's slow or down can also wedge the API server, so set sane timeoutSeconds and failurePolicy on your own webhooks.

Common mistakes: etcd on network storage; an even number of etcd members; no tested restore; letting Events or CRDs balloon the DB; a mutating/validating webhook with a long timeout and failurePolicy: Fail that takes the cluster down when the webhook is unhealthy; and treating "kubectl is down" as "the site is down" without checking the data plane.

System-design connectionWhere this reaches into architecture

The control plane is a reference architecture you'll reuse: a stateless, horizontally-scalable API tier (the API server) in front of a strongly-consistent store (etcd via Raft). That split — scale reads/compute by adding stateless replicas, keep exactly one consistent source of truth behind them — is how you build many systems, and the reason the hard part (consensus) is concentrated in one component you can reason about and protect. Raft and quorum are the consensus building blocks we formalise in Chapter 83; leader election for the scheduler/controller-manager is the same idea applied to "only one active instance." The watch mechanism is change-data-capture: publish a durable log of changes and let many consumers react — a pattern you'll see again in event-driven systems (Chapter 84). And etcd is the reason a single Kubernetes cluster has a ceiling (roughly a few thousand nodes before etcd write throughput and object counts hurt), which is why large organisations shard into many clusters rather than one giant one — a concrete instance of the scaling limits in Chapter 95. Finally, API Priority & Fairness is load-shedding and fair queuing done right: protect the critical traffic and reject excess early, the same discipline you apply at any overloaded service (Chapter 88).

30-secWhat happens to a request between kubectl apply and the object being stored?

It hits the API server over TLS and runs a fixed pipeline: authentication (who are you), authorization (are you allowed — usually RBAC), mutating admission (webhooks that can change the object, like sidecar injection), schema validation and defaulting, then validating admission (policy that can only accept or reject, like Pod Security). If it survives all that, the API server serializes it and writes it to etcd, which commits it once a quorum of members agrees. The write bumps a resourceVersion and anyone watching that resource gets notified. Fail at any stage and you get a specific error — 401, 403, 422 — before etcd is ever touched.

2-minExplain etcd's role and why quorum and disk latency matter.

etcd is the cluster's single source of truth — every object lives there under /registry, and the API server is the only thing that reads or writes it. It's a Raft-consensus store: writes go to a leader, replicate to followers, and commit only when a majority — (N/2)+1 — has persisted them. So you run an odd number, 3 or 5, across failure domains; 3 tolerates losing 1, 5 tolerates losing 2. Lose quorum and no writes commit — the control plane freezes, though already-running pods keep serving because the data plane is independent. Disk latency matters because every commit fsyncs the write-ahead log; on slow or network-attached disks fsync latency spikes, Raft heartbeats miss, leaders flap, and the whole API server feels slow. So etcd wants fast local SSD, a size kept under the 8 GB recommendation via compaction and defrag, and regular, restore-tested snapshots — because that snapshot file is the entire cluster.

DeepHow does the scheduler choose a node, and how does the choice take effect?

The scheduler watches for pods with no nodeName and runs the scheduling framework in two phases. Filtering removes infeasible nodes — insufficient allocatable CPU/memory, an untolerated taint, a nodeAffinity/nodeSelector mismatch, volume topology constraints, node not Ready — leaving the feasible set; if that's empty the pod stays Pending with a FailedScheduling event naming the failed predicates. Scoring then ranks the feasible nodes with weighted plugins: spread across nodes/zones, least- or most-allocated for bin-packing, pod affinity/anti-affinity, topology spread. The highest score wins, ties broken randomly. Then it binds — writes the chosen node via a Binding subresource through the API server. That's all it does: it decides and records, it never starts a container. The kubelet on that node is watching, sees the pod assigned to it, and actually runs it. Because the scheduler is just another API client, you can run a second custom scheduler for specific pods or replace it entirely without touching the rest of the system.

ScenarioUsers report kubectl is slow and sometimes returns 429. Where do you look?

429 is API Priority & Fairness shedding load, so I start there rather than assuming the API server is undersized. I check the APF metrics — apiserver_flowcontrol_rejected_requests_total and current in-queue requests by priority level, and the live dump at /debug/api_priority_and_fairness/dump_priority_levels — to see which priority level is saturated and which flow (user/verb/resource) is filling it. Almost always it's a client doing frequent full LISTs — a controller without an informer, or a script polling all pods every second — which is expensive because the API server has to pull and serialize large result sets from etcd. In parallel I check etcd latency, because slow etcd also makes everything slow. The fix is on the client: switch to watch/informers so it reads from a cache, page large lists, add backoff. Bumping APF concurrency is a stopgap; the durable fix is making the noisy client stop listing the world. And I'd confirm essential traffic — leader election, node heartbeats — is still protected in its own priority level, which is what stops this becoming a full outage.

Follow-upThe entire control plane is down. Are my applications down?

Probably not. The control plane and data plane are decoupled: kubelets, running pods, and kube-proxy on each node keep operating from the state they already have, so existing pods keep running and Services keep routing to them. What you lose while the control plane is down is the ability to change anything — no scheduling of new pods, no scaling, no self-healing if a pod or node dies, no config updates, no new deployments. So a node failure during a control-plane outage is bad, because nothing will reschedule its pods until the control plane returns. The practical implication for incident response is that "control plane impaired" and "site down" are different severities: first thing I do is curl the actual user-facing endpoints to establish whether customers are affected, then work on restoring etcd quorum and the API server. It also argues for HA control planes and, for the data plane, enough spare capacity and anti-affinity that you can ride out a control-plane blip without a node loss turning into an outage.

RetainQuick revision

The control plane is the brain and the ledger. The API server is the single front door and the only etcd client; every write runs authentication → authorization → mutating admission → schema validation → validating admission → persist to etcd, and a failure at any stage returns before the store is touched. etcd is the Raft-replicated source of truth: writes commit only at quorum ((N/2)+1), so you run 3 or 5 members across failure domains, give them fast local SSD (fsync latency is everything), keep the DB under ~8 GB with compaction/defrag, and take restore-tested snapshots. The scheduler turns unbound pods into bound ones by filtering to feasible nodes, scoring them, and writing nodeName — it decides, the kubelet runs. The controller manager bundles the reconcile loops, leader-elected in HA. Under load the API server sheds with Priority & Fairness (429), which is why controllers must use watches, not polling LISTs. And the control plane is independent of the data plane: if it's down, running pods keep serving — you just can't change anything.

The 10 things to remember

  1. The API server is the only component that talks to etcd; everything else goes through the API server.
  2. Write path: authn → authz (RBAC) → mutating admission → schema validation → validating admission → etcd.
  3. 401 = identity, 403 = RBAC or a policy webhook, 422 = bad object. The stage tells you where it died.
  4. etcd uses Raft: writes commit at quorum (N/2)+1. Run 3 or 5 members, never even numbers.
  5. Lose etcd quorum → no writes → control plane frozen; but running pods keep running.
  6. etcd is disk-latency bound (fsync per commit) — fast local SSD, never network storage.
  7. etcd DB quota is 2 GiB by default, ~8 GB max; compact + defrag, and take tested snapshots.
  8. Scheduler = filter (feasible) → score (rank) → bind (write nodeName). It decides; the kubelet runs.
  9. controller-manager and scheduler are leader-elected in HA so exactly one instance is active.
  10. Under load the API server throttles via Priority & Fairness (429) — so use watches/informers, not polling LISTs.
