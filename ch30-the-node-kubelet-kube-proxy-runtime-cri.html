Part IV · Kubernetes — Architecture & Internals · Chapter 30

The node: kubelet, kube-proxy, runtime, CRI

The scheduler decided where. Now a single agent on that machine — the kubelet — has to make it real: pull images, ask the runtime to start containers, watch that they stay alive, report health, and shed load when the node runs low. When a node goes NotReady, pods get evicted, or "PLEG is not healthy" shows up, this chapter is the difference between reading tea leaves and reading a diagnosis.

Start: Beginner→→→End: Staff-level ~50 min read · kind + crictl

By the end of this chapter you can

  • Describe the kubelet sync loop and PLEG, and explain the "PLEG is not healthy" incident.
  • Trace how a pod actually starts on a node through the CRI — sandbox, images, containers.
  • Name the node conditions and explain how a node goes NotReady and when its pods get rescheduled.
  • State the default node-pressure eviction thresholds and which pods get evicted first, and tell eviction apart from OOMKilled.
  • Say what kube-proxy does — and, just as important, what it does not do.

Why this exists · the problemDeciding isn't doing

Chapter 29 ended with the scheduler writing spec.nodeName — a decision recorded in etcd. But a decision is just a note on a whiteboard. Nothing is running yet. No image has been pulled, no namespace created, no process started. Somebody standing on that machine has to read the note and do the work.

And it's not a one-shot "start it and walk away." That machine's agent has to keep the containers in the state the spec asks for: restart one that crashes, run its health probes, mount its volumes, wire up its network, and report back honestly whether the pod is healthy. It has to notice when a container dies even though nothing told it. And when the machine itself runs low on memory or disk, it has to make a hard call — start killing pods to keep the node alive rather than let the whole thing fall over.

That agent is the kubelet, and this chapter is where all the frightening node-level symptoms come from. "Pod stuck in ContainerCreating." "Node NotReady." "Pods Evicted." "PLEG is not healthy." Every one of those is the kubelet (or something it depends on) telling you exactly what's wrong — if you know how it works. The data plane is also where your apps actually live, so this is the layer that's up at 3am when the control plane isn't.

Key point

The kubelet is a level-triggered reconciler for one node, exactly like the controllers in Chapter 28 — but its "desired state" is "the pods assigned to me" and its "actual state" is "what the container runtime is really running." It watches, it compares, it acts, forever. Everything below is that loop with the details filled in.

Mental model · analogyThe mental model: a franchise store manager

Real-world analogy

Head office (the control plane) decides which products each store carries and posts assignments to a shared board. Each store manager (the kubelet) runs one shop and does everything local. They read the board for products assigned to their store, order stock from suppliers (pull container images), and put it on the shelves (start containers). They don't stock shelves personally — they phone the warehouse crew (the container runtime, containerd) and hand them a precise packing slip (the CRI request); the crew do the lifting with their forklifts (runc).

The manager walks the floor every minute to check nothing's fallen off a shelf (PLEG relisting containers), and calls head office regularly to say "store's open, all good" (the node heartbeat / Lease). If those calls stop, head office assumes the store is dark and re-routes its products to other stores (the node goes NotReady, pods reschedule).

And when the store is running out of shelf space or the power's failing (disk or memory pressure), the manager doesn't wait for a total blackout — they start pulling the least important stock off the shelves to keep the store open (eviction), sacrificing the cheap impulse-buys before the premium goods. Out front, a directory sign (kube-proxy) points a customer asking for "the pharmacy" to whichever aisle currently has it, even as aisles get rearranged.

Internal workingThe sync loop, PLEG, CRI startup, and eviction

1 · The kubelet sync loop

At its core the kubelet runs syncLoop, which wakes on any of several channels and, for each pod, reconciles reality toward the spec:

  • API updates — a new/changed/deleted pod assigned to this node arrives over the watch.
  • PLEG events — a container changed state (started, died) since last time.
  • A periodic sync — a timer (~1s) that re-reconciles every pod even if nothing signalled, because it's level-triggered and shouldn't rely on catching every event.
  • Probe results — a liveness/readiness/startup probe changed a container's status.
  • Housekeeping — clean up dead containers, orphaned volumes, unused images.

Each pod gets its own worker goroutine running syncPod: compute the pod's current status from the runtime, then make it match — ensure the sandbox exists, ensure each container is running the right image in the right state, (re)start what's missing, run the probes, and write the pod's status back to the API server. Kill the kubelet and restart it and it simply re-observes every container from the runtime and reconciles — the same restart-safety you saw in every other controller.

2 · PLEG — how the kubelet notices a container died

Here's a subtlety that trips people up: nothing pushes "your container just crashed" to the kubelet reliably. So the Pod Lifecycle Event Generator (PLEG) polls. Every second it asks the runtime for the full list of containers, diffs it against the previous list, and generates events (ContainerStarted, ContainerDied) that wake syncLoop to react — restart a crashed container, update status.

That relist is cheap when a node has 20 containers and a healthy runtime. It gets expensive when the node is dense (hundreds of containers) or the runtime is struggling (slow disk, a wedged containerd). PLEG records the timestamp of its last successful relist; if that goes stale past the 3-minute threshold, the kubelet declares itself unhealthy, which flips the node's Ready condition and you see the infamous line:

text
Ready   False   ... KubeletNotReady   PLEG is not healthy: pleg was last seen active 3m0s ago; threshold is 3m0s

So "PLEG is not healthy" almost never means PLEG is broken — it means the runtime couldn't answer the relist fast enough, which points at disk I/O, containerd health, or container density. (Newer kubelets can use event-driven PLEG, consuming CRI container events instead of relisting constantly, which cuts this class of problem — but the relist safety net remains.)

3 · How a pod actually starts, over the CRI

The kubelet never runs a container itself. It speaks the Container Runtime Interface — a gRPC API with two services, RuntimeService (sandboxes and containers) and ImageService (images) — to the runtime (containerd). For one pod, in order:

  1. Admit the pod. The kubelet checks the node can take it (resources, security policy). If not, it rejects it locally rather than starting anything.
  2. Pull images. ImageService.PullImage for each container image, honouring imagePullPolicy and any pull secrets. A stuck pull here is your ImagePullBackOff.
  3. RunPodSandbox — create the pod's shared context. The runtime creates the pause container, which owns the pod's network and IPC namespaces, and invokes the CNI plugin to set up the network namespace and assign the pod its IP. A failure here is the classic "stuck in ContainerCreating" — no IP, no sandbox.
  4. Run init containers, in order. Each must complete successfully before the next; the app containers wait.
  5. Create and start the app containers. CreateContainer then StartContainer per container; each joins the pause container's network namespace, so they all share the pod IP and reach each other on localhost. containerd uses runc to actually create each one (the OCI handoff from Chapter 26).
  6. Run probes, report status. Startup → liveness/readiness probes run; when readiness passes, the pod is marked Ready and its status flows up to the API server. Only now does kube-proxy start routing Service traffic to it.

Note there's no Docker anywhere in that path. The old Docker shim was removed in Kubernetes 1.24; today the kubelet talks CRI to containerd or CRI-O directly. That's why "Kubernetes deprecated Docker" only ever meant "the kubelet stopped using Docker as its runtime" — your Docker-built images run unchanged, because they're just OCI images.

4 · Node status, heartbeats, and going NotReady

The kubelet tells the control plane it's alive two ways: it periodically writes full NodeStatus (capacity, conditions, addresses), and — to keep that cheap at scale — it renews a lightweight Lease object in kube-node-lease roughly every 10 seconds. The node lifecycle controller (in the controller manager, Chapter 29) watches those heartbeats. If a node stops renewing for the node-monitor-grace-period (about 40 seconds by default), the controller sets the node's Ready condition to Unknown — the node is NotReady — and taints it NoExecute. Pods on a NotReady node aren't killed instantly; by default they tolerate the taint for 300 seconds, after which they're evicted and rescheduled elsewhere. That delay is intentional: a 30-second network blip shouldn't reschedule the whole node's workload.

5 · Node-pressure eviction

Separately from the node-controller path, the kubelet defends its own node. Its eviction manager watches signals and acts when one crosses a threshold. The default hard thresholds are worth memorising:

SignalDefault hard thresholdMeaning
memory.available< 100MiNode is nearly out of RAM
nodefs.available< 10%The kubelet/root filesystem is filling up
imagefs.available< 15%The image/container-writable filesystem is filling up
nodefs.inodesFree< 5%Out of inodes (many small files)

When a threshold is crossed, the kubelet sets the matching condition (MemoryPressure, DiskPressure, PIDPressure), tries to reclaim first (delete dead containers, unused images), and if that's not enough, evicts pods — ranked by QoS class and usage over requests: BestEffort pods go first, then Burstable pods exceeding their requests, and Guaranteed pods last (Pod Priority also factors in). An evicted pod ends up with phase Failed and reason Evicted.

Eviction is not the same as OOMKilled

Two different killers, and confusing them wastes incident time. Kubelet eviction is proactive and node-level: the kubelet sees pressure building and gracefully removes whole pods to protect the node — you get Evicted pods and a MemoryPressure/DiskPressure condition. OOMKilled is reactive and kernel-level: a container blew past its cgroup memory limit and the Linux OOM killer terminated that process instantly (Chapter 3) — you get a container with reason OOMKilled that usually restarts in place. Eviction is the manager clearing shelves; OOMKilled is a breaker tripping on one appliance.

Think first: a node flips to NotReady, then back to Ready 90 seconds later, and no pods moved. What likely happened, and why didn't pods reschedule?

Most likely the kubelet briefly stopped heart-beating — a transient (a kubelet restart, a short API-server connectivity blip, or a PLEG stall that cleared) — long enough to exceed the ~40s grace period, so the node controller marked it NotReady and applied the NoExecute taint. Pods didn't reschedule because the default toleration for that taint is 300 seconds, and the node recovered (kubelet resumed heartbeats, Ready flipped back, taint removed) well inside that window. The lesson: NotReady is not automatically an outage — there's a deliberate grace period before, and a deliberate 5-minute delay after, precisely so short blips don't cause pod churn. If you want a flap like this to not even reach NotReady, you chase the root cause of the missed heartbeat (often kubelet↔apiserver networking or a slow runtime), not the timers.

ComponentsThe node's pieces, named

  • kubelet — the node agent. Owns: reconciling assigned pods, calling the runtime over CRI, mounting volumes and Secrets, running probes, collecting stats (cAdvisor), reporting node/pod status, and eviction. One per node, run by systemd (not itself a pod).
  • CRI — the gRPC contract between kubelet and runtime (RuntimeService + ImageService). A clean interface, which is why runtimes are swappable.
  • Container runtime — containerd (or CRI-O) — implements the CRI: pulls images, manages sandboxes and containers, streams logs. Uses an OCI runtime underneath.
  • OCI runtime — runc — actually creates the container: namespaces, cgroups, seccomp, and execve (Chapters 22–27). Swap it for a sandboxed runtime (gVisor's runsc, Kata) via RuntimeClass for stronger isolation.
  • CNI plugin — sets up the pod's network namespace and assigns its IP during sandbox creation. The whole of Part V is this boundary; here, just know the kubelet/runtime calls it and a failure shows as ContainerCreating.
  • kube-proxy — the Service datapath on each node. Watches Services and EndpointSlices and programs the kernel (iptables by default; IPVS for very large Service counts; the newer nftables mode) so that traffic to a Service's stable ClusterIP is load-balanced to the current set of healthy pod IPs. It does not do pod-to-pod networking (that's the CNI) and it does not proxy every packet in userspace — it installs kernel rules and gets out of the way. Details in Chapter 43.
  • The pause container — the tiny process that holds a pod's namespaces so the IP survives app-container restarts.

Data flowFollowing one pod as it lands on the node

The scheduler bound the pod in Chapter 29. Now, on the node:

  1. The kubelet's watch delivers a pod with spec.nodeName = this node. syncLoop wakes.
  2. The kubelet admits it, then calls ImageService.PullImage for the container image(s).
  3. It calls RunPodSandbox: containerd creates the pause container and invokes CNI, which hands back the pod IP. The pod now has a network identity.
  4. Init containers run to completion, then the kubelet CreateContainer/StartContainers the app containers via runc; they join the pause namespace and share the IP.
  5. Probes run; readiness passes; the kubelet writes pod status: Ready up to the API server. PLEG will keep relisting to catch any later death.
  6. kube-proxy, watching EndpointSlices, sees this pod become a ready endpoint of its Service and updates the node's kernel rules so Service traffic now reaches it. The pod is serving.
Think first: a pod shows Running but not Ready, and gets no traffic. What's the difference, and who decides?

Running means the kubelet started the container process; Ready means the container's readiness probe is passing, and the kubelet is what runs that probe. They're deliberately separate: an app can be up but still warming caches, loading config, or waiting on a dependency — not yet safe to serve. Only Ready pods are published as Service endpoints, so kube-proxy routes traffic only to them. So "Running but not Ready, no traffic" is the system working as designed — check the readiness probe and what it gates on (kubectl describe pod shows probe failures). It's also why a too-strict readiness probe can quietly pull a perfectly healthy pod out of rotation and look like a traffic bug.

Lab 3Break — cordon and drain a node for maintenanceBreak

The everyday node operation: take a node out of service safely. First put a workload on it, then cordon (stop new pods landing) and drain (evict existing ones):

bash
kubectl create deployment demo --image=nginx:1.27-alpine --replicas=3
kubectl cordon $NODE
kubectl get node $NODE            # STATUS now: Ready,SchedulingDisabled
kubectl drain $NODE --ignore-daemonsets --delete-emptydir-data --force
Outputnode/node-control-plane cordoned evicting pod default/demo-... evicting pod default/demo-... node/node-control-plane drained

cordon marks the node Unschedulable so the scheduler stops placing new pods; drain then evicts the existing pods (respecting PodDisruptionBudgets and skipping DaemonSet pods, which belong to every node). In a real multi-node cluster the drained pods reschedule onto other nodes before you reboot or replace this one. Put it back in service with kubectl uncordon $NODE. This exact two-step is the safe front half of every node upgrade and every "this node is misbehaving, get workloads off it" response.

Lab 4Troubleshoot — a pod stuck in ContainerCreatingTroubleshoot

Uncordon first (kubectl uncordon $NODE). Now a pod that references a Secret that doesn't exist — a very common cause of a pod that schedules but never starts:

bash
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: { name: stuck }
spec:
  containers:
    - name: c
      image: nginx:1.27-alpine
      volumeMounts: [{ name: cfg, mountPath: /cfg }]
  volumes:
    - name: cfg
      secret: { secretName: does-not-exist }
EOF
kubectl get pod stuck
OutputNAME READY STATUS RESTARTS AGE stuck 0/1 ContainerCreating 0 20s

It scheduled fine (it has a node) but the container never creates. The scheduler is done; this is a kubelet problem. Where does the kubelet record why? Work it out before revealing.

Reveal the diagnosis

The kubelet posts the reason as a pod Event — always your first stop for ContainerCreating:

bash
kubectl describe pod stuck | sed -n '/Events/,$p'
OutputWarning FailedMount kubelet MountVolume.SetUp failed for volume "cfg" : secret "does-not-exist" not found

The kubelet can't mount the volume, so it won't create the container — it's blocked at a pre-start step, reconciling and retrying forever until the Secret appears. ContainerCreating has a short list of usual causes, and the Event names which: a missing Secret/ConfigMap (this), a volume that won't attach/mount, an image still pulling, or CNI failing to give the pod an IP. The fix follows from the Event — here, create the Secret. The habit to build: ContainerCreating or Pending → kubectl describe → read Events; the kubelet almost always told you exactly what it's waiting on. Clean up: kubectl delete pod stuck.

Lab 5Production challenge — induce disk-pressure evictionSenior challenge

See the eviction manager act. We'll fill the node's writable filesystem until nodefs.available drops below the 10% threshold and watch the kubelet evict. Safety: this consumes disk inside the kind node container, not your Mac's home directory, and we delete it after — but don't run it on a cluster you care about.

bash
# A BestEffort pod (no requests/limits) writing a large file to ephemeral storage.
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: { name: hog, labels: { app: hog } }
spec:
  containers:
    - name: hog
      image: busybox:1.36
      command: ["sh","-c","dd if=/dev/zero of=/data/fill bs=1M count=200000 || sleep 3600"]
      volumeMounts: [{ name: d, mountPath: /data }]
  volumes: [{ name: d, emptyDir: {} }]
EOF
kubectl get pod hog -w

Before it finishes, the node crosses the disk threshold. The question: what condition appears, which pod gets evicted and why that one, and how would you tell this apart from an OOMKill in a postmortem? Reason it through, then check.

Reveal what happens and why

As free space drops under 10%, the kubelet sets DiskPressure=True on the node, tries to reclaim (delete unused images and dead containers), and when that isn't enough, evicts pods — starting with BestEffort ones consuming the resource, which is exactly our hog:

bash
kubectl get pod hog -o jsonpath='{.status.phase} {.status.reason}{"\n"}'
kubectl describe node $NODE | grep -A2 DiskPressure
kubectl get events | grep -i evict
OutputFailed Evicted DiskPressure True KubeletHasDiskPressure Warning Evicted ... The node was low on resource: ephemeral-storage.

Why that pod: eviction ranks by QoS then usage over requests — hog is BestEffort (no requests) and is the one consuming the disk, so it's first out. Give a pod requests/limits (Burstable/Guaranteed) and it's protected relative to BestEffort, which is the whole practical reason to set them on anything important. Eviction vs OOMKilled: this shows phase Failed, reason Evicted, and a node DiskPressure (or MemoryPressure) condition — a proactive, node-level, whole-pod action by the kubelet. An OOMKill instead shows a container with reason OOMKilled that restarts in place, driven by the kernel hitting a cgroup memory limit, with no node condition. In a postmortem, "Evicted + pressure condition" points at node capacity/headroom; "OOMKilled" points at a single container's memory limit. Clean up: kubectl delete pod hog, then kind delete cluster --name node.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · node NotReady

Symptom: a node shows NotReady; after a few minutes its pods start rescheduling. First cut: kubectl describe node and read the Ready condition's reason; then, on the node, journalctl -u kubelet. Usual causes: the kubelet crashed or can't reach the API server (so heartbeats stopped), the runtime is unhealthy, the disk is full, or PLEG went stale. Confirm: can the kubelet talk to the API server; is containerd healthy (crictl ps responds quickly)? Fix is cause-specific, but the flow is always describe-node → kubelet logs → runtime health.

Incident pattern · PLEG is not healthy

Symptom: Ready condition flips False with "PLEG is not healthy: pleg was last seen active 3m…". Cause: the runtime can't answer the ~1s container relist fast enough — nearly always disk I/O saturation, a wedged/very busy containerd, or too many containers per node. Confirm: node disk latency and containerd health; container count. Fix: relieve the disk (it's often the same event as DiskPressure), restart/upgrade containerd if wedged, and cap pods-per-node. It is not a bug in "PLEG" — it's a slow runtime.

Incident pattern · a wave of Evicted pods

Symptom: many pods show Evicted, concentrated on one node, with a pressure condition set. Cause: the node hit a memory or disk eviction threshold; the kubelet shed BestEffort and over-request Burstable pods to survive. Confirm: which condition (MemoryPressure vs DiskPressure) and what filled it — a log-spewing app filling nodefs, images filling imagefs, or genuine memory over-commit. Fix: set requests/limits so important pods aren't BestEffort, reserve resources for the system, and leave headroom. Evicted pod objects linger for visibility; garbage-collect them once understood.

Production · security · performanceWhat matters in production

Give the node headroom, and reserve it explicitly. Set --system-reserved and --kube-reserved so the OS and the kubelet/containerd always have CPU and memory the scheduler won't hand to pods — otherwise a full node starves the very agents that keep it alive, and you get cascading NotReady. Keep eviction thresholds as an intentional safety margin, not something you disable. Don't pack nodes to 100% of allocatable; the gap between "requests fit" and "actually out of memory" is what eviction and the OOM killer live in.

Set requests and limits — QoS is your eviction insurance. A pod with no requests is BestEffort and first to be evicted; a pod whose requests equal its limits is Guaranteed and evicted last. For anything that matters, set them. This is the concrete, node-level reason the abstract advice "always set resource requests" exists.

Make node maintenance boring. The runbook is cordon → drain (respecting PodDisruptionBudgets) → do the work → uncordon. Define PDBs so drain can't take down all replicas of a service at once, and use graceful node shutdown so a planned reboot gives pods their termination grace period. This is 90% of day-to-day node ops.

Monitor the node's own signals. Alert on node conditions (any pressure True, Ready not True), kubelet health, PLEG relist latency (kubelet_pleg_relist_duration_seconds), disk and inode usage on nodefs/imagefs, and container restart rates. These lead the user-visible symptoms — DiskPressure and PLEG stalls usually share a root cause (a full or slow disk), so watching disk latency catches both early.

Choose kube-proxy mode deliberately at scale. iptables mode is fine into the low thousands of Services, but rule evaluation grows with Service count; very large clusters move to IPVS (hash-based, O(1) lookup) or the newer nftables mode. It's a per-cluster decision you make once, covered in Chapter 43. Common mistakes: no reserved resources, everything BestEffort, no PDBs (so a drain causes an outage), etcd/runtime on slow disks (PLEG stalls), and confusing OOMKilled with Evicted and chasing the wrong fix.

System-design connectionWhere this reaches into architecture

The kubelet is a case study in a pattern you'll design with directly: the autonomous edge agent. The control plane decides intent; the agent on each machine acts locally and keeps acting even when it can't reach the control plane — which is why the data plane survives control-plane outages. When you build fleet systems (config agents, edge devices, per-host daemons), copy this: push desired state to the edge, let the edge reconcile locally and buffer, and treat central connectivity as best-effort. Eviction is load-shedding with a priority order — the same discipline as API Priority & Fairness (Chapter 29) and circuit breakers (Chapter 88): when you can't serve everything, drop the least important on purpose rather than failing randomly, and let QoS classes encode "least important." The CRI, CNI, and CSI boundaries are textbook dependency inversion: the kubelet depends on interfaces, not implementations, which is exactly what lets you swap containerd for CRI-O, or runc for gVisor/Kata, without touching Kubernetes — the plug-in architecture that made the ecosystem possible. And the split between "scheduler decides, kubelet acts" is separation of a slow global optimisation from fast local execution, a decomposition that recurs whenever you scale a control system.

InterviewInterview questions & answers

Answer each in your head before opening it.

30-secWhat does the kubelet do?

It's the node agent, one per node. It watches the API server for pods assigned to its node and reconciles them into reality: pulls images, tells the container runtime over the CRI to create the pod sandbox and containers, mounts volumes and Secrets, runs health probes, and reports pod and node status back. It also defends the node — evicting pods under memory or disk pressure — and renews the node's heartbeat. It doesn't run containers itself or decide placement; it turns the scheduler's decision into running containers and keeps them in the desired state.

2-minWalk me through how a pod starts on a node.

The kubelet's watch delivers a pod bound to its node and the sync loop wakes. It admits the pod against node resources and policy, then pulls the images via the CRI ImageService. Next it runs the pod sandbox: the runtime creates the pause container that holds the pod's network and IPC namespaces and calls the CNI plugin to set up the network namespace and assign the pod IP — a failure here is the classic ContainerCreating hang. Then init containers run to completion in order, and the app containers are created and started via the CRI RuntimeService, each joining the pause namespace so they share the IP and localhost. containerd does this using runc as the OCI runtime. Finally probes run; once readiness passes the pod is Ready, status flows up to the API server, and kube-proxy starts routing Service traffic to it. Throughout, PLEG relists containers about once a second so the kubelet notices if one dies and restarts it. Note there's no Docker in the path — the shim was removed in 1.24; the kubelet talks CRI to containerd directly.

DeepWhat is PLEG and what does "PLEG is not healthy" tell you?

PLEG — the Pod Lifecycle Event Generator — is how the kubelet learns that containers changed state without relying on the runtime to push events reliably. It relists all containers from the runtime roughly every second, diffs against its previous view, and emits ContainerStarted/ContainerDied events that wake the sync loop to react. It records the timestamp of its last successful relist; if that goes stale past a 3-minute threshold, the kubelet reports itself unhealthy, which flips the node's Ready condition and surfaces "PLEG is not healthy: pleg was last seen active 3m…". The key insight is that this is almost never a PLEG bug — it means the container runtime couldn't answer the relist in time, which points at disk I/O saturation, a wedged or overloaded containerd, or too many containers per node. So the investigation is node disk latency and containerd health, not PLEG itself. Newer kubelets can run event-driven PLEG that consumes CRI container events instead of constant relisting, reducing this failure mode, but the relisting safety net remains for correctness.

ScenarioHalf a node's pods show "Evicted" and others "OOMKilled". Are these the same thing?

No — different killers with different meanings, and separating them decides the fix. "Evicted" pods come from the kubelet's node-pressure eviction: the node crossed a memory or disk threshold, so the kubelet proactively removed whole pods to keep the node alive, starting with BestEffort and over-request Burstable pods. You'll see a node condition like MemoryPressure or DiskPressure and pods in phase Failed/Evicted. "OOMKilled" comes from the Linux kernel: a container exceeded its cgroup memory limit and the OOM killer terminated that process; the container typically restarts in place and there's no node condition. So Evicted points me at node capacity and headroom — reserve resources, set requests/limits so important pods aren't BestEffort, stop over-committing, or add nodes. OOMKilled points me at one container's limit — either it has a leak or genuinely needs more memory, so I profile and right-size the limit. Seeing both together often means a node under real memory pressure where some pods hit their own limits and the kubelet is also evicting to protect the node.

Follow-upWhat does kube-proxy do, and what does it not do?

kube-proxy implements Kubernetes Services on each node. It watches Services and EndpointSlices and programs the kernel — iptables by default, IPVS or the newer nftables mode at scale — so that traffic sent to a Service's stable ClusterIP is load-balanced (via DNAT) to the current set of ready pod IPs, and it updates those rules as pods come and go. What it does not do is equally important: it doesn't provide pod-to-pod connectivity — that's the CNI plugin and the cluster network — and in its normal modes it doesn't proxy packets through a userspace process per connection; it installs kernel rules and steps aside, so the datapath cost is just kernel packet processing. So "Service works but pods can't reach each other" is a CNI problem, not kube-proxy, and "Service isn't load-balancing to a new pod" is kube-proxy or EndpointSlices. We take the actual datapath apart in Part V.

RetainQuick revision

The kubelet is the per-node agent and a level-triggered reconciler: it watches the API server for pods bound to its node and drives the container runtime over the CRI to make them real — pull images, RunPodSandbox (pause container + CNI IP), start init then app containers via containerd/runc, run probes, report status. PLEG relists containers about once a second so the kubelet notices deaths; if the runtime can't answer within 3 minutes you get "PLEG is not healthy," which means a slow runtime/disk, not a PLEG bug. The kubelet heartbeats via a Lease every ~10s; miss the ~40s grace period and the node controller marks the node NotReady and taints it, rescheduling pods after a 300s toleration. Under pressure the kubelet evicts pods at the default thresholds (memory<100Mi, nodefs<10%, imagefs<15%, inodes<5%), lowest QoS first — which is different from a kernel OOMKill of a single container. kube-proxy programs kernel rules so Service IPs reach live pods, but it doesn't do pod-to-pod networking. When a pod is stuck or a node is unhappy, the answer is almost always in kubectl describe Events, node conditions, and journalctl -u kubelet.

The 10 things to remember

  1. The kubelet is the node agent: it reconciles pods assigned to its node against what the runtime is actually running.
  2. It never runs containers itself — it calls the runtime (containerd) over the CRI, which uses runc.
  3. Pod startup: admit → pull images → RunPodSandbox (pause + CNI IP) → init → app containers → probes.
  4. No Docker in the path since 1.24 (shim removed); the kubelet speaks CRI to containerd/CRI-O.
  5. PLEG relists containers ~every 1s; "PLEG is not healthy" (3m threshold) means a slow runtime/disk.
  6. The kubelet heartbeats via a Lease (~10s); missing ~40s → node NotReady → NoExecute taint → reschedule after 300s.
  7. Node conditions: Ready, MemoryPressure, DiskPressure, PIDPressure — read them first in any node incident.
  8. Default hard eviction: memory<100Mi, nodefs<10%, imagefs<15%, inodes<5%; BestEffort evicted first.
  9. Evicted (kubelet, node-level, whole pod) ≠ OOMKilled (kernel, cgroup limit, one container).
  10. kube-proxy programs kernel rules for Service IPs; it does not do pod-to-pod networking (that's CNI).
