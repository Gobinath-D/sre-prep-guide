Part IV · Kubernetes — Architecture & Internals · Chapter 31

The reconciliation loop, controllers, informers

Chapter 28 told you controllers reconcile; Chapter 29 warned that polling the API server melts it. This is the machinery that squares the two: watch, a local cache, a work queue, and an idempotent reconcile. Every built-in controller, every operator you'll write, and Argo CD all run this exact pattern — so learn it once, deeply.

Start: Beginner→→→End: Staff-level ~40 min read · kind

Why this exists · the problemHow does a controller know when to act?

You have the model: a controller compares desired state to actual state and closes the gap. But that leaves a mechanical hole. When does it run the comparison? The naive answer — "every second, list every pod and check" — is exactly the mistake Chapter 29 showed melting an API server: full LISTs are expensive, they serialize the world out of etcd, and doing that on a timer across dozens of controllers is a self-inflicted outage.

The opposite naive answer — "have the API server call me when something changes" — has its own trap. If the controller reacts only to the change event ("pod-42 was deleted"), then a missed event (the controller was restarting, the connection dropped) leaves it permanently wrong, because nothing re-fires an old event. That's the fragility of edge-triggered logic from Chapter 28.

So Kubernetes needs a machine that gets change notifications cheaply and stays correct when notifications are missed or duplicated. That machine is the trio you'll meet here: a watch (a cheap change stream), an informer (a local, always-current cache fed by that stream), and a work queue feeding an idempotent reconcile that always reads current state. It's the shared skeleton of every controller in the cluster, and once you can draw it, "why did the controller do that?" becomes answerable instead of magic.

Key point

The resolution is a split: events tell the controller when to look; the cache tells it what is true. A change enqueues a reminder to reconcile object X — but reconcile then reads X's full current state and acts on that, ignoring what the event said changed. Miss an event and you're only late, never wrong. That single idea is the whole chapter.

Mental model · analogyThe mental model: an assistant with a change feed and an in-tray

Real-world analogy

Imagine a meticulous assistant whose job is to keep a set of orders in the right state. They don't re-read the entire master ledger every minute — that would be absurd. Instead they subscribe once to a change feed from the records office ("order 42 touched," "order 51 touched") and use it to keep a personal photocopy of the ledger up to date (the informer cache). The change feed is cheap; their copy is always current.

For every change that comes in, they don't act immediately. They drop a sticky note with just the order number into an in-tray (the work queue). The tray is smart: if order 42 changes five times before they get to it, there's still only one sticky for 42 — the notes deduplicate. And the sticky says only "look at 42," never "42 changed from X to Y."

They work the tray one sticky at a time. For each, they pull order 42's latest record from their photocopy, compare it to how it should be, and fix whatever's off. If a fix fails (the records office is busy), they put the sticky back — but at the bottom, and they wait a little longer each time before retrying (backoff), so a stubborn order doesn't starve the rest. Because they always read the current record, it doesn't matter if they missed a change or five piled up: the final state is what they act on.

Internal workinglist/watch, the informer, the queue, the reconcile

1 · list + watch: a consistent stream, cheaply

Two API primitives make this possible. A LIST returns all objects of a type and a resourceVersion — a monotonically increasing marker for "the state of the world as of here." A WATCH opens a long-lived streaming connection that delivers every change since a given resourceVersion: added, modified, deleted. So a controller lists once to get the full picture and a starting version, then watches from that version to receive a live delta stream — no polling, and the API server serves it from its own watch cache, cheaply, to thousands of watchers.

Watches aren't forever. Connections drop; the API server may send a 410 Gone if your resourceVersion is too old to resume from (the change history it keeps is bounded). The client handles this by relisting to get a fresh resourceVersion and resuming the watch — which is also a correctness reset. Periodic watch bookmarks keep the client's resourceVersion current so relists stay rare.

2 · The informer: a local cache you can read for free

An informer wraps list/watch into a maintained local cache. Its parts:

  1. Reflector. Runs the ListAndWatch loop against one resource type and pushes every change into a DeltaFIFO queue as a delta (Added/Updated/Deleted).
  2. DeltaFIFO → Indexer. The informer pops deltas in order and updates the Indexer — a thread-safe in-memory store keyed by namespace/name, optionally indexed by labels/fields for fast lookups. This Indexer is the cache; it always reflects the latest observed state.
  3. Event handlers. As it applies each delta, the informer calls your registered OnAdd/OnUpdate/OnDelete handlers. Note that well-written handlers do almost nothing except compute a key and enqueue it — they don't reconcile inline.
  4. Resync. Periodically the informer re-delivers everything in its cache through the handlers, even with no changes. That's a deliberate level-triggered safety net: it re-drives reconciliation so nothing sits un-reconciled forever.

The "Shared" in SharedInformer matters at scale: one informer per resource type is shared by every controller in the process, so pods are listed and watched once and everyone reads the same cache — instead of each controller opening its own watch. This is the mechanized version of the Chapter 29 rule "use informers, not per-controller LISTs."

3 · The work queue: debounce and backoff

Handlers enqueue keys, not objects, into a rate-limited work queue with three properties that make controllers well-behaved:

  • Deduplication. A key already waiting isn't added twice. Ten rapid changes to one Deployment collapse into one reconcile — natural debouncing.
  • Rate limiting & backoff. On a failed reconcile you call AddRateLimited(key), which re-adds it with exponential backoff (milliseconds, then seconds, capped). A persistently failing object retries forever but slowly, so it can't hammer the API server or starve other keys.
  • Delayed adds. AddAfter(key, 30s) lets a reconcile ask to be re-run later — e.g. "check again in 30s" while waiting for something to settle.

4 · The reconcile: idempotent, level-triggered

A worker goroutine pops a key and runs the reconcile. This is where you'd write your own logic; the shape is always:

go
func reconcile(key string) error {
    obj, exists := lister.Get(key)   // read CURRENT state from the cache — not from the event
    if !exists {
        return handleDeleted(key)     // object is gone; clean up if needed
    }
    desired  := obj.Spec              // what should be
    actual   := observeWorld(obj)     // what is (children, external systems…)
    if !equal(desired, actual) {
        return act(diff(desired, actual))  // idempotent create/update/delete
    }
    return nil                        // success → queue.Forget(key)
}

Three properties do all the work. It reads current state from the cache, so it's level-triggered — the key was just a nudge. It's idempotent — running it twice on the same state changes nothing the second time, so duplicate or replayed keys are harmless. And it returns an error to requeue or nil to forget, so transient failures retry with backoff and successes stop churning. Restart the controller and it relists, refills the cache, resyncs every key, and converges — the same restart-safety as every loop in this Part.

Think first: a controller misses a delete event for a pod while it was restarting. Does the pod's owner stay broken?

No. On restart the informer does a fresh LIST, so its cache reflects reality: the pod is simply absent. When the owner (say a ReplicaSet) is reconciled — either because the resync re-drives every key, or because the missing pod changed the observed count — the reconcile reads the current cache, counts the pods that actually exist, sees it's one short of desired, and creates a replacement. It never needed the delete event; it needed the current count, which it reads every time. This is the concrete reason level-triggered controllers tolerate missed events: the event was only a hint to look, and the LIST-backed cache is the source of "what is." An edge-triggered handler that decremented a counter on the delete event would now be permanently wrong.

ComponentsThe pieces, named

  • Watch / List — the API primitives: full snapshot + resourceVersion (List), streaming deltas from a version (Watch). The foundation everything else sits on.
  • Reflector — runs ListAndWatch for one type and feeds the DeltaFIFO.
  • Informer (SharedInformer) — maintains the cache (Indexer) from the delta stream and fans out events to handlers; shared across controllers in a process.
  • Indexer / Lister — the in-memory cache and the read API over it. Reconcile reads here, not from the API server, so reads are free and fast.
  • Work queue — the deduplicating, rate-limited queue of keys between handlers and workers.
  • Reconciler — your function: read current state, converge, return error-or-nil.
  • ownerReferences & the garbage collector — metadata linking children to a parent (a ReplicaSet owns its pods). A controller watches its children and maps each back to the owner's key to reconcile the owner; and when a parent is deleted, the GC controller deletes objects whose owner is gone (cascading delete).
  • controller-runtime / Manager — the library (used by Kubebuilder/Operator SDK) that wires informers, queues, workers, and leader election together so you write only the reconcile. This is the bridge to operators in Chapter 32.

Data flowFollowing "delete a ReplicaSet's pod" through the machine

Chapter 28 showed this self-heals; now watch the actual parts move. You delete one pod owned by a ReplicaSet that wants 3:

  1. The API server records the deletion and bumps the global resourceVersion.
  2. The ReplicaSet controller's pod informer receives the delete on its watch, removes the pod from its cache, and fires the OnDelete handler.
  3. The handler reads the pod's ownerReferences, finds the owning ReplicaSet, and enqueues the ReplicaSet's key (not the pod's) — you reconcile the owner, because the owner is what has a desired count.
  4. A worker pops the ReplicaSet key. Via the Lister it reads the ReplicaSet (desired: 3) and lists pods matching its selector from the cache (now: 2). Diff: +1.
  5. The reconcile creates one Pod via the API server, with an ownerReference back to the ReplicaSet. Success → the key is forgotten.
  6. That create is itself a change: the pod informer sees the new pod, the ReplicaSet is reconciled again, counts 3 = 3, and does nothing. Equilibrium.

No step referenced the delete event's contents. The controller learned "something about this ReplicaSet's world changed," then read the current counts and acted. That's the pattern doing exactly what the analogy promised.

Think first: five controllers in one controller-manager all need to watch Pods. How many pod watches hit the API server?

One. That's what the Shared in SharedInformer buys you: a single informer per resource type lists and watches Pods once, keeps one cache, and every controller in that process reads from it and registers its own handlers. Without sharing, five controllers would open five watches and hold five copies of the same data — five times the API-server and memory cost for no benefit. This is the mechanical reason the controller-manager bundles dozens of controllers into one binary: they share informers. It's also why a rogue controller that opens its own per-object LISTs instead of using the shared cache stands out immediately as an API-server hog (the Chapter 29 incident).

Lab 2Understand — see the controller reconcile via EventsUnderstand

Controllers record their actions as Events on the object, which is the cleanest way to watch a reconcile without reading source. Look at the ReplicaSet:

kubectl describe rs -l app=web | sed -n '/Events/,$p'

That ownerReference is how a pod event gets mapped back to the ReplicaSet key to enqueue — and how deleting the ReplicaSet later garbage-collects these pods.

Lab 3Break — watch reconciliation from the controller's sideBreak

You've deleted a pod before; now connect it to the machinery. Delete a pod and immediately read the ReplicaSet's Events again — you'll see a fourth create appear, the reconcile reacting to the enqueued owner key:

bash
kubectl delete pod $(kubectl get pod -l app=web -o name | head -1)
sleep 2

OutputNormal SuccessfulCreate replicaset-controller Created pod: web-xxxx-ddddd

Trace it against the flow: delete → pod informer fires OnDelete → handler enqueues the ReplicaSet key → worker reads desired (3) and cached pod count (2) → creates one → records the Event. The controller never handled a "pod deleted" case specially; it recounted and converged. That's self-healing you can now explain mechanically, not just observe.

Lab 4Troubleshoot — an object stuck TerminatingTroubleshoot

Finalizers are how a controller says "let me clean up before this object is really deleted" — and they're a top cause of stuck deletions. Create an object with a finalizer nobody removes:

bash
kubectl create configmap demo-cm --from-literal=k=v
kubectl patch configmap demo-cm --type=merge \
  -p '{"metadata":{"finalizers":["example.com/needs-cleanup"]}}'
kubectl delete configmap demo-cm --wait=false
kubectl get configmap demo-cm
OutputNAME DATA AGE demo-cm 1 30s # still here — delete "succeeded" but object remains

The delete didn't delete. Why is it stuck, and what's the safe fix versus the dangerous one? Reason first.

Reveal the diagnosis

The object now has a deletionTimestamp (it's marked for deletion) but a non-empty finalizers list, and the API server won't actually remove an object until its finalizers are all cleared. Normally a controller owns that finalizer: it sees the deletionTimestamp, does its cleanup (drain external resources, deregister DNS, etc.), then removes its finalizer, and the object disappears. Here no controller owns example.com/needs-cleanup, so it hangs forever in Terminating. Confirm:

bash
kubectl get configmap demo-cm -o jsonpath='{.metadata.deletionTimestamp} {.metadata.finalizers}{"\n"}'
Output2026-09-21T...Z [example.com/needs-cleanup]

The right fix in production is to make the owning controller healthy so it removes its finalizer after cleanup. The blunt fix, when the controller is gone for good and you accept skipping its cleanup, is to remove the finalizer by hand — kubectl patch configmap demo-cm --type=merge -p '{"metadata":{"finalizers":null}}' — after which it deletes instantly. Force-removing finalizers on real resources (namespaces stuck Terminating, PVs) can orphan external infrastructure, so it's a last resort, not a reflex. This exact "stuck Terminating" shape recurs with operators and namespaces throughout the book.

Lab 5Production challenge — a hot-looping reconcileSenior challenge

The opposite failure of "not reconciling" is "reconciling constantly without progress" — a hot loop. Reproduce the shape by pointing a Deployment at an unpullable image, then reason about how you'd detect a hot loop in general:

bash
kubectl set image deployment/web nginx=nginx:nope-not-real
kubectl get events --sort-by=.lastTimestamp | tail -8
Output... BackOff Back-off pulling image "nginx:nope-not-real" ... Failed Failed to pull image ... ... FailedCreate/SuccessfulCreate (repeating) ...

The controllers keep retrying with backoff — that's healthy backoff, not a bug. But how would you tell a pathological hot loop (a controller burning CPU and API calls, making no progress) from normal backoff, and what usually causes it? Think, then reveal.

Reveal the approach

You look at the controller's own signals, not the app's. Controllers built on client-go/controller-runtime export work-queue metrics — workqueue_depth (keys waiting), workqueue_adds_total, workqueue_retries_total, and reconcile latency/error counters. A healthy controller under backoff shows a bounded queue and retries spaced out by exponential backoff. A hot loop shows retries climbing without bound, high adds_total with no drop in depth, and often 100% CPU on the controller — it's re-enqueuing faster than backoff intends.

The usual causes are self-inflicted: a reconcile that isn't idempotent, so every pass writes the object (a status update, a defaulted field) which fires the informer, which re-enqueues the same key — an infinite feedback loop the controller creates itself. Or two controllers fighting the same field (a manifest and the HPA both setting replicas), each undoing the other forever. Or returning an error on a permanent condition so it requeues endlessly at the backoff cap. The fixes: make reconcile idempotent and only write when something actually changed (compare before update); ensure exactly one owner per field; and treat permanent failures as terminal (record status, stop requeuing) rather than as retryable errors. This is precisely the failure mode you'll debug in operators (Chapter 32) and as "Argo CD stuck OutOfSync / reconcile error" in Chapter 65. Clean up: kubectl rollout undo deployment/web, then kind delete cluster --name ctrl.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · a controller stopped reconciling

Symptom: you change desired state and nothing happens — no new pods, no events, the object just sits. First cut: is the controller running and is it the leader? For built-ins, check the controller-manager pod and its leader-election Lease; for an operator, its Deployment and logs. Usual causes: the controller crashed or lost leader election, its informer cache never synced (it's still doing the initial LIST, or the watch is wedged), or RBAC forbids it from watching the resource. Confirm: controller logs showing "caches synced" and no watch errors; kubectl auth can-i --as the controller's ServiceAccount. Fix is cause-specific, but "is the loop even turning, and is this the active replica?" is always the first question.

Incident pattern · hot loop / rising work-queue depth

Symptom: a controller is at high CPU and the API server sees a flood of writes from it, but nothing converges. First cut: its workqueue_depth and workqueue_retries_total metrics, and diff two dumps of the target object to see if a field is flapping. Usual causes: a non-idempotent reconcile that writes every pass and re-triggers itself, two controllers fighting one field, or retrying a permanent error forever. Fix: only write on real change, one owner per field, make permanent failures terminal.

Incident pattern · object stuck Terminating

Symptom: a delete "succeeds" but the object stays, phase Terminating, for a long time. Cause: a finalizer whose owning controller is down, missing, or erroring during cleanup. Confirm: read deletionTimestamp and finalizers, and check that controller's health/logs. Fix: restore the controller so it completes cleanup and removes its finalizer; only force-remove the finalizer when you've accepted skipping the cleanup and understand the orphaned resources.

Production · security · performanceWhat matters in production

Reconcile must be idempotent and quiet. The single most important property of any controller you write or operate is that a reconcile with no real change makes no writes. Compare current to desired and only call the API when they differ; otherwise you create the feedback loop that becomes a hot loop and a self-DoS on the API server. Keep reconciles fast and non-blocking — never sleep or make long synchronous calls inside one; if you must wait, requeue with AddAfter and return.

Use informers; never poll. This is the Chapter 29 lesson made concrete: read from the informer cache (Lister), share informers across controllers, and let watch deliver changes. A controller that does periodic full LISTs against the API server is the classic cause of control-plane overload at scale. Watch the work-queue and reconcile metrics as first-class SLOs for your controllers — queue depth, retry rate, reconcile error rate, reconcile duration.

One owner per field, and respect backoff. Two controllers writing the same field will fight forever; decide ownership explicitly (server-side apply's field management helps). Let the rate limiter do its job — return errors for transient failures so they back off, and treat permanent failures as terminal (set a status condition, stop requeuing) rather than retrying at the cap indefinitely. Give HA controllers leader election so exactly one instance reconciles.

Mind cache staleness and finalizers. The cache is eventually consistent — you may reconcile on data a few hundred milliseconds old, so writes can hit a 409 Conflict; handle it by requeuing and re-reading, not by force-writing. And if you add a finalizer, you are promising a healthy controller will remove it — an operator that adds finalizers and then gets uninstalled leaves objects un-deletable. Common mistakes: non-idempotent reconciles, blocking reconciles, per-controller LISTs, fighting over a field, retrying permanent errors, and orphaned finalizers.

System-design connectionWhere this reaches into architecture

This pattern is bigger than Kubernetes — it's a general recipe for a control system that survives failure, and you'll reach for it whenever you build something that must keep an external world in a desired state. The ingredients: a change stream (watch is change-data-capture, the same idea as a database's replication log or a Kafka topic — Chapter 84), a local cache so reads are cheap and you don't hammer the source of truth, a debounced, backpressured work queue so bursts collapse and failures back off instead of amplifying, and an idempotent, level-triggered worker so the system converges regardless of what it missed. Every Kubernetes operator (Chapter 32), cert-manager, external-dns, and the GitOps engines Argo CD and Flux (Chapter 65) are this recipe pointed at a different desired state — a git repo, a certificate authority, a DNS provider. When you design your own sync engine or automation, copying this structure buys you self-healing, restart-safety, and graceful behaviour under load for free; rolling your own edge-triggered event handlers buys you subtle, permanent inconsistencies. It's also the deep reason Kubernetes is extensible at all: because everything is this loop over API objects, adding a new kind of object plus a controller that reconciles it makes your abstraction a first-class citizen of the platform (Chapter 32).

InterviewInterview questions & answers

Answer each in your head before opening it.

30-secWhat is an informer and why not just poll the API server?

An informer keeps a local, always-current cache of a resource type by doing one LIST and then a streaming WATCH, and it fires event handlers as changes arrive. Controllers read from that cache instead of calling the API server, so reads are free and fast. Polling — repeatedly LISTing everything on a timer — is expensive: it serializes large result sets out of etcd and, done across many controllers, overloads the API server. Watch delivers only deltas over a single long-lived connection and is served cheaply from the API server's watch cache. So informers give you fresh data and low load at once.

2-minWalk me through the path from an object changing to a controller acting.

The change lands in the API server, which bumps a resourceVersion. The controller's informer, which is watching that resource, receives the delta on its watch stream, updates its local cache (the Indexer), and fires the matching event handler. The handler doesn't reconcile inline — it computes the object's key, namespace/name (or maps a child to its owner's key via ownerReferences), and enqueues that key into a rate-limited work queue that deduplicates, so rapid changes collapse into one item. A worker goroutine pops the key and runs reconcile: it reads the object's current state from the cache via a Lister, observes the actual world, and if they differ, makes idempotent API calls to converge. On success it forgets the key; on a transient error it requeues with exponential backoff. The important subtlety is that the event only decided when to reconcile — the reconcile reads current state and acts on that, which is what makes it level-triggered and tolerant of missed or duplicate events.

DeepControllers are driven by events but called level-triggered. Reconcile that.

The events and the logic operate at different layers. Watch delivers edges — "this object changed" — purely as an efficiency mechanism so the controller doesn't poll; the event is a notification to look, and its payload is essentially ignored beyond identifying which object. The reconcile logic is level-triggered: it reads the object's full current state from the cache and computes desired-versus-actual from scratch every time, so it's a function of state, not of the transition. Three things make this resilient. First, the informer's cache is backed by a periodic relist and a resync that re-drives every key, so even if a watch event is missed, the current level is re-observed and reconciled. Second, reconcile is idempotent, so a duplicate or replayed key is a no-op. Third, the work queue deduplicates, so a burst of edges becomes one level-read. The upshot: edges optimise when work happens; levels determine what work happens. That's why you can drop events, restart the controller, or replay, and it still converges — and why edge-triggered handlers that mutate state per-event (incrementing a counter on each delete) are the classic way to introduce permanent drift.

ScenarioYou change a Deployment and nothing happens. How do you tell if the controller is even running?

I separate "did my change land" from "is the loop turning." First I confirm the write persisted — kubectl get deploy -o yaml shows my new spec and a bumped generation — so the API server accepted it. Then I check the controller. For a built-in, that's the kube-controller-manager pod: is it Running, and does its log show "caches synced" and no watch/authorization errors, and — in HA — is this the leader holding the leader-election Lease? For an operator, it's that operator's Deployment and logs. Common findings: the controller crashed or lost leadership so no instance is reconciling; its informer never finished the initial sync so it's not acting yet; or RBAC forbids it from watching the resource, which shows as watch errors in the log. I'd also check the object's Events and the controller's work-queue depth metric to see whether it enqueued the key at all. The mental model is the loop: is it running, is it the active replica, did it see the change, and did reconcile error — in that order.

Follow-upHow does this pattern relate to operators and GitOps tools?

They're the same machine pointed at different desired state. An operator (Chapter 32) is a custom controller for a Custom Resource: you define a new kind of object with its spec, then write a reconcile — using controller-runtime, which wires up the informer, work queue, workers, and leader election for you — that makes some real system match that spec. cert-manager reconciles Certificates against a CA; external-dns reconciles DNS records against a provider. GitOps engines like Argo CD (Chapter 65) do the same with the desired state living in a git repo: they watch the repo and the cluster, diff, and reconcile the cluster toward git, with the identical "OutOfSync detected → converge → retry with backoff" loop — which is why an Argo app "stuck OutOfSync" or "reconcile error" is debugged exactly like a stuck or hot-looping controller here. Learning this loop once means you understand every controller, every operator, and every reconcile-based delivery tool in the ecosystem.

RetainQuick revision

Controllers don't poll — they use list + watch to get a cheap, consistent change stream, and an informer turns that stream into a local, always-current cache (Reflector → DeltaFIFO → Indexer) plus event handlers. Handlers enqueue the object's key into a work queue that deduplicates and rate-limits with exponential backoff; a worker pops each key and runs an idempotent reconcile that reads current state from the cache, compares desired to actual, and acts through the API server, requeuing on error. The events only decide when to look; the cache decides what is true — so the loop is level-triggered and tolerant of missed or duplicate events, and it self-heals and survives restarts. The same skeleton powers every built-in controller, every operator, and Argo CD. Two failures dominate: a controller that stopped reconciling (crashed, not leader, cache not synced, RBAC) and one hot-looping (non-idempotent reconcile, two owners fighting a field, retrying a permanent error). And an object stuck Terminating is a finalizer whose controller isn't removing it.

The 10 things to remember

  1. Controllers use list + watch, never polling: LIST gives a snapshot + resourceVersion, WATCH streams deltas from it.
  2. An informer maintains a local cache (Indexer) from the watch stream and fires Add/Update/Delete handlers.
  3. "Shared" informers list/watch each type once for all controllers in a process — the fix for API-server overload.
  4. Handlers enqueue the object's key (namespace/name), not the object; the work queue deduplicates pending keys.
  5. The work queue rate-limits and backs off, so a failing key retries slowly and can't starve others.
  6. Reconcile reads current state from the cache and acts idempotently — the event only said "look now."
  7. That split makes controllers level-triggered: missed or duplicate events only delay, never corrupt.
  8. ownerReferences map children to owners (enqueue the owner's key) and drive cascading garbage collection.
  9. Stopped reconciling = crashed / not leader / cache unsynced / RBAC; hot loop = non-idempotent or fighting a field.
  10. Object stuck Terminating = a finalizer whose owning controller hasn't cleaned up and removed it.
