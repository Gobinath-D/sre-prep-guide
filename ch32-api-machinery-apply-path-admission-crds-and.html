Part IV · Kubernetes — Architecture & Internals · Chapter 32

API machinery: apply path, admission, CRDs and operators

Every kubectl apply is a request that gets authenticated, mutated, validated, and only then written to etcd — and you can splice your own code into that path, add your own object types, and write a controller that reconciles them. That is the whole extension model of Kubernetes in one chapter.

Start: Beginner→→→End: Staff-level ~40 min read · kind

By the end of this chapter you can

  • Trace a write from kubectl apply through authn, admission, validation, and into etcd — naming each stage.
  • Explain the difference between a mutating and a validating admission webhook, and where each runs in the chain.
  • Say what server-side apply is, why managedFields exists, and how two controllers can share one object without a fight.
  • Define a CRD, create a custom resource, and explain how that plus a controller equals an operator.
  • Diagnose the two API-machinery incidents that page you: a webhook outage that blocks every write, and an object stuck Terminating on a finalizer.

Why this exists · the problemThe problem: a shared API that anyone can extend

By now you can create a Deployment and watch it reconcile (Chapter 31). But two questions were left hanging. First: when you run kubectl apply -f app.yaml, what actually happens between "the YAML leaves your laptop" and "the object exists in etcd"? It is not a dumb write. The API server has to decide who you are, whether you may do this, fill in the defaults you left out, reject anything malformed, and only then persist it. That pipeline is the same for every object, and half of your "why did my apply do that?" questions live inside it.

Second: the built-in objects — Pod, Deployment, Service — cover generic workloads, but your platform has its own nouns. "A database cluster." "A hosted CI runner." "A certificate." You could bolt those on with a pile of Helm templates and a cron job, but then they are second-class: no kubectl get, no RBAC, no watch, no reconciliation. Kubernetes offers something better. You can teach the API server a new object type — a CustomResourceDefinition — and write a controller that reconciles it. From that moment your "database cluster" is a first-class API object, with the same declarative, self-healing loop as everything else. That combination is an operator.

Both answers come from one place: the API machinery. It is the request pipeline plus the extension points wired into it. Learn the pipeline and you can reason about every write; learn the extension points and you can make the platform speak your language.

Key point

The API server is not a database with a REST veneer. It is a validation and admission pipeline in front of etcd. Every write passes through authentication, authorization, mutating admission, schema validation, and validating admission before it is stored. Webhooks and CRDs are how you extend that pipeline and that schema with your own logic and your own object types — without recompiling Kubernetes.

Mental model · analogyThe mental model: a permit office

Real-world analogy

Think of the API server as a city building-permit office. You walk in with an application (your apply). At the front desk they check your ID (authentication) and your file to confirm you're allowed to file this kind of permit (authorization). Neither of those changes your form; they decide whether you get to the next window at all.

Then a clerk takes your form and fills in the standard blanks you left empty — the default setback, the standard inspection schedule — and stamps a reference number on it. That clerk is mutating admission: it can change the document. Next, an inspector checks the finished form against the building code, line by line, and either passes it or rejects it with a reason — but changes nothing. That's validating admission. Only a form that survives both gets filed in the official register (etcd).

Here's the extension part. The office can hire outside consultants for specialised checks — a fire-safety firm, a heritage board. The office sends your form out to them and waits for a yes/no (an admission webhook). If the consultant's phone is dead and the office is configured to refuse permits it can't get a ruling on, the whole permit desk grinds to a halt — a real failure you will cause at least once. And the office can agree to start accepting a brand-new kind of permit form it never handled before — a "backyard-observatory permit" — by registering its template (a CRD). After that, filing one is as routine as any other.

ArchitectureThe write path: apply → admission → etcd → controller

Here is the shape of one write. Read it left to right: your request enters the API server, passes through the gauntlet, lands in etcd, and only then does a controller — watching via the mechanism from Chapter 31 — notice and act. Nothing reconciles until the object is safely stored.

Why an SRE cares

Because both admission stages sit in the synchronous path of every write, they are a single point of failure you install yourself. A webhook you deployed with failurePolicy: Fail and a pod that later crashes will make the API server reject creates cluster-wide — including, if you're not careful, the pods that would restart your webhook. That is the classic self-inflicted outage of this chapter, and it is entirely preventable once you understand where webhooks sit.

Internal workingWhat happens between apply and etcd

1 · Every object is spec and status

Almost every Kubernetes object has two halves. spec is desired state — what you asked for, written by you. status is observed state — what is actually true, written by the controller. You apply the spec; the controller reconciles reality toward it and reports back in status. The API server enforces this split: a normal write to a resource with a status subresource ignores your status, and a write to /status ignores your spec. That's why you can't "fix" a Deployment by editing its status — status is a readout, not a control. Keep this straight and half of "my change didn't take" mysteries dissolve.

2 · The pipeline, stage by stage

When your apply arrives (as an HTTP PATCH or POST), the API server runs it through a fixed sequence:

  1. Authentication. Who is this? A client cert, a bearer token, or an OIDC identity is resolved to a username and groups. No identity, no entry.
  2. Authorization. May this identity perform this verb (create, update, patch) on this resource in this namespace? RBAC answers (Chapter 39). A no ends here with a 403.
  3. Mutating admission. Built-in mutating plugins and any registered MutatingWebhookConfiguration run. They may rewrite the object: apply defaults, inject a sidecar, add labels. Webhooks are called one at a time and can each patch the object further.
  4. Schema validation. The (possibly mutated) object is checked against the resource's OpenAPI schema — required fields present, types correct, enums valid. For a CRD, this is the schema you wrote in the CRD. This is also where structural rules and defaulting from the CRD apply.
  5. Validating admission. Built-in validating plugins, any ValidatingAdmissionPolicy (in-cluster CEL rules, no server to run), and any ValidatingWebhookConfiguration run. They may only accept or reject — no mutation. Rejections come back with a reason.
  6. Persist. The object is serialized and written to etcd through a quorum write (Chapter 29). Its resourceVersion is bumped. Only now is it real.
  7. Watchers notified. The write becomes a watch event, and every informer watching that type — including the controllers that will reconcile it — sees it. Reconciliation begins.

The order is not arbitrary. Mutating runs before validating so that defaults and injections are in place before anyone judges the object — otherwise a webhook would validate a half-filled form. And admission runs before persistence so that nothing invalid ever reaches etcd.

3 · Mutating vs validating webhooks

A webhook is an HTTPS service you run in the cluster. The API server POSTs it an AdmissionReview and reads back an allow/deny (and, for mutating, a JSON patch). Two kinds, two jobs:

  • MutatingWebhookConfiguration — runs in the mutating phase, returns a patch. Used to inject things: a service mesh injecting its sidecar, a policy engine adding default resource limits. Order matters and later webhooks see earlier webhooks' changes.
  • ValidatingWebhookConfiguration — runs in the validating phase, returns only allow/deny with a message. Used to enforce policy: "every pod must have resource limits," "no :latest tags." It cannot change the object, only refuse it.

Both carry the field that will page you one day: failurePolicy. Fail means "if you can't reach me, reject the request." Ignore means "if you can't reach me, allow it through." Fail is safer for security policy and more dangerous for availability. Both carry timeoutSeconds (keep it small — a slow webhook slows every write it matches) and selectors (namespaceSelector, objectSelector) to scope which requests they intercept. Scoping is not optional at scale; an unscoped Fail webhook is a cluster-wide fuse.

Prefer in-tree policy where you can

For pure validation — "reject pods without limits," "require a label" — you often don't need a webhook at all. ValidatingAdmissionPolicy (GA since Kubernetes 1.30) lets you write the rule in CEL as an API object that the API server evaluates itself. No server to run, no failurePolicy outage to cause, no extra network hop on every write. Reach for a webhook only when you need to mutate, or when your logic can't be expressed in CEL. This is the current, recommended default for policy enforcement.

4 · Server-side apply and managedFields

Old kubectl apply computed diffs on the client using a "last-applied-configuration" annotation — fragile, and it lost track when more than one actor edited an object. Server-side apply (SSA) moved that logic into the API server. Each actor declares a field manager name and sends only the fields it owns; the API server records, per field, who owns it in metadata.managedFields. If two managers try to own the same field with different values, you get a conflict — surfaced instead of silently overwritten. You resolve it by force-applying (take ownership) or by not touching fields you don't own.

This is why controllers and GitOps engines use SSA: it lets a Deployment's replicas be owned by an HPA while its image is owned by your CI, on the same object, without them clobbering each other. When you see managedFields cluttering a kubectl get -o yaml, that's SSA bookkeeping — the record of who owns what.

5 · Finalizers: deletion with a pause

A finalizer is a string in metadata.finalizers that means "don't actually delete this object until I've cleaned up." When you delete an object that has finalizers, the API server does not remove it. Instead it sets metadata.deletionTimestamp — the object is now "marked for deletion" but still present. A controller that owns the finalizer notices the timestamp, performs its cleanup (deregister DNS, delete a cloud load balancer, snapshot a volume), then removes its finalizer string. When the last finalizer is gone, the API server deletes the object for real. Finalizers are how Kubernetes guarantees external cleanup happens before an object vanishes — and, when the owning controller is dead, exactly why objects get stuck Terminating forever.

Think first: you register a validating webhook with failurePolicy: Fail, then its pod crashes. What happens to unrelated kubectl apply commands?

They fail — if they match the webhook's rules. With failurePolicy: Fail, the API server must get an allow from the webhook before persisting a matching object; if it can't reach the webhook, it rejects the write with an error like failed calling webhook ... connection refused. So every create/update the webhook was scoped to now returns an error, even though the object itself is fine and etcd is healthy. The blast radius is exactly the webhook's rules and selectors: an unscoped webhook that matches pods in all namespaces will block pod creation cluster-wide — potentially including the webhook's own replacement pod, which is how these turn into deadlocks. The fixes are all preventive: scope tightly with selectors, exclude kube-system, keep timeoutSeconds low, run the webhook HA, and use Ignore (or in-tree policy) for anything that isn't a hard security gate.

ComponentsThe pieces, named

  • kube-apiserver — runs the whole pipeline: authn, authz, admission, schema validation, persistence, and watch. Everything in this chapter is a stage or an extension point inside it.
  • Admission plugins (built-in) — compiled-in mutating and validating controllers (defaulting, NamespaceLifecycle, ResourceQuota, PodSecurity, and others). They run before any webhook.
  • MutatingWebhookConfiguration / ValidatingWebhookConfiguration — API objects that register your out-of-process webhooks into the mutating and validating phases, with rules, selectors, failurePolicy, and timeoutSeconds.
  • ValidatingAdmissionPolicy — in-tree CEL policy evaluated by the API server itself; the webhook-free way to enforce validation rules (GA since 1.30).
  • CustomResourceDefinition (CRD) — apiextensions.k8s.io/v1. Teaches the API server a new resource type, with its OpenAPI schema, versions, and whether it has a status subresource.
  • Custom Resource (CR) — an instance of a CRD's type. Once the CRD exists, a CR behaves like any built-in object: stored in etcd, RBAC-controlled, watchable, gettable with kubectl.
  • Controller / operator — the reconcile loop (Chapter 31) that watches your CRs and makes reality match them. CRD + controller = operator.
  • Finalizers & managedFields — the two metadata fields this chapter turns from mystery into tool: deletion hooks, and server-side-apply ownership.

Data flowFollowing one kubectl apply of a Deployment

Watch a single kubectl apply -f deploy.yaml go all the way through:

  1. kubectl reads your file and sends a server-side apply PATCH to /apis/apps/v1/namespaces/default/deployments/web, with a field-manager name of kubectl.
  2. The API server authenticates you and checks RBAC: may you patch deployments here? Yes.
  3. Mutating admission runs: defaulting fills in the fields you omitted (strategy, revisionHistoryLimit), and any mutating webhook — say a mesh injector — patches in a sidecar container.
  4. The merged object is schema-validated against the apps/v1 Deployment schema. Missing a required field or a bad type fails here.
  5. Validating admission runs: ResourceQuota checks you're within namespace limits, PodSecurity checks the pod template against the namespace's standard, and any validating webhook or policy has its say. All allow.
  6. The API server records field ownership in managedFields (yours as kubectl), writes the object to etcd, and bumps its resourceVersion.
  7. The write is now a watch event. The Deployment controller's informer sees the new object, reconciles it into a ReplicaSet, which reconciles into Pods (Chapter 33). None of that happened during your apply — your apply just made the desired state real; the loop took it from there.

Every one of those stages can reject you, and each rejection has a distinct fingerprint: 401 (authn), 403 (RBAC), a defaulting surprise (mutating), a schema error (validation), a policy denial (validating). Knowing which stage spoke tells you where to look.

Lab 1Build — define a CRD and create a custom resourceBuild

Teach the API server a new type, then use it like any built-in. Save this CRD — a toy "Widget" with a schema and a status subresource:

yaml
# widget-crd.yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: widgets.demo.example.com
spec:
  group: demo.example.com
  scope: Namespaced
  names: { kind: Widget, plural: widgets, singular: widget, shortNames: [wg] }
  versions:
  - name: v1
    served: true
    storage: true
    subresources: { status: {} }
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            required: [size]
            properties:
              size: { type: integer, minimum: 1, maximum: 10 }
          status:
            type: object
            properties:
              phase: { type: string }
bash
kubectl apply -f widget-crd.yaml
kubectl api-resources | grep widgets
kubectl apply -f - <<'EOF'
apiVersion: demo.example.com/v1
kind: Widget
metadata: { name: w1 }
spec: { size: 3 }
EOF
kubectl get widgets
Outputwidgets demo.example.com/v1 true Widget NAME AGE w1 4s

You just extended the API. widgets is now a first-class resource: kubectl get/describe/edit work, RBAC applies, and informers can watch it. Prove the schema is real — try an out-of-range value:

bash
kubectl apply -f - <<'EOF'
apiVersion: demo.example.com/v1
kind: Widget
metadata: { name: bad }
spec: { size: 99 }
EOF
OutputThe Widget "bad" is invalid: spec.size: Invalid value: 99: spec.size in body should be less than or equal to 10

That rejection came from schema validation, stage 4 of the pipeline — the API server enforcing your CRD schema. There is no controller yet, so nothing acts on the Widget; a CRD alone gives you storage and validation. Add a reconciler and you have an operator.

Lab 2Understand — server-side apply and field ownershipUnderstand

See managedFields record who owns what, then trigger a conflict on purpose.

bash
kubectl create deployment web --image=nginx:1.27-alpine
# Actor A ("ci") owns the image via server-side apply:
kubectl apply --server-side --field-manager=ci -f - <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata: { name: web }
spec:
  template:
    spec:
      containers:
      - { name: nginx, image: nginx:1.27-alpine }
EOF
kubectl get deploy web -o jsonpath='{range .metadata.managedFields[*]}{.manager}{"\n"}{end}'
Outputkubectl ci

Two managers own different slices of the same object. Now have a second actor try to set the same image to a different value, without forcing:

bash
kubectl apply --server-side --field-manager=other -f - <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata: { name: web }
spec:
  template:
    spec:
      containers:
      - { name: nginx, image: nginx:1.25 }
EOF
Outputerror: Apply failed with 1 conflict: conflict with "ci": .spec.template.spec.containers[name="nginx"].image Please review the fields above--they currently have a manager. You may co-own fields ... or --force-conflicts.

That conflict is the whole point of SSA: two actors wanting the same field is surfaced, not silently resolved by whoever wrote last. In a GitOps setup this is how Argo CD (Chapter 65) detects that something else is fighting it for a field. You'd resolve it deliberately — one owner per field, or an explicit --force-conflicts to take over.

Lab 3Break — a webhook outage blocks every applyBreak

You don't need to write a webhook server to feel the failure mode — you just need to register a webhook that points at a service that isn't there, with failurePolicy: Fail. This is the single most common self-inflicted API-machinery outage, reproduced safely.

bash
kubectl apply -f - <<'EOF'
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata: { name: doomed }
webhooks:
- name: doomed.demo.example.com
  admissionReviewVersions: ["v1"]
  sideEffects: None
  failurePolicy: Fail
  timeoutSeconds: 5
  clientConfig:
    service: { name: nowhere, namespace: default, path: "/validate" }
  rules:
  - apiGroups: [""]
    apiVersions: ["v1"]
    operations: ["CREATE"]
    resources: ["configmaps"]
EOF
# Now try to create a ConfigMap — the webhook it points to does not exist:
kubectl create configmap probe --from-literal=k=v
OutputError from server (InternalError): Internal error occurred: failed calling webhook "doomed.demo.example.com": failed to call webhook: Post "https://nowhere.default.svc:443/validate?timeout=5s": service "nowhere" not found

Every ConfigMap create in the cluster now fails — not because ConfigMaps are broken, but because a Fail webhook in the write path can't be reached. You caused a cluster-wide outage with one manifest and no running code. Before you clean it up, notice the shape of the error: failed calling webhook is the fingerprint. Now think about the safe version.

How would you have made this webhook safe to deploy?

Four levers, and you'd use all of them. Scope it with a namespaceSelector so it only intercepts the namespaces it must — and always exclude control-plane namespaces (label kube-system and add a selector that skips it), so a broken webhook can never block the pods that would fix it. Choose failurePolicy: Ignore unless this is a hard security gate; a policy webhook that fails open degrades gracefully, one that fails closed takes an outage. Keep timeoutSeconds small (1–5s) so a slow webhook doesn't add latency to every write it matches. And run the webhook HA with a PodDisruptionBudget so a single node drain doesn't down it. For pure validation, skip the webhook entirely and use a ValidatingAdmissionPolicy — no server, no outage to cause. Clean up: kubectl delete validatingwebhookconfiguration doomed, and ConfigMap creates work again instantly.

bash
kubectl delete validatingwebhookconfiguration doomed
Lab 4Troubleshoot — a custom resource stuck TerminatingTroubleshoot

Give the Widget a finalizer that no controller owns, then delete it and watch it refuse to go.

bash
kubectl patch widget w1 --type=merge \
  -p '{"metadata":{"finalizers":["demo.example.com/cleanup"]}}'
kubectl delete widget w1 --wait=false
kubectl get widget w1
OutputNAME AGE w1 5m # still here — the delete "succeeded" but the object remains

The delete returned without error, yet w1 is still listed. Why is it stuck, and what is the difference between the safe fix and the dangerous one? Work it out before revealing.

Reveal the diagnosis

The object now carries a deletionTimestamp (it's marked for deletion) but its finalizers list is non-empty, and the API server will not remove an object until every finalizer is cleared. Normally a controller owns that finalizer: it sees the deletionTimestamp, runs its cleanup, removes its finalizer, and the object disappears. Here nothing owns demo.example.com/cleanup, so it hangs in Terminating forever. Confirm:

bash
kubectl get widget w1 -o jsonpath='{.metadata.deletionTimestamp}{"  "}{.metadata.finalizers}{"\n"}'
Output2026-09-21T10:14:03Z ["demo.example.com/cleanup"]

The right fix in production is to make the owning controller healthy again so it completes cleanup and removes its own finalizer. The blunt fix — only when the controller is gone for good and you accept skipping whatever cleanup it would have done — is to clear the finalizer by hand: kubectl patch widget w1 --type=merge -p '{"metadata":{"finalizers":null}}', after which it deletes instantly. Force-clearing finalizers on real resources (a namespace stuck Terminating, a PV) can orphan external infrastructure — a cloud load balancer or disk the controller never got to delete — so it is a last resort, not a reflex. This exact shape recurs everywhere finalizers do: operators, namespaces, PVs.

Lab 5Production challenge — design a mutating webhook you can trustSenior challenge

Your platform team wants to inject a default set of resource limits into every pod that lacks them, cluster-wide, via a mutating webhook. That is a webhook in the write path of every pod creation — including system pods and its own. Sketch how you'd deploy it without ever taking the cluster down. Reason first.

Reveal the approach

Start by questioning the webhook at all: if you only need to enforce that limits exist, a ValidatingAdmissionPolicy in CEL does it with no server. But injection is a mutation, so a mutating webhook is justified here. Then make it safe by construction:

  • Scope by namespace. Use a namespaceSelector that opts namespaces in (a label like limits-injection=enabled) rather than matching everything. Explicitly exclude kube-system and your own webhook's namespace so the control plane and the injector itself are never intercepted.
  • failurePolicy: Ignore, at least at first. A defaulting webhook that fails open lets pods through un-injected during an outage — degraded, not down. You can tighten to Fail later once it has proven reliable, and only if the injection is truly mandatory.
  • Small timeoutSeconds and HA. 1–2 seconds, at least two replicas across nodes, a PDB with minAvailable: 1, and — critically — the webhook's own pods excluded from its rules so it can always restart.
  • reinvocationPolicy and idempotency. Other mutating webhooks may run after yours; set reinvocationPolicy: IfNeeded if order matters, and make the patch idempotent so re-invocation doesn't double-inject.
  • Roll out behind a canary namespace. Enable the opt-in label on one test namespace, verify injection, then widen. Watch API-server request latency and webhook error rate as you go.

The through-line: a webhook is infrastructure in the synchronous path of writes, so you engineer its availability like any other critical dependency — scope, timeouts, HA, fail-open by default, and a self-exclusion so it can never wedge its own recovery. Failure & troubleshootingHow this shows up in real incidents

Incident pattern · a webhook outage blocks all writes

Symptom: kubectl apply and controllers start failing across the cluster with failed calling webhook ...; new pods won't create, deployments stall. First cut: read the error — it names the webhook. kubectl get validatingwebhookconfigurations,mutatingwebhookconfigurations and find the one whose backing service is unhealthy. Usual cause: a webhook with failurePolicy: Fail whose pods are down (node drain, crash, image pull) and which is scoped too broadly. Fix now: restore the webhook's pods; if they can't start because the webhook blocks their own creation, delete the offending WebhookConfiguration to break the deadlock, then fix and re-apply it with a self-exclusion and tighter scope.

Incident pattern · object stuck Terminating on a finalizer

Symptom: a delete "succeeds" but the object lingers in Terminating for minutes or forever — common with namespaces and CRs from operators. Confirm: read metadata.deletionTimestamp and metadata.finalizers; the object is marked for deletion but a finalizer remains. Cause: the controller that owns that finalizer is down, uninstalled, or erroring during cleanup. Fix: make that controller healthy so it finishes cleanup and removes its finalizer; force-remove the finalizer only when you've accepted the orphaned external resources.

Incident pattern · SSA field conflicts / fields flapping

Symptom: a field (often replicas or an image) keeps reverting, or apply fails with conflict with "<manager>". Cause: two actors own the same field — a manifest and the HPA both setting replicas, or two GitOps tools managing one object. Confirm: read metadata.managedFields to see who owns the contested field. Fix: decide one owner per field — stop managing replicas from git if the HPA owns it — rather than force-applying in a loop, which just moves the fight.

Production · security · performanceWhat matters in production

Webhooks are availability risks, so treat them as critical infrastructure. Every admission webhook you register sits in the synchronous path of the writes it matches, which means its availability is now your cluster's write availability for those objects. Scope every webhook with selectors, exclude control-plane namespaces, keep timeouts to a few seconds, run at least two replicas with a PDB, and default to failurePolicy: Ignore unless the check is a hard security gate that you'd genuinely rather fail closed. Never let a webhook match its own pods. For pure validation, prefer ValidatingAdmissionPolicy — no server means no outage to cause.

CRDs are a schema and an API contract — version them like one. A CRD's OpenAPI schema is the validation for its CRs, so write it tightly (required fields, ranges, enums) rather than accepting free-form objects. When the schema changes incompatibly, add a new version and a conversion strategy; don't mutate a served version's meaning under running controllers. Mark exactly one version as storage: true. Remember the etcd cost: thousands of CRs are thousands of objects the API server lists and watches, so a chatty operator that creates a CR per request will pressure the control plane the same way any object churn does (Chapter 29).

Admission is a security control, but PodSecurity Admission replaced PSP. The built-in Pod Security Admission controller enforces the Pod Security Standards (privileged / baseline / restricted) per namespace via labels — this is the current mechanism; PodSecurityPolicy was removed in 1.25 and you should never reach for it. Layer your own policy on top with ValidatingAdmissionPolicy or a policy engine (Kyverno, Gatekeeper) running as webhooks. Keep in mind that admission runs after authorization, so it's defense in depth on top of RBAC, not a replacement for it.

Common mistakes: an unscoped Fail webhook (the outage in Lab 3); a webhook that matches its own namespace and deadlocks its recovery; treating a CRD's schema as optional and getting garbage CRs; force-applying in a loop to "win" an SSA conflict instead of fixing ownership; and adding a finalizer from an operator that later gets uninstalled, leaving objects un-deletable. Each one is avoidable with the model in this chapter.

System-design connectionWhere this reaches into architecture

This chapter is why Kubernetes is a platform and not just a container runner. The CRD-plus-controller pattern means the API server is an extensible, watchable, RBAC-governed database of desired state that you get to add nouns to — and the reconcile loop (Chapter 31) makes each new noun self-healing for free. That's the foundation of the entire operator ecosystem: cert-manager reconciles Certificate objects against a CA, external-dns reconciles DNS records, and a database operator reconciles a PostgresCluster into StatefulSets, Services, and backups. When you design an internal platform, the decision "should this be a CRD or just config?" is really "does this deserve a control loop, RBAC, and status?" — if yes, model it as a CRD and you inherit the whole machine. Admission is the other half of the design story: it's where org-wide policy lives — no :latest images, mandatory limits, required labels — enforced uniformly at the one chokepoint every write must pass. And server-side apply is what makes GitOps engines like Argo CD (Chapter 65) able to co-manage objects with HPAs and other controllers without an endless overwrite war. Get this layer right and your platform is declarative, governed, and extensible; get it wrong and you've either bolted brittle automation onto the side or installed a fuse that blows the whole cluster.

30-secWhat is the difference between a mutating and a validating admission webhook?

Both are HTTPS services the API server calls during a write, but they run in different phases and have different powers. A mutating webhook runs first and can change the object — return a patch to add defaults or inject a sidecar. A validating webhook runs after, once the object is finalized, and can only accept or reject it with a reason — it cannot mutate. Mutating before validating is deliberate, so the object is fully formed before anyone judges it. Both carry a failurePolicy that decides what happens if the webhook is unreachable.

2-minWalk me through what happens from kubectl apply to the object being stored.

kubectl sends the manifest as a request to the API server — with server-side apply, a PATCH tagged with a field-manager name. The API server authenticates the caller, then authorizes with RBAC: may this identity perform this verb on this resource here? Then mutating admission runs — built-in defaulting plus any mutating webhooks — which can rewrite the object, adding defaults or injecting containers. The merged object is validated against its OpenAPI schema (for a CRD, the schema you defined). Then validating admission runs — ResourceQuota, PodSecurity, any validating webhook or CEL policy — which can only accept or reject. If everything allows, the API server records field ownership in managedFields, writes the object to etcd via a quorum write, and bumps its resourceVersion. That write becomes a watch event, and only then do controllers see it and begin reconciling. The key idea: the API server is an admission pipeline in front of etcd, and reconciliation is a separate, later step driven by watch.

DeepWhat is server-side apply solving, and how do managedFields work?

The problem is multiple actors editing one object. The old client-side apply stored your last-applied config in an annotation and diffed against it on the client, which broke when anything other than you also edited the object — you'd silently clobber a field an HPA or another controller set. Server-side apply moves the merge into the API server and tracks ownership per field. Each actor supplies a field-manager name and sends only the fields it intends to own; the API server records, in metadata.managedFields, which manager owns which field paths. If a second manager tries to set a field a different manager already owns to a conflicting value, the apply fails with a conflict instead of overwriting — you either co-own, hand off, or explicitly force. This is what lets a Deployment's replicas be owned by an HPA while its image is owned by CI, on the same object, without a fight, and it's how Argo CD detects drift and rival managers. The cost is the managedFields bookkeeping cluttering objects, but the payoff is deterministic multi-writer semantics. It pairs naturally with the reconcile loop: controllers apply only the fields they own, every reconcile, idempotently.

ScenarioSuddenly no new pods can be created cluster-wide and applies fail with "failed calling webhook." What do you do?

I read the error first — it names the webhook. That tells me an admission webhook with failurePolicy: Fail is in the write path and unreachable. I list validatingwebhookconfigurations and mutatingwebhookconfigurations, find the named one, and check its backing service and pods — almost always they're down: a node drain, a crash, an image-pull failure, or the webhook got scoped so broadly it's now blocking its own replacement pod from starting, a deadlock. To restore writes immediately I delete that WebhookConfiguration, which removes it from the path; pod creation recovers at once. Then I fix the root cause — get the webhook's pods healthy — and re-register it, this time scoped with a namespaceSelector that excludes kube-system and the webhook's own namespace, with a small timeout, HA replicas plus a PDB, and failurePolicy: Ignore unless it's a hard security gate. The lesson I'd state: a webhook is a synchronous dependency of every write it matches, so its availability is cluster write availability, and it must never be able to block its own recovery.

Follow-upWhat exactly is an operator, and when should something be a CRD?

An operator is a custom controller plus the custom resource type it reconciles: you define a CRD — say PostgresCluster — with its schema and status, then run a controller (usually built with controller-runtime, which wires up the informer, work queue, and workers for you) that watches those CRs and makes real infrastructure match them: StatefulSets, Services, backups, failover. It's the exact reconcile loop from the controllers chapter, pointed at your domain. Something should be a CRD when it deserves a control loop and an API: when you want kubectl get, RBAC, watch, status, and self-healing reconciliation for a concept your platform owns. If it's just static values a pod reads once, a ConfigMap is enough — you don't need an API object or a controller. The test I use: does this thing have a desired state that drifts and must be continuously reconciled against reality? If yes, model it as a CRD and inherit the whole machine; if no, it's config. cert-manager, external-dns, and every database operator are this pattern, and so is Argo CD reconciling git into the cluster.

RetainQuick revision

The API server is an admission pipeline in front of etcd, not a plain datastore. Every write is authenticated, authorized (RBAC), mutated (defaulting and mutating webhooks, which can change the object), schema-validated, then validated (built-in checks, CEL policy, validating webhooks, which can only accept or reject), then persisted — and only after persistence do controllers see it via watch and reconcile. Objects are split into spec (desired, yours) and status (observed, the controller's). Server-side apply tracks per-field ownership in managedFields so multiple actors can co-manage one object and conflicts surface instead of silently clobbering. Finalizers pause deletion until an owning controller cleans up and removes them — and a finalizer whose controller is gone is why objects stick in Terminating. You extend the platform with CRDs (new object types with their own schema) plus controllers that reconcile them; CRD + controller = operator. The two incidents that page you: a broadly-scoped failurePolicy: Fail webhook whose outage blocks all matching writes, and a stuck-Terminating object waiting on an unowned finalizer.

The 10 things to remember

  1. The API server runs a pipeline before etcd: authn → authz → mutating admission → schema validation → validating admission → persist → watch.
  2. spec is desired state (you write it); status is observed state (the controller writes it) — editing status doesn't change reality.
  3. Mutating webhooks run first and can change the object; validating webhooks run after and can only accept or reject.
  4. failurePolicy: Fail makes an unreachable webhook block matching writes; scope tightly, exclude kube-system, prefer Ignore for non-security checks.
  5. For pure validation, use in-tree ValidatingAdmissionPolicy (CEL, GA 1.30) — no server, no outage to cause.
  6. Server-side apply tracks per-field ownership in managedFields; conflicting owners surface a conflict instead of overwriting.
  7. A finalizer pauses deletion (sets deletionTimestamp) until its owning controller cleans up and removes it.
  8. A CRD (apiextensions.k8s.io/v1) teaches the API server a new type with its own OpenAPI schema, versions, and status subresource.
  9. CRD + a controller that reconciles it = an operator; that's the platform's whole extension model.
  10. Pod Security Admission (not PSP, removed in 1.25) enforces Pod Security Standards per namespace; admission runs after RBAC, as defense in depth.
