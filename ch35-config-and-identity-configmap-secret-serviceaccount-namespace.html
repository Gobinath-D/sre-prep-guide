Part IV · Kubernetes — Architecture & Internals · Chapter 35

Config and identity: ConfigMap, Secret, ServiceAccount, Namespace

A container image should never know which environment it's running in, and a pod should never carry a password baked into its filesystem. Kubernetes solves both with objects you'll touch every single day — and two of them, Secret and Namespace, are far weaker guarantees than their names suggest until you understand exactly what they do and don't do.

Start: Beginner→→→End: Staff-level ~40 min read · kind

By the end of this chapter you can

  • Mount a ConfigMap and a Secret both ways — env var and volume — and say precisely which one updates live and which one doesn't.
  • Explain why a Secret is base64, not encryption, and what actually has to be true for Secrets to be encrypted at rest.
  • Use the downward API and a projected volume to hand a container its own pod metadata without an API call.
  • Trace a ServiceAccount token from creation to auto-rotation, and say why long-lived Secret-based tokens are legacy.
  • Diagnose the two incidents that show up here every quarter: a leaked Secret, and a config change that "didn't take."

Why this exists · the problemThe problem: code shouldn't know where it's running

Take the simplest possible service: it needs a database hostname, an API key, and it needs to prove to the cluster who it is when it calls another service. You could bake all three into the container image. Don't — you'd need a new image for every environment, the API key would sit in your image registry forever, and "who is this pod" would have no answer at all beyond "some process."

Kubernetes splits this into two separate problems, because they have different owners and different risk. Configuration is data your app needs to run correctly — hostnames, feature flags, timeouts. It's not secret; it's just external, so the same image runs anywhere. Identity is a different question entirely: when this pod calls the API server, or another service, who is it, and what is it allowed to do? Configuration is a ConfigMap. Sensitive configuration — passwords, tokens, certificates — is a Secret. Identity is a ServiceAccount. And the boundary all of these live inside, the unit you scope access and quota to, is a Namespace.

The trap is assuming the names tell you the whole story. "Secret" sounds encrypted. It isn't, by default. "Namespace" sounds like a security boundary. It's a scoping boundary — security is what you build on top of it with RBAC. This chapter is about closing that gap between what these objects sound like and what they actually guarantee.

Key point

A ConfigMap and a Secret are the same object shape — key/value data attached to a Pod — with different intent and different handling. A ServiceAccount is a pod's identity when it talks to the API server or anything federated to it. A Namespace is the scope that all of the above, plus RBAC and quota, are evaluated inside. None of these four objects are encrypted, isolated, or secure by themselves; each one becomes secure only when you configure the layer underneath it.

Mental model · analogyThe mental model: move-in day in an office building

Real-world analogy

Picture an office building split into floors, one floor per team — that's a Namespace. Move into your floor and you get a company ID badge automatically, the same badge everyone on your floor starts with unless you request a different one — that's the default ServiceAccount, issued per namespace whether you ask for it or not.

Pinned to the break-room wall is a memo board anyone on the floor can read: the wifi password for guests, today's lunch menu, the build number to deploy. That's a ConfigMap — plain, readable, not meant to be sensitive. Now picture a supply cabinet labeled "Confidential" — except the door is glass. Anyone who can reach the cabinet can see exactly what's inside; there's no lock unless you install one. That's a Secret: it looks separate and special, but by default it's just as readable as the memo board to anyone with permission to open the cabinet door — the "encryption" is nothing more than the equivalent of frosted glass (base64), not a lock.

Your ID badge itself isn't a lifetime pass. It's reissued fresh — say, every hour — and the front desk automatically swaps your old badge for a new one before it expires, so you're never caught standing at a door with a dead badge. That's the modern, auto-rotating ServiceAccount token. The old way — a badge printed once, laminated, and valid forever until someone remembers to shred it — is exactly the legacy long-lived Secret-based token Kubernetes stopped issuing by default years ago.

ArchitectureFour sources, two delivery paths, one boundary

Everything in this chapter reduces to one diagram. ConfigMaps, Secrets, a pod's own downward-API fields, and its ServiceAccount token all reach a container through exactly two mechanisms — an environment variable or a mounted file — and those two mechanisms behave differently in the one way that causes the most incidents: whether they update after the pod has started.

Why an SRE cares

This one diagram explains two incidents you will absolutely have. "I rotated the Secret and nothing changed" means the consumer used an env var. "Anyone with read access to this namespace can see our API keys in plaintext" means nobody turned on encryption at rest. Neither is a bug — both are the system doing exactly what it says, read by someone who assumed otherwise.

Internal workingHow config and identity actually reach a container

1 · Env var vs volume — the distinction that matters most

A ConfigMap or Secret's keys can be consumed four ways: as individual env vars (valueFrom.configMapKeyRef / secretKeyRef), as a bulk set of env vars (envFrom), as files in a mounted volume, or by an app reading the Kubernetes API directly. The first two are fixed at container start — the kubelet resolves the value once, injects it into the container's environment, and never touches it again. The third is different: the kubelet's sync loop notices when the underlying ConfigMap or Secret changes and rewrites the files in the volume, typically propagated by a watch (the default), so the container sees new content without a restart.

Two sharp edges. First, a volume mount using subPath to expose a single file does not get updates — Kubernetes has to bind-mount that one path at pod start and can't re-target it later, so subPath quietly opts you out of live updates. Second, even a live-updating volume only changes the file on disk — your process has to notice and reread it. Most apps don't watch their config files, so "the volume updated" and "the app picked it up" are two different facts.

2 · Secrets are base64, not encryption — and here's what actually encrypts them

A Secret's data field holds base64-encoded strings. Base64 is an encoding, not a cipher — there is no key, and kubectl get secret -o jsonpath='{.data.password}' | base64 -d reverses it in one command, for anyone with RBAC read on that Secret. That's true of the copy the API server hands back to kubectl, and it's true of the copy sitting in etcd, unless you've configured something specifically to change that.

The something is an EncryptionConfiguration passed to the API server via --encryption-provider-config. It lists providers per resource type — identity (no encryption, the default), aescbc/aesgcm/secretbox (a local key you manage), or kms (envelope encryption through an external key-management service). KMS v2 is stable since Kubernetes 1.29; KMS v1 is deprecated since 1.28 and disabled by default since 1.29. Envelope encryption means the actual Secret bytes are encrypted with a data-encryption key (DEK), and the DEK itself is encrypted by a key-encryption key (KEK) that lives in your remote KMS — the API server never sees the KEK directly, only a wrapped DEK it hands to a local KMS plugin over a Unix socket. KMS v2 generates a fresh DEK per encryption via a key-derivation function and caches unwrapped DEKs in memory, which is why it's faster than v1 under load. Once configured, an encrypted Secret in etcd is prefixed k8s:enc:kms:v2: instead of sitting there in the clear. The Kubernetes project recommends rotating the KEK at least every 90 days.

Turning on encryption doesn't retroactively encrypt anything

Encryption at rest only applies to writes made after you configure it. Every Secret written before that point stays exactly as it was in etcd until something rewrites it. The documented fix is a deliberate no-op update across every Secret: kubectl get secrets --all-namespaces -o json | kubectl replace -f -. Skip that step and you've enabled encryption in name only.

3 · The downward API: a pod reading its own fields, no API call needed

Sometimes a container just needs to know about itself — its own name, its namespace, which node it landed on — without linking a Kubernetes client into the app. The downward API exposes a fixed set of fields two ways, and the two ways don't expose the same fields:

  • Available as either env var or volume file: metadata.name, metadata.namespace, metadata.uid, a single metadata.labels['key'], a single metadata.annotations['key'].
  • Env var only: spec.serviceAccountName, spec.nodeName, status.hostIP, status.podIP (and their dual-stack *IPs forms).
  • Volume only: the entire metadata.labels or metadata.annotations map, one per line — you cannot get "all labels" as a single env var, only individual keys.
  • Container resources, via resourceFieldRef: limits.cpu, requests.cpu, limits.memory, requests.memory, and the ephemeral-storage/hugepages-* equivalents. If you expose a limit that was never set, the kubelet falls back to the node's allocatable capacity rather than reporting nothing.

The same env-vs-volume rule from section 1 applies here too: a downward-API volume updates when the underlying label or annotation changes; a downward-API env var is frozen at start, full stop — this is explicitly true even with in-place pod resizing, where a resized container's downward-API volume reflects the new CPU/memory values but its env vars still show what was set at creation.

Think first: your app reads its database password from an env var sourced from a Secret. You rotate the Secret in place. Does the running pod pick up the new password?

No. An env var sourced via secretKeyRef is resolved once, when the container starts, and the kubelet never revisits it. The Secret object now holds the new password; the running container's environment still holds the old one, indefinitely, until something restarts that container — a new rollout, a crash, a manual kubectl rollout restart. This is precisely why "I rotated it" and "it's rotated everywhere" are different claims. If you need rotation to propagate without a restart, the consumer has to mount the Secret as a volume and actively reread the file, or you accept that rotation requires a rollout.

4 · Projected volumes: one mount, several sources

A projected volume combines secret, configMap, downwardAPI, and serviceAccountToken sources into a single volume with one mount point, each source landing at whatever path you specify. This is exactly how the default ServiceAccount token is delivered — not as a lone Secret mount but as a projected volume carrying the token file, a ca.crt, and the namespace, all under /var/run/secrets/kubernetes.io/serviceaccount/. Reach for a projected volume any time an app expects several unrelated inputs under one directory instead of scattered across separate mounts.

5 · A ServiceAccount token's actual life cycle

Every pod runs as a ServiceAccount — the namespace's default one if you don't specify another, auto-recreated by the control plane if you delete it. Since Kubernetes 1.22, when a pod is admitted, the kubelet doesn't just find a pre-existing Secret to attach — it calls the TokenRequest API to mint a fresh, bound JWT: bound to an audience (who may accept it), a time limit (roughly one hour by default), and the object using it (that specific pod, by UID). The kubelet mounts it into the projected volume above and rotates it automatically, requesting a replacement well before expiry so the container never holds a dead token. Delete the pod, and the API server can invalidate the token immediately because it's bound to that pod's UID — a property a plain long-lived Secret never had.

That's a deliberate replacement for the old model. Before 1.24, every ServiceAccount got a permanent, non-expiring kubernetes.io/service-account-token Secret automatically, and that Secret was the credential — steal it once and it works forever. The LegacyServiceAccountTokenNoAutoGeneration feature gate stopped that automatic creation by default from 1.24, and by 1.27 that new behavior became permanent — you can still manually mint a long-lived Secret-based token if something truly needs one, but the project explicitly does not recommend it. Set automountServiceAccountToken: false on the ServiceAccount or the Pod when a workload never talks to the API server at all — the most common, cheapest hardening step nobody does by default.

This same identity is the seed for cloud IAM federation. When a pod's ServiceAccount token is trusted by AWS via an OIDC federation, that pod can assume a real IAM role with no static AWS credentials anywhere in the cluster — that's IRSA, and its EKS-native successor, covered in full in Chapter 55. Everything in this section — bound, short-lived, audience-scoped tokens — is exactly what makes that federation safe to trust.

Think first: does deleting a Secret that a pod's environment variable already pulled a value from affect that running pod?

Not immediately, and not automatically. Deleting the Secret removes the object from etcd and the API, so nobody can read it going forward — but a container that already has the value in its process environment keeps running with it in memory; the kubelet doesn't reach into a live container and scrub variables. A volume-mounted Secret behaves differently the moment the source disappears: the mount may go stale or empty on the next sync, which is often worse — the app can start failing reads with no warning rather than continuing to run on an old value. Either way, "delete the Secret" is not "revoke the credential" for anything already running; it only stops new consumers from reading it. If the credential itself must stop working, you rotate it at the source (the database, the third-party API) and restart every consumer — deleting the Kubernetes object is bookkeeping, not revocation.

6 · Namespace: the scope everything above lives inside

A Namespace partitions names, RBAC, and quota — a ConfigMap named app-config in team-a is a completely different object from one named app-config in team-b. Not everything is namespaced: Nodes, PersistentVolumes, ClusterRoles, and CustomResourceDefinitions themselves are cluster-scoped, visible and named the same everywhere. Every cluster starts with four namespaces: default (where unqualified objects land), kube-system (control-plane and system components — never put workloads here), kube-public (readable by every authenticated user, rarely used), and kube-node-lease (one Lease object per node, used for fast node-heartbeat tracking). RBAC's RoleBinding can grant a ServiceAccount from one namespace access to resources in another — the standard pattern for "let this CI pipeline in ci read Jobs in batch" — which is the first sign that a Namespace boundary is a scoping convenience, not a hard wall; access across it is one RoleBinding away. Full RBAC mechanics are Chapter 39. And because deleting a Namespace cascades to everything inside it, a Namespace can get stuck Terminating for exactly the finalizer reasons covered in Chapter 32 — a custom resource inside it with a finalizer whose controller is gone will hold the whole namespace open.

ComponentsThe pieces, named

  • ConfigMap — v1; plain UTF-8 data or base64 binaryData, capped at 1 MiB, optionally immutable: true to cut watch load at scale.
  • Secret — v1; same shape as a ConfigMap but base64 by convention and intent, with typed variants (Opaque, kubernetes.io/tls, kubernetes.io/dockerconfigjson, kubernetes.io/basic-auth, and the legacy kubernetes.io/service-account-token).
  • EncryptionConfiguration + KMS provider — the API server flag and plugin that turn "base64 in etcd" into "actually encrypted in etcd."
  • Downward API — fieldRef (pod metadata) and resourceFieldRef (container requests/limits), exposed as env vars or a downwardAPI volume.
  • Projected volume — one mount combining secret, configMap, downwardAPI, and serviceAccountToken sources.
  • ServiceAccount — a pod's identity; bound, time-limited tokens minted via TokenRequest, auto-mounted and auto-rotated by the kubelet.
  • Namespace — the scope for names, RBAC, and ResourceQuota/LimitRange (Chapter 37); not a security boundary by itself.
  • External secret managers — tools that keep the source of truth outside etcd entirely: the External Secrets Operator syncs from a real secret store into a Secret object; Sealed Secrets encrypts a Secret client-side into a CRD safe to commit to git; SOPS encrypts values inside a file that a GitOps tool decrypts on apply; HashiCorp Vault's agent or CSI provider can inject secrets straight into a pod's filesystem without a Kubernetes Secret ever existing.

Data flowFollowing one pod from creation to a config change

A Deployment creates a pod that mounts a ConfigMap as a volume, a Secret as an env var, and reads its own name via the downward API:

  1. The API server admits the pod (Chapter 32's pipeline), the scheduler binds it to a node, and the kubelet there starts pulling everything the pod spec references: the ConfigMap, the Secret, and — because no ServiceAccount was named — the namespace's default ServiceAccount.
  2. The kubelet calls TokenRequest for a bound token scoped to this exact pod, writes it into a projected volume alongside a CA cert and the namespace name, and mounts the ConfigMap's data as files in a second volume.
  3. For the Secret's env var, the kubelet resolves the current value once and injects it into the container's environment before the process starts. That value is now frozen for the container's lifetime.
  4. The container starts. It reads its own name from a downward-API env var, reads the ConfigMap's files off disk, and reads the Secret's value from its environment. Three different mechanisms, three different objects, one container.
  5. An operator edits the ConfigMap. Within one kubelet sync interval, the volume's files update on disk — but the running process only sees the change if it actively rereads those files.
  6. The same operator rotates the Secret. The volume-based ConfigMap updated; the env-var-based Secret does not — the container keeps running with the old value until something restarts it. Meanwhile, in the background, the kubelet has already requested and swapped in a fresh ServiceAccount token twice, and the container never noticed, because that rotation was designed to be invisible.

Hands-onLabs — build, understand, break, troubleshoot

Lab 1Build — mount a ConfigMap and a Secret both waysBuild

Create both objects, then a pod that consumes the ConfigMap as an env var and a volume, and the Secret as a volume.

bash
kubectl create configmap app-config --from-literal=greeting=hello-v1
kubectl create secret generic app-secret --from-literal=password=S3cr3t!

kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: { name: demo }
spec:
  containers:
  - name: demo
    image: busybox:1.36
    command: ["sh","-c","sleep 1d"]
    env:
    - { name: GREETING_ENV, valueFrom: { configMapKeyRef: { name: app-config, key: greeting } } }
    volumeMounts:
    - { name: cfgvol, mountPath: /etc/cfg }
    - { name: secvol, mountPath: /etc/sec }
  volumes:
  - { name: cfgvol, configMap: { name: app-config } }
  - { name: secvol, secret: { secretName: app-secret } }
EOF
kubectl wait --for=condition=Ready pod/demo --timeout=60s
bash
kubectl exec demo -- sh -c 'echo ENV=$GREETING_ENV; echo FILE=$(cat /etc/cfg/greeting); echo SEC=$(cat /etc/sec/password)'
OutputENV=hello-v1 FILE=hello-v1 SEC=S3cr3t!

Both paths work. Now prove the Secret is base64, not encryption — no cluster access beyond normal read permission required:

bash
kubectl get secret app-secret -o jsonpath='{.data.password}'
kubectl get secret app-secret -o jsonpath='{.data.password}' | base64 -d; echo
OutputUzNjcjN0IQ== S3cr3t!

One shell pipe, no key required. That's the entire "encryption" a default cluster gives you — anyone who can get this Secret can read the plaintext in one step.

Lab 2Understand — the downward API, and which half updatesUnderstand

Expose the pod's labels both as an env var (a single key) and as a volume (the whole map), then change a label and watch only one of them notice.

bash
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: downward
  labels: { tier: "v1" }
spec:
  containers:
  - name: demo
    image: busybox:1.36
    command: ["sh","-c","sleep 1d"]
    env:
    - name: TIER_ENV
      valueFrom: { fieldRef: { fieldPath: "metadata.labels['tier']" } }
    volumeMounts:
    - { name: dvol, mountPath: /etc/podinfo }
  volumes:
  - name: dvol
    downwardAPI:
      items:
      - { path: "labels", fieldRef: { fieldPath: metadata.labels } }
EOF
kubectl wait --for=condition=Ready pod/downward --timeout=60s
kubectl exec downward -- sh -c 'echo ENV=$TIER_ENV; cat /etc/podinfo/labels'
OutputENV=v1 tier="v1"

Now relabel the running pod and give the volume a moment to sync:

bash
kubectl label pod downward tier=v2 --overwrite
sleep 5
kubectl exec downward -- sh -c 'echo ENV=$TIER_ENV; cat /etc/podinfo/labels'
OutputENV=v1 tier="v2"

The volume file caught the new label; the env var is exactly what it was when the container started and will stay that way for the container's entire life. This is the same rule as Lab 1's Secret, just proven on the pod's own metadata instead of a Secret you created.

Lab 3Break — "I changed the config and nothing happened"Break

Reproduce the single most common config ticket. Update app-config from Lab 1 and check both consumers in the same pod.

bash
kubectl create configmap app-config --from-literal=greeting=hello-v2 \
  --dry-run=client -o yaml | kubectl apply -f -
sleep 5
kubectl exec demo -- sh -c 'echo ENV=$GREETING_ENV; echo FILE=$(cat /etc/cfg/greeting)'
OutputENV=hello-v1 FILE=hello-v2

Same ConfigMap, same pod, two different answers. Before you reach for a restart, work out exactly why FILE moved and ENV didn't, and what the fix actually is.

Reveal the reasoning and the fix

FILE reads a live-synced volume mount, so the kubelet rewrote it on disk within one sync interval. ENV was injected into the container's process environment at start-up and nothing in Kubernetes ever revisits a running container's environment variables — there is no mechanism that could update it short of restarting the process. This isn't a bug to patch; it's the documented contract of env-var-based config. The fix is either operational (roll the Deployment so containers restart and re-resolve their env vars: kubectl rollout restart deployment/<name>) or architectural (switch that value to a volume mount and have the app watch the file, or read it fresh on every use instead of caching it into an env var at boot). For anything you expect to change without a redeploy — feature flags, log levels — prefer the volume from day one.

Lab 4Troubleshoot — a leaked Secret and what rotation really requiresTroubleshoot

Simulate the leak: the Secret from Lab 1 just showed up in a CI log because a script echoed an env var. Rotate it and confirm what is and isn't actually fixed.

bash
# who can even read this Secret right now?
kubectl auth can-i get secret/app-secret --as=system:serviceaccount:demo:default
kubectl create secret generic app-secret --from-literal=password=BrandNewPass! \
  --dry-run=client -o yaml | kubectl apply -f -
kubectl exec demo -- sh -c 'echo LIVE_ENV=$(env | grep -c PASSWORD || true); cat /etc/sec/password'
Outputyes password LIVE_ENV=0 BrandNewPass!

The volume-mounted copy in /etc/sec/password updated. But this pod never actually read the password from that file — Lab 1's app reads it from an env var, which this pod doesn't even have wired to the new Secret. Before you declare the incident closed, answer: is the leaked password still valid anywhere right now?

Reveal the diagnosis

Yes, almost certainly — and that's the point of this lab. Rotating the Kubernetes Secret object changes what the object holds; it does nothing to the real-world credential the old value authenticated against unless that system is a downstream consumer reading this exact Secret live. If S3cr3t! was a real database password, the database still accepts it until you change the password at the database. The full incident checklist, in order: rotate the credential at its source system first (the database, the third-party API, the signing key) so the leaked value stops working everywhere, not just in Kubernetes; update the Kubernetes Secret to match; then restart every consumer that reads it via an env var, because — as Lab 3 showed — they will keep using the stale value in memory indefinitely otherwise. Checking kubectl auth can-i and kubectl get events/audit logs for who actually read the Secret while it was exposed tells you your real blast radius. "I rotated the Secret" is the middle step of a three-step process, not the whole fix.

Lab 5Production challenge — inspect and scope a ServiceAccount tokenSenior challenge

Look at exactly what the default token contains, then decide when a workload should get no token at all.

bash
kubectl exec demo -- cat /var/run/secrets/kubernetes.io/serviceaccount/token | cut -d. -f2 | base64 -d 2>/dev/null; echo
Output{"aud":["https://kubernetes.default.svc"],"exp":1758XXXXXX,"iss":"https://kubernetes.default.svc", ... "kubernetes.io":{"namespace":"demo","pod":{"name":"demo","uid":"..."},"serviceaccount":{"name":"default","uid":"..."}},"sub":"system:serviceaccount:demo:default"}

That token is scoped to exactly this pod, this namespace, this audience, and expires roughly an hour from now — decode the exp field and compare it to the current time to see for yourself. Now the design question: this particular workload, demo, never calls the Kubernetes API. Reason about the right fix before revealing, then apply it.

Reveal the approach

If a workload never talks to the API server, it has no business holding a token that could — every mounted token is a credential an attacker who compromises that container gets for free, and "never used it" is not the same as "couldn't use it." The fix is automountServiceAccountToken: false, settable on the Pod spec or on the ServiceAccount itself (the Pod-level setting wins if both are set):

bash
kubectl patch serviceaccount default -n demo -p '{"automountServiceAccountToken": false}'
kubectl delete pod demo && kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: { name: demo }
spec:
  containers:
  - { name: demo, image: busybox:1.36, command: ["sh","-c","sleep 1d"] }
EOF
kubectl exec demo -- ls /var/run/secrets/kubernetes.io/serviceaccount/ 2>&1
Outputls: /var/run/secrets/kubernetes.io/serviceaccount/: No such file or directory

No token, no volume, nothing to steal. The broader principle for a production cluster: never let workloads inherit the namespace's default ServiceAccount by accident — give every workload that genuinely needs API access its own narrowly-scoped ServiceAccount and RBAC role, and disable automount everywhere else. If you need a token for something outside the cluster — a script, a CI job — mint a short-lived, audience-scoped one on demand with kubectl create token <name> --duration=10m rather than reaching for a permanent Secret-based token. Clean up: kind delete cluster --name cfg.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · a Secret leaked into logs, git, or a screenshot

Symptom: a password or API key shows up somewhere it shouldn't — a CI log, a support ticket, a committed manifest with stringData in plaintext. First cut: assume it's compromised the moment it's out, because base64 is not a barrier to anyone who saw it. Fix, in order: rotate the credential at its real source system first, then update the Kubernetes Secret, then restart every env-var consumer — a volume consumer picks it up on its own, an env-var one won't. Prevent next time: encryption at rest doesn't stop this class of leak at all (it protects etcd on disk, not values already exposed to an authorized reader) — the real prevention is RBAC scoping on who can get Secrets, and never letting anything print a Secret's decoded value to a log.

Incident pattern · "I changed the config and nothing happened"

Symptom: a ConfigMap or Secret is updated, kubectl get shows the new value, but the running app behaves as if nothing changed. First cut: check how the pod consumes it — kubectl get pod -o yaml and look for configMapKeyRef/secretKeyRef in env versus a volumeMounts entry. Usual cause: it's an env var, which is frozen at container start by design, or it's a volume using subPath, which never gets live updates at all. Fix: roll the workload to force a restart, or move that value to a plain (non-subPath) volume mount and make the app reread the file.

Incident pattern · the default ServiceAccount turns out to be over-privileged

Symptom: a security review finds that dozens of unrelated pods across a namespace can all read Secrets, list pods, or worse — because someone once bound a permissive Role to the namespace's default ServiceAccount to unblock one workload, and every pod that never specified its own ServiceAccount inherited it silently. Confirm: kubectl get rolebinding,clusterrolebinding -o wide and search for default as a subject; cross-check with kubectl get pods -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.spec.serviceAccountName}{"\n"}{end}' to see how many pods are riding on it. Fix: give the workload that actually needs access its own dedicated ServiceAccount and role, strip the binding from default, and set automountServiceAccountToken: false on default so future pods stop inheriting a live token by accident.

Production · security · performanceWhat matters in production

Treat "Secret" as a label for intent, not a security guarantee. A cluster with RBAC misconfigured, no encryption at rest, and no audit logging protects a Secret exactly as well as a ConfigMap — which is to say, only as well as who can run kubectl get. Turn on encryption at rest with KMS v2 for any cluster holding real credentials, remember the no-op re-encrypt pass for existing data, and rotate the KEK on a real schedule (90 days is the project's own recommendation) rather than never. Then layer RBAC tightly around who may read Secrets at all — that permission is far more consequential than most teams treat it.

For anything genuinely sensitive at scale, keep the value out of etcd entirely. A K8s Secret is still a plaintext value one API call away from anyone with read access; the ecosystem exists because that's not always good enough. External Secrets Operator and Vault's injector keep the real value in a dedicated secret store and sync or inject it just-in-time; Sealed Secrets and SOPS solve the adjacent problem of storing an encrypted Secret safely in git for GitOps, decrypting only inside the cluster or at apply time. None of these replace RBAC and encryption at rest — they reduce how many places the plaintext ever has to exist.

Identity should be scoped per workload, not inherited by accident. Give each workload its own ServiceAccount named for what it does, bind it the minimum RBAC it needs, and set automountServiceAccountToken: false everywhere else — most pods never call the API server and shouldn't carry a credential that could. At scale, mark ConfigMaps and Secrets immutable: true where the data genuinely never changes in place (a build artifact's config, a pinned certificate); it stops accidental edits and — documented directly by the project — meaningfully cuts kube-apiserver watch load once you're in the tens of thousands of ConfigMap-to-pod mounts.

Common mistakes: assuming base64 is encryption; putting a value that changes often behind an env var and being surprised rollouts are the only way to refresh it; using subPath on a ConfigMap/Secret volume and losing live updates without realizing it; letting every pod in a namespace silently share one over-permissioned default ServiceAccount; and treating "I rotated the Kubernetes Secret" as equivalent to "I rotated the credential," when the real system the credential authenticates against was never touched.

System-design connectionWhere this reaches into architecture

Config and identity are the seam between your GitOps pipeline and your security posture. The moment you store config declaratively in git (Chapter 64), you inherit a hard question: config can go in git as plain YAML, but Secrets can't, so every serious GitOps setup pairs with Sealed Secrets, SOPS, or an external store precisely to keep the declarative model without putting plaintext credentials in version control. Namespace as a scoping unit is also your multi-tenancy primitive — how you carve a shared cluster between teams (quota, RBAC, network policy) starts from "one namespace per tenant" and gets refined from there. And ServiceAccount identity is the foundation the entire cloud-identity federation story sits on: IRSA and EKS Pod Identity (Chapter 55) let a pod assume a real cloud IAM role using nothing but the bound, auto-rotating token this chapter just walked through — no static cloud credentials stored anywhere, which is the difference between "we rotate secrets" and "there is no long-lived secret to rotate." Get the identity model right at this layer and half of your cloud security posture follows for free; get it wrong and every downstream integration inherits an over-broad, static credential.

InterviewInterview questions & answers

Answer each in your head before opening it.

30-secIs a Kubernetes Secret encrypted?

Not by default. A Secret's values are base64-encoded, which is an encoding you can reverse with one command, not a cipher — anyone with RBAC read access to the Secret can decode it instantly, and by default it's stored the same way in etcd. Actual encryption at rest requires configuring an EncryptionConfiguration on the API server with a real provider — a local key or, for production, a KMS provider (KMS v2, stable since 1.29) doing envelope encryption. Without that configured, "Secret" is a naming convention and an intent signal, not a security control.

2-minWalk me through what happens when a pod's ConfigMap changes after the pod is already running.

It depends entirely on how the pod consumes it, and there are three cases. If it's an individual env var via configMapKeyRef, or a bulk set via envFrom, the kubelet resolved that value once at container start and never revisits it — the running container's environment is frozen regardless of what the ConfigMap does afterward. If it's mounted as a volume, the kubelet's sync loop notices the change — by default via a watch — and rewrites the files on disk, typically within a sync interval, no restart required; but that only means the file changed, not that the app reread it, since most apps cache config in memory at startup unless they explicitly watch the file. The third case is a volume using subPath to expose a single file — that bind-mounts a specific path at pod start and structurally cannot pick up updates at all, live-updating volume or not. So the practical answer is: volume mounts can update live, env vars never do, and subPath opts out of updates even as a volume. If you need config changes to actually take effect, either mount a plain volume and have the app watch it, or accept that a rollout restart is the mechanism.

DeepExplain how a ServiceAccount token is created and rotated today, and why that's different from a few years ago.

When a pod starts, the kubelet calls the TokenRequest API to mint a bound token — a JWT scoped to a specific audience, a time limit (on the order of an hour by default), and the exact object using it, typically that pod by UID. It's delivered via a projected volume, not a plain Secret mount, alongside a CA cert and the namespace. The kubelet proactively requests a replacement well before expiry, so the token in the mount is always fresh without the container ever restarting, and because it's bound to the pod's UID, deleting the pod lets the API server invalidate that token immediately. This has been the default path for the auto-mounted token since Kubernetes 1.22. Before that, and fully before the LegacyServiceAccountTokenNoAutoGeneration change took hold by 1.24–1.27, every ServiceAccount automatically got a permanent kubernetes.io/service-account-token Secret with no expiry — a credential that, once leaked, worked forever until someone manually deleted it. The shift to bound, short-lived, auto-rotating tokens closes exactly that gap: theft has a shelf life measured in an hour instead of forever, and the token can't be replayed outside its declared audience or after its bound object is gone. You can still manually create a long-lived Secret-based token for a legitimate external use case, but it's explicitly discouraged, and the default for everything running inside the cluster is the bound, rotating model.

ScenarioA teammate says "I rotated the leaked database password's Secret two hours ago, but the leaked value still works against the database." What's going on and what did they miss?

Rotating the Kubernetes Secret object only changes what that object holds — it does nothing to the actual database user's password unless the database itself was also changed, because the two are entirely separate systems connected only by the app reading one to authenticate to the other. If the leaked value still works against the database, the database's own password was never changed; only the Kubernetes-side copy was. The correct order is: change the password at the source system first — the database — so the leaked credential stops being valid anywhere, then update the Kubernetes Secret to match the new value, then restart every consumer that reads that Secret via an environment variable, since those are frozen at container start and won't pick up the new value on their own even after both of the first two steps. I'd also check who had read access to that Secret and for how long, since that's the actual blast radius, and confirm whether any consumer mounts it as a volume — those pick up the new value automatically once the object updates, but only after the app itself rereads the file.

Follow-upWhy isn't a Namespace a security boundary by itself?

A Namespace scopes names, and it's the unit RBAC and ResourceQuota are evaluated against, but nothing about a Namespace alone stops access across it. A ClusterRoleBinding grants permissions cluster-wide regardless of namespace; a RoleBinding in namespace B can name a ServiceAccount subject from namespace A, explicitly granting cross-namespace access; and by default, pods in different namespaces can still reach each other over the network unless a NetworkPolicy says otherwise. So a Namespace gives you organization and a place to hang RBAC and quota rules, but the actual isolation — who can read what, and what can talk to what over the network — has to be deliberately configured on top of it. Multi-tenant clusters that treat "put each team in its own namespace" as sufficient isolation, without RBAC scoped tightly per namespace and NetworkPolicies restricting cross-namespace traffic, generally discover the gap the hard way.

RetainQuick revision

ConfigMap and Secret are the same shape — key/value data attached to a pod — with Secret meant for sensitive values but only base64-encoded by default, not encrypted; real encryption at rest needs an EncryptionConfiguration and a provider like KMS v2 (stable since 1.29), and it only protects writes made after you turn it on. Both can be consumed as an env var (frozen at container start, forever) or a volume (kept in sync by the kubelet, except under subPathresourceFieldRef. A ServiceAccount is a pod's identity; since 1.22 its token is minted per-pod via TokenRequest, bound to an audience and a roughly one-hour expiry, auto-rotated by the kubelet — the old permanent Secret-based token stopped being created by default starting in 1.24 and that became permanent by 1.27. A Namespace scopes names, RBAC, and quota, but is not itself a security boundary — cross-namespace access is one RoleBinding away, and isolation has to be built deliberately with RBAC and NetworkPolicy.

The 10 things to remember

  1. ConfigMap and Secret share a shape; Secret is base64, not encrypted, by default — decode it with one base64 -d.
  2. Encryption at rest needs an explicit EncryptionConfiguration + KMS provider (KMS v2, stable since 1.29), and only covers writes made after it's enabled.
  3. Env vars from a ConfigMap/Secret are resolved once at container start and never update; volume mounts sync live — except under subPath, which never updates either.
  4. A file updating on disk doesn't mean the app noticed — most apps cache config at startup unless they explicitly watch the file.
  5. The downward API splits fields between env-only, volume-only, and both — whole label/annotation maps are volume-only.
  6. A projected volume combines Secret, ConfigMap, downward-API, and ServiceAccount-token sources into one mount.
  7. Since 1.22, ServiceAccount tokens are bound (audience, time, object) via TokenRequest and auto-rotated by the kubelet — roughly an hour TTL.
  8. Permanent Secret-based ServiceAccount tokens stopped being auto-created by default from 1.24, permanently from 1.27 — don't reach for them.
  9. Set automountServiceAccountToken: false on any workload that never calls the API server.
  10. A Namespace scopes names/RBAC/quota; it is not a security boundary until you add RBAC and NetworkPolicy on top of it.
