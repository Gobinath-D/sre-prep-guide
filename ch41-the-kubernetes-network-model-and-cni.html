Part V · Kubernetes Networking at Packet Level · Chapter 41

The Kubernetes network model and CNI

Calico, Cilium, Flannel, the AWS VPC CNI — four products with almost nothing in common under the hood, and every one of them satisfies the exact same one-page contract. Kubernetes never asks how a network plugin does its job; it only ever checks whether four rules hold. Learn the contract and no CNI is a black box again.

Start: Beginner→→→End: Staff-level ~45 min read · kind + kubectl lab

By the end of this chapter you can

  • State the Kubernetes network model's four rules from memory, and explain why flat, routable pod IPs won over per-node NAT.
  • Explain the difference between the Kubernetes network model (the what) and the CNI specification (the how) — two documents from two different projects, constantly confused as one.
  • Read a CNI plugin's config from /etc/cni/net.d and know exactly what each field controls.
  • Say precisely what a CNI plugin owns — IPAM, the veth, host-side routes — and name the things it explicitly does not own.
  • Diagnose a CNI DaemonSet that isn't ready and a cluster that's run out of pod IP address space, from their distinct symptoms.

Why this exists · the problemOne rulebook, any contractor

You already know from Chapter 25 how a single Docker host wires containers up: a bridge, veth pairs, private addresses, and NAT to hide those addresses behind the host's own IP. That works for one machine. Put fifty machines in a cluster and it collapses immediately — if every node hands out its own private 172.17.x.x range, every node hands out the same range, addresses collide across the cluster, and a pod on node 3 can never uniquely name a pod on node 41. You'd be back to publishing ports and chasing NAT tables for every pod-to-pod call, which doesn't survive a service with a thousand replicas across a hundred nodes.

Kubernetes' answer was to write down a small, non-negotiable contract and refuse to ship its own implementation of it. The contract is four rules:

  • Every pod gets its own unique IP address, valid cluster-wide.
  • Any pod can reach any other pod's IP directly, without NAT — the destination sees the source's real IP.
  • Agents on a node (the kubelet, system daemons) can reach every pod on that node.
  • A pod's own view of its IP matches everyone else's view of it — it is never secretly translated.

Kubernetes itself doesn't implement any of this. It defines the rules, then delegates the actual wiring to a pluggable component invoked at exactly one moment — when a pod's sandbox is created — through a generic, pre-existing interface called the Container Network Interface (CNI). This is the detail almost everyone glosses over: the four rules above are Kubernetes' requirement, published in Kubernetes' own docs, while CNI is a separate specification from a separate project that predates Kubernetes adopting it and has nothing Kubernetes-specific in it at all. Kubernetes just happens to be CNI's most famous customer. Keeping those two documents distinct in your head is most of what this chapter is trying to teach.

Key point

The Kubernetes network model is the what: four rules, owned by Kubernetes, non-negotiable for anything calling itself a conformant cluster. The CNI specification is the how: a generic plugin contract, owned by an independent project, that Kubernetes delegates to so it never has to ship — or pick a winner among — network implementations. Any plugin that honors the contract is free to satisfy the rules however it wants underneath.

Mental model · analogyThe mental model: a building code and a standard contractor agreement

Real-world analogy

A property developer writes a building code every unit in every building must meet, no matter who builds it: every unit gets its own real, unique street address; any unit's front door reaches any other unit directly, with no forwarding desk translating the visitor in between; building staff can reach every unit in their own building; and the address on your mailbox is the same address everyone else uses to find you. That code is the Kubernetes network model — four fixed requirements, owned by the developer, and every building must meet them regardless of who wires it.

The developer doesn't do the wiring. Instead, they hire under a standard electrician contract that says: "when a unit is being fitted out, we'll call you with a work order — ADD — and you run the cable, set the meter, and tell us the unit's assigned address; when the unit is vacated, we call you with DEL and you disconnect it." Any electrician who signs that standard contract can take the job — one crew might run copper through a shared conduit, another might use a wireless mesh, another might tap directly into the city grid with its own numbering. The developer never inspects how the wiring was run. They only ever check that the building code holds. That contract is CNI, and it's generic enough that it was never written with buildings — or Kubernetes — specifically in mind; it's just the interface Kubernetes chose to hire electricians through.

ArchitectureInvocation, then wiring — and the promise it produces

Two things happen in sequence: the kubelet invokes a plugin at one specific moment, and that invocation produces a piece of wiring that must keep the model's four promises for as long as the pod lives. Why an SRE cares

This split is why swapping a CNI is a real, done-in-production migration rather than a rewrite. Moving from Flannel to Calico, or to the AWS VPC CNI, changes IPAM, the wiring, and which optional extras (like NetworkPolicy enforcement) you get — but no application changes, because no application was ever allowed to depend on anything beyond the four rules. When someone says "we're migrating CNIs," this is the guarantee that makes it a platform-team project instead of an every-team fire drill.

Internal workingWhat actually happens when the kubelet calls the plugin

"Invoke the plugin" is one box in the figure above. Here's the literal mechanism, because the CNI spec is short enough to actually read in full and worth doing once:

  1. The kubelet asks the container runtime to create the pod's sandbox. The CRI creates the pause container and an empty network namespace — no interfaces except a loopback, and it starts down. Nothing is wired yet.
  2. The kubelet (or the runtime, on its behalf) reads the CNI configuration. It looks in /etc/cni/net.d/ for a .conflist (or a single .conf) file. If several exist, the one that sorts first lexically by filename wins — a fact that causes real incidents when an upgrade leaves an old config file behind alongside a new one. The chosen config names one or more plugins by type, plus a subnet/IPAM block, and any plugin-specific parameters like MTU.
  3. It executes the plugin binary from /opt/cni/bin/ matching that type, setting environment variables the spec defines — CNI_COMMAND=ADD, CNI_CONTAINERID, CNI_NETNS (the namespace path), CNI_IFNAME (usually eth0) — and feeding the JSON config to the plugin's stdin. This is the entire interface: environment variables plus JSON over standard streams, nothing Kubernetes-specific about any of it.
  4. The plugin does its job. For a typical plugin this means three things: run IPAM to obtain an address (often by delegating to a separate IPAM plugin, like host-local, which tracks allocations in files on disk), create a veth pair and move one end into the pod's namespace as eth0, and wire the host-side routes (or bridge membership) so the address is reachable — the exact same three nouns Chapter 42 goes deep on.
  5. If the config file is a .conflist, plugins run in a chain. A connectivity plugin (bridge, Calico, Cilium, whichever) runs first and does the real wiring; smaller "meta" plugins can run after it against the same interface — portmap to implement a pod's hostPort, bandwidth to apply traffic shaping, tuning to set sysctls on the interface. Each one only modifies what the previous plugin already built; none of them do IPAM or create the veth themselves.
  6. The plugin prints a result to stdout — the assigned IP, routes, and DNS info, as JSON — and exits. The kubelet reads that result and records the address; this is, mechanically, where a pod's .status.podIP comes from. Only now does the kubelet tell the runtime to start the actual application containers, into a namespace that already has a real, working network identity.
  7. Teardown is the mirror image. When the pod is deleted, the kubelet invokes the same binary with CNI_COMMAND=DEL, and the plugin releases the IPAM allocation and removes what it created. CHECK and VERSION are two smaller commands the spec also defines, for verifying an existing attachment and negotiating protocol versions.
The CNI spec is generic — Kubernetes is just its most famous caller

Nothing in steps 1–7 mentions a Pod object, a kubelet, or etcd. The CNI specification defines a protocol for "wire up a network namespace" and "tear it down," full stop — it was built to be usable by any container runtime, and Kubernetes adopted it rather than inventing its own. That's why a CNI plugin's config and binary have no idea what a Kubernetes Service or a NetworkPolicy even is unless the specific plugin chooses to also watch the Kubernetes API on the side and layer that behavior in — which is exactly what Calico and Cilium do, and exactly what a bare bridge+host-local setup does not.

Think first: a node's /etc/cni/net.d/ has both 05-flannel.conflist (from an old install) and 10-calico.conflist (from a botched migration) sitting side by side. Which one actually runs?

05-flannel.conflist — the kubelet picks the config file that sorts first lexically by filename, and 05 sorts before 10. Every new pod on that node gets wired by Flannel, silently, even though the team believes they've migrated to Calico. This is a real, recurring class of incident: nothing crashes, nothing errors, pods get IPs and appear to work — until something that depends on Calico-specific behavior (a NetworkPolicy, an encryption feature) quietly doesn't apply, and nobody notices until a security review or an outage exposes it. The fix is procedural as much as technical: a CNI migration has to explicitly remove the old config (and ideally the old binary) from every node, not just install the new one alongside it, and it's worth checking ls /etc/cni/net.d/ on more than one node before declaring a migration done.

ComponentsThe pieces, and who owns which

  • The Kubernetes network model. The four rules, owned and documented by Kubernetes itself. No plugin, no config file — it's a design requirement any conformant cluster must meet, checked by conformance tests, not by any single piece of software.
  • The CNI specification (cni.dev). A general-purpose contract for wiring and tearing down a network namespace: the commands (ADD/DEL/CHECK/VERSION), the execution protocol (env vars, JSON on stdin/stdout), and the config file formats. Owned by an independent project, usable by any container runtime, not just Kubernetes.
  • CNI config files — /etc/cni/net.d/*.conf or *.conflist. Which plugin (or chain of plugins) runs, in what order, with what subnet, IPAM type, and MTU. The first file by filename sort order wins.
  • CNI plugin binaries — /opt/cni/bin/*. The actual executables: connectivity plugins (bridge, ptp, or a vendor's own like Calico's or Cilium's), IPAM plugins (host-local, or a cloud-delegating one), and meta plugins (portmap, bandwidth, tuning).
  • IPAM plugins. A specific category of plugin whose only job is address assignment — handed the same config, called with the same commands, but responsible only for "give me an address" and "release this address," not for any wiring.
  • The kubelet and the container runtime (CRI). The callers. The kubelet drives the pod's lifecycle and triggers sandbox creation; the runtime creates the sandbox and network namespace the CNI plugin is handed.
  • The pod sandbox / pause container. Holds the network namespace open for the pod's whole life, so the CNI attachment and the assigned IP survive individual app containers restarting inside it.
  • What a CNI plugin explicitly does not own. Service virtual IPs and their DNAT rules (kube-proxy's job, Chapter 43), DNS resolution (CoreDNS, Chapter 45), and — unless the specific plugin chooses to add it — NetworkPolicy enforcement, which is an optional extra some CNIs implement and some don't.

Data flowFollowing the promise from ADD to every later chapter

A pod is scheduled to a node. The runtime creates its sandbox and empty namespace; the kubelet reads that node's CNI config, execs the plugin with ADD, and the plugin runs IPAM against this node's slice of the cluster's pod CIDR, creates the veth, wires the host side, and hands back an address — say 10.244.1.6. The kubelet records it as .status.podIP. From this exact moment, the model's four rules are now live promises about that address: it's unique across the whole cluster, not just this node; any other pod, anywhere, can open a connection to it and this pod will see that peer's real address, untranslated; the kubelet and any node-level agent on this node can reach it directly; and every consumer of that IP — a Service's endpoint list, a NetworkPolicy selector, a monitoring scrape target — sees the same address this pod sees itself.

Everything Part V covers after this chapter is really just an account of how that promise gets kept and used. Chapter 42 is the mechanism behind "reachable without NAT," in full: the veth, the same-node bridge or routes, the cross-node native routing or overlay. Chapter 43 builds a virtual, load-balanced address on top of a list of these real ones. None of it works if the CNI plugin didn't keep this chapter's promise at ADD time — which is exactly why "is the CNI healthy" is the first thing to check when pod networking looks broken anywhere in the stack.

Think first: a brand-new, custom-written CNI plugin passes every test you throw at it — pods get IPs, pod-to-pod pings work, everything looks fine on one node. What haven't you actually verified yet?

Whether it holds up across nodes, and whether it's really not translating anything. Same-node connectivity can work by pure accident — even a plugin that quietly NATs traffic through the node's own IP can still pass a same-node ping, because the reply finds its way back regardless of whose address is on it. The model's actual claims only get tested by a cross-node call where you inspect what address the destination pod actually sees the source as, and by checking that a node-local agent (not just another pod) can reach the pod directly. A CNI that's never been checked against all four rules specifically, only against "does networking seem to work," is exactly how a subtly broken plugin ships to production and breaks something three layers up — a NetworkPolicy that never matches because the source IP it sees isn't the real one, for instance — weeks later.

Hands-onLabs — build, understand, break, troubleshoot

A plain two-node kind cluster, using its default CNI, kindnet — a real, if minimal, CNI plugin, not a simulation of one.

bash
kind create cluster --name cnilab --config - <<'EOF'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
EOF
Lab 1Build — read the actual CNI config and binaries on a nodeBuild

Stop treating the CNI as a black box. A kind node is just a Docker container, so read the files directly:

bash
docker exec cnilab-worker ls /etc/cni/net.d/
docker exec cnilab-worker cat /etc/cni/net.d/10-kindnet.conflist
Output (trimmed)10-kindnet.conflist { "cniVersion": "0.3.1", "name": "kindnet", "plugins": [ { "type": "ptp", "ipMasq": false, "ipam": { "type": "host-local", "dataDir": "/run/cni-ipam-state", "ranges": [[{"subnet": "10.244.1.0/24"}]] }, "mtu": 1500 }, { "type": "portmap", "capabilities": {"portMappings": true} } ] }

Read it like a sentence: one .conflist, so this is a plugin chain. ptp is the connectivity plugin — a point-to-point veth style, not a bridge (which is exactly what let you predict, back in Chapter 42's terms, that this CNI forwards same-node traffic with routes, not a cni0 bridge). Its ipam block says host-local, handing out addresses from 10.244.1.0/24 — this node's own slice. portmap runs second, purely to implement hostPort; it never touches IPAM or the veth. Now find the binaries that actually get executed:

bash
docker exec cnilab-worker ls /opt/cni/bin/
Outputbridge host-local loopback portmap ptp ...

ptp and host-local and portmap are right there — ordinary executables, not daemons, run once per pod and exiting immediately after. This is the entire "CNI plugin" for this node: two files and a handful of binaries.

Lab 2Understand — every node's slice, and the no-NAT promise, empiricallyUnderstand

The config file said 10.244.1.0/24 for this one node. Confirm the cluster hands each node a distinct slice, and that pod IPs really do land inside it:

bash
kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"  "}{.spec.podCIDR}{"\n"}{end}'
Outputcnilab-control-plane 10.244.0.0/24 cnilab-worker 10.244.1.0/24

Deploy pods on each node and check where their IPs actually fall:

bash
kubectl run a --image=busybox:1.36 --overrides='{"spec":{"nodeName":"cnilab-worker"}}' --command -- sleep 3600
kubectl run b --image=busybox:1.36 --overrides='{"spec":{"nodeName":"cnilab-control-plane"}}' --command -- sleep 3600
kubectl wait --for=condition=Ready pod/a pod/b --timeout=60s
kubectl get pods -o wide
OutputNAME READY STATUS IP NODE a 1/1 Running 10.244.1.2 cnilab-worker b 1/1 Running 10.244.0.4 cnilab-control-plane

Exactly the slices the config predicted. Now prove the model's second rule — no NAT — without touching a packet capture yet; a plain connection is enough to show the destination sees a real, unmodified peer address:

bash
B_IP=$(kubectl get pod b -o jsonpath='{.status.podIP}')
kubectl exec a -- wget -T3 -qO- "$B_IP" 2>&1 | head -1 || true
kubectl exec a -- ping -c2 "$B_IP"
OutputPING 10.244.0.4: 2 packets transmitted, 2 packets received, 0% packet loss

Two pods, two nodes, a direct connection, no port mapping, no gateway you configured by hand. Exactly how that packet actually crosses from one node's veth to the other's is Chapter 42's whole subject — this lab only needed to prove that the promise holds, not yet how it's kept.

Lab 3Break — a CNI DaemonSet that isn't readyBreak

The CNI plugin binary only runs when the kubelet calls it — but something has to keep the config and binaries in place and healthy on every node, and for most real CNIs that's a DaemonSet. Take it down on one node and watch what breaks, and what doesn't:

bash
kubectl -n kube-system get pods -l app=kindnet -o wide
# find the kindnet pod on cnilab-worker and delete it, then immediately try a new pod there:
KPOD=$(kubectl -n kube-system get pods -l app=kindnet -o jsonpath='{range .items[?(@.spec.nodeName=="cnilab-worker")]}{.metadata.name}{end}')
kubectl -n kube-system delete pod "$KPOD" --grace-period=0 --force
kubectl run c --image=busybox:1.36 --overrides='{"spec":{"nodeName":"cnilab-worker"}}' --command -- sleep 3600
kubectl get pod c -w

Before you look at the new pod's status, predict two things: does pod a, already running on that same node from Lab 2, notice anything at all? And does the new pod c behave the same way? Reason about what the CNI actually did at ADD time versus what it would need to do again, then check.

Reveal what happens to each
OutputNAME READY STATUS RESTARTS AGE c 0/1 ContainerCreating 0 75s

Pod a is untouched — its ADD already happened, its veth and routes already exist in the kernel, and none of that depends on kindnet's pod still running afterward. Pod c is a brand-new sandbox that needs a brand-new ADD call, and if the CNI's own components aren't healthy on that node, that call either fails outright or never gets attempted, so c sits in ContainerCreating indefinitely. Confirm from the events, then bring kindnet back — the DaemonSet controller (Chapter 31) reschedules it automatically:

bash
kubectl describe pod c | grep -A2 Events
kubectl -n kube-system get pods -l app=kindnet -o wide   # wait for it to come back Running
kubectl delete pod c

This is the shape of the real incident named in this chapter's opening: a CNI DaemonSet crash-looping or not-yet-scheduled on a node makes that one node unable to network new pods, while doing nothing at all to the pods already wired there — which is exactly why the symptom is "new pods stuck, old pods fine, on one specific node" rather than a clean, obvious network outage.

Lab 4Troubleshoot — run out of address space to hand outTroubleshoot

IPAM exhaustion doesn't require filling up 254 addresses one pod at a time — the cheapest way to see it is to start a cluster whose total pod-IP pool is smaller than what its nodes need. Build one on purpose:

bash
kind create cluster --name tinynet --config - <<'EOF'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
networking:
  podSubnet: "10.245.0.0/26"
nodes:
  - role: control-plane
  - role: worker
EOF
kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"  "}{.spec.podCIDR}{"\n"}{end}'
Outputtinynet-control-plane 10.245.0.0/24 tinynet-worker

One node has a podCIDR; the other has nothing at all — an empty field. A /26 is only 64 addresses total, and the default per-node allocation needs a full /24, so the pool ran out after the first node. Before revealing, work out what this does to any pod scheduled onto the empty-CIDR node, and what you'd check first if you found this in a real cluster with no idea it had been misconfigured at creation time.

Reveal the symptom chain and the fix

Schedule a pod onto the starved node and it never gets networked at all:

bash
kubectl run stuck --image=busybox:1.36 --overrides='{"spec":{"nodeName":"tinynet-worker"}}' --command -- sleep 3600
kubectl describe pod stuck | grep -A3 Events
OutputWarning FailedCreatePodSandBox ... failed to set up sandbox container ... network: failed to allocate for range 0: no IP addresses available in range ...

The error names the exact failure — IPAM has nothing left to hand out, because the node was never even given a CIDR to allocate from. In a real cluster you'd never see the empty podCIDR as obviously as this lab makes it — you'd only see "pods on this node never leave ContainerCreating with a sandbox-allocation error," so kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.spec.podCIDR}{"\n"}{end}' is the one command that turns "networking seems broken" into "this node was never given address space" in a single line. The fix is always sizing the pool before launch: choose a podSubnet large enough for (expected node count) × (per-node CIDR size) with real headroom for growth, because changing it after nodes already hold CIDR allocations is disruptive on most clusters, not a live edit. This is the cluster-CIDR-pool flavor of IPAM exhaustion; the AWS VPC CNI's flavor is different in mechanism — it runs out of secondary IPs per ENI, not out of a CIDR to slice — but it's the same shape of incident, and you'll meet it directly in Chapter 58. Clean up: kind delete cluster --name tinynet.

Lab 5Production challenge — capacity looks fine, but pods won't land on one nodeSenior challenge

Back on the original cnilab cluster. A team reports: "one of our nodes has plenty of free CPU and memory, but new pods just won't schedule there — everything else looks healthy." No commands yet: given everything in this chapter, list every mechanically distinct cause you'd consider before touching the cluster, in the order you'd check them.

Reveal the reasoning and the check for each

"Won't schedule" and "won't get an IP" are different failures with different owners, so separate them first — this is exactly the isolate step from Chapter 40's framework, applied here. Three genuinely distinct, ordered hypotheses:

bash
# 1. Is the node schedulable at all — cordoned, tainted, or NotReady?
kubectl get node cnilab-worker -o jsonpath='{.spec.taints}{"\n"}{.status.conditions[?(@.type=="Ready")].status}{"\n"}'

# 2. Has the node hit its pod-COUNT ceiling — nothing to do with IP space at all?
kubectl get node cnilab-worker -o jsonpath='{.status.allocatable.pods}{"\n"}'
kubectl get pods -A --field-selector spec.nodeName=cnilab-worker --no-headers | wc -l

# 3. Has the node's CNI IPAM pool specifically run out, even though its podCIDR is fine?
kubectl get node cnilab-worker -o jsonpath='{.spec.podCIDR}{"\n"}'
docker exec cnilab-worker sh -c 'ls /run/cni-ipam-state/*/  2>/dev/null | wc -l'

Each check rules a specific cause in or out with evidence, not with a guess: a taint or NotReady means the scheduler never even considers the node — CPU and memory being free is irrelevant if nothing gets placed there in the first place. A pod count already at .status.allocatable.pods (the kubelet's own ceiling, 110 by default, entirely independent of address space — a node with a roomy /24 of 254 addresses can still refuse a 111th pod on count alone) explains "healthy CPU/memory, no new pods" perfectly without any networking cause at all. Only if the first two are clean do you look at IPAM specifically — a full host-local allocation directory with a healthy podCIDR otherwise. The trap this scenario is built to catch: assuming any pod-placement failure on a network-adjacent-sounding symptom must be a CNI or IP problem, when a kubelet-level pod-count cap produces the exact same user-visible complaint and has nothing to do with addressing at all.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · CNI DaemonSet not ready

Symptom: new pods stuck in ContainerCreating on one or a few specific nodes, with a sandbox-creation error in events, while already-running pods on those same nodes are completely unaffected. First cut: is the CNI's own DaemonSet pod Running and healthy on the affected node? Confirm: its logs, and whether the node shows a related condition. Usual cause: the CNI DaemonSet pod crash-looping, evicted, or not yet scheduled on a freshly-joined node — the ADD call has nowhere healthy to land, but nothing retroactively breaks pods that already completed ADD successfully.

Incident pattern · IPAM / CIDR exhaustion

Symptom: a sandbox-creation error naming IP allocation specifically ("no IP addresses available"), or a node with an entirely empty .spec.podCIDR. First cut: kubectl get nodes -o jsonpath for podCIDR across every node — an empty one means the cluster-wide pool ran out before this node got its share. Usual cause: a podSubnet sized without headroom for the eventual node count, discovered only once the cluster actually grows to fill it — the fix is a bigger pool from the start, since resizing it live is disruptive on most clusters.

Incident pattern · stale CNI config left behind by a migration

Symptom: a CNI migration is declared complete, but some security or policy feature the new plugin should provide silently isn't applying — no errors, pods get IPs, everything "works." First cut: ls /etc/cni/net.d/ on more than one node. Usual cause: the old plugin's config file was never removed, sorts first by filename, and is quietly still the one actually running — the new plugin's binary may not even be invoked at all. The fix is deleting the old config (and ideally the old binary) from every node as part of the migration, not just installing the new one alongside it.

Production · security · performanceWhat matters in production

Choosing a CNI is mostly about the optional extras, because the mandatory floor is identical everywhere. Every conformant CNI already gives you the four rules — that part isn't a differentiator. What actually differs, and what you're really evaluating, is what each plugin adds on top: NetworkPolicy enforcement (some CNIs implement it, some silently no-op unenforced policies — a dangerous gap if you assume otherwise), encryption between nodes, observability and flow logs, and the performance profile of native routing versus an overlay's encapsulation tax (Chapter 42).

Size the pod CIDR before launch, not after. The per-node allocation size (how big a slice each node gets) and the overall pool have to cover your expected node count with real headroom, because most clusters treat this as effectively fixed at creation time — Lab 4's starved cluster is what happens when nobody did this math, and in production it shows up months later as the cluster grows into a ceiling nobody knew existed.

Verify a new or custom CNI actually keeps all four promises before trusting it. A broken or half-finished plugin that silently NATs pod-to-pod traffic, or leaks a node's private range onto pod addresses, breaks assumptions in every chapter above this one — Services, NetworkPolicy, DNS, a mesh sidecar — none of which re-verify the model themselves; they all just assume it holds. Common mistakes: treating "which CNI" as a single interchangeable checkbox rather than a real decision about optional extras; picking a small pod CIDR "to keep things tidy" and hitting exhaustion at the worst time; leaving an old CNI's config file on disk during a migration; and assuming any pod-placement failure near networking must be the CNI, when a kubelet pod-count ceiling produces an identical symptom for a completely unrelated reason.

System-design connectionWhere this reaches into architecture

The what/how split in this chapter is the same decoupling pattern Chapter 38 showed for storage: a fixed contract (PV/PVC there, the four network rules here) lets a completely different implementation sit underneath without touching a single application. That's why "swap the CNI" is a real platform-level lever — moving to Calico or Cilium for policy enforcement, or to the AWS VPC CNI for native VPC-routable pod IPs (Chapter 58, where ENIs and cloud IPAM replace veths and host-local entirely, while still honoring these exact same four rules) — without a migration touching application code. When you design a platform, this chapter is where you decide how much of the optional surface (policy, encryption, observability) you need before you even open a CNI's feature comparison page, because the mandatory floor was never the interesting part of the decision.

30-secWhat are the four rules of the Kubernetes network model, and who enforces them?

Every pod gets a unique, cluster-wide IP; any pod can reach any other pod's IP directly with no NAT; a node's own agents can reach every pod on that node; and a pod's view of its own IP matches everyone else's — it's never secretly translated. Kubernetes defines these rules and checks for them via conformance testing, but doesn't implement them itself — it delegates the actual wiring to a CNI plugin, invoked once per pod at sandbox creation. Any plugin that keeps these four promises is a valid choice; how it keeps them is entirely up to it.

2-minWalk through what happens, mechanically, from the kubelet scheduling a pod to that pod having a usable IP.

The kubelet asks the container runtime to create the pod's sandbox — a pause container holding an empty network namespace with just a loopback, nothing wired yet. The kubelet then reads the CNI configuration from /etc/cni/net.d, picking the file that sorts first by name if more than one exists, and executes the plugin binary from /opt/cni/bin that the config names, passing CNI_COMMAND=ADD, the container ID, and the namespace path as environment variables, with the JSON config on stdin — that's the entire interface the CNI spec defines, nothing Kubernetes-specific about it. The plugin runs IPAM to get an address from this node's slice of the pod CIDR, creates a veth pair with one end moved into the pod's namespace as eth0, wires the host side so the address is reachable, and prints the assigned IP back as JSON on stdout. The kubelet records that as the pod's status.podIP and only then starts the actual application containers. Teardown calls the same binary with CNI_COMMAND=DEL to release the address and undo the wiring.

DeepWhat's the actual difference between "the Kubernetes network model" and "the CNI specification" — why are they two separate things?

The Kubernetes network model is Kubernetes' own design requirement — four specific rules about pod IP uniqueness and NAT-free reachability, published in Kubernetes' documentation and checked by Kubernetes' own conformance tests. It says nothing about how those rules get satisfied. The CNI specification is a completely separate, general-purpose contract from an independent project for wiring up and tearing down any network namespace — commands, environment variables, a JSON protocol over stdin/stdout — with nothing Kubernetes-specific anywhere in it; it predates its adoption by Kubernetes and is used by other container runtimes too. Kubernetes chose CNI as the mechanism to satisfy its own model rather than writing a bespoke plugin interface, which is why you'll never find "pod" or "Service" mentioned in the CNI spec itself. The practical reason this distinction matters: when you're evaluating a CNI plugin, you're really checking two different things — does it satisfy the fixed, non-negotiable model (nearly all mainstream ones do), and what optional behavior does it add on top, which is where the real differences between Calico, Cilium, Flannel, and the AWS VPC CNI actually live.

ScenarioA node's CPU and memory both show plenty of headroom, but new pods won't schedule there while other nodes take load fine. What do you check, and in what order?

I'd separate "won't schedule" from "won't get networked," because they have different owners. First, is the node schedulable at all — cordoned, tainted, or reporting NotReady? That alone would explain the symptom regardless of free capacity, since the scheduler never places anything there in the first place. Second, and easy to miss: has the node hit its own pod-count ceiling, the kubelet's allocatable pod limit, which defaults to 110 and has nothing to do with IP address space — a node can have a roomy CIDR and still refuse further pods purely on count. Only third would I look at CNI-specific IPAM exhaustion on that node specifically, checking whether its podCIDR is actually populated and whether its local allocation state still has room. I check in that order because the first two explain the exact same user-visible symptom without touching networking at all, and jumping straight to "it's the CNI" because the complaint sounds network-adjacent is the mistake this scenario is built to catch.

Follow-upName two things a CNI plugin is explicitly not responsible for, and say who is.

Service virtual IPs and their load balancing — a CNI plugin never creates or DNATs a ClusterIP; that's kube-proxy, watching Services and EndpointSlices and programming the node's iptables, IPVS, or nftables rules, entirely independent of whichever CNI is installed. And NetworkPolicy enforcement is not universally a CNI responsibility either — it's an optional capability some CNIs choose to implement (Calico, Cilium) and others simply don't (a bare bridge-and-host-local setup, and Flannel without an add-on), so a NetworkPolicy object can exist, look correctly written, and be silently unenforced if the underlying CNI never implements that part of the API at all. Both are easy to assume are "the CNI's job" because they're networking-adjacent, and both assumptions are wrong in ways that matter operationally.

RetainQuick revision

Kubernetes defines a network model — four rules: unique pod IPs, no NAT pod-to-pod, node agents reach their pods, and no secretly-translated addresses — and delegates satisfying it to a CNI plugin rather than implementing it itself. The CNI specification is a separate, generic contract, not Kubernetes-specific, defining a plugin invoked with environment variables and JSON over stdin/stdout for exactly two moments: ADD at pod sandbox creation and DEL at teardown. The kubelet reads the config from /etc/cni/net.d (first file wins by name), execs the binary from /opt/cni/bin, and the plugin runs IPAM, creates a veth, and wires host-side routes before returning the pod's IP — which becomes .status.podIP. A .conflist chains plugins: one does real connectivity, others (portmap, bandwidth, tuning) only modify what it built. A CNI plugin owns IPAM, the veth, and host routes; it does not own Services, DNS, or NetworkPolicy enforcement unless it specifically chooses to add that. This split is why swapping a CNI is a real, application-transparent migration, and why sizing the pod CIDR pool before launch matters — running out of it, or losing a healthy CNI DaemonSet on even one node, breaks new pods while leaving already-wired ones completely unaffected.

The 10 things to remember

  1. The Kubernetes network model (four rules) is Kubernetes' own requirement; CNI is a separate, generic plugin contract it delegates to.
  2. The four rules: unique pod IPs, no NAT pod-to-pod, node agents reach their pods, no secretly-translated addresses.
  3. The kubelet invokes the CNI plugin exactly twice per pod's life: ADD at sandbox creation, DEL at teardown.
  4. Config lives in /etc/cni/net.d (first file by name wins); binaries live in /opt/cni/bin; the interface is env vars + JSON on stdin/stdout.
  5. A .conflist chains plugins — one does IPAM/veth/wiring, others (portmap, bandwidth, tuning) only modify what it built.
  6. A CNI plugin owns IPAM, the veth, and host-side routes — never Services, DNS, or (unless it opts in) NetworkPolicy enforcement.
  7. A pod's .status.podIP is literally the plugin's ADD result, recorded by the kubelet — nothing more mysterious than that.
  8. A CNI DaemonSet down on one node blocks new pods there; it does nothing to pods whose ADD already succeeded.
  9. IPAM/CIDR exhaustion shows up as an empty .spec.podCIDR or a sandbox error naming IP allocation — size the pool before launch.
  10. A pod-placement failure isn't automatically a CNI problem — a kubelet pod-count ceiling (default 110) produces the identical symptom.
