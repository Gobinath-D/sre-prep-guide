Part V · Kubernetes Networking at Packet Level · Chapter 42

Pod networking internals: Pod → Pod

Two pods on different nodes talk to each other by IP as if they were on the same flat LAN — no NAT, no port mapping. That promise is the whole Kubernetes network model, and underneath it is a veth pair, a routing table, and sometimes a UDP tunnel doing quiet work. Learn where every packet goes and cross-node bugs stop being spooky.

Start: Beginner→→→End: Staff-level ~50 min read · kind + kubectl + tcpdump lab

By the end of this chapter you can

  • State the four rules of the Kubernetes network model and why "no NAT pod-to-pod" is the one that matters.
  • Find a running pod's network namespace and the exact veth that carries its traffic to the node.
  • Draw the same-node datapath (veth → bridge/routes → veth) and the cross-node datapath (native routing vs VXLAN overlay).
  • Capture pod-to-pod traffic with tcpdump in both cases and read the pod IPs off the wire.
  • Diagnose the classic "cross-node traffic silently breaks for big packets" incident — an MTU/overlay mismatch — from first principles.

Why this exists · the problemThe problem the pod network solves

You know from Chapter 25 how a single Docker host wires containers up: a bridge, veth pairs, and NAT to hide private container IPs behind the host. That model works on one machine. It falls apart the moment you have fifty machines and want a container on node 3 to reach a container on node 41 by address, the way two processes on one host reach each other by localhost.

Docker's answer on a single host was "give containers private 172.17.x.x addresses and NAT them." If Kubernetes did that per node, every node would hand out the same 172.17.0.2, addresses would collide across the cluster, and a pod could never name another pod uniquely. You'd be back to publishing ports and chasing NAT tables for every pod-to-pod call — unworkable when a single service has a thousand replicas spread across a hundred nodes.

So Kubernetes made a deliberate architectural choice, and wrote it down as a contract every network plugin must satisfy. It's four rules, and I want you to memorise the shape of them because the rest of Part V is just their consequences:

  • Every pod gets its own unique, cluster-wide IP address.
  • Any pod can reach any other pod's IP directly, without NAT — the destination pod sees the source pod's real IP.
  • Agents on a node (kubelet, system daemons) can reach all pods on that node.
  • A pod's view of its own IP is the same as everyone else's view of it. It isn't secretly translated.

The second rule is the load-bearing one. "Any pod talks to any pod without NAT" is what lets you treat the cluster as one flat network and stop thinking about which machine anything runs on. The job of a CNI plugin (Chapter 41) is to make that true — to build a fabric where a packet from 10.244.0.5 to 10.244.3.9 arrives with both addresses intact, whether those pods share a node or sit two racks apart.

Key point

A pod's eth0 is still one end of a veth pair, exactly like a Docker container's — that part didn't change. What changed is the routing policy around it: pod IPs are real and cluster-routable, and pod-to-pod traffic is not source-NATed. Hold those two facts and the entire datapath is just "how does this pod's packet reach that pod's veth."

Mental model · analogyThe mental model: one phone system across many buildings

Real-world analogy

Picture a company with buildings scattered across a city. In Chapter 25 we had one building with an internal switchboard and extensions — but every building ran its own switchboard, so extension 202 existed in all of them and you had to dial the building's public number first, then the extension. Confusing and error-prone.

Kubernetes rips that out and installs one company-wide phone system. Every desk in every building gets a globally unique direct-dial number (the pod IP). You dial 5-0-9-1 and it rings that one specific desk, whether it's down the hall or across town. Nobody dials a building number first; nobody's call gets its caller-ID rewritten on the way. The caller sees the callee's number and the callee sees the caller's number — every time.

Making that work needs wiring between buildings. Two ways to do it: run direct fibre between buildings and program the routers so "numbers 5-0-xx live in the east building" (that's native routing — no rewrapping, just good directions), or lay the calls inside company courier pouches addressed building-to-building, unpacked at the far end (that's an overlay/VXLAN tunnel — the original call rides inside an outer envelope). Both deliver the same call intact; the pouch just adds envelope weight, which matters when the envelope plus the letter won't fit through the mail slot.

ArchitectureSame-node and cross-node datapaths

Start with the easy case: two pods on the same node. Each pod lives in its own network namespace with an eth0 that's one end of a veth pair; the other end sits in the node's root namespace. Delivery between the two host-side veths happens one of two ways, and which one you get depends on the CNI:

  • Bridge-style CNIs attach every host-side veth to a Linux bridge (often called cni0 or kube-bridge). Same-node pod-to-pod is then a plain layer-2 hop across that bridge — MAC to MAC, exactly like Docker's docker0.
  • Pure-L3 CNIs (Calico, and kind's kindnet in its point-to-point mode) skip the bridge. The host side of each veth gets a /32 route to that one pod, and the node's routing table forwards between them. No bridge, just routes and proxy_arp.

Either way the pod IPs are untouched and there's no NAT. Here's the same-node path with both delivery styles drawn in:

Now the interesting case: pod A on node 1 wants pod B on node 2. The packet leaves pod A exactly as before — out eth0, across the veth, into node 1's root namespace. Then it has to cross the physical (or virtual) network between nodes, and this is where CNIs diverge hard. Two families:

Think first: on the cross-node native-routing path, what does tcpdump on the node's physical interface show — pod IPs or node IPs?

Pod IPs. With native routing there's no encapsulation, so the packet on the wire between nodes still has source 10.244.0.5 and destination 10.244.1.6 — the node's interface is just routing them. That's exactly why native routing is easier to debug: what you capture is what the pods sent. On an overlay you'd instead see the outer node-to-node UDP packet, and you'd have to ask tcpdump to decode VXLAN (or capture on the tunnel device) to see the inner pod addresses. This single difference — "can I see pod IPs on the physical NIC?" — tells you in one command which family your CNI is in.

Internal workingWhat the CNI does when a pod starts

When the kubelet asks the container runtime to create a pod, the runtime creates the pod's sandbox (the pause container, which does nothing but hold the namespaces open) and then calls the CNI plugin with ADD. Here's what happens, step by step, and it will look familiar after Chapter 25:

  1. The runtime creates the pod's network namespace. It's empty except for a loopback that starts down. Every container you list in the pod spec will join this namespace — that's why containers in one pod share localhost and one IP. The pause container owns the namespace so it survives individual containers restarting.
  2. The kubelet invokes the CNI plugin. It reads the CNI config from /etc/cni/net.d/, then runs the plugin binary from /opt/cni/bin/ with the namespace path and the action ADD on stdin. This is the contract defined by the CNI spec — the kubelet doesn't know or care whether the plugin is Calico, Cilium, Flannel, or kindnet.
  3. The plugin creates a veth pair. Two linked virtual interfaces. One end is moved into the pod's namespace and renamed eth0; the other stays in the node's root namespace as vethXXXX. Whatever enters one end leaves the other.
  4. The plugin does IPAM and assigns the pod IP. It picks an address from the node's slice of the cluster pod CIDR — for kind, each node owns a /24 out of 10.244.0.0/16. It sets that on eth0, brings lo and eth0 up, and installs a default route inside the pod pointing at the veth (often via a link-local gateway or the veth itself).
  5. The plugin wires the root-namespace side. Bridge-style: enslave vethXXXX to cni0. Pure-L3 (Calico, kindnet ptp): add a /32 route on the host for the pod via its veth and enable proxy_arp on the veth. This is what decides same-node delivery.
  6. The fabric learns the route to this pod's node. For the pod to be reachable from other nodes, every node needs to know "pod CIDR X lives behind node Y." Native-routing CNIs install those routes (kindnet writes host routes for peer nodes; Calico distributes them over BGP; the VPC CNI programs VPC route tables and ENIs). Overlay CNIs instead maintain a map of pod-CIDR → node-IP and program the VXLAN device (flannel.1) so encapsulated packets go to the right node.
Containers in a pod share one network namespace

This is why a sidecar can reach the main container on localhost:8080 with no service, no DNS, no cross-pod anything — they're literally in the same netns, sharing lo, the same eth0, and the same single pod IP. It's also why two containers in one pod cannot both bind the same port: one port space. The service mesh proxies of Part VII (Chapter 67) rely on exactly this — the Envoy sidecar intercepts the app's traffic because it shares the pod's network namespace.

ComponentsThe pieces and what each owns

  • The pod network namespace — one per pod, holding lo, eth0, the pod's routing table, and its single IP. Held open by the pause/sandbox container so it outlives individual app containers.
  • The veth pair — the virtual cable. eth0 inside the pod, vethXXXX in the node root namespace. The kernel hands frames straight from one end to the other.
  • The node root namespace's delivery layer — either a bridge (cni0) that switches at L2, or a set of per-pod /32 routes that forward at L3. This is the same-node datapath.
  • The CNI plugin — the binary in /opt/cni/bin/ plus its config in /etc/cni/net.d/, invoked per pod. It owns IPAM, the veth, the host-side wiring, and (with its daemon) the cross-node routes or overlay. Calico, Cilium, Flannel, Weave, the AWS VPC CNI, and kindnet are all interchangeable implementations of the same contract.
  • The inter-node fabric — the thing that makes a pod on node 2 reachable from node 1. Native: routes/BGP/VPC. Overlay: a VXLAN (or Geneve/WireGuard) tunnel device on each node and a mapping of pod CIDRs to node IPs.
  • The pause container — one per pod, near-zero footprint, whose only job is to hold the namespaces so the pod's IP and netns are stable across container restarts.

Data flowFollowing one cross-node request end to end

Pod A (10.244.0.5 on node 1) opens a TCP connection to pod B (10.244.1.6 on node 2), native-routing CNI. A's stack looks at its routing table: 10.244.1.6 isn't on-link, so it goes to A's default route — out eth0, across the veth into node 1's root namespace. Node 1's routing table has an entry the CNI installed: 10.244.1.0/24 via 172.18.0.4 dev eth0 (node 2's address). So node 1 forwards the packet — source and destination still the pod IPs — out its physical interface toward node 2. Node 2 receives a packet destined for 10.244.1.6; its routing table says that address is on-link via vethB, so it delivers across the veth into pod B's namespace, where B's eth0 accepts it. B replies to 10.244.0.5 and the mirror-image path carries it home. No address was rewritten anywhere; conntrack didn't touch it. That's the model's promise made concrete.

Swap in an overlay and only the middle changes: node 1's route for 10.244.1.0/24 points at the VXLAN device, which wraps the whole pod packet in an outer node1→node2 UDP datagram, node 2's kernel decapsulates it, and the inner packet is delivered to vethB exactly as before. The pods never know. The network only ever saw node-to-node traffic.

Think first: a pod's eth0 shows MTU 1500, but the CNI uses VXLAN over a 1500-MTU network. What breaks, and when?

Large packets break; small ones don't. VXLAN adds about 50 bytes of outer headers. If the pod emits a full 1500-byte packet, wrapping it makes a 1550-byte packet that won't fit the node network's 1500 MTU. The handshake (small packets) succeeds, DNS succeeds, tiny requests succeed — so the app "connects fine." Then a bulk response, a large POST, or a TLS certificate chain pushes a full-size segment, and it's silently dropped or needs fragmentation that the overlay may not allow (the DF bit + a blocked ICMP "packet too big" gives a blackhole). The fix is to set the pod MTU to the underlay MTU minus the encap overhead — 1450 for VXLAN on a 1500 underlay — so pods never emit a packet that can't be wrapped and forwarded. This is the single most common cross-node CNI incident, and we reproduce it in the labs.

Hands-onLabs — build, understand, break, troubleshoot

You need Docker plus kind and kubectl. kind runs each Kubernetes node as a Docker container, so "the node" is something you can docker exec into and run ip, tcpdump, and crictl inside. Build a two-node cluster with kind's default CNI (kindnet):

bash
# Two nodes: one control-plane, one worker. Default CNI is kindnet.
kind create cluster --name netlab --config - <<'EOF'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
EOF

kubectl get nodes -o wide            # note the two node names + their IPs
docker ps --format '{{.Names}}'      # netlab-control-plane, netlab-worker
Lab 1Build — find a pod's veth and its network namespaceBuild

Deploy two pods and force them onto different nodes so we can study both the same-node and cross-node paths. A tiny netshoot pod gives us tcpdump, dig, and ip inside the pod netns.

bash
kubectl run p1 --image=nicolaka/netshoot --overrides='{"spec":{"nodeName":"netlab-worker"}}' --command -- sleep infinity
kubectl run p2 --image=nicolaka/netshoot --overrides='{"spec":{"nodeName":"netlab-control-plane"}}' --command -- sleep infinity
kubectl wait --for=condition=Ready pod/p1 pod/p2 --timeout=90s
kubectl get pods -o wide             # p1 and p2, their pod IPs, and their nodes
OutputNAME READY STATUS IP NODE p1 1/1 Running 10.244.1.2 netlab-worker p2 1/1 Running 10.244.0.5 netlab-control-plane

Each node owns a /24 out of 10.244.0.0/16. Now find the veth. Inside the pod, eth0's iflink is the interface index of its host-side partner; match that index on the node:

bash
IDX=$(kubectl exec p1 -- cat /sys/class/net/eth0/iflink)
echo "host-side veth ifindex = $IDX"
docker exec netlab-worker ip -o link | grep -E "^$IDX:"
Outputhost-side veth ifindex = 8 8: veth9c3a1f2b@if2: <BROADCAST,MULTICAST,UP,LOWER_UP> ... link-netns cni-xxxx

That veth9c3a1f2b is the node end of p1's cable; the @if2 tells you the pod's eth0 is index 2 inside its namespace. Now see the namespace itself from the node — every non-hostNetwork pod is a distinct net namespace:

bash
docker exec netlab-worker lsns -t net    # root netns + one per pod (the pause proc)

You've now located, by hand, the two objects that carry every one of this pod's packets: the veth in the node's root namespace, and the isolated netns on the other side of it. That's the whole physical basis of pod networking.

Lab 2Understand — capture same-node pod-to-pod, then see the shared-netns trickUnderstand

Put two pods on the same node and watch a ping cross. First, how does kindnet actually deliver same-node traffic — bridge or routes? Ask the node:

bash
kubectl run s1 --image=nicolaka/netshoot --overrides='{"spec":{"nodeName":"netlab-worker"}}' --command -- sleep infinity
kubectl run s2 --image=nicolaka/netshoot --overrides='{"spec":{"nodeName":"netlab-worker"}}' --command -- sleep infinity
kubectl wait --for=condition=Ready pod/s1 pod/s2 --timeout=90s

docker exec netlab-worker ip route            # per-pod /32 routes? or a cni0 bridge?
docker exec netlab-worker bridge link 2>/dev/null | head  # empty on a pure-L3 CNI
Output (kindnet — pure L3)10.244.1.2 dev veth9c3a1f2b scope host 10.244.1.3 dev vethb71e0a44 scope host default via 172.18.0.1 dev eth0

No cni0; kindnet installs a /32 host route per local pod and forwards between them in the node's routing table. (A bridge-style CNI would show a cni0 with the veths enslaved to it — same idea, different plumbing.) Now capture the ping inside s2 using an ephemeral debug container that shares s2's netns, and ping from s1:

bash
S2_IP=$(kubectl get pod s2 -o jsonpath='{.status.podIP}')
# Terminal A — sniff inside s2's network namespace:
kubectl debug -it s2 --image=nicolaka/netshoot --target=s2 -- tcpdump -ni eth0 icmp
# Terminal B — ping s2 from s1:
kubectl exec s1 -- ping -c3 "$S2_IP"
Output (inside s2)IP 10.244.1.4 > 10.244.1.5: ICMP echo request, id 12, seq 1 IP 10.244.1.5 > 10.244.1.4: ICMP echo reply, id 12, seq 1

Source and destination are the two pod IPs, untouched — no NAT on the same-node path, precisely as the model requires. For the shared-namespace point: exec into any pod and note that a sidecar would reach the app on 127.0.0.1 because they'd share this exact lo and eth0. One netns, one IP, one port space per pod.

Lab 3Break — cross-node traffic that works small and dies bigBreak

This is the incident that eats afternoons. First confirm the cross-node path works normally, then introduce an MTU mismatch and watch it break in the most misleading way possible. p1 (worker) and p2 (control-plane) are on different nodes from Lab 1.

bash
P2_IP=$(kubectl get pod p2 -o jsonpath='{.status.podIP}')
kubectl exec p1 -- ping -c2 "$P2_IP"                       # cross-node, works
kubectl exec p1 -- ping -c2 -M do -s 1400 "$P2_IP"         # 1400+28 payload, DF set — works

# Now shrink p1's eth0 MTU to simulate an overlay whose encap overhead wasn't accounted for,
# while the path still advertises 1500. Small packets fine; full-size ones will vanish.
kubectl exec p1 -- ip link set eth0 mtu 1400
kubectl exec p1 -- ping -c2 -M do -s 1400 "$P2_IP"         # now what?

Small pings still pass. A large TCP transfer, though, stalls after the handshake. Reproduce that shape with a big payload over TCP and watch it hang, then investigate before reading the reveal:

bash
# Serve 5 MB from p2 and pull it from p1 — the handshake completes, the body stalls:
kubectl exec p2 -- sh -c 'head -c 5000000 /dev/urandom > /tmp/blob && nohup python3 -m http.server 8080 --directory /tmp >/dev/null 2>&1 &'
kubectl exec p1 -- curl -s -m 8 -o /dev/null -w '%{http_code} %{size_download}\n' "http://$P2_IP:8080/blob"
Output000 0 # timed out: connection opened, bytes never arrived

The connection establishes but the download hangs and times out. Ping works, small requests work, the app logs show a connection that "just stopped." What is actually happening? Work it out from what you know about packet sizes, then check.

Reveal the cause

It's an MTU blackhole. You set p1's eth0 to 1400, but the TCP handshake negotiated a maximum segment size assuming a larger path, and — more to the point — p2 is still sending full-size segments toward p1. When p2's 1500-byte segments hit the constrained path with the "don't fragment" bit set, they're too big and get dropped; the ICMP "fragmentation needed" that should tell the sender to back off is often filtered or lost, so the sender just retransmits the same too-big packet forever. Small packets (pings, the handshake, HTTP headers) fit and pass, which is why everything looks healthy until the first full-size data segment.

Confirm it directly — the smaller payload that fits still works, the larger one with DF set fails:

bash
kubectl exec p1 -- ping -c2 -M do -s 1372 "$P2_IP"   # 1372+28 = 1400: passes
kubectl exec p1 -- ping -c2 -M do -s 1400 "$P2_IP"   # 1400+28 = 1428 > 1400: fails

In a real cluster you don't set the MTU by hand — the CNI does, and the bug is that it set the pod MTU to 1500 while the actual path is an overlay that only carries 1450 of payload (VXLAN eats ~50 bytes). Fix it at the CNI: set the pod/overlay MTU to underlay-minus-encap. Restore the lab with kubectl exec p1 -- ip link set eth0 mtu 1500. The reflex to build: "works small, dies big, ping is fine" is MTU until proven otherwise.

Lab 4Troubleshoot — prove the cross-node mechanism from the wireTroubleshoot

Is your CNI routing natively or tunnelling? Don't guess — capture on the node's physical interface while pods talk across nodes, and read the addresses. This is the fastest way to classify any CNI.

bash
# Show the route node1 uses to reach node2's pod CIDR:
docker exec netlab-worker ip route | grep 10.244
# Capture on the worker's physical interface while p1 pings p2 (other node):
P2_IP=$(kubectl get pod p2 -o jsonpath='{.status.podIP}')
docker exec netlab-worker timeout 6 tcpdump -ni eth0 "icmp or udp port 4789 or udp port 8472" &
kubectl exec p1 -- ping -c3 "$P2_IP"

Look at what crosses eth0. Are the addresses the pod IPs, or node IPs wrapping something? Decide which family you're in before revealing.

Reveal how to read it
Output (kindnet — native routing)# ip route 10.244.0.0/24 via 172.18.0.3 dev eth0 # control-plane's pod CIDR via its node IP default via 172.18.0.1 dev eth0 # tcpdump on eth0 IP 10.244.1.2 > 10.244.0.5: ICMP echo request, id 20, seq 1 IP 10.244.0.5 > 10.244.1.2: ICMP echo reply, id 20, seq 1

The pod IPs appear directly on the node's physical interface, and the route shows 10.244.0.0/24 via 172.18.0.3 — node 2's address. That's native routing: no encapsulation, the network itself carries pod packets because kindnet installed a route per peer node's CIDR. You saw no traffic on UDP 4789/8472 because there is no VXLAN here.

On an overlay CNI the same capture would show IP 172.18.0.2.<port> > 172.18.0.3.4789: VXLAN, ... IP 10.244.1.2 > 10.244.0.5: ICMP — node IPs on the outside, pod IPs nested within, and you'd add -vv or capture on the tunnel device (flannel.1) to see the inner packet. One capture, one question answered: is this cluster routing or tunnelling?

Lab 5Production challenge — a cross-node blackhole with a green dashboardSenior challenge

Simulate the incident an on-call engineer actually gets paged for: pods on one node can't reach pods on another, but every pod is Running, every readiness probe is green (probes are local, kubelet-to-pod), and same-node traffic is fine. Break the fabric by deleting node 1's route to node 2's pod CIDR, then work it like a real incident.

bash
# Break it: drop the worker's route to the control-plane node's pod CIDR.
CP_CIDR=$(kubectl get node netlab-control-plane -o jsonpath='{.spec.podCIDR}')
GW=$(docker exec netlab-worker ip route | awk -v c="$CP_CIDR" '$1==c{print $3}')
docker exec netlab-worker ip route del "$CP_CIDR"
# Symptom: cross-node dead, same-node alive, pods all Ready.
P2_IP=$(kubectl get pod p2 -o jsonpath='{.status.podIP}')   # p2 is on control-plane
kubectl exec p1 -- ping -c2 -W1 "$P2_IP" || echo "CROSS-NODE DOWN"
kubectl get pods -o wide

Now the senior question, no hand-holding: you have "some pods can't reach some other pods, intermittently by which node they're on, and nothing is CrashLooping." What is your ordered investigation, and what class of cause are you steering toward? Reason it out before revealing.

Reveal the approach and the fix

First, characterise the blast radius by topology, not by service. The tell in this whole class of bug is that reachability correlates with which nodes the source and destination are on. Test a matrix: same-node pairs (work) vs cross-node pairs (fail). The moment you see "same-node fine, cross-node broken," you've eliminated the app, the Service layer, and DNS — this is the pod fabric between nodes.

Then inspect the fabric on the node, not the pod. Check the routes and the CNI agent:

bash
docker exec netlab-worker ip route | grep 10.244        # is the peer CIDR route present?
kubectl -n kube-system get pods -l app=kindnet -o wide   # is the CNI daemon healthy on every node?
kubectl -n kube-system logs -l app=kindnet --tail=20

The missing 10.244.0.0/24 via 172.18.0.3 route is the smoking gun: node 1 has no idea how to reach node 2's pods. In the wild this is a dead or crash-looping CNI agent on one node, a broken BGP session (Calico), a VXLAN device that didn't come up, a cloud route table or security group blocking node-to-node traffic, or an MTU blackhole like Lab 3 that only kills large packets. Restore the route and connectivity returns instantly:

bash
docker exec netlab-worker ip route add "$CP_CIDR" via "$GW"
kubectl exec p1 -- ping -c2 "$P2_IP"                     # back

The durable lesson: pod-to-pod reachability failures that track node topology are a fabric problem — routes, the CNI daemon, overlay devices, node firewalls, or MTU — and readiness probes will happily stay green throughout, because the kubelet probes each pod locally and never tests the cross-node path. When you're done: kind delete cluster --name netlab.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · cross-node traffic works small, breaks big (MTU)

Symptom: connections between pods on different nodes establish, then hang; small requests and health checks pass, large responses or uploads stall. Often "TLS handshake to service X times out" because the certificate chain is the first full-size packet. First cut: ping -M do -s <size> across nodes, bisecting the size to find the cliff. Confirm: compare the pod interface MTU with the underlay and the CNI's encap overhead (VXLAN ~50 bytes, WireGuard ~60, Geneve variable). Usual cause: pod MTU set to the underlay MTU without subtracting encap overhead, plus ICMP "packet too big" being filtered so Path MTU Discovery can't self-correct (RFC 1191).

Incident pattern · one node is an island

Symptom: pods on a specific node can't reach pods elsewhere (or can't be reached), while that node's own same-node traffic is fine and all pods show Running/Ready. First cut: build a reachability matrix by node; if failures cluster on one node, it's that node's fabric. Confirm: is the CNI agent pod healthy on that node, are its routes/BGP sessions/overlay devices present, does node-to-node traffic pass the underlay firewall? Usual cause: a crashed CNI daemon, a broken route/BGP peering, or a security group / firewall dropping node-to-node or VXLAN UDP.

Incident pattern · pod stuck ContainerCreating with a network error

Symptom: a pod never gets an IP; events show failed to set up sandbox ... plugin ... or failed to allocate IP. First cut: kubectl describe pod and the kubelet/CNI logs on that node. Usual cause: the CNI binary or config missing from /opt/cni/bin or /etc/cni/net.d, the CNI daemon not yet running on a fresh node, or IPAM exhaustion — the node's pod CIDR (or, on the VPC CNI, the node's available IPs, Chapter 58) is full. The pod networking never even got built; this isn't a datapath bug, it's a setup bug.

Production · security · performanceWhat matters in production

Choosing native vs overlay. If your network can route pod CIDRs — a flat L2 (kind), BGP to the fabric (Calico), or a cloud that hands pods real VPC addresses (the AWS VPC CNI, Chapter 58) — prefer native routing. It's faster, and every packet on the wire is a real pod IP, so tcpdump and flow logs mean something. Reach for an overlay when you can't change the underlay's routing but you can send UDP between nodes; you pay encap CPU and the MTU tax in exchange for running almost anywhere. Whatever you pick, set the MTU deliberately and check it after every CNI upgrade — silent MTU regressions are a recurring outage.

Security. The flat, NAT-free model means every pod can reach every other pod by default — including across namespaces. That's convenient and dangerous: a compromised pod has L3 reach to your whole cluster. The control for that is NetworkPolicy (Chapter 47), which most CNIs enforce with eBPF or iptables at the pod's veth. Also remember the shared-netns fact: anything in a pod can sniff and talk on that pod's lo, which is exactly how sidecar proxies intercept traffic — a feature for a mesh, a risk if you put untrusted containers in one pod.

Performance. The veth hop is cheap; the expensive parts are encapsulation (per-packet CPU, worse with software checksums) and conntrack on the paths that do use NAT (Services and egress, next two chapters). Overlays also interact badly with NIC offloads unless the CNI enables VXLAN offload. For latency-sensitive or very high packet-rate workloads this is where eBPF-based datapaths (Cilium) and native routing earn their keep. Common mistakes: assuming pod IPs are stable (they change every reschedule — never hard-code them, use Services and DNS, Chapters 43 and 45); assuming pods can't reach each other across namespaces (they can, until a NetworkPolicy says otherwise); and blaming the app for a hang that is really an MTU blackhole two layers below it.

System-design connectionWhere this reaches into architecture

The flat pod network is the substrate every higher layer assumes. Services (Chapter 43) are just kernel rules that DNAT a virtual IP to one of these pod IPs — they only work because any node can already reach any pod. Cluster DNS (Chapter 45) resolves names to pod and service IPs on this same fabric. A service mesh (Chapter 66) rides on it by sharing the pod netns. When you design for scale, the pod network is where you decide the shape of the whole platform: how many pods per node (IPAM and CIDR sizing), whether pod IPs are routable off-cluster (native/VPC) or hidden (overlay), and how you'll segment a flat network that trusts itself by default. Get the CIDR math and the MTU right at cluster-build time; both are painful to change once workloads depend on them. This is also the layer AWS reshapes most in Chapter 58, where pods get first-class VPC IPs and the "fabric" becomes the VPC itself.

InterviewInterview questions & answers

Answer each in your head first, then open it.

30-secWhat are the rules of the Kubernetes network model?

Every pod gets its own unique, cluster-wide IP; any pod can reach any other pod's IP directly without NAT; node agents can reach all pods on their node; and a pod sees its own IP the same way everyone else does. The one that drives everything is "pod-to-pod without NAT" — it lets you treat the cluster as one flat network and stop caring which node a pod runs on. The CNI plugin's job is to make that true, whether by routing pod CIDRs natively or by tunnelling them in an overlay.

2-minTrace a packet from a pod on node 1 to a pod on node 2.

The source pod's stack sees the destination isn't on-link and sends it to its default route: out eth0, which is one end of a veth pair, into the node's root namespace on the other end. Node 1's routing table has a CNI-installed entry for the destination pod's CIDR. With native routing that entry points at node 2's address, so node 1 forwards the packet — pod IPs untouched — out its physical NIC; node 2 receives it, its routing says the destination is on-link via that pod's veth, and delivers it into the pod's namespace. With an overlay, node 1's route points at a VXLAN device that wraps the pod packet in an outer node1-to-node2 UDP datagram; node 2 decapsulates and delivers the inner packet the same way. Either path preserves the source and destination pod IPs and does no NAT. Return traffic mirrors it. The only difference between the two families is whether the network sees pod IPs or node IPs on the wire.

DeepWhy do overlays cause MTU problems, and how do you size the MTU correctly?

An overlay wraps each pod packet in outer headers — VXLAN adds roughly 50 bytes (outer IP + UDP + VXLAN), Geneve is variable, WireGuard about 60. If the pod MTU equals the underlay MTU, a full-size pod packet plus the outer headers exceeds what the underlay can carry, so the encapsulated packet is dropped or needs fragmentation. Because the "don't fragment" bit is usually set and the ICMP "packet too big" messages are often filtered, Path MTU Discovery can't correct it and you get a blackhole that only affects large packets — handshakes and small requests pass, bulk transfers and TLS chains hang. The fix is to set the pod (or tunnel-device) MTU to the underlay MTU minus the encapsulation overhead: 1450 for VXLAN over a 1500 underlay. On jumbo-frame underlays you get more headroom. The rule I keep: the pod must never be able to emit a packet that can't survive encapsulation and forwarding.

ScenarioPods on node A can't reach pods on node B, but same-node traffic is fine and all pods are Ready. Where do you look?

The topology correlation is the whole clue: reachability tracking "which nodes" means it's the inter-node fabric, not the app, Services, or DNS. I'd confirm with a quick same-node vs cross-node matrix, then move to the nodes: are the CNI agent pods healthy on both nodes, are the routes to each other's pod CIDRs present (or the BGP sessions up, or the VXLAN devices up), and does node-to-node traffic pass the underlay firewall — including the VXLAN UDP port if it's an overlay? I'd also check MTU, since an MTU blackhole presents as cross-node failures that spare small packets. Readiness stays green through all of this because the kubelet probes each pod locally and never exercises the cross-node path, so I never trust "all Ready" to mean "network is fine."

Follow-upWhy can two containers in the same pod talk over localhost, and what are the consequences?

Because every container in a pod joins the same network namespace — held open by the pause container — so they share one lo, one eth0, and one pod IP. A sidecar reaches the main container on 127.0.0.1 with no Service or DNS involved. The consequences: containers in a pod can't both bind the same port (single port space), they can sniff each other's loopback traffic, and this is precisely the mechanism a service mesh uses — the Envoy sidecar shares the netns and intercepts the app's traffic. It's a feature for tightly coupled helpers and a risk if you'd colocate untrusted code, so the guidance is one concern per pod unless the containers genuinely must share a network identity.

RetainQuick revision

Kubernetes gives every pod a unique, cluster-routable IP and requires that any pod reach any other pod without NAT. A pod's eth0 is one end of a veth pair whose other end is vethXXXX in the node's root namespace; containers in a pod share that one namespace and IP. Same-node delivery is either a layer-2 hop across a bridge (cni0) or L3 forwarding between per-pod /32 routes — the CNI decides. Cross-node delivery is either native routing (pod IPs stay on the wire; the network routes pod CIDRs via node IPs, over host routes, BGP, or VPC routes) or an overlay (the pod packet is wrapped in an outer node-to-node VXLAN/UDP datagram and decapsulated at the far node). Overlays add ~50 bytes, so the pod MTU must be the underlay MTU minus that overhead or large packets blackhole while small ones pass. Capture on the node's physical NIC and the addresses tell you which family you're in. Pod-to-pod failures that track node topology are fabric problems — routes, CNI daemon, overlay, firewall, or MTU — and readiness probes stay green through all of them.

The 10 things to remember

  1. The model: unique pod IPs, pod-to-pod with no NAT, node reaches its pods, and a pod's IP isn't secretly translated.
  2. A pod's eth0 is one end of a veth pair; the host end vethXXXX lives in the node's root namespace.
  3. All containers in a pod share one network namespace and IP (held by pause): they talk over localhost.
  4. Same-node delivery is a bridge (cni0, L2) or per-pod /32 host routes (L3) — the CNI chooses; pod IPs stay intact either way.
  5. Cross-node native routing keeps pod IPs on the wire; the network routes pod CIDRs via node IPs (host routes, BGP, VPC).
  6. Cross-node overlay wraps the pod packet in an outer node-to-node VXLAN/UDP packet and decapsulates at the far node.
  7. Overlays add ~50 bytes; set pod MTU = underlay MTU − encap overhead (1450 for VXLAN/1500) or large packets blackhole.
  8. "Works small, dies big, ping is fine" = MTU until proven otherwise; bisect with ping -M do -s.
  9. tcpdump on the node's physical NIC: pod IPs = native routing; node IPs on UDP 4789/8472 = overlay.
  10. Pod-to-pod failures that correlate with node topology are fabric bugs — routes, CNI daemon, overlay, firewall, MTU — not the app.
