CoreDNS and service discovery

Every Service you've called by name in the last two chapters worked because of a lookup you never saw. CoreDNS is the piece that turns "api" into a ClusterIP — and the pod's own resolver settings quietly decide whether that lookup costs one query or four.

Start: Beginner→→→End: Staff-level ~50 min read · kind + dig lab

By the end of this chapter you can

  • Read a pod's /etc/resolv.conf and predict exactly which names resolve in one query and which don't.
  • Explain what ndots:5 actually costs, and why it's not quite what most write-ups claim.
  • Trace a Service name from a pod's query to CoreDNS's plugin chain and, when needed, an upstream resolver.
  • Explain what NodeLocal DNSCache changes about the datapath, and the specific kernel race it exists to avoid.
  • Diagnose cluster-wide name-resolution failure and tell it apart from one misbehaving pod.

Why this exists · the problemPods need names, not just addresses

Chapter 43 gave every Service a ClusterIP. That solves "the pod IPs behind this name keep changing," but it quietly assumes you already know the ClusterIP — and nobody wants to hard-code 10.96.12.34 into an application config. You want to write http://api and have it work, the same way you don't memorise your bank's IP address; you type its name and trust something else to fill in the number.

That something is DNS, and inside a Kubernetes cluster it's a specific piece of software: CoreDNS, running as an ordinary Deployment, fronted by an ordinary Service (conventionally named kube-dns for historical reasons, even though the software is CoreDNS), doing an ordinary job — answer queries — for a very specific set of names it's authoritative for: everything under cluster.local. Every pod's own DNS resolver is pointed at it automatically, no configuration required on your part. That last sentence is doing a lot of work, and this chapter is about exactly how.

Key point

CoreDNS isn't a separate subsystem bolted onto the cluster — it's a Service, like any other, and it's reachable through the exact DNAT machinery from Chapter 43. The interesting parts are what decides which name a pod actually asks for before that query ever leaves it, and what CoreDNS does once the query lands.

Mental model · analogyThe mental model: a mailroom that guesses before it asks outside

Real-world analogy

Picture a large corporate mailroom that receives an envelope addressed simply to "Priya" — no floor, no building, nothing else. Company convention says: assume that's shorthand, and try the most specific guess first — "Priya, 4th floor, Marketing" — then a broader one — "Priya, 4th floor" — then broader still — "Priya, this building." Each wrong guess gets stamped "no such person on file" instantly, because the mailroom keeps its own building directory and never has to phone anyone outside to know that. Only once every internal guess is exhausted does the mailroom accept that "Priya" might be a complete, external address after all, and hand it to the actual postal service to deliver.

That's fine when the envelope really was shorthand for someone inside the building. It's wasteful when the envelope was always meant for "Priya Sharma, Consulate Plaza" — an address that happens to look short enough, by the mailroom's own counting rule, that it still tries all three internal guesses before finally sending it out. Three stamps of "no such person," then finally the real delivery. That counting rule — how many parts an address needs before the mailroom trusts it's already complete — is ndots. And because the mailroom keeps a logbook of both delivered mail and known-bad guesses for a while, asking for the same wrong guess twice in a row is at least cheap the second time — that's caching, including negative caching.

ArchitecturePod query → CoreDNS → upstream

A pod's DNS query is just another packet, and it follows a path built entirely from pieces you already know. It leaves the pod addressed to a ClusterIP — the kube-dns Service's — gets DNATed by kube-proxy to an actual CoreDNS pod exactly as Chapter 43 described for any Service, and lands in CoreDNS's plugin chain. What happens next depends on whether the name is one CoreDNS owns.

Think first: in Chapter 15 you rewrote a plain Linux box's resolv.conf to mimic a pod's and watched api.github.com turn into four DNS packets, all leaving your own machine. Inside a real cluster, do all four of those packets leave the cluster too?

No — and this is the correction worth holding onto. In Chapter 15's simulation there was no CoreDNS in the loop, so every one of the four attempts had nowhere to go but out to the real nameserver you configured. Inside a cluster, three of those four attempts — api.github.com.default.svc.cluster.local, api.github.com.svc.cluster.local, api.github.com.cluster.local — all still end in cluster.local, so CoreDNS's kubernetes plugin claims them, finds nothing, and returns NXDOMAIN itself, without ever forwarding upstream. Only the fourth, absolute attempt — api.github.com., no cluster suffix — actually falls through to the forward plugin and leaves the cluster. The cost of the cascade is real, but it's mostly three extra round trips through the Service datapath and three extra lookups on CoreDNS's own CPU, not three extra trips to the internet.

Internal workingFrom a bare name to a cascade of queries

  1. The kubelet writes each pod's /etc/resolv.conf at creation time. With the default dnsPolicy: ClusterFirst, it sets nameserver to the cluster DNS Service's ClusterIP (commonly 10.96.0.10, configured via the kubelet's --cluster-dns flag), a search line with <namespace>.svc.cluster.local svc.cluster.local cluster.local — and, unless it would exceed the resolver's own limits, the node's own search domains appended after those. Most C libraries cap the search list around six entries; if the merge would exceed that, the kubelet truncates it and records a warning event rather than silently guessing.
  2. It also sets options ndots:5. Per resolv.conf(5), if a queried name has fewer dots than the ndots value, the resolver tries each search-list suffix, in order, before ever trying the name as given; names with ndots or more dots — or any name ending in a literal trailing dot — are tried as-is first. Kubernetes picks 5 specifically because the deepest ordinary in-cluster form, <svc>.<ns>.svc.cluster.local, has only 4 dots — one below the threshold — which guarantees that even the fully-written form still gets the search-list treatment, and more importantly guarantees that the common shorthand people actually type (api, 0 dots) resolves in a single query by matching the very first search suffix.
  3. The app calls getaddrinfo("api"), or your code just opens http://api. The C library resolver reads resolv.conf, counts the dots (zero, well under 5), and tries the first search suffix: api.default.svc.cluster.local. For a real Service in the pod's own namespace, that's an immediate hit — one query, one answer. This is why short in-cluster names are cheap: the search list is built specifically so the common case lands on the first try.
  4. The query travels to the kube-dns ClusterIP and gets DNATed by kube-proxy exactly like any other Service call from Chapter 43 — possibly to a CoreDNS pod on a different node, possibly with the usual conntrack bookkeeping. DNS riding on the Service datapath is not a special case; it's the same machinery, just answering port 53.
  5. CoreDNS runs the query through its plugin chain, in the order the Corefile lists them. The default chain is roughly errors → health → ready → kubernetes cluster.local → prometheus → forward . /etc/resolv.conf → cache → loop → reload → loadbalance. The kubernetes plugin is configured as authoritative for the cluster.local zone: any query whose name ends in that suffix is its to answer, and it answers by looking up Services, EndpointSlices, and (if pods insecure is set) pod IPs directly from the API server — the same watch-based pattern as every controller in this book. If the plugin doesn't recognise the object, it returns a real, authoritative NXDOMAIN. It does not fall through to forward for names inside its own zone.
  6. A query that doesn't end in cluster.local at all skips the kubernetes plugin entirely and reaches forward, which relays it to whatever upstream resolver the node itself uses (typically inherited from the node's own /etc/resolv.conf — your VPC's resolver, or a corporate DNS server). That's a real network call, with real recursive-resolution latency, and it's the only step in the whole cascade that actually leaves the cluster's DNS boundary.
  7. The cache plugin sits across all of this and remembers both positive answers and negative ones (NXDOMAIN), each for a bounded TTL. A second identical failed search-suffix attempt doesn't repeat the kubernetes plugin's lookup work — it's served straight from CoreDNS's own cache — but it's still a full network round trip from the pod to get there, unless something is caching even closer to the pod.
So what does ndots really cost?

For a short external name like api.stripe.com (2 dots, under the threshold), the resolver tries three suffixed forms before the real one — api.stripe.com.default.svc.cluster.local, ...svc.cluster.local, ...cluster.local — and all three still end in cluster.local, so CoreDNS's kubernetes plugin fails them locally, fast, with no upstream trip. Only the fourth attempt, the bare name with a trailing dot, actually reaches forward and the real internet. The tax isn't "four internet lookups" — it's three extra hairpins through the Service datapath and three extra lookups of CoreDNS's own CPU, on every cold lookup, for every pod that ever calls an external host by a short name. At scale, across thousands of pods calling dozens of external APIs, that's still real load and real latency; it's just not the exact shape most explanations claim.

Think first: a pod calls an external API using its fully-qualified name with a trailing dot — api.stripe.com. — instead of api.stripe.com. What changes?

A trailing dot tells the resolver "this is already absolute" and skips the search list entirely, regardless of ndots or how few dots the name has. So api.stripe.com. goes straight to CoreDNS as a single query, misses the cluster.local suffix immediately, falls through to forward, and resolves in one round trip instead of four. This is a real, standard mitigation for the ndots problem — some organisations configure their SDKs or base images to append the trailing dot on known-external hostnames — but it only helps for names you control in code you can change; it does nothing for third-party libraries that build hostnames internally, which is most of them.

ComponentsThe pieces and what each owns

  • The kubelet's DNS config injection. Owns writing each pod's /etc/resolv.conf based on its dnsPolicy (ClusterFirst by default; Default inherits the node's own resolv.conf; None hands full control to dnsConfig; ClusterFirstWithHostNet for host-networked pods that still want cluster DNS).
  • The kube-dns Service. An ordinary ClusterIP Service in front of the CoreDNS Deployment. Its own ClusterIP is what every pod's nameserver line points at.
  • CoreDNS itself. A Deployment of stateless, horizontally-scalable pods running the Corefile you (or your distribution) configured, stored as a ConfigMap. It answers over UDP and TCP on port 53.
  • The kubernetes plugin. Owns everything authoritative about cluster.local: Service A records pointing at ClusterIPs, headless-Service A records pointing directly at ready pod IPs, and (optionally) per-pod A records under pod.cluster.local.
  • The forward plugin. Owns everything that isn't cluster.local — it's a plain recursive-DNS relay to whatever upstream the node itself trusts.
  • The cache plugin. Owns short-term memory for both answers and failures, bounded by TTL, sitting between the other plugins and the wire.
  • NodeLocal DNSCache. An optional DaemonSet that runs a caching agent on every node, bound to a link-local address (commonly 169.254.20.10), and rewrites pods' nameserver to point at it instead of the central Service — moving the cache physically onto the same node as the pod asking.

Data flowFollowing two lookups from the same pod

A pod in namespace default runs curl http://api, then a moment later calls out to a payment provider at api.stripe.com. Trace both.

  1. For api: 0 dots, under ndots:5, search list applies. First suffix: api.default.svc.cluster.local. That's a real Service in this namespace, so CoreDNS's kubernetes plugin answers immediately with the ClusterIP. One query, one answer, and the rest of the request follows Chapter 43's Service datapath exactly.
  2. For api.stripe.com: 2 dots, still under 5, search list applies again. api.stripe.com.default.svc.cluster.local — ends in cluster.local, kubernetes plugin claims it, finds no such object, answers NXDOMAIN, locally, fast.
  3. api.stripe.com.svc.cluster.local — same story, same fast local NXDOMAIN.
  4. api.stripe.com.cluster.local — same story again. Three failed round trips down, each one a real hop from the pod, through kube-proxy's DNAT, into a CoreDNS pod, and back — just never past CoreDNS.
  5. The search list is exhausted, so the resolver finally tries api.stripe.com. as absolute. It doesn't end in cluster.local, so the kubernetes plugin doesn't touch it; it falls through to forward, which relays it to the node's real upstream resolver, which recurses out to the actual internet and returns Stripe's IP. This one query pays real, external latency — the other three didn't, but they weren't free either.

Lab 1Build — read a real pod's resolv.conf and resolve a ServiceBuild

Deploy a Service, then look at exactly what the kubelet wrote into a client pod's DNS config before asking it to resolve anything.

bash
kubectl create deployment api --image=hashicorp/http-echo -- /http-echo -listen=:8080 -text=hi
kubectl expose deployment api --port=8080
kubectl run c --image=nicolaka/netshoot --command -- sleep infinity
kubectl wait --for=condition=Ready pod/c --timeout=60s

kubectl exec c -- cat /etc/resolv.conf
kubectl exec c -- dig +short api.default.svc.cluster.local
Outputnameserver 10.96.0.10 search default.svc.cluster.local svc.cluster.local cluster.local options ndots:5 10.96.x.x

That's the whole configuration in three lines, and it just resolved a fully-qualified in-cluster name in one query. Now try the bare name people actually type in code:

bash
kubectl exec c -- dig +search api A
Output;; QUESTION SECTION: ;api.default.svc.cluster.local. IN A ;; ANSWER SECTION: api.default.svc.cluster.local. 30 IN A 10.96.x.x

dig +search applies the same search-list logic the C library would. The bare word api became api.default.svc.cluster.local on the very first attempt — exactly the "one query" case the search order is built around.

Lab 2Understand — watch the ndots cascade land entirely inside the clusterUnderstand

Now the query that matters: an external-looking name with too few dots. Capture on the CoreDNS pod itself so you can see exactly which queries it answers locally and which one it forwards.

bash
COREDNS_POD=$(kubectl -n kube-system get pods -l k8s-app=kube-dns -o jsonpath='{.items[0].metadata.name}')
kubectl -n kube-system exec "$COREDNS_POD" -- sh -c 'command -v tcpdump' || \
  kubectl -n kube-system debug -it "$COREDNS_POD" --image=nicolaka/netshoot -- \
    tcpdump -ni any -c8 port 53 &
sleep 1
kubectl exec c -- dig +search api.github.com A +time=2
Output (captured on the CoreDNS pod)A? api.github.com.default.svc.cluster.local. → NXDOMAIN (kubernetes plugin, local) A? api.github.com.svc.cluster.local. → NXDOMAIN (kubernetes plugin, local) A? api.github.com.cluster.local. → NXDOMAIN (kubernetes plugin, local) A? api.github.com. → NOERROR (forwarded upstream, real answer)

Four queries reach CoreDNS; only the last one leaves it. Check the CoreDNS logs (with the log plugin enabled, or via kubectl -n kube-system logs if verbose logging is on) and you'll see the same pattern from the other side — three quick authoritative NXDOMAINs, one real forward. That's the nuance from this chapter's opening recall, confirmed on the wire.

Think first: a service that calls a dozen different external APIs by short name, from thousands of pods, moves to Kubernetes. CPU on CoreDNS climbs sharply, but the actual outbound API calls aren't noticeably slower. Does that match the ndots story?

Yes, and it's the more common real-world shape than "everything got slower." The three wasted attempts per lookup don't add much wall-clock latency to any single request — they're fast, local NXDOMAINs — but they multiply the total query volume CoreDNS has to process by roughly 4x for every short external name. Across thousands of pods doing this constantly, that shows up first as CoreDNS CPU and request-rate metrics climbing, and only later (if CoreDNS starts falling behind) as visible latency. This is exactly why "reduce DNS query volume" and "reduce DNS latency" are sometimes two different investigations with the same root cause.

Lab 3Break — take down CoreDNS and watch what "breaks" and what doesn'tBreak

Scale CoreDNS to zero. Nothing about the pod network, Services, or NetworkPolicy changes — only names stop resolving. Confirm existing connections and IP-based traffic keep working while name-based traffic doesn't.

bash
API_IP=$(kubectl get svc api -o jsonpath='{.spec.clusterIP}')
kubectl exec c -- curl -s -m3 "http://$API_IP:8080"     # by IP — works

kubectl -n kube-system scale deployment coredns --replicas=0
sleep 3
kubectl exec c -- curl -s -m3 "http://$API_IP:8080" || echo "still fine by IP"
kubectl exec c -- curl -s -m3 http://api:8080 || echo "FAILS by name"
Outputhi still fine by IP curl: (6) Could not resolve host: api FAILS by name

Every existing IP-based path is unaffected — this isn't a Service, routing, or policy failure. Before restoring CoreDNS, think about the blast radius: what in a real cluster resolves names constantly, even for things that never look like "DNS traffic" to a human watching dashboards?

Reveal the blast radius

Almost everything, because almost nothing calls anything by raw IP. Every Service call your app makes by name, every external API call, health checks that curl a hostname, sidecars discovering peers by name, even the kubelet's own occasional lookups — all of it stalls or fails the instant CoreDNS is unreachable, which is why a CoreDNS outage reads as "the entire cluster is broken" even though pod networking, Services, and NetworkPolicy are all perfectly healthy. This is why CoreDNS deserves real replica counts, a PodDisruptionBudget, and anti-affinity so a single node failure can't take out every replica at once — it's a single point of failure sized like the whole cluster's blast radius. Restore it: kubectl -n kube-system scale deployment coredns --replicas=2.

Lab 4Troubleshoot — the intermittent DNS timeout that isn't CoreDNS's faultTroubleshoot

A different, nastier symptom: DNS mostly works, but roughly one lookup in a few hundred takes exactly 5 seconds before succeeding or failing, and it happens on Alpine-based images far more than on Debian-based ones. CoreDNS's own metrics show it's healthy and not overloaded. Investigate before revealing.

bash
# Loop a lookup fast enough to make a rare race show up:
kubectl run alpine-c --image=alpine:3.20 --command -- sleep infinity
kubectl wait --for=condition=Ready pod/alpine-c --timeout=60s
kubectl exec alpine-c -- sh -c 'apk add --no-cache bind-tools >/dev/null; for i in $(seq 1 200); do time getent hosts api.default.svc.cluster.local >/dev/null; done 2>&1 | grep real' | sort | uniq -c | tail -5

On a busy enough cluster you'll occasionally see one iteration report something close to 5 seconds among hundreds that report milliseconds. Musl's resolver, as Chapter 15 covered, fires its A and AAAA queries close together rather than one after the other — what does that have to do with an occasional multi-second stall, specifically in a cluster and not on a plain host?

Reveal the mechanism

It's a kernel-level race in conntrack, not a CoreDNS problem at all. UDP has no connection state of its own, so when two DNS queries from the same pod arrive at the node's conntrack table at nearly the same instant — which is exactly what happens when a resolver fires A and AAAA back to back — the kernel has to create two new conntrack entries for what looks, for a brief window, like the same flow. Under load, that entry-creation can race: one of the two packets loses and gets dropped silently, with no error returned to the pod. Since UDP gives the resolver no signal that a packet vanished, it just waits for its own internal timeout — commonly 5 seconds — before retrying. CoreDNS never sees the dropped query at all, which is exactly why its own metrics look perfectly healthy throughout.

This is precisely the failure NodeLocal DNSCache exists to remove: it moves the resolver's target onto the same node, and its fallback path to the real cluster DNS Service runs over TCP, which conntrack handles without this race, instead of UDP. It also means most queries never touch the DNAT path at all, which is a second, separate latency win layered on top of the race fix. The reflex: intermittent, low-frequency, exactly-one-timeout-duration DNS stalls that don't correlate with CoreDNS load are a conntrack-race smell, not a CoreDNS capacity problem — don't scale CoreDNS to fix this; deploy NodeLocal DNSCache.

Lab 5Production challenge — deploy NodeLocal DNSCache and prove it changed the pathSenior challenge

Design and verify the fix from Lab 4, not just describe it. You need a DaemonSet bound to a link-local IP, and pods that actually use it. Reason through what has to change before opening the walkthrough.

Reveal the deployment and the verification

Install the upstream manifest (templated with your cluster's real values — the kube-dns ClusterIP and the cluster domain), which runs a DaemonSet listening on 169.254.20.10:53 on every node's host network, and reconfigures the kubelet (via --cluster-dns or a per-node config) so new pods get that address as their nameserver instead of the central Service:

bash
kubectl -n kube-system get pods -l k8s-app=node-local-dns -o wide   # one per node, hostNetwork: true
kubectl run fresh --image=nicolaka/netshoot --command -- sleep infinity
kubectl wait --for=condition=Ready pod/fresh --timeout=60s
kubectl exec fresh -- cat /etc/resolv.conf
Outputnameserver 169.254.20.10 search default.svc.cluster.local svc.cluster.local cluster.local options ndots:5

The nameserver changed; nothing else about the search list or ndots did — this is purely a datapath change, not a resolution-logic one. Confirm the cache is actually local by hammering the same lookup and checking that repeat queries never leave the node:

bash
kubectl exec fresh -- sh -c 'for i in $(seq 1 5); do dig +short api.default.svc.cluster.local; done'
kubectl -n kube-system logs -l k8s-app=node-local-dns --tail=20 | grep -c cache_hit  # if metrics/logging enabled

The senior habit this reinforces: NodeLocal DNSCache is a datapath optimisation, not a change to DNS semantics — ndots, the search list, and the kubernetes/forward split all behave identically before and after. What changes is where the first hop lands and what protocol a cache miss uses to fall back to the real Service, which is exactly the pair of things (an extra network+DNAT hop, and a UDP conntrack race) that were costing you latency and the occasional 5-second stall.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · intermittent, exactly-5-second DNS stalls

Symptom: occasional slow requests whose latency histogram shows a sharp spike right around a resolver timeout value; CoreDNS metrics look calm throughout. First cut: is the workload UDP-heavy on DNS (default), and does the stall rate track query volume rather than CoreDNS CPU? Confirm: the failure is invisible to CoreDNS itself — it's dropped in conntrack before ever arriving. Cause is usually: the UDP conntrack insertion race on near-simultaneous A/AAAA queries. Fix: deploy NodeLocal DNSCache, which falls back to TCP and removes the race, and incidentally removes the Service hairpin too.

Incident pattern · cluster-wide outage that "isn't networking"

Symptom: everything using a hostname fails at once — Service calls, external API calls, health checks — while direct IP traffic keeps working and Services/Endpoints/NetworkPolicy all look untouched. First cut: kubectl -n kube-system get pods -l k8s-app=kube-dns — are they up? Confirm: a name lookup fails while the same call by raw IP succeeds. Cause is usually: CoreDNS crash-looping, OOM-killed, or scaled down, often with too few replicas or no anti-affinity so a single node event took all of them at once.

Incident pattern · unexplained CoreDNS CPU and query-rate growth after a migration

Symptom: CoreDNS CPU and QPS climb steadily after moving workloads onto the cluster, with no obvious increase in real traffic. First cut: sample CoreDNS query logs for NXDOMAIN answers ending in cluster.local that clearly aren't cluster names — github.com.default.svc.cluster.local and similar. Confirm: the ratio of NXDOMAIN-under-cluster.local to real answers is roughly 3:1 for a given external name. Cause is usually: the ndots-5 default combined with heavy use of short external hostnames, multiplying query volume roughly fourfold per cold external lookup. Fix: use fully-qualified names with a trailing dot for known-external hosts where the code allows it, and give CoreDNS the replica count and cache size to absorb the rest.

Production · security · performanceWhat matters in production

Treat CoreDNS's availability like a cluster primitive, not an app. Run more than one replica, spread across nodes with anti-affinity or topology spread constraints, and set a PodDisruptionBudget so a voluntary drain can't take every replica down together. Every Service call in the cluster depends on it being reachable, so its blast radius is the whole cluster's, not just "the DNS pods."

Reach for NodeLocal DNSCache once you have real scale. It fixes the conntrack race, cuts the average lookup's network hops, and takes load off central CoreDNS by absorbing repeat queries at the node. It's not free — it's one more DaemonSet to run and watch — so it earns its place once query volume or the occasional 5-second stall is actually showing up in your metrics, not as a default for every cluster on day one.

Tune the cache and watch the right signals. CoreDNS's cache plugin size and TTL floor trade memory for hit rate; too small a cache under high query volume just pushes load back onto the kubernetes/forward plugins. Watch CoreDNS's own request-duration and error-rate metrics, and specifically the NXDOMAIN rate for names ending in cluster.local that clearly aren't real cluster objects — a high rate there is the ndots tax showing up in your own numbers. Common mistakes: assuming a DNS outage is a networking or NetworkPolicy problem because "nothing else changed"; scaling CoreDNS to fix a conntrack-race symptom that scaling can't touch; running CoreDNS at a single replica with no disruption budget; and never noticing how much of the query volume is self-inflicted by short external hostnames.

System-design connectionWhere this reaches into architecture

Service discovery by name, not by address, is the same idea every architecture eventually needs — Kubernetes just makes it a first-class, cluster-wide default instead of something you bolt on with a service registry. The layering here is worth carrying forward: an authoritative, narrowly-scoped resolver (the kubernetes plugin) for names it truly owns, a forwarding relay for everything else, and a cache in between — that's the same shape as any DNS split-horizon or service-mesh discovery system you'll design later. The conntrack-race lesson generalises too: any design that fires two independent, near-simultaneous UDP requests through the same NAT/connection-tracking boundary is exposed to the same class of silent drop, whether that boundary is kube-proxy or a cloud NAT gateway. And the DNS-as-single-point-of-failure lesson connects straight to Part VIII's reliability material: a dependency that everything else calls transitively, constantly, and invisibly deserves availability engineering proportional to the whole system it underpins, not to how "small" the DNS component looks on an architecture diagram.

InterviewInterview questions & answers

Answer each in your head before opening it.

30-secHow does a pod resolve a Service name like api?

The kubelet writes the pod's /etc/resolv.conf pointing at the kube-dns Service's ClusterIP, with a search list of <namespace>.svc.cluster.local, svc.cluster.local, and cluster.local, plus ndots:5. Because api has zero dots, the resolver appends the first search suffix, sending api.<namespace>.svc.cluster.local to CoreDNS, which is authoritative for that zone via its kubernetes plugin and answers with the Service's ClusterIP directly from watching the API server. One query, one answer, for the common case.

2-minWalk me through what actually happens when a pod looks up a short external hostname like api.stripe.com.

api.stripe.com has two dots, still under the cluster's ndots:5 threshold, so the resolver applies the search list before trying it as-is. It tries api.stripe.com.default.svc.cluster.local first — that still ends in cluster.local, so CoreDNS's kubernetes plugin claims the query, finds no matching object, and returns an authoritative NXDOMAIN without forwarding anywhere. The same happens for svc.cluster.local and cluster.local as suffixes — two more fast, local failures. Only once the search list is exhausted does the resolver try the name absolutely, as api.stripe.com.; that doesn't match the cluster.local zone, so it falls through to CoreDNS's forward plugin, which relays it to the node's real upstream resolver and gets a genuine answer from the internet. So the cost is four total queries, but only the last one leaves the cluster — the other three are local, fast NXDOMAINs, though they still consume real hops across the Service datapath and real CoreDNS CPU. This is why the practical fix is a fully-qualified name with a trailing dot where you control the code, and enough CoreDNS capacity where you don't.

DeepWhat is the conntrack race that NodeLocal DNSCache fixes, and why doesn't scaling CoreDNS help?

DNS resolvers commonly send an A query and an AAAA query for the same name in quick succession — musl, notably, fires them close together. Both are UDP, and UDP has no connection state, so when the node's conntrack subsystem has to create new tracking entries for two packets that look like the same flow arriving almost simultaneously, that entry creation can race under load; one packet's conntrack entry loses the race and the packet is silently dropped before it's ever forwarded. The pod's resolver never gets a response, has no way to know the packet vanished versus is just slow, and falls back to its own internal timeout — commonly 5 seconds — before retrying. Because the dropped packet never reaches a CoreDNS pod at all, CoreDNS's own metrics stay clean throughout, which is exactly why this looks like a mysterious client-side stall rather than a server problem. Scaling CoreDNS adds more pods to answer queries that do arrive; it does nothing about a packet that gets dropped in the node's own conntrack table before it ever gets that far. NodeLocal DNSCache fixes it structurally: most queries are answered from a cache on the same node with no DNAT involved at all, and the fallback path to the real Service on a cache miss uses TCP, which doesn't have this race.

ScenarioAfter a big migration, every service that calls external APIs is slightly slower, and CoreDNS's CPU has tripled. Nothing else changed. What do you check?

My first suspect is the ndots cascade multiplying query volume, because "slightly slower external calls plus much higher CoreDNS CPU, nothing else changed" is close to a textbook signature. I'd sample CoreDNS's query logs (or turn on the log plugin briefly) looking for a high rate of NXDOMAIN answers for names that end in cluster.local but clearly aren't cluster objects — something like stripe.com.default.svc.cluster.local. If that ratio is roughly three failed local lookups per one real external hostname resolved, that confirms it: every short external hostname the migrated workloads call is costing four queries instead of one, and the CPU is going into the kubernetes plugin repeatedly failing to find those as cluster objects. From there the fix is twofold — get the migrated code to use fully-qualified trailing-dot hostnames for known-external calls where practical, and size CoreDNS's replica count and cache appropriately for the new baseline query volume rather than treating the higher number as an anomaly to chase away.

Follow-upIs NodeLocal DNSCache always worth running?

Not always — it's a scale-driven optimisation, not a default every cluster needs from day one. It earns its place once you have enough query volume that central CoreDNS load or the Service-datapath hop actually matters, or once you've seen the specific symptom of intermittent multi-second DNS stalls that point at the UDP conntrack race. On a small cluster with light DNS traffic, the extra DaemonSet is one more thing to run, monitor, and reason about for a benefit you won't notice. I'd introduce it reactively — after seeing CoreDNS CPU climb, or after diagnosing a conntrack-race stall like the one in this chapter's labs — rather than proactively bolting it onto every cluster regardless of size.

RetainQuick revision

Every Service name a pod resolves goes through CoreDNS, itself just a Deployment behind a Service, reached via the same DNAT datapath as any other Service call. The kubelet writes each pod's /etc/resolv.conf with a search list (<ns>.svc.cluster.local, svc.cluster.local, cluster.local) and ndots:5, which makes short in-cluster names resolve in one query but makes short external names pay a search-list cascade first. That cascade isn't as costly as it looks: every suffixed attempt still ends in cluster.local, so CoreDNS's kubernetes plugin fails them locally and fast — only the final, un-suffixed attempt actually forwards upstream via the forward plugin. The cache plugin remembers both answers and NXDOMAINs. A separate, unrelated failure mode — the UDP conntrack race on near-simultaneous A/AAAA queries — causes intermittent multi-second stalls that CoreDNS's own metrics never show, because the packet never arrives; NodeLocal DNSCache fixes it by caching on-node and falling back over TCP. CoreDNS being down breaks nearly everything that isn't already talking by raw IP, which makes its own availability a cluster-wide concern.

The 10 things to remember

  1. CoreDNS is an ordinary Deployment behind an ordinary Service (kube-dns); DNS rides the same datapath as any Service call.
  2. The kubelet writes each pod's resolv.conf: nameserver = cluster DNS ClusterIP, a 3-entry search list, ndots:5.
  3. ndots:5 means names with fewer than 5 dots try the search list first — short in-cluster names hit on the first try.
  4. Short external names (2–4 dots) pay a search-list cascade, but every suffixed attempt still ends in cluster.local.
  5. The kubernetes plugin answers cluster.local queries authoritatively and fails them locally — no upstream trip for those.
  6. Only the final, absolute attempt (no cluster suffix) reaches the forward plugin and actually leaves the cluster.
  7. The cache plugin caches negatives too, but repeat queries still cost a network hop unless cached closer to the pod.
  8. The UDP conntrack race (near-simultaneous A/AAAA) causes silent packet drops and resolver-timeout-length stalls invisible to CoreDNS.
  9. NodeLocal DNSCache fixes the race and cuts hops by caching on-node and falling back to the Service over TCP, not UDP.
  10. CoreDNS down breaks nearly every name-based call cluster-wide while IP traffic keeps working — run it for that blast radius.
