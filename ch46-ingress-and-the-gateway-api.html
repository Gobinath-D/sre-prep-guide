Ingress and the Gateway API

A NodePort gets a packet into the cluster. It has no idea what to do with a Host header, a URL path, or a certificate. Something has to read the request itself and decide where it actually goes — that's an Ingress controller, and the Gateway API is the rewrite that fixes the parts of Ingress that never quite worked cleanly.

Start: Beginner→→→End: Staff-level ~50 min read · kind + ingress-nginx lab

By the end of this chapter you can

  • Explain what an Ingress object actually configures, and who — not what — turns it into working routing.
  • Route two different paths and two different hosts to two different backends, and add TLS to one.
  • Say precisely what GatewayClass, Gateway, and HTTPRoute each own, and why that split exists.
  • Explain what cert-manager automates, including the HTTP-01 chicken-and-egg problem it has to solve.
  • Diagnose a 404 versus a 503 from an ingress, and tell a routing mistake from a backend mistake.

Why this exists · the problemNodePort gets you in the door; it can't read the request

Chapter 44 got a packet from the internet to a node and, from there, to a pod. But that mechanism is deliberately dumb — it matches a port number and forwards. It has no idea that shop.example.com/api/cart and shop.example.com/checkout should go to two completely different backends, or that images.example.com is a different app entirely from shop.example.com, even though both might arrive at the exact same external IP and the exact same port, 443.

Reading that kind of detail — the Host header, the URL path, the TLS handshake's SNI — means terminating the connection and actually looking at the HTTP request. That's layer 7, and it needs a real piece of software in the path: an Ingress controller. You describe the routing you want declaratively, as a Kubernetes object, and the controller's job is to turn that description into a running reverse proxy that does exactly what you asked. Ingress was the first API for this description, and it shipped with real limitations. The Gateway API is the newer, more expressive API meant to replace it — not a competing product, a successor.

Key point

Neither Ingress nor the Gateway API routes a single packet by itself. Both are just declarative descriptions. A controller — ingress-nginx, Envoy-based, a cloud's own implementation — has to be running, watching those objects, and reconfiguring a real proxy. No controller, no routing, no matter how correct your YAML is.

Mental model · analogyThe mental model: one shared reception desk in a multi-tenant building

Real-world analogy

Picture an office building with one shared reception desk serving many tenant companies. Visitors arrive with an address that includes the company name and sometimes a specific department. The receptionist reads that, matches it against a set of instructions, and points the visitor to the right floor. That receptionist, doing real work on every arrival, is the Ingress controller. The instructions taped to the desk are the Ingress object.

The trouble with early building conventions was that any tenant could tape up their own instruction slip, in whatever format they liked, with no shared numbering for which slip takes priority when two overlap. Two companies' notes conflict, and which one the receptionist actually follows depends on which specific receptionist is on shift — different buildings' staff resolve ambiguity differently. That's Ingress: one shared object, annotation-driven extensions bolted on per vendor, and priority between overlapping rules left to each controller's own judgment.

The Gateway API is the building switching to a proper front-desk system with clear job separation. Building management configures the desk itself once — which doors it watches, which ports, which credentials it checks visitors against (TLS). That's the Gateway. Each tenant company then gets their own clearly-scoped page in the ledger — "anyone asking for us, on this path, goes to our floor" — that only affects their own routing and can't silently clobber another tenant's page. That's an HTTPRoute. And the whole desk-configuration format itself — what a valid entry even looks like — is set once by whoever manufactures front-desk systems for this kind of building. That's the GatewayClass.

ArchitectureL7 routing to backends

An Ingress controller is, physically, just another workload: a Deployment of proxy pods, sitting behind a Service that's exposed to the outside world exactly the way Chapter 44 described — usually type: LoadBalancer or a NodePort behind your own load balancer. External traffic reaches those proxy pods first, before it ever reaches your application.

The controller does its own load balancing across backend pods because it already has to track EndpointSlices to know where to send traffic — routing through the backend's ClusterIP and paying kube-proxy's DNAT a second time would add a hop for no benefit. This is worth remembering: an Ingress controller behaves like the ip-target-type load balancer from Chapter 52, not like a plain Service client.

Think first: two separate Ingress objects, created by two different teams, both define a rule for the exact same host and path, pointing at different backends. What happens?

It's implementation-defined, and that's the actual problem, not a quirk of one controller. The core Ingress API has no formal precedence rule for resolving conflicts across separate objects — the docs acknowledge that behaviour can differ between controllers, and in practice most controllers pick one deterministically (often by creation time, or alphabetically) but won't warn you about the conflict. You end up with routing that "happens to work" today and can flip to the other team's backend after a controller upgrade, a Helm chart change, or simply re-applying manifests in a different order. This exact ambiguity is one of the concrete reasons the Gateway API defines an explicit, conformance-tested matching precedence instead of leaving it to each vendor.

Internal workingFrom YAML to a working reverse proxy

  1. You deploy an Ingress controller — a Deployment of proxy pods (ingress-nginx wraps nginx; others wrap Envoy or their own engine) plus a Service exposing it externally, using the exact NodePort/LoadBalancer mechanism from Chapter 44. Nothing routes yet; the controller is just running.
  2. The controller watches the API server for Ingress objects matching its IngressClass (or, historically, the legacy kubernetes.io/ingress.class annotation — deprecated in favour of the dedicated IngressClass resource and spec.ingressClassName), and for the EndpointSlices of every Service those Ingress objects reference. This is the same watch-and-reconcile pattern as every controller in this book.
  3. It compiles what it sees into real dataplane configuration. ingress-nginx literally generates an nginx.conf and triggers a reload (or, for endpoint-only changes, patches upstreams dynamically without a full reload); Envoy-based controllers push configuration over xDS with no reload at all. Either way, the Ingress object you wrote is now a live, running proxy configuration.
  4. A request arrives and TLS terminates first, if configured. The controller picks which certificate to present based on the TLS handshake's SNI — the hostname the client asked for before any HTTP headers are even visible — which is why the tls.hosts list on an Ingress and the actual Host header need to agree.
  5. The controller matches rules in order of specificity, not declaration order. A pathType: Exact match beats a Prefix match; a longer prefix beats a shorter one. This ordering is well-defined within one Ingress object; it's the cross-object case from the recall above that's genuinely ambiguous.
  6. The matched rule points at a Service, but the controller resolves that straight to pod IPs via the Service's EndpointSlices, and load-balances across them itself — it does not send the request to the Service's ClusterIP and let kube-proxy handle it a second time.
The Gateway API's actual fix

Gateway API doesn't just rename Ingress's fields. It splits one object into three with different owners (GatewayClass, Gateway, HTTPRoute), it standardises rich matching (headers, methods, query parameters, weighted traffic splitting) that Ingress only ever offered through vendor-specific annotations, and — the part this chapter's recall exposed — it defines a strict, conformance-tested precedence order for overlapping matches: exact path matches beat prefix matches, longer prefixes beat shorter ones, and further ties are broken deterministically by rule and object age rather than by whichever controller you happen to run. The goal is the same routing behaviour on every conformant implementation, which Ingress never fully delivered.

Think first: an app team wants to add a new path rule to a Gateway that the platform team owns. Under the Gateway API's role split, whose object do they edit?

Their own HTTPRoute — never the Gateway itself. The app team creates or edits an HTTPRoute in their own namespace with a parentRefs field pointing at the platform team's Gateway, and lists their own hostnames, paths, and backend Services in it. The platform team's Gateway object — its listeners, ports, and TLS configuration — never needs to change for this. That's the entire point of the split: an app team can add, change, or break their own routing without ever touching, or needing permission to touch, the shared front-desk configuration. Contrast that with a shared Ingress object, where adding a rule sometimes means editing the exact same object another team already has rules in.

ComponentsThe pieces and what each owns

  • Ingress (networking.k8s.io/v1) — host/path rules pointing at backend Services, plus a tls block referencing a Secret. Owns intent; does nothing on its own.
  • IngressClass — names which controller should implement a given Ingress, replacing the old class annotation. A cluster can run multiple controllers side by side, each claiming its own class.
  • The Ingress controller — the actual proxy plus its control loop. Owns turning Ingress objects and EndpointSlices into live routing, TLS termination, and (via annotations, since the core API has no field for it) most of the extra behaviour real production traffic needs — rewrites, rate limiting, auth.
  • cert-manager's Certificate, Issuer/ClusterIssuer — declare "I want a valid cert for this host, issued by this authority, kept in this Secret," and cert-manager's controllers own requesting, validating, and renewing it automatically, writing the result into the Secret the Ingress already references.
  • GatewayClass (Gateway API, cluster-scoped) — names which controller implements Gateways of this class, the same role IngressClass plays.
  • Gateway — the shared, infrastructure-owned listener configuration: ports, protocols, hostnames, TLS. Typically owned by a platform team.
  • HTTPRoute (and its siblings GRPCRoute, TCPRoute, TLSRoute for non-HTTP traffic) — the app-team-owned routing rules: matches on path, header, method, or query, weighted backendRefs for traffic splitting, referencing a parent Gateway.
  • ReferenceGrant — the explicit permission slip that lets an HTTPRoute in one namespace point at a Service in another; without it, cross-namespace backend references are refused, closing a gap Ingress never guarded.

Data flowFollowing one HTTPS request end to end

A browser resolves shop.example.com to the Ingress controller's external IP — via Route 53 or whatever DNS you run (Chapter 53) — and connects on 443. The TLS handshake's SNI says shop.example.com; the controller picks the certificate cert-manager provisioned for that host and terminates TLS. It reads the now-decrypted request: GET /api/cart, Host shop.example.com. Among the Ingress rules it's watching, one matches this exact host with path prefix /api, pointing at Service tg-api. The controller resolves that Service's current EndpointSlice, picks one of the ready pod IPs, and forwards the request there directly — no ClusterIP, no kube-proxy DNAT for this hop. The pod answers; the controller streams the response back over the same TLS connection it terminated. If that pod had zero ready endpoints, the controller would have nothing to forward to and would answer with its own 503 — the same "no healthy backend" shape you've already seen at the Service layer in Chapter 43, one layer up.

Lab 1Build — route two paths to two backendsBuild

Deploy two tiny apps and one Ingress that splits traffic between them by path.

bash
for name in a b; do
  kubectl create deployment echo-$name --image=hashicorp/http-echo -- /http-echo -listen=:8080 -text="echo-$name"
  kubectl expose deployment echo-$name --port=8080
done

kubectl apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: split, annotations: { nginx.ingress.kubernetes.io/rewrite-target: /} }
spec:
  ingressClassName: nginx
  rules:
    - http:
        paths:
          - { path: /a, pathType: Prefix, backend: { service: { name: echo-a, port: { number: 8080 } } } }
          - { path: /b, pathType: Prefix, backend: { service: { name: echo-b, port: { number: 8080 } } } }
EOF
kubectl wait --for=condition=ready pod -l app.kubernetes.io/component=controller -n ingress-nginx --timeout=60s
curl -s http://localhost/a
curl -s http://localhost/b
Outputecho-a echo-b

One controller, one external port, two completely different backends selected purely by URL path. Nothing about ClusterIPs or NodePorts changed — this whole split happened inside the controller's own L7 logic.

Lab 2Understand — route by host, and read the compiled configUnderstand

Add host-based routing, then look at what the controller actually generated from your YAML — the same nginx.conf the analogy's receptionist would be reading off.

bash
kubectl apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: by-host }
spec:
  ingressClassName: nginx
  rules:
    - host: a.local
      http: { paths: [{ path: /, pathType: Prefix, backend: { service: { name: echo-a, port: { number: 8080 } } } }] }
    - host: b.local
      http: { paths: [{ path: /, pathType: Prefix, backend: { service: { name: echo-b, port: { number: 8080 } } } }] }
EOF
curl -s -H 'Host: a.local' http://localhost/
curl -s -H 'Host: b.local' http://localhost/

CTRL_POD=$(kubectl -n ingress-nginx get pods -l app.kubernetes.io/component=controller -o jsonpath='{.items[0].metadata.name}')
kubectl -n ingress-nginx exec "$CTRL_POD" -- grep -A2 'server_name a.local' /etc/nginx/nginx.conf
Outputecho-a echo-b server_name a.local ; listen 80 ; listen 443 ssl http2 ;

The same request, the same port, the same IP — routed entirely by the Host header, and the exact server_name block sitting in the controller's real config is right there for you to read. Ingress is a description; this is the thing that actually decides.

Now add real TLS, entirely locally — no ACME issuer needed to prove the mechanism. Generate a self-signed certificate for a.local, store it as the Secret type Ingress expects, and reference it:

bash
openssl req -x509 -nodes -days 30 -newkey rsa:2048 \
  -keyout a-local.key -out a-local.crt -subj "/CN=a.local" >/dev/null 2>&1
kubectl create secret tls a-local-tls --cert=a-local.crt --key=a-local.key

kubectl patch ingress by-host --type=merge -p '{"spec":{"tls":[{"hosts":["a.local"],"secretName":"a-local-tls"}]}}'
curl -vk --resolve a.local:443:127.0.0.1 https://a.local/ 2>&1 | grep -E 'subject|HTTP/'
Output* subject: CN=a.local < HTTP/2 200

That's a genuinely working TLS listener — the certificate presented now actually matches the host, sourced from a Secret the controller picked up with no reload command from you. This is the working baseline the next lab is about to quietly break.

Lab 3Break — a TLS secret that doesn't existBreak

Working TLS, one small change away from broken: point the same Ingress at a Secret name that doesn't exist — a typo any templating mistake could produce — and see exactly what happens to the connection. Not an outright failure, which is what makes this mistake easy to miss.

bash
kubectl patch ingress by-host --type=merge -p '{"spec":{"tls":[{"hosts":["a.local"],"secretName":"a-local-tls-typo"}]}}'
curl -vk --resolve a.local:443:127.0.0.1 https://a.local/ 2>&1 | grep -E 'subject|SSL certificate|HTTP/'
Output* SSL certificate problem: self-signed certificate * subject: CN=Kubernetes Ingress Controller Fake Certificate < HTTP/2 200

The connection succeeds, the app answers 200 — but the certificate presented is the controller's own built-in placeholder, not anything for a.local. A real browser would show a hard certificate warning; a strict client (most API clients, by default) would refuse the connection outright with a certificate verification error, not a helpful message about a missing Secret. Before revealing: why does the controller serve a fake cert instead of just failing the whole route?

Reveal the reasoning

Because failing the TLS handshake entirely would take down every other host this same controller serves on the same port — TLS termination happens before the controller even knows which Ingress rule a request is headed for, so it has to present some certificate the instant a client connects. When the referenced Secret is missing, ingress-nginx falls back to a built-in self-signed default certificate for that listener rather than refusing the connection. The failure is real, it's just silent and one layer removed from where you're looking: kubectl describe ingress by-host and the controller's own logs will show a warning about the missing Secret, but curl without -k, or any TLS-verifying client, will simply report a certificate error with no obvious link back to a typo'd secretName. Fix it: create the actual Secret cert-manager or you would normally provision, matching the name exactly.

Lab 4Troubleshoot — 404 from an ingress that looks completely correctTroubleshoot

A very common real ticket: "the Ingress is applied, the pods are healthy, but I get a 404." Reproduce it by simply forgetting the Host header a host-based rule requires.

bash
curl -s -o /dev/null -w '%{http_code}\n' http://localhost/       # no Host header override at all
kubectl get pods -l app=echo-a                                    # definitely running
Output404 NAME READY STATUS echo-a-5d9c7f6b8d-x2z9k 1/1 Running

The pod is healthy, the Ingress exists, and you still get a 404. Work out why a perfectly healthy backend produces a 404 with no backend ever involved, before opening the answer.

Reveal the cause

Every rule in by-host requires a specific Host header — a.local or b.local — and a plain curl http://localhost/ sends Host: localhost, which matches neither. With no matching host, the controller never reaches a backend at all; it answers from its own built-in default backend, whose entire job is to return 404 for anything nothing else claims. This is the single most common "my Ingress doesn't work" report, and the fix is never in the backend — it's confirming the client is actually sending the Host (or SNI, for HTTPS) the rule expects. The general triage: a 404 from an ingress means no rule matched the request at all; a 503 (Lab 3's territory, one layer deeper) means a rule matched but the backend had nothing healthy to serve it. Those are two different bugs in two different places, and the status code tells you which one you're looking at before you touch a single pod.

kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.1.0/standard-install.yaml
kubectl get crd | grep gateway.networking.k8s.io
Reveal the object split and how to verify it without a full controller installed

The platform team's object — one Gateway, naming the shared listeners:

yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: { name: shop-gw }
spec:
  gatewayClassName: example-controller     # whichever implementation you run
  listeners:
    - { name: http, protocol: HTTP, port: 80 }

Each app team's object — an HTTPRoute that only touches their own routing:

yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: echo-a-route }
spec:
  parentRefs: [{ name: shop-gw }]
  hostnames: ["a.local"]
  rules:
    - backendRefs: [{ name: echo-a, port: 8080 }]
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: echo-b-route }
spec:
  parentRefs: [{ name: shop-gw }]
  hostnames: ["b.local"]
  rules:
    - backendRefs: [{ name: echo-b, port: 8080 }]

Neither HTTPRoute mentions the other, and neither had to touch shop-gw to exist — exactly the isolation the analogy promised. Without an actual Gateway API controller running (installing one — Envoy Gateway, Istio, a cloud-managed implementation — is a real, separate undertaking beyond CRDs alone), these objects won't route live traffic. But Gateway API's richer status subresource lets you verify the configuration is well-formed even with no controller attached, which Ingress never offered:

bash
kubectl apply -f gateway.yaml -f route-a.yaml -f route-b.yaml
kubectl describe httproute echo-a-route | sed -n '/Status:/,$p'
OutputStatus: Parents: Conditions: Type: ResolvedRefs Status: Unknown Reason: Pending # no controller has claimed this GatewayClass yet

That Pending status is itself the lesson: Gateway API objects report their own resolution state as a first-class field, so "is my routing config even valid and attached to something" is a kubectl describe away instead of a guess from behaviour — a real, structural improvement over Ingress that this chapter's earlier labs had no equivalent for.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · 404 from the ingress, backend perfectly healthy

Symptom: a 404 comes back before any backend is ever touched; pods are Running and Ready. First cut: does the request's Host header (or TLS SNI) actually match a rule? Confirm: check what the client is actually sending versus what the Ingress/HTTPRoute rules expect — a missing ingressClassName, a wrong IngressClass, or simply no rule for this host all land here too. Cause is usually: a routing mismatch, not an application problem — the default backend is answering, not your app.

Incident pattern · 503 from the ingress, Ingress rule clearly correct

Symptom: a rule matches, but the response is 503 from the controller itself. First cut: kubectl get endpointslices -l kubernetes.io/service-name=<backend> — is it empty? Confirm: same root cause as a bare Service with no endpoints (Chapter 43), one layer removed — the controller resolved the rule correctly and simply had nothing to forward to. Cause is usually: a failing readiness probe, a selector mismatch, or a scale-to-zero Deployment behind the referenced Service.

Incident pattern · TLS works for the wrong reason, and nobody notices

Symptom: HTTPS "works" (connections succeed) but strict clients fail with certificate errors, or a security scan flags a self-signed certificate on a production hostname. First cut: check the certificate actually presented — openssl s_client -connect host:443 -servername host and read the subject. Confirm: it's the controller's built-in fallback certificate, not the one you expected. Cause is usually: a secretName typo, a Secret in the wrong namespace, or a cert-manager Challenge that never completed — check kubectl get certificate,challenge -A before assuming the Ingress config is wrong.

Production · security · performanceWhat matters in production

Automate certificates, and understand the chicken-and-egg problem in HTTP-01. cert-manager's HTTP-01 challenge proves you control a domain by having Let's Encrypt (or another ACME issuer) fetch a token at a specific path over the real, public internet — which means the domain has to already be publicly reachable on port 80 before you can get a cert for it on 443. A domain that isn't live yet, or one gated by a NetworkPolicy or a firewall that blocks that path, will leave the resulting Challenge stuck pending indefinitely. DNS-01 validation (proving control via a DNS TXT record instead) sidesteps this and is the right choice for internal-only hosts or anything not yet publicly reachable — at the cost of needing your DNS provider's API credentials configured in the Issuer.

Decide your annotation dependency up front. Nearly everything beyond basic host/path routing on Ingress — rate limiting, rewrites, auth, canary weights — is a controller-specific annotation, not a portable field. That's fine as long as you accept you're coupled to that controller; migrating to a different one, or to Gateway API, means translating every annotation by hand. Gateway API pulls the genuinely common cases (traffic splitting, header matching) into the portable core specifically to shrink this exposure.

Watch the controller's own health, not just your app's. The Ingress controller is now a single, shared point every external request passes through — size it, and its own dataplane reload behaviour, for your real traffic. A controller that reloads its full config on every Ingress or Endpoint change can visibly hiccup during a busy rollout; prefer implementations (or configurations) that patch dynamically instead. Common mistakes: assuming the Ingress object itself does the routing; forgetting that TLS SNI has to match what the Host header will say; debugging a 503 by checking the Ingress instead of the backend's endpoints; and running two controllers claiming the same IngressClass with overlapping rules and being surprised by which one wins.

System-design connectionWhere this reaches into architecture

This is the layer where "how does traffic get to my service" stops being purely a networking question and starts being an organisational one — the Gateway API's role split between Gateway (platform-owned) and HTTPRoute (app-owned) is a direct answer to the multi-tenant ownership problem that plagued shared Ingress objects, and it's the same shape you'll reach for anywhere many teams share one edge. On AWS, this whole chapter has a parallel implementation path: the AWS Load Balancer Controller can drive an Ingress straight into an ALB with L7 rules (Chapter 60), or increasingly a Gateway API implementation targeting the same ALB — same concepts, different dataplane. And the controller-reads-objects-and-programs-a-dataplane pattern here is identical in shape to a service mesh's control plane pushing configuration to Envoy sidecars (Chapter 67) — Ingress and Gateway API are, in effect, a mesh's edge-only special case, which is exactly why some meshes implement Gateway API directly instead of inventing their own ingress format.

InterviewInterview questions & answers

Answer each in your head before opening it.

30-secWhat does an Ingress object actually do?

By itself, nothing — it's a declarative description of host/path routing and TLS termination rules. An Ingress controller, a real running proxy watching the API server, turns that description into live routing by compiling it into its own dataplane configuration. The controller also resolves backends straight to pod IPs via EndpointSlices rather than going through the backend Service's ClusterIP, so it's doing its own load balancing, not deferring to kube-proxy.

2-minWhy did the Gateway API replace Ingress, specifically?

Ingress has three real limitations the Gateway API targets directly. First, it's a single object shared by everyone who wants to route into a cluster, with no ownership boundary — any team can add rules to it, and there's no formal precedence for conflicting rules across separate Ingress objects, which different controllers resolve differently. Second, almost anything beyond basic host/path matching — rewrites, rate limiting, weighted traffic splitting, header matching — has to be expressed as controller-specific annotations rather than portable fields, which locks you to one controller's syntax. Third, Ingress has a thin status subresource, so there's little built-in way to see whether a rule is actually valid or attached to anything. Gateway API answers all three: it splits one object into GatewayClass/Gateway/HTTPRoute with different owners and RBAC boundaries, standardises richer matching and traffic splitting in the portable core API, defines a strict conformance-tested precedence order for overlapping matches, and gives every object a rich status subresource reporting its own resolution state.

DeepWalk through exactly what cert-manager automates, and where it can get stuck.

You declare a Certificate naming a host, an Issuer or ClusterIssuer, and a target Secret. cert-manager's controller creates a CertificateRequest, and for an ACME issuer like Let's Encrypt, that spawns an Order and one or more Challenge resources — one per domain being validated. For an HTTP-01 challenge, cert-manager temporarily serves a token at a well-known path on that host and the ACME server fetches it over the real internet to prove domain control; once validated, it issues the certificate and cert-manager writes it into the target Secret, which your Ingress or Gateway already references, so it picks it up with no further action. The stuck case is structural: HTTP-01 validation requires the domain to already be publicly reachable on port 80 at the moment of the challenge, so a domain that isn't live yet, or one behind a NetworkPolicy or firewall blocking that specific path, leaves the Challenge pending forever with no certificate ever issued. DNS-01, which proves control via a TXT record instead of a live HTTP fetch, avoids that dependency entirely and is the right choice for internal or not-yet-public hosts, at the cost of needing DNS provider API access configured into the Issuer.

ScenarioUsers report your site is down; you check and get a 503 directly from the ingress. Walk me through the triage.

A 503 from the ingress itself, as opposed to a 404, tells me a rule matched — so routing configuration isn't the problem, and I don't need to touch the Ingress or HTTPRoute at all. What it means is the controller resolved the rule to a backend Service and found nothing healthy to send the request to. So my next command is checking that Service's EndpointSlices, exactly as I would for a bare Service returning connection errors: are they empty, and if so, why — a failing readiness probe, a label selector that stopped matching after a deploy, or a Deployment that got scaled to zero. If the endpoints do exist and look healthy, I'd widen the check to whether the controller itself can actually reach the pod network — a NetworkPolicy change or a CNI issue on the controller's own node could produce the same symptom from the other direction. Throughout, I'm treating the 503 as a strong signal pointing one layer past the ingress config, not a reason to start editing routing rules.

Follow-upHow does this whole chapter relate to a service mesh's ingress gateway?

They're the same idea at a different scope. A mesh's ingress gateway is itself frequently just an Envoy proxy exposed the Chapter 44 way, configured by a control plane that watches routing objects and pushes configuration to it — the identical watch-compile-serve loop an Ingress controller runs, and increasingly the exact same Gateway API objects, since several service meshes implement Gateway API directly as their ingress configuration surface rather than inventing a separate one. The difference is scope and what happens after the edge: a plain Ingress controller's job ends once it's picked a backend pod, while a mesh's ingress gateway is the front door into a system where every hop afterward also gets mTLS, retries, and traffic policy from the same control plane. Understanding Ingress cold makes a mesh's ingress gateway look like a special case rather than a new concept.

RetainQuick revision

A NodePort or LoadBalancer gets a packet to a node; it takes a real proxy reading the actual request — an Ingress controller — to route by Host header, URL path, or TLS SNI. Ingress (networking.k8s.io/v1) describes that routing declaratively; the controller watching it compiles the description into a live reverse proxy and resolves backends straight to pod IPs via EndpointSlices, skipping kube-proxy. Ingress's real limits — one shared object with no cross-object precedence rule, annotation-dependent extensions, thin status reporting — are what the Gateway API fixes by splitting the config into GatewayClass (which controller), Gateway (platform-owned listeners/TLS), and HTTPRoute (app-owned routing rules), with a formal, conformance-tested matching precedence and a rich status subresource. cert-manager automates certificate issuance through Certificate/Issuer objects and ACME challenges, but HTTP-01 validation needs the domain already publicly reachable — DNS-01 is the fix for anything that isn't. A 404 from the ingress means no rule matched; a 503 means a rule matched but the backend had nothing healthy — different bugs, different places to look.

The 10 things to remember

  1. An Ingress object is a description; an Ingress controller — a real running proxy — is what actually routes anything.
  2. The controller watches Ingress/HTTPRoute objects and EndpointSlices, and compiles both into live dataplane config.
  3. Backends are resolved straight to pod IPs via EndpointSlices — the controller does its own load balancing, bypassing kube-proxy.
  4. Ingress has no formal cross-object precedence rule for overlapping host/path matches — behaviour is controller-defined.
  5. Gateway API splits config by owner: GatewayClass (which controller), Gateway (platform), HTTPRoute (app team).
  6. Gateway API defines a strict, conformance-tested match precedence and gives objects a rich status subresource.
  7. TLS terminates before routing decisions are made — a missing/wrong Secret falls back to the controller's own fake cert, not an error.
  8. 404 from an ingress = no rule matched (check Host/SNI); 503 = a rule matched but the backend had no ready endpoints.
  9. HTTP-01 cert validation needs the domain already publicly reachable; DNS-01 doesn't — use it for internal/not-yet-live hosts.
  10. Almost everything beyond basic host/path matching on Ingress is a controller-specific annotation, not a portable field.
