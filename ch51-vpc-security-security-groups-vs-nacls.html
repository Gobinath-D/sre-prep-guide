VPC security — Security Groups vs NACLs

Two firewalls guard every packet in a VPC, and they disagree about almost everything: one remembers you, the other doesn't; one only says yes, the other can say no in writing. Mix up which is which and you'll spend an afternoon debugging a reply that got silently dropped on its way home.

Start: Beginner→→→End: Staff-level ~32 min read · AWS CLI / LocalStack

By the end of this chapter you can

  • Explain precisely what a Security Group and a NACL each attach to, and the stateful-vs-stateless difference that drives every gotcha in this chapter.
  • Trace one packet through both layers on the way in, and both layers again — differently — on the way out.
  • Predict, before testing, why a stateless NACL can block a reply even when the matching request sailed straight through.
  • Tell a "connection refused" apart from a "connection timed out" and know which layer each one points at.
  • Redesign a flat, everything-open Security Group into a least-privilege chain that references other Security Groups instead of IP ranges.

Why this exists · the problemThe problem VPC security groups solve

Chapter 50 got you a subnet with a path to the internet. Notice what it didn't get you: any control over who uses that path. Route tables answer "can a packet physically get there." They say nothing about "should this packet be allowed to." Wire up a public subnet with nothing else and every port on every instance in it is fair game to anyone who can route to it.

So AWS gives you two independent filters, and it's worth asking why two instead of one. A Security Group answers "who may talk to this specific network interface" — fine-grained, per-resource, and it follows the resource around. A network ACL answers "what may cross the boundary of this entire subnet" — coarse, blunt, and it doesn't care what's inside. One gives you precision; the other gives you a blast door you can slam on a whole subnet regardless of what any individual instance's rules say. Together they're defense in depth: a mistake in one is supposed to be caught by the other.

The trouble is that "two firewalls" sounds redundant until you learn they behave nothing alike, and production incidents live exactly in that gap.

Key point

A Security Group is stateful and can only allow. A network ACL is stateless and can allow or explicitly deny, evaluated in a strict numbered order. Everything unusual in this chapter — the asymmetric NACL block, the "which layer do I even check" question — falls out of that one paragraph. Memorize it before anything else here.

Mental model · analogyThe mental model: a personal bodyguard and a lobby checkpoint

Real-world analogy

A Security Group is a personal bodyguard assigned to one specific person (your network interface). When a visitor arrives, the bodyguard checks a short list of who's allowed in — and here's the important part — remembers that visitor. When your host later sends a reply out to that same visitor, the bodyguard waves it through without checking anything, because they remember letting the visitor in a moment ago. The bodyguard only ever says "yes, I recognize this" or silently ignores everyone else; there's no "no" on the list, just an absence of "yes."

A network ACL is the building's lobby checkpoint, and it works completely differently. It checks every single person crossing the lobby doors — on the way in and on the way out — against a numbered list of rules, top to bottom, first match wins. And it has no memory at all: it doesn't know or care that it waved someone in five minutes ago. If a rule doesn't explicitly permit someone leaving, they don't leave — even if they were let in by rule #1 a moment earlier. That's why the checkpoint needs separate, explicit rules for people coming in and people going out, and why forgetting the "going out" rule traps your own visitors inside.

ArchitectureOne packet, two gates, in both directions

Every packet entering a subnet crosses the NACL first, at the subnet boundary, then the Security Group, right at the destination's network interface. On the way back out, it's the reverse order — but which layer actually has to check anything is where the two mechanisms stop looking alike.

Read the two boxes in the figure like rulebooks with different grammar. A Security Group's rules are all allow statements, and AWS evaluates them as a set: if any rule matches, the traffic is allowed; if none match, it's dropped by default — there's no explicit "deny" statement to write, and none is needed. A NACL's rules are numbered, each one either ALLOW or DENY, and AWS walks them in ascending order and stops at the first match — a low-numbered DENY will shadow a higher-numbered ALLOW for the same traffic, and every NACL ends with an implicit * rule that denies anything nothing else matched.

Why an SRE cares

Security Groups don't filter everything, even when they're locked down tight. AWS explicitly carves out a handful of exceptions that always get through regardless of your rules: DNS, DHCP, the EC2 and ECS metadata endpoints, Windows license activation, and the Amazon Time Sync service. That's a real, documented fact worth knowing before you assume a restrictive Security Group has fully sealed an instance off — its metadata endpoint is reachable from that instance no matter what you write, which is exactly the door Chapter 54's IMDSv2 material and Chapter 55's IRSA material both care about.

Internal workingWhy the reply is the hard part

Follow one TCP connection all the way through, because the asymmetry only shows up if you track both directions separately.

  1. Request arrives at the subnet boundary. The NACL's inbound rule list is checked, in ascending rule-number order. Say rule 100 allows TCP 443 from 0.0.0.0/0 — match, allowed, stop checking further rules.
  2. Request arrives at the destination ENI. The Security Group's inbound rules are checked, all together. One of them allows 443 from the ALB's Security Group — match, allowed. The Security Group also opens a connection-tracking entry: it now remembers this 5-tuple (protocol, source IP/port, destination IP/port) as an established flow.
  3. The application sends its reply. The reply is outbound from the ENI's point of view. The Security Group checks its tracking table, finds this flow already established, and allows it automatically — it never even consults the outbound rule list for a tracked reply.
  4. The reply reaches the subnet boundary, outbound. The NACL has no memory of step 1 at all — it's a completely separate evaluation. It walks its outbound rule list from the top. If there's no rule allowing the reply's source port range (the original client's ephemeral port, typically somewhere in 1024–65535 depending on the client OS) out to the client's address, the implicit final DENY catches it and the reply is dropped, silently, at the subnet edge.
  5. From the client's point of view, the connection just hangs and eventually times out — indistinguishable, without server-side visibility, from the request never having arrived at all.

That's the entire asymmetric-NACL trap in one sequence: the Security Group's statefulness means you almost never think about outbound rules for reply traffic, which trains you to forget that a NACL needs that same reply traffic spelled out explicitly, twice — once as an inbound allow for the original request, once as an outbound allow for the response.

Think first: your Security Group allows inbound 443 from anywhere, and your NACL allows inbound 443 too. Is that enough to guarantee the connection completes?

No — you've only covered the request leg. TCP's handshake and the HTTP response both need outbound traffic to leave the subnet, and the Security Group will handle that automatically because it's stateful. The NACL will not. Unless the NACL's outbound rule list separately allows the ephemeral port range the client is using, every reply gets silently dropped at the subnet boundary and the client just sees a hang. Two "inbound 443 allowed" rules, one on each layer, is a classic half-finished setup — it feels complete because the request gets through, and the failure only shows up on the way back.

ComponentsThe pieces, and what each one owns

  • Security Group. Owns per-resource, stateful, allow-only filtering. Attached to one or more ENIs (an instance can have several Security Groups; a Security Group can be attached to many ENIs). A brand-new custom Security Group starts with no inbound rules and one default outbound rule allowing everything.
  • Security Group rule. Owns a single allow condition: protocol, port range, and a source (or destination) that can be a CIDR block or another Security Group's ID. Referencing a Security Group as the source is the feature that makes least-privilege chains maintainable — the rule tracks the group, not a list of IPs that changes every time you scale.
  • Network ACL. Owns subnet-wide, stateless, ordered allow/deny filtering. Every subnet has exactly one NACL — the default one if you never attach a custom one — and one NACL can be associated with several subnets.
  • NACL rule. Owns a numbered evaluation position, a protocol/port/CIDR match, and an explicit ALLOW or DENY action, separately for inbound and outbound. Numbers are just evaluation order — leaving gaps (100, 110, 120) is standard practice so you can slot a new rule in later without renumbering everything.
  • The implicit * rule. Every NACL — default or custom — ends with an unremovable, highest-numbered rule that denies anything nothing above it matched. You can't delete it; you can only make sure your own rules catch what you actually want allowed before evaluation ever reaches it.

Data flowFollowing one HTTPS request through both layers, both ways

A client at 203.0.113.9 opens a connection to an EC2 instance at 10.0.0.15:443, sitting in a subnet with a custom NACL and a locked-down Security Group. The SYN packet hits the subnet boundary first: the NACL's inbound rule 100 (ALLOW 443 tcp from 0.0.0.0/0) matches, so it proceeds. It reaches the instance's ENI: the Security Group's inbound rule (ALLOW 443 from sg-alb, say, or a CIDR) matches, so the OS delivers the SYN to the listening process, and the Security Group opens a tracking entry for this flow. The SYN-ACK leaves the instance: the Security Group sees the tracked flow and auto-allows it outbound with no rule lookup. It hits the subnet boundary outbound: the NACL's outbound rule 100 (ALLOW 1024-65535 tcp to 0.0.0.0/0) — written specifically to cover ephemeral-port replies — matches, and the SYN-ACK reaches the client. The rest of the TCP handshake and every subsequent packet in both directions repeats exactly this pattern: Security Group remembers and waves it through; NACL re-checks from scratch, every single time, in both directions.

Lab 1Build — a locked-down Security GroupBuild

Create a Security Group that allows HTTPS in from anywhere and nothing else, and inspect the default outbound rule you didn't have to write.

bash
SG_ID=$(aws ec2 create-security-group --group-name web-sg --description "web tier" \
  --vpc-id $VPC_ID --query 'GroupId' --output text)

aws ec2 authorize-security-group-ingress --group-id $SG_ID \
  --protocol tcp --port 443 --cidr 0.0.0.0/0

aws ec2 describe-security-groups --group-ids $SG_ID \
  --query 'SecurityGroups[].{in:IpPermissions,out:IpPermissionsEgress}'
Output (trimmed)[{ "in": [{ "IpProtocol": "tcp", "FromPort": 443, "ToPort": 443, "IpRanges": [{"CidrIp": "0.0.0.0/0"}] }], "out": [{ "IpProtocol": "-1", "IpRanges": [{"CidrIp": "0.0.0.0/0"}] }] }]

You wrote one inbound rule. The outbound rule — allow all protocols, all ports, anywhere — was there the moment the group was created; it's the Security Group default, and most teams never touch it for a plain web tier since the statefulness of inbound replies is what actually matters for serving traffic. You'll tighten this in Lab 5.

Lab 2Understand — build a NACL and watch rule order decide the outcomeUnderstand

Create a custom NACL, add rules deliberately out of the order you'd naturally write them, and read how AWS actually evaluates them.

bash
NACL_ID=$(aws ec2 create-network-acl --vpc-id $VPC_ID --query 'NetworkAcl.NetworkAclId' --output text)

# Rule 90: deny this one bad actor's /32, checked BEFORE the broad allow.
aws ec2 create-network-acl-entry --network-acl-id $NACL_ID --rule-number 90 \
  --protocol tcp --port-range From=443,To=443 --cidr-block 198.51.100.66/32 \
  --rule-action deny --ingress

# Rule 100: allow everyone else on 443.
aws ec2 create-network-acl-entry --network-acl-id $NACL_ID --rule-number 100 \
  --protocol tcp --port-range From=443,To=443 --cidr-block 0.0.0.0/0 \
  --rule-action allow --ingress

aws ec2 describe-network-acls --network-acl-ids $NACL_ID \
  --query 'NetworkAcls[].Entries[?Egress==`false`].{num:RuleNumber,action:RuleAction,cidr:CidrBlock}'
Output[ { "num": 90, "action": "deny", "cidr": "198.51.100.66/32" }, { "num": 100, "action": "allow", "cidr": "0.0.0.0/0" }, { "num": 32767, "action": "deny", "cidr": "0.0.0.0/0" } ]

Rule 32767 is the implicit catch-all — you didn't create it and can't remove it. Trace two source IPs by hand: 198.51.100.66 hits rule 90 first (lower number wins) and is denied, never reaching rule 100's allow. Any other IP skips rule 90 (no match), matches rule 100, and is allowed — evaluation stops there and never reaches 32767. Order, not intent, decides.

No-cost local alt: same commands against LocalStack, or work the two traces on paper — the algorithm is just "walk the numbers up, stop at first match."

Lab 3Break — the NACL that only lets requests in, never answers outBreak

Associate the NACL from Lab 2 with a subnet holding a web server, curl it from outside, and watch it hang. The Security Group is wide open. Investigate before revealing.

bash
aws ec2 associate-network-acl --network-acl-id $NACL_ID --subnet-id $SUBNET_ID

curl -m 5 https://10.0.0.15
# curl: (28) Connection timed out after 5001 milliseconds

# Check the full rule set, both directions, on the instance's own NACL:
aws ec2 describe-network-acls --network-acl-ids $NACL_ID \
  --query 'NetworkAcls[].Entries[].{num:RuleNumber,egress:Egress,action:RuleAction,port:PortRange}'
Output[ { "num": 90, "egress": false, "action": "deny", "port": {"From":443,"To":443} }, { "num": 100, "egress": false, "action": "allow", "port": {"From":443,"To":443} }, { "num": 32767, "egress": false, "action": "deny", "port": null }, { "num": 32767, "egress": true, "action": "deny", "port": null } ]

Every rule you created has egress: false — inbound only. There's exactly one outbound rule in the whole list, and it's the implicit deny-all. Before opening the answer: given everything you now know about statefulness, why does a fully-open Security Group not save you here?

Reveal the cause

There is no outbound allow rule at all, on the one layer that actually needs one written out. The Security Group's statefulness means its own outbound rules were never in question — the reply is auto-allowed there regardless. But the NACL evaluates outbound completely separately, with zero memory of the inbound request it just let through, and this NACL has no outbound rule except the implicit deny-all at 32767. Every reply — the SYN-ACK, every response byte — gets silently dropped the instant it tries to leave the subnet.

The fix is an explicit outbound rule allowing the reply's port range back to the client: create-network-acl-entry --rule-number 100 --protocol tcp --port-range From=1024,To=65535 --cidr-block 0.0.0.0/0 --rule-action allow --egress. Note the range: the reply leaves from the server's port 443 but arrives addressed to whatever ephemeral port the client picked for the request, so the outbound rule has to permit that broad range, not just 443. This exact gap is the single most common NACL production incident.

Lab 4Troubleshoot — refused vs timed outTroubleshoot

Two tickets land the same afternoon. Ticket A: curl to one instance returns instantly with "connection refused." Ticket B: curl to another instance just hangs until it times out. Before running anything, decide which layer you'd check first for each — then confirm.

bash
# Ticket A:
curl -m 5 http://10.0.1.20:8080
# curl: (7) Failed to connect to 10.0.1.20 port 8080: Connection refused

# Ticket B:
curl -m 5 http://10.0.1.21:8080
# curl: (28) Connection timed out after 5001 milliseconds
Outputrefused → the packet reached the host; something answered "nobody's listening" timeout → the packet was dropped somewhere and got no answer at all

Work out what each signature rules out before you open the diagnosis below.

Reveal the diagnostic logic

"Connection refused" means the packet already cleared both the NACL and the Security Group. A refusal is an active TCP RST sent by the destination host's own network stack, and a host can only send an RST for a packet it actually received. If nothing crossed the network filters, there'd be silence, not a RST. So for Ticket A, skip straight past both firewall layers — the real cause is that nothing is listening on port 8080 on that host (wrong port, app crashed, app bound to 127.0.0.1 instead of 0.0.0.0). Checking Security Groups here wastes time.

"Timed out" means something dropped the packet silently, and a silent drop is exactly what both a NACL DENY and a Security Group with no matching allow rule produce — from outside, they're indistinguishable without server-side tooling. For Ticket B, that's where you start: describe-network-acls for the subnet, then describe-security-groups for the instance's ENI, checking both directions on each. The signature doesn't tell you which of the two layers is the blocker, but it tells you immediately that it is one of them, and that the app itself is very likely fine.

Lab 5Production challenge — from one flat Security Group to a least-privilege chainSenior challenge

You inherit a three-tier app — web, app, database — all sharing one Security Group that allows every port from 0.0.0.0/0, because it was fastest to ship. Redesign it into least privilege, tier by tier, before opening the answer.

bash
aws ec2 describe-security-groups --group-ids sg-flat \
  --query 'SecurityGroups[].IpPermissions[].{proto:IpProtocol,port:FromPort,src:IpRanges[0].CidrIp}'
Output[{ "proto": "-1", "port": null, "src": "0.0.0.0/0" }] # everything, from anywhere, into every tier
Reveal the redesign

Create one Security Group per tier and chain them by reference, not by CIDR: web-sg allows 443 from 0.0.0.0/0 (it's the only tier that should ever face the internet); app-sg allows its application port only --source-group web-sg; db-sg allows 5432 only --source-group app-sg. Nothing in the app or database tier accepts a CIDR block at all anymore.

bash
aws ec2 authorize-security-group-ingress --group-id $APP_SG \
  --protocol tcp --port 8080 --source-group $WEB_SG
aws ec2 authorize-security-group-ingress --group-id $DB_SG \
  --protocol tcp --port 5432 --source-group $APP_SG

The reason this matters beyond "fewer open ports": a group reference tracks membership automatically. When the app tier autoscales and launches ten new instances, every one of them either has app-sg attached or it doesn't — there's no IP allow-list to edit, no CIDR to widen, no stale entry left behind when an instance terminates. A CIDR-based rule has to be maintained by hand as the fleet changes shape; a group-reference rule maintains itself. That's the actual staff-level upgrade here — not just "tighter rules" but rules that stay correct without anyone remembering to update them.

No-cost local alt: the same three authorize-security-group-ingress --source-group calls against LocalStack demonstrate the chain exactly; no live traffic needed to see the API accept a group ID as a source.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · Security Group vs NACL confusion

Symptom: a connection is silently dropped and the on-call engineer starts editing Security Group rules that were never the problem. First cut: check both layers, in both directions, before changing either — describe-security-groups and describe-network-acls side by side. Usual cause: tunnel vision on the per-resource layer (Security Groups feel more familiar) while the actual block is a subnet-wide NACL rule nobody remembered existed.

Incident pattern · asymmetric NACL blocking the return leg

Symptom: requests appear to arrive (server-side logs show the connection) but clients report timeouts and never see a response. First cut: check the NACL's outbound rules specifically for the ephemeral port range — not just whether inbound looks fine. Usual cause: an inbound-only rule set, exactly as built in Lab 3, that lets requests in and then drops every reply at the subnet boundary.

Incident pattern · "it worked yesterday," NACL edition

Symptom: traffic that was fine for months suddenly starts failing, with no application deploy anywhere near the timeline. First cut: diff the NACL's rule list, sorted by number, against its last known-good state. Usual cause: someone inserted a new rule at a lower number than an existing allow — often a well-intentioned, narrowly-scoped deny — and first-match-wins means it now shadows a rule that used to fire first.

Production · security · performanceWhat matters in production

Reach for Security Groups first. AWS's own guidance is direct about this: in most cases, Security Groups alone meet your needs, and NACLs are the additional layer you add for defense in depth — a hard, subnet-wide backstop, not your primary control. Trying to run fine-grained, per-service policy through NACLs fights the tool; NACLs are coarse on purpose.

Never open 22 or 3389 to 0.0.0.0/0. This is AWS's own explicit best-practice warning, not a house style opinion: authorize only the specific address ranges that legitimately need SSH or RDP. The same discipline applies to any administrative port. Prefer referencing a bastion's or a bastion Security Group's ID over a CIDR wherever the source is another one of your own resources.

Know what Security Groups never filter. DNS, DHCP, the instance metadata endpoint, ECS task metadata, Windows activation, and Amazon Time Sync all bypass Security Group rules entirely, by design. That's not a loophole to patch — it's documented behavior — but it means "my Security Group is locked down" is never the same claim as "this instance can't reach the metadata service," which matters directly for the IMDSv2 and IRSA material two chapters over.

Common mistakes: writing a NACL inbound allow and assuming the reply is covered; putting a narrow deny at a lower rule number than the allow it was meant to sit beside, without checking existing numbers first; referencing a Security Group as a source and then wondering why a same-named group in a different VPC doesn't work (group references are scoped to a VPC, with a separate cross-VPC feature required otherwise); and leaving the default Security Group — which allows all outbound and inbound from itself — attached to production resources nobody meant to expose that way.

System-design connectionWhere this reaches into architecture

This chapter is the literal enforcement layer underneath every "zero trust microsegmentation" slide you'll sit through. A least-privilege Security Group chain — each tier only accepting traffic from the specific group in front of it — is the same idea as a Kubernetes NetworkPolicy restricting pod-to-pod traffic (Chapter 47), just enforced one layer down, on the ENI instead of the pod. On EKS with the VPC CNI, pods share their node's Security Groups by default, which is precisely why NetworkPolicy exists as the pod-granular tool, and why AWS also offers security groups for pods as a heavier, per-pod alternative when compliance genuinely requires it (Chapter 58). And the stateful-vs-stateless distinction here is worth carrying forward: it's the same reasoning that shows up anywhere you design a system with a fast, "remembers you" cache in front of a strict, "checks everything again" audit layer.

InterviewInterview questions & answers

Answer each in your head before opening it.

30-secWhat's the core difference between a Security Group and a network ACL?

Scope, memory, and vocabulary. A Security Group attaches to a network interface and is stateful — it remembers a connection and auto-allows the reply — and it can only allow, never explicitly deny. A network ACL attaches to a whole subnet and is stateless — every packet, in either direction, is checked fresh against a numbered rule list with no memory of anything before it — and it can both allow and explicitly deny, evaluated in ascending order with first match winning. In practice: Security Groups do most of your day-to-day access control; NACLs are the coarse, subnet-wide backstop.

2-minWalk me through why a NACL can block a reply even though the request got through fine.

It comes down to statefulness. When a request arrives, the NACL checks its inbound rules and the Security Group checks its inbound rules — if both allow it, the Security Group additionally opens a tracking entry for that connection. When the server replies, the Security Group consults that tracking entry and auto-allows the outbound traffic without even looking at its outbound rule list; that's what stateful means. The NACL does no such tracking. It evaluates the reply's outbound leg completely fresh, as if it had never seen the inbound request, against its own separate outbound rule list. If that list doesn't have a rule allowing the reply's traffic — typically the ephemeral port range the client is using — the implicit deny-all at the end catches it and the reply is dropped silently at the subnet boundary. The client just sees a hang. The fix is always the same: NACLs need explicit, mirrored rules for both directions, because unlike a Security Group they never infer one direction from the other.

DeepWhy does AWS give you two separate mechanisms instead of one better one?

They solve different-shaped problems, and collapsing them into one tool would make both worse at what they're currently good at. A Security Group needs to be attached to a resource and travel with it — when you scale a fleet, every new instance should inherit its tier's rules automatically, and stateful tracking is exactly what makes "allow the reply" require zero extra rules as your traffic patterns get more complex. That precision is expensive to apply at scale, though: writing per-resource state for every flow crossing a whole subnet's worth of traffic doesn't fit a blunt, subnet-wide instrument. A NACL solves the opposite problem — "I need a hard, auditable, impossible-to-accidentally-bypass block at a boundary regardless of what any individual resource's rules say" — and stateless, ordered, allow-or-deny evaluation is the right tool for that: predictable, doesn't depend on connection state that could be manipulated, and enforceable uniformly across everything in the subnet. Defense in depth isn't a slogan here; a misconfigured Security Group on one instance is still caught by a correct NACL at the subnet edge, and vice versa. Two tools, two different jobs, not one job done twice.

ScenarioA client reports "connection refused" hitting your service. Where do you look first, and why not at the Security Group?

"Connection refused" is a signal I take literally: it means a TCP RST came back, and a host can only send a RST in response to a packet it actually received on that port. That already tells me the packet cleared both the NACL and the Security Group — a network-level block produces silence, a timeout, never an active refusal. So I don't start with either firewall layer; I start on the host itself. Most likely nothing is listening on the port the client hit — wrong port number, the app crashed, or it's bound to 127.0.0.1 instead of all interfaces so it never accepts a connection from outside the loopback address. I'd confirm with ss -tlnp or the equivalent on the instance before touching a single Security Group rule, because the evidence already rules the network filters out.

Follow-upHow does Security Group referencing scale better than CIDR-based rules?

A CIDR-based rule encodes a snapshot of IP addresses that's only correct until your fleet changes shape — every autoscale event, every instance replacement, potentially requires someone to update an allow-list, and in practice nobody keeps that current, so teams over-widen the CIDR "just in case" and privilege creeps outward over time. A Security Group reference encodes membership instead of addresses: --source-group app-sg means "anything currently wearing this group," and that set updates itself the instant an instance attaches or detaches the group, with zero rule edits. It's the same shift as moving from a hardcoded server list to a service registry — the access-control question becomes "is this identity in the right group" instead of "is this the right IP today," and the former stays correct under change while the latter quietly rots.

RetainQuick revision

Security Groups and NACLs both filter traffic, and that's nearly the only thing they have in common. A Security Group attaches to a network interface, is stateful, and can only allow — matching rules are OR'd together, and a tracked connection's reply is auto-allowed with no outbound rule needed. A NACL attaches to a subnet, is stateless, and evaluates numbered rules in ascending order with first match winning, ending in an implicit deny-all you can't remove; it re-checks every packet in both directions with zero memory between them, which is exactly why an inbound-only NACL rule set traps replies at the subnet boundary. "Connection refused" means the packet cleared both layers and nothing was listening; "timed out" means something dropped it silently, and either layer is a suspect. Security Groups are your primary tool; NACLs are the coarse backstop. And referencing a Security Group as a rule's source, instead of a CIDR block, is what makes least privilege survive a fleet that keeps changing shape.

The 10 things to remember

  1. Security Groups attach to ENIs and are stateful; NACLs attach to subnets and are stateless.
  2. Security Groups can only allow (rules OR'd together); NACLs can allow or explicitly deny, evaluated in ascending order, first match wins.
  3. A tracked connection's reply is auto-allowed by the Security Group — no outbound rule needed there.
  4. A NACL re-checks every packet fresh in both directions, so it needs explicit, separate inbound and outbound rules for the same flow.
  5. Every NACL ends in an implicit, unremovable deny-all at the highest rule number.
  6. "Connection refused" = packet reached the host, nothing listening; "timed out" = dropped somewhere, check both firewall layers.
  7. Security Groups don't filter DNS, DHCP, instance metadata, ECS task metadata, Windows activation, or Amazon Time Sync — by design.
  8. Never open SSH or RDP to 0.0.0.0/0 — AWS's own best-practice guidance says so directly.
  9. Reference a Security Group as a rule's source instead of a CIDR wherever the source is one of your own resources — it self-updates as the fleet changes.
  10. Reach for Security Groups first; treat NACLs as the subnet-wide defense-in-depth backstop, not your primary control.
