Part VI · AWS & EKS for SREs · Chapter 55

IRSA and EKS Pod Identity

A pod has no access key sitting on disk for anyone to steal, and yet it calls S3 as if it does. The trick is that Kubernetes hands STS a signed note instead of a credential, and STS already knew how to deal with signed notes — it's the exact door Chapter 54 walked through, just with a different kind of ID at the window.

Start: Beginner→→→End: Staff-level ~42 min read · eksctl / kubectl / AWS CLI

By the end of this chapter you can

  • Explain the problem IRSA solves that "just give every node one big IAM role" doesn't, and why a pod needed a new mechanism at all.
  • Trace a projected service account token from the kubelet's disk write all the way to a completed sts:AssumeRoleWithWebIdentity call, in order.
  • Tell IRSA and EKS Pod Identity apart — what changed, what stayed the same, and which one to reach for on a new cluster.
  • Annotate a ServiceAccount, exec into a pod, and reach S3 with no static credential anywhere on the box.
  • Debug "pod can't access S3" by checking the trust policy, the ServiceAccount annotation, and the token's claims, in that order.

Why this exists · the problemA pod isn't an EC2 instance, and IMDS doesn't know that

Chapter 54 ended with an EC2 instance pulling its attached role's credentials off the Instance Metadata Service — clean, no static secret, works great for one process per machine. Now put forty pods from six different teams on that same instance. IMDS still only knows about the node. Every pod that curls 169.254.169.254 gets back the exact same node-level role, whether it's the billing service that needs to write to a database or a static file server that needs nothing at all. Your options with that constraint are both bad: give the node role the union of everything any pod on it might ever need — enormous, standing over-privilege — or run one tiny single-tenant node group per workload, which defeats half the point of bin-packing pods onto shared nodes in the first place.

What you actually want is an IAM role per pod, or more precisely per workload. But a pod has no hardware identity the way an EC2 instance does — it's a Linux process, not a machine IMDS was ever designed to recognize individually. So AWS needed a different question to ask at the door. Instead of "prove you're this EC2 instance," the question becomes "prove you're this specific Kubernetes ServiceAccount" — and Kubernetes already has a built-in way to prove exactly that: a signed token. IAM Roles for Service Accounts (IRSA), and its newer sibling EKS Pod Identity, are both just AWS teaching IAM's trust machinery to accept that Kubernetes-signed proof in place of an existing AWS credential.

Key point

Nothing about the authorization half of this chapter is new. Once a pod has temporary credentials, they're checked against a permission policy exactly the way Chapter 54 described — same STS, same temporary-credential shape, same evaluation rules. The only genuinely new idea here is on the authentication half: what a pod presents as proof of who it is, and who AWS trusts to have signed that proof.

Mental model · analogyThe mental model: the same badge desk, a new kind of ID

Real-world analogy

Remember the temp-badge desk from Chapter 54 — you showed a permanent company badge, the desk checked its rulebook, you walked away with a temporary badge. IRSA teaches that same desk one new trick: it now also keeps a list of outside notaries it has agreed in advance to trust, and it will accept a properly signed note from one of them in place of your company badge. The notary it registers is Kubernetes itself — specifically, one particular cluster's own signing key.

Every pod that needs AWS access carries exactly one such note: a signed, short-lived token, naming precisely one requester ("this note is for system:serviceaccount:payments:billing-writer, nobody else") and automatically replaced with a fresh one before the old one goes stale. The pod hands that note to the badge desk instead of a company badge. The desk checks two things: is this note genuinely signed by the notary it registered (Kubernetes' signature verifies), and does the note's stated purpose match what this specific temporary badge requires ("only issue this badge to notes naming exactly billing-writer")? Pass both, and out comes a temporary badge — identical in every way to the one Alice got in Chapter 54, just requested with a very different kind of ID.

EKS Pod Identity is the same idea with the paperwork simplified: instead of you personally registering the outside notary and hand-writing the note-matching rule into the badge's own rulebook, a dedicated clerk (an agent running on every floor of the building) handles the whole notary relationship for you and just hands the badge straight to the pod.

ArchitectureOIDC federation, a projected token, and one scoped role

Every EKS cluster has its own OIDC issuer URL — a real, discoverable OpenID Connect endpoint that publishes its own signing keys, exactly like any other identity provider. IRSA's setup has exactly one manual, one-time step per cluster: register that issuer as an IAM OIDC identity provider, so IAM is willing to trust JSON Web Tokens signed by this specific cluster at all. From there, an IAM role's trust policy can name that provider as a Federated principal and add a condition pinning the token's sub claim to one exact string — system:serviceaccount:<namespace>:<service-account-name> — and its aud claim to sts.amazonaws.com. That condition is the entire scoping mechanism: it's not "any pod in this cluster," it's one specific ServiceAccount, full stop.

On the Kubernetes side, you annotate that ServiceAccount with the role's ARN. A mutating admission webhook that ships with EKS watches for pods using an annotated ServiceAccount and, at pod creation, injects a projected volume containing a freshly requested token plus two environment variables — AWS_ROLE_ARN and AWS_WEB_IDENTITY_TOKEN_FILE. Any AWS SDK that sees both of those variables already knows, with zero application code changes, to read the token file and call AssumeRoleWithWebIdentity with it. That auto-detection is deliberate — it's the same mechanism the SDK already used for other web-identity flows, just pointed at a new token source.

Why an SRE cares

The webhook injects that projected token and those two environment variables at pod creation, through admission. A pod that was already running when you annotated its ServiceAccount does not retroactively get either one — it has to be recreated. "I annotated the ServiceAccount and it still doesn't work" is very often just an old pod that was never touched by the webhook at all.

Internal workingFrom one-time cluster setup to one completed AssumeRoleWithWebIdentity

Walk the full chain in the order it actually happens, because every lab in this chapter is a variation on one step in this list going wrong.

  1. Register the cluster's OIDC issuer with IAM, once per cluster. eksctl utils associate-iam-oidc-provider (or the console equivalent) creates an IAM OIDC identity provider whose URL matches the cluster's own issuer and whose audience is sts.amazonaws.com. Skip this and no role anywhere can trust tokens from this cluster, no matter how correctly everything else is configured.
  2. Create a role whose trust policy names that provider, with a Federated principal and a condition pinning <oidc-provider>:sub to one exact system:serviceaccount:namespace:name string and <oidc-provider>:aud to sts.amazonaws.com. This is the scoping mechanism — get the namespace or name even slightly wrong here and the role trusts nothing real.
  3. Annotate the matching ServiceAccount with eks.amazonaws.com/role-arn: <the role's ARN>. This is a plain Kubernetes object annotation — it does nothing by itself until a pod using this ServiceAccount is actually created.
  4. A pod using that ServiceAccount is scheduled. EKS's mutating admission webhook intercepts the pod spec before it's persisted and injects a projected volume (sourced from the Kubernetes TokenRequest API, requesting audience sts.amazonaws.com), a fixed mount path for it, and the two environment variables the SDK looks for.
  5. The kubelet requests the actual token from the API server at pod startup, and keeps refreshing it automatically well before it expires — the running container never has to think about rotation.
  6. The AWS SDK inside the container detects AWS_WEB_IDENTITY_TOKEN_FILE and AWS_ROLE_ARN and, the first time any AWS call is made, reads the token file and calls sts:AssumeRoleWithWebIdentity with the role ARN and the token as WebIdentityToken.
  7. STS verifies the JWT's signature against the OIDC provider's published public keys, confirms it hasn't expired, and evaluates the target role's trust policy — does the Federated principal match, and do the token's sub and aud claims satisfy the policy's conditions?
  8. If everything matches, STS mints temporary credentials — the identical access key / secret key / session token shape from Chapter 54 — and the SDK caches and uses them exactly like any other assumed-role session, refreshing them again via the same flow once they near expiry.

EKS Pod Identity collapses several of these steps. There's no IAM OIDC provider for you to create, and no manual ServiceAccount annotation with a role ARN — instead you create a Pod Identity association (aws eks create-pod-identity-association) that directly links a cluster, a namespace, and a ServiceAccount name to a role ARN as a first-class EKS object. A dedicated EKS Pod Identity Agent, running as a DaemonSet on every node, handles the credential exchange locally, and the role's trust policy uses a dedicated pods.eks.amazonaws.com service principal instead of a Federated OIDC-provider principal with hand-written sub/aud conditions. The pod still gets a projected token; there's simply less of the OIDC federation plumbing for you to wire up and get wrong by hand.

Think first: you annotate a ServiceAccount correctly, but a pod that's been running for three days using it still fails to authenticate as the role. Why?

The webhook only acts at pod admission — the moment a pod is created, it inspects the ServiceAccount it's using and injects the token volume and environment variables then, and only then. A pod that was already running before you added the annotation was never touched by the webhook; it has neither the projected token nor the two environment variables, so its SDK calls fall through to whatever the next credential source in the chain happens to be (very possibly the node's own role, silently, which is its own problem). The fix is simply to delete and recreate the pod — a rolling restart of its Deployment does this for you — so the webhook gets a fresh chance to mutate it at creation time.

ComponentsThe pieces, and what each one owns

  • IAM OIDC identity provider. Owns the one-time trust relationship between IAM and one specific cluster's token signer. Required for IRSA; not needed for EKS Pod Identity.
  • Role trust policy (IRSA form). Owns the scoping: a Federated principal plus sub/aud conditions that pin the role to exactly one namespace:ServiceAccount pair.
  • ServiceAccount annotation. Owns the Kubernetes-side pointer from a ServiceAccount to a role ARN, for IRSA. Does nothing retroactively — it only affects pods created after it's set.
  • Pod Identity association. Owns the same cluster/namespace/ServiceAccount-to-role link for EKS Pod Identity, as a queryable EKS API object instead of an annotation plus a hand-written trust policy.
  • The mutating admission webhook (IRSA) / Pod Identity Agent (Pod Identity). Owns injecting the projected token and, for IRSA, the two environment variables, at pod creation time.
  • Projected ServiceAccount token. Owns proof of identity: a short-lived, audience-scoped JWT naming exactly one ServiceAccount, automatically refreshed by the kubelet for the life of the pod.

Data flowOne aws s3 ls, from inside the pod to the bucket

A pod in namespace payments uses ServiceAccount billing-writer, annotated with a role that trusts exactly system:serviceaccount:payments:billing-writer. Someone execs in and runs aws s3 ls s3://invoices/. The CLI's SDK layer sees AWS_WEB_IDENTITY_TOKEN_FILE and AWS_ROLE_ARN already set in the environment, reads the projected token from disk, and calls sts:AssumeRoleWithWebIdentity. STS fetches the cluster's public keys, verifies the token's signature, and checks its sub claim — system:serviceaccount:payments:billing-writer — against the role's trust policy condition. They match, so STS returns temporary credentials. The CLI signs the S3 ListObjectsV2 request with them; S3 checks the role's permission policy, finds an allow for s3:ListBucket on invoices, and returns the listing. Nothing in that entire chain — not the token, not the temporary credentials — was ever written to a secret, a config file, or anything that outlives the pod.

Hands-onLabs — build, understand, break, troubleshoot

This chapter's core mechanism only means something against a real EKS cluster's own OIDC issuer — a kind cluster's issuer isn't something IAM will ever trust, so unlike earlier chapters, LocalStack and local clusters can't meaningfully stand in for the cluster-to-IAM trust relationship itself. Where a lab genuinely needs real AWS, it says so; where the IAM side alone can be rehearsed for $0, it's noted.

bash
CLUSTER=my-cluster
OIDC_ID=$(aws eks describe-cluster --name $CLUSTER \
  --query "cluster.identity.oidc.issuer" --output text | cut -d '/' -f 5)
echo $OIDC_ID

# No-cost local alt for the IAM half only: LocalStack Community can accept
# create-open-id-connect-provider and create-role calls so you can validate

Lab 1Build — associate an OIDC provider and scope a role to one ServiceAccountBuild

Do the one-time cluster setup, then create a role that trusts exactly one namespace:ServiceAccount pair — not the whole cluster.

bash
# One-time per cluster.
eksctl utils associate-iam-oidc-provider --cluster $CLUSTER --approve

OIDC_PROVIDER="oidc.eks.us-east-1.amazonaws.com/id/$OIDC_ID"
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)

cat > trust.json <<EOF
{ "Version": "2012-10-17", "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::$ACCOUNT_ID:oidc-provider/$OIDC_PROVIDER" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": { "StringEquals": {
      "$OIDC_PROVIDER:sub": "system:serviceaccount:payments:billing-writer",
      "$OIDC_PROVIDER:aud": "sts.amazonaws.com"
} } }] }
EOF
aws iam create-role --role-name billing-writer-role --assume-role-policy-document file://trust.json
aws iam put-role-policy --role-name billing-writer-role --policy-name s3-invoices \
  --policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":["s3:GetObject","s3:PutObject"],"Resource":"arn:aws:s3:::invoices/*"}]}'

kubectl annotate serviceaccount billing-writer -n payments \
  eks.amazonaws.com/role-arn=arn:aws:iam::$ACCOUNT_ID:role/billing-writer-role
Output (from get-role){ "Role": { "Arn": "arn:aws:iam::111122223333:role/billing-writer-role" } } serviceaccount/billing-writer annotated

Look closely at the trust policy's Condition block: it names one exact namespace and one exact ServiceAccount name, not a wildcard. That single string is the entire boundary between "this role belongs to the billing writer" and "this role belongs to anything in the cluster."

No-cost local alt: the trust-policy JSON and put-role-policy calls run identically against LocalStack for $0; only associate-iam-oidc-provider and the eventual pod-side test need a real cluster.

Lab 2Understand — exec in and read exactly what the SDK readsUnderstand

Roll a pod using that ServiceAccount, then look at precisely what the webhook injected — the environment variables and the token's actual claims.

bash
POD=$(kubectl get pod -n payments -l app=billing-writer -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n payments $POD -- env | grep AWS

# Decode the token's payload (the middle third of the JWT) without verifying it:
kubectl exec -n payments $POD -- sh -c \

OutputAWS_ROLE_ARN=arn:aws:iam::111122223333:role/billing-writer-role AWS_WEB_IDENTITY_TOKEN_FILE=/var/run/secrets/eks.amazonaws.com/serviceaccount/token {"aud":["sts.amazonaws.com"],"exp":1758480000, "sub":"system:serviceaccount:payments:billing-writer", ...}

The sub claim in that decoded token is character-for-character the same string you wrote into the trust policy's condition in Lab 1 — that's not a coincidence, it's the entire mechanism. Now prove the whole chain actually works:

bash
kubectl exec -n payments $POD -- aws sts get-caller-identity
kubectl exec -n payments $POD -- aws s3 ls s3://invoices/
Output{ "Arn": "arn:aws:sts::111122223333:assumed-role/billing-writer-role/botocore-session-..." } 2026-09-10 09:14:02 8421 q3-acme.csv

No-cost local alt: none meaningful — this lab is inherently about a real cluster's live token and a real STS call, which is the whole point of it.

Lab 3Break — the pod that can't authenticate at allBreak

Someone copies the ServiceAccount and role from Lab 1 into a new namespace, payments-staging, expecting it to just work. It doesn't. Investigate before revealing.

bash
kubectl exec -n payments-staging $POD -- aws s3 ls s3://invoices/
OutputAn error occurred (AccessDenied) when calling the AssumeRoleWithWebIdentity operation: Not authorized to perform sts:AssumeRoleWithWebIdentity

Note where this fails: it's an AssumeRoleWithWebIdentity error, not an S3 error — the call never even got as far as S3. Decode the token in this pod and compare its sub claim against what's actually in the role's trust policy before opening the answer.

Reveal the cause

The token's sub claim is system:serviceaccount:payments-staging:billing-writer, but the role's trust policy condition still says system:serviceaccount:payments:billing-writer. The ServiceAccount got copied into a new namespace, and the annotation came with it — but nobody updated the IAM role's trust policy to match the new namespace, so the condition is now checking against a string the token will never produce. STS correctly refuses: this pod really isn't the principal the role trusts, by exactly one namespace's worth of difference.

The fix is either updating the trust policy's condition to the new namespace, or — better, if both environments genuinely need this access — adding a second condition value (or a second statement) so the role trusts both payments:billing-writer and payments-staging:billing-writer explicitly. What it should never become is a wildcard sub condition "to make the error go away" — that's the scoping mechanism gone entirely.

Lab 4Troubleshoot — no error at all, just silence and the wrong identityTroubleshoot

A different pod, different day. No AssumeRoleWithWebIdentity error this time — aws sts get-caller-identity just quietly returns an identity nobody expected. Investigate before revealing.

bash
kubectl exec -n payments $POD2 -- env | grep AWS
# (nothing printed at all)

kubectl exec -n payments $POD2 -- aws sts get-caller-identity
Output{ "Arn": "arn:aws:sts::111122223333:assumed-role/eksctl-nodegroup-role/i-0abc123..." }

There's no AWS_ROLE_ARN, no AWS_WEB_IDENTITY_TOKEN_FILE — the webhook injected nothing into this pod at all — and yet the SDK still returned an identity. Whose, and why didn't it just fail?

Reveal the cause

This is the node's own instance-profile role, reached through IMDS, exactly as in Chapter 54 — and it's answering because the SDK's credential-provider chain doesn't stop and error out when the IRSA-specific environment variables are missing; it just keeps falling through to the next source, and IMDS is the fallback of last resort. Checking the ServiceAccount's annotation turns up a typo: eks.amazonaws.com/role-arn with a trailing space in the annotation key, which Kubernetes treats as a completely different, unrecognized annotation — so the webhook never matched this ServiceAccount at all, and silently injected nothing.

This is worse than an outright failure, and worth sitting with: a broken annotation doesn't make the pod fail loudly, it makes the pod quietly inherit whatever the node's role can do. If that node role is broad — which it often is, because it also needs to support the CNI, kubelet, and image pulls — this pod may have far more access than anyone intended, and nothing about its behavior looks broken until someone notices the identity in a CloudTrail log. Fix the annotation key, recreate the pod, and confirm the environment variables actually appear this time before considering it resolved.

Lab 5Production challenge — can a pod just skip IRSA and ask the node directly?Senior challenge

Lab 4 hinted at something worth testing on purpose. If a pod's own credentials are misconfigured, it falls back to the node's role — but could a pod reach the node's IMDS credentials even when its own IRSA setup is perfectly correct, just by asking directly? Try it, then design the fix.

bash
# From inside the correctly-configured billing-writer pod:
kubectl exec -n payments $POD -- curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600" -o /tmp/t
kubectl exec -n payments $POD -- sh -c \
  'curl -s -H "X-aws-ec2-metadata-token: $(cat /tmp/t)" http://169.254.169.254/latest/meta-data/iam/security-credentials/'
Outputeksctl-nodegroup-role

It answered. A pod with a perfectly correct, narrowly-scoped IRSA role can still reach out and pull the node's role credentials directly, because by default nothing stops pod network traffic from reaching the node's link-local metadata address at all — Security Groups don't filter this traffic either, as Chapter 51 noted. Design the fix before opening it.

Reveal the fix

The durable fix is architectural, not a firewall rule: never let the node's role be worth stealing. Keep node instance-profile roles down to exactly what kubelet, the CNI, and image pulls genuinely require — nothing application-shaped should ever live there — and give every workload its own IRSA role or Pod Identity association for anything it actually needs to do. If the node role can't read customer data, a pod reaching it via IMDS is a non-event.

As defense in depth on top of that, some clusters additionally block pod-to-IMDS traffic at the network layer — either an explicit rule dropping pod-sourced traffic to 169.254.169.254, or tuning the instance's metadata hop limit, though how effective a given hop-limit setting is depends on exactly which VPC CNI networking mode the cluster runs, so treat it as a secondary control to verify for your specific setup, not a substitute for keeping the node role minimal in the first place. The senior-level takeaway is the ordering: fix the blast radius first (minimal node role, IRSA/Pod Identity everywhere), then add network-layer hardening if you still want the extra layer — never the other way around.

No-cost local alt: the vulnerability itself needs a real node and real IMDS to demonstrate; the fix — auditing what a node role actually grants and trimming it — is a policy-review exercise you can do against any account's IAM console for $0.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · AssumeRoleWithWebIdentity rejected outright

Symptom: the SDK fails before ever reaching the target AWS service, with an explicit AssumeRoleWithWebIdentity denial. First cut: decode the pod's token and diff its sub/aud claims against the role's trust policy condition, character for character. Usual cause: a namespace or ServiceAccount name that drifted out of sync between the Kubernetes annotation and the IAM trust policy — commonly after copying manifests into a new namespace.

Incident pattern · no error, but the wrong identity entirely

Symptom: calls succeed, but get-caller-identity shows the node's instance-profile role instead of the expected assumed role, and no error was ever raised. First cut: check whether AWS_ROLE_ARN and AWS_WEB_IDENTITY_TOKEN_FILE are actually present in the pod's environment at all. Usual cause: a typo'd or missing ServiceAccount annotation that the webhook silently never matched, so the SDK fell all the way through to IMDS.

Incident pattern · it worked, then stopped, after an unrelated deploy

Symptom: a workload that authenticated fine for weeks suddenly can't, right after a routine rollout. First cut: did the rollout change the ServiceAccount the pod uses, or was the annotation added after pods were already running rather than before? Usual cause: the webhook only injects at admission time — an annotation added to an already-running Deployment's ServiceAccount does nothing until the pods are actually recreated.

Production · security · performanceWhat matters in production

Scope every role to one workload, not a shared ServiceAccount for convenience. The entire security value of IRSA comes from the trust policy's sub condition naming exactly one ServiceAccount. Reusing one ServiceAccount — and therefore one role — across several unrelated workloads quietly rebuilds the node-level over-privilege problem this chapter exists to solve, just one layer up.

Keep node roles minimal, always, regardless of IRSA. Because pod network traffic can reach a node's IMDS unless something specifically blocks it, a node role is only as safe as "boring" — kubelet, CNI, and image-pull permissions, nothing that looks like an application permission. This isn't optional hardening; it's the actual backstop behind every correctly-configured IRSA role on that node.

Prefer EKS Pod Identity for new clusters, but know IRSA cold regardless. Pod Identity removes the OIDC-provider bookkeeping and the hand-written trust-policy conditions, which removes a whole category of the mistakes in this chapter's labs. That said, IRSA is what the overwhelming majority of production EKS fleets run today, and CloudTrail entries, trust policies, and incident write-ups you'll encounter for years will assume you can read IRSA's mechanics fluently.

Common mistakes: annotating a ServiceAccount and expecting already-running pods to pick it up without a restart; wildcarding a trust policy's sub condition to make an error disappear instead of fixing the actual mismatch; sharing one ServiceAccount across workloads with different permission needs; and assuming a locked-down Security Group protects a node's IMDS endpoint, when Security Groups explicitly don't filter that traffic at all.

System-design connectionWhere this reaches into architecture

IRSA and Pod Identity are the reason "zero static secrets in the platform" is achievable at all on EKS, and that property is worth stating out loud in any system-design answer involving Kubernetes on AWS: every workload gets exactly the AWS permissions it needs, provably scoped, with nothing to rotate by hand and nothing sitting on disk for an attacker to find. It's the direct payoff of everything built up to here — Chapter 54's trust-policy and AssumeRole mechanics, Chapter 35's ServiceAccount as a first-class Kubernetes identity, and Chapter 58's fact that a pod is a fully-addressable citizen of the VPC, which is exactly why its traffic can reach IMDS in Lab 5 and exactly why that has to be designed around rather than assumed away. It also mirrors Kubernetes' own RBAC story (Chapter 39): both systems answer "what is this workload allowed to do," just against two different APIs, and a mature EKS platform has to get both stories right, not just one.

InterviewInterview questions & answers

Answer each in your head before opening it.

30-secWhat problem does IRSA solve, in one sentence?

It gives an individual Kubernetes pod its own scoped IAM role instead of forcing every pod on a node to share that node's one instance-profile role — replacing "prove you're this EC2 instance" (what IMDS answers) with "prove you're this exact ServiceAccount," which a Kubernetes-signed token can do and a node-level mechanism never could.

2-minWalk me through what happens from a pod calling an AWS API to getting a response, under IRSA.

The ServiceAccount the pod uses is annotated with a role ARN, and at pod creation a mutating webhook injects a projected token — a short-lived JWT naming that exact ServiceAccount as its sub claim and sts.amazonaws.com as its aud — plus two environment variables the AWS SDK recognizes automatically. When the app makes its first AWS call, the SDK reads that token file and calls sts:AssumeRoleWithWebIdentity with the role ARN and the token. STS verifies the token's signature against the cluster's OIDC provider, which had to be registered with IAM as a one-time setup step, then checks the role's trust policy: a Federated principal naming that OIDC provider, with a condition pinning the token's sub and aud to expected values. If that matches, STS returns ordinary temporary credentials — identical in shape to any other assumed-role session — and every subsequent call is authorized against that role's permission policy. The one idea I'd anchor the whole answer on: only the first hop, proving identity with a signed token instead of an existing credential, is new; everything after "STS mints temporary credentials" is unchanged from a plain AssumeRole.

DeepHow does EKS Pod Identity actually differ from IRSA, mechanically?

IRSA relies on general-purpose OIDC federation: you register the cluster's OIDC issuer as an IAM identity provider yourself, and every role's trust policy has to spell out a Federated principal plus hand-written sub/aud string conditions that have to exactly match a token's claims — powerful, but entirely dependent on you getting several independent strings correct across two different systems. Pod Identity replaces that hand-wiring with a first-class EKS object, the Pod Identity association, that directly declares "this namespace and ServiceAccount maps to this role" without you touching an OIDC provider ARN or writing a condition block at all; the trust policy instead just trusts the dedicated pods.eks.amazonaws.com service principal. Operationally, a Pod Identity Agent DaemonSet on every node handles the credential exchange, rather than the pod's own SDK independently performing a public AssumeRoleWithWebIdentity call with a JWT it read off disk. The pod still gets a projected token under the hood, but there's meaningfully less surface area for a typo to silently break trust — which is precisely why most of this chapter's labs are IRSA-shaped: that's where the interesting failure modes concentrate.

ScenarioA pod's AWS calls are succeeding, but with permissions nobody granted it. What's your first hypothesis?

My first hypothesis is that IRSA never actually engaged for this pod, and it's quietly running on the node's own instance-profile role via IMDS instead — which explains both "it works" and "with permissions nobody granted," since the node role was scoped for kubelet and CNI needs, not for this workload. I'd check the pod's environment for AWS_ROLE_ARN and AWS_WEB_IDENTITY_TOKEN_FILE first; their absence confirms the webhook never touched this pod, usually because of a ServiceAccount annotation typo, a missing recreation after the annotation was added, or the pod using a different ServiceAccount than intended. I'd also directly confirm by calling get-caller-identity and checking whether the ARN says assumed-role/<expected-role> or assumed-role/<node-group-role> — that single string answers the question immediately. This is exactly why keeping node roles minimal matters regardless of how well IRSA is configured elsewhere: a misconfigured pod fails safe only if there's nothing dangerous to fail into.

Follow-upWhy can't a pod's Security Group protect it from a node-role IMDS leak?

Because Security Groups don't filter traffic to the EC2 instance metadata endpoint at all — it's one of a documented handful of exceptions, alongside DNS, DHCP, and a few others, that always bypass Security Group rules by design, covered back in Chapter 51. A pod can be sitting behind the tightest Security Group imaginable and still reach 169.254.169.254 freely, because that traffic was never subject to Security Group evaluation in the first place. That's exactly why the durable fix in Lab 5 has to be architectural — keep the node role harmless to steal — rather than relying on any firewall-layer control to block the path, since the most obvious firewall layer was never in a position to block it at all.

RetainQuick revision

A pod has no hardware identity, so IMDS can only ever answer at the node level — every pod on a node sharing one role is the problem IRSA and EKS Pod Identity both solve, by teaching AWS's trust machinery to accept a Kubernetes-signed token as proof of identity instead of an existing credential. IRSA needs a cluster's OIDC issuer registered with IAM once, a role trust policy with a Federated principal and sub/aud conditions pinned to one exact namespace:ServiceAccount, and a ServiceAccount annotation that a mutating webhook uses to inject a projected token plus two environment variables into pods at creation time only. The SDK auto-detects those variables and calls sts:AssumeRoleWithWebIdentity; everything from there — temporary credentials, permission-policy evaluation — is identical to a plain AssumeRole. EKS Pod Identity replaces the OIDC federation and hand-written conditions with a first-class association object and an on-node agent, with less to misconfigure. Debugging means decoding the token's actual claims and diffing them against the trust policy, checking whether the webhook's environment variables are present at all, and never forgetting that a pod can reach a node's IMDS directly regardless of how correct its own IRSA setup is — which is why the node's own role has to stay minimal no matter what.

The 10 things to remember

  1. IMDS answers per node, not per pod — one shared node role for many pods is exactly the over-privilege problem IRSA solves.
  2. IRSA swaps "prove you're this EC2 instance" for "prove you're this ServiceAccount," using a Kubernetes-signed token as the proof.
  3. Registering the cluster's OIDC issuer with IAM is a one-time, per-cluster step; skip it and no role can ever trust this cluster's tokens.
  4. A role's trust policy scopes IRSA to one exact namespace:ServiceAccount via sub/aud conditions — never widen this to make an error disappear.
  5. The mutating webhook injects the token and environment variables only at pod creation; an annotation added later needs the pod recreated to take effect.
  6. Once STS mints temporary credentials, everything is identical to a plain AssumeRole from Chapter 54 — nothing new past that point.
  7. EKS Pod Identity replaces OIDC federation and hand-written trust conditions with a first-class association and an on-node agent — fewer moving parts.
  8. Missing IRSA environment variables don't cause a loud failure — the SDK silently falls through to the node's role via IMDS instead.
  9. Security Groups don't filter traffic to the instance metadata endpoint, so a pod can reach a node's IMDS regardless of its own network policy.
  10. The durable defense is architectural: keep node instance-profile roles minimal, and give every workload its own IRSA or Pod Identity role for everything it actually needs.
