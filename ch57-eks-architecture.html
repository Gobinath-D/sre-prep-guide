Part VI · AWS & EKS for SREs · Chapter 57

EKS architecture

EKS runs the Kubernetes control plane so you don't have to — and then hides it behind an endpoint and an IAM handshake. That trade is what makes EKS pleasant on a good day and baffling on a bad one. When kubectl says "you must be logged in to the server," you're standing at exactly the seam this chapter takes apart.

Start: Beginner→→→End: Staff-level ~45 min read · AWS CLI / eksctl (kind fallback)

By the end of this chapter you can

  • Draw what AWS runs for you in EKS and what stays your problem — the shared-responsibility line.
  • Choose between managed node groups, self-managed nodes, and Fargate, and say why.
  • Explain exactly how kubectl authenticates to EKS: the STS token, the webhook, then RBAC.
  • Map an IAM principal to cluster access two ways — the legacy aws-auth ConfigMap and the newer access entries — and know which to reach for.
  • Diagnose "you must be logged in to the server (Unauthorized)" and a node that never joins, from first principles.

Why this exists · the problemRunning the control plane yourself is a second job

In Chapter 29 you took the Kubernetes control plane apart: the API server, etcd, the scheduler, the controller manager. Now picture owning all of that in production. etcd wants an odd number of members spread across availability zones, with backups you've actually tested restoring. The API server wants at least two instances behind a load balancer, with certificates that rotate before they expire. Every quarter there's a Kubernetes minor upgrade, and you get to sequence it: control plane first, then nodes, without dropping the cluster. Get any of it wrong and the blast radius is every workload on the cluster.

That's a full-time on-call rotation before you've shipped a single application. Most teams don't want it, and AWS will sell you out of it. Amazon EKS runs the control plane for you — the API server, etcd, the scheduler, and the controller manager live in an AWS-owned account, spread across three availability zones, patched and scaled and backed up by AWS. You get one thing back: a highly-available API endpoint. You never SSH to a control-plane node, never touch etcd, never see those machines.

The catch is that "managed" doesn't mean "invisible." EKS glues its control plane to your world with two seams, and both become your incident when they leak. The first is identity: EKS decides who you are using AWS IAM, then hands you to normal Kubernetes RBAC — so a perfectly valid kubectl can be rejected before it reaches any authorization rule. The second is the network path between the managed control plane and your nodes, stitched with cross-account network interfaces dropped into your subnets. This chapter makes both seams visible so they stop being mysterious.

Key point

EKS is Kubernetes with the control plane converted into an AWS service. The Kubernetes you learned in Part IV is unchanged — same API objects, same reconciliation, same RBAC. What's new is a thin identity-and-networking shell AWS wraps around it. Learn the shell and EKS stops being "different Kubernetes"; it's the Kubernetes you know, reached through an IAM front door.

Mental model · analogyThe mental model: a managed apartment building

Real-world analogy

Think of EKS as a serviced apartment building. Down in a locked basement is the mechanical core — the boilers, the electrical panels, the water mains. That's the control plane, and building management (AWS) owns it completely. You never get a key to the basement; if a boiler fails at 3am, that's their pager, not yours. In exchange you get reliable heat and water at a wall socket — the cluster endpoint.

You rent units on the floors above — that's your data plane, where your furniture (pods) actually lives. And you choose how much furnishing you want to manage: a unit where you bring and maintain everything yourself (self-managed nodes), a serviced unit where management handles appliances and repairs on a schedule (managed node groups), or a hotel-style room you just walk into per-guest with no furniture to own at all (Fargate).

To give any instruction — "let a plumber into unit 5" — you first show ID at the concierge desk. The concierge checks your government ID (your IAM identity) against the building's guest list (the aws-auth ConfigMap, or the newer access entries) to learn which tenant you are, and only then do the house rules (Kubernetes RBAC) decide what that tenant may actually do. Fail the ID check and you're turned away at the desk — you were never let inside to be told "no, you can't do that."

ArchitectureThe managed control plane, your data plane, and the wire between

Here's the shape of it. Everything above the dashed line is AWS's problem; everything below is yours. The two are joined by the endpoint (how you reach the API) and by cross-account network interfaces (how the control plane reaches back into your VPC for things like kubectl exec, logs, and admission webhooks).

The second picture is the one that trips people up most, because nothing about it looks like vanilla Kubernetes: how a kubectl call proves who you are. EKS bolts an AWS-IAM front door onto the standard Kubernetes webhook token authenticator.

Internal workingWhat AWS runs, your compute choices, and the identity handshake

1 · What AWS actually runs for you

When you create a cluster, AWS provisions a dedicated Kubernetes control plane in an account it owns — not shared with your other clusters. It runs the API server on at least two instances behind an AWS-managed load balancer, keeps etcd across three availability zones with automated backups, and runs the scheduler and controller manager. It rotates the internal certificates, patches the OS, scales the API servers under load, and replaces any instance that fails. You are charged a flat hourly fee per cluster for this, on top of your data-plane compute. What AWS does not do is run your workloads or your nodes — that's the line the whole chapter turns on.

You can turn on control-plane logging to CloudWatch for five log types — api, audit, authenticator, controllerManager, and scheduler. The authenticator log is the one you'll grep during an access incident: it records every IAM-principal-to-Kubernetes-identity decision the front door makes.

2 · Your three data-plane options

The nodes are yours, and EKS gives you three ways to run them. The choice is a trade of control against toil:

OptionWho runs the machineReach for it when
Managed node groupAWS runs the EC2 Auto Scaling group, supplies the EKS-optimised AMI, and cordons+drains nodes during a rolling update you trigger.You want normal EC2 nodes without hand-building the ASG, bootstrap, and upgrade dance. The default choice.
Self-managed nodesYou. Your own ASG, your own AMI (or a customised EKS AMI), your own bootstrap and upgrade automation.You need something the managed group won't do — a custom kernel, a special AMI, GPU quirks, Windows edge cases, bespoke bootstrap.
FargateAWS. Each pod runs in its own right-sized microVM; there is no node for you to see, patch, or scale.You want zero node management and per-pod isolation, and can accept its limits (no DaemonSets, no privileged pods, no host access, sized per pod).

There is now a fourth path, EKS Auto Mode, where AWS manages the compute, scaling, networking, and storage for you — it runs Karpenter and the core add-ons under the hood so you stop managing node groups at all. Treat it as "managed node groups plus autoscaling plus add-ons, operated by AWS." Under everything, though, the mechanics are still the kubelet, the runtime, and the CNI from Chapter 30 — Auto Mode doesn't change what a node is, only who babysits it.

3 · The authentication handshake, in detail

This is the part that has no analogue in vanilla Kubernetes, so slow down here. Your kubeconfig (written by aws eks update-kubeconfig) doesn't hold a static token. Instead it holds an exec block that runs aws eks get-token every time you call the cluster. That command uses your AWS credentials to build a presigned URL for sts:GetCallerIdentity and base64-encodes it into a bearer token that starts with k8s-aws-v1.. The token is short-lived (about 15 minutes) and proves one thing: "whoever holds this could call GetCallerIdentity as this IAM principal, right now."

  1. kubectl gets a token. The kubeconfig execs aws eks get-token --cluster-name X, which signs a GetCallerIdentity request with your IAM credentials and returns the k8s-aws-v1. token.
  2. kubectl sends it as a bearer token to the cluster endpoint over TLS, exactly like any Kubernetes token.
  3. The API server verifies it through EKS's webhook token authenticator: EKS actually executes that presigned GetCallerIdentity call against STS to confirm the token is genuine and to learn the caller's IAM ARN. A forged or expired token dies here.
  4. EKS maps the IAM ARN to a Kubernetes identity — a username and a set of groups — using either an access entry or the aws-auth ConfigMap (next section). No mapping, no identity.
  5. RBAC authorizes. Now it's plain Kubernetes: the resolved username/groups are checked against Roles and ClusterRoles. This is where a mapped-but-under-privileged user gets "forbidden" (as opposed to "Unauthorized").
"Unauthorized" and "Forbidden" are different failures

Two error messages, two entirely different fixes. "error: You must be logged in to the server (Unauthorized)" means step 3–4 failed: your IAM identity isn't mapped to any Kubernetes identity — no access entry, no aws-auth row. The front door didn't recognise you. "Error from server (Forbidden)" means steps 1–4 succeeded — you're a known Kubernetes user — but RBAC says that user can't do this action. Unauthorized is an identity-mapping problem (fix the access entry / aws-auth); Forbidden is an RBAC problem (fix the Role/binding). Read which word you got before touching anything.

4 · Two ways to grant access: aws-auth vs access entries

Step 4 above needs a mapping from IAM principal to Kubernetes identity, and EKS has two mechanisms. The original one is the aws-auth ConfigMap in kube-system: a YAML blob with mapRoles and mapUsers lists that pair an IAM ARN with a Kubernetes username and groups. It works, but it's a foot-gun — it lives inside the cluster, so a bad edit can lock everyone out, and there's no AWS-side audit of who has access. Node groups also depend on it: the node instance role is mapped here to system:bootstrappers and system:nodes so kubelets can register.

The newer, and now recommended, mechanism is access entries, managed through the EKS API itself (aws eks create-access-entry). An access entry associates an IAM principal with Kubernetes permissions in one of two ways: attach an access policy (an AWS-maintained permission template like AmazonEKSClusterAdminPolicy, AmazonEKSAdminPolicy, AmazonEKSEditPolicy, or AmazonEKSViewPolicy, optionally scoped to specific namespaces), or map the principal to Kubernetes groups and write your own RBAC. Because it lives in the EKS control plane, it's auditable in CloudTrail, editable even when you can't reach the Kubernetes API, and it can't be wiped by a fat-fingered ConfigMap edit.

Which is active is set by the cluster's authentication mode: CONFIG_MAP (aws-auth only — legacy), API_AND_CONFIG_MAP (both, access entries win — the migration sweet spot), or API (access entries only — the end state). You can move a cluster forward through those modes but not backward. New clusters should start at API; existing clusters should migrate their aws-auth rows to access entries and switch to API_AND_CONFIG_MAP, then API.

One migration gotcha worth knowing before it bites

When you enable access entries on an existing cluster, EKS auto-creates an entry only for the original cluster creator. Every other row in your aws-auth ConfigMap — the developer roles, the CI role, the service roles — is not migrated automatically. If you switch straight to API mode expecting parity, you'll lock those principals out. Migrate each row to an explicit access entry first, verify, then flip the mode.

5 · EKS add-ons

A bare cluster needs a few components to be useful: the VPC CNI for pod networking (Chapter 58), kube-proxy for Services, and CoreDNS for service discovery. You can install those yourself as plain manifests ("self-managed"), or let EKS install and version them as EKS add-ons — curated, AWS-tested packages you manage through the EKS API (aws eks create-addon). Add-ons are versioned against your Kubernetes version, can be upgraded with a defined conflict-resolution strategy, and can be wired to an IAM role for their AWS permissions. The common ones: VPC CNI, kube-proxy, CoreDNS, the EBS and EFS CSI drivers, and the EKS Pod Identity Agent. Using managed add-ons is the difference between "which random YAML version of the CNI is on this cluster?" and "the CNI is add-on v1.x, upgraded through the API, logged in CloudTrail."

Think first: your teammate can run kubectl get pods but you get "Unauthorized" with the same cluster and the same command. What's different, and where do you look?

Same command, same cluster, different IAM identity. Authentication on EKS is per-principal, so the variable is which AWS role/user each of you is. Your teammate's ARN is mapped (via an access entry or an aws-auth row) to a Kubernetes identity; yours isn't. Confirm your own identity first with aws sts get-caller-identity — you may be assuming a different role than you think (a common cause: a stale profile, or update-kubeconfig written with --role-arn pointing at a role you can't assume). Then check whether that exact ARN has a mapping: aws eks list-access-entries --cluster-name X and, if the cluster still uses it, the aws-auth ConfigMap. The fix is to add an access entry for your ARN — not to touch RBAC, because RBAC was never reached. "Unauthorized" is always an identity-mapping story.

ComponentsThe pieces, named

  • The managed control plane — API server, etcd, scheduler, controller manager, in an AWS account, multi-AZ. Owns: serving the Kubernetes API and keeping cluster state durable. You never log into it.
  • The cluster endpoint — the HA URL you point kubectl at. Can be public, private (reachable only from your VPC/peered networks), or both. Owns: being the one door into the API.
  • Cross-account ENIs — elastic network interfaces EKS places in your subnets so the control plane can reach your pods for exec, logs, port-forward, and admission webhook calls. Owns: the control-plane-to-node direction of traffic.
  • Node groups / Fargate profiles — your compute. Managed node groups and self-managed nodes are EC2; Fargate profiles select which pods run serverless. Owns: actually running your containers.
  • The cluster IAM role and the node IAM role — the control plane's role (to manage AWS resources on your behalf) and the nodes' instance role (with AmazonEKSWorkerNodePolicy and image-pull permissions). Owns: the clusters' and nodes' own AWS permissions.
  • The OIDC provider — the cluster's identity issuer, registered in IAM, that makes IRSA possible (Chapter 55). Owns: letting pods assume IAM roles.
  • Access entries / aws-auth — the IAM-to-Kubernetes identity mapping. Owns: who gets in and as whom.
  • Add-ons — AWS-managed installs of CNI, kube-proxy, CoreDNS, CSI drivers, Pod Identity Agent. Owns: the cluster's baseline plumbing.

Data flowFollowing one kubectl get pods

You type kubectl get pods -n prod against an EKS cluster. Here's every hop:

  1. kubectl reads your kubeconfig, sees the exec credential plugin, and runs aws eks get-token. That signs a GetCallerIdentity request with your current AWS credentials and returns a k8s-aws-v1. bearer token.
  2. kubectl opens TLS to the cluster endpoint and sends GET /api/v1/namespaces/prod/pods with that bearer token.
  3. The API server hands the token to the EKS authenticator, which executes the presigned STS call, confirms it's valid, and extracts your IAM ARN.
  4. EKS looks up an access entry (or aws-auth row) for that ARN and resolves it to a Kubernetes username and groups — say, group view-only.
  5. RBAC checks: does view-only have get/list on pods in prod? If yes, the request proceeds; if no, you get "Forbidden."
  6. The API server reads the pod list from etcd (managed by AWS) and returns it. If you'd asked for kubectl logs, the API server would instead reach your pod through a cross-account ENI — the reverse direction.

Hands-onLabs — build, understand, break, troubleshoot

The AWS-specific labs assume you can create a cluster (eksctl create cluster gives you one in ~15 minutes) and have the AWS CLI configured. Each lab notes a local alternative you can run on kind when you don't have an account handy — the identity flow is EKS-specific, but the Kubernetes side (RBAC, ConfigMaps) is identical.

bash
# AWS path: a small cluster to explore (managed node group, 2 nodes).
eksctl create cluster --name lab57 --nodes 2 --node-type t3.small --version 1.31

# Local alternative for the Kubernetes-side labs:
kind create cluster --name lab57
Lab 1Build — read the control plane you don't ownBuild

describe-cluster is the single most useful EKS command: it shows the endpoint, version, the managed-vs-yours boundary, and the OIDC issuer, without touching Kubernetes at all.

bash
aws eks describe-cluster --name lab57 \
  --query 'cluster.{version:version,endpoint:endpoint,status:status,oidc:identity.oidc.issuer,authMode:accessConfig.authenticationMode}'
Output{ "version": "1.31", "endpoint": "https://A1B2C3.gr7.us-east-1.eks.amazonaws.com", "status": "ACTIVE", "oidc": "https://oidc.eks.us-east-1.amazonaws.com/id/A1B2C3...", "authMode": "API_AND_CONFIG_MAP" }

That endpoint is the wall socket from the analogy — the only thing AWS exposes of the control plane. The OIDC issuer is what makes IRSA possible. The auth mode tells you whether access entries, aws-auth, or both are in force. Local alternative: on kind the analogue is kubectl cluster-info and kubectl config view --minify — same idea (an endpoint URL and a credential), minus the AWS managing it for you.

Lab 2Understand — watch the IAM handshake happenUnderstand

See the token your kubeconfig actually sends, and confirm which IAM identity you are. These two facts explain almost every access surprise.

bash
aws sts get-caller-identity            # WHO am I to AWS right now?
aws eks get-token --cluster-name lab57 | head -c 120 ; echo
kubectl config view --minify -o jsonpath='{.users[0].user.exec.command} {.users[0].user.exec.args}{"\n"}'
Output (trimmed){ "Arn": "arn:aws:iam::111122223333:role/Admin/alice" } {"kind":"ExecCredential","status":{"token":"k8s-aws-v1.aHR0cHM6Ly9zdHMu... aws [eks get-token --cluster-name lab57 --output json]

Read it top to bottom: AWS knows you as that ARN; kubectl turns that identity into a k8s-aws-v1. token on every call; the kubeconfig proves it does so by exec-ing the CLI rather than storing a static secret. The token is a base64 presigned STS URL — decode it and you'll literally see sts.amazonaws.com/?Action=GetCallerIdentity. Local alternative: kind uses a client certificate instead of an exec plugin — inspect it with the same kubectl config view --minify to contrast a static credential with EKS's dynamic one.

Think first: why does EKS use a short-lived presigned STS URL as the token instead of a long-lived static token like a plain Kubernetes ServiceAccount?

Because it makes AWS IAM the single source of truth for human access and avoids a standing secret. A static token, if leaked, is valid until someone notices and rotates it. The presigned URL expires in about 15 minutes and carries no secret material of its own — it's a signature over a request that only your IAM credentials could have produced. So access follows your IAM identity automatically: disable the IAM principal and the cluster access dies with it, no per-cluster token to hunt down. It also means every human's cluster access inherits IAM's controls — MFA, permission boundaries, CloudTrail — for free. The trade is that you depend on STS being reachable and on the CLI/credentials being present, which is why "my token expired" or "wrong profile" shows up as an auth failure rather than an RBAC one.

Lab 3Break — get yourself "Unauthorized"Break

Reproduce the classic failure on purpose. Assume (or create) an IAM role that has no mapping on the cluster, point kubectl at it, and call the API.

bash
# Write a kubeconfig entry that authenticates as an unmapped role:
aws eks update-kubeconfig --name lab57 --alias lab57-stranger \
  --role-arn arn:aws:iam::111122223333:role/some-unmapped-role
kubectl --context lab57-stranger get pods
Outputerror: You must be logged in to the server (Unauthorized)

The token was valid — AWS happily proved you can assume that role — but EKS found no Kubernetes identity for its ARN, so you never reached RBAC. Before revealing, ask yourself: which of the two error words did you get, and what does that alone tell you to fix?

Reveal the diagnosis

The word is Unauthorized, so this is an identity-mapping failure, not an RBAC one — do not go editing Roles. Confirm the role has no entry and confirm which ARN you're actually presenting:

bash
aws eks list-access-entries --cluster-name lab57
kubectl --context lab57-stranger config view --minify \
  -o jsonpath='{.users[0].user.exec.args}{"\n"}'   # shows the --role-arn in play

If the role ARN isn't in the access-entries list (and isn't in aws-auth), that's your whole story: EKS doesn't know who this is. The fix is Lab 4 — add an access entry. The habit: on any "Unauthorized" from EKS, run aws sts get-caller-identity first to see who you really are, then check the mappings for that exact ARN. Nine times out of ten it's the wrong profile/role, not a cluster problem.

Lab 4Troubleshoot — grant access with an access entryTroubleshoot

Fix Lab 3 the modern way — no ConfigMap edits. Create an access entry for the role and attach a read-only access policy scoped to the whole cluster.

bash
ROLE=arn:aws:iam::111122223333:role/some-unmapped-role
aws eks create-access-entry --cluster-name lab57 --principal-arn $ROLE
aws eks associate-access-policy --cluster-name lab57 --principal-arn $ROLE \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSViewPolicy \
  --access-scope type=cluster
kubectl --context lab57-stranger get pods -A | head
OutputNAMESPACE NAME READY STATUS RESTARTS AGE kube-system aws-node-4t8bx 1/1 Running 0 12m kube-system coredns-6f9-abcde 1/1 Running 0 14m

Now the same role that got "Unauthorized" can list pods — because EKS resolves its ARN to a Kubernetes identity and the AmazonEKSViewPolicy grants read access. Try kubectl delete pod as this role and you'll get Forbidden instead: mapped identity, but the view policy doesn't allow writes. That's the two-step in action. Local alternative: on kind you can't use access entries, but you can model the same authorization half — create a ServiceAccount, bind it to the built-in view ClusterRole, and see the identical "can list, can't delete" behaviour.

Lab 5Production challenge — you locked everyone outSenior challenge

The nightmare: someone edited the aws-auth ConfigMap and removed a needed row, or switched the cluster to API auth mode without migrating all the aws-auth entries, and now the whole team gets "Unauthorized." No one can kubectl in to fix it — the fix normally lives inside the very API you're locked out of. What do you do?

Reveal the recovery paths

This is exactly the failure access entries were built to survive, because they live in the EKS control-plane API, not inside Kubernetes. From any principal with EKS IAM permissions (eks:CreateAccessEntry, eks:AssociateAccessPolicy) you can restore access without touching the Kubernetes API at all:

bash
MYARN=$(aws sts get-caller-identity --query Arn --output text)
aws eks create-access-entry --cluster-name lab57 --principal-arn $MYARN
aws eks associate-access-policy --cluster-name lab57 --principal-arn $MYARN \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy \
  --access-scope type=cluster

That grants you cluster-admin through the AWS side and you're back in. Two things make this work as a break-glass: the cluster must be in API or API_AND_CONFIG_MAP mode (so access entries are honoured), and the original cluster creator's identity always retains an auto-created admin access entry — so worst case, whoever created the cluster can always get in. This is the single best argument for migrating off pure aws-auth: with CONFIG_MAP-only mode, a bad ConfigMap edit can leave you with no AWS-side lever, and recovery means an AWS support case. Clean up: eksctl delete cluster --name lab57 (and kind delete cluster --name lab57).

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · "you must be logged in to the server (Unauthorized)"

Symptom: every kubectl command returns Unauthorized, often right after a role change, a new CI pipeline, or an auth-mode migration. First cut: aws sts get-caller-identity — are you even the ARN you think you are? A wrong profile or an un-assumable --role-arn in the kubeconfig is the most common cause. Confirm: is that exact ARN in aws eks list-access-entries (or the aws-auth ConfigMap)? Usual cause: the principal was never mapped, or an aws-auth row was dropped during a migration. Fix: add an access entry for the ARN. Do not touch RBAC — "Unauthorized" means RBAC was never reached.

Incident pattern · nodes stuck NotReady / never join the cluster

Symptom: EC2 instances launch but never appear in kubectl get nodes, or appear and stay NotReady. First cut: on a node, journalctl -u kubelet — you'll often see the kubelet failing to register with an auth error. Usual causes: the node instance role isn't mapped (missing system:bootstrappers/system:nodes in aws-auth, or no EC2 access entry), the role lacks AmazonEKSWorkerNodePolicy, or the nodes can't reach the endpoint (security group / private-endpoint / no route). Confirm: node role policies, the mapping, and endpoint reachability from the node subnet. With managed node groups on access-entry clusters, EKS creates the node mapping for you — a big reason to prefer them.

Incident pattern · "the cluster is up but I can't reach it from my laptop"

Symptom: the cluster is ACTIVE and colleagues in the office VPN can use it, but you time out connecting to the endpoint. Usual cause: the endpoint is configured private-only (or public access is restricted to an allow-list of CIDRs that doesn't include you). Confirm: aws eks describe-cluster --query 'cluster.resourcesVpcConfig' and read endpointPublicAccess, endpointPrivateAccess, and publicAccessCidrs. Fix: connect through the VPC (VPN, bastion, or SSM) for a private endpoint, or add your CIDR to the public allow-list — deliberately, since widening public access is a security decision, not a convenience one.

Production · security · performanceWhat matters in production

Lock the endpoint down on purpose. A brand-new cluster defaults to a public endpoint reachable from anywhere (still IAM-authenticated, but reachable). For anything real, enable private access and either disable public access or restrict it to known CIDRs. The pattern most teams settle on is a private endpoint reached over VPN or SSM, with the control-plane logs shipping to CloudWatch so you keep an audit trail.

Treat access as least-privilege and auditable. Migrate off the aws-auth ConfigMap to access entries and move the cluster to API auth mode. Grant humans the narrowest access policy that works — AmazonEKSViewPolicy for most, namespace-scoped AmazonEKSEditPolicy for app teams, and AmazonEKSClusterAdminPolicy for a small break-glass set. Because access entries are IAM-native, you get CloudTrail records of who was granted what, which is the difference between passing and failing an access review.

Plan upgrades; they're not optional. AWS supports each Kubernetes minor version for a bounded window (roughly 14 months of standard support before extended-support surcharges), so you're upgrading about every year whether you like it or not. Upgrade the control plane first, then the node groups, and test against the deprecated-API warnings before you go — a minor bump can remove an API your manifests still use. Managed node groups make the node half a rolling, cordon-and-drain operation instead of a hand-built one.

Prefer managed add-ons and managed node groups. Managed add-ons give you versioned, API-driven, CloudTrail-logged CNI/kube-proxy/CoreDNS instead of drifting manifests, and managed node groups handle bootstrap and upgrades and wire up node access for you. Common mistakes: leaving a wide-open public endpoint; running CONFIG_MAP-only auth so a bad ConfigMap edit can lock everyone out with no AWS-side recovery; forgetting that the node role needs both the EKS worker policy and image-pull permissions; and assuming "managed" means you never upgrade.

System-design connectionWhere this reaches into architecture

EKS is the textbook example of a shared-responsibility boundary, and drawing that boundary is a design skill you'll use far beyond Kubernetes. AWS took the hardest-to-run, highest-blast-radius component — a replicated, consensus-backed control plane — and turned it into a service with an SLA, leaving you the part that's genuinely yours: your workloads and the compute under them. When you architect any platform, the same question applies: which components are undifferentiated heavy lifting you should buy as a managed service, and which are your actual product? The seams EKS exposes — an endpoint and an identity handshake — are also a lesson in interface design under a trust boundary: two parties that don't share an account still need a crisp, auditable contract for "who are you" (IAM + STS) and "how do we reach each other" (the endpoint and cross-account ENIs). That authentication-then-authorization split — one system proves identity, a different system decides permissions — is the same pattern you'll design into any multi-tenant service, and getting the two stages cleanly separated is what lets you reason about "Unauthorized" versus "Forbidden" instead of one muddy "access denied." It connects forward to Chapter 55, where the same OIDC-and-STS machinery lets your pods assume IAM roles.

30-secWhat does EKS manage, and what do you still own?

EKS manages the Kubernetes control plane — the API server, etcd, scheduler, and controller manager — in an AWS-owned account, spread across three AZs, patched, scaled, and backed up by AWS, exposed to you only as a highly-available API endpoint. You own everything below that line: the VPC, the nodes (managed node groups, self-managed, or Fargate), the workloads, the add-ons, and the IAM and networking that connect it all. The Kubernetes itself is unchanged; EKS just converts the control plane into a managed service and wraps it in an IAM front door.

2-minWalk me through how kubectl authenticates to an EKS cluster.

The kubeconfig doesn't hold a static token; it holds an exec block that runs aws eks get-token on every call. That command uses your AWS credentials to build a presigned URL for sts:GetCallerIdentity and base64-encodes it into a bearer token starting with k8s-aws-v1., valid about 15 minutes. kubectl sends it to the endpoint over TLS. The API server passes it to EKS's webhook authenticator, which actually executes that presigned STS call to verify the token is genuine and to learn the caller's IAM ARN. EKS then maps that ARN to a Kubernetes username and groups using either an access entry or the aws-auth ConfigMap. Finally, plain Kubernetes RBAC authorizes the resolved identity. The key insight is that this is two separate stages: AWS decides who you are, Kubernetes decides what you may do. So "Unauthorized" means the identity mapping failed — RBAC was never reached — while "Forbidden" means you were recognised but RBAC said no. That one distinction resolves most EKS access incidents.

DeepCompare the aws-auth ConfigMap with access entries. Why did AWS build the second one?

Both map an IAM principal to a Kubernetes identity for step 4 of authentication. The aws-auth ConfigMap is the original mechanism: a YAML object in kube-system with mapRoles/mapUsers lists. Its problems are structural — it lives inside the cluster, so a bad edit can lock everyone out with no AWS-side recovery; there's no CloudTrail audit of access grants; and it's just free-form YAML with no validation. Access entries move this into the EKS control-plane API: you manage them with aws eks create-access-entry, attach AWS-maintained access policies (ClusterAdmin, Admin, Edit, View) optionally scoped to namespaces, and it's all IAM-native — auditable in CloudTrail, editable even when the Kubernetes API is unreachable, and impossible to wipe with a ConfigMap edit. The auth mode controls which is live: CONFIG_MAP, API_AND_CONFIG_MAP, or API, moving forward only. AWS built access entries mainly to kill the lockout foot-gun and to make cluster access a first-class, auditable IAM concept. The migration gotcha: enabling access entries only auto-creates an entry for the original cluster creator, so you must migrate every other aws-auth row by hand before switching to API-only.

ScenarioNew nodes launch but never join the cluster. How do you debug it?

I'd split it into "can the node authenticate and register?" and "can the node reach the control plane?" First, on the node (or its console/SSM), journalctl -u kubelet — the kubelet almost always logs why registration fails. If it's an auth error, the node instance role either isn't mapped to system:bootstrappers/system:nodes (in aws-auth) or lacks an EC2 access entry, or the role is missing AmazonEKSWorkerNodePolicy and image-pull permissions — I'd check the role's policies and the mapping. If instead the kubelet can't reach the API at all, it's networking: the node's security group or the cluster security group, a private-only endpoint the node subnet can't route to, or missing outbound to the endpoint. I'd verify endpoint reachability from the node subnet and the security-group rules between nodes and control plane. Managed node groups on access-entry clusters wire the node mapping automatically, so if I'm hand-rolling self-managed nodes I'd suspect the mapping first; if it's a managed group, I'd suspect networking or the role policies first.

Follow-upWhen would you pick Fargate over managed node groups, and what do you give up?

Fargate when I want zero node management and per-pod isolation — no OS to patch, no ASG to size, and each pod in its own microVM, which is attractive for spiky or untrusted workloads and small teams. You pay per pod-resource rather than per node, which can be cheaper for bursty low-density workloads and pricier for steady high-density ones. What you give up is real: no DaemonSets (so node-level agents like some log shippers or the standard CNI/kube-proxy model don't apply the same way), no privileged pods or host access, no GPUs, sizing fixed per pod, and slower cold starts since each pod provisions a microVM. So Fargate for isolation and no-ops; managed node groups when you need DaemonSets, custom AMIs, GPUs, host access, or the density economics of packing many pods per node. Many clusters run both — Fargate for a few isolated or bursty services, managed node groups for the bulk.

RetainQuick revision

EKS runs the Kubernetes control plane — API server, etcd, scheduler, controller manager — in an AWS-owned account across three AZs, and exposes it to you as one HA endpoint; you own the VPC, the nodes, and the workloads. Your compute is managed node groups (the default), self-managed nodes (most control, most toil), or Fargate (no nodes, per-pod microVMs), with EKS Auto Mode as an AWS-operated option on top. Authentication is AWS IAM: kubectl runs aws eks get-token to build a short-lived presigned STS token, EKS verifies it and resolves your IAM ARN to a Kubernetes identity via an access entry or the aws-auth ConfigMap, and only then does RBAC authorize — so "Unauthorized" is an identity-mapping failure and "Forbidden" is an RBAC failure. Access entries are the modern, IAM-native, auditable, lockout-resistant replacement for aws-auth; auth modes move forward CONFIG_MAP → API_AND_CONFIG_MAP → API only. Add-ons (CNI, kube-proxy, CoreDNS, CSI, Pod Identity Agent) are best run as versioned EKS-managed add-ons. When access breaks, read the error word, run aws sts get-caller-identity, and check the mapping for that exact ARN.

The 10 things to remember

  1. EKS manages the control plane (API server, etcd, scheduler, controller manager) multi-AZ; you own the data plane.
  2. The control plane is exposed only as an endpoint (public and/or private) plus cross-account ENIs into your subnets.
  3. Data-plane options: managed node groups (default), self-managed nodes, Fargate; EKS Auto Mode operates compute for you.
  4. Auth is IAM: aws eks get-token makes a short-lived presigned sts:GetCallerIdentity token (k8s-aws-v1.).
  5. EKS verifies the token, resolves the IAM ARN to a Kubernetes user+groups, then RBAC authorizes — two stages.
  6. "Unauthorized" = identity not mapped (fix access entry/aws-auth); "Forbidden" = mapped but RBAC denies.
  7. Access entries (EKS API, auditable, lockout-resistant) are the modern replacement for the aws-auth ConfigMap.
  8. Auth modes go forward only: CONFIG_MAP → API_AND_CONFIG_MAP → API; only the creator's entry auto-migrates.
  9. Nodes that never join usually mean an unmapped node role, a missing worker policy, or no route to the endpoint.
  10. Lock the endpoint down, ship control-plane logs to CloudWatch, and plan a Kubernetes upgrade roughly yearly.
