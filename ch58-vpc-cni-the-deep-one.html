Part VI · AWS & EKS for SREs · Chapter 58

VPC CNI: the deep one

On EKS a pod's IP isn't a made-up overlay address — it's a real, routable VPC IP, handed out by the Amazon VPC CNI. That single design choice makes pods first-class citizens of your network and also makes them run out of addresses. This is the chapter where Part V's packet knowledge and Part VI's AWS knowledge fuse into one line you can trace end to end.

Start: Beginner→→→End: Staff-level ~55 min read · AWS CLI + a node shell (kind for contrast)

By the end of this chapter you can

  • Explain why every EKS pod gets a real VPC IP, and what that buys and costs you.
  • Compute a node's max pods in both secondary-IP mode and prefix-delegation mode, from the instance type.
  • Describe the warm-IP pool and why ipamd pre-allocates addresses.
  • Trace a packet from a pod's network namespace all the way to a VPC route table and Security Group.
  • Diagnose "failed to assign an IP address" — telling node exhaustion apart from subnet exhaustion — and fix it with prefix delegation or more address space.

Why this exists · the problemPods need IPs, and AWS gives them real ones

Back in Chapter 41 you learned the Kubernetes rule: every pod gets its own IP, and every pod can reach every other pod without NAT. A CNI plugin makes that true. Most CNIs build an overlay — they invent a private pod network (say 10.244.0.0/16) that lives on top of the real network and tunnel pod traffic between nodes. The pod IPs are fictional as far as the underlying network is concerned; the VPC never sees them.

The Amazon VPC CNI takes the opposite approach, and it's the thing that makes EKS networking unusual. It gives each pod a real private IP from your VPC subnet — the same address space your EC2 instances, RDS databases, and load balancers use. There's no overlay and no tunnel. A pod at 10.0.1.23 is, to the VPC, indistinguishable from any other network interface at 10.0.1.23.

That buys you a lot. A pod can talk straight to an RDS instance with no gateway in between. An Application Load Balancer can send traffic directly to a pod's IP. VPC Flow Logs, Security Groups, and route tables all apply to pod traffic because it is VPC traffic. You get one flat, observable network instead of a network-inside-a-network.

It also costs you something real, and this is the half that becomes your incident: pods consume actual VPC IP addresses, and VPCs have a finite supply. Subnets are sized in CIDR blocks; a /24 has 251 usable addresses, and every pod eats one. Pack the cluster densely enough, or size the subnets carelessly enough, and you hit a wall that overlay users never see — pods stuck in ContainerCreating with the message failed to assign an IP address to container. This chapter is how that IP gets assigned, how the supply is managed, and what to do when it runs dry.

Key point

The VPC CNI trades address abundance for network simplicity. Overlays give you effectively unlimited pod IPs but a second network to reason about; the VPC CNI gives you one flat network where pods are real VPC endpoints — at the price of planning your address space as carefully as you plan compute. Almost every hard EKS networking problem is a consequence of that trade.

Mental model · analogyThe mental model: real phone extensions, not internal codes

Real-world analogy

Imagine an office building where the phone company owns a block of real, dialable extensions — say 555-0100 through 555-0355 for one floor (that's your subnet CIDR). Every desk, printer, and contractor phone gets a genuine extension from that block, not a made-up internal code. That's the VPC CNI: pods get real numbers anyone in the building — or the phone company's records — can see and route to.

The office manager (the CNI's ipamd daemon) doesn't call the phone company each time a contractor arrives; that call is slow. Instead the manager keeps a small stash of pre-activated spare extensions in a drawer (the warm-IP pool) so a new contractor gets a working phone in seconds. Each wall panel on the floor (an ENI) has a fixed number of jacks; fill a panel and the manager installs another, up to the building's wiring limit (the instance type's max ENIs).

Two ways to run dry. A single floor's panels fill up — no more jacks on this floor even though the desk is empty (node IP exhaustion: the instance hit its ENI/IP limit). Or the phone company's whole block for the floor is used up — no numbers left to hand anyone (subnet exhaustion). Prefix delegation is the manager negotiating extensions in blocks of 16 at a time instead of one at a time: one jack now backs sixteen phones, so panels fill far more slowly and the manager rarely calls the phone company.

ArchitectureStitching a pod to the VPC

Here is the whole line, from a process inside a pod to a destination out in the VPC. Follow it once slowly; every EKS networking incident lives somewhere on this path. The pod's eth0 is one end of a veth pair; the other end sits in the host network namespace, where per-ENI policy routing sends the packet out the right elastic network interface. The pod's IP is a secondary IP (or an IP from a delegated prefix) on that ENI. From the ENI, normal VPC routing takes over — the subnet route table decides local-VPC versus internet — and a Security Group is enforced right at the ENI.

The other picture you need is the one that decides how many pods a node can hold. Each ENI has a fixed number of IP slots set by the instance type. In the default mode, each slot holds one IP. In prefix mode, each slot holds a /28 — sixteen IPs. Same ENIs, same slot count, sixteen times the pods:

Internal workingENIs, the warm pool, prefixes, and where the IPs run out

1 · ENIs and secondary IPs — the base model

The CNI runs on every node as the aws-node DaemonSet. Inside it is ipamd (the IP-address-management daemon) and, dropped onto the host, the CNI binary at /opt/cni/bin/aws-cni. When a node boots, ipamd attaches a primary elastic network interface and asks EC2 for a batch of secondary IP addresses on it. Each ENI's first IP is the interface's own primary address (used by the node); the rest are the pool ipamd hands to pods.

Every instance type caps two numbers: how many ENIs it can attach, and how many IPs each ENI can hold. An m5.large allows 3 ENIs of 10 IPs each; a t3.medium allows 3 ENIs of 6 IPs. From those two numbers you get the node's pod ceiling in the default mode:

text
max pods = (ENIs × (IPs_per_ENI − 1)) + 2

m5.large:   (3 × (10 − 1)) + 2 = 29 pods
t3.medium:  (3 × ( 6 − 1)) + 2 = 17 pods
t3.small:   (3 × ( 4 − 1)) + 2 = 11 pods

The − 1 is the ENI's own primary IP, which pods don't use. The + 2 is for the two pods that run in the host's network namespace — aws-node and kube-proxy — and therefore don't draw an IP from the pool. That's the whole formula, and it explains a surprise every EKS beginner hits: a t3.small node with 2 vCPU and plenty of RAM refuses to schedule an 18th pod, not because it's out of CPU but because it's out of IPs.

2 · The warm-IP pool — why ipamd hoards addresses

Calling the EC2 API to assign an IP takes real time — hundreds of milliseconds, and attaching a whole new ENI can take up to ten seconds. If ipamd did that on the critical path of every pod start, pod launches would stall. So it keeps a warm pool: spare, already-assigned IPs sitting ready. When a pod lands, the CNI takes one from the pool instantly; in the background, ipamd tops the pool back up. Three environment variables tune the trade between fast launches and wasted addresses:

  • WARM_ENI_TARGET (default 1) — keep one entire spare ENI's worth of IPs ready. Fast, but on a big instance that can reserve dozens of IPs a node isn't using.
  • WARM_IP_TARGET — keep exactly this many spare IPs, regardless of ENI boundaries. Tighter on addresses.
  • MINIMUM_IP_TARGET — the floor of total IPs to hold, sized to your typical pods-per-node so a node comes up pre-warmed.

The default (WARM_ENI_TARGET=1) favours launch speed and can waste IPs — exactly the wrong default when your subnets are tight. Setting WARM_IP_TARGET and MINIMUM_IP_TARGET together is the classic knob for conserving a scarce address space, at the cost of occasionally waiting on an EC2 call.

3 · Prefix delegation — 16 IPs per slot

Prefix delegation (VPC CNI 1.9.0 and later, enabled with ENABLE_PREFIX_DELEGATION=true) changes what fills an ENI slot. Instead of assigning individual secondary IPs, ipamd assigns /28 IPv4 prefixes — a contiguous block of 16 addresses — and hands pod IPs out of those blocks. The instance's ENI and slot limits don't change, but each usable slot now backs 16 pods instead of 1. On a c5.large, whose ENI holds 10 IPs, a single ENI with no secondary IPs can carry up to 9 prefixes — 144 pod addresses from one ENI:

text
max pods (prefix) = (ENIs × (IPs_per_ENI − 1) × 16) + 2

c5.large, 1 ENI:  (1 × 9 × 16) + 2 = 146   →  capped in practice to 110
m5.large, 3 ENIs: (3 × 9 × 16) + 2 = 434   →  capped in practice to 110 (or 250)

Kubernetes itself recommends no more than 110 pods per node, so AWS's max-pods-calculator.sh caps the result (110 for smaller instances, up to 250 for large ones) rather than letting a single node try to run 400+ pods. Two operational facts matter. First, you must tell the kubelet the higher number explicitly — set --max-pods and --use-max-pods=false in the node's bootstrap, or the node keeps the old secondary-IP ceiling. Second, prefixes need contiguous /28 blocks; on a fragmented subnet, EC2 can refuse the allocation (more on that in the failure section). The payoff: far higher density, and far fewer EC2 API calls — attaching a prefix takes under a second versus up to ten for a new ENI. The default WARM_PREFIX_TARGET=1 keeps one spare prefix ready, which can leave up to 15 unused IPs per node — a fine trade unless addresses are precious.

You can't quietly downgrade out of prefix mode

Once prefix delegation is enabled and prefixes are attached to ENIs, you cannot downgrade the VPC CNI below 1.9.0 without deleting and recreating every node. And AWS recommends you don't do a rolling enable either: create fresh node groups with prefix mode on, drain the old ones, and delete them — because a node carrying both individual secondary IPs and prefixes reports inconsistent capacity, which confuses scheduling. Treat turning on prefix delegation as a node-group replacement, not an in-place toggle.

4 · Where the IPs actually run out

There are two distinct exhaustion points, and mixing them up sends you fixing the wrong thing:

  1. Node-level exhaustion. A node has hit its ENI/IP ceiling — every slot is used. A new pod scheduled there can't get an IP, so the CNI's ADD fails and the pod hangs in ContainerCreating with failed to assign an IP address to container. This usually means max-pods was set higher than the node's real IP capacity, so the scheduler placed more pods than the node could address. The fix is aligning max-pods to capacity, or prefix delegation for more room.
  2. Subnet-level exhaustion. The subnet's CIDR is used up — no free addresses left in the whole block. Now ipamd asks EC2 for more IPs and EC2 refuses with InsufficientFreeAddressesInSubnet. Every node in that subnet is affected, not just one. The fix is more address space: a bigger subnet, additional subnets, or the CNI's custom networking feature, which places pods on a separate secondary VPC CIDR (commonly the 100.64.0.0/10 carrier-grade NAT range) so pods stop competing with nodes and load balancers for the primary subnet's addresses.

Prefix delegation helps the first problem enormously (each node needs far fewer discrete allocations) and helps the second indirectly (fewer, larger allocations fragment the subnet less) — but if you've genuinely run the subnet dry, only more address space fixes it.

5 · The datapath, packet by packet

Now trace an outbound packet using the big diagram. A process in pod A (10.0.1.23) sends to another pod or to RDS. The packet leaves the pod's eth0, crosses the veth pair into the host network namespace, and hits the host's routing. Because the pod's IP is a secondary IP on a specific ENI, the CNI has installed an ip rule that steers this pod's traffic to that ENI's own route table — this is source-based policy routing, and it's what guarantees a pod's replies leave by the same ENI its address belongs to. The packet exits that ENI as ordinary VPC traffic. The ENI's Security Group is evaluated here (Security Groups are stateful and act at the interface — Chapter 51). Then the subnet's route table decides: destination inside the VPC CIDR goes local and reaches the target directly; 0.0.0.0/0 goes to the NAT gateway and out. For internet egress the CNI source-NATs the pod IP to the node's primary IP by default, so return traffic comes back to the node (set AWS_VPC_K8S_CNI_EXTERNALSNAT=true to disable that when you have your own return path — the subject of Chapter 48).

Think first: your pods can reach an RDS database in the same VPC, but an app team swears their pod IPs are "random" and keep changing. Are the pod IPs real, and why do they change?

They're entirely real VPC addresses — that's precisely why the pod can hit RDS with no gateway in between; the database sees a normal in-VPC client. They "change" because pods are ephemeral: every new pod gets a fresh IP from the node's warm pool, and when the pod dies the IP goes back. That's not randomness, it's the pod lifecycle. The lesson is the same one as everywhere in Kubernetes — never pin anything to a pod IP; use a Service (stable ClusterIP) or DNS name. The pod IP being real matters for reachability and security groups and flow logs, not for addressing a workload. If the RDS side wants to allow-list the cluster, allow-list the node/pod Security Group or the subnet CIDR, never individual pod IPs.

ComponentsThe pieces, named

  • aws-node DaemonSet — one pod per node, host-networked. Contains the init container that lays down the CNI binary and config, the ipamd daemon, and (in recent versions) the network-policy agent. Owns: all IP management on the node.
  • ipamd — the long-running daemon that attaches ENIs, requests secondary IPs or prefixes from EC2, keeps the warm pool, and answers the CNI binary over a local gRPC socket. Owns: the node's IP supply. Its log lives at /var/log/aws-routed-eni/ipamd.log.
  • The CNI binary (aws-cni) — invoked by the kubelet on pod create/delete. Asks ipamd for an IP, then wires the veth pair, addresses, and policy-routing rules. Owns: the per-pod plumbing. Its log is plugin.log in the same directory.
  • ENIs and their IPs/prefixes — the actual VPC interfaces and the addresses attached to them. Owns: being real, routable network endpoints.
  • The ENIConfig CRD — used by custom networking to map an availability zone to a specific subnet and Security Group, so pods get IPs from a secondary CIDR. Owns: the "pods on a different subnet than nodes" story.
  • Security Groups — applied at the ENI by default (all pods on a node share the node's SG). With security groups for pods (branch ENIs on supported Nitro instances), specific pods can get their own SG via a SecurityGroupPolicy. Owns: L3/L4 filtering of pod traffic.
  • eni-max-pods.txt — AWS's published table of ENI and IP limits per instance type, the source of every max-pods number. Owns: the ground truth for capacity math.

Data flowFollowing one pod as it gets an IP

A pod is scheduled to a node. Here's how it goes from "assigned" to "has a working VPC IP":

  1. The kubelet runs the pod sandbox and calls the CNI ADD for the new pod (the RunPodSandbox step from Chapter 30).
  2. The aws-cni binary asks ipamd over its local socket for a free IP.
  3. ipamd takes one from the warm pool and returns it instantly. If the pool is below target, it asynchronously asks EC2 for more IPs, or attaches a new ENI/prefix — off the critical path.
  4. The CNI creates the veth pair, moves one end into the pod's netns as eth0, assigns the IP, and installs the host-side ip rule and route so the pod's traffic uses the correct ENI.
  5. The pod now has a real VPC address and can send and receive immediately; its Security Group is the ENI's SG.
  6. If no IP is available (node or subnet exhausted), the ADD fails, the sandbox never completes, and the pod sits in ContainerCreating — the failure this whole chapter prepares you to read.

Hands-onLabs — build, understand, break, troubleshoot

These labs read real ENI and IP state, which only exists on EKS — so the AWS path is primary, with a local kind alternative noted for the parts that are conceptual rather than AWS-specific. Assume a cluster and a node instance ID handy (aws eks ... / kubectl get nodes -o wide).

Lab 1Build — see the real ENIs and IPs on a nodeBuild

Prove to yourself that pod IPs are VPC IPs living on ENIs. First from Kubernetes, then from EC2's own view of the same node.

bash
kubectl get pods -A -o wide | awk '{print $1,$2,$7}' | head   # pod IPs = VPC IPs
INSTANCE=$(kubectl get node NODE -o jsonpath='{.spec.providerID}' | awk -F/ '{print $NF}')
aws ec2 describe-network-interfaces \
  --filters Name=attachment.instance-id,Values=$INSTANCE \
  --query 'NetworkInterfaces[].{eni:NetworkInterfaceId,primary:PrivateIpAddress,secondary:PrivateIpAddresses[].PrivateIpAddress,prefixes:Ipv4Prefixes[].Ipv4Prefix}'
Output (trimmed)[ { "eni": "eni-0a1b...", "primary": "10.0.1.5", "secondary": ["10.0.1.5","10.0.1.23","10.0.1.24","10.0.1.25"], "prefixes": [] }, { "eni": "eni-0c2d...", "primary": "10.0.1.40", "secondary": ["10.0.1.40"], "prefixes": ["10.0.1.96/28"] } ]

Every pod IP from the first command appears as a secondary IP (or inside a /28 prefix) on one of these ENIs. That's the entire model in one screen: pods are addresses on real interfaces. Local alternative: on kind, kubectl get pods -A -o wide shows IPs like 10.244.0.x — a made-up overlay range. Try to find them with any cloud API and you can't, because they don't exist outside the node. Holding those two outputs side by side is the fastest way to feel the difference between an overlay and the VPC CNI.

Lab 2Understand — do the prefix-delegation mathUnderstand

The capacity numbers come straight from the instance type. AWS ships a script that reads the same eni-max-pods.txt table and applies both formulas — run it for one instance both ways and read the difference.

bash
# From the amazon-vpc-cni-k8s repo (runs locally; needs awscli + bash):
curl -sO https://raw.githubusercontent.com/awslabs/amazon-eks-ami/master/templates/al2/runtime/max-pods-calculator.sh
chmod +x max-pods-calculator.sh
./max-pods-calculator.sh --instance-type m5.large --cni-version 1.19.0
./max-pods-calculator.sh --instance-type m5.large --cni-version 1.19.0 --cni-prefix-delegation-enabled
Output29 110

Same instance: 29 pods in the default secondary-IP mode, 110 with prefix delegation (the raw formula gives 434, capped to the recommended 110). Confirm by hand from the table — m5.large is 3 ENIs × 10 IPs: (3 × 9) + 2 = 29, and (3 × 9 × 16) + 2 = 434 before the cap. Local alternative: this lab is pure arithmetic against a published table, so it runs anywhere — you don't need a cluster at all, only the instance type you plan to use. Do this before choosing node sizes: a fleet of tiny instances can starve for IPs long before it starves for CPU.

Think first: a team runs 50 small services on t3.small nodes and keeps seeing pods Pending or stuck ContainerCreating even though CPU and memory dashboards look half-empty. What's the likely ceiling?

IP address capacity, almost certainly. A t3.small caps at (3 × (4−1)) + 2 = 11 pods in the default mode — a tiny number that has nothing to do with CPU or memory. With 50 services plus their sidecars and system pods, they'll hit that per-node ceiling constantly, so pods either stay Pending (scheduler can't find a node under its max-pods) or land and fail the CNI ADD. The half-empty CPU/memory graphs are the tell: they're bottlenecked on addresses, not compute. Two fixes: turn on prefix delegation to lift the per-node ceiling roughly 10× (a t3.small goes from 11 toward the 110 cap), or move to fewer, larger nodes so each node's ENI/IP budget covers more pods. This is the single most common "my nodes look empty but nothing schedules" cause on EKS.

Lab 3Break — drive a node out of IPs and read the failureBreak

Reproduce node IP exhaustion deliberately. On a single small node (say a t3.small, ceiling 11), scale a deployment past what its IPs can cover and watch the CNI fail the extras.

bash
kubectl create deployment fill --image=nginx:1.27-alpine
kubectl scale deployment fill --replicas=25    # more than the node can address
kubectl get pods -l app=fill -o wide | grep -c Running
kubectl get pods -l app=fill | grep ContainerCreating | head -1
Output9 fill-7c9d5-xy12 0/1 ContainerCreating 0 40s

Some pods run; the rest wedge in ContainerCreating. Before revealing: where does the CNI record why it couldn't place them, and which of the two exhaustion types is this?

Reveal the diagnosis

The reason is on the pod as an Event, and the detail is in the CNI's plugin log on the node:

bash
kubectl describe pod fill-7c9d5-xy12 | sed -n '/Events/,$p'
# On the node (via a debug pod or SSM):
sudo tail -n 20 /var/log/aws-routed-eni/ipamd.log
OutputWarning FailedCreatePodSandBox ... failed to assign an IP address to container ipamd.log: "DataStore has no available IP/Prefix addresses"

This is node-level exhaustion: the instance hit its ENI/IP ceiling, ipamd's datastore is empty, and the CNI ADD failed. The subnet still has plenty of free IPs — only this node ran out of slots. The fix isn't more subnet space; it's more IP capacity per node (prefix delegation) or fewer pods per node (bigger instances, or a correct max-pods). Clean up: kubectl delete deployment fill. Local alternative: kind can't reproduce ENI exhaustion, but the shape — pod stuck ContainerCreating, reason in kubectl describe Events — is identical to the Chapter 30 sandbox failures, so the diagnostic reflex transfers directly.

Lab 4Troubleshoot — subnet exhaustion, the cluster-wide versionTroubleshoot

Now the nastier one: pods across many nodes start failing to get IPs at once, and new nodes come up but can't address their pods either. Investigate before assuming it's the same as Lab 3.

bash
SUBNET=subnet-0abc123
aws ec2 describe-subnets --subnet-ids $SUBNET \
  --query 'Subnets[].{cidr:CidrBlock,free:AvailableIpAddressCount}'
kubectl logs -n kube-system ds/aws-node -c aws-node | grep -i insufficient | tail
Output[ { "cidr": "10.0.1.0/24", "free": 0 } ] ipamd: "failed to allocate IP address: InsufficientFreeAddressesInSubnet"

The signal is unmistakable: AvailableIpAddressCount is 0 and ipamd is getting InsufficientFreeAddressesInSubnet from EC2. This is subnet-level exhaustion — the whole /24 is spent, so it hits every node in that subnet, and adding nodes makes it worse (each new node also wants IPs from the same dry subnet). The fix is address space, not node sizing: add subnets, use a larger CIDR, or enable custom networking so pods draw from a secondary VPC CIDR like 100.64.0.0/10. If instead you saw plenty of free subnet IPs but a single node failing, you'd be back in Lab 3's node-level case — which is exactly why you check the subnet's free count first. Local alternative: conceptual only on kind; the transferable skill is "one node failing vs every node failing" as the branch between node and subnet exhaustion.

Lab 5Production challenge — will this cluster fit, and how do you turn on prefixes safely?Senior challenge

You're asked to run 4,000 pods on EKS. Each AZ has one /24 pod subnet (251 usable). Nodes are m5.large. Work out whether it fits and design the rollout — before reading the answer.

Reveal the capacity plan

Does it fit? Three /24s give ~753 pod IPs total — nowhere near 4,000. Address space, not compute, is the binding constraint, so the plan is about IPs first. Step one, more space: enable custom networking and put pods on a secondary CIDR (a 100.64.0.0/10 block gives millions of addresses) so pods stop competing with nodes and load balancers for the primary subnets. Step two, density: turn on prefix delegation so each node addresses far more pods with fewer, larger allocations — 4,000 pods at ~110/node is ~37 nodes, and prefix mode keeps each node's allocations contiguous and cheap. Step three, roll it out safely: because you can't toggle prefixes in place, create new node groups with ENABLE_PREFIX_DELEGATION=true, --max-pods set to the prefix number, and --use-max-pods=false; protect workloads with PodDisruptionBudgets; then cordon and drain the old node groups and delete them. Step four, conserve: set WARM_PREFIX_TARGET=1 (or WARM_IP_TARGET if even one spare prefix is too wasteful) and reserve subnet CIDR space so /28 prefixes stay contiguous. The senior instinct here is to treat the VPC address plan as a capacity-planning exercise on par with CPU and memory — because on the VPC CNI it is.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · pods stuck ContainerCreating, "failed to assign an IP address"

Symptom: new pods sit in ContainerCreating; kubectl describe pod shows FailedCreatePodSandBox … failed to assign an IP address to container. First cut: is it one node or many? Check that node's IP usage against its ceiling, and the subnet's AvailableIpAddressCount. Usual cause: node-level — max-pods set above the node's real IP capacity, so the scheduler over-packed it. Confirm: /var/log/aws-routed-eni/ipamd.log saying the datastore has no addresses. Fix: align max-pods to capacity or enable prefix delegation; don't just add nodes if the cause is per-node.

Incident pattern · subnet exhaustion — InsufficientFreeAddressesInSubnet

Symptom: pods fail to get IPs across many nodes at once, and new nodes don't help. First cut: aws ec2 describe-subnets — is AvailableIpAddressCount at or near 0? Confirm: aws-node logs showing InsufficientFreeAddressesInSubnet. Cause: the pod subnet's CIDR is spent — often because pods, nodes, and load balancers all draw from the same small subnets. Fix: add subnets or a larger CIDR, and adopt custom networking to move pods onto a secondary CIDR (e.g. 100.64.0.0/10). Adding nodes without adding addresses makes it worse.

Incident pattern · prefix attach fails — InsufficientCidrBlocks

Symptom: after enabling prefix delegation, some nodes still can't get IPs and the CNI log shows InsufficientCidrBlocks: There are not enough free cidr blocks in the specified subnet to satisfy the request. Cause: the subnet is fragmented — plenty of scattered free IPs, but no contiguous /28 block to hand out as a prefix. Confirm: the subnet has free addresses yet prefix allocation fails. Fix: use VPC subnet CIDR reservations to set aside contiguous space for prefixes, or dedicate a fresh subnet to prefix-mode nodes. This is the failure mode unique to prefix delegation, and it's about contiguity, not raw free count.

Production · security · performanceWhat matters in production

Plan the address space before the cluster, not after. The VPC CNI turns IP planning into capacity planning. Size pod subnets for the pod count you'll grow into, keep pods on their own subnets (ideally a large secondary CIDR via custom networking) so they don't fight nodes and load balancers for addresses, and reserve contiguous space if you'll use prefixes. Retrofitting address space onto a running cluster is far more painful than getting it right up front — you often end up rebuilding node groups.

Default to prefix delegation for density, and set max-pods to match. For most clusters prefix delegation is the right default: higher pod density, fewer EC2 API calls, faster launches. Just remember it's a node-group replacement, not a toggle, and that the kubelet needs the explicit --max-pods and --use-max-pods=false or it keeps the old ceiling. Tune WARM_PREFIX_TARGET/WARM_IP_TARGET to trade launch speed against wasted addresses in tight subnets.

Know your Security Group model. By default every pod on a node shares the node's Security Group, so pod-to-pod filtering isn't SG-based — that's what NetworkPolicy is for (Chapter 47). When compliance genuinely needs per-pod Security Groups, the CNI's security-groups-for-pods feature assigns a branch ENI per pod on supported Nitro instances via a SecurityGroupPolicy — powerful, but it consumes branch-ENI capacity and adds complexity, so use it where you must, not everywhere.

Watch the right signals and avoid the classic mistakes. Alert on per-node IP utilisation and per-subnet AvailableIpAddressCount — both lead the ContainerCreating symptom by minutes. Keep the CNI add-on current (managed add-on, upgraded one minor version at a time). Common mistakes: setting max-pods above real IP capacity; running everything in a couple of small shared subnets; leaving WARM_ENI_TARGET=1 on tiny subnets and wondering where the IPs went; treating prefix delegation as an in-place toggle; and allow-listing individual pod IPs on a database instead of a Security Group or subnet.

System-design connectionWhere this reaches into architecture

The VPC CNI is a clean case study in a recurring design decision: flat native addressing versus an overlay. Giving every pod a real, routable address buys you a single observable network, direct integration with the rest of the platform (databases, load balancers, flow logs, security groups), and no tunnelling overhead on the datapath — at the cost of coupling your workload scale to a finite, carefully-planned address space. Overlays make the opposite trade: effectively unlimited pod IPs and freedom from VPC address planning, but a second network to operate and debug, plus encapsulation cost. Neither is universally right; the choice depends on whether you value network transparency and integration (native) or address abundance and decoupling (overlay). The warm-IP pool is another portable pattern — amortising a slow, rate-limited backend (the EC2 API) behind a local cache — the same shape as a connection pool or a DNS cache, where you pre-provision to keep a slow dependency off the request's critical path and accept some waste for latency. And the whole chapter is a reminder that at scale, the address space is a capacity dimension as real as CPU and memory: systems that treat IPs as infinite eventually meet a wall, and the ones that plan for it — subnet sizing, secondary CIDRs, prefix density — scale smoothly. That planning connects directly to Chapter 48's egress story and to Chapter 60, where these pod IPs become the direct targets of a load balancer.

InterviewInterview questions & answers

Answer each in your head before opening it.

30-secWhat makes the Amazon VPC CNI different from a typical overlay CNI?

It gives every pod a real, routable IP from the VPC subnet instead of a made-up overlay address, with no tunnel. Pods are first-class VPC endpoints: they can reach RDS directly, a load balancer can target a pod IP, and Security Groups, route tables, and flow logs all apply to pod traffic because it's ordinary VPC traffic. The trade is that pods consume real VPC addresses, so you have to plan your subnet address space for pod scale — which is why "failed to assign an IP" is an EKS-specific class of incident overlay users never hit.

2-minHow does a node decide how many pods it can run, and how does prefix delegation change it?

Each instance type caps two numbers: how many ENIs it can attach and how many IPs each ENI holds. In the default secondary-IP mode, one IP per slot, so max pods is (ENIs × (IPs-per-ENI − 1)) + 2 — the minus one is each ENI's own primary IP, the plus two is the host-networked aws-node and kube-proxy pods that don't draw from the pool. An m5.large is 3 ENIs of 10 IPs, so (3 × 9) + 2 = 29 pods, regardless of how much CPU it has. Prefix delegation, enabled with ENABLE_PREFIX_DELEGATION=true on CNI 1.9+, changes what fills a slot: instead of one IP it assigns a /28 prefix of 16 addresses, so the same slots back up to 16× the pods — the formula becomes (ENIs × (IPs-per-ENI − 1) × 16) + 2, capped in practice to around 110 to match Kubernetes' recommended pods-per-node. You have to set the kubelet's --max-pods explicitly and it's a node-group replacement rather than an in-place toggle. The reason it exists is both density and fewer EC2 API calls, since attaching a prefix is one fast call that covers 16 addresses.

DeepWhat is the warm-IP pool, and how would you tune it on a cluster with scarce subnet space?

The warm pool is ipamd's stash of pre-allocated IPs kept ready so pod launches don't wait on the EC2 API — assigning an IP is hundreds of milliseconds and attaching a new ENI can be up to ten seconds, and you don't want that on every pod start. By default WARM_ENI_TARGET=1 keeps a whole spare ENI's worth of IPs warm, which is fast but wasteful: on a large instance that reserves dozens of addresses the node isn't using. On a cluster where subnet space is scarce, I'd stop reserving by ENI and reserve by IP instead: set WARM_IP_TARGET to a small number of spare IPs and MINIMUM_IP_TARGET to roughly the pods a node normally runs, so nodes come up pre-warmed but don't hoard. That trades a little launch latency for a lot of reclaimed addresses. In prefix mode the analogous knob is WARM_PREFIX_TARGET, default 1, which keeps one spare /28 — up to 15 unused IPs per node — so if even that's too much I'd switch to WARM_IP_TARGET below 16 to avoid holding a whole extra prefix. The general principle: the warm pool is a latency-versus-utilisation dial, and tight subnets push you toward utilisation.

ScenarioPods across the cluster suddenly can't get IPs. Walk me through isolating it.

First question: one node or many? I'd look at whether the failing pods are concentrated on a node or spread across the cluster, because that splits the two exhaustion types. If it's one node, it's node-level: that instance hit its ENI/IP ceiling, usually because max-pods was set higher than its real IP capacity — I'd confirm in that node's ipamd.log ("no available IP addresses") and fix by aligning max-pods or enabling prefix delegation. If it's cluster-wide and new nodes don't help, it's subnet-level: I'd run aws ec2 describe-subnets and look at AvailableIpAddressCount — if it's near zero, the CIDR is spent and aws-node logs will show InsufficientFreeAddressesInSubnet. That's fixed with address space: more subnets, a bigger CIDR, or custom networking onto a secondary 100.64.0.0/10 range. There's a third, prefix-specific variant: if prefix mode is on and I see InsufficientCidrBlocks despite free IPs, the subnet is fragmented and can't produce a contiguous /28 — fixed with subnet CIDR reservations. So the decision tree is: scope it to node vs subnet first, check the subnet's free count, then read the exact CNI error, and only then choose between max-pods, address space, or contiguity as the fix.

Follow-upHow do Security Groups apply to pods under the VPC CNI?

By default, all pods on a node share the node's ENI Security Groups, because pod IPs are secondary IPs on those node ENIs. So SGs give you node-level filtering, not pod-level — for pod-to-pod policy you use Kubernetes NetworkPolicy, which the CNI's network-policy agent can enforce. When you genuinely need per-pod Security Groups — say, one workload must have database access that its neighbours don't — you enable security groups for pods, where the CNI assigns the pod a branch ENI (via a trunk ENI) on supported Nitro instance types and applies a Security Group from a SecurityGroupPolicy to that pod specifically. It's the right tool for compliance boundaries, but branch ENIs are a limited resource and add complexity, so I'd reserve it for the pods that actually need distinct SGs rather than turning it on cluster-wide. Either way, the fact that pod traffic is real VPC traffic is what makes SGs relevant to pods at all — that's the through-line of the whole chapter.

RetainQuick revision

The Amazon VPC CNI gives each pod a real, routable VPC IP — no overlay — which makes pods first-class VPC endpoints (direct RDS access, load-balancer targeting, Security Groups, flow logs) and makes them consume finite VPC addresses. Each instance type caps ENIs and IPs-per-ENI; default max pods is (ENIs × (IPs-per-ENI − 1)) + 2, so small nodes starve for IPs long before CPU. ipamd in the aws-node DaemonSet keeps a warm pool of pre-allocated IPs (tuned by WARM_ENI/WARM_IP/MINIMUM_IP targets) so launches don't wait on EC2. The datapath is pod eth0 → veth → host policy routing → ENI (where the pod IP lives) → Security Group → subnet route table → local VPC or NAT-to-internet. Two exhaustion points: node-level ("failed to assign an IP", one node, fix with max-pods/prefixes) and subnet-level (InsufficientFreeAddressesInSubnet, cluster-wide, fix with address space/custom networking); prefix mode adds a contiguity failure (InsufficientCidrBlocks). Plan address space like you plan compute.

The 10 things to remember

  1. VPC CNI gives every pod a real routable VPC IP — no overlay, no tunnel; pods are first-class VPC endpoints.
  2. The upside is integration and observability; the cost is that pods consume finite VPC addresses.
  3. Default max pods = (ENIs × (IPs-per-ENI − 1)) + 2 — small instances hit an IP ceiling before a CPU one.
  4. ipamd (in aws-node) keeps a warm pool of IPs so pod launches don't wait on the EC2 API.
  5. WARM_ENI_TARGET (default 1) trades launch speed for wasted IPs; WARM_IP_TARGET/MINIMUM_IP_TARGET conserve.
  6. Prefix delegation makes each slot a /28 (16 IPs): up to ~16× density, capped ~110/node, needs explicit max-pods.
  7. Enabling prefixes is a node-group replacement, not a toggle; you can't downgrade the CNI below 1.9 afterward.
  8. Datapath: pod eth0 → veth → host policy routing → ENI → Security Group → subnet route table → VPC/internet.
  9. Node exhaustion ("failed to assign an IP", one node) ≠ subnet exhaustion (InsufficientFreeAddressesInSubnet, cluster-wide).
  10. Plan subnets/CIDRs for pod scale up front; use custom networking (100.64/10) to give pods their own space.
