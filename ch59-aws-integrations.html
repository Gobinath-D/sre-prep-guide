Part VI · AWS & EKS for SREs · Chapter 59

AWS integrations

A raw EKS cluster from the last two chapters can run pods and address them — but it still can't provision a load balancer, get a DNS name, mount a durable volume, or add a node on its own. Something has to translate Kubernetes intent into AWS API calls, authenticated as something more specific than "the whole node." That something is a set of in-cluster controllers, and the credential underneath every one of them is this chapter's spine.

Start: Beginner→→→End: Staff-level ~48 min read · EKS cluster (or eksctl/aws eks describe)

By the end of this chapter you can

  • Explain how a pod gets its own scoped AWS permissions via IRSA or EKS Pod Identity, and say which one you'd reach for today.
  • Trace what happens from annotating an Ingress to a working ALB actually routing traffic.
  • Tell the EBS and EFS CSI drivers apart by what they can do on Fargate and what access mode they give you.
  • Describe how Karpenter provisions nodes differently from a fixed-shape Auto Scaling group, and why that matters for cost and speed.
  • Diagnose "the load balancer never appears" from first principles instead of guessing at annotations.

Why this exists · the problemKubernetes objects don't reach outside the cluster

Create an Ingress on plain Kubernetes and nothing happens — it's just a record sitting in etcd until something reads it and acts. Create a PersistentVolumeClaim and it stays Pending forever unless something provisions real storage for it. Create a pod that doesn't fit anywhere and it stays unschedulable unless something adds capacity. Kubernetes describes desired state; it never once promised to reach out to a cloud provider's API on your behalf.

On EKS, a handful of controllers exist purely to close that gap: the AWS Load Balancer Controller turns an Ingress into a real ALB, ExternalDNS turns a Service or Ingress into a Route 53 record, the EBS and EFS CSI drivers turn a PersistentVolumeClaim into a real volume, Karpenter turns an unschedulable pod into a freshly-launched EC2 instance, and the CloudWatch Observability add-on turns cluster activity into metrics and logs somewhere you can actually query them. Every one of them runs as an ordinary pod inside your cluster and needs to make real, authenticated AWS API calls — ec2:RunInstances, route53:ChangeResourceRecordSets, elasticloadbalancing:CreateLoadBalancer.

That leaves one question underneath all five integrations: how does a pod get AWS credentials without either baking a long-lived access key into an image (never do this) or inheriting the entire node's IAM role (way too broad — every pod on that node would share it)? The answer is IRSA — IAM Roles for Service Accounts — and its newer, simpler sibling EKS Pod Identity. Understand that one mechanism well and the rest of this chapter is just "which controller watches which object, and what does it do with the AWS access it's been handed."

Key point

Every integration in this chapter follows the identical shape: a controller pod watches a Kubernetes object, and when it sees one it cares about, it makes a scoped, authenticated AWS API call to make reality match it. That's the exact same reconciliation loop from Chapter 31 — the only thing that changed is that the "external system" being reconciled against is AWS instead of another in-cluster object.

Mental model · analogyThe mental model: embassies inside a foreign country

Real-world analogy

Picture your cluster as a foreign country, and each controller as a small embassy planted inside it. The embassy doesn't try to run the country — it watches for its own citizens' paperwork (an Ingress, a PersistentVolumeClaim, an unschedulable pod) and, when it sees a form it recognizes, picks up the phone and does business back home on that citizen's behalf.

To make that call, the embassy needs diplomatic credentials — not a passport that opens every door in the home country, just a scoped set of privileges good for exactly the business this embassy handles. That credential is an IAM role, and the mechanism that hands it out safely is IRSA or EKS Pod Identity. Before honoring the call, the home country's switchboard checks the credential at a kind of passport control — a trust-policy condition that confirms this specific embassy, and no impostor claiming to be it, is the one calling. Get that check wrong and either the embassy can't do its job, or worse, some other tenant of the building can pretend to be it.

ArchitectureIn-cluster controllers calling AWS APIs

Every controller in this chapter has the same two halves: a pod inside the cluster, and a scoped IAM role outside it, joined by IRSA or Pod Identity. Here's the whole cast at once:

Why an SRE cares

Almost every "it worked in one cluster but not this one" ticket for these integrations is a scoping mismatch: the controller's role is missing a permission, the trust policy doesn't match this exact ServiceAccount, or the controller was installed without any role at all and is quietly running with whatever the node happens to have. Once you know the shared shape — object watched, identity exchanged, scoped API call made — every one of these integrations debugs the same way.

Internal workingIRSA, Pod Identity, and what each controller actually does

1 · IRSA — the original mechanism

Every EKS cluster gets its own OIDC issuer, registered as an IAM identity provider in your account. A pod's ServiceAccount, when annotated with eks.amazonaws.com/role-arn, gets a projected, signed token mounted into it (a ProjectedServiceAccountToken, not the old non-expiring service-account token) alongside AWS_ROLE_ARN and AWS_WEB_IDENTITY_TOKEN_FILE environment variables. Any AWS SDK that reads the default credential chain calls sts:AssumeRoleWithWebIdentity with that token, and STS hands back temporary credentials — but only if the target role's trust policy explicitly allows it, gated by two conditions: <oidc-provider>:aud must equal sts.amazonaws.com, and <oidc-provider>:sub must equal system:serviceaccount:<namespace>:<name>. Get that :sub condition even slightly wrong — wrong namespace, wrong name — and the role simply refuses the call. The signing key behind the whole exchange rotates every 7 days on the EKS side.

2 · EKS Pod Identity — the newer, simpler path

Pod Identity removes the OIDC trust-policy bookkeeping entirely. The role's trust policy just trusts the pods.eks.amazonaws.com service principal for sts:AssumeRole and sts:TagSession — the same trust statement for every role, every cluster. What actually connects a ServiceAccount to a role is a separate object, a Pod Identity association (aws eks create-pod-identity-association --cluster-name X --namespace ns --service-account name --role-arn ...), created and changed purely through the EKS API. An EKS Pod Identity Agent DaemonSet on each node serves credentials to pods locally. AWS now recommends Pod Identity for anything new: no OIDC provider math, roles are reusable across clusters without editing their trust policy, and associations are visible and auditable as first-class EKS objects rather than buried in a role's trust document. IRSA isn't going away — it's what you'll still find on older setups and what you need outside EKS — but Pod Identity is the path of least friction today.

3 · AWS Load Balancer Controller

This controller watches Ingress objects and Service objects of type LoadBalancer, plus (from v2.14+) the Kubernetes Gateway API. An Ingress becomes an ALB. A Service of type LoadBalancer becomes an NLB — and since controller version 2.5, it's the default handler for those Services, via a mutating webhook that sets spec.loadBalancerClass to service.k8s.aws/nlb, rather than falling back to the legacy in-tree AWS cloud provider (which only ever made Classic Load Balancers, and which you should not be relying on in 2026). NLBs can target either EC2 instances or pod IPs directly (ip mode) since controller 2.3.0. Every behavior — which subnets, which certificate, internal versus internet-facing, health-check path — is set through annotations on the Kubernetes object; the controller reads them and translates them into ELB API calls.

Auto-discovery of subnets depends entirely on tags: public subnets need kubernetes.io/role/elb: 1, private ones need kubernetes.io/role/internal-elb: 1, both alongside kubernetes.io/cluster/<cluster-name>: shared (or owned). eksctl-created VPCs get these automatically; hand-rolled or Terraform-managed VPCs frequently don't — and an untagged subnet is one of the single most common reasons a load balancer never provisions.

4 · ExternalDNS

ExternalDNS watches the same objects — Ingress and Service — for a hostname, and keeps a DNS provider in sync with whatever address the LB Controller (or anything else) assigned. On Route 53 it writes an alias or CNAME record, plus a TXT record recording that it owns that name — so it can tell "a record I created" apart from "a record some other process or team owns," and refuses to overwrite the latter. Multiple clusters sharing one hosted zone need distinct --txt-owner-id values so their ExternalDNS instances don't fight over the same names. Its IAM role needs to be scoped to specific hosted zone IDs, not "every zone in the account" — a controller that can rewrite DNS for zones it has no business touching is a bigger blast radius than most teams intend to grant.

5 · EBS and EFS CSI drivers

The EBS CSI driver provisions block storage: one volume, one pod, ReadWriteOnce. It cannot attach a volume to a Fargate pod at all, and its node component (the part that actually mounts volumes) only runs on EC2 — Fargate has no node for it to run on. The EFS CSI driver provisions NFS-backed storage, so it supports ReadWriteMany — many pods, same volume, at once. It works with Fargate for static provisioning (point at an existing EFS file system), but dynamic provisioning (the driver creates a new access point per claim) needs driver 1.2+ and doesn't run on Fargate. Both drivers need their own scoped role — AmazonEBSCSIDriverPolicyV2 or AmazonEFSCSIDriverPolicy — bound to the driver's controller ServiceAccount via IRSA or Pod Identity; skip that step and the very first PVC you create fails with could not create volume in EC2: UnauthorizedOperation, not because anything about the PVC is wrong.

6 · Karpenter

Karpenter watches for unschedulable pods and reasons directly from their requirements — CPU/memory requests, node selectors, affinities, tolerations — to the right EC2 instance, instead of asking a fixed-shape Auto Scaling group to grow and hoping the shape matches. You define a NodePool (constraints: instance types, capacity type, taints, limits) and an EC2NodeClass (the AWS-specific detail: AMI, subnets, security groups); Karpenter provisions directly against EC2, often in under a minute. Consolidation (consolidationPolicy: WhenEmptyOrUnderutilized, tuned with consolidateAfter) continuously looks for cheaper or more tightly-packed arrangements and replaces nodes to get there; a pod annotated karpenter.sh/do-not-disrupt is exempt. For Spot capacity, Karpenter handles interruption natively — including the two-minute Spot reclaim notice — by watching an SQS queue you provide via --interruption-queue, tainting and draining the node ahead of the actual termination (the same SQS mechanics from Chapter 56, put to a very different use). Karpenter's own controller pods must run somewhere it doesn't manage — a small static node group or a Fargate profile — because a node can't safely be responsible for deciding to remove itself.

7 · CloudWatch Observability

Clusters on Kubernetes 1.28+ get a small set of control-plane and scheduler metrics in the AWS/EKS namespace for free, with no add-on installed at all. The Amazon CloudWatch Observability EKS add-on (an operator) goes further: it installs the agents that produce Container Insights (per-node, per-pod, per-container metrics and logs) and Application Signals (traces), across both Linux and Windows nodes. Like every other controller here, its permission to call PutMetricData and write logs comes from a role bound to its own ServiceAccount, not the node's.

Think first: your teammate's chart installs cleanly on their cluster's LB Controller but yours refuses every Ingress with an IAM error. Same chart, same version. What's almost certainly different?

Not the chart — the identity. The controller pod on your cluster is either missing its IRSA annotation / Pod Identity association entirely, or it has one pointing at a role whose trust policy doesn't match this exact ServiceAccount (wrong namespace or name in the :sub condition, for IRSA), or the role exists but is missing the ELB/EC2 permissions the controller actually needs. Confirm with kubectl describe sa aws-load-balancer-controller -n kube-system for the annotation, or aws eks list-pod-identity-associations for an association, then check the role's trust policy and attached policy directly in IAM. The chart is never the problem here — the identity binding is cluster-specific by design.

ComponentsThe pieces, named

  • OIDC provider / Pod Identity Agent. The trust broker — verifies a pod's identity claim and hands STS something it will actually honor. Owns: the credential exchange, not the permissions themselves.
  • ServiceAccount + role binding. An IRSA annotation or a Pod Identity association tying one Kubernetes identity to one IAM role. Owns: which pods may assume which role.
  • AWS Load Balancer Controller. Owns: turning Ingress/Service/Gateway objects into real ALBs and NLBs, and keeping their target groups in sync with pod or node membership.
  • ExternalDNS. Owns: keeping Route 53 (or another provider) in sync with the addresses Kubernetes objects actually have, with TXT-based ownership so it never clobbers records it doesn't manage.
  • EBS / EFS CSI drivers. Owns: turning a PVC into a real, attached (EBS) or mounted (EFS) volume, and knowing what Fargate can and can't do.
  • Karpenter — NodePool + EC2NodeClass. Owns: deciding what capacity to add for a specific set of unschedulable pods, and when to consolidate it away again.
  • CloudWatch Observability add-on. Owns: getting metrics, logs, and traces out of the cluster and into something queryable.

Data flowFrom an annotated Ingress to a working ALB

You apply an Ingress annotated alb.ingress.kubernetes.io/scheme: internet-facing and a few more. The LB Controller's informer sees the create event. Using its IRSA/Pod-Identity-issued credentials, it calls the ELB API to create a load balancer and a target group, discovering subnets by their kubernetes.io/role/elb tags. Because the target type defaults to ip, it registers pod IPs directly — the exact VPC-CNI addresses from Chapter 58 — as targets, skipping kube-proxy and NodePorts entirely. Health checks against those pod IPs begin; once they pass, the controller writes the new ALB's DNS name into the Ingress's status.loadBalancer field.

ExternalDNS, watching that same Ingress, notices the status now has an address. It calls Route 53 to create an alias record for your hostname pointing at the ALB, plus its TXT ownership marker. DNS propagates — instantly for most resolvers, since alias records track the target automatically — and a request from the actual internet now resolves your hostname straight to the ALB, which forwards to a healthy pod. Every step here was one controller reacting to a change another controller (or you) made; nothing was manually wired together, and this exact chain is what Chapter 60 traces packet-by-packet from the other direction.

Lab 2Understand — annotate an Ingress and watch the ALB appearUnderstand

One Ingress, three annotations, and a real address a few minutes later.

bash
cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
spec:
  ingressClassName: alb
  rules:
  - http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service: { name: web, port: { number: 80 } }
EOF

kubectl get ingress web -w
OutputNAME CLASS HOSTS ADDRESS PORTS web alb * k8s-default-web-1a2b3c4d.us-east-1.elb.amazonaws.com 80

Confirm the same load balancer independently, from the AWS side: aws elbv2 describe-load-balancers --query 'LoadBalancers[?contains(LoadBalancerName,`k8s-default-web`)]'. Two different tools, same object — which is exactly the habit you want when something in this chain doesn't match up.

Think first: the target type in that annotation is "ip." What's different about the request path compared to "instance" mode, and which chapter already taught you why?

With ip targets, the ALB registers pod IPs directly and sends traffic straight to a pod's real VPC address — the exact addresses the VPC CNI hands out in Chapter 58. There's no NodePort and no kube-proxy hop. With instance targets, the ALB instead targets a node's NodePort, and kube-proxy's iptables rules DNAT that packet to whichever pod gets picked — an extra hop, plus health checks that test the node's proxying rather than the pod itself. ip mode is the modern default for exactly this reason: fewer hops, and a health check that means what you think it means.

Lab 3Break — an Ingress that never gets an addressBreak

Reproduce the single most common integration failure on purpose: remove the subnet tags the controller relies on for auto-discovery.

bash
aws ec2 delete-tags --resources subnet-0abc123 --tags Key=kubernetes.io/role/elb
kubectl delete ingress web && kubectl apply -f web-ingress.yaml

OutputNAME CLASS HOSTS ADDRESS PORTS web alb * 80

ADDRESS stays empty indefinitely. Before revealing, check the one place that always has the real reason: the controller's own logs.

Reveal where the error actually lives
bash
kubectl logs -n kube-system deployment/aws-load-balancer-controller | tail -20
Output{"level":"error","msg":"failed to build LoadBalancer", "error":"unable to resolve at least one subnet (0 match VPC and AZ)"}

The Ingress object itself has no useful error surface here — the controller's log is where the actual cause lives. This particular message is the subnet-tag failure specifically; the other three shapes to know by the exact wording: an IAM AccessDenied means the controller's role is missing a permission; a webhook/annotation parse error means a typo'd annotation key; and if the controller never even attempts a call, check whether it's actually the active controller at all — the legacy in-tree cloud provider can still be silently handling LoadBalancer Services if the LB Controller was installed without disabling it.

Reveal the check and the fix

Confirm which identity the driver's controller pod is actually running as:

bash
kubectl describe sa ebs-csi-controller-sa -n kube-system

Lab 5Production challenge — size a NodePool and reason through a Spot interruptionSenior challenge

Given this NodePool requirements block, work out what Karpenter will and won't do before opening the answer.

yaml
requirements:
- key: karpenter.sh/capacity-type
  operator: In
  values: ["spot"]
- key: node.kubernetes.io/instance-type
  operator: In
  values: ["m5.large", "m5.xlarge", "c5.large", "c5.xlarge"]
disruption:
  consolidationPolicy: WhenEmptyOrUnderutilized
  consolidateAfter: 1m

A batch of pods needing 2 CPU / 4Gi each goes Pending. A critical pod is annotated karpenter.sh/do-not-disrupt. Ten minutes later a Spot reclaim notice arrives for one of the nodes. Reason through what happens at each point, then check yourself.

Reveal the reasoning

Karpenter provisions from the four allowed instance types on Spot capacity only — it will pick whichever satisfies the pending pods' requests using the Price-Capacity-Optimized allocation strategy, most likely an m5.large or c5.large for a 2 CPU/4Gi pod, and it does this directly against EC2, not through an ASG. Once the batch finishes and a node sits empty (or badly underutilized) for a full minute, consolidation kicks in and Karpenter drains and terminates it to save cost — except a node holding the do-not-disrupt pod is exempt from that removal entirely, by design. When the Spot reclaim notice lands, Karpenter — watching the interruption queue you configured with --interruption-queue — taints and starts draining that node immediately, well ahead of the actual two-minute reclaim deadline, and provisions a replacement in parallel rather than waiting for the pod to fail first. Nothing here touches a fixed ASG desired-count at any point; every decision is made directly against the pending or interrupted pods.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · the load balancer never provisions

Symptom: an Ingress or LoadBalancer Service sits with no ADDRESS indefinitely. First cut: kubectl logs on the LB Controller deployment — the real reason always lives there, never on the Kubernetes object itself. The four usual causes, in the order to check them: (1) missing or mis-scoped IRSA/Pod Identity permissions — look for AccessDenied; (2) subnets not tagged with kubernetes.io/role/elb or internal-elb — look for "unable to resolve at least one subnet"; (3) a typo'd or unsupported annotation key, which the webhook usually rejects with a clear parse error; (4) the legacy in-tree cloud provider still active instead of the LB Controller, quietly doing nothing or making a Classic Load Balancer you didn't ask for.

Incident pattern · PVC stuck Pending with UnauthorizedOperation

Symptom: kubectl describe pvc shows could not create volume in EC2: UnauthorizedOperation or an EFS equivalent. First cut: check whether the CSI controller's ServiceAccount has an IRSA annotation or Pod Identity association at all. Usual cause: the driver was installed without its IAM role ever being created or bound, so it's running on whatever the node's own role happens to allow. Fix: create and bind the driver-specific managed policy; no change to the PVC or StorageClass is needed.

Incident pattern · ExternalDNS won't touch a record it should own

Symptom: a hostname never resolves, or resolves to something stale, despite the Ingress having a valid address. First cut: check the ExternalDNS pod's logs for a message about an existing record without a matching TXT owner marker. Usual cause: a record already exists in the zone (created manually, or by another cluster with a different --txt-owner-id) and ExternalDNS is correctly refusing to overwrite something it doesn't own. Fix: resolve the ownership conflict deliberately — delete the stale record or reconcile the owner ID — rather than forcing an overwrite.

Production · security · performanceWhat matters in production

Security. Give every controller its own role with only the permissions it actually needs — the AWS-published policy documents for the LB Controller and each CSI driver are already scoped tightly; resist the urge to attach something broader "to save time." Scope ExternalDNS to specific hosted zone IDs, never an account-wide DNS permission. Prefer Pod Identity for anything new — one fewer place (the OIDC trust policy) to get wrong.

Performance and cost. ip-mode targets are both faster (no kube-proxy hop) and more accurate (health checks test the actual pod); default to them. Karpenter's consolidation is where most of the cost savings over a static ASG-based node group actually show up — give it room to work rather than pinning nodes unnecessarily. EFS adds real per-operation latency compared to EBS; reach for it because you need ReadWriteMany or Fargate compatibility, not as a default choice.

Common mistakes: installing the LB Controller without disabling the legacy in-tree cloud provider, leaving two systems able to react to the same Service; creating a VPC by hand (or via a Terraform module that doesn't know about EKS conventions) and forgetting the subnet tags eksctl would have added automatically; running Karpenter's own controller on a node Karpenter itself manages; and treating "the chart installed" as proof the underlying IAM binding is correct, when it's a completely separate, cluster-specific step every time.

System-design connectionWhere this reaches into architecture

Every controller here is the same idea you first met in Chapter 31, aimed outward: watch an object, reconcile reality toward it, repeat forever. That pattern — "infrastructure as Kubernetes objects, reconciled by a controller" — is the seed of the whole GitOps and infrastructure-as-Kubernetes-API movement you'll meet properly in Chapter 64: once you accept that a controller can safely reconcile a NodePool against EC2 or an Ingress against an ALB, there's no principled reason it can't reconcile a database or a DNS zone the same way. The IRSA/Pod-Identity model is also a clean, general answer to a problem every multi-tenant platform hits: how do you hand out narrow, per-workload cloud credentials instead of one broad credential shared by everything running on the same host.

InterviewInterview questions & answers

Answer each in your head before opening it.

30-secWhat does the AWS Load Balancer Controller actually do, and why does it need IRSA?

It's a Kubernetes controller that watches Ingress and LoadBalancer-type Service objects and calls the ELB API to create real ALBs and NLBs pointed at your pods or nodes, translating annotations into load-balancer configuration. It needs IRSA (or EKS Pod Identity) because it has to make real, permissioned AWS API calls — CreateLoadBalancer, RegisterTargets — and the only safe way to give one specific pod exactly those permissions, without handing every pod on the node the same access, is to bind a scoped IAM role to its own ServiceAccount rather than relying on the node's broader role.

2-minWalk me through what happens from annotating an Ingress to a working ALB.

You apply an Ingress with annotations like scheme and target-type. The LB Controller's informer sees the create event and, authenticated through its IRSA-issued role, calls the ELB API to create a load balancer and target group, discovering subnets by their kubernetes.io/role/elb tags. With the default ip target type it registers pod IPs directly as targets — real VPC-CNI addresses, no NodePort involved — and health checks against them begin. Once targets pass, the controller writes the load balancer's DNS name back into the Ingress's status. Separately, ExternalDNS is watching that same object; once it sees the status populated, it creates an alias record and a TXT ownership marker in Route 53 pointing at that DNS name. From that point, a real client resolving your hostname gets routed straight to the ALB and on to a healthy pod. The whole thing is two independent controllers each reacting to state, not a single script wiring it together.

DeepCompare IRSA and EKS Pod Identity. Which would you use today, and why?

Both solve the same problem — giving one pod a scoped IAM role instead of the node's — but differ in mechanism. IRSA relies on a per-cluster OIDC provider; a pod's ServiceAccount is annotated with a role ARN, gets a projected signed token, and the SDK exchanges it via sts:AssumeRoleWithWebIdentity, gated by trust-policy conditions on the exact OIDC audience and subject. That trust policy is cluster- and ServiceAccount-specific, which means every role needs its own carefully-written condition, and a typo in the namespace or ServiceAccount name silently breaks the whole chain. Pod Identity replaces that with a single, identical trust statement for every role — trust the pods.eks.amazonaws.com principal — and moves the actual binding into a separate, EKS-API-managed association between a namespace/ServiceAccount pair and a role, created and inspected with plain eks: API calls. That's simpler to audit, easier to move a role between clusters without editing its trust policy, and harder to get subtly wrong. I'd default to Pod Identity for anything new today, and keep IRSA in mind for older clusters or for anything outside EKS that still needs OIDC federation.

ScenarioYou create an Ingress and no ALB ever shows up. How do you debug it?

I go straight to the LB Controller's own logs rather than the Ingress object, because the object itself rarely carries a useful error. From there I check, in order: whether the controller's calls are failing with AccessDenied, which points at a missing or mis-scoped IRSA/Pod Identity permission; whether the log mentions being unable to resolve a subnet, which points at missing kubernetes.io/role/elb or internal-elb tags — very common on hand-built or Terraform-managed VPCs that skipped the tagging convention eksctl applies automatically; whether an annotation was rejected outright, which points at a typo in the annotation key; and finally whether the controller is even the one handling this object at all, since the legacy in-tree AWS cloud provider can still silently pick up LoadBalancer Services if it was never disabled. I'd also independently check the AWS side with describe-load-balancers to confirm nothing partial got created and orphaned.

Follow-upHow is Karpenter different from the Cluster Autoscaler, and why might you choose it?

Cluster Autoscaler works by adjusting the desired count of existing, fixed-shape Auto Scaling groups — it can only grow or shrink groups that already exist with a predetermined instance type, so matching diverse pod requirements often means maintaining many node groups. Karpenter skips that layer entirely: it watches unschedulable pods directly and provisions EC2 capacity that fits their actual requirements — instance type, zone, capacity type — through a NodePool and EC2NodeClass, and can launch a right-sized node in under a minute without any pre-existing group shaped for that pod. It also owns consolidation natively, continuously looking for cheaper or tighter arrangements and replacing nodes to get there, and handles Spot interruption directly against an SQS notification queue rather than relying on a separate node-termination handler. I'd choose it for workloads with spiky or diverse compute requirements where maintaining a matrix of node groups doesn't scale, and lean on managed node groups instead for steady, predictable capacity where that flexibility isn't buying you anything.

RetainQuick revision

Nothing outside plain Kubernetes objects happens on its own — a controller has to watch the object and call an AWS API to make it real, and every one of those calls needs a scoped identity delivered by IRSA (OIDC, sts:AssumeRoleWithWebIdentity, :aud/:sub trust conditions) or the simpler EKS Pod Identity (a pods.eks.amazonaws.com trust statement plus an association). The AWS Load Balancer Controller turns Ingress/Service/Gateway objects into ALBs and NLBs, preferring ip-mode targets that skip kube-proxy. ExternalDNS keeps Route 53 in sync using TXT-based ownership. The EBS CSI driver gives ReadWriteOnce block storage with no Fargate support; EFS gives ReadWriteMany and works with Fargate for static provisioning only. Karpenter provisions right-sized EC2 capacity directly against pending pods instead of through a fixed ASG, and consolidates aggressively unless told not to. When a load balancer never appears, the controller's own logs — not the Kubernetes object — hold the answer, and it's almost always one of four things: permissions, subnet tags, annotations, or a leftover legacy controller.

The 10 things to remember

  1. None of "provision a load balancer, get a DNS name, mount durable storage, or scale nodes" is native Kubernetes — an AWS-facing controller does each one.
  2. Every controller needs its own scoped AWS permissions, delivered to its pod via IRSA or the newer EKS Pod Identity — not the node's own role.
  3. IRSA uses the cluster's OIDC provider and an STS AssumeRoleWithWebIdentity call, gated by an :aud/:sub trust-policy condition tied to one ServiceAccount.
  4. EKS Pod Identity is the simpler successor: a pods.eks.amazonaws.com trust relationship plus an association — no OIDC trust-policy editing per role.
  5. The AWS Load Balancer Controller turns an Ingress into an ALB and a Service of type LoadBalancer into an NLB by default (v2.5+); annotations configure everything else.
  6. The most common "no ALB appears" causes are: missing IRSA/Pod Identity permissions, un-tagged subnets, wrong annotation keys, and the legacy in-tree provider still active.
  7. ExternalDNS watches Service/Ingress objects and keeps Route 53 records in sync, using a TXT record so it never clobbers records it doesn't own.
  8. The EBS CSI driver gives ReadWriteOnce block volumes (no Fargate); the EFS CSI driver gives ReadWriteMany NFS volumes (Fargate-friendly, static provisioning only there).
  9. Karpenter provisions right-sized EC2 capacity directly against pending pods (NodePool + EC2NodeClass) instead of going through a fixed-shape Auto Scaling group.
  10. CloudWatch now ships some EKS control-plane metrics for free (1.28+); the Observability EKS add-on layers on Container Insights and Application Signals.
