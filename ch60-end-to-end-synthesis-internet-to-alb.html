Part VI · AWS & EKS for SREs · Chapter 60

End-to-end synthesis — Internet to ALB to Service to Pod

You now know each piece — DNS, the load balancer, Security Groups, the VPC CNI, kube-proxy — in isolation, from separate chapters. "The app is down" doesn't announce which one broke. This chapter puts all of it into one trace, in the order you should actually check it, so EKS stops being six mental models and becomes one white box.

Start: Beginner→→→End: Staff-level ~50 min read · EKS cluster (or eksctl/aws describe)

By the end of this chapter you can

  • Trace one HTTPS request from a browser all the way to a pod's listening socket, naming every hop.
  • Tell apart the two datapaths — ip-mode target and instance/NodePort target — and say which hops each one adds or skips.
  • Point to exactly where IAM, Security Groups, and the VPC CNI each apply along that path.
  • Given only a symptom like "504 from the ALB," decide which layer to check first and why that order is faster than starting at the pod.
  • Explain how the reply gets back to the client, and what conntrack has to do with it.

Why this exists · the problemKnowing the pieces isn't the same as knowing the order

Route 53 is one chapter. The ALB and target groups are another. Security Groups are another. The VPC CNI is its own flagship chapter. Services and kube-proxy came from Part V. Each one, read on its own, makes sense. None of that tells you what to check first when a page says "the app is down" and you have four minutes before someone escalates.

Engineers who only know the pieces in isolation default to checking the thing closest to them — the pod — first, because that's the layer they're most comfortable in. That's often the slowest possible starting point: it's the last hop in a chain of six or seven, and if you start there you learn nothing about the five hops before it. This chapter's entire point is to give you the order, not just the parts: start in the middle of the chain, at the target group's health check, and bisect from there. That single habit is worth more than memorizing any individual layer.

Key point

Every layer in this trace has exactly one command or log that tells you, definitively, whether the request got that far. Learn the seven checkpoints once and "which layer is broken" stops being a guess — it becomes a five-minute bisection.

Mental model · analogyThe mental model: a parcel through a courier network

Real-world analogy

A parcel starts with a sorting-label lookup — the address gets translated into a routing code before anything moves. That's DNS: Route 53 turns a hostname into the load balancer's own address. The parcel then arrives at a regional depot, where a clerk reads the label and picks which delivery van will carry it onward — that's the ALB's listener rule choosing a target group. Before the van even gets loaded, it has to clear the depot's own security checkpoint — a Security Group, checked right there at the depot's gate.

From here there are two kinds of van route. Some depots have a van that drives straight to the recipient's actual door — no intermediate stop, because the depot already knows exactly which building and unit to go to. That's an ip-mode target: straight to the pod's real address. Other depots only know a general delivery office in the neighborhood — the van drops the parcel there, and an internal mail clerk re-addresses it to the correct unit before it goes any further. That's an instance/NodePort target: the van (the ALB) reaches a node, and kube-proxy is the mail clerk doing the re-addressing (DNAT) to the actual pod. Either way, there's a hand-off scanner at every checkpoint along the route — a place where you could, right now, check whether the parcel actually got that far.

ArchitectureThe whole path, annotated

Here is every hop in one picture, with both datapaths shown side by side from the target group down, and IAM, Security Groups, and the VPC CNI marked exactly where each one actually applies.

Internal workingThe forward trace, hop by hop

Follow a real GET https://app.example.com/. Each step names the checkpoint and the one command that proves the request reached it.

  1. DNS resolves the hostname. Route 53's alias record for app.example.com resolves to the ALB's own DNS name, which in turn resolves to one IP per enabled Availability Zone. Alias records track the ALB automatically and cost nothing to query. Check: dig app.example.com.
  2. TCP and TLS connect to an ALB node. The client opens a connection to one of those per-AZ IPs and completes a TLS handshake; the ALB terminates it there. Check: curl -v https://app.example.com/ — a hang here means DNS resolved but nothing answered on 443.
  3. The listener evaluates rules in priority order and the first match forwards to a target group. Check: aws elbv2 describe-rules --listener-arn ....
  4. The ALB's own Security Group is enforced at its ENI before anything else happens — inbound 443 from the client has to be allowed here, or the connection in step 2 never completes at all. Check: aws ec2 describe-security-groups --group-ids <alb-sg>.
  5. The target group picks a healthy target. Only targets currently passing their health check are candidates — this is the single fastest signal in the whole chain, because it tells you in one call whether everything downstream of this point is even reachable. Check: aws elbv2 describe-target-health --target-group-arn ....
  6. The path splits by target type. In ip mode (the default via the AWS Load Balancer Controller from Chapter 59), the ALB opens a back-end connection straight to the pod's real VPC-CNI address — a secondary IP or an address inside a delegated prefix, exactly as built in Chapter 58. In instance/NodePort mode, it instead connects to a node's IP on the Service's NodePort. Check: the target's Id in the previous step's output — an IP address means ip mode, an instance ID means instance mode.
  7. A second Security Group check happens at whichever ENI was just targeted — the pod's ENI in ip mode, or the node's ENI in instance mode, which must allow the ALB's Security Group as a source on the relevant port (the container port, or the NodePort range). Check: aws ec2 describe-network-interfaces for the target's ENI, then its attached Security Groups.
  8. In instance mode only, kube-proxy takes over. The packet lands on the node at NodeIP:NodePort, and the node's iptables rules — the KUBE-SERVICES chain, exactly as built in Part V's Services chapter — DNAT it to a specific pod IP:port, chosen by the weighted KUBE-SEP rules. Check: iptables -t nat -L KUBE-SERVICES -n | grep <service> on the node, or simply kubectl get endpointslices to see which pods are even in rotation.
  9. The packet crosses the veth pair into the pod's network namespace and hits the container's listening socket. This is the same handoff from Chapter 42, just arriving from outside the cluster instead of from another pod. Check: kubectl exec <pod> -- ss -tlnp to confirm something is actually listening on the expected port.
Why an SRE cares

Step 5 is worth memorizing on its own: a single describe-target-health call tells you whether steps 1 through 5 are fine (a healthy target exists) or rules out the entire second half of the chain (no healthy targets, so nothing downstream matters yet). That's why the checklist in this chapter doesn't start at the pod, and it's why it doesn't start at DNS either — it starts in the middle, where one call answers the most questions per second spent.

Think first: a request works when curled directly against a pod's IP from inside the cluster, but fails through the ALB. Does that tell you the pod is fine?

It tells you the pod and its listening socket are fine — step 9 works. It tells you nothing about steps 1 through 8. A curl from inside the cluster skips DNS, the ALB, both Security Group checks, and (in instance mode) kube-proxy's DNAT entirely. This is exactly the trap of "starting at the pod": a healthy pod proves the last hop works and leaves every earlier hop still unverified. Work from the target group's health check outward instead — it's the one call that tells you whether the ALB can even reach anything, before you've spent time confirming a hop that was never in question.

ComponentsThe pieces, and where they were actually built

  • Route 53 alias record. Owns: turning a hostname into the ALB's address, for free, with automatic tracking. Built in Chapter 53.
  • ALB listener, rules, target group. Owns: which target group a request goes to, and which targets in it are currently eligible. Built in Chapter 52.
  • Security Groups. Owns: the two independent allow/deny checkpoints — at the ALB's ENI and at the target's ENI. Built in Chapter 51.
  • The VPC CNI / pod ENI. Owns: the pod's real, routable address that an ip-mode target reaches directly. Built in Chapter 58.
  • kube-proxy / iptables. Owns: the DNAT decision from a NodePort or ClusterIP to a specific pod, in instance mode only. Built in Part V's Services chapter.
  • conntrack. Owns: remembering a DNAT decision so the reply doesn't need kube-proxy to decide again. Native to the Linux network stack.
  • The AWS Load Balancer Controller and its IRSA/Pod Identity role. Owns: keeping the target group's membership in sync with pod or node reality in the first place. Built in Chapter 59.

Data flowFollowing the reply back

The forward trace gets most of the attention; the reply is where the two datapaths actually feel different. In instance mode, the node's kernel made a DNAT decision in step 8 — packets addressed to NodeIP:NodePort got rewritten to a pod's real address. Nothing forces kube-proxy to make that same decision again for the reply: the kernel's connection-tracking table (conntrack) already recorded the mapping when the first packet passed through, so the reply is un-DNAT'd automatically back to look like it came from NodeIP:NodePort, and the ALB's back-end connection sees a normal, consistent conversation. You can watch this table directly on the node with conntrack -L | grep <pod-ip>.

In ip mode, there's nothing to reverse in the first place. The ALB's back-end connection went straight to the pod's real VPC IP, so the reply is just an ordinary TCP response leaving that real address, routed by the VPC like any other traffic, arriving back at the ALB's open connection. This is the quieter, and arguably more important, reason ip mode is simpler to reason about under load: there's one fewer piece of kernel state (a conntrack entry) that has to exist, stay correct, and not get evicted under connection-table pressure before the conversation finishes.

Hands-onLabs — build, understand, break, troubleshoot

These labs assume the Ingress and controller from Chapter 59 are already in place. Each one is really a rehearsal of the checklist above under a specific failure.

Lab 1Build — run the seven-checkpoint trace on a working requestBuild

Before anything is broken, run every checkpoint once so you know what "healthy" looks like at each hop.

bash
dig +short app.example.com
curl -v https://app.example.com/ 2>&1 | grep -E 'Connected|HTTP'
aws elbv2 describe-target-health --target-group-arn $TG_ARN \
  --query 'TargetHealthDescriptions[].{id:Target.Id,state:TargetHealth.State}'
kubectl get endpointslices -l kubernetes.io/service-name=web
Output203.0.113.9 * Connected to app.example.com (203.0.113.9) port 443 < HTTP/1.1 200 [ { "id": "10.0.3.14", "state": "healthy" } ] NAME ADDRESSTYPE PORTS ENDPOINTS web-abcde IPv4 8080 10.0.3.14

Four commands, four different layers, all consistent with each other. That consistency — the target ID matching the endpoint IP matching what actually answered — is what you're listing for on every future incident, and this is your baseline for what "matching" looks like.

Lab 2Understand — compare the two target modes side by sideUnderstand

Deploy the same app behind two Services, one annotated for ip-mode, one left at the NodePort default, and watch the datapath actually differ.

bash
aws elbv2 describe-target-health --target-group-arn $TG_IP_ARN \
  --query 'TargetHealthDescriptions[].Target.Id'
aws elbv2 describe-target-health --target-group-arn $TG_INSTANCE_ARN \
  --query 'TargetHealthDescriptions[].Target.Id'
Output[ "10.0.3.14" ] [ "i-0a1b2c3d4e5f60789" ]

One target group lists a pod IP; the other lists an EC2 instance ID. Now generate traffic to each and check the node behind the instance-mode target:

bash
ssh $NODE 'sudo conntrack -L | grep 10.0.3'
Outputtcp 6 431999 ESTABLISHED src=203.0.113.9 dst=10.0.5.20 dport=31200 src=10.0.3.14 dport=8080 [ASSURED]

That conntrack entry — a NodePort (31200) rewritten to a pod address (10.0.3.14:8080) — only exists for the instance-mode path. Run the same check against the ip-mode target's node and you'll find nothing, because the ALB never touched that node at all.

Think first: why might a platform team standardize on ip mode for every Ingress, even though NodePort mode "also works"?

Fewer moving parts under load. NodePort mode adds a node hop, a kube-proxy DNAT decision, and a conntrack entry that has to survive for the life of the connection — any one of which is one more thing that can be wrong, evicted, or exhausted (conntrack tables have finite size). It also means the ALB's health check is testing a node's proxying behavior rather than the pod directly, so a healthy-looking target can still route to a pod that's actually struggling. ip mode collapses that down to "does the ALB have a direct, working connection to this exact pod" — a strictly more honest signal, with one fewer hop to debug at 3am.

Lab 3Break — pull one Security Group rule and watch which checkpoint failsBreak

Remove the rule that lets the ALB's Security Group reach the pod's container port, and run the checklist top to bottom.

bash
aws ec2 revoke-security-group-ingress --group-id $POD_SG \
  --protocol tcp --port 8080 --source-group $ALB_SG
curl -v https://app.example.com/
Outputcurl: (28) Failed to connect to app.example.com port 443 after 30001 ms: Connection timed out

DNS clearly worked — you got an IP and attempted a connection. Before revealing, run the checklist yourself: which checkpoint is the first one to show something wrong?

Reveal which checkpoint catches it
bash
aws elbv2 describe-target-health --target-group-arn $TG_ARN \
  --query 'TargetHealthDescriptions[].TargetHealth'
Output[ { "State": "unhealthy", "Reason": "Target.Timeout" } ]

Target.Timeout, not Target.FailedHealthChecks — the health checker sent packets and got silence, which is the fingerprint of a Security Group quietly dropping traffic, not an application actively refusing it. The target group check catches this in one call, well before you'd have needed to inspect the pod, the node, or kube-proxy at all — exactly the bisection this chapter is arguing for. Restore the rule and confirm the target flips back to healthy within a couple of health-check intervals.

Lab 4Troubleshoot — a 504 with every pod reporting RunningTroubleshoot

The ticket: users get 504 Gateway Timeout. kubectl get pods shows everything Running and 1/1 Ready. Decide your first three commands before reading on.

bash
aws elbv2 describe-target-health --target-group-arn $TG_ARN
kubectl exec debug-pod -- curl -m 3 -w '%{http_code}\n' http://10.0.3.14:8080/
Output[ { "Target": {"Id":"10.0.3.14"}, "TargetHealth": {"State":"healthy"} } ] 000

The target is marked healthy by the ALB's own check, yet a direct curl to the same pod from inside the cluster times out with no HTTP code at all. Reconcile that contradiction before opening the answer.

Reveal the reconciliation

"Ready" and "healthy" and "fast enough for this one request" are three different claims. 1/1 Ready only reflects the pod's own readiness probe, which usually hits a cheap, dependency-free endpoint. The ALB's health check hits whatever path you configured, on whatever schedule — it can lag reality by up to a full unhealthy-threshold's worth of failed checks before it flips. And a 504 specifically means a target was reached but didn't answer within the ALB's idle timeout — which fits a pod that's technically up and technically passing quick health checks, but is wedged or overloaded on a particular slow code path (a hung downstream call, a lock, a GC pause) that only shows up under the real request, not the health check's lightweight one. The fix here isn't at any of the AWS-layer checkpoints — it's inside the application, and the way you found that out was by noticing the target group said healthy while a real request still failed, which rules out every hop before the pod and points you straight at it.

Lab 5Production challenge — it works from the office, not from homeSenior challenge

Half your users report total failure; the other half say it's fine. Nothing was deployed today. Work out a diagnostic order before opening the answer.

Reveal the diagnostic order and the likely causes

"Some users, not others" almost always means the split is happening at a layer that treats different clients differently — which rules out the pod and kube-proxy immediately, since neither one knows or cares where a client is connecting from. That leaves two real suspects, and you check them in order of how fast each is to rule out: first, the ALB's own Security Group — is it restricted to specific CIDRs (an office IP range) rather than open to the internet, which would explain "office yes, home no" perfectly and takes one describe-security-groups call to confirm. Second, if the SG is wide open, check target distribution across Availability Zones and cross-zone settings — an uneven or partially-unhealthy target set can make some ALB nodes route successfully while others don't, which correlates with client location only by accident (whichever AZ's node your ISP's routing happens to hit). The Security Group check comes first because it's the deliberate-looking cause and the cheapest to confirm; you'd only move to the AZ/target-distribution theory once you've ruled out something that was configured on purpose to restrict access.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · "the app is down," diagnosed by bisection

Symptom: a vague report, no clue which of the seven hops is at fault. The order that wastes the least time: start at the target group's health check — it single-handedly confirms or rules out everything from DNS through the Security Group at once. If targets are healthy, the problem is likely inside the app or a downstream dependency (go to the pod). If targets are unhealthy, split further: Target.Timeout points at a Security Group or network path; Target.FailedHealthChecks points at nothing listening on that port; a wrong HTTP status points at the health-check path/matcher. Only after target health is explained should you touch DNS (fast to rule out anyway, do it first if it's free) or the pod directly.

Incident pattern · 504 with healthy-looking pods

Symptom: Gateway Timeout from the ALB; kubectl get pods shows nothing wrong. First cut: confirm the target group itself reports healthy — if it does, the gap between "passes a lightweight readiness probe" and "answers this specific real request in time" is the actual bug, and it lives in the application or a dependency it calls, not in any AWS-layer checkpoint. Usual cause: a slow code path, a hung downstream call, or resource contention that a cheap health check never exercises.

Incident pattern · works for some clients, not others

Symptom: failure correlates with the client's network, not with time or deploys. First cut: the ALB's own Security Group — is public access actually as open as you think? Confirm: describe-security-groups on the ALB's ENIs. Usual cause: a CIDR restriction added for a legitimate reason (an office allow-list, a WAF rule) that's now blocking traffic it wasn't meant to.

Production · security · performanceWhat matters in production

Keep this checklist somewhere the on-call can find at 3am — a runbook that's just this chapter's seven checkpoints, in order, with the exact command for each, turns a stressful bisection into a mechanical one. Prefer ip-mode targets across the board: fewer hops, a more honest health check, and no dependency on conntrack table capacity holding up under load. Reference Security Groups by ID, not CIDR, wherever the source is another AWS resource (the ALB) rather than a genuine external network — SG-to-SG references survive scaling and IP churn that CIDR rules don't.

Common mistakes: starting every investigation at the pod, which is the slowest possible entry point into a seven-hop chain; treating a passing readiness probe as proof a pod can handle the real request; forgetting that Security Groups apply at two separate ENIs on the path, not one; and not knowing, off the top of your head, which target mode your own Ingress is even using — that single fact changes which three of the seven checkpoints are relevant at all.

System-design connectionWhere this reaches into architecture

The method in this chapter — draw the full request path, then bisect it from the middle instead of guessing — is not EKS-specific. It's the same discipline Chapter 103 generalizes to any distributed system, and it's the first thing worth sketching in almost any system-design interview: before you optimize anything, you need the one diagram this chapter just built, because you can't reason about where a request is slow, insecure, or failing until you can point at every hop it takes. The specific insight that the fastest diagnostic isn't always at either end of a chain — it's wherever a single check rules out the most other checks — is a general debugging principle worth carrying into Chapter 93 and every incident you'll ever run.

InterviewInterview questions & answers

Answer each in your head before opening it.

30-secDescribe the path from a browser to a pod on EKS, in one breath.

DNS resolves the hostname to the ALB via a Route 53 alias record; the ALB's listener matches a rule and forwards to a target group; a Security Group is checked at the ALB's own ENI; the target group picks a healthy target, either a pod's real VPC-CNI address directly (ip mode) or a node's NodePort (instance mode); a second Security Group is checked at whichever ENI was targeted; in instance mode, kube-proxy's iptables rules DNAT the packet to a specific pod; and the packet crosses a veth pair into the pod's network namespace to reach the listening container.

2-minWalk through every hop, and what you'd check to confirm each one.

Start with DNS — dig the hostname and confirm it resolves to the ALB, which costs nothing and takes a second. Then the TLS handshake — curl -v shows whether anything answered on 443 at all. Next the listener's rule evaluation, checkable via describe-rules, though this rarely breaks since it's pure configuration. The most valuable single check comes next: describe-target-health, which tells you in one call whether a healthy target exists at all — if it doesn't, everything downstream is moot, and the failure reason string (Target.Timeout versus FailedHealthChecks versus a bad status code) tells you which specific thing to check next. If a target is healthy, the Security Group at that target's ENI has to allow the ALB's SG on the relevant port — describe-network-interfaces plus describe-security-groups confirms it. In instance mode specifically, kube-proxy's iptables KUBE-SERVICES chain on the node is doing a DNAT to a chosen pod, checkable with iptables -L or just by confirming the right pods appear in the Service's EndpointSlices. Finally, ss -tlnp inside the pod confirms something is actually listening on the expected port. I'd run these roughly in this order, but jump straight to target health first if I'm in a hurry, because it answers the most questions per command.

DeepHow does the datapath differ between an ip-mode target and an instance-mode target, and why does it matter operationally?

In ip mode, the ALB registers pod IPs directly and opens its back-end connection straight to a pod's real VPC-CNI address — there's no NodePort, no kube-proxy DNAT, and no conntrack entry required on any node, because the node was never involved in the forwarding decision at all. In instance mode, the ALB connects to a node's IP on the Service's NodePort, and that node's kube-proxy rewrites the destination to a specific pod via iptables, which means a conntrack entry has to exist and survive for the life of the connection so the reply gets un-DNAT'd correctly. Operationally this matters in three ways: ip mode's health check tests the actual pod, so "healthy" means what you think it means, where instance mode's health check partly tests the node's proxying; ip mode has one fewer hop and no dependency on a node's conntrack table capacity, which matters under high connection churn; and debugging instance-mode failures requires knowing about a layer (kube-proxy, conntrack) that ip mode removes from the picture entirely. That's why ip mode is the modern default and generally the better choice unless you have a specific reason to target instances.

ScenarioThe ALB returns 504, but every pod looks healthy in kubectl. Where do you look, and in what order?

I'd check the target group's health state first, because it's the fastest way to split the problem in two: if the ALB itself considers the target unhealthy, the issue is somewhere between the ALB and that target — a Security Group, or the health-check configuration — and kubectl's view of the pod is irrelevant to that. If the target is healthy by the ALB's own check, then the gap is between "passes a cheap health check" and "answers a real, possibly slower request within the ALB's idle timeout" — which means the actual problem lives inside the application or something it calls: a slow query, a hung downstream dependency, contention under real load that a lightweight probe never exercises. I'd confirm by hitting the pod directly with something closer to the real request and timing it, rather than trusting that Ready in kubectl says anything about request-level latency, since a readiness probe and a real request are not the same check.

Follow-upHow does the reply actually get back to the client, and what does conntrack have to do with it?

In ip mode, the reply needs no special handling — the pod's real address sent it, ordinary VPC routing carries it back to the ALB's open back-end connection, and the ALB relays it to the client over the original front-end connection. In instance mode, the forward packet was DNAT'd by kube-proxy from NodeIP:NodePort to a pod's address, and the reply has to be un-DNAT'd back to look like it came from NodeIP:NodePort or the ALB's back-end connection would see an address it never dialed. The Linux kernel's connection-tracking table, conntrack, is what makes that automatic: it recorded the original DNAT mapping when the first packet passed through, so every subsequent packet in that same connection — including the replies — gets translated consistently without kube-proxy having to re-decide anything. It's also why instance mode has a real, finite resource (conntrack table size) that ip mode simply doesn't need to worry about.

RetainQuick revision

The full path is DNS (Route 53 alias) → ALB listener/rule → target group → Security Group → either a pod's real VPC-CNI address directly (ip mode) or a node's NodePort followed by kube-proxy's iptables DNAT to a pod (instance mode) → the pod's network namespace. Security Groups apply twice: at the ALB's ENI and again at the target's ENI. The single fastest diagnostic is the target group's health state, because it confirms or rules out everything before it in one call — start there, not at the pod. 503 means no healthy target; 504 means a target was reached but didn't answer in time, which usually means the bug is inside the app, not the AWS layers. conntrack is what lets a NodePort's DNAT decision survive for the reply without kube-proxy re-deciding — and it's exactly the piece of state ip mode doesn't need at all.

The 10 things to remember

  1. The path is: DNS (Route 53) → ALB listener/rule → target group → (pod directly, or node+kube-proxy) → pod network namespace.
  2. Route 53 alias records resolve for free and auto-track the target resource's address — check with dig first, it's free and instant.
  3. Security Groups are enforced at the ALB's ENI and again at the target's ENI — two separate checkpoints, not one.
  4. ip-mode targets go straight to a pod's real VPC IP (VPC CNI) — no kube-proxy hop, no NodePort, no extra DNAT.
  5. instance/NodePort-mode targets hit a node's NodePort, and kube-proxy's iptables rules DNAT the packet to a chosen pod — an extra hop ip mode skips.
  6. Target group health checks are the fastest single signal — check them before you check a single pod, because they rule in/out half the path at once.
  7. conntrack remembers a NodePort's DNAT decision so replies don't have to be re-decided by kube-proxy on the way back.
  8. "Unauthorized" (IAM) and "connection timeout" (network/SG) are different failure families that live at different hops — don't mix up which tool answers which.
  9. 503 from the ALB means no healthy target; 504 means a target was picked but never answered in time; neither means "the pod crashed" by itself.
  10. Bisect the path instead of guessing: check the middle of the chain (target health) first, then narrow toward DNS or toward the pod based on the result.
