Part VII · Platform Engineering — Packaging, IaC, GitOps, Mesh, Access · Chapter 61

Helm

You've written a lot of raw YAML by now. Deploying "the same app" to dev, staging, and prod with nothing but copy-pasted manifests is how a team ends up with three quietly-diverging YAML trees and no real answer to "what did we actually ship last Tuesday." Helm is the package manager that fixes that — and the rollback it gives you is the reason this chapter exists at all.

Start: Beginner→→→End: Staff-level ~46 min read · Helm 3 on kind

By the end of this chapter you can

  • Explain what a chart, a release, and a revision actually are, and where Helm stores each one.
  • Predict exactly which value wins when the same key is set in three different places.
  • Use helm template and helm lint to catch problems before anything touches a cluster.
  • Break a real deployment with a bad value, then use helm rollback to recover it in seconds, not minutes.
  • Say why hook resources aren't cleaned up on uninstall, and what to do about it.

Why this exists · the problemA folder of YAML doesn't know what version it is

Every Deployment, Service, ConfigMap, and Ingress you've written since Part IV has been a separate file, applied by hand or by a script. That works for one environment. It stops working the moment you need the same app running in dev, staging, and prod with slightly different replica counts, image tags, and resource limits — you either maintain three near-duplicate copies of every manifest, or you bolt on sed/envsubst scripts that nobody fully trusts. And when an upgrade goes wrong, "what did we have running five minutes ago, exactly" is a question raw kubectl apply has no good answer to.

An operating system solved this exact problem decades ago with a package manager: one versioned unit (a package), a way to install it with your own choices layered over sane defaults, and a record of what's installed so you can remove or upgrade it cleanly. Helm is that, for Kubernetes. A chart is the package — a set of templated manifests plus a default configuration. Installing a chart creates a release — one named, tracked instance of it running in your cluster — and every install or upgrade of that release is a numbered revision you can inspect, diff conceptually, or go back to.

A version note, before we go further

Helm 4 shipped in 2026 with real changes — server-side apply by default for new installs, a WebAssembly-based plugin system, and renamed flags (--atomic is now --rollback-on-failure, --force is now --force-replace). This chapter teaches Helm 3.x deliberately: it's still what the overwhelming majority of production clusters run, it's what "no Tiller" refers to — the architectural change that actually matters — and every idea here (charts, values, releases, hooks) carries forward into v4 unchanged in spirit. Where a v4 rename matters, it's flagged.

Mental model · analogyThe mental model: a recipe card, not a plated dish

Real-world analogy

A chart is a recipe card — a set of instructions (templates) plus a default ingredient list (values.yaml). Cooking it for tonight's table (installing it into a specific cluster and namespace) lets you swap ingredients — more salt, a different cut of meat — without rewriting the recipe itself; that's overriding values. What actually lands on the table, the plated dish, is the rendered Kubernetes manifest Helm actually sends to the API server. The kitchen keeps an order ticket on file for every dish served — that's a release revision — so if tonight's version disappoints, you can tell the kitchen "make me exactly what you served last time" without re-explaining the whole recipe. That's helm rollback.

ArchitectureValues + templates → rendered manifests → release

Helm 3 has no server-side component — no Tiller. It's two parts: a client (the CLI you run) and a library it calls into, and that library talks to the Kubernetes API server directly, using your own kubeconfig credentials. There is nothing else installed in your cluster just to make Helm work.

Why an SRE cares

Because there's no separate Helm server, there's no separate thing to compromise, upgrade, or lose — a real security and operability win over Helm 2's Tiller. It also means release state lives exactly where your cluster's own RBAC and backups already cover it. The trade-off: whoever runs helm commands needs Kubernetes API access with real permissions, not just "access to a Helm server" — so CI's Helm identity needs its own scoped RBAC, same as anything else that talks to the API server.

Internal workingCharts, values, releases, repos, dependencies, hooks

1 · Chart anatomy

A chart is a directory: Chart.yaml (name, version, apiVersion: v2, an optional appVersion for the app's own version separate from the chart's), values.yaml (defaults), templates/ (the actual manifests, plus a conventional _helpers.tpl for named template snippets and an optional NOTES.txt printed after install), and charts/ (vendored subchart dependencies). A crds/ directory holds CRDs that Helm installs first and never templates, upgrades, or deletes automatically — the replacement for a removed Helm 2 mechanism called crd-install.

2 · The values hierarchy — who wins

Values merge from several sources, in a fixed order of increasing precedence: the chart's own values.yaml (lowest) is overridden by a parent chart's values for a subchart, which is overridden by any -f file passed on the command line (and if you pass -f more than once, a later file wins over an earlier one), which is overridden by --set (and its siblings --set-string, --set-json, --set-file — highest of all). Keep values trees shallow where you can; deep nesting makes precedence harder to reason about, not easier.

One trick worth knowing cold: setting a key to null deletes it from the merged result instead of layering on top of it. That matters when a default sets one sub-key of a structure (say, a liveness probe's httpGet) and you need to switch to a different sub-key (exec) entirely — Kubernetes won't accept both on one probe, so you override with the new key and null out the old one, or the merge leaves both present and the manifest fails validation at the API server, not at render time.

3 · Templates

Templates are Go's text/template syntax plus the Sprig function library, with a handful of built-in objects: .Values (the merged values), .Release (name, namespace, revision, whether this is an install or upgrade), .Chart (the chart's own metadata), .Files (non-template files in the chart), and .Capabilities (what the target cluster supports). helm template renders everything locally with zero cluster contact — the fastest possible feedback loop — and helm lint checks structure, required fields, and common mistakes before you've even rendered anything.

4 · Releases and revisions — where the state actually lives

A release is one named installation of a chart. Install the same chart twice under two different release names and you get two fully independent releases — two Redis instances, say, each with its own history. Helm 3 stores each release's state — the chart, the computed values, the rendered manifest, and metadata — as a Kubernetes Secret, one per revision, named sh.helm.release.v1.<release>.v<revision>, sitting in the release's own namespace. No external database, nothing outside the cluster.

helm upgrade creates a new revision. helm history <release> lists every one of them. helm rollback <release> [revision] — omit the revision, or pass 0, for "the previous one" — re-applies an older revision's already-rendered manifest. That's a subtlety worth being precise about: rollback creates a brand-new revision that happens to match an old one's content. History only ever grows forward; there's no time travel that erases what happened in between. --history-max (default 10) caps how many old revisions stay retained per release.

5 · Repositories

The classic model is an index.yaml plus packaged .tgz charts served over plain HTTP(S) — added with helm repo add, refreshed with helm repo update, searched with helm search repo. The increasingly common model is an OCI registry: helm push a chart to oci://..., helm pull it back, helm registry login to authenticate. ECR itself can host Helm charts as OCI artifacts, which is why many teams have quietly stopped running a dedicated chart-repository server at all.

6 · Dependencies

A chart declares the other charts it needs in Chart.yaml's dependencies list — name, version, repository, and optionally a condition or tags key that lets a values override toggle a whole subchart on or off. helm dependency update resolves that list, downloads the packaged subcharts into charts/, and writes a Chart.lock — a lockfile pinning exactly which versions were resolved, so a second dependency update six months later doesn't silently pull something newer. Subcharts see their own values under their own name in the parent's values file, and anything under a top-level global: key is visible to every subchart at once — the mechanism an umbrella chart uses to configure many services from one place.

7 · Hooks

A hook is a normal template with a special annotation — helm.sh/hook: pre-install, for instance — that pulls it out of the ordinary apply-and-move-on lifecycle. The defined hooks are pre-install, post-install, pre-delete, post-delete, pre-upgrade, post-upgrade, pre-rollback, post-rollback, and test (run only by helm test). Hooks of the same kind run in ascending order of helm.sh/hook-weight (a string-encoded integer, default effectively 0); if the hook resource is a Job or Pod, Helm blocks and waits for it to finish, and a failing hook fails the whole release operation.

Hook resources are not part of the release

Once a hook resource reaches its ready state, Helm walks away from it — it's not tracked as part of the release, which means helm uninstall will not clean it up by default. If you need it removed, add a helm.sh/hook-delete-policy annotation: before-hook-creation (the default — delete the previous run's resource right before a new one is created), hook-succeeded, or hook-failed. Leaving a one-shot migration Job lying around forever, because nobody set a delete policy, is a very common source of cluster clutter.

Think first: helm upgrade exits with a success message. Does that tell you the new pods are actually healthy?

No — by default it tells you only that the rendered manifest was accepted by the API server. Helm's default behavior doesn't wait to confirm the workload became Ready; a Deployment can be happily crash-looping while the CLI has already returned exit code 0 and printed "STATUS: deployed." Getting Helm's notion of success to match reality needs --wait (block until resources report ready) and, better, --atomic (wait, and automatically roll back if that wait fails) — neither of which is the default, which is exactly the gap the next lab walks straight into.

ComponentsThe pieces, named

  • Chart.yaml. Owns: the chart's identity — name, version, apiVersion: v2, dependency declarations.
  • values.yaml. Owns: the lowest-precedence defaults every override layers on top of.
  • templates/. Owns: the actual Go-templated manifests, helpers, and NOTES.
  • charts/ + Chart.lock. Owns: resolved, pinned subchart dependencies.
  • crds/. Owns: CRDs installed once, up front, never templated or auto-removed.
  • A release (Secret per revision). Owns: the full history of what was actually installed, in-cluster, with no external store.
  • A repository — index.yaml or OCI registry. Owns: where charts are found, versioned, and pulled from.

Data flowFollowing one real helm upgrade --install

You run helm upgrade --install myapp ./mychart -f prod-values.yaml --set image.tag=1.4.2. The client loads the chart and merges values by the precedence just covered — prod-values.yaml over the chart's defaults, --set over that. It renders every template locally against the computed values, entirely offline so far. Because a release named myapp already exists, this becomes an upgrade: the library runs any pre-upgrade hooks first and waits for them to finish. It then applies the rendered resources to the API server — using your own credentials, still no Tiller anywhere — creates or patches whatever changed, runs any post-upgrade hooks, and (only if you passed --wait or --atomic) blocks until the new resources actually report ready. Finally it writes the new revision's Secret, bumps the release's revision number, and prints NOTES.txt. If --atomic was set and that final wait failed, this whole sequence runs again automatically in reverse — a rollback to the previous revision — before the command returns control to you.

Hands-onLabs — build, understand, break, troubleshoot

All five labs run on a local kind cluster — nothing here needs a cloud account.

bash
kind create cluster --name lab61
helm version   # confirm you're on Helm 3.x — no separate server to start
Lab 1Build — scaffold, render, and install a chartBuild

helm create scaffolds a working chart. Render it without touching the cluster first, then actually install it.

bash
helm create mychart
helm template mychart | head -20
helm install demo ./mychart
helm list
helm status demo
OutputNAME NAMESPACE REVISION STATUS CHART APP VERSION demo default 1 deployed mychart-0.1.0 1.16.0

helm template showed you the exact YAML before anything was applied — that render is deterministic and entirely local. helm status and helm list both read from the same place: the revision Secret Helm just wrote for this release.

Lab 2Understand — prove the values precedence with your own eyesUnderstand

Override the same key three ways and confirm which one actually won.

bash
echo 'replicaCount: 3' > staging-values.yaml
helm upgrade demo ./mychart -f staging-values.yaml --set replicaCount=5
helm get values demo
helm show values ./mychart | grep replicaCount
OutputUSER-SUPPLIED VALUES: replicaCount: 5 --- replicaCount: 1 # the chart's own untouched default

--set replicaCount=5 beat the -f staging-values.yaml file's 3, which in turn overrode the chart's own default of 1 — exactly the precedence order, confirmed by two different commands that read two different things: get values shows what was actually applied for this release, show values shows the chart's untouched defaults.

Think first: you pass both -f base.yaml -f override.yaml. If both files set the same key, which one wins?

override.yaml — with multiple -f flags, files are merged left to right and the last one given wins on any key they share. This is the part of the precedence rule people get backwards most often, because it's easy to assume "more specific filename" or "the one listed first" matters; only order matters. It's also why layering a base file and an environment-specific file works cleanly as long as you always pass the base file first and the environment override second, consistently, in your deploy tooling.

Lab 3Break — feed a value that breaks the app at runtimeBreak

Not a YAML syntax error — a value that renders fine and fails only once Kubernetes tries to run it.

bash
helm upgrade demo ./mychart --set image.tag=does-not-exist
kubectl rollout status deployment/demo --timeout=30s
OutputRelease "demo" has been upgraded. Happy Helming! Waiting for deployment "demo" rollout to finish: 0 of 1 updated replicas are available... error: timed out waiting for the condition

helm upgrade printed "Happy Helming" and exited 0. The rollout never actually finished. Before revealing: what does Helm's own view of this release say right now, and why did the CLI not warn you?

Reveal what happened and why
bash
helm status demo
kubectl describe pod -l app.kubernetes.io/instance=demo | grep -A2 Events
OutputSTATUS: deployed Warning Failed ... Failed to pull image "...:does-not-exist": not found

Helm's status still says deployed — because by default, applying the manifest successfully is Helm's whole definition of success, and this run had no --wait or --atomic flag telling it to check further. The pod is stuck in ImagePullBackOff, and nothing about the Helm CLI's own output told you that. This gap — "the manifest was accepted" versus "the workload is actually healthy" — is exactly what causes a broken upgrade to sit unnoticed in production until someone happens to check pods directly.

Lab 4Troubleshoot — the rollback that saves itTroubleshoot

Recover from Lab 3 the way you actually would in production: find the last good revision and go back to it.

bash
helm history demo
OutputREVISION STATUS CHART APP VERSION DESCRIPTION 1 superseded mychart-0.1.0 1.16.0 Install complete 2 superseded mychart-0.1.0 1.16.0 Upgrade complete 3 deployed mychart-0.1.0 1.16.0 Upgrade complete

Revision 3 is marked deployed, but you know from Lab 3 that it's the broken one. Which revision would you actually roll back to, and what will helm history look like immediately afterward — a restored revision 2, or something else? Decide before opening the answer.

Reveal the rollback and what history actually shows next
bash
helm rollback demo 2
kubectl rollout status deployment/demo --timeout=30s
helm history demo | tail -1
Outputdeployment "demo" successfully rolled out 4 deployed mychart-0.1.0 1.16.0 Rollback to 2

Notice the new row: revision 4, not a return to revision 2. Rollback re-applies revision 2's rendered manifest as a brand-new entry in the history — the count only ever goes up, which is exactly why helm history is always the true, append-only story of a release, never something you can quietly rewrite. deployed on revision 3 the whole time was never a health signal — it only meant the manifest was accepted, which is the exact gap Lab 3 exposed.

Lab 5Production challenge — harden this so Lab 3 can't happen quietly againSenior challenge

Design a chart that catches this class of failure before it ever reaches the state Lab 3 did, before opening the answer.

Reveal the hardening

Three layers, cheapest first. Make Helm's success check the truth: run every upgrade with --atomic (which implies --wait) — Helm blocks until the Deployment actually reports ready, and automatically rolls back to the previous revision if it doesn't, all inside the one command, instead of leaving a broken release marked deployed for a human to notice. Catch bad structure before install: run helm lint --strict in CI so structural problems fail the pipeline, not the cluster; add a values.schema.json to the chart root so Helm validates the shape of values.yaml — wrong types, missing required keys — automatically on every install, upgrade, and even template. Catch bad behavior, not just bad structure: a pre-upgrade hook Job that smoke-tests the new image (even something as simple as confirming it exists and starts) before the real rollout ever begins, so a typo'd tag fails fast and loud in the hook instead of quietly inside a Deployment nobody's watching. None of these three replace the others — --atomic catches what lint can't, and lint catches what a smoke test would be too slow to run for.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · "helm upgrade succeeded" but the app is down

Symptom: the release shows STATUS: deployed, the CLI exited 0, and the workload is unhealthy or crash-looping. First cut: check whether the upgrade was run with --wait/--atomic at all — without them, "deployed" only means the manifest was accepted. Confirm: kubectl rollout status and pod events tell the real story. Fix now: helm rollback to the last good revision. Fix permanently: make --atomic the standard for every upgrade going forward.

Incident pattern · values did something you didn't expect

Symptom: a value you thought you set didn't take effect, or an unrelated field changed. First cut: helm get values <release> to see exactly what was actually applied, versus what you intended. Usual cause: a precedence surprise — multiple -f files in the wrong order, or a deep merge combining two sub-keys that should have been mutually exclusive (fixed with an explicit null override). Fix: flatten the values structure where you can, and be deliberate about -f file order in your deploy tooling.

Incident pattern · "works on my machine," fails in CI

Symptom: a chart installs fine locally but fails to render or install in the pipeline. First cut: was helm dependency update run recently enough that charts/ and Chart.lock actually match Chart.yaml? Usual cause: a subchart dependency resolved locally months ago and never refreshed, drifting from what CI resolves fresh every run — or a target-cluster Kubernetes version CI never validated against. Fix: commit Chart.lock, and run helm lint --kube-version <target> against the real target version in CI, not whatever version happens to be on a laptop.

Production · security · performanceWhat matters in production

Security. Helm has no built-in secrets management — a value in values.yaml is just YAML, and if that file is in git, so is whatever you put in it. Keep real secrets out of values entirely; reference something that manages them separately. Because Helm acts with whatever identity ran the command, give CI's Helm identity scoped, namespaced RBAC rather than cluster-admin — the same rule that applies to any other client of the Kubernetes API.

Operability. Make --atomic and --wait the default in your deploy tooling, not something an engineer remembers to type under pressure. Set --history-max deliberately rather than letting revision Secrets accumulate forever. Prefer OCI registries over standing up and maintaining your own chart-repository server.

Common mistakes: treating a clean helm template render as proof the chart will actually run — rendering success and runtime success are unrelated claims; forgetting hook resources aren't garbage-collected on uninstall and leaving one-shot Jobs behind indefinitely; two teams maintaining conflicting values files for the same chart with no agreed precedence; and not pinning subchart versions, so a routine dependency update pulls in an unplanned breaking change.

System-design connectionWhere this reaches into architecture

A chart plus a values file is already a declarative description of desired state — which is exactly the input Argo CD will later reconcile continuously instead of you running helm upgrade by hand from a laptop, the subject of Chapter 64. The values-hierarchy pattern itself — layered defaults, environment overrides, and explicit last-mile overrides, each with a fixed precedence — isn't a Helm quirk; it's the same shape you'll meet in Terraform's variable precedence, application config profiles, and most serious configuration systems, because "defaults you can override, in a predictable order" is close to a universal requirement once more than one environment exists.

InterviewInterview questions & answers

Answer each in your head before opening it.

30-secWhat is Helm, and why not just kubectl apply -f a folder of YAML?

Helm is Kubernetes' package manager: a chart packages a set of templated manifests with default configuration, installing it creates a tracked release, and every install or upgrade is a numbered revision you can inspect or roll back to. Plain kubectl apply on a folder of YAML has no concept of versioning, no parameterization beyond what you script yourself, and no built-in way to answer "what did we have running before this change" — Helm gives you all three, on top of manifests you'd otherwise be maintaining by hand across every environment.

2-minWalk me through exactly what happens when I run helm upgrade --install.

The client loads the chart and merges values from every source in precedence order — chart defaults, parent chart values, any -f files in the order given, then --set flags last and highest. It renders every template locally against that computed value set, entirely offline. If a release by this name doesn't exist yet, this becomes an install; if it does, an upgrade — either way, any pre-install or pre-upgrade hooks run first and Helm waits for them to finish before touching the main resources. The library then applies the rendered manifests directly to the Kubernetes API server using your own credentials, since Helm 3 has no separate server component. Post-install or post-upgrade hooks run next. If you passed --wait or --atomic, Helm blocks until the new resources actually report ready, and with --atomic specifically, a failed wait triggers an automatic rollback to the previous revision. Finally, the new revision — chart, computed values, rendered manifest, metadata — is written as a Secret in the release's namespace, and NOTES.txt prints. Without --wait or --atomic, "success" only ever meant the manifest was accepted, which is the gap that causes most "upgrade succeeded but the app is broken" incidents.

DeepWhere does Helm store release state, and what changed from Helm 2's Tiller?

Helm 3 stores every release revision as a Kubernetes Secret, named sh.helm.release.v1.<release>.v<revision>, in the same namespace as the release — no external database, nothing outside the cluster. Helm 2 instead ran a server-side component called Tiller inside the cluster, which held broad permissions to manage releases on behalf of any client that could reach it, and which itself needed installing, upgrading, and securing as a standing piece of infrastructure. Removing Tiller in Helm 3 meant the client and library talk to the API server directly using the caller's own Kubernetes credentials, so Helm's authorization model collapsed into "does this identity have RBAC to create these resources" — the exact same question you'd ask about any other API client — instead of a separate, additional trust boundary around Tiller itself. It's a real security simplification: one fewer privileged, always-on component to compromise.

ScenarioAn upgrade just broke production. What do you do in the next two minutes?

First, confirm it's actually this release and not something else entirely — helm history on the affected release to see the most recent revision and its description. If the previous revision was known-good, I run helm rollback with no revision argument, which defaults to the previous one, and that re-applies the last-good rendered manifest as a new revision immediately — I don't spend time diagnosing the root cause of the break before restoring service, because rollback doesn't require understanding why the new revision failed. Once traffic is healthy again, I'd check helm get values and helm get manifest on the bad revision to actually understand what changed, and only then dig into why the health check I should have had (--atomic, in hindsight) didn't catch it before it reached users. Restore first, diagnose second — the rollback is fast specifically because Helm already has the last-good manifest on file; there's nothing to reconstruct.

Follow-upWhy aren't resources created by a hook cleaned up when you helm uninstall?

Because Helm deliberately doesn't track hook-created resources as part of the release's managed set — once a hook resource reaches its ready state, Helm considers its job done and stops watching it. That's a design choice, not an oversight: hooks are meant for one-off actions (a migration Job, a pre-delete cleanup task) whose resources often shouldn't disappear the instant the hook finishes, and sometimes shouldn't disappear even when the whole release is later uninstalled — a backup Job's output, for instance. If you do want a hook's resource removed automatically, you set a helm.sh/hook-delete-policy annotation explicitly: before-hook-creation (the default, which deletes the previous run right before a new one starts), hook-succeeded, or hook-failed. Leaving that unset and then being surprised that helm uninstall left something behind is one of the most common Helm surprises in practice.

RetainQuick revision

A chart is a versioned, parameterized package of manifests; a release is one named, tracked instance of it; a revision is one numbered install or upgrade of that release. Helm 3 has no Tiller — client and library talk to the Kubernetes API server directly, and every revision is stored as a Secret in-cluster, nothing external. Values merge by precedence: chart defaults, then parent-chart values, then -f files in the order given, then --set highest — and a null override deletes rather than merges. helm template/lint catch problems before a cluster is ever touched, but a successful helm upgrade only proves the manifest was accepted, not that the workload is healthy, unless you pass --wait or --atomic. helm rollback re-applies an old revision's manifest as a brand-new revision — history only ever grows. Hooks run outside the normal resource lifecycle and are never cleaned up automatically unless you set a deletion policy. Dependencies resolve into charts/ and a Chart.lock for reproducibility.

The 10 things to remember

  1. A chart is a versioned, parameterized package of manifests; a release is one named, tracked instance of a chart running in a cluster.
  2. Helm 3 has no Tiller — the client and library talk to the Kubernetes API server directly; release state lives in a Secret per revision, in-cluster.
  3. Values merge by precedence: chart defaults < parent chart values < -f file(s) in order given < --set/--set-string/--set-json (highest).
  4. Setting a value to null deletes an inherited default instead of merging on top of it.
  5. helm template/--dry-run renders manifests locally with no cluster changes; helm lint catches structural problems before either.
  6. helm upgrade applying successfully only means the manifest was accepted — it says nothing about whether the workload became healthy.
  7. helm rollback <release> [revision] re-applies an older revision's rendered manifest as a brand-new revision — it moves history forward, it doesn't erase it.
  8. Hooks (helm.sh/hook: pre-install, etc.) run outside the normal resource lifecycle and are not tracked by the release — they aren't deleted on uninstall unless you set a deletion policy.
  9. Chart.yaml's dependencies block plus helm dependency update resolve subcharts into charts/ and a Chart.lock, for reproducible installs.
  10. --atomic (auto-rollback on a failed upgrade) plus a real readiness probe is what makes Helm's "success" match the workload's actual health.
