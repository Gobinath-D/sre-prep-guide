Terraform I — model, resources, state, the dependency graph

You've packaged the app with Helm. Nobody has packaged the infrastructure underneath it. If that VPC, that database, that load balancer still gets created by someone clicking through a console or running a one-off script, you don't actually know what's running — you know what you think you clicked last time.

Start: Beginner→→→End: Staff-level ~42 min read · Terraform CLI + Docker provider (local)

By the end of this chapter you can

  • Explain what a provider, resource, data source, and the state file each are and how they fit together.
  • Read a terraform plan diff and predict what apply will actually do before you run it.
  • Read a terraform graph and say which resources Terraform can build in parallel and which it can't.
  • Point at the exact line in state that tells Terraform a resource already exists.
  • Diagnose a plan that wants to destroy and recreate something you didn't expect to change.

Why this exists · the problemClicking buttons doesn't scale, and scripts don't know when they're done

Say you need a VPC, a couple of subnets, a database, and a load balancer. You could click through the AWS console. That works once. It does not survive a second environment, a teammate who wasn't in the room, or you six months from now trying to remember which of the four almost-identical security groups is actually load-bearing.

So you write a script instead — a pile of AWS CLI calls in order. That's better: it's at least reviewable text. But it has a different problem. The script only knows how to create. Run it twice and it either fails on "already exists" or, worse, creates a second database next to the first one. It has no concept of "what already exists and what still needs to change." It's a sequence of commands, not a description of an end state — and if a step halfway through fails, you're left in some unknown, unnamed condition between "before" and "after" with no record of which resources actually got made.

Infrastructure-as-code tools exist to fix exactly that gap. You write down what you want to exist — not the steps to get there — and the tool figures out the steps, keeps a record of what it already built, and only changes the parts of the real world that no longer match what you wrote. Terraform is the one you'll meet in almost every SRE job. It's declarative, it works across dozens of providers with one workflow, and its core trick — a dependency graph plus a persisted state file — is the same trick every tool in this space uses in some form, so understanding it here pays off even the day you touch a different one.

Key point

Terraform's job is convergence, not execution. You describe a target. It compares that target against what it last recorded as real, computes the smallest set of changes to close the gap, and only then touches anything. Everything else in this chapter is really just "how does it compute that gap, safely, and in what order."

Mental model · analogyThe mental model: a blueprint and a general contractor

Real-world analogy

You're the architect. You draw a blueprint — a description of the finished building, not a step-by-step build order. You hand it to a general contractor. The contractor doesn't start swinging hammers randomly; they work out that the foundation has to exist before the walls, and the walls before the roof, and they hire the right subcontractors for plumbing and electrical because those trades speak a different language than "general construction."

Critically, the contractor keeps a punch list — a ledger of exactly what's been built so far and its details: this outlet, this exact model, installed on this date, at this address. When you come back next year with a change, the contractor checks the punch list first. They don't rebuild the whole house from scratch and they don't guess whether the deck already exists — the punch list tells them. Lose that punch list, and the contractor is back to guessing, which is exactly as dangerous as it sounds.

ArchitectureProviders, resources, data sources, and state

A Terraform configuration is plain text (HCL) describing a handful of block types, and almost everything else builds on these:

  • Provider. A plugin that knows how to talk to one system's API — AWS, Docker, Kubernetes, GitHub, whatever. You declare which ones you need and pin their versions in a required_providers block; terraform init downloads the matching plugin binaries and records the exact versions it resolved in a dependency lock file, .terraform.lock.hcl, so a second init next month — on your laptop or in CI — doesn't silently pick up a newer provider release.
  • Resource. One thing you want Terraform to own the full lifecycle of — create it, update it in place when it can, destroy it when you remove the block. A resource's address is type.name, e.g. docker_container.web, and that address is exactly what ties a block in your config to an entry in state.
  • Data source. A read-only lookup — "what's the latest AMI matching this filter," "what's this existing VPC's ID." Terraform doesn't manage a data source's lifecycle; it just reads a value at plan/apply time so you can use it elsewhere.
  • Variables, locals, outputs. Variables are inputs you can override per environment. Locals are computed, named values you're tired of repeating. Outputs are values a config exposes on purpose — for a human running terraform output, or for another module to consume.

The state file is the punch list made concrete. By default it's a local JSON file, terraform.tfstate — Terraform's own docs are blunt about why it exists at all: it maps real-world objects back to the resource blocks in your config, tracks metadata, and lets Terraform avoid re-querying the entire world on every run. Never hand-edit it; use the terraform state subcommands if you need to inspect or fix it, because the CLI insulates you from the underlying format changing between Terraform versions.

Why an SRE cares

A clean terraform plan is a change-review artifact, not just a convenience. Paste it into a pull request and a reviewer can see exactly what will be created, changed, or destroyed before anyone runs apply against production. That's the same review discipline you already expect from application code — Terraform is what makes infrastructure changes reviewable the same way.

Internal workingHow the graph gets built, and how Terraform walks it

This is the part most engineers use for years without ever seeing. Here's what Terraform actually does, in order, every time you run plan or apply:

  1. Add a resource node for every resource block. If a resource uses count greater than 1, each index gets its own node, plus a resource meta-node that groups them for convenience — it doesn't do anything on its own.
  2. Attach state and diff metadata. If a resource already exists in state, or has a pending diff from a plan, that data rides along on its node.
  3. Map resources to provisioners, if any are declared — done after every resource node exists, so resources sharing a provisioner type can share the implementation.
  4. Add explicit depends_on edges. This is the escape hatch for a dependency Terraform can't see any other way — usually because it's a side effect, not a referenced attribute.
  5. Add orphaned resources. Anything present in state but no longer in config gets a node too, so it can be scheduled for destruction. Orphans never carry configuration, because state doesn't store any.
  6. Map every resource to its provider configuration node. This creates the edge "this resource depends on its provider being configured" — which is why a provider block with a typo breaks everything that provider touches, all at once.
  7. Parse interpolations to find implicit dependencies. Any time one resource's config references another resource's attribute (like docker_container.web reading docker_image.nginx.image_id), that reference becomes a graph edge automatically. This is how most dependencies get discovered — you rarely write depends_on by hand.
  8. Create a single root node pointing at every resource, purely so the graph has one entry point. It's ignored when Terraform decides execution order.
  9. Split replace operations. If a diff says a resource must be destroyed and recreated, its single node splits into a destroy node and a create node, because destroy order and create order aren't always the same thing (this is exactly what create_before_destroy, covered in the next chapter, controls).
  10. Validate. No cycles allowed, and exactly one root. If your config has a circular reference, this is the step that catches it and Terraform refuses to proceed.

Walking the finished graph is a standard depth-first traversal, done in parallel: a node runs as soon as every node it depends on has finished, not in one single-file line. By default up to 10 nodes run concurrently — controlled by -parallelism on plan, apply, and destroy — and HashiCorp is explicit that this isn't meant for routine tuning; some providers (AWS included) handle their own API rate limiting with backoff inside the provider itself, so Terraform's parallelism knob isn't the tool for that problem.

terraform plan walks this same graph to compute a diff per node — refreshing real infrastructure state first, comparing it against config, and ordering the comparisons so a value computed upstream is available when a downstream resource needs to reference it. terraform apply walks it again for real, making the actual API calls. terraform destroy walks it in the reverse dependency order, so the container gets torn down before the network it depends on, never the other way round.

Think first: two resources have no reference between them anywhere in your config. Does Terraform create them one after another, or at the same time?

At the same time, up to the parallelism limit. Terraform only serializes work where the graph has an actual edge — a reference, a depends_on, or a shared provider-configuration dependency. No edge means no ordering constraint, so both nodes become eligible to run as soon as their own (separate) prerequisites are satisfied. This is exactly why unrelated resources in a large plan often apply in a burst rather than a strict top-to-bottom list — and why adding an unnecessary depends_on "just to be safe" quietly costs you real wall-clock time on every apply.

ComponentsThe pieces, named

  • HCL configuration files (.tf). Owns: the desired end state, as data — not a script.
  • Terraform Core. Owns: parsing config, building and walking the graph, computing diffs, talking to providers over a plugin protocol.
  • Providers. Own: translating resource blocks into real API calls for one specific system.
  • The state file. Owns: the one-to-one mapping between your config's resource addresses and real-world object IDs, plus metadata.
  • The dependency lock file (.terraform.lock.hcl). Owns: exactly which provider versions were resolved, so init is reproducible across machines.
  • The Terraform Registry. Owns: where providers and modules are published, versioned, and discovered.

Data flowFollowing one real init & plan & apply

You write a small config: a docker_image, a docker_network, and a docker_container that references both. terraform init reads required_providers, downloads the Docker provider plugin, and writes the lock file. terraform plan builds the graph from the steps above, refreshes any existing state against the real Docker daemon, walks the graph to compute what's missing, and prints a diff — + for create, ~ for update in place, -/+ for destroy-then-recreate. terraform apply asks for confirmation, then walks the same graph for real: the image and network nodes have no edge between them, so they can both proceed as soon as the provider is configured; the container node waits for both, because its config reads their attributes. Once everything succeeds, Terraform writes a new state file recording each object's real ID — and that ID is what makes the next plan a comparison instead of a guess.

Hands-onLabs — build, understand, break, troubleshoot

All five labs run against the Docker provider on your own machine — no cloud account needed. You just need Docker and the Terraform CLI installed.

bash
mkdir tf-lab62 && cd tf-lab62
terraform version   # confirm the CLI is installed; any recent 1.x works
Lab 1Build — a real container, managed as codeBuild

Create main.tf:

hcl
terraform {
  required_providers {
    docker = { source = "kreuzwerker/docker" }
  }
}
provider "docker" {}

resource "docker_image" "nginx" {
  name = "nginx:1.27-alpine"
}
resource "docker_network" "app" {
  name = "tf-lab62-net"
}
resource "docker_container" "web" {
  name    = "tf-lab62-web"
  image   = docker_image.nginx.image_id
  ports   { internal = 80  external = 8080 }
  networks_advanced { name = docker_network.app.name }
}
bash
terraform init
terraform plan
terraform apply -auto-approve
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080
Output (trimmed)Plan: 3 to add, 0 to change, 0 to destroy. ... Apply complete! Resources: 3 added, 0 changed, 0 destroyed. 200

Three resources, zero edges you wrote by hand between image/network and the container — those two references (image_id, docker_network.app.name) were enough for Terraform to work out the order on its own.

Lab 2Understand — read the punch list yourselfUnderstand

State isn't a black box. Look straight at it.

bash
terraform state list
terraform state show docker_container.web | head -8
Output (trimmed)docker_container.web docker_image.nginx docker_network.app # docker_container.web: resource "docker_container" "web" { id = "3f1a9c…" image = "sha256:8e9c…" name = "tf-lab62-web"

That id is the real Docker container ID, not something Terraform invented — it's the exact value the punch list carries forward so next time it doesn't have to guess whether this container exists. Compare with the raw JSON directly:

bash
terraform show -json | python3 -c "import json,sys; d=json.load(sys.stdin); print(len(d['values']['root_module']['resources']), 'resources in state')"
Output3 resources in state
Think first: someone tells you Terraform could just re-query the real infrastructure every time instead of keeping a state file. What would that lose?

Two things, mainly. First, plenty of real objects don't expose a clean, unique key that maps back to "this resource address in my config" — Terraform's own docs are explicit that the primary purpose of state is recording that mapping, because the provider's API often can't hand it back to you cheaply on demand. Second, performance: refreshing thousands of resources by querying live on every single command would make Terraform unusably slow at any real scale. State is a cache with a very specific, deliberate job — not an accident of implementation.

Lab 3Break — a change you didn't expect to be destructiveBreak

Not every config change updates in place. Some attributes can only be changed by destroying and recreating the object. Change the container's name:

bash
sed -i.bak 's/tf-lab62-web/tf-lab62-web-v2/' main.tf
terraform plan
Output (trimmed) # docker_container.web must be replaced -/+ resource "docker_container" "web" { ~ name = "tf-lab62-web" -> "tf-lab62-web-v2" # forces replacement ... } Plan: 1 to add, 0 to change, 1 to destroy.

Read the symbols like a sentence: -/+ means destroy-then-create, not update. The comment forces replacement is Terraform telling you exactly which attribute triggered it — the Docker provider can't rename a running container via its API, so the only path is a new one. This is normal and often fine; it's dangerous only when you didn't expect it.

Lab 4Troubleshoot — find out why, before you applyTroubleshoot

Imagine you inherited this repo and someone else made that name change weeks ago. The plan above lands on your screen during a routine apply. Before you scroll up: which single word in the plan output tells you the cause, and where do you look to confirm it's really unavoidable rather than a mistake?

Reveal the approach

The word is forces replacement, printed right next to the specific changed line — Terraform always tells you which attribute triggered a replace, so you never have to guess by diffing the whole resource by eye. To confirm whether it's avoidable, check the provider's own documentation for that resource and that attribute specifically: some "ForceNew" attributes are a genuine API limitation (like this one), and some are a modeling choice a newer provider version relaxed. If it's a real limitation, your only options are to accept the replacement, or use create_before_destroy so the new one exists before the old one disappears — covered properly in the next chapter, because it interacts with every dependent resource too.

Lab 5Production challenge — read the raw graph, and meet drift earlySenior challenge

Undo the rename (mv main.tf.bak main.tf) and look at the graph Terraform actually built for this config:

bash
terraform graph
Output (trimmed)digraph { "docker_container.web" -> "docker_image.nginx" "docker_container.web" -> "docker_network.app" "docker_image.nginx" -> "provider[\"docker\"]" "docker_network.app" -> "provider[\"docker\"]" }

That's Graphviz DOT syntax — each line is one edge, read as "the left node depends on the right node." Even without rendering it, you can answer the graph-reading question cold now: which two lines describe resources with no dependency edge between each other at all, meaning Terraform is free to build them at the same time? (docker_image.nginx and docker_network.app — neither line mentions the other.) If graphviz is installed, terraform graph | dot -Tsvg > graph.svg renders it visually; the reasoning doesn't need the picture.

Now, one more thing, without touching any .tf file — reach outside Terraform entirely and change something it manages:

bash
docker rename tf-lab62-web tf-lab62-web-renamed-by-hand
terraform plan
Output (trimmed) # docker_container.web has changed outside of Terraform ~ resource "docker_container" "web" { ~ name = "tf-lab62-web-renamed-by-hand" -> "tf-lab62-web" }

Terraform noticed immediately, on the very next plan, because plan refreshes real state before comparing. This is drift — reality moved without going through code — and right now your only tool for it is "notice it by accident on the next plan." Chapter 63 is entirely about state at scale, and drift is the first thing it takes seriously.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · "apply wants to destroy half my infrastructure"

Symptom: a routine apply proposes replacing far more than you touched. First cut: read the plan for forces replacement comments — count how many distinct resources actually changed versus how many are just downstream of one that did. Confirm: a resource that many others reference (a shared VPC, a shared security group) changed in a way that forces its own replacement, and everything referencing it gets rescheduled to depend on the new one. Usual cause: a seemingly small attribute change on a heavily-shared resource, or a provider upgrade that changed a default value you never set explicitly.

Incident pattern · "plan is clean locally, CI shows something different"

Symptom: your laptop's plan shows no changes; the same commit in CI shows a diff. First cut: compare provider versions — did CI resolve a newer version because .terraform.lock.hcl wasn't committed, or was skipped? Usual cause: an uncommitted lock file, or someone applied manually from a machine whose local state is now stale relative to the shared one.

Incident pattern · manual change, silent drift

Symptom: a resource's real-world settings don't match what's in code, and nobody remembers changing the code. First cut: terraform plan — the diff shows exactly which attribute drifted. Usual cause: someone made an emergency fix directly against the cloud console or CLI during an incident, and the fix was never ported back into the Terraform config. Chapter 63 covers detecting this deliberately instead of by accident, and deciding whether to keep the manual fix or revert it.

Production · security · performanceWhat matters in production

Security. The state file routinely contains plaintext values for anything a resource's attributes expose — including secrets a resource generated, like a database's initial password. Marking a variable or output sensitive = true only redacts it from CLI and UI output; it does not encrypt it inside state. Treat the state file itself as a secret: encrypt the backend storing it, and restrict read access as tightly as you would restrict access to the secrets it might contain.

Performance. Parallelism defaults to 10 concurrent graph nodes for a reason — it's a reasonable default, not a dial to casually crank up. If a provider's API is rate-limiting you, that's the provider's job to back off gracefully, not something you fix by lowering Terraform's parallelism across the board.

Common mistakes at this stage: hand-editing the state file directly instead of using terraform state subcommands; treating a stale local plan as still valid after time has passed and the real world could have changed; and reaching for -target as a normal part of the workflow — it's an emergency escape hatch that breaks the very completeness guarantee the dependency graph exists to give you, and it should feel unusual every time you type it.

System-design connectionWhere this reaches into architecture

The state file is functionally a cache with a job: remember what's real so the next comparison is cheap and accurate instead of a live query against everything. That's the same shape as a Kubernetes controller's watch cache, or any reconciler that tracks "what I last observed" separately from "what I want" — you'll meet the same pattern by name in Chapter 28 and Chapter 31. And a config that declaratively describes desired infrastructure state, reviewed as a diff before it's applied, is exactly the kind of artifact a pull-based delivery system can operate on automatically instead of a human running apply from a laptop — which is precisely where Chapter 64 picks up.

InterviewInterview questions & answers

Answer each in your head before opening it.

30-secWhat problem does Terraform actually solve?

It lets you describe infrastructure as a desired end state instead of a sequence of imperative steps, and it converges real infrastructure to match that state safely — creating what's missing, updating what can change in place, destroying what's no longer declared — using a persisted state file to know what already exists and a dependency graph to work out safe ordering. The alternative, hand-written scripts or console clicks, has no concept of "already done" and no reviewable diff before a change lands.

2-minWalk me through what happens between running terraform plan and it printing a diff.

Terraform parses the configuration and builds a dependency graph: one node per resource (or per index under count), a node per provider configuration, edges from explicit depends_on, edges discovered automatically whenever one resource's config references another resource's attribute, and a single root node pointing at everything so there's one entry point. Any resources present in state but no longer in config get added as orphan nodes destined for destruction. Before comparing anything, Terraform refreshes: it queries the real infrastructure for every resource already in state to catch drift. Then it walks the graph — in parallel wherever nodes have no dependency edge between them, serialized wherever they do — computing a diff at each node between refreshed real state and desired config. The output uses +/~/-/-/+ to mean create, update in place, destroy, and destroy-then-recreate respectively, and any destroy-then-recreate is called out with the specific attribute that forced it.

DeepWhy does Terraform need a state file at all — why not just query the real infrastructure every time?

Two separate reasons, and I'd give both. First, mapping: state's primary documented purpose is binding a resource address in your config to a specific real-world object's identity, and plenty of provider APIs have no clean way to hand that mapping back to you on demand — without state, Terraform would have no reliable way to know "this config block corresponds to that exact object" versus a different one that happens to look similar. Second, performance and metadata: querying every attribute of every resource live on every single command doesn't scale, and state also carries metadata the provider's API doesn't expose at all. The trade-off is that state becomes a single point of failure and a sensitive artifact in its own right — which is exactly why remote backends with locking exist, covered in the next chapter.

ScenarioA plan you didn't expect wants to destroy and recreate a resource lots of other things depend on. What do you do before running apply?

First, I read the plan output for the specific attribute Terraform flagged with "forces replacement" — it always names the exact field, so I don't have to diff the whole resource by eye. Then I check whether that's a genuine provider limitation (some attributes truly can't be updated in place via the underlying API) or an accidental change, like a default value shifting after a provider upgrade nobody reviewed carefully. If it's a real limitation and the resource is something expensive or risky to recreate, I'd look at whether create_before_destroy is safe for it and for everything that depends on it, since that lifecycle rule propagates to dependencies automatically. If it's not actually necessary, I fix the config instead of applying the replacement. Either way, I would not apply a surprise destroy-and-recreate against anything with real dependents without understanding exactly why it's happening first.

Follow-upHow does the dependency graph decide what can run in parallel?

Purely from edges. Two resource nodes with no path between them — no explicit depends_on, no attribute reference, no shared forced ordering from a replace split — have no ordering constraint, so both become eligible to execute as soon as their own prerequisites (typically just their provider being configured) are satisfied, up to the parallelism limit, which defaults to 10 concurrent nodes and is adjustable with -parallelism. Anywhere an edge does exist, the downstream node simply waits until the upstream node finishes. That's also why an unnecessary manual depends_on has a real cost — it serializes work the graph would otherwise have run concurrently.

RetainQuick revision

Terraform describes infrastructure declaratively and converges real resources to match. A provider translates resource blocks into real API calls; a resource is one thing Terraform fully owns; a data source is a read-only lookup. State maps config addresses to real-world object identities and is the only reason Terraform doesn't have to guess what already exists. The dependency graph has resource nodes, provider-configuration nodes, and a root node, with edges built from explicit depends_on and — far more often — automatically discovered attribute references; it's walked depth-first, in parallel wherever there's no edge, serialized wherever there is. plan refreshes real state, then diffs against config, before anything is touched. A destroy-then-recreate is always labeled with the exact attribute that forced it. Never hand-edit state; treat it as a secret. Drift is what happens the moment reality changes without going through code — and it's the entire subject of the next chapter.

The 10 things to remember

  1. Terraform converges real infrastructure to a declared desired state — it doesn't just execute a script of steps.
  2. A provider is a plugin per target system; a resource is fully owned by Terraform; a data source is read-only.
  3. State maps your config's resource addresses to real-world object identities — that mapping is its whole reason to exist.
  4. The dependency lock file (.terraform.lock.hcl) pins provider versions so init is reproducible across machines.
  5. Most graph edges are discovered automatically from attribute references, not written by hand as depends_on.
  6. The graph is walked depth-first, in parallel wherever nodes have no edge between them — default parallelism is 10.
  7. plan refreshes real state before diffing against config — that's how drift gets noticed at all.
  8. Plan symbols: + create, ~ update in place, - destroy, -/+ destroy-then-recreate — always with the forcing attribute named.
  9. sensitive = true hides a value from CLI/UI output; it does not encrypt it inside the state file.
  10. -target is a break-glass tool, not a habit — it bypasses the completeness guarantee the graph exists to provide.
