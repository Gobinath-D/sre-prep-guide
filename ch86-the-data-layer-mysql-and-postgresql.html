Part IX · Distributed Systems, Data & Reliability · Chapter 86

The data layer — MySQL and PostgreSQL

Every "stateless" service you've ever run is a thin wrapper around a database that isn't stateless at all. The day it can't keep up, kubectl scale stops helping and you're reading lock tables at 2 a.m.

Start: Beginner→→→End: Staff-level ~50 min read · Docker lab (MySQL + PostgreSQL)

By the end of this chapter you can

  • Explain why a B-tree index turns a table scan into a handful of page reads, and why the wrong index doesn't help at all.
  • Say what a transaction isolation level actually changes about what one connection can see of another's work.
  • Read an EXPLAIN plan and tell whether it's using an index or quietly scanning the whole table.
  • Explain MVCC well enough to say why a long-running SELECT doesn't block writers, and why that isn't free.
  • Diagnose connection exhaustion and lock contention from first principles, not from a runbook you memorized.
  • Plan a schema change on a live, busy table without taking an outage to do it.

Why this exists · the problemThe problem every database is actually solving

Your app has state. A user's balance, an order's status, a session — something has to remember it after the request that created it is long gone. You could keep it in a process's memory, but that memory disappears the moment the process restarts, and it's invisible to every other process that also needs to read or change that same fact. So you put it somewhere shared and durable: a file, then a table, then a database.

The moment you do that, three problems show up at once. Many callers want to read and write the same rows at the same time, and if you let them do it carelessly they'll corrupt each other's work — two requests both reading a balance of 100, both subtracting 30, both writing back 70, and now 30 dollars just vanished. The machine can crash mid-write, and when it comes back the data has to be exactly as correct as it was the instant before the crash, not "mostly." And someone is going to ask a question you didn't precompute an answer for — "which orders shipped late last Tuesday" — and it has to come back in milliseconds, not by reading every row ever written.

MySQL and PostgreSQL are the two relational databases you'll run into constantly as an SRE. They solve the same three problems — concurrency, durability, fast lookup — with genuinely different internals, and the differences are exactly where the interesting incidents live. This chapter is about the machinery underneath the SQL: what a B-tree actually does, what a transaction is actually promising you, and what happens the instant two people try to touch the same row.

Key point

A relational database is a concurrency-control system with a storage engine bolted on, not the other way around. Almost every production incident you'll hit — deadlocks, connection storms, a migration that hung — is a concurrency problem wearing a SQL costume.

Mental model · analogyThe mental model: a library, not a filing cabinet

Forget "database" for a second and picture a library that's open 24 hours, with thousands of people walking in and out.

Real-world analogy

The books themselves, sitting on shelves in whatever order they were shelved, are your table's rows. Finding a book by walking every shelf works, but it's slow once the library gets big. So the library keeps a card catalog — index cards sorted by title, pointing you straight to a shelf and position. That catalog is your index: a B-tree, sorted, letting you jump to the right neighborhood in a handful of steps instead of scanning the whole building.

Now, two people want the same reference copy of a book at once. The library can hand out a "reading room" copy that says as of the moment you sat down — you keep reading your version undisturbed even if someone else checks out and replaces the real copy five minutes later. That's MVCC: readers work off a consistent snapshot instead of getting blocked by writers, or seeing a half-finished change.

But some things can't be duplicated — there's exactly one master ledger of who currently has book #4471 checked out. Only one person edits that ledger entry at a time; everyone else waits their turn. That's a row lock. And when the front desk has exactly 100 numbered visitor badges and 150 people are waiting for one, that's connection exhaustion — the building isn't full, the badges are.

ArchitectureFrom your app to a page on disk

Every query travels the same rough path: your app opens or borrows a connection, sends SQL text, the engine turns that text into a plan, the plan touches an index and then the underlying rows, and somewhere in there the engine has to decide what you're allowed to see and what you're allowed to lock.

The two engines differ from the very first hop. MySQL/InnoDB hands each connection a thread; the thread lives for the connection's lifetime and is comparatively cheap, though still bounded by max_connections (151 by default in MySQL 8). PostgreSQL forks an entire OS process per connection — heavier, with its own memory footprint, but a genuinely simpler mental model for isolation between sessions. That one architectural choice is why PgBouncer or another external pooler is close to mandatory on Postgres at any real scale, and it's the root cause behind one of the labs later in this chapter.

The other architectural fork is how rows are actually stored. InnoDB is index-organized: the primary key's B-tree leaf pages are the row data, and every secondary index stores the indexed columns plus the primary key value, not a raw pointer. Postgres stores rows in a plain heap — insertion order, mostly — and every index, including the primary key's, is a separate structure holding a pointer (a page number and slot, called a TID) back into that heap. Practically: an InnoDB primary-key lookup is one B-tree walk, full stop. A Postgres primary-key lookup is a B-tree walk followed by a heap fetch. Neither is "better" — it's a tradeoff between write amplification, clustering locality, and how updates are handled — but if you've ever wondered why the two engines behave differently under the same-looking schema, this is usually why.

Think first: your query has a WHERE clause on an indexed column, but EXPLAIN shows a full table scan anyway. Is the index broken?

Almost never. The optimizer decides an index is worth using based on estimated selectivity — if it thinks the WHERE clause matches a large fraction of the table, a scan can genuinely be cheaper than millions of index-then-heap round trips. Common real causes: stale statistics (run ANALYZE), a function or implicit type cast wrapped around the column (WHERE YEAR(created_at) = 2024 can't use a plain index on created_at), or a leading wildcard in a LIKE. The index isn't broken; the query just isn't shaped for it.

Internal workingWhat a transaction actually does, step by step

Say your app runs UPDATE accounts SET balance = balance - 100 WHERE id = 42; and commits. Here's the machinery underneath, in both engines' rough shape:

  1. Parse and plan. The engine turns SQL text into a parse tree, then the optimizer picks a plan using table statistics — here, "use the primary key index on id."
  2. Walk the index. A B-tree traversal — root, branch, leaf — lands on row 42 in a handful of page reads, usually 3-4 even on a huge table, because a B-tree's height grows logarithmically with row count.
  3. Acquire the lock. The lock manager checks whether row 42 is free. If another open transaction already holds an exclusive lock on it, this one queues, and if it waits past innodb_lock_wait_timeout or Postgres's lock_timeout, it gives up with an error instead of hanging forever.
  4. Apply MVCC visibility. Before changing anything, the engine has to know what this transaction is even allowed to see. InnoDB keeps the old row version reachable through an undo log; Postgres keeps it directly in the heap as a separate tuple with hidden xmin/xmax columns marking which transactions created and deleted it. Either way, other transactions with an earlier snapshot keep seeing the old balance until you commit.
  5. Write ahead, then touch the page. Durability is bought with a rule, not a hope: the change is written to a sequential log first — InnoDB's redo log, Postgres's WAL — before the in-memory data page is modified. If the machine dies right after, replaying the log on restart reproduces the change. The actual data page just gets marked dirty in the buffer pool; it's flushed to disk later, at a checkpoint, not immediately.
  6. Commit: fsync and release. On commit, the engine forces the log to durable storage (an fsync) and only then tells your app "done." The row lock is released, and the new balance becomes visible to transactions that start a snapshot from this point on.

Isolation levels are the knob that decides how loose step 4 is allowed to be. The SQL standard defines four: read uncommitted (you can see another transaction's uncommitted change — a "dirty read"), read committed (you never see uncommitted data, but a second read in the same transaction can see a different value if someone else committed in between), repeatable read (your snapshot is fixed for the whole transaction), and serializable (transactions behave as if run one at a time). Here's the fact that trips people up in interviews and in production: MySQL/InnoDB defaults to REPEATABLE READ; PostgreSQL defaults to READ COMMITTED. Move an app between them without checking, and its behavior under concurrent load genuinely changes.

A sharp edge: gap locks

Under InnoDB's REPEATABLE READ, a locking read doesn't just lock the row you matched — it can lock the gap before it too, to stop phantom inserts (a "next-key lock"). That means an UPDATE ... WHERE id BETWEEN 10 AND 20 can block an INSERT of a value that doesn't even exist yet in that range. Switching that session to READ COMMITTED disables gap locking for plain searches. Postgres doesn't use gap locks; its repeatable read is snapshot isolation, and true serializable behavior comes from a separate mechanism (SSI, with predicate locking) that can abort a transaction with a serialization failure instead of blocking it.

ComponentsThe pieces you'll name in every incident

  • Buffer pool / shared_buffers. The page cache for the database — RAM holding recently used table and index pages. Sized wrong, everything else in this chapter gets worse.
  • WAL / redo log + undo log. The append-only durability record (Postgres's WAL, InnoDB's redo log), plus InnoDB's undo log holding old row versions for MVCC and rollback.
  • Lock manager. Tracks who holds what lock on what row or table, queues waiters, and detects deadlocks.
  • Background writer / checkpointer. Flushes dirty pages from the buffer pool to disk on its own schedule, so a crash never has to replay an unbounded amount of log.
  • Replication stream. MySQL ships a binary log (binlog) of logical or row-based changes; Postgres streams the WAL itself. Either way, a replica is applying a change log, slightly behind.
  • Vacuum / purge. Postgres's autovacuum removes dead row versions the heap is holding onto; InnoDB's purge thread does the equivalent for the undo log. Fall behind on either and the database bloats.

Data flowFollowing one write to a replica

Take that same balance update, now with a read replica behind it. Your app's write goes to the primary, which runs the six steps above and commits. The WAL record (or binlog event) for that commit is shipped to the replica — usually within milliseconds, asynchronously. The replica replays it, applying the same change to its own copy. A read hitting the replica a moment too soon sees the old balance; this is replication lag, and it's a real, physical delay, not a bug. If your app reads its own write back from a replica right after writing to the primary, you will occasionally see stale data — which is why "read your own writes" flows usually pin to the primary or a synchronous replica for that one read.

Hands-onLabs — build, understand, break, troubleshoot

Start both engines locally. Keep both terminals open — several labs need two sessions against the same database.

bash
# MySQL 8, with a throwaway database:
docker run --rm -d --name sre-mysql -e MYSQL_ROOT_PASSWORD=sre -e MYSQL_DATABASE=shop -p 3306:3306 mysql:8.4

# PostgreSQL 16, same idea:
docker run --rm -d --name sre-pg -e POSTGRES_PASSWORD=sre -e POSTGRES_DB=shop -p 5432:5432 postgres:16

# give them a few seconds, then connect:
docker exec -it sre-mysql mysql -uroot -psre shop
docker exec -it sre-pg psql -U postgres -d shop
Lab 1Build — EXPLAIN a slow query, then fix itBuild

In the MySQL session, build a table big enough to feel a scan, and query it without an index:

sql
CREATE TABLE orders (id INT PRIMARY KEY AUTO_INCREMENT, customer_id INT, status VARCHAR(20), created_at DATETIME);
-- load ~200k rows with a stored procedure loop, or any seed script; then:
EXPLAIN SELECT * FROM orders WHERE customer_id = 4471;
Output+----+-------------+--------+------+---------------+------+---------+------+--------+-------------+ | id | select_type | table | type | possible_keys | key | key_len | ref | rows | Extra | +----+-------------+--------+------+---------------+------+---------+------+--------+-------------+ | 1 | SIMPLE | orders | ALL | NULL | NULL | NULL | NULL | 198341 | Using where |

type: ALL is the tell — a full table scan, rows: 198341 examined for one customer. Add the missing index and ask again:

sql
CREATE INDEX idx_orders_customer ON orders(customer_id);
EXPLAIN SELECT * FROM orders WHERE customer_id = 4471;
Output| 1 | SIMPLE | orders | ref | idx_orders_customer | idx_orders_customer | 5 | const | 12 | NULL |

type: ref, rows: 12. Same question, twelve rows examined instead of two hundred thousand. This is the entire job of an index in one before/after.

Lab 2Understand — watch MVCC let a reader ignore a writerUnderstand

In Postgres, open two psql sessions against the same row. Session A:

sql
CREATE TABLE accounts(id INT PRIMARY KEY, balance INT);
INSERT INTO accounts VALUES (42, 500);
BEGIN;
UPDATE accounts SET balance = 400 WHERE id = 42;  -- do NOT commit yet

Session B, while A's transaction is still open:

sql
SELECT balance FROM accounts WHERE id = 42;
Output balance --------- 500 (1 row)

Session B reads instantly and sees 500 — the pre-update value — with no wait at all. It isn't blocked by A's uncommitted exclusive lock on that row, because a plain read doesn't take a lock; it reconstructs a consistent snapshot from the row's version info. Now commit A and re-run B's SELECT: it flips to 400. Readers never block writers and writers never block readers under MVCC — only writer-versus-writer contention takes a lock.

Think first: if readers never block on MVCC, why does a table ever need "vacuuming"?

Because every update in Postgres doesn't overwrite the row — it writes a brand new tuple version and marks the old one dead, right there in the heap. Nothing physically removes the old version until VACUUM confirms no active snapshot can still need it, then reclaims the space. Skip vacuuming (or let autovacuum fall behind on a hot table) and the table bloats with dead versions the index still has to skip past on every scan — a real, common cause of a table that "used to be fast."

Lab 3Break — cause a real deadlockBreak

Two sessions, MySQL this time, each locking the same two rows in opposite order. Session A:

sql
CREATE TABLE accounts(id INT PRIMARY KEY, balance INT);
INSERT INTO accounts VALUES (1, 100), (2, 100);
BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;  -- A now holds the lock on row 1

Session B:

sql
BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id = 2;  -- B holds row 2
UPDATE accounts SET balance = balance + 10 WHERE id = 1;  -- B now waits on A's lock

Back in session A, ask for row 2:

sql
UPDATE accounts SET balance = balance + 10 WHERE id = 2;

Before you run it: A wants row 2, which B holds. B wants row 1, which A holds. Neither can finish. What does the database do about it — hang forever, or something else? Decide, then run it.

Reveal what happens
OutputERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction

InnoDB's lock manager runs a wait-for-graph check, finds the cycle, and kills the transaction that did the least work (session A, here) so the other can proceed. Postgres does the same thing with error 40P01. Neither engine will ever leave two transactions stuck forever — but the killed transaction's work is gone, and it's your application's job to catch that error and retry. An app that doesn't handle a deadlock error is an app that occasionally, silently drops a write.

Lab 4Troubleshoot — exhaust every connectionTroubleshoot

Postgres, freshly started, defaults to max_connections = 100. Lower it to something you can hit fast and restart:

bash
docker exec -it sre-pg psql -U postgres -c "ALTER SYSTEM SET max_connections = 10;"
docker restart sre-pg

Now open eleven simultaneous connections and leave them idle (a quick Python loop with psycopg2.connect(...) and no close(), or eleven manual psql tabs). The eleventh gets:

Outputpsql: error: connection to server failed: FATAL: sorry, too many clients already

The database isn't slow, isn't down, and every existing connection still works fine. It is simply out of badges at the front desk. Before reading on: how would you confirm this is the cause on a real, unfamiliar production database, and what would you check to find out who is holding the connections?

Reveal an approach
sql
SELECT count(*), state, application_name FROM pg_stat_activity GROUP BY state, application_name;

If most connections sit in idle state from one application_name, that's a client-side leak or a pool that's too large for what the server allows — the classic version of this is a Kubernetes Deployment that scaled from 10 pods to 50, each opening its own 20-connection pool, quietly asking a database configured for 100 connections for 1,000. The database didn't get slower; math ran out. The fix is almost never "raise max_connections" — each Postgres connection is a full OS process with real memory overhead, and cranking the limit just moves the failure to an out-of-memory one. The fix is a connection pooler like PgBouncer in front of the database, and a hard cap on pool size per pod tied to replica count.

Lab 5Production challenge — a migration that won't moveSenior challenge

Simulate the classic "the migration is just hanging" incident. Session A opens a transaction and never finishes it — a common real cause is a web request that opened a transaction and then made a slow HTTP call before committing:

sql
-- Session A (Postgres):
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;  -- and just... sit here

Session B tries to run a routine deploy-time migration:

sql
-- Session B:
ALTER TABLE accounts ADD COLUMN status TEXT NOT NULL DEFAULT 'active';

It hangs — no error, no progress, just silence. Your deploy pipeline is now stuck too. Before revealing the cause: what lock would an ALTER TABLE need, and what would already be holding it?

Reveal the cause and the fix

ALTER TABLE needs an ACCESS EXCLUSIVE lock on the table — the strongest one there is — and it has to wait behind session A's row lock from the still-open FOR UPDATE, even though A only touched one row. Check with:

sql
SELECT pid, state, wait_event_type, query FROM pg_stat_activity WHERE state != 'idle';

A long-idle-in-transaction session blocking DDL for everyone is one of the most common "why is the deploy stuck" incidents there is. The immediate fix is killing the offending session (pg_terminate_backend) and setting idle_in_transaction_session_timeout so it can't happen unattended again. The durable fix is how you write the migration in the first place: use expand/contract instead of one big blocking change. Add the new column as nullable with no default rewrite required, ship code that writes both old and new, backfill in small batched transactions, cut reads over, then drop the old column later — never one statement that needs the strongest lock in the database held against a live table.

Failure & troubleshootingHow this shows up in real incidents

Incident pattern · connection exhaustion after a scale-out

Symptom: right after a deployment scales up pod replicas, new requests start failing with connection errors, even though the database's CPU and disk look fine. First cut: check the database's current connection count against max_connections. Confirm: pg_stat_activity or SHOW PROCESSLIST, grouped by source host or app name. Cause is usually: replica count × per-pod pool size now exceeds what the database allows — nobody did that multiplication before the scale-out.

Incident pattern · lock contention from one slow transaction

Symptom: a specific set of queries suddenly time out or queue, while the database otherwise looks idle. First cut: SHOW ENGINE INNODB STATUS (MySQL) or pg_locks joined to pg_stat_activity (Postgres) to find the blocking session. Cause is usually: a transaction opened, then left idle mid-request — a slow downstream API call, a bug that forgot to commit, a debugger breakpoint hit inside a transaction in staging that got copy-pasted into a prod code path.

Incident pattern · the migration that took the site down

Symptom: a routine deploy runs a schema change, and suddenly every write to that table stalls. First cut: is the migration holding an exclusive table lock while ordinary traffic keeps arriving and queuing behind it. Cause is usually: an ALTER TABLE that needs a full table rewrite (changing a column type, adding a NOT NULL without a fast path) run directly against a large, busy table during business hours, with no lock timeout set to fail fast instead of queuing every other writer behind it.

Production · security · performanceWhat matters in production

Security. Application database users should hold exactly the privileges their code needs — a reporting job doesn't need DELETE, and almost nothing needs a superuser or root account. Credentials belong in a secrets manager the app reads at startup, not in a ConfigMap or a baked-in image layer. Network access should be restricted to the subnets and security groups that actually run your application, not "anywhere in the VPC."

Performance. Buffer pool or shared_buffers sizing is the single highest-leverage setting either engine has — roughly 60-75% of available RAM on a dedicated database host is a reasonable starting point, tuned from there against your actual cache-hit ratio. Read replicas move read load off the primary but introduce lag you have to design around. The N+1 query pattern — one query to list rows, then one more query per row in application code — turns a single request into hundreds of round trips and is still the most common self-inflicted latency problem in any codebase with an ORM.

Common mistakes. Foreign key columns with no index on them, which turns every parent-row delete into a full scan of the child table. Migrations run with no statement or lock timeout, so a small mistake becomes an hours-long stall instead of a fast, safe failure. Treating a read replica as instantly consistent with the primary. And sizing connection pools per-pod without ever multiplying by replica count — the single most common way teams find max_connections the hard way.

System-design connectionWhere this reaches into architecture

Replication topology is a design decision, not an afterthought: asynchronous replication risks losing the last few committed transactions on failover, semi-synchronous trades a little write latency for a durability guarantee that at least one replica has the data before you acknowledge the client. Either way, promoting a replica to primary during a failover is the moment split-brain becomes possible — two nodes both believing they're the writable primary — which is why failover automation needs a fencing mechanism, not just a health check and a DNS flip. We build on this in Chapter 82 and Chapter 90.

At scale, the database is almost never the first thing that sees a request — a cache absorbs the read traffic that would otherwise hit it (Chapter 85), and a connection pooler sits between a fleet of stateless pods and a database that can only hold a few hundred real connections open. Sharding and read replicas both buy you more capacity, but neither one is free: sharding gives up cross-shard transactions and joins, replicas give up strict read-after-write consistency. Knowing exactly which guarantee you're trading away is the actual system-design skill here — not knowing that replicas or shards exist.

InterviewInterview questions & answers

30-secWhat's the difference between a B-tree index and the table itself?

The table holds the actual row data; an index is a separate, sorted structure that lets you find a row without scanning every one. In InnoDB the primary key index and the row data are the same structure — it's index-organized. In Postgres they're separate: an index stores a pointer into a heap where the row actually lives. Either way, a query that can use an index turns an O(n) scan into an O(log n) tree walk.

2-minWalk me through what happens when a transaction commits.

The engine parses and plans the statement, walks whatever index applies, and acquires the locks it needs on the rows it touches — waiting if someone else holds a conflicting lock. Before touching the actual data page, it writes the change to a sequential log — the WAL in Postgres, the redo log in InnoDB — because that log write is what durability is actually built on. The in-memory page gets modified and marked dirty; it's flushed to disk later, not synchronously. On commit, the engine forces that log to durable storage and only then tells the client it succeeded, then releases the row locks so the new value becomes visible to future snapshots. If the machine crashes after the log fsync but before the data page is flushed, recovery replays the log and reproduces the change — that's the whole guarantee.

DeepExplain MVCC, and why it isn't free.

MVCC lets a reader work off a consistent snapshot of the data instead of taking a lock that would block writers, by keeping more than one version of a row around. Postgres keeps old versions directly in the heap with hidden xmin/xmax transaction-id columns marking validity; InnoDB keeps them in an undo log and reconstructs an older view on demand. The cost shows up later: those old versions don't disappear on their own. Postgres needs VACUUM to reclaim dead tuples once no snapshot can still need them, and a long-running transaction anywhere in the system can pin an old snapshot in place, which stops vacuum from doing its job and lets the table bloat. InnoDB's purge thread has the same job for the undo log. MVCC buys you non-blocking reads at the cost of a cleanup process you now have to keep healthy.

ScenarioEvery new request is suddenly failing to reach the database, right after a deploy. How do you investigate?

First I check whether the database itself is healthy — CPU, disk, replication lag — because if those look normal, this isn't a database performance problem, it's a connection or lock problem. I'd look at current connection count against the configured max, broken down by source: if one deployment's pods are holding most of them, that's a pool-sizing math error following a scale-out, and the fix is capping pool size per replica or fronting the database with a pooler, not raising the connection limit. If connections are fine but queries are queuing, I'd check for a blocking transaction — something holding a lock and sitting idle, often from a slow call made while inside an open transaction. Either way I'm finding who's holding the resource before I touch any configuration.

Follow-upHow would you change a large, frequently-written table's schema with zero downtime?

I wouldn't run one statement that needs a long-held exclusive lock against live traffic. I'd use expand/contract: add the new column or table in an additive, non-blocking way — nullable, or with a default that doesn't force a full rewrite — deploy application code that writes to both the old and new shape, backfill existing rows in small batched transactions so no single transaction holds a lock for long, cut reads over to the new shape once backfill is verified, and only then drop the old column in a later, separate deploy. I'd also set a lock timeout on the migration itself, so if it can't get its lock quickly it fails fast and retries later instead of queuing every other writer behind it.

RetainQuick revision

A database is a concurrency-control system first. Indexes are sorted structures that turn a scan into a handful of page reads — but only for queries shaped to use them. Isolation levels decide how much of another transaction's in-flight work you can see; MySQL defaults to REPEATABLE READ, Postgres to READ COMMITTED, and that difference has teeth. MVCC lets readers ignore writers by keeping old row versions around, which is why vacuum/purge exist and why they matter. Locks serialize writers, and a deadlock is the database refusing to let two transactions wait on each other forever — your app still has to retry. Connections are a finite resource independent of query performance, and Postgres's one-process-per-connection model makes that ceiling lower than people expect. And a schema change on a busy table is a concurrency problem before it's a syntax problem.

The 10 things to remember

  1. A relational database's real job is safe concurrency; storage is the easy part.
  2. A B-tree index turns an O(n) scan into an O(log n) walk — but only if the query can use it.
  3. InnoDB is index-organized (the PK index holds the row); Postgres is heap-plus-separate-indexes.
  4. MySQL's default isolation is REPEATABLE READ; Postgres's is READ COMMITTED. That's a real behavioral difference, not trivia.
  5. MVCC means readers never block writers and writers never block readers — only writer-vs-writer contention locks.
  6. Old row versions don't clean themselves up. Vacuum/purge falling behind is a real, common cause of "this table got slow."
  7. A deadlock is detected and resolved by killing one transaction — your application must catch that error and retry.
  8. Connections are bounded independently of database load. Postgres's per-connection process makes that ceiling especially real.
  9. Writes are durable because the log is written before the data page — not because the data page is written fast.
  10. Schema changes on live tables want expand/contract, not one big blocking statement holding the strongest lock available.
